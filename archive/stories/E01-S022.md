## AC5 字型渲染驗證
本機沒有連上 claude-in-chrome 擴充套件(嘗試 `tabs_context_mcp` 回報「Browser extension is not connected」),改用 Playwright(repo 既有依賴)以丟棄式 port(3910,避開 `tests/e2e` 寫死的 3000/3001,不需搶 flock)驅動真實 Chromium,對真實 `/login` 頁面做兩種驗證:

1. **截圖直接肉眼確認**(`/tmp/.../login-real.png`,未進 repo,純驗證用):「登入」「帳號」「密碼」「使用 SSO 登入」等中文清晰可讀、粗細正常,不是幾乎看不見的極細字——直接反證了 spec 特別警告的「依賴 Noto Sans TC 預設 wght 100」陷阱。
2. **程式化驗證字型家族**:透過 Playwright 開一個 CDP session,呼叫 `CSS.getPlatformFontsForNode`(與 DevTools「Rendered Fonts」面板背後同一組資料)——
   - `<h1>`(「登入」)、`<label>`(「帳號」)、`<button type="submit">`(「登入」)全部回報 `familyName: "Noto Sans TC..."`。
   - 額外注入一個純英文文字節點(`"SSO Login"`,`font-family: var(--font-roboto), var(--font-noto-sans-tc)`),回報 `familyName: "Roboto"`(`postScriptName: "Roboto-Regular"`)——證實 Latin 字元確實由 Roboto(堆疊中第一個)提供字形,中文才落到 Noto Sans TC。

**過程中的一個誠實記錄**:`CSS.getPlatformFontsForNode` 對 variable font 的「粗細」回報不可靠——不論實際 `font-weight` 設 100/400/900,回報的 `postScriptName` 永遠是該字型的預設具名實例(`NotoSansTC-Thin`)。一開始誤以為這代表字重插值失效,進一步用純像素截圖比對 100/400/900 三種粗細(見下方),確認視覺上確實正確漸層(細/正常/粗),證明 `next/font/local` 的可變軸插值運作正常,只是這個 CDP 欄位對 variable font 的具名實例回報是已知限制,不是渲染的實際狀態。

```

測試 900   (visibly bold strokes)
```
