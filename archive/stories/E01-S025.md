## 全量 E2E 分析(14 個失敗)

**先確認一個關鍵事實:本 story 自己實際修改的五個頁面,各自的既有
E2E spec 全部通過,零失敗**——`knowledge-list.spec.ts`、
`knowledge-documents.spec.ts`(含 E05-S029 徽章 role 測試)、
`maintenance-home.spec.ts`、`profile.spec.ts`、`login.spec.ts` 皆全綠。
本 story 自己新增的 `pages-m3-axe.spec.ts` 7/7 全綠。

14 個失敗中:

1. **`api-sandbox.spec.ts:143`**(1 個)——斷言 `/v1/health` 回傳
   `status: "ok"`,實際回傳 `"degraded"`。**這是一個真實、結構性的
   既有 bug,不是環境雜訊**:根因是 `apps/api/src/config.ts` 的
   `asrProvider` 預設 `whisper-server`,dev/test 環境沒有可連線的
   sidecar,導致 `checkAsr` 恆為 `down` → `overallStatus` 恆為
   `degraded`,自 E04-S047 引入 ASR health check 起即如此,與本 story
   的改動(純前端 className/CSS)無任何關聯。已回報 `ai-km-e4`,總指揮
   已立案 **E04-S056**(見 `docs/stories/PROGRESS.md` E04 章節)追蹤修復,
   **本 story 的 AC1 計數明確排除此項**,不算入下方「14 個失敗」的
   本 story 相關判定。
2. **導覽逾時(共 12 個)**:`conversation-detail.spec.ts` ×1、
   `conversation-history-pagination.spec.ts` ×3、`model-selector.spec.ts`
   ×3(皆因同一個「下一頁」按鈕點擊後等不到 URL 變化)、`erp-e2e.spec.ts`
   ×2、`erp-home.spec.ts` ×1、`knowledge-create.spec.ts` ×1、
   `admin-analytics-e2e.spec.ts` ×1。**錯誤訊息的關鍵特徵**:全部是
   `page.waitForURL: Test timeout of 30000ms exceeded`,不是
   `locator.click` 本身逾時或找不到元素——代表點擊動作已經成功執行,
   只是之後的頁面載入/導覽在 30 秒內沒完成。這是效能/延遲特徵,不是
   「點擊目標被我的 CSS 擋住」的特徵(後者會在 `.click()` 那一步本身
   逾時)。失敗分布橫跨對話分頁、ERP、knowledge 建立、admin 回饋佇列
   等彼此無關的頁面與元件,與 `api-sandbox.spec.ts` 觀察到的 API
   degraded 狀態及跑測全程 load average 12~17(非安靜環境)一致,指向
   系統性延遲而非個別頁面的內容缺陷。
   - 其中 `erp-e2e.spec.ts`/`erp-home.spec.ts` 的 3 個失敗發生在本
     story 有改動的 ERP 頁面附近,已特別檢查:失敗的點擊目標
     (`list.getByRole("link", {...}).click()`)是 `erp-query-list.tsx`
     裡我加了 `.m3-list-item-link`(`display: block; color: inherit;
     text-decoration: none;`)的同一個 `<Link>`——這個 class 沒有
     `pointer-events`、沒有定位/z-index 相關規則,純粹是排版與顏色,
     結構上不會擋住點擊;而且錯誤訊息本身已經證明點擊有成功執行
     (逾時發生在 `waitForURL`,不是 `.click()`)。判斷為上述系統性延遲
     的一部分,不是本 story 造成。
3. **`smoke.spec.ts:50`**(1 個,**已解決,非本 story 待證項目**)——當時
   `getByText('AI KM', {exact:true})` 同時命中 header 與 Next.js
   route-announcer 的既知碰撞。本次全量跑測時我的 branch 落後 main
   9 個 commit,尚未包含 W1 於 `4f001c1`(E01-S033)加入的修正
   (`getByRole("banner").getByText(...)`)。**rebase 到最新 main 之後
   重新確認**:`tests/e2e/specs/smoke.spec.ts:73` 已是修正後的版本,
   此失敗屬於落後分支的過期程式碼,不是本 story 的問題,也不需要另外
   重跑驗證——修正本身已在 main 上,不是本 story 的變更範圍。

## Rebase 後安靜環境目標重跑

`ai-km-e4` 指示:「推理可以換來一次針對性重跑的資格,但不能取代重跑本身」
——上面的 14 個失敗分析只是推理,rebase 到最新 main 之後,針對這些失敗
實際重跑才是證據。程序:

1. `git fetch . main && git rebase main`——歷經兩輪(main 在 rebase 過程中
   又推進了一次,含 `ea3ecd7` 這個 E04-S056 立案 commit),最終
   `git merge-base --is-ancestor main HEAD` 成立,`docs/stories/PROGRESS.md`
   的合計欄位在兩輪衝突中都用 `awk` 獨立驗證過。
2. Rebase 後重跑 `pnpm --filter @ai-km/web typecheck`(0)、
   `pnpm --filter @ai-km/web lint`(0)、`pnpm --filter @ai-km/web test`
   (**1756/1756**,全綠,因其間 main 上其他 lane 新增了測試,基準數字比
   `1734` 高但零失敗)。
3. 用 `tests/e2e/test-results/.last-run.json` 精確取回原本 14 個失敗的
   test ID(而非重猜檔名/行號),在 `.e2e.lock` 持鎖狀態下(寫入
   `.e2e.owner`、跑前清過期 port、`uptime` 記錄前後負載)以
   `pnpm exec playwright test --last-failed` 重跑。該指令實際挑到 13 個
   (第 14 個 `admin-analytics-e2e.spec.ts` 因故未被 `--last-failed` 選中,
   另外用 `pnpm exec playwright test admin-analytics-e2e.spec.ts
   --project=admin` 補跑,同樣持鎖)。

**結果:14 個全部通過,0 個失敗**(跑前 load average 11.73~13.84,跑後
16.21~16.73——雖非絕對安靜,但無其他 lane 佔用 `.e2e.lock`/`.e2e.owner`,
且與造成原始 14 敗的「非安靜環境」相比,無並發 E2E 或 port 佔用):

**12 個導覽逾時目標全數轉綠,是本 story AC1 的最終證據**——不是靠推理
本身收尾,而是靠這次實際重跑的通過結果收尾。`smoke.spec.ts` 通過進一步
實證確認 rebase 已帶進 `4f001c1` 的修正。

**根因歸屬更新(誠實記錄,非本 story 逕自認定)**:rebase 過程中 main 上
出現 `c0f22e8`(E04-S056 修正版規格),W3 用實跑推翻了我原本「系統性延遲
(machine load)」的單一推理框架,補上一個直接牽涉本 story 這次重跑方法
論的新假說:本地預設 `reuseExistingServer: !CI`(local 為 `true`)——若
啟動 playwright 前 `:3000`/`:3001` 已有殘留 dev server 被「收編」而非
重新啟動,會**靜默遺失** `playwright.config.ts` webServer 專屬注入的
`CONVERSATIONS_PAGE_SIZE=2`/`FEATURE_MOCK_TRIGGERS=true` 等環境變數,
頁面大小退回預設 20 會讓分頁「下一頁」按鈕失去導覽目標,呈現與純負載延遲
**無法區分**的 `waitForURL` 逾時特徵。E04-S056 AC5.2 是專門釐清此假說的
實驗,尚未有結論,不由本 story 越權認定。
**但這不影響本 story 自己這次重跑的證據力**:上方「orphan cleanup」步驟
已先確認 `:3000`/`:3001`/`:4100` 皆無殘留監聽(`ss -ltnp` 顯示
`none listening`)才啟動 playwright,代表這次重跑的 web/admin server
必然是全新啟動、環境變數必然正確注入——不論「系統性延遲」或「收編殘留
server 遺失環境變數」何者才是**原始** 311/325 跑測 12 個失敗的真正成因,
都不影響這次重跑本身的有效性。因此上方「證實系統性延遲推理」的措辭已
修正為單純陳述觀察結果,根因歸屬留給 E04-S056 定論。

**`api-sandbox.spec.ts` 附帶說明**:此次重跑通過(先前全量跑測時是
`degraded`)。W3 已用實跑確認、非本 story 自行推測:`playwright.config.ts`
的 apps/api webServer 專屬實例自 E03-S038 起就設定
`AI_KM_ASR_PROVIDER: "fake"` 且 `reuseExistingServer: false`(永遠全新
啟動),所以這條 spec 在乾淨 tree 上本就應該 4/4 綠——先前全量跑測觀察到
`degraded` 的真正來源是**手動啟動、長駐的共用 `:4000` 執行個體**
(`api-sandbox.spec.ts:147` 把一個路由測試耦合到 ASR 這個非必要子系統的
運作狀態),不是本次重跑的隔離測試實例。E04-S056 的立案與後續處置仍由
總指揮/W3 認定,本 story 僅誠實記錄與本 story 相關的觀察。
