## Contract / Migration 差異

**全部為新增,無既有 consumer,不構成 breaking change。** Migration:None。

3 個 operation,與規格逐條對照,沒有多也沒有少:

```
POST /auth/login     → 200 AuthSession + Set-Cookie；400/401/403/415/503/500
POST /auth/logout    → 204 + 清除 cookie(未登入亦 204,冪等)
GET  /auth/session   → 200 AuthSession；401 UNAUTHENTICATED
```

`AuthSession` 逐欄等於 `packages/auth-client/src/index.ts` 既有的
`AuthSession`(`userId`、`roles`、`expiresAt` 必填;`name`／`email`／
`department`／`group` 選填),**沒有新增任何欄位**。`AuthErrorCode` 的四個值
與既有 union 完全相同。

`auth.yaml` 同時是 **`sessionCookie` security scheme 的正式定義處**;其他
spec 描述的是同一個 cookie,新 spec 應 `$ref` 這份而非各自重寫。

### redocly 的 2 個 warning(未抑制,兩者皆為刻意設計)

1. **`operation-4xx-response`(`POST /auth/logout` 沒有 4xx)** ——
   **這正是規格要求的行為**:登出是冪等的,沒有 session、session 過期、
   已登出,一律 204。使用者按登出就是想變成已登出狀態;為「你本來就已經
   登出了」回一個錯誤,client 沒有任何有意義的處理方式,而且會洩漏 token
   是否仍有效。為了讓 linter 閉嘴而捏造一個 4xx 會讓契約變差。
2. **`no-unused-components`(`AuthErrorCode`)** —— 它存在是為了讓 codegen
   產出這個型別(相容性 gate 正是拿它跟 client 的 union 做等值比對),而
   每個錯誤回應各自 pin 一個單值 enum 以求精確,所以沒有直接 `$ref` 它。

兩者都**沒有**用 `--generate-ignore-file` 蓋掉。AC1 要求「lint 0 error」,已達成。

### E2E:1 個既有 flaky(非本 story 造成),並帶回一項具體發現

`admin-analytics-e2e.spec.ts:44`(E13-S017 admin 首頁導覽)在全量並行下失敗,

  `contracts/` 不出現在任何 `tsconfig.json`／`.eslintrc*`／`vitest.config.*`／
  `playwright.config.*`／`next.config.*`／`turbo.json`——完全在所有 build／
  test graph 之外,不可能影響 apps/admin。
- 失敗原因是 **timeout,不是斷言不符**:
  `Test timeout of 30000ms exceeded` / `locator.click`,而且 log 顯示
  `locator resolved to <a href="/latency">延遲儀表板</a>` ——**元素找到了**,
  是點擊/導覽沒能在時限內完成。

**新發現(值得回饋給 E01-S027)**:這支測試**即使單獨執行也要 24.2 秒**,

### Security / Authorization

| AC | 驗證 |
|---|---|
| token 只存於 HttpOnly cookie,回應 body 永不含 token | `info.description` 專段明文;`AuthSession` 為 `additionalProperties: false` 且無任何 token 欄位;`TokenFree<>` 編譯期斷言涵蓋 `AuthSession` 與 `LoginRequest`,mutation 測試 A 證明注入 `token` 會讓 gate 變紅 |
| server 只存 token 雜湊 | `info.description` 與 `securitySchemes.sessionCookie.description` 兩處明文(SHA-256),並說明其目的:資料庫外洩不會直接產生可用的 session |

補充(規格未明列,但屬 Security Boundary):
- `LoginRequest` 是 `additionalProperties: false` 且有 `OwnerFree<>` 斷言——
  沒有任何欄位能讓 caller 指定 `userId`／`roles`／`ownerKey`。身分是 server
  **從憑證推導**出來的,不是 caller 宣稱的。
- 401 `INVALID_CREDENTIALS` 對「帳號不存在」與「密碼錯誤」刻意**不可區分**,
  避免這個端點變成帳號列舉工具;403 `ACCOUNT_DISABLED` 是刻意的例外並已在
  response description 說明理由(密碼是對的,使用者需要知道該找管理員,而
  不是一直重試)。
- `password` 標 `format: password` 並明文「永不記錄、永不回傳、不進任何
  error body 或 audit payload」。
- `AuthSession.roles` 的 description 明文「僅供 UI 顯示,client 不得據以
  推導出比 server 更寬鬆的權限;空陣列代表沒有角色,不是全部角色」。

## Assumptions / 計畫外事項

1. **`POST /auth/logout` 宣告 `security: [sessionCookie, {}]`** —— 規格要求
   「未登入亦 204」,所以它必須能在沒有 session 的情況下被呼叫。空的 security
   requirement `{}` 是 OpenAPI 表達「亦可不帶認證」的標準寫法。
2. **`POST /auth/login` 宣告 `security: []`** —— 登入本來就不需要既有 session。
3. **`conversations.yaml` 的 `sessionCookie` 仍是內嵌定義,未改為 `$ref auth.yaml`**
   —— `conversations.yaml` 不在本 story 的允許修改清單內,**故意不碰**。
   兩處定義的欄位完全相同(`apiKey` / `cookie` / `ai_km_session`),不影響
   任何 consumer。已在 `contracts/openapi/README.md` 註明 `auth.yaml` 是正式
   定義處、新 spec 應 `$ref` 它。若要統一既有 spec,應另立 story。
4. **`ACCOUNT_DISABLED` 用 403 而非 401** —— 規格明訂 403。
5. **`info.license`** —— 沿用 E04-S038 的 `UNLICENSED` /
   `LicenseRef-Proprietary`,消除 redocly 的 `info-license` warning。
