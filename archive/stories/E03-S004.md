# E03-S004 — Knowledge selector multi-select

- 狀態:DONE
- Branch:story/E03-S004-knowledge-selector-multi-select
- 日期:2026-08-14

## Scope 說明

Epic 檔案把 E03-S003 標題訂為「Knowledge selector **single-select**」、
E03-S004 訂為「Knowledge selector **multi-select**」——兩者是同一個
能力的兩個階段,不是兩個獨立功能。本 story 把 S003 的 `<select>`
單選介面**升級**成核取方塊群組多選介面,取代而非疊加。

## 設計決策

1. **`ConversationSummary.knowledgeScope: KnowledgeScope | null` 改名為
   `knowledgeScopes: KnowledgeScope[]`**(欄位改名 + 型別改變,不是
   新增第二個欄位):`[]`(空陣列)延續 S003 的 fail-closed 預設決策
   （不猜測 auto-select 該選什麼)。
2. **`setConversationKnowledgeScope(id, scope)` 改名為
   `setConversationKnowledgeScopes(id, scopes)`**:每次呼叫**取代
   整組選擇**,不是新增/移除單一項目——這對應核取方塊群組「回報目前
   完整勾選狀態」的自然行為,呼叫端(`KnowledgeSelector`)不需要自己
   對照前一次的選擇做差異運算。
3. **UI 從 `<select>` 改成 `<fieldset><legend>` + 核取方塊群組**:
   `<fieldset>`/`<legend>` 是多選核取方塊群組的原生無障礙標記方式
   （隱含 `role="group"`,`<legend>` 提供 accessible name),延續
   `ModeSwitch`(S002)用 `role="group"` 的既有模式,只是這次用原生
   語意元素而非手動 ARIA 屬性。
4. **`pending` 時整個 `<fieldset disabled>`**:除了防止使用者在請求
   進行中誤觸發第二次切換,`disabled` 的原生行為本身就會讓核取方塊
   在停用期間完全不觸發 `onChange`,從瀏覽器層級就避免了競態,不需要
   額外的防重複呼叫邏輯。

## Assumptions / 計畫外事項

1. **`setConversationKnowledgeScopes` 採「整組取代」而非
   「新增/移除單一項目」的 API 設計**:這是刻意的設計選擇,對應
   核取方塊群組的自然回報方式,也讓函式簽章保持簡單(一個陣列參數,
   不需要 `add`/`remove` 兩個獨立函式)。
2. **未對「選擇的知識範圍數量上限」做任何限制**:SOURCE_BASELINE
   沒有提到多選是否有上限,依「不得自行猜測」不發明限制。
