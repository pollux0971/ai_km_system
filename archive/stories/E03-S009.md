## Scope 說明

SOURCE_BASELINE.md 對 S09 只給標題「E03-S09 Send Message」,epic 檔案
展開版命名為「Send-message optimistic state」。開工前先用背景 agent
徹底核對:S09 自己的章節與 S06 逐字比對後確認是完全相同的樣板(唯一
差異是標題字串本身),沒有任何 S09 專屬的具體規格;E04-S002「定義
Message entity」(Team B 未來真正的 contract)本身也還是同樣的空白
樣板,沒有任何欄位清單。全文搜尋「樂觀」/optimistic 除了每個 story
都有的通用 Frontend/UX Boundary 那一句「Optimistic UI 若涉及
mutation，失敗時必須 rollback 或明確 reconcile。」之外,沒有任何
訊息傳送狀態機的具體定義。也確認 S10(Streaming Response)/S11
（Generation Status)/S12(Stop Generation)三個故事在整份 epic 檔案裡
沒有任何一處以 story ID 明確依賴或引用 S09——三者都是獨立、平行、
目前仍是空白樣板的未來故事,S09 完全沒有義務(也沒有根據)去模擬
任何 AI/assistant 回覆。

因此本 story 的範圍精確界定為:**使用者自己的訊息**能夠送出、樂觀
呈現、成功後與失敗後正確收斂(reconcile)——不模擬、不假裝有任何
AI 回覆(那是 S10-S12 明確、獨立、尚未建置的責任)。這與 S01 面對
Team B 尚不存在的 Conversation entity 時的處理方式完全一致:建立一個
**Team A 自己擁有的本地 mock**,誠實記錄它不是真正的 E04-S002 contract。

## 設計決策

1. **`lib/messages.ts` 獨立成新檔案,不塞進 `conversations.ts`**——
   Message 是以 `conversationId` 為外鍵的獨立集合,不是
   `ConversationSummary` 的欄位,延續 `ai-models.ts`/`knowledge-scopes.ts`
   各自獨立成檔的既有慣例。
2. **持久化的 `Message` 沒有 `status` 欄位**——凡是寫進 store 的訊息
   定義上就是已送出;`"pending"`/`"failed"` 是純 UI 層、暫時性的狀態,
   只存在於 `message-thread.tsx` 的本地 `DisplayMessage` 判別聯集裡,
   從未寫進 `lib/messages.ts` 的 store。這讓「持久化資料」與「UI 暫態」
   的界線非常乾淨。
3. **`role` 只有 `"user"` 一種值,不預先加入 `"assistant"`**——S10-S12
   是尚未建置、負責任何 assistant 回覆概念的獨立故事;現在就加入
   一個永遠不會被產生的 `"assistant"` 角色型別,屬於「為假設性的
   未來需求設計」,違反不要為投機性未來預先設計的原則。
4. **`sendMessage` 對不存在的 conversationId 回傳 `NOT_FOUND`**——
   重用 `updateConversation`(透過 `getConversation`)既有的檢查邏輯,
   不是發明一個新的「模擬隨機失敗」機制。這同時給了「樂觀
   pending→失敗→重試」流程一個真實、決定性(非隨機)、可測試的失敗
   路徑,而不是憑空編造一個業務規則。
5. **失敗時訊息保持可見並標記為「傳送失敗」+ 重新傳送按鈕,而非直接
   消失**——這正是 Frontend/UX Boundary「失敗時必須 rollback 或明確
   reconcile」的落地:選擇 reconcile(讓 UI 準確反映「這則訊息沒有
   送出去」)而非靜默 rollback(消失可能讓使用者以為輸入內容整個
   不見了)。
6. **`MessageComposer` 新增*可選*的 `onSubmit` prop,而非把送出邏輯
   整個搬出去**——維持 S06-S08 既有的
   `conversation_message_compose_submit` telemetry(UI 層級:使用者
   是否操作了 compose 控制項)不變,`onSubmit` 只是額外掛勾,讓父層
   （`message-thread.tsx`)疊加真正的網域層級送出邏輯(樂觀新增、呼叫
   `sendMessage`、根據結果收斂)。可選、向後相容——S06-S08 既有全部
   17 個測試中沒有傳入 `onSubmit` 的測試維持原樣通過。
7. **`MessageThread` 同時擁有訊息清單與 render `MessageComposer`**——
   兩者緊密耦合(送出動作直接影響清單顯示),比起 `ConversationDetail`
   分別協調兩個獨立 sibling、再手動橋接狀態,由 `MessageThread` 統一
   擁有更簡單、更符合一般聊天介面「訊息串 = 歷史清單 + 底部輸入框」
   的組合方式。
8. **`sendMessage` 成功後呼叫新增的 `touchConversationLastMessage`**,
   更新對話的 `lastMessageAt`/`lastMessagePreview`——這兩個欄位從
   E03-S001 建立時就已宣告(`lastMessagePreview: "尚無訊息。"`),但
   一直沒有辦法更新,因為在本故事之前根本不可能送出任何訊息。這是
   完成該欄位既有宣告意圖,不是新增範圍外功能。附件無文字時的預覽
   使用「已傳送 N 個附件」的佔位文字,呼應 S01「尚無訊息。」的既有
   佔位文字風格。
9. **E2E 沒有涵蓋「傳送失敗 + 重新傳送」流程**——真正觸發失敗需要
   讓對話 id 在使用者已經在瀏覽的頁面上失效,這在真實使用者操作
   流程中沒有自然的觸發方式(除非直接操控 sessionStorage 繞過 UI,
   那樣測的是實作細節而非使用者流程)。這個失敗+重試路徑已經由
   `message-thread.test.tsx` 的 mock 層級測試完整、確定性地涵蓋
   （不像隨機失敗那樣需要 E2E 層級才能驗證時機),延續 E03-S001 對
   「not-found」情境改用 component test 而非勉強湊 E2E 的既有判斷。

## Assumptions / 計畫外事項

1. **S09 不模擬任何 AI/assistant 回覆**:SOURCE_BASELINE 與 epic 檔案
   都沒有任何文字把 S09 與 S10(Streaming Response)/S11(Generation
   Status)/S12(Stop Generation)綁定為依賴關係,三者是獨立、平行、
   尚未建置的故事。依「不發明」原則,S09 只完成使用者自己的訊息
   送出與樂觀狀態收斂。
2. **失敗的決定性觸發條件是「對話 id 不存在」(NOT_FOUND)**,而非
   模擬隨機網路錯誤——重用既有的 `updateConversation` id 檢查邏輯,
   給樂觀 UI 的失敗路徑一個真實、可重現、非隨機的觸發方式,而非
   發明一個新的模擬失敗機制。
3. **E2E 沒有涵蓋失敗+重新傳送流程**,理由見設計決策 9——已由
   `message-thread.test.tsx` 的 mock 層級測試確定性地完整涵蓋。
4. **`Message` 沒有 `status` 欄位**:pending/failed 純粹是 UI 暫態,
   從未持久化——這是刻意的資料模型簡化,不是遺漏。
