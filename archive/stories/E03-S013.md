## Scope 說明

SOURCE_BASELINE.md 對 S13 只給標題「E03-S13 Citation Badge」加上兩行範例
（「例如：」「[1]」，第 1160-1164 行），epic 檔展開版是與其他多數 story
相同的完全空白樣板（Metadata/Scope/Preconditions/8 條 Functional AC/
Security/Data/UX Acceptance 皆為通用範本文字），唯一值得特別記錄的是
Security Acceptance 其中一行：「Unauthorized source 不得進入 LLM
context、citation、export 或 logs」——這行明確指出真正的引用系統應該
綁定授權，但目前沒有真正的 RAG/citation 後端（E04 尚不存在），mock 的
引用標記完全沒有連結任何真實文件或權限，因此這條 AC 現階段是 N/A（與
本 session 其他 mock-only story 的既有論證一致）。

本 story 明確只做「引用標記渲染」本身。SOURCE_BASELINE 緊接在 S13 之後
的下一筆條目就是「E03-S14 Citation Preview」（第 1168 行），代表顯示
File/Page/Snippet 細節的互動是刻意留給 S14 的獨立 story，本 story 不
提前做。

## 設計決策

1. **直接從純文字 `content` 用 regex（`/(\[\d+\])/g`）解析 `[N]` 標記**，
   不建立結構化的 Citation 資料型別——沒有真正的來源 metadata（檔名/
   頁碼/片段）可以連結，發明這些等同捏造商業內容（與 E03-S005 從不
   發明真實模型廠商名稱的紀律一致）。真正接上 E04 後，引用應該是帶
   character offset 的結構化資料，不是從純文字解析。
2. **渲染成非互動的 `<sup>`,不是按鈕/連結**——S14「Citation Preview」
   才是負責點擊/hover 後顯示來源細節的 story;現在就加上點擊行為會
   提前侵入 S14 的範圍,且點下去也無處可去。
3. **只在 `withCitations={role === "assistant"}` 時解析**——使用者自己
   輸入的文字如果剛好包含 `[1]` 這樣的字串,不應該被誤判成引用,這會
   是使用者完全無法預期的行為。
4. **不使用 `role="doc-noteref"`**（DPUB-ARIA 規範中教科書式正確的引用
   參照 role）。直接驗證發現 Chromium 的 accessibility tree 對這個
   explicit role 沒有反應,無聲地回退成 `<sup>` 元素自己的 implicit
   role「superscript」（用 Playwright 對同一個頁面的 aria snapshot
   直接確認：`role="doc-noteref"` 的 `<sup>` 仍被回報為
   `superscript: "[1]"`,不是 `doc-noteref`）。既然這個專案的 E2E
   工具鏈就是靠 role-based query（`getByRole`）驗證行為,選一個真實
   瀏覽器不會正確曝光的 role 會讓這個功能變得無法用既有慣例測試。
   `<sup>` 本身在 ARIA-in-HTML 對照表中已經有正確、標準的 implicit
   role,jsdom（unit test）與 Chromium（E2E）對它的判定一致,因此改用
   這個原生語意,不去對抗工具鏈硬要一個測不到的 role。`aria-label`
   仍然保留「引用來源 N」的完整描述,不受 role 選擇影響。
5. **`lib/streaming.ts` 的 `MOCK_REPLY` 補上結尾的 `[1]`**——讓這個
   功能在真正跑一次對話時就看得到,不是只靠 unit test 的合成字串才
   驗證得到（延續 S05 模型選項、S10 串流回覆等既有 mock 都要「真的
   看得見」的慣例）。附加在結尾而非嵌入某個特定語句中間,避免暗示
   上面某句話「真的」被驗證過某份文件。

**兩輪除錯,皆已定位根因,誠實記錄**:

1. **DPUB role 在真實瀏覽器不被支援**:初版用
   `role="doc-noteref"`,unit test（jsdom + testing-library)可以正常
   用 `getByRole("doc-noteref")` 找到,但 E2E（Chromium）跑起來直接
   `element(s) not found`。用 Playwright 的 aria snapshot 直接檢查
   當下頁面,確認 Chromium 把這個 `<sup>` 回報成
   `superscript: "[1]"`,不是 `doc-noteref`——瀏覽器對不認得的 DPUB
   role 靜默回退成 host element 自己的 implicit role,不是報錯。修正
   為改用 `role="superscript"` 查詢（`<sup>` 自己正確、標準的
   implicit role),同步修正 `message-content.tsx`（移除
   explicit role,保留 `aria-label`)、`message-content.test.tsx`、
   `message-thread.test.tsx`、`citation-badge.spec.ts` 四處的查詢方式。
2. **`pnpm test` 全量跑時,一個與本 story 無關的既有測試
   （`stop-generation.spec.ts` 的第二個 E2E)出現 flaky 紅燈**:錯誤是
   Playwright 的「element was detached from the DOM」,發生在按下
   「停止生成」按鈕時。由於這個測試完全沒被本 story 碰過,先用
   `git stash push -u` 把本 story 所有變更（含未追蹤的新檔案）暫存,
   讓工作目錄回到 S013 開始前的狀態,再用 `pnpm turbo run test
   --force`（跳過 cache,強制真的重新執行,複製造成 flaky 的相同高
   併發負載)重跑——**同一個測試、同一個錯誤,在完全沒有本 story
   任何變更的程式碼上一樣重現**,證實這是 S012 遺留、與 S013 無關的
   既有時序脆弱點,只是恰好在本 story 全量驗證時被撞見。`git stash
   pop` 恢復本 story 變更後,判斷這屬於「實作中發現必要的計畫外
   變更」（因為 `pnpm test` 正是 CI 實際執行的指令,放著不修會讓本
   story 自己的 CI 也有機率被這個無關的 flaky 燈拖累)。根因:該測試
   用固定的 `page.waitForTimeout(100)` 猜測「已經有內容開始累積」,
   但 `message-thread.tsx` 在顯示「AI 回覆中…」的同一次 state
   update 裡就已經寫入第一個字元,額外的固定等待毫無必要,只是讓測試
   多曝露在後續串流仍持續觸發 re-render 的時間窗裡;在高併發（`pnpm
   test` 同時跑全部套件的 vitest 加上一個真實 Chromium session)下,
   偶爾會讓串流在按鈕點擊重試迴圈還沒完成前就自然跑完並收斂為
   `sent`（移除按鈕),導致按鈕在點擊過程中被移除。修正:移除固定的
   100ms 等待,「AI 回覆中…」一出現就立刻點擊。修正後
   `pnpm turbo run test --force` 連續兩次乾淨重跑（不吃 cache)皆
   66/66 全過,確認修正有效且非僥倖一次過。

## Assumptions / 計畫外事項

1. **不使用 `role="doc-noteref"`,改用 `<sup>` 的 implicit role
   `superscript`**:SOURCE_BASELINE 未定義任何 ARIA role 需求;這是
   為了讓功能在本專案實際使用的 E2E 工具鏈（Playwright + Chromium)
   下可測試、可驗證所做的技術選擇,不影響視覺呈現或
   `aria-label` 提供的語意描述。
2. **修改了 `tests/e2e/specs/stop-generation.spec.ts`（S012 的檔案,非
   本 story 原計畫範圍)**:在 `pnpm test` 全量驗證期間發現既有的
   flaky 測試,用 `git stash` 完整診斷確認與本 story 無關（見上方除錯
   過程)。判斷為「實作中發現必要的計畫外變更」而非放著不管,因為
   `pnpm test` 正是 CI 實際執行的指令,不修的話本 story 自己的 CI
   run 也有機率被這個無關的 flaky 燈拖累,徒然消耗未來排查的成本。
   修改範圍僅限移除一行 `page.waitForTimeout(100)` 並調整周邊註解,
   未改動任何實作程式碼,未放寬任何 assertion。
3. **`MOCK_REPLY` 補上的 `[1]` 附加在結尾,不嵌入句子中間**:避免暗示
   前面某句特定文字「真的」被驗證過某份來源文件,維持與既有 mock
   （S05 模型選項、S10 串流回覆)相同的誠實標示紀律。
