# E03-S019 — Regenerate answer action

## Scope 說明

SOURCE_BASELINE.md 對 S19 只給標題「E03-S19 Regenerate Answer」
（第 1194 行),完全沒有內文。epic 檔展開版把標題具體化為
「**Regenerate answer action**」——確認這是給「已經成功送出的 AI
回覆」提供「要求重新生成一次」的動作,與 S12「Stop Generation」
（中止進行中的生成)和 S09/S10 既有的失敗重試（`handleRetry`/
`handleRetryStream`,只適用於失敗狀態)是三個不同的能力,互不重疊。

明確排除:
- 只能對**整個對話的最後一則**、且是已 settle（`kind: "sent"`)的
  AI 回覆使用——SOURCE_BASELINE 完全沒有定義「重新產生對話中間某一則
  回覆」該怎麼處理後面所有訊息（要保留?要一併丟棄?要分支?),真實
  聊天產品（延續 S12/S17 已用過的同一個「真實聊天產品慣例」論證)
  幾乎都只在「最新的回覆」上提供這個動作,不主動發明未定義的分支
  語意。
- 不新增獨立的 telemetry 事件——重新產生完全重用既有的 `runStream`
  （與 S12 的 stop、S10 的 retry 共用同一套 `conversation_message_
  stream_*` 事件),不是一個新的動作類型,沿用既有的既有先例
  （`handleRetryStream` 本身也沒有專屬 telemetry)。

## 設計決策

1. **`handleRegenerate` 重用整個既有的 `runStream`（phases +
   streaming + persist + stop 全部原封不動)**,不是平行實作一套新的
   生成邏輯——這代表「重新產生」自動繼承 S11 的階段顯示、S12 的
   停止能力、既有的 telemetry,不需要額外程式碼。
2. **重新產生前,先呼叫新的 `deleteMessage(messageId)` 刪除舊的已
   持久化訊息**——這是本 story 真正核心的資料完整性問題:如果不刪除
   舊訊息,`runStream` 最終會透過既有的 `receiveAssistantReply`
   新增一則全新的訊息,舊的卻還留在 store 裡,使用者畫面上看起來是
   「取代」了,但 reload 之後兩則都會出現——這正是 Functional AC 5
   「重複請求/重試不得造成未定義重複 side effect」明確禁止的情況。
   `deleteMessage` 是新增到 `lib/messages.ts` 的函式,刻意不做
   `getConversation` 存在性檢查（不同於 `sendMessage`/
   `receiveAssistantReply`)——唯一呼叫者傳入的 id 一定是畫面上正在
   渲染的訊息,對話存在性不需要重新驗證。
3. **按鈕文案用「重新產生」,不是既有 S10 失敗重試的「重新產生
   回覆」**——避免同一段文字在兩種不同觸發條件（失敗重試 vs.
   成功後主動要求重來)下出現,造成語意混淆或測試選擇器歧義。
4. **停止一個「重新產生」中的生成,若在任何內容抵達前就停止,不會
   恢復被刪除的舊回覆**——這是刻意接受的、composed 出來的結果:
   `deleteMessage` 在點擊「重新產生」的當下就已經執行,S12 既有的
   「空內容停止 → 整個項目移除」邏輯完全不知道有「舊回覆」這件事。
   兩個已經各自獨立合理化過的能力組合起來,產生「這一輪完全沒有
   回覆」的結果,是可以接受的——發明「如果提早停止就恢復舊回覆」的
   undo 語意,是規格完全沒有要求的新功能,不主動加上。

## 變更檔案

- `apps/web/src/lib/messages.ts`——新增 `deleteMessage(messageId)`。
- `apps/web/src/lib/messages.test.ts`——新增 3 個測試:刪除指定 id
  的訊息、不影響同一對話的其他訊息、刪除不存在的 id 不會失敗。
- `apps/web/src/app/(app)/conversations/[id]/_components/message-thread.tsx`
  ——新增 `handleRegenerate`;render 的 `.map()` 加上 `index`,只在
  `isLastEntry && kind === "sent" && role === "assistant"` 時顯示
  「重新產生」按鈕。
- `apps/web/src/app/(app)/conversations/[id]/_components/message-thread.test.tsx`
  ——新增 5 個測試:按鈕只出現在最後一則已 settle 的 AI 回覆（不在
  使用者訊息上)、更早的 AI 回覆在有更新輪次後不再顯示按鈕、點擊後
  刪除舊訊息並以新的串流取代、重新產生期間鎖住 composer（沿用 S17
  機制)、在任何內容抵達前停止會讓這一輪完全沒有回覆。
- `tests/e2e/specs/regenerate-answer.spec.ts`（新增)——2 個 E2E:
  重新產生取代最後一則回覆且 reload 後不會出現重複、按鈕只出現在
  最後一則訊息上。
- `tests/e2e/specs/stop-generation.spec.ts`——修正一個在本 story
  VERIFY 期間又復發的既有 flaky 測試（見下方除錯過程,非本 story
  邏輯造成)。

**兩輪除錯,皆已定位根因,誠實記錄**:

1. **自己的新測試又踩到兩種已知的 gate-pattern 陷阱**（「停止一個
   重新產生」測試):第一次用「yield 一個 phase 後永久 `await` 一個
   不會 resolve 的 Promise」模擬階段卡住,結果消費迴圈永遠沒有機會
   重新檢查停止旗標,測試逾時。修正為既有的「可控制 release 的
   gate」模式後,又抓到第二個問題:最終斷言原本寫
   `toHaveBeenCalledTimes(1)`（誤以為刪除+空停止代表完全沒有任何
   訊息異動),但這個假設本身不影響這個特定測試（本測試沒有這個
   斷言),不過在撰寫過程中重新核對 `receiveAssistantReply` 從未被
   呼叫的正確斷言,確認邏輯無誤後才定案。
2. **`pnpm test` 全量跑時,`stop-generation.spec.ts`（S012 既有檔案,
   E03-S013 已經修過一次的同一個測試)在本 story 的 VERIFY 期間又
   復發**:先用 `git diff main...HEAD -- tests/e2e/specs/stop-generation.spec.ts`
   確認本 story 完全沒有碰過這個檔案,再單獨隔離執行
   `stop-generation.spec.ts` 確認它自己乾淨地通過兩次——確認不是
   S019 造成的迴歸,而是同一類「高併發下的 flaky」問題,只是隨著
   session 累積的 E2E 規格越來越多、系統負載更重,連 E03-S013 當初
   修過的版本都又被觸發。深入分析錯誤日誌（重複出現的「element is
   not stable」)後判斷:每個串流字元都會重新渲染整個 `<li>`,包含
   內容持續增長的相鄰 `<span>`,在系統負載夠重時,這會讓「停止生成」
   按鈕的畫面座標在 Playwright 用來判斷「穩定」的連續影格之間持續
   微幅偏移,導致 mouse click 的 actionability 檢查永遠等不到兩個
   連續穩定的影格,一直重試,直到串流本身先完成、按鈕被移除
   （「element was detached from the DOM」)。這是比 E03-S013 當初
   移除固定 100ms 睡眠更深一層的根因。修正:在這一個已經透過
   `getByText("AI 回覆中…")` 獨立確認按鈕真的存在、可見、可用的
   點擊上,明確加上 `{ force: true }`,跳過 Playwright 對「畫面座標
   跨影格穩定」這一項因為相鄰內容持續變動而不可靠的檢查——不是放寬
   斷言（後續的 `expect` 完全沒有變動,一樣嚴格核對按鈕消失、訊息
   數量、內容長度),只是改變「怎麼點擊」這一個已經獨立確認存在的
   元素。修正後對這個特定 spec 單獨重跑確認正常,再對全量
   `pnpm turbo run test --force` 連續重跑三次（比照 S013 兩次的
   慣例再加一次,因為這次是更深層的根因修正)確認乾淨無 flaky。

## Assumptions / 計畫外事項

1. **重新產生只作用於整個對話的最後一則已 settle 的 AI 回覆**:
   SOURCE_BASELINE 未定義中間訊息的處理方式,依真實聊天產品的常見
   慣例（延續 S12/S17 的同一個論證來源)採用,而非任意假設分支/
   保留語意。
2. **新增 `deleteMessage`,刻意不做 conversation 存在性檢查**:與
   `sendMessage`/`receiveAssistantReply` 不同,因為唯一呼叫者傳入的
   id 一定是畫面上正在渲染的訊息,對話存在性在呼叫當下已經確定。
3. **在任何內容抵達前停止重新產生,不會恢復被刪除的舊回覆**:見設計
   決策 4——這是組合兩個各自獨立合理化過的能力（regenerate 的先刪除
   + S12 的空內容停止移除)所產生的、可接受的結果,不主動發明 undo
   語意。
4. **修正了 `tests/e2e/specs/stop-generation.spec.ts` 這個 S012 既有
   檔案的一個 flaky 測試**:在本 story 的全量 VERIFY 期間復發（已用
   `git diff` 與隔離執行證實與 S019 無關),判斷為「實作中發現必要的
   計畫外變更」(STORY_WORKFLOW Phase 1 允許,且不跨 domain)——放著
   不修會讓本 story 自己的 CI 也有機率被這個無關的 flaky 燈拖累。
   詳細根因與修法已記錄在程式碼註解與上方除錯過程。
