# E03-S022 — Conversation History Pagination

- 狀態:DONE
- Branch:story/E03-S022-conversation-history-pagination
- 日期:2026-08-14

## Scope 說明

SOURCE_BASELINE.md 對本 story(line 1215)只有標題「E03-S22 Conversation
History」,無任何內文。Epic 檔的展開標題「Conversation history
pagination」提供了關鍵、具體的方向:這是替 E03-S001 建立的對話列表路由
(`/conversations`)加上分頁,不是替單一對話內的訊息加分頁(那是完全
不同的概念,這個 epic 從未在任何地方提到過)。

## 設計決策

1. **`pageSize` 固定為 2,不是一個「看起來合理」的生產數字(如 10/20)**
   ——這個 mock 的種子資料(`SAMPLE_CONVERSATIONS`)固定只有 3 筆。選
   2 是刻意的:讓這個固定的 3 筆種子資料集本身就跨兩頁,不需要任何
   測試或 E2E 流程額外透過 UI 先建立更多對話才能示範分頁存在。這是
   針對「固定小型 mock 資料集」的誠實、可測試性驅動的選擇,不是在
   宣稱這是真實生產環境會用的頁面大小——同一類誠實揭露,呼應
   S021 固定 fallback 句子、S010 固定 MOCK_REPLY 文字的既有精神。

2. **頁碼式(page number)分頁,非 cursor-based**——這是一個純記憶體
   陣列,沒有真實資料庫並行寫入需要 cursor 解決的問題,offset-by-page
   是最簡單、正確的選擇,不是偷工減料。

3. **`listConversations(page)` 的回傳型別從 `ConversationSummary[]`
   改為 `ConversationListPage`(`{items, page, pageSize, totalCount,
   totalPages}`)**——這是必要的破壞性變更,不是可用 optional 參數
   繞過的擴充:分頁 UI 需要知道目前頁碼、總頁數才能正確渲染
   上一頁/下一頁按鈕的啟用狀態,單純回傳「這一頁的陣列」不足以支援
   分頁。影響範圍已確認僅 2 個消費端(`conversation-list.tsx` 與
   其測試)+ 來源自己的測試,範圍可控。

4. **`page` 參數寬容處理(clamp 到最小 1、超出範圍回傳空陣列),不
   fail-closed 拒絕**——這是一個純讀取的顯示參數,不是安全或
   mutation 相關輸入,Functional AC 2 的 fail-closed 要求是針對「可能
   造成 partial side effect 或錯誤結果」的輸入,分頁頁碼兩者都不是。

5. **UI 用上一頁/下一頁按鈕,不是編號頁碼連結**——只有兩頁時,編號
   頁碼清單相對於兩個按鈕是不必要的複雜度(MVP 可簡化視覺)。只有
   `totalPages > 1` 時才渲染分頁控制項,避免在只有一頁資料時顯示
   毫無作用的按鈕。

6. **換頁沿用既有的 `loading` 狀態,沒有另外設計「換頁中」狀態**——
   這個 codebase 目前沒有任何「原地換頁同時保留舊內容」的既有先例,
   MVP 可簡化視覺,沿用已驗證過的 loading/error/empty/loaded 狀態機
   比發明新狀態更一致。

## 除錯過程

1. **根因判斷**:第 1 次全量 force 重跑時,4 個測試變紅(3 個在
   `model-selector.spec.ts`、1 個在 `conversation-detail.spec.ts`),
   錯誤皆為「找不到 `Q3 銷售報表彙整` 連結」逾時。這些測試都不是
   本 story 撰寫或曾經修改過的檔案。用 `grep` 找出全部使用該連結
   文字的測試位置,確認每一處都是「剛降落 `/conversations` 就立刻
   點擊該連結」的模式。對照 `SAMPLE_CONVERSATIONS` 陣列順序
   (`產品保固政策詢問`, `設備 E-204 錯誤代碼排查`, `Q3 銷售報表彙整`)
   與新的 `CONVERSATIONS_PAGE_SIZE=2`:第 3 筆(`Q3 銷售報表彙整`)
   落在 page 2,不再出現在剛降落頁面時的初始渲染——這是本 story
   自己的分頁變更造成的、預期內但先前未察覺的必然結果,不是巧合
   或無關的既有 flaky。
2. **修復**:在兩個檔案共 4 個發生此模式的位置,於點擊
   `Q3 銷售報表彙整` 連結前插入點擊「下一頁」按鈕,並附上解釋分頁
   影響的註解。用 `grep -rln "Q3 銷售報表彙整" specs/*.ts` 確認只有
   這兩個檔案(加上本 story 自己新增的 E2E spec)引用這筆種子對話,
   範圍完整、沒有遺漏其他受影響的測試;另用同樣方式確認
   `設備 E-204 錯誤代碼排查`(第 2 筆,仍在 page 1)不受影響,不需
   修改。
3. **重新驗證**:隔離跑修復後的兩個檔案(6/6 通過)後,依 Phase 4
   規則從 typecheck 重新開始整個 gate 序列(而非只重跑先前失敗的
   E2E),確認修復未意外破壞任何其他 gate,再連續兩輪全量 force
   重跑確認徹底轉綠、無殘留不穩定。

## Assumptions / 計畫外事項

1. **`getRecentConversations`（Home Dashboard widget,E01-S008）未
   受影響、未修改**——它直接呼叫 `readStore().slice(0,3)`，不經過
   `listConversations`，本來就與此 story 的分頁邏輯完全獨立，確認
   後未做任何變動。
2. **分頁狀態不透過 URL query 參數（如 `?page=2`）**——目前頁碼只存在
   於元件的 local state，離開再返回一律重置回 page 1。SOURCE_BASELINE
   與 epic 檔皆未提及「可分享/可加書籤的分頁 URL」這個需求，發明
   這個能力會是本 story 沒人要求的範圍擴張。
3. **`model-selector.spec.ts`/`conversation-detail.spec.ts` 的修正
   範圍界定**——已用 `grep -rln "Q3 銷售報表彙整" specs/*.ts` 與
   `grep -rln "設備 E-204" specs/*.ts` 雙向確認：前者只有這兩個既有
   檔案（加上本 story 自己新增的 spec）受影響，後者（仍在 page 1
   的第 2 筆種子對話）不受影響、未做任何修改。
4. **`CONVERSATIONS_PAGE_SIZE` 未做成可設定/環境變數**——SOURCE_BASELINE
   未要求可設定的頁面大小，MVP 簡化為單一固定常數，需要時未來的
   story 可以再擴充。

## Rollback

Revert 本 story 的 merge commit 即可，是自包含的變更集（`conversations.ts`
的分頁邏輯、`conversation-list.tsx` 的分頁 UI、對應測試、新增 E2E
spec 檔）。`model-selector.spec.ts`/`conversation-detail.spec.ts` 的
修正必須與 `conversations.ts`/`conversation-list.tsx` 的分頁變更一起
revert（不能只 revert 其中一邊），否則這兩個檔案會回到「假設
`listConversations` 一次回傳全部」的舊行為，與尚未 revert 的分頁
UI 不相容,造成 gate 紅。
