## Scope 說明

E03 的最後一個 story。與 S31/S32 相同的情況:**SOURCE_BASELINE.md
完全沒有這個 story 的章節**(E03 條目在 S30 結束,line 1255 直接跳到
E04),epic 檔(line 6732)的展開一樣是每個晚期 story 都有的標題唯一
樣板文字。

與 S31/S32 不同的地方:這個 story 的標題本身**直接就是要交付的東西**
——「conversation E2E with mocked backend」不是一個新的使用者可見
行為,而是「針對這整個對話功能、用 mock 後端寫端對端測試」這件事
本身。SOURCE_BASELINE.md §11 團隊分工也把「E2E」列為 Team A 的
直接負責項目之一。這不需要走 `/advisor`——不是規格不明,而是規格
指向的動作(寫測試)已經非常明確,唯一需要判斷的是「寫什麼測試」。

**判斷依據:稽核現有 30+ 個 E2E spec 後發現一個真實、具體的覆蓋
缺口**——E03 到目前為止的每一個 story(S09 到 S32)都只新增「單一
功能、單一輪對話」的窄範圍測試,從來沒有一個測試把多個功能串在
**同一個、會成長的 session** 裡驗證彼此不會互相干擾。這不是臆測,
是逐一檢查既有 spec 後的具體發現:

1. `regenerate-answer.spec.ts` 的「only offered on the last message」
   測試,全程只有**一則**assistant 回覆存在,只驗證使用者自己的訊息
   不會有「重新產生」——從未驗證「當第二則 assistant 回覆出現後,
   第一則原本的『重新產生』按鈕會消失」這個 S19 last-entry-only 規則
   真正的動態轉換情境。
2. `copy-answer.spec.ts` 證明兩則訊息都會拿到各自的複製按鈕,但從未
   在同一個 session 裡**真的點擊兩個**,驗證 S27 修正過的
   Map-keyed 狀態(避免不同訊息互相覆蓋確認狀態的 race)在真實
   多輪對話而不只是 component test 的合成並發情境下依然成立。
3. 沒有任何測試驗證:當後面的訊息在串流中斷(S31)時,前面已經
   settled 的訊息的 citation/複製功能是否完全不受影響。
4. 沒有任何測試驗證:reload 之後,一個從未真正 settle 的
   `stream-disconnected` entry 會乾淨消失,而不是變成殘留的重複項或
   卡住的錯誤狀態,同時它前面已經 persist 的訊息與其後已經 persist
   的使用者訊息(送出後才斷線,使用者訊息本身已經送成功)都正確存活。

這些都是**組合層級**的正確性,不是任何單一 feature 的正確性——是
單元測試、component 測試、既有窄範圍 E2E 測試在結構上都不會覆蓋到
的一類 bug(A 功能只有在 B 功能已經發生過之後才會壞掉)。這正是
「conversation E2E with mocked backend」這個標題字面上該做的事。

**不需要新的前端程式碼**——這是純測試新增的 story,`Scope Out` 的
「以 mock 假裝 production path 已完成」不適用,因為這裡本來就沒有
假裝任何東西完成,只是用既有的、每個 story 都已經誠實建立好的 mock
機制(sendMessage/streamAssistantReply/receiveAssistantReply 等)
組合出一個更真實的使用情境。

## 設計決策

1. **新增一個獨立的 spec 檔,不擴充任何既有 spec 檔**——每個既有
   spec 檔案是屬於它自己那個 story 的證據(evidence),擴充別人的
   spec 檔案來塞入這個 story 的測試,會混淆「這個測試是哪個 story
   加的」這件事,也不符合「一個 story 一個 branch、範圍清楚」的
   紀律。新檔案 `tests/e2e/specs/conversation-e2e-mocked-backend.spec.ts`
   獨立存在,清楚對應這個 story。

2. **兩個測試,不是十個**——第一個(主測試)串連:送出→citation
   預覽→複製→確認「重新產生」在場;送出第二則(含附件)→確認
   「重新產生」正確從第一則消失、出現在第二則;對兩則**同時**複製,
   確認各自獨立的「已複製」;對第二則重新產生,確認修訂記錄只出現
   在第二則不出現在第一則;最後 reload 驗證以上全部存活。第二個
   測試專注在失敗/重試這條軸線與已 settle 狀態的交互:後面一輪斷線
   不影響前面已 settle 的 citation/複製,reload 後只有真正 persist
   過的項目留下。這兩個測試分別覆蓋「一切都成功」與「後段失敗」
   兩種組合情境,足以證明真正的組合正確性,不需要窮舉每一種功能
   兩兩組合(那會是沒人要求的過度測試,且大部分排列組合彼此無關,
   不會有交互作用需要證明)。

3. **citation 按鈕的 locator 必須 scope 到各自的 `<li>`**——實作時
   發現(見下方 Gate 紀錄的 FIX 說明)`message-content.tsx` 的
   citation 按鈕 accessible name 是從訊息自己的 `[N]` marker 數字
   算出來的(逐則訊息各自從 1 開始),不是全對話累加的索引——一旦
   同一個 session 有兩則以上帶引用的回覆,無 scope 的
   `page.getByRole("button", {name: "檢視引用來源 1"})` 會同時命中
   兩個按鈕造成 Playwright strict-mode 衝突。這正是本 story 想找的
   那一類「只有多則訊息同時存在才會浮現」的組合陷阱,測試本身也
   踩到了一次,已經正確用 `messageItems(page).nth(N)` 收斂 locator。

**Next.js App Router 自己內建的 route announcer**
