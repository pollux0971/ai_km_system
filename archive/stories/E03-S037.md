## 變更檔案
- `apps/web/src/lib/messages.ts` — 全面改寫:移除 `sessionStorage`/`readStore`/`writeStore`;新增 `messageCache`(`Map<messageId, Message>`,取代 spec 描述的「Map messageId→conversationId」——實際需要更完整的最後已知訊息物件,才能保留 `submitFeedbackReason`(需 `feedback==="NG"`)、`submitFeedbackComment`(需已有 `feedback`)、`submitAnswerFeedback`/`submitCitationFeedback`(需 `role==="assistant"`)、`submitCitationFeedback`(需 `citationId` 存在於 `content`)這些既有 client-side fail-closed 檢查,不需要額外的 network round-trip 才能查——這些檢查全都不需要新的 API 呼叫,`toResult` 呼叫前就地判斷,細節見下方「與 spec 技術決策的落地差異」。`sendMessage`/`receiveAssistantReply` 移除了原本呼叫 `getConversation` 的預先存在性檢查——contract 的 `POST .../messages` 本身就會對不存在的 conversationId 回 404,不需要重複查一次。`deleteMessagesForConversation` 改為 deprecated no-op(server cascade)。
- `apps/web/src/lib/conversations.ts` — 僅移除 `touchConversationLastMessage`(函式本身,連同其早已無呼叫端的殘留)。
- `apps/web/src/test/fake-api.ts` — 擴充 6 個 message 端點(`GET/POST .../messages`、`POST .../revisions`、`PUT .../feedback`、`PUT .../feedback/reason`、`PUT .../feedback/comment`、`PUT .../citations/{id}/feedback`),每個都對照 `conversations.yaml` 的實際文件行為(`createMessage` 連動更新對話的 `lastMessageAt`/`lastMessagePreview`;`createMessageRevision` 只允許 `role:assistant`;`setMessageFeedbackReason` 要求既有 `feedback==="NG"`;`setMessageFeedbackComment` 要求既有 `feedback`;`citations/{id}/feedback` 要求 `citationId` 出現在訊息內容);新增 `getFakeApiRequestCount()`(AC4 的「未發 request」斷言用)。
- `apps/web/src/test/fake-api.test.ts` — 新增 6 個 message 端點的 Contract 自驗測試。
- `apps/web/src/lib/messages.test.ts` — 見下方「舊案例→新案例對照表」。
- `docs/stories/E03-S034.md` — 附帶記錄 W7 回填的 turbo.json 乾淨基準驗證(與本 story 無關,commit 分開)。

## 與 spec 技術決策的落地差異(誠實記錄)
spec 原文寫「adapter 內以 `listMessages` 快取(Map messageId→conversationId,來自本 session 已載入的訊息)解析」。實作時發現只快取 `conversationId` 不足以保留 AC4 明確要求「保留」的三個 client-side fail-closed 檢查(`submitFeedbackReason` 的「需 NG」、`submitFeedbackComment` 的「需已有 verdict」、`submitCitationFeedback` 的「citationId 需存在」),因為這三個檢查都需要訊息的其他欄位(`feedback`、`content`),不只是 `conversationId`。因此把快取從「Map messageId→conversationId」擴大為「Map messageId→完整最後已知 Message」——`conversationId` 只是這個更大快取的其中一個用途。這個改動符合 spec 的「保留」要求(字面上更難做到,但更完整地實現了 spec 真正要保留的行為),不是自己發明新規則,已誠實記錄判斷理由。

`sendMessage`/`receiveAssistantReply` 移除了 `getConversation` 的預先存在性檢查(spec 原文沒有明講要不要保留),因為 contract 的 `createMessage` 本身就有 404 NotFound 回應,重複查一次是多餘的 round trip;`toResult`(經 `apiClient` 的 `getConversation` 曾經做的事)現在由 `POST .../messages` 自己的錯誤回應直接提供,行為(AC 的「NOT_FOUND」語意)不變,只是少了一次網路呼叫。

## AC8 / L3 補證(2026-08-29,E04-S042/S043 合併後)

依 E03-S036 已建立的模式(丟棄式 port + 丟棄式 sqlite + `AI_KM_TEST_SANDBOX=true`

(送訊息→假回覆→修訂→NG→原因→留言→引用回饋→重整讀回):

```
$ AI_KM_DB_PATH=/tmp/.../db.sqlite AI_KM_API_PORT=4722 AI_KM_API_HOST=127.0.0.1 AI_KM_TEST_SANDBOX=true node_modules/.bin/tsx src/main.ts
{"msg":"applied pending migrations","applied":[...4 個既有 migration...]}
{"msg":"Server listening at http://127.0.0.1:4722"}

# 1. 建立對話
$ curl -X POST http://127.0.0.1:4722/v1/conversations -H "x-test-user: smoke-user-1" -d '{}'
{"id":"466fc811-...","title":"新對話",...}

# 2. 送訊息(user)
$ curl -X POST .../messages -d '{"role":"user","content":"保固期多久？","attachmentNames":[]}'
{"id":"58fbf2a2-...","role":"user","content":"保固期多久？",...}

# 3. 假回覆(assistant,內容含 [1] 引用標記,供步驟 8 用)
$ curl -X POST .../messages -d '{"role":"assistant","content":"保固期從出貨日起算 12 個月 [1]。",...}'
{"id":"19f13421-...","role":"assistant","state":"ANSWERED",...}

# 4. 修訂
$ curl -X POST .../messages/19f13421-.../revisions -d '{"content":"保固期從出貨日起算 12 個月，另含 3 個月延長保固 [1]。",...}'
{"revisions":["保固期從出貨日起算 12 個月 [1]。"],...}   # 舊內容正確存進 revisions

# 5. NG feedback
$ curl -X PUT .../messages/19f13421-.../feedback -d '{"verdict":"NG"}'
{"feedback":"NG",...}

# 6. NG 原因
$ curl -X PUT .../messages/19f13421-.../feedback/reason -d '{"reason":"INCOMPLETE"}'
{"feedbackReason":"INCOMPLETE",...}

# 7. 留言
$ curl -X PUT .../messages/19f13421-.../feedback/comment -d '{"comment":"少了延長保固的部分。"}'
{"feedbackComment":"少了延長保固的部分。",...}

# 8. 引用回饋(citationId "1",對應內容裡的 [1])
$ curl -X PUT .../messages/19f13421-.../citations/1/feedback -d '{"verdict":"OK"}'
{"citationFeedback":{"1":"OK"},...}

# 9. 重整讀回(GET 完整 thread,模擬重整後重新載入)
$ curl http://127.0.0.1:4722/v1/conversations/466fc811-.../messages
[
  {"id":"58fbf2a2-...","role":"user","content":"保固期多久？",...},
  {"id":"19f13421-...","role":"assistant",
   "content":"保固期從出貨日起算 12 個月，另含 3 個月延長保固 [1]。",
   "revisions":["保固期從出貨日起算 12 個月 [1]。"],
   "feedback":"NG","feedbackReason":"INCOMPLETE",
   "feedbackComment":"少了延長保固的部分。",
   "citationFeedback":{"1":"OK"}}
]
```

## Assumptions / 計畫外事項
- `messageCache` 只在本次瀏覽器 session 內累積(頁面重整後清空)。若使用者重整頁面後直接對一個「這次 session 還沒 `listMessages` 過」的訊息呼叫 `reviseMessage`/`submit*`,會得到 NOT_FOUND——這與 spec 描述的「找不到→NOT_FOUND(與既有語意相同)」一致,但實務上代表這幾個函式的呼叫端(`message-thread.tsx`,零改動)必須先載入過訊息串才能操作,這已經是現有 UI 流程的實際使用方式(訊息一定是先顯示在畫面上才有回饋按鈕可按),不是新限制。
- `createMessageRevision`/`setMessageFeedbackReason`/`setMessageFeedbackComment`/`setCitationFeedback` 的伺服器端驗證規則(assistant-only、需要既有 verdict、citationId 存在)在 fake API 中依 contract 文件逐條實作;AC8 的 L3 smoke 已對真實 `apps/api` 逐步驗證這些欄位(修訂/NG/原因/留言/引用回饋)寫入與讀回皆與 fake API 行為一致,未發現落差。
