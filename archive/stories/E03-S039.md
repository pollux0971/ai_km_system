## SELF-REVIEW 階段發現並修正的兩個真缺陷(誠實記錄)

依 ai-km-e4 的要求,兩個缺陷分開記錄各自的診斷與修正過程,因為除了「都是
這個 story 過程中發現的」以外彼此沒有關聯,合併敘述只會讓兩者都更難覆核。

### Bug 1 — Next.js `rewrites()` 的預設 gzip 壓縮讓 SSE 永遠連上但收不到資料

**症狀**:`EventSource` 的 `onopen` 正常觸發(連線狀態變成 `open`),但無論
在另一個分頁做任何動作(建立對話、送訊息),都收不到任何 `ChangeEvent`。

**診斷(三方比對,不是用猜的)**:
1. 直接打 `apps/api`(繞過 Next.js,略過 `/api/v1/*` rewrite):連線標頭無
   `content-encoding`,建立對話後 **19ms 內**收到 `conversation.created`。
2. 透過 Next.js rewrite(`localhost:3910/api/v1/conversations/events`):
   回應帶 `content-encoding: gzip`,同一個動作**完全收不到任何 frame**。
3. ai-km-e4 提出假說:在 `next.config.ts` 的 `headers()` 對這條路徑加
   `Cache-Control: no-transform`,看 Next.js 的壓縮中介層是否放行——**實際
   測試(不是用猜的)**:加了之後仍是 `content-encoding: gzip`,仍然收不到
   任何 frame。假說不成立,已捨棄(見下方 next.config.ts 的完整取捨記錄)。

**根因**:Next.js 的預設 gzip 壓縮(`compress: true`)包住這個 server 送出
的**所有**回應,包含 `rewrites()` 轉發的回應——它沒有「這個 content-type
需要即時串流」的概念,會等到湊滿一個可壓縮區塊或串流結束才 flush,而 SSE
連線是長駐、永遠不會「結束」的,所以永遠等不到那個 flush 時機。

**修正**:`next.config.ts` 加 `compress: false`。**這是站台等級的取捨,不是
局部修正**——影響本 app 送出的**所有** HTML/JS/CSS/JSON 回應,全部失去
gzip。已在 `next.config.ts` 該行正上方寫入完整理由,包含:
1. 已嘗試過的局部替代方案(`no-transform` header)與失敗證據;
2. 明白陳述的站台級成本(不是局部修正);
3. 標為技術債,附上未來可回退的條件(Next.js 之後提供 per-route 壓縮控制,
   或把這個端點從 `rewrites()` 移到自製 Route Handler 用 `ReadableStream`
   直接串流,兩者都不受這個壓縮包裝影響)。

**權限**:`next.config.ts` 不在本 story 允許修改清單內。總指揮
(ai-km-e4)2026-08-29 於對話中明確授權:「Scope extension authorized
either way... `next.config.ts` is outside E03-S039's literal allowed
list, and I'm authorizing it — the feature does not function without it」
——本 EVIDENCE 依 §5-theta 補上這筆書面記錄,不讓授權只存在於聊天訊息裡。

**額外查核**(ai-km-e4 要求):`/api/v1/*` 底下除了這個 SSE 端點,沒有任何
其他端點使用串流回應(`grep` 過 `apps/web/src`、`apps/api/src`、
`services/` 的 `ReadableStream`/`text/event-stream`/`chunked` 使用處,
唯一命中是這個端點自己)——沒有其他端點共享這個缺陷。

### Bug 2 — `EventSource` 建在 lazy `useState` initializer 裡,洩漏一條永遠沒人訂閱的連線

**症狀**:修正 Bug 1 後,以原始 `fetch`/`curl` 等方式直接驗證 SSE 端點都
正常(參見 Bug 1 的三方比對),但真正跑 `cross-window-sync.spec.ts` 仍然
逾時——B 分頁的側欄沒有在 5 秒內出現新對話。

**診斷(不是用推理帶過,是實際加 log 逐層往下查)**:
1. 先在 `conversation-events.ts` 的 lib 層加 `window.__sseDebugLog`,記錄
   每個 `created`/`onopen`/`event` 事件——發現 A、B 兩分頁**都**正確收到了
   `conversation.created`(時間戳幾乎同步),證明 SSE 傳輸本身沒問題。
2. 但 UI 仍然沒有更新。往上一層,在 `sidebar.tsx` 的
   `useConversationEvents` handler 與 `refetchHistory` 加 log——完全沒有
   看到「event received」的 log 輸出,代表 sidebar 訂閱的 handler 根本沒被
   呼叫到。
3. 回到 lib 層,在事件送達時多印一個 `handlerCount: changeHandlers.size`
   ——**關鍵證據**:事件送達當下 `handlerCount: 0`。同時發現
   `window.__sseDebugLog` 裡有**兩筆**時間戳完全相同的 `"created"` log。

**根因**:`ConversationEventsProvider` 原本用
`useState(() => source ?? createConversationEventSource(...))` 這種
「lazy initializer」建立真正的 `EventSource`。React 18 StrictMode 在
development 模式會**刻意呼叫 lazy initializer 兩次**,藉此幫忙抓出不純
(impure)的邏輯——但這個「呼叫兩次」**不像 effect 那樣保證兩次呼叫之間有
cleanup**(effect 是 mount → cleanup → mount,lazy initializer 沒有這個
保證)。由於 `createConversationEventSource()` 內部會真的打開一條網路連線
(副作用),StrictMode 的兩次呼叫會**真的開兩條獨立的 EventSource
連線**,React 只會留其中一個當作真正的 state,另一個被丟棄卻**從未被
關閉**——那條被丟棄的連線仍然存活、仍然正確收到伺服器事件,只是**從來沒有
任何人訂閱它**。

**這不是「dev-only 的假警報」,是 concurrent React 底下本來就不安全的寫法
被 StrictMode 提前抓出來而已**(ai-km-e4 的提醒,記錄於此避免未來有人誤判
成「關掉 StrictMode 就好」):在 concurrent React 下,一次 render 本來就
可能被丟棄,initializer 裡建立的任何東西都會跟著洩漏。正確的地方永遠是
`useEffect`——它是唯一有「重跑前一定先 cleanup」保證的地方。

**修正**:把建立 `EventSource`的邏輯搬進 `useEffect`(見
`conversation-events-context.tsx` 對應段落的完整註解)。同時把原本合併在
一個 context 裡的 `subscribe`(整個元件生命週期內身分不變)與 `status`
(連線狀態變動就換一次)拆成兩個獨立 context——這**不是順手做的額外重構**,
而是搬進 `useEffect` 之後的直接後果:如果不拆開,每次 `status` 變動都會讓
`useConversationEvents` 的所有訂閱者重新訂閱一次,是可以避免的浪費。

**驗證**:修正後,`cross-window-sync.spec.ts` 在真實瀏覽器下
`--repeat-each=3` 連續 3 次全過(見下方 Gate 紀錄)。

### 既有測試的窄修正(Phase 4 第 5 點窄例外,誠實記錄)

全量 E2E(256 個)第一次跑完是 **255 passed, 1 failed**——失敗的是
`answer-state.spec.ts:64`(既有測試,本 story 未曾主動修改內容)。

**失敗原因**:該測試斷言
`page.getByText("找不到足夠企業資料支持此答案")`(無 scope)在頁面上恰好
出現一次。本 story 之前,側欄的「歷史對話」preview 只在導航時重抓(等於
「這次對話還沒送出訊息前的舊快照」),所以這段文字不可能同時出現在側欄。
本 story 讓側欄在 `conversation.updated` 時**即時**重抓(AC2/AC5 本身要求
的行為),於是這次回覆送出後,側欄的 preview 立刻更新成同一段文字,跟訊息串
裡的同一段文字同時出現在頁面上,讓原本 `getByText` 命中一個元素變成命中
兩個(Playwright strict mode 判定為錯誤)。

**判斷「是測試選擇器問題,不是本 story 實作問題」的理由**:
1. 同一個測試的**前一行**(line 74)已經用
   `page.getByRole("main").getByText(...)` 這個 scope,顯然作者當時已經
   知道側欄可能有同名文字這個既有陷阱(這個陷阱本身在這個 repo 從
   ux/enterprise-polish 那個 story 就存在,本 story 只是讓它第一次在**這個
   特定測試**裡真的觸發)——line 78 沒有比照辦理更像是原作者的疏漏,不是
   這次新引入的假設。
2. AC2/AC5 明確要求側欄即時更新;把測試改成「側欄不能即時更新」來讓舊
   selector 過,才是真正的「改實作配合測試」,方向反了。
3. 修正只動了 selector 的 scope,斷言內容(要出現的文字、後面「不該出現的
   文字」)完全沒變,前後測試驗證的行為完全一致。

**修正**:在 `page.getByText(...)` 前加 `.getByRole("main")`,與
line 74 完全同樣的寫法。修正後 `answer-state.spec.ts` 3/3、連帶重跑
`answer-revision.spec.ts`(2 個)、`conversation-e2e-mocked-backend.spec.ts`
(2 個,同樣涉及對話內容渲染,主動加驗)全部通過,再次全量重跑
256/256 全過。
