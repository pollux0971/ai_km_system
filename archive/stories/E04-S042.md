## 測試修正記錄(若有)
1 筆,屬 Phase 4 第 5 點窄例外(測試本身技術錯誤,非放寬驗證):
- `routes/messages.test.ts`「POST .../messages > 401s with no session」原本送出空 body `{}`,但 `CreateMessageRequest` schema 要求 `role`/`content` 為必填,導致 Fastify 在 preHandler(`requireSession`)執行前的 schema 驗證階段就先以 400 拒絕——這是 Fastify 生命週期本身的行為(validation 早於 preHandler),不是實作邏輯錯誤。修正:改送符合 schema 的合法 body(`{role:"user", content:"hi"}`),讓測試真正隔離出「未登入」這個情境。修正前後皆為單一斷言,判斷理由:此為測試對 Fastify 生命週期的錯誤假設,而非「401 情境」這個行為本身需要放寬。

## Assumptions / 計畫外事項

1. **`attachmentNames` 上限採契約的 10,而非 spec 文字的「>20」**:本 story spec(`docs/stories/specs/E04-S042.spec.md`)Functional AC8 寫「attachmentNames >20 個」,但 `contracts/openapi/conversations.yaml` 的 `CreateMessageRequest.attachmentNames` 明確宣告 `maxItems: 10`。依 CLAUDE.md 參考順位與 STORY_WORKFLOW「Contract 是唯一真相來源」,實作採信契約的 10,不採 spec 文字的 20;JSON Schema 直接轉寫自契約(見下一點),測試以 11 個(剛好超過契約上限)驗證 400,而非 spec 文字暗示的 21 個。

2. **仍使用「逐字轉寫 JSON Schema」而非 `app.contracts.getSchema()`,原因與 E04-S041 不同**:E04-S041 遇到的 `app.contracts` 裝飾器順序問題已由 **E04-S049** 修正(見其 EVIDENCE)。本 story 開發中途一度切換成真正的 `getSchema()` 呼叫,型別檢查與本 package 147 個測試皆綠燈,但實測發現一個**新的、獨立的**問題:`apps/api/src/server.ts` 無條件註冊 `conversationPlugin`,而 `apps/api` 自己一部分測試(`server.test.ts`、`db/migrate.test.ts`)刻意用只含 `"sample"` 這個 spec 的 fixture 契約目錄(`src/testing/fixtures`)建構 server,以便獨立測試 bootstrap 行為、不依賴會演進的 domain 契約。一旦 message routes 在註冊階段呼叫 `app.contracts.getSchema("conversations", ...)`,這些 fixture-based 測試就會因為找不到 `"conversations"` spec 而全部拋錯(`契約 "conversations" 不存在`)——實測讓 91 個 apps/api 測試中的 28 個(所有經由 fixture 建構 server 的測試)全部失敗。修正這個問題需要調整 `apps/api` 的測試 fixture 或讓 domain plugin 註冊變成有條件(比照現有 `__test__` routes 的做法),兩者皆超出本 story 允許修改清單(`services/conversation/**`)。已改回轉寫寫法,並將此發現回報總指揮,建議另立 story(比照 E04-S049 的處理方式)。**下游 story(E04-S043、E04-S044)在這個問題解決前,仍需採用相同的轉寫做法。**

3. **seed 訊息的 user 內容來源(ASSUMPTION)**:spec 只說「內容取自前端 SAMPLE_CONVERSATIONS.lastMessagePreview」,但只有 assistant 訊息有明確對應來源;user 訊息內容 spec 未定義。實作選擇沿用該對話的 `title` 作為 user 訊息內容(合理的「使用者問題」替身,非憑空發明),已記錄於 `sample-messages.ts` 檔案內註解。
