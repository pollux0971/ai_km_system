## Assumptions / 計畫外事項

1. **未使用允許清單裡的 `apps/api/src/events/**`**:spec 的允許修改清單包含這個路徑(可能預期 `ChangeEventBus` 要放在 host app 層級,由 `apps/api/src/server.ts` 建立並注入給多個 domain)。實作後發現這是不必要的:`ChangeEventBus` 只有 `services/conversation` 自己使用(目前沒有其他 domain 需要跨 domain 共用同一個 event bus),把它完全放在 `conversationPlugin` 自己的範圍內(建立、裝飾、消費都在同一個套件),不需要 `apps/api` 知道它的存在,diff 更小、耦合更少。若未來真的有其他 domain 需要訂閱同一組事件,屆時再依實際需求決定是否要升級成 host 層級的共享服務。
2. **回頭修正 `conversations.ts`/`messages.ts`(POST 部分)/`message-feedback.ts`(全部 4 個)遺漏的 `db.transaction()` 包裹**:這是本 story 開發途中發現的既有(E04-S041/E04-S043)正確性缺口——這些 route 的「寫入資料」與「寫入 change_events」原本是兩個各自 auto-commit 的獨立敘述,不是同一個交易,與 `contracts/events/conversation-change-events.md` §4「An event row is written in the SAME transaction as the change it describes」的規範不符。本 story 需要「commit 後才能安全 emit」這個交易邊界才能正確實作 AC8,因此在允許修改範圍內(`services/conversation/**`)一併修正,而非只加新程式碼、放著已知的不一致不管。修正前後行為對外部呼叫者透明(仍是同樣的 200/201/204,同樣的錯誤碼),不影響任何既有 AC;E04-S041/S042/S043 的既有測試(147+25 個相關測試)修正後全數維持綠燈(見上方 apps/api 與 service-conversation 的全量數字)。
3. **`conversationPlugin` 改用 `fastify-plugin` 的 `fp()` 包裝**:原本(E04-S041~S043)是純函式,Fastify 預設會給它自己的封裝子情境(encapsulation),`app.decorate("changeEventBus", ...)` 這個裝飾只會在該子情境內可見,外部(包含本 package 自己的測試 harness `build-test-app.ts`)拿不到。改用 `fp()` 讓裝飾器落在呼叫端(`apps/api/src/server.ts`、或本 package 測試自建的 root app)看得到的同一個實例上。這不影響 route 註冊行為(routes 本來就是直接函式呼叫,不受封裝邊界影響),已用 172(舊)+26(新)=198 個測試與 `apps/api` 98 個測試證實無回歸。
