# E05-S014 — URL import

- 狀態:APPROVED

## Scope 說明

E05 的第十四個 story。與 S001-S013 相同情況:SOURCE_BASELINE.md 對 E05
只有一份扁平標題清單,本 story 在 epic 檔中只有標題,無進一步內文。已讀
過 epic 檔本 story 自己的章節(line 2742-2951,下一節「Text
knowledge input」從 line 2952 開始),並用 `diff` 直接逐字比對本
story 章節與 S013 章節的內文(排除 H1 標題與「User / System Value」
段落唯一的 story 名稱代換),確認兩者逐字相同,是通用 MVP 樣板文字,
無本 story 專屬內容。

**與 S011-S013 的關鍵差異:第一次為文件加入「無真實大小」的合法狀態**
——S011(單檔)、S012(多檔)、S013(資料夾)都是從真實 `File` 物件
取得 `sizeBytes`,即使沒有真實上傳,至少檔案大小本身是真的。URL
匯入完全不同:沒有任何檔案被讀取,不存在任何真實位元組數可回報。
真正的 URL 擷取(E06-S18 URL Ingestion)與 HTML 擷取(E06-S19 HTML
Extraction)都屬於 E06(Team B),目前皆 `todo`。因此本 story 面臨
一個 S011-S013 都不用處理的問題:`KnowledgeBaseDocument.sizeBytes`
原本是必填欄位,若沿用會被迫捏造一個不存在的數字。

## 設計決策

1. **`KnowledgeBaseDocument.sizeBytes` 改為選填,而非為 URL 匯入捏造
   一個佔位數字(如 0)**——0 位元組是一個具體、可能誤導的宣稱(暗示
   「真的有一個空檔案」),而實際狀況是「根本沒有大小這個概念可回報」
   。這與 S006/S007「is a setting only」測試同一種「不假裝擁有不存在
   的資料」紀律,只是套用在數值型別而非布林行為上。純新增選填欄位,
   既有呼叫端(`addKnowledgeBaseDocument`,S011-S013 皆透過它)完全
   不受影響,仍然總是提供真實數字。
2. **新增獨立的 `addKnowledgeBaseDocumentFromUrl`,不是讓
   `addKnowledgeBaseDocument` 的 `name` 參數身兼二職**——URL 需要
   自己專屬的驗證(必須能被解析為合法 URL、必須是 http/https),這與
   檔案上傳的「非空白字串」驗證是不同性質的檢查(檔案的 `.name`
   本來就由作業系統選擇器保證合法);把兩種不同的驗證邏輯硬塞進
   同一個函式參數,只會讓「這個參數什麼時候驗證什麼」變得含糊。
   拒絕非 http(s)協定(例如 `javascript:`、`file:`)的理由直接來自
   本 story 自己的標題——「URL import」指的是匯入網頁內容,不是任意
   URI scheme——不是憑空發明的安全限制;本程式庫從未把文件 `name`
   渲染成可點擊的 `<a href>`,因此本來就不存在基於導覽的 XSS 風險,
   這條驗證純粹是「這個功能名稱該做的事」的字面意義。
3. **`KnowledgeDocumentUrlImport` 是獨立元件,不是
   `KnowledgeDocumentUpload` 的第三種模式**——`KnowledgeDocumentUpload`
   整個內部狀態機都是圍繞 `File[]` 打造(選取、逐一移除、批次上傳);
   URL 匯入是單一文字欄位 + 明確送出,互動形狀完全不同,與
   `MessageComposer` 的文字輸入和 `FileAttachmentPicker` 即使組合在
   同一頁面仍是兩個獨立元件同一種考量。渲染在同一個
   `/knowledge/[id]/documents` 頁面上(非獨立路由),與
   `KnowledgeDocumentUpload` 共用同一個 `refetchDocuments` callback
   (該函式本來就與上傳來源無關,只負責重新抓取清單,直接重用)。
4. **輸入框用 `type="text"`,不是看起來更「正確」的 `type="url"`**
   ——開發過程中發現的技術問題,見下方技術發現。
5. **直接顯示 `result.error.message`(具體訊息),不是像 S009
   `knowledge-model-editor.tsx` 那樣用固定通用字串**——刻意的偏離,
   理由記在元件自己的 doc comment:`addKnowledgeBaseDocumentFromUrl`
   回傳的四種訊息都是本程式庫自己撰寫、預先翻譯好的 UI 文字(不是
   原始例外或 stack trace,UX Acceptance 真正要防的是後者),且與
   S009 的 disabled-model 情境(UI 本身的 `<option disabled>`
   已經通常阻止使用者選到)不同,URL 格式錯誤是使用者輸入這個功能
   時**預期會遇到**的常態路徑,給出具體訊息(「請輸入有效的網址」)
   比通用的「匯入失敗，請稍後再試」更直接可操作。
6. **失敗時保留已輸入的網址,不清空**——與 S08 的提示詞編輯器、
   `KnowledgeDocumentUpload` 失敗保留已選檔案同一種對使用者友善的
   處理。
7. **Telemetry 不記錄網址本身**——即使 URL 本質上是公開的網址(不像
   檔名可能本身就洩漏內部資訊),仍可能夾帶敏感的查詢參數或透露
   使用者正在研究的內部主題;延續 S008(提示詞)、S011(檔名)已有
   的「不記錄自由格式使用者輸入內容」克制,保持一致而非因為「URL
   相對公開」就放寬。Functional AC 7(稽核事件)判定不適用,理由與
   S011-S013 相同(內容新增,非存取控制變更)。

## 開發過程中的技術發現(FIX 循環,2 次)

**第一次(unit test)**:第一輪執行單元測試時,3 個測試因
`await screen.findByRole("alert")` 逾時失敗——原因是 `<input
type="url">` 觸發瀏覽器(以及 jsdom)自己內建的 HTML5 constraint
validation:當輸入值(例如「not a url」)不符合瀏覽器對 `type="url"`
的原生格式判定時,表單的 `submit` 事件會被瀏覽器**直接攔截**,
`handleSubmit`(以及裡面呼叫的 `addKnowledgeBaseDocumentFromUrl`)
根本沒有機會執行,自然也不會出現任何 alert。這代表 `type="url"`
會製造出**雙重且不一致**的驗證:瀏覽器原生驗證(無法客製訊息、
不遵循本專案的中文/樣式規範,且判定規則與 `new URL()` 不完全相同)
會搶在我們自己精心設計的驗證與錯誤訊息之前介入。修法:改用
`type="text"`,讓 `addKnowledgeBaseDocumentFromUrl` 成為「什麼是
合法網址」的唯一事實來源,與本程式庫其他表單一貫「用 JS 驗證,不
依賴原生 HTML 限制」的既有原則一致(例如 `renameConversation` 的
trim 檢查)。

**第二次(E2E)**:修正第一個問題後跑 E2E,新增的測試因
`page.getByRole("alert")`(未限定範圍)同時命中我們自己的錯誤訊息
**與** Next.js 自己隱藏的 route-announcer div
(`id="__next-route-announcer__"`)而失敗——這與
`knowledge-create.spec.ts`(E05-S003)當年第一次記錄的完全是同一個
碰撞,修法沿用該既有先例:改用
`page.getByRole("main").getByRole("alert")` 限定範圍。

兩次修正皆從 VERIFY 第一個 gate 重新完整跑過
(typecheck→lint→unit→build→E2E),符合 STORY_WORKFLOW Phase 4 規則。

## Assumptions / 計畫外事項

1. **`sizeBytes` 改為選填,而非為 URL 匯入捏造數字**——見設計
   決策 #1,延續本程式庫「不假裝擁有不存在的資料」的一貫紀律。
2. **新增獨立函式而非讓 `addKnowledgeBaseDocument` 身兼二職**——
   見設計決策 #2,URL 與檔名需要不同性質的驗證。
3. **拒絕非 http(s) 協定,理由來自 story 標題字面意義,非發明的
   安全限制**——見設計決策 #2 的完整說明。
4. **輸入框用 `type="text"` 而非 `type="url"`**——見設計決策 #4
   與技術發現,避免瀏覽器原生驗證與自訂驗證衝突。
5. **顯示具體錯誤訊息,偏離 S009 用固定通用字串的既有做法**——
