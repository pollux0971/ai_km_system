## 2026-09-02 修正記錄 —— 反向驗證 #1 的陳述不實(測試技術性錯誤,非實作錯誤)

**被獨立審核拒絕的原因**:實作本身經審核者以原始 SQL 直接查 `_vec`/`_meta`
兩表驗證正確(真 `BEGIN`/`ROLLBACK`、無 dangling chunk),**不需要改動任何
production 程式碼**。被拒絕的是下方「反向驗證 #1」原始記錄裡的這句話——

> AC1、AC2 皆變紅——且 AC1 是靠「finance 重匯前後查詢結果逐筆相同」的斷言
> 變紅,不是靠「有沒有拋錯」變紅(拋錯的斷言在這個探針下本來就會失敗,但
> 重點是這條規則本身:斷言的是可見性有沒有變,不是有沒有錯誤)。

**這句話與程式碼實際行為不符。** `store.test.ts`/`sqlite-vec-store.integration
.test.ts` 的 AC1/AC2 測試寫法是:

```js
await expect(store.upsert([...])).rejects.toBeInstanceOf(DocumentScopeConflictError);
const after = await store.query(QUERY, FINANCE_SCOPE, 10);
expect(after).toEqual(before);
```

Vitest 在一個測試裡遇到第一個失敗斷言就中止該測試。guard 被停用後,
`store.upsert(...)` 不再拋錯,`.rejects.toBeInstanceOf(...)` 這一行本身就先失敗
(`promise resolved "undefined" instead of rejecting`),下面的
`expect(after).toEqual(before)` **從未執行**——也就是說,這個 story 存在的
理由(「AC1 不是『有拋錯』,是逐筆比對」)在反向驗證 #1 底下,實際變紅的
機制**正是**規格明文禁止的「有沒有拋錯」,不是宣稱的逐筆比對。上面引用的
那句話是假的。

（`sqlite-vec-store.integration.test.ts` 的 `AC5` parity 測試也有同一類缺陷,
只是形狀不同:它用 `try/catch` 手動捕捉錯誤而非 `.rejects`,但
`expect(memoryError).toBeInstanceOf(...)` 這行斷言仍然排在 `toEqual` 逐筆比對
之前——`memoryError` 在 guard 被停用後是 `undefined`,一樣會在到達逐筆比對
之前就讓測試中止。）

**判斷:這是測試本身的技術性錯誤,不是實作錯誤**——依 `STORY_WORKFLOW.md`
Phase 4 §5 的窄例外:實作已經被審核者用原始 SQL 獨立驗證為正確;錯的是斷言
的**順序**讓決定性斷言在能被機會執行之前就被一個更早、形狀不同的斷言擋住,
不是決定性斷言本身的邏輯有誤,也不是它想驗證的行為需要放寬。修法是把「有沒有
拋錯」的斷言從擋在前面移到最後,讓資料比對的斷言在任何情況下都會先執行——
**不刪除、不放寬 error-type 斷言本身,只是讓它變成可達的(reachable)**。

## Assumptions / 計畫外事項

1. **同一次 upsert 呼叫內部就帶兩個不同 scopeKey(同一 documentId)也視為衝突
   而拒絕**——spec 明確描述的情境是「先後兩次匯入用不同 scope」,沒有明講
   「同一批次內部自相矛盾」這種情況。判斷:這仍然是同一條 Deny-Wins 底線的
   延伸(不縮小拒絕範圍,只是把同一守門邏輯也套用到批次內部自相矛盾的輸入),
   不是在回答 Scope Out 裡「文件能否屬於多個 scope」那個問題——即使沒有這個
   額外檢查,現有的「與既有 chunk 比對」機制也會在下一次獨立呼叫時擋下真正的
   跨部門搬移;這個額外檢查只是讓「同一批次內部就已經自相矛盾」這種輸入更早、
   更明確地被拒絕,而不是被兩個 scopeKey 中較晚寫入的那個悄悄決定結果。有一條
   測試(`store.test.ts`「同一次 upsert 呼叫本身對同一 documentId 帶兩個不同
   scopeKey」)專門釘住這個決定,方便日後 review 時單獨評估是否要調整。
2. **sqlite-vec 的交易改用 `db.exec("BEGIN"/"COMMIT"/"ROLLBACK")` 而非
   better-sqlite3 原生的 `db.transaction()`**——因為 `SqliteDatabase` 是本檔案
   自訂的 structural type(讓沒裝 better-sqlite3 的環境也能 typecheck),幫它
   加一個 `transaction()` 方法會擴大這個介面的面積,而既有測試裡的
   `counting`/`faulty` db 替身都只實作 `prepare`/`exec`/`close` 三個方法。
   用 `exec()` 跑裸 SQL `BEGIN`/`COMMIT`/`ROLLBACK` 不需要擴大介面,且
   better-sqlite3、真實連線上的語意等價。
3. 未新增任何 migration——`_meta`/`_vec` 表結構本來就有 `chunk_id`/`document_id`
   欄位,足以支撐這次的查詢與刪除;沒有新增欄位。
4. **未回答 Scope Out 的兩個問題**(文件能否屬於多個 scope;`chunkId` 是否該帶
   scope 維度)——維持 spec 要求的「在使用者裁示之前一律拒絕」,未在本 story
   內做任何決定或鋪路性的 schema 變更。
