## Scope 說明

E07 第五個 story,是「`/maintenance/new` 共用表單」系列(S002-S005)的
最後一個欄位,也是本次 session 第一個從第一輪 gate 就全綠、完全零 FIX
循環的 E07 story。

**刻意不新增儲存欄位,直接讓 `title` 本身變成問題描述**:這個決策不是
臨時起意,而是兌現這個檔案自己從 S002 開始就寫在 doc comment 裡的承諾
——「title starts as the selected equipment's own name (the only
honest label available before S005 exists) — S005 is free to
overwrite it once a real problem description exists」。回頭檢視 S001
自己的三筆 seed 資料標題(「生產線 3 號機台異音診斷」「包裝機感測器
故障排除」「空壓機無法啟動」),會發現它們讀起來本來就已經像是簡短的
問題描述,而不是設備名稱——這代表 `title` 這個欄位從一開始的語意就是
「這個案例的簡短描述」,S002-S004 只是因為問題描述還不存在,暫時借用
設備名稱當 placeholder。S005 要做的不是新增一個平行的
`problemDescription` 欄位,而是讓 `title` 終於能被使用者自己的文字
填滿,回到它原本該有的語意。

**不驗證格式,不限制長度**:同 `serialNumber` 的既定判斷——
SOURCE_BASELINE 沒有定義任何格式或長度限制,不發明規則。

**Telemetry 完全不含問題描述本身**:同 `serialNumber`/URL/prompt 文字
的既定限制——這是使用者自己撰寫的自由文字,而且比序號更可能包含企業
內部細節(設備狀況、現場描述),排除的理由比 serialNumber 更充分。

## 獨立審核結果

以「沒有參與實作的獨立審查者」身分重新核對,不信任 EVIDENCE 的文字
敘述,逐項親自複驗:

1. **Diff 範圍**:`git diff main...HEAD --name-status` 共 7 個檔案,
   全部是修改既有檔案(無新增原始碼檔案),皆在 Team A 允許清單內。
2. **造假跡象掃描**:grep 全部修改檔案的
   `.skip`/`.only`/`passWithNoTests`/`force-exit`/`xdescribe`/`xit(`
   與 `console.*`/`TODO`/`FIXME`/`debugger`,均為 0 命中。
3. **對抗性複驗「省略時保留設備名稱 fallback」的核心主張**(本 story
   零 FIX 循環,沒有具體 bug 可還原重現,審核者改為直接對
   `title: trimmedProblemDescription || equipment.name` 這一行做
   對抗性突變測試):把 `||` 改成 `??`(兩者對一般truthy 值行為相同,
   但對「空字串」的處理不同——`??` 只在 null/undefined 時才 fallback,
   對空字串不會),重跑單元測試,**立即抓到**
   `expected '' to be '空壓機 A'` 的失敗。這證實了兩件事:(a) 「省略時
   fallback 到設備名稱」這個屬性確實被測試網住,不是文件上的空話;
   (b) 原始碼選用 `||` 而非 `??` 是刻意、正確的選擇,不是隨手寫的
   運算子,因為表單傳入的 `problemDescription` 永遠是字串(從未是
   null/undefined),`??` 在這個情境下永遠不會觸發 fallback。還原
   突變,確認
   `git diff HEAD -- apps/web/src/lib/maintenance-cases.ts | wc -l`
   = 0。
4. **Gate 全部強制單獨重跑**:`typecheck --force` 20/20、
   `lint --force` 20/20、`build --force` 12/12,皆單獨執行,皆過。
   審核者自己重新觸發的全量測試:`pnpm --filter @ai-km/web test`
