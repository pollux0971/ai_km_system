# E07-S006 — Diagnostic session shell

- Branch: `story/E07-S006-diagnostic-session-shell`
- Date: 2026-08-15
- Status: DONE

## Scope 說明

E07 第六個 story,是「`/maintenance/new` 共用表單」系列(S002-S005)結束後
的下一步:一個維修案例被建立之後,實際落腳的診斷畫面骨架
(`/maintenance/[id]/session`)。這個 story **不做**逐步診斷的實際內容
(問題卡片、決策樹節點、SOP 連結)——那些是 S007 起(對應 Team B
E08-S10「Node Transition」以後)的責任;S006 只做「殼」:讀取案例、
取得或建立一筆診斷 session、顯示其狀態,和一個返回首頁的連結。

**`DiagnosticSessionStatus` 五個值逐字取自 SOURCE_BASELINE.md 的 E08
「Session State」清單**(`OPEN`/`IN_PROGRESS`/`RESOLVED`/`ESCALATED`/
`CANCELLED`)——不是發明的,新 session 一律從 `OPEN` 開始(S006 自己的
範圍只是殼,還沒有任何真正的步驟被完成,所以不會是 `IN_PROGRESS`)。
真正的 `DecisionSession`/`DecisionEvent` 屬於 Team B 的 E08-S08/S09,
`contracts/` 底下目前兩者都不存在 contract,`diagnostic-sessions.ts`
是純前端 mock,與 E05/E07 至今每一個實體相同的「本地 mock,等對應
domain 的 contract 出現再替換」既定模式。

**Resume,不是 upsert**:`getDiagnosticSessionForCase` 與
`createDiagnosticSession` 刻意分成兩個函式,呼叫方(`MaintenanceSession`
元件)自己負責「先查、查無才建立」的順序,而不是把這個判斷藏進單一個
合併函式裡——同 `knowledge-document-list.tsx` 自己「先確認 parent 存在
再動作」的兩段式 fetch 已建立的先例,讓「resume」與「start」保持兩個
誠實、各自可測試的結果。

**`NewMaintenanceCasePage` 的重導目標改變**:成功建立案例後,從
S002-S005 沿用至今的 `router.replace("/maintenance")` 改成
`router.replace(\`/maintenance/${id}/session\`)`——因為這個 session
路由(以 case id 為 key,獨立於還沒建立的 `/maintenance/[id]` 詳情頁)
現在真的存在了,鏡射 `conversations/new` 自己「直接落腳新項目」的先例,
取代 S002 當初借用的 `knowledge/new`「重導回列表」先例(那是因為當時
`/knowledge/[id]` 也還不存在)。

### SELF-REVIEW 期間發現並修正的真實缺口(非計畫內變更)

實作完成、VERIFY 全綠之後,SELF-REVIEW 檢查「Security AC:無權限使用者
不得讀取受保護內容」這一項時,沒有照抄過去 S001-S005「同 S001,N/A」的
結論就結案,而是實際去追 `RoleGuard` 怎麼判斷一個路徑要不要限制角色—
—發現 `apps/web/src/lib/nav-items.ts` 的 `rolesRequiredFor()`
**只做完全相等比對**(`item.href === pathname`),而這個檔案自己的
doc comment 早就精準預言了這個情境:「Exact match only, deliberately
— none of E05/E07/E09's routes have nested pages yet (e.g.
/maintenance/<id>). When one of those epics adds a sub-route that
needs the same restriction as its parent, add an explicit NAV_ITEMS
entry (or extend this to prefix-match) at that time.」

這代表:`rolesRequiredFor("/maintenance/xxx/session")` 目前回傳
`undefined`(NAV_ITEMS 裡沒有這個路徑的完全相等項目),而
`RoleGuard` 把 `undefined` 當成「不限制」——也就是說,S006 新增的
`/maintenance/[id]/session` 路由,連同 S002 就已經存在、至今從未被
發現的 `/maintenance/new`,**目前任何已登入使用者(包含
general_user、sales_purchasing)都能直接存取**,完全繞過了
S001 為 `/maintenance` 本身設下的 `maintenance_engineer`/
`super_administrator` 限制。這直接違反本 story 自己的 Security
Acceptance 第 3 條「無權限使用者不得讀取、推導、顯示或記錄受保護內容」
——不是理論風險,是這個 story 自己新增的路由一上線就會有的真實缺口。

**修法**:採用該檔案自己 doc comment 提出的第二個選項——把
`rolesRequiredFor` 從完全相等比對擴充為「完全相等,或
`${item.href}/` 前綴」,讓 `/maintenance` 底下所有巢狀路徑自動繼承
父路徑的角色限制,不需要為每一個未來的巢狀路由手動加一筆 NAV_ITEMS
(這些巢狀路徑本來就不該出現在 NAV_ITEMS/側邊欄——它們不是獨立的導覽
入口)。`${item.href}/`(而非直接 `startsWith(item.href)`)刻意避免
誤配到 `/maintenance-report` 這種恰好共享字首、但其實無關的路徑。

這個修改屬於 `apps/web/src/lib/nav-items.ts`,形式上是 E01-S017 的
檔案而非 E07 的檔案。判斷不算「跨 Domain」(E01/E07 同屬 Team A,不是
Team B 邊界),也不算「順手重構」——這是這個共用守門元件自己的 doc
comment 明確指定給「未來新增巢狀路由的那個 story」做的擴充點,而且是
本 story 自己 Security AC 通過與否的必要條件,不修就等於帶著一個已知
安全缺口宣稱 DONE。同一類先例:S001 也曾經修改 E01-S017 自己的
`route-guards.spec.ts`(把「尚未建置頁面的角色限制路由」範例從
`/maintenance` 換成 `/erp`)。修正後追加的迴歸測試涵蓋
`/maintenance/new`(S002 既有的缺口,順帶補上)與
`/maintenance/[id]/session`(本 story)兩者。

**兩個非 production-code 的測試自身缺陷,誠實記錄**:
1. `maintenance-session.spec.ts` 第二個測試最初的寫法是「呼叫
   `login()`(內含 `page.goto("/login")`)之後再 `page.goto()` 到
   session URL」——但這個順序本身就有邏輯錯誤:第二次 `page.goto()`
   是另一次 hard reload,會把第一次 `login()` 剛建立的 in-memory
   session 立刻清空(hard reload 清空 session 這件事,不會因為「上一步
   才剛登入過」而有例外)。實際執行結果證實了這個推理——頁面停在
   `/login`,不是預期的 session 頁。改用
   `session-gate.spec.ts` 自己「protected route → /login(帶正確
   returnUrl)→ 登入 → 自動導回原路徑」這條已經證實可行的 round trip
   來抵達已知的 session URL,不再需要自己額外呼叫 `login()`。
2. 同一個修正順帶讓「negative-authorization E2E 測試現在真的可行」
   這件事被發現——S001 自己的 doc comment 記載「general_user 沒有
   側邊欄連結可點,直接 goto 又會被 SessionGate 導去 /login,測不到
   RoleGuard 真正的 FORBIDDEN 分支」,所以 S001 移除了對應的 E2E
   測試。但 round trip 技巧證實:goto 一個受保護的巢狀路徑 → 導去
   /login(帶正確 returnUrl)→ **用想測試的那個角色登入** → 自動導回
   原本要去的路徑,這時候是「真的以那個角色登入」抵達目標路徑,不是
   「先登入又被登出」——這正是 S001 當時缺少的技巧。因此本 story
   新增了一個真正的 general_user 負向測試(見上方「SELF-REVIEW 期間
   發現」與下方 AC 對照)。

`knowledge-ui-e2e.spec.ts` 的逾時失敗與本 story 完全無關(本 story
未觸碰任何 KB 相關檔案),初步判斷屬於 `conversations.spec.ts` 自己
doc comment 記載過的同一類「多個 worker 併發打同一個 `next dev`
instance」假影,已用單獨重跑(single worker,只跑這兩個 spec 檔案)
與後續全量重跑證實不是真的退步。

## AC 對照

**Functional**:
1. 合法且有權限輸入 → 預期成功結果:`diagnostic-sessions.test.ts`
   「creates a session at status OPEN for a real case, and it's then
   findable...」+ `maintenance-session.test.tsx`「creates a new
   session at status OPEN...」+ E2E「creating a case opens its
   diagnostic session showing the case title and 待處理」。
2. 缺少必要輸入 → fail-closed,無 side effect:
   `diagnostic-sessions.test.ts`「fails with NOT_FOUND for an unknown
   maintenanceCaseId, with no side effect on the store」——明確在
   呼叫前後都檢查 store 狀態不變。
3. 無權限使用者不得讀取/顯示受保護內容 → **本 story 才是真正驗證這條
   的第一個 E07 story**(S001-S005 因為當時的路由/mock session 限制
   只能判斷 N/A):SELF-REVIEW 抓到 `rolesRequiredFor` 的巢狀路徑缺口
   並修正,新增 `role-guard.test.tsx` 兩個單元測試 + E2E 負向測試
   (general_user 直接造訪 session URL 被拒,`getByText("待處理")`
   確認未顯示)。
4. Dependency timeout/unavailable → 可分類錯誤,不誤標成功:
   `maintenance-session.test.tsx` 三個獨立錯誤情境測試(案例載入
   失敗、session 載入失敗、session 建立失敗),皆各自呈現同一個
   「無法載入維修診斷。」錯誤狀態,不會誤顯示為成功。
5. 重複請求/重試不得造成未定義重複 side effect → 這就是本 story的
   核心能力「resume, not duplicate」:單元測試「resumes an
   already-existing session instead of creating a second one」
   (`mockedCreateDiagnosticSession` 未被呼叫)+ E2E 測試(經
   returnUrl round trip 重新造訪已存在的 session,`sessionStorage`
   內該案例的 session 筆數維持 1)。
6. 成功與失敗路徑皆有 correlation id/telemetry → `useEffect` 一開始
   產生一個 `correlationId`,整個 effect 內每一次 `logger.info`/
   `logger.error` 呼叫都帶著同一個值(載入案例、載入/建立 session、
   成功/失敗皆然)。
7. 敏感操作需 audit event → 判斷 N/A,理由同 S002-S005:開啟/恢復
   一個診斷 session 是內容操作,不是存取控制變更,不屬於這個分類。
8. MVP 可簡化但能力不可缺席 → 「尚未有診斷步驟。」是刻意的佔位文字
   (S007 起才會有真正內容),但 session 本身的建立、恢復、狀態顯示
   都是完整、可運作的能力,不是空殼。

**Security**:
- Authorization 在資料取得之前完成 → `MaintenanceSession` 元件只會在
  `RoleGuard` 判定通過之後才會被掛載(`RoleGuard` 包在 `(app)` layout
  最外層,子樹要 render 才會執行);`useEffect` 裡的三個 fetch
  (`getMaintenanceCase`/`getDiagnosticSessionForCase`/
  `createDiagnosticSession`)全部在元件掛載之後才觸發,不可能搶在
  RoleGuard 之前執行。
- Deny Wins/revoked permission 不因 stale cache 繼續有效/未授權來源
  不進 LLM context/citation/export/log → 判斷 N/A,理由同
  S001-S005:沒有新增的受保護資源類型,沒有 LLM/citation 涉入本
  story。
- 所有外部輸入均做 schema validation → 唯一的外部輸入是路由參數
  `id`,經 `getMaintenanceCase(id)` 查表,查無時回傳 `null`(不會
  crash),與這個 codebase 裡每一個 `[id]` 路由的既有處理方式一致。

**Data/Contract**:`createdAt`/`updatedAt` 使用
`new Date().toISOString()`(UTC);`id` 使用 `crypto.randomUUID()`,
不依賴任何 UI 顯示文字。無 migration(無真實資料庫)。

**UX**:loading(`LoadingIndicator`)/not-found(與一般 error 明確區分
的獨立狀態)/error(`SERVICE_UNAVAILABLE` 情境)/loaded 四態皆有明確
呈現;狀態一律以文字顯示(`SESSION_STATUS_LABELS`),不靠顏色傳達;
`ErrorMessage message="無法載入維修診斷。"` 是固定中文訊息,不暴露原始
錯誤/stack trace;返回連結是標準 `<Link>`,鍵盤可操作。
