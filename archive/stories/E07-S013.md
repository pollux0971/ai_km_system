## Scope 說明

E07 第十三個 story。SOURCE_BASELINE/epic 檔標題僅有「Photo upload」/
「Upload Photo」,無更多描述——與 S012 不同,這次規格真的沒有現成答案,
開工前先跑 `/advisor`。

**`/advisor` 決策摘要**(完整分析見對話紀錄,此處記結論):
問題是兩個獨立的設計分歧——(a) 照片上傳該綁定在 `selectDecisionOption`
(同 S009 `detail` 先例,bundled)還是獨立動作(同 S011
`restartDiagnosticSession` 先例,standalone);(b) 資料模型該存什麼。
查過 policies/SOURCE_BASELINE/epic 邊界皆無直接答案後,進入 Step 3
選項分析:

1. 檢視這個 codebase 對「檔案」的既有處理慣例——`knowledge-documents.ts`
   的 `KnowledgeBaseDocument`(`name`/`sizeBytes?`)與 `lib/messages.ts`
   的 `attachmentNames`(明確 doc comment 記載「File 物件不持久化,只存
   名稱」)兩者一致指向同一個慣例:**mock 只存 metadata,真正的 `File`
   只活在元件自己的 state 裡**。`conversations/[id]/_components/
   file-attachment-picker.tsx` 的 `FileAttachmentPicker` 也是同樣道理
   ——它持有真實 `File[]`,但那是 UI 選取階段的暫存,不是持久層。
2. 綁定方式:照片是「對某個具體回答的證據」,語意上更接近 S009 的
   `detail`(附加在一次提交上),不是 S011 的「session 層級動作」。且
   S012 本身已經示範過「新能力不必然擴及既有的每一個函式」——`detail`
   從未擴及 `skipDiagnosticStep`,這次比照同一種克制,photo 也只加在
   `selectDecisionOption`,不加進 `skipDiagnosticStep`。
3. 依 Advisor Step 4 判定:單一 story 範圍、低風險、可回退、無 contract/
   安全/跨組介面影響,**可自行採納**,不需 `AskUserQuestion`/
   `PENDING_DECISIONS.md`。

**核心設計決策**:
1. `selectDecisionOption(sessionId, optionId, detail?, photo?: File)`——
   新增第四個選填參數,只存 `photo.name`/`photo.size` 到新欄位
   `lastPhotoFileName?`/`lastPhotoSizeBytes?`,不持久化真正的檔案內容,
   同 `DiagnosticSession` 既有 metadata-only mock 慣例。
2. **明確不擴及 `skipDiagnosticStep`**——理由見上方決策 #2。
3. `goToPreviousStep`/`restartDiagnosticSession` 一併清空
   `lastPhotoFileName`/`lastPhotoSizeBytes`——這是這兩個既有函式當初就
   已經對 `lastSelectedOptionId`/`lastFreeTextDetail` 建立的「切換到不
   適用情境就清空舊欄位」慣例,新欄位比照辦理,對抗性複驗已驗證(見下方
   Gate 紀錄)。
4. `skipDiagnosticStep` 的 `updated` 物件也一併明確清空這兩個新欄位
   (雖然目前 2-step 模型下不可獨立觸發到,同檔案既有測試對
   `lastFreeTextDetail` 的「not reachable...but proves the field-clearing
   logic itself is unconditional」註解已承認同一種局限)——保持三個
   「離開這個答案」路徑(上一步/重新開始/略過)對新欄位的處理彼此一致,
   不留下只清 2/3 條路徑的不對稱漏洞。
5. UI 端手動渲染「已選擇:檔名(大小)+ 移除相片按鈕」的預覽,不依賴瀏覽器
   原生 file input 的檔名顯示——同 `FileAttachmentPicker` 既有先例(瀏覽器
   原生呈現不含大小、不同瀏覽器不一致、且不一定能被 Playwright/RTL 穩定
   查詢)。`accept="image/*"` 僅是挑選器的提示,不是強制限制,同
   `FileAttachmentPicker` 自己 doc comment 記載的「不發明 spec 未定義的
   type/size 限制」克制。
6. `formatFileSize` 在 current-step-card.tsx 內重新寫一份 module-private
   版本,不 import 既有兩份(`knowledge/[id]/documents/_components/
   format-file-size.ts` 的 E05 共用版、`file-attachment-picker.tsx` 的
   E03 module-private版)——這正是 `format-file-size.ts` 自己 doc comment
   明確記載的既有慣例(跨 vertical 各自維護一份,不建立不必要的耦合),
   這是第三份,不是新慣例。
