## Scope 說明

E07 第十四個 story。SOURCE_BASELINE/epic 檔標題僅有「AI explain-step
panel」,無更多描述,規格同 S013 一樣沒有現成答案。開工前先做既有「mock
AI 內容」先例研究(未跑正式 `/advisor` 對話式流程,但完成同等的 Step
2/3——查權威來源 + 精讀現有程式碼建立選項分析——結論足夠明確,判斷屬於
Advisor Step 4 的「可自行採納」情境,理由與過程完整記於此)。

**研究摘要**:
1. 這個 codebase 對「AI 生成內容」有兩種既有先例:`answer-state.ts` 的
   `ANSWER_STATE_FALLBACK_CONTENT`(純同步字串常數)與
   `streaming.ts` 的 `streamAssistantReply`(async generator,帶
   `delay()`、真實 disconnect 失敗模式,doc comment 明確記載是為了模擬
   「真正的 Model Gateway/RAG 平台(E04/E12,Team B)尚不存在」的延遲與
   失敗)。
2. `current-step-card.tsx`(本 story 要修改的檔案)自己對「每一個既有
   mutation」統一用 `Promise<Result<T,ApiError>>` + `pending`/`error`
   狀態,即使那些 mutation 也沒有真正的網路延遲——這是整個 lib/*.ts 的
   一致慣例,不是「AI 內容」專屬的特殊處理。
3. 結論:內容本身(某一步驟固定的 2 筆說明文字)是靜態、已知、不需要
   「即時運算」的,同 `diagnostic-steps.ts` 自己 doc comment 對
   `getCurrentDiagnosticStep` 保持同步的理由(「沒有真正的失敗模式」)一致
   ——但因為這代表「未來真實 AI 服務呼叫」的角色,且要放進一個已經統一用
   async+Result 慣例的檔案,選擇 async+`Result<string,ApiError>` 包裝
   (無 artificial delay,同其餘 lib/*.ts 大多數函式),不做 E03 那種完整
   分階段串流演出(delay/generator)——那是 MVP scope 之外的過度工程。

**核心設計決策**:
1. 新檔案 `lib/diagnostic-explanations.ts` 的
   `explainDiagnosticStep(stepIndex): Promise<Result<string, ApiError>>`
   ——不是 `diagnostic-steps.ts` 自己的欄位(那個檔案自己的 doc comment
   明確主張保持同步,加一個 async 函式進去會違反它自己已經寫定的理由),
   也不是 `diagnostic-sessions.ts` 的函式(這個能力完全不觸碰
   `DiagnosticSession`,不需要 `sessionId`,語意上不是 session mutation)。
2. **內容固定,標示「（模擬說明）」**——同 `answer-state.ts`/
   `diagnostic-steps.ts` 既有的括號標示慣例,這裡的「說明」是既有兩個字
   (「回覆」「步驟」)都不適用的新詞,同每個既有內容種類各自造詞的先例。
3. **UI 面板 gated 在 `sessionId` 存在,不是 `step.options` 存在**——
   說明「這一步為什麼要做」在任何步驟(有沒有選項都一樣)都有意義,不同於
   補充說明/附加照片/略過原因(那三者沒有選項就沒有東西可以附加)。這個
   gating 條件不只是主題一致,而是**必要**:S007 既有的
   「renders no option buttons when the step has no options」測試斷言
   `sessionId` 不存在時零按鈕,若面板按鈕不受 gating 直接渲染,會打破這個
   凍結測試的前提。
4. **獨立的 `explainPending`/`explainError` 狀態,不與既有 `pending`/
   `error` 共用**——與既有四個 mutation(select/back/restart/skip)不同,
   讀取說明不是 mutation,共用狀態會讓「純粹在讀說明」時連帶把選項/略過/
   重新開始按鈕也 disable,是真實的 UX 退步,不是這個 story 該引入的。
5. **`explanation` 短路 `handleToggleExplain`,已載入時重新展開不重打**
   ——內容是固定的靜態文字,同一步驟內沒有「重新整理」的意義,重打只是
   浪費;對抗性複驗已驗證此邏輯真實生效(見下方 Gate 紀錄)。
6. `goToPreviousStep`/`restartDiagnosticSession`/`skipDiagnosticStep`
   **完全不需要改動**——因為這個能力不寫入 `DiagnosticSession` 的任何
   欄位,清空邏輯的問題(S013 EVIDENCE 記錄的既有 `lastSkipReason` 缺口)
   與本 story 無關;`maintenance-session.tsx`/`maintenance-session.test.tsx`
   同樣零異動,同 S010/S011 的先例(能力完全自足在 current-step-card.tsx
   內,不需要從 parent 多傳一個新 prop)。

## AC 對照

**Functional**:
1. 合法輸入 → 預期成功結果:`diagnostic-explanations.test.ts`「resolves
   an honestly-labeled, simulated explanation for step 0/1」+
   `current-step-card.test.tsx`「clicking AI 說明 shows a loading
   indicator, then the explanation once resolved」+ E2E「opening AI 說明
   shows an honestly-labeled simulated explanation...」。
2. 缺少必要輸入 → fail-closed:N/A——這是純讀取能力,`stepIndex` 恆由
   `getCurrentDiagnosticStep` 保證有效,沒有「使用者可能漏填」的輸入面。
3. 無權限使用者不得讀取/顯示受保護內容:N/A 新增面——沒有新的受保護
   資源類型,`nav-items.ts`/`role-guard.tsx` 零異動,沿用既有 RoleGuard。
4. Dependency timeout/unavailable → 可分類錯誤:
   `diagnostic-explanations.test.ts`「fails with NOT_FOUND for a
   stepIndex with no defined explanation」(結構上不可達,但同
   `selectDecisionOption` 的 optionId 驗證一樣是縱深防禦)+
   `current-step-card.test.tsx`「shows an error message when loading the
   explanation fails」驗證 UI 端正確呈現該分類錯誤。
5. 重複請求/重試不得造成未定義重複 side effect:
   `current-step-card.test.tsx`「re-opening an already-loaded
   explanation does not call explainDiagnosticStep a second time」——本
   story 對這條 AC 的核心測試,已對抗性複驗確認真實有效(見上方 Gate
   紀錄)。
6. 成功與失敗路徑皆有 correlation id/telemetry:`handleToggleExplain` 新增
   `maintenance_session_explain_step_attempt/success/failure` 三個事件,
   只帶 `stepIndex`/`code`,不帶說明文字本身(已用 grep 核對零內容外洩,
   見 SELF-REVIEW checklist)。
7. 敏感操作需 audit event:判斷 N/A,理由同 S001-S013;讀取模擬說明文字
   不是敏感操作。
8. MVP 可簡化但能力不可缺席:內容是固定文字(簡化的部分),但「展開→載入
   →顯示→收合→再展開用快取」這個完整互動循環是真實、可測試的能力,
   不是視覺裝飾。

**Security**:
- Authorization 在資料取得之前完成:未變更,沿用既有 `RoleGuard` 保護。
- Deny Wins/revoked permission/未授權來源不進 LLM context/citation/
  export/log:N/A,理由同 S001-S013;telemetry 只帶 `stepIndex`(數字)
  與 `code`(固定錯誤碼),不帶任何使用者或說明內容。
- 所有外部輸入均做 schema validation:`stepIndex` 為內部保證有效的
  `number`,非使用者可任意輸入的欄位;`explainDiagnosticStep` 仍對超出
  已定義範圍的 `stepIndex` 回傳 NOT_FOUND(結構縱深防禦)。

**Data/Contract**:無 migration(無真實資料庫)。新模組不影響任何
`contracts/` schema,也不觸碰 `DiagnosticSession` 型別本身。

**UX**:載入/錯誤/已載入三態使用既有 `LoadingIndicator`(role="status")/
`ErrorMessage`(role="alert")共用元件,明確可區分;動態說明文字包成獨立
`<span>`(同 S009/S010/S012/S013 已建立的慣例);AI 說明按鈕原生
`<button>`,鍵盤可操作;不靠顏色傳達;失敗訊息取用伺服器回傳的
