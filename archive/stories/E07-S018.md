# E07-S018 — Escalation action

- Branch: `story/E07-S018-escalation-action`

## Scope 說明

E07 第十八個 story。SOURCE_BASELINE/epic 檔標題僅有「Escalation action」,
無更多描述。與 S014-S017(唯讀面板或 UI gating)不同,這是一個真正改變
session 狀態的 mutation,語意上與 `selectDecisionOption`/
`skipDiagnosticStep`/`restartDiagnosticSession` 同一量級,設計決策判斷
已足夠明確,直接進入實作。

**核心設計決策**:
1. **`escalateDiagnosticSession(sessionId, reason)`,`reason` 必填**——
   逐字比照 `skipDiagnosticStep` 的形狀(mandatory reason,
   VALIDATION_ERROR 於空白/純空白)。獨立欄位 `lastEscalationReason`,
   不重用 `lastSkipReason`——兩者語意不同(略過一個步驟 vs 放棄整個
   引導流程),同 `lastSkipReason` 自己當初不重用 `lastFreeTextDetail`
   的理由一致。
2. **不推進 `currentStepIndex`,不清空既有答案記錄**
   (`lastSelectedOptionId`/`lastFreeTextDetail`/`lastPhotoFileName`/
   `lastPhotoSizeBytes`)——升級是放棄整個引導流程,不是「回答」或
   「略過」某一步,接手升級案例的人需要完整的既有記錄,不是被清空的
   狀態。這與 `restartDiagnosticSession`(全部重置)和
   `selectDecisionOption`/`skipDiagnosticStep`(推進+記錄或清空)兩種
   既有模式都不同,是第三種、專屬於這個 story 的行為。
3. **Repeat-guard 用 allow-list(`status !== "OPEN" && status !==
   "IN_PROGRESS"`),不是只擋 `=== "ESCALATED"` 的 block-list**——
   `DiagnosticSessionStatus` 是 SOURCE_BASELINE 釘死的 5 值型別,
   allow-list 正確涵蓋型別定義的全部終態(RESOLVED、CANCELLED),不只是
   目前這個檔案自己的函式能產生的那個(ESCALATED)。RESOLVED/CANCELLED
   目前在整個 app 裡都不可達(這個檔案裡沒有任何函式會設成這兩個狀態)
   ,所以刻意不為它們寫專屬測試(見下方測試範圍說明),但guard 邏輯本身
   是為型別的完整形狀寫的,不是只為目前可達的子集合。
4. **`restartDiagnosticSession` 也清空 `lastEscalationReason`**——與它
   已經清空的其他欄位一致,「忘記發生過的事,重新開始」自然也包含
   「不再是已升級狀態」。
5. **刻意不 gate 在 E07-S017 的安全確認勾選框後面**——升級是「向外求助
   處理風險」的動作,不是「繼續走進風險」的動作;要求「先確認危險才能
   求助」在邏輯上是反過來的,這個 story 明確測試了這一點(unit + E2E
   各一個測試)。
6. **`current-step-card.tsx` 內共用既有的 `pending`/`error` 狀態**,不
   像 AI 說明/SOP 引用來源那樣獨立——升級是真正的 mutation,與
   select/back/restart/skip 結構上同屬「同一時間只有一個動作在進行」,
   同這個檔案自己的既有理由一致。
7. **UI 用 `recordedEscalationReason` 的存在本身切換顯示**(已升級 →
   隱藏表單、顯示原因;未升級 → 顯示表單),不額外傳遞
   `session.status` 這個新 prop——因為 `lastEscalationReason` 恆與
   `status: "ESCALATED"` 同時被設定,拿它當代理信號是安全且更簡單的
   選擇,同 `recordedDetail`/`recordedSkipReason`/`recordedPhotoFileName`
   已建立的「recorded 值存在與否切換 UI」慣例一致。

## Gate 紀錄

**1 次 FIX 循環(測試本身的技術性錯誤,非實作邏輯有誤,依 Phase 4 第 5
點的窄例外處理)**:第一輪 `pnpm test`(含 E2E)發現本 story 自己新增
的 2 個 E2E 測試皆失敗,錯誤訊息為 Playwright strict mode violation
(`getByText('已升級')` 命中 2 個元素)——根因是頁面頂部既有的
`診斷狀態:<span>已升級</span>`(S006 既有)與本 story 新增的
「已升級此案例,原因:...」文字,兩者在預設子字串比對下都包含
「已升級」這個子字串,彼此撞在一起。這是**測試自己選錯了 selector**
(不夠精確,不是實作邏輯問題),同 E07-S004/E07-S008 已建立的
`exact: true` 修正先例完全相同類型。因為是本 story**剛寫的、尚未通過
審核的新測試**(不是既有的凍結測試),修正安全、直接:兩處
`page.getByText("已升級")` 改為 `page.getByText("已升級", { exact:
true })`。修正後單獨重跑這 2 個測試確認通過,依協定從 VERIFY 第一個
gate 重跑。
