## Scope 說明

E07 第二十一個 story。SOURCE_BASELINE/epic 檔標題僅有「Case detail」,
無更多描述。這是 `MaintenanceCaseList`(S001)自己的既有 doc comment
與 `MaintenanceHistoryList`(S020)自己的既有 doc comment 都明確點名
「等待這個 story」的路由(`/maintenance/[id]`)——跨 epic 有直接前例:
`KnowledgeDetail`(E05-S005)完全就是為了填補 `KnowledgeList`
(E05-S001)自己留白的同一種「detail 路由等 story 補上」關係。

**核心設計決策**:

1. **唯讀頁面,不是第二個互動 stepper**——同 `KnowledgeDetail` 自己的
   既有原則(「Read-only — editing stays on its own separate route」)
   :互動流程留在既有的 `/maintenance/[id]/session`(S006),這個
   story 只加一個「查看診斷內容」連結過去,不複製 `CurrentStepCard`
   的任何互動邏輯。
2. **兩次既有讀取的組合,零新 lib 函式**——完全重用
   `getMaintenanceCase`(S001)+ `getDiagnosticSessionForCase`
   (S006),與 `maintenance-session.tsx` 自己已經在用的**同一組**
   函式對(不是新發明的組合)。
3. **任一讀取失敗 → 整頁 fail-closed,不是局部降級**——這裡刻意選擇
   `maintenance-session.tsx` 自己的既有前例,而不是
   `KnowledgeDetail` 自己的「documentCount 獨立降級成 -」模式:
   `KnowledgeDetail` 的文件計數是建立在「已經成功」的主要內容之上的
   **次要**聚合值;但這個頁面裡,診斷 session 的狀態**就是**頁面的
   主要內容之一,不是錦上添花的次要值——更直接對應的既有前例是
   `maintenance-session.tsx` 自己對這**同一組**函式的既有處理方式
   (兩者皆 fail-closed),不是另一個 domain、另一種資料組合形狀的
   `KnowledgeDetail`。對抗性複驗證實了這個選擇的必要性(見下方 Gate
   紀錄)。
4. **顯示欄位刻意設限,不硬塞 `currentStepIndex`/`lastSelectedOptionId`
   **——`DiagnosticSession` 自己的資料模型是「扁平、不分支、只留
   最後一次答案」(`diagnostic-steps.ts` 自己的既有 doc comment),
   一旦 `currentStepIndex` 已經前進,已經沒有辦法誠實重建「在哪一步
   選了哪個選項」——顯示這兩者風險是呈現誤導性的偽歷史,而不是誠實
   摘要,所以刻意不顯示。顯示的其餘 5 個既有欄位(`lastFreeTextDetail`
   /`lastSkipReason`/`lastPhotoFileName`+`lastPhotoSizeBytes`/
   `lastCompletionSummary`/`lastEscalationReason`)皆為自足的、不需要
   額外上下文就能誠實呈現的自由文字,沿用 `current-step-card.tsx`
   自己既有的「您的補充說明:」/「已略過此步驟,原因:」/「已附加照片:」
   標籤慣例(簡化為「補充說明:」/「略過原因:」/「附加照片:」,拿掉
   在互動情境下才有意義的「您的」/「已...此步驟」敘事包裝),以及
   本 session 剛在 S020 建立的「摘要:」/「原因:」簡短標籤慣例。
5. **NOT_FOUND 用通用文案,不自訂訊息**——原本草稿曾經想自訂
   「找不到這個維修案例。」,但比對 `maintenance-session.tsx` 自己與
   `knowledge-detail.tsx` 自己的既有 NOT_FOUND 處理,兩者都只用
   `<ErrorMessage code="NOT_FOUND" />`(通用「找不到您要的內容。」),
   沒有任何一個既有 `[id]` 路由自訂過 NOT_FOUND 文案——已改正為遵循
   這個一致的既有慣例。
6. **永遠顯示同一個「查看診斷內容」連結,不依狀態切換文字**——
   `/maintenance/[id]/session` 自己已經完整處理過全部 5 種狀態的
   呈現(S018/S019 已經做完),這個頁面不需要重複那套依狀態切換的
   分支邏輯。
7. **本地第 4 份 `formatFileSize` 複製**、**第 3 份
   `SESSION_STATUS_LABELS` 複製**——同 `formatFileSize` 自己已經在
   這個 codebase 建立的「小到不值得跨檔案耦合」既有慣例,S020 自己
   的 EVIDENCE 已經引用過同一個理由做第 2 份複製。
8. **刻意不把 `MaintenanceCaseList`(S001)或
   `MaintenanceHistoryList`(S020)的項目改成連結**——這是本 story
   唯一真正卡住、需要完整說明的決策,見下方獨立一節。

## 一個刻意不做的retrofit:為什麼列表項目仍然不是連結

`MaintenanceCaseList` 自己的既有 doc comment 與 `MaintenanceHistoryList`
自己的既有 doc comment 都明確寫著「等 E07-S021 存在之後」——跨 epic
有直接前例:`KnowledgeList`(E05-S001)在 `KnowledgeDetail`(E05-S005)
建成時,確實把項目改成了連結。表面上,這個 story 理應對
`MaintenanceCaseList`/`MaintenanceHistoryList` 做同樣的 retrofit。

但兩個既有元件各自都有一個「已核准」的測試,斷言**恰好零個連結**:

- `MaintenanceCaseList`:「renders no links on any case item (E07-S021
  owns the not-yet-existing detail route)」——
  `expect(screen.queryAllByRole("link")).toHaveLength(0)`
- `MaintenanceHistoryList`:「renders no links on any case item
  (E07-S021 owns the not-yet-existing detail route)」——同樣的斷言

若把項目改成連結,這兩個斷言會直接從「真」變成「假」——不是
「補一個新的互動步驟,原始斷言逐字不動」(`.claude/rules/
STORY_WORKFLOW.md` Phase 4 第 5 點、E07-S017 自己的既有前例走的
路),而是**斷言本身的真假值被推翻**。逐字重讀 STORY_WORKFLOW
唯一允許的例外(測試本身技術性錯誤,或後面 story 讓早期測試的
「前提」過期、但只能新增互動步驟並保留原始斷言逐字不變)——兩者的
機制都預設「新增步驟」,不是「翻轉一個既有斷言的真假值」。這個情境
不乾淨地落在任何一個既有例外的字面機制內。

這個規則本身是這個 repo 最近才新增的鐵律(`git log` 顯示
`docs(workflow): add TDD rule — tests first, frozen except additions`
是這個 session 開始前的最後一個 commit),判斷值得從嚴解讀,不擴大
解釋既有的窄例外去配合這次的產品完整性期待。

**選擇的做法**:這個 story 只交付真正、完整、可獨立運作的
`/maintenance/[id]` 路由本身(唯讀,兩個既有函式的真實組合,對抗性
驗證過的 fail-closed 保護),但**不**改動 `MaintenanceCaseList`/
`MaintenanceHistoryList` 或它們的測試——這個決策依 `/advisor` Step 4
的標準屬於「單一 story 範圍、低風險(不影響任何既有行為)、可回退
(未來任何時候都能安全地加上連結)」,可自行採納,不升級到
`PENDING_DECISIONS.md` 卡住整個 story(不同於真正需要使用者決策才能
繼續動工的情境,例如 E05-S024 那種)。這個頁面目前只能透過直接網址
/ deep link 到達,E2E 測試用 `maintenance-session.spec.ts` 自己已經
建立的「登入 → 建立案例 → page.goto() 深連結 → 遺失 session → 重新
登入 → 回到目標路由」既有 round-trip 樣式驗證。

**留給未來的候選項**:等使用者有空確認這個規則張力的正確解法(是否
該把 STORY_WORKFLOW 的例外正式擴充為也涵蓋「翻轉斷言真假值」這種
情境,或是應該由一個新的、專門的小 story 明確地做這個 retrofit
並在那個 story 自己的 Phase 1 PLAN 階段就把「修改這兩個既有斷言」
列入計畫範圍),可以再處理。這不阻塞任何其他 story 的選取順序。
