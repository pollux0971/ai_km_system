## Scope 說明

E09 的第十三個 story,「中繼資訊呈現」子流程(S012-S015:applied-filter
/data-freshness/source-system/query-history)的第二個,顯示「這份結果
是什麼時候產生的」。

## 設計決策

**這個 mock 沒有真正的 ERP 後端同步流程,唯一誠實的「資料更新時間」
就是本次查詢自己的執行時間**:與其他報表工具常見的「資料每 N 小時從
來源系統同步一次」不同,這個系統目前沒有真正的 ERP 資料倉儲、沒有
真正的排程同步——`executedAt`(S006 已核准、已經在稽核的執行時間戳記
)是這個查詢的結果實際產生的唯一真實時刻。因此「資料更新時間」直接
顯示 `executedAt`,不假裝有一個獨立於查詢本身的資料同步時間軸。

**不建立新的 lib 檔案——這是這個 epic 目前唯一一個「不需要」獨立
lib 檔案的呈現 story**:S007-S012 每個都涉及真正的衍生/計算邏輯
(情境查表、分頁數學、筆數統計、比例計算、關鍵字比對),值得獨立
測試。本 story 的邏輯僅僅是 `new Date(x).toLocaleString("zh-TW")`
——這正是元件裡 `erpQuery.createdAt` 已經在用、且從 S001 至今都
沒有獨立 lib 檔案或獨立單元測試的完全相同一行程式碼。為了與既有
先例一致(而不是為了「每個 story 都要有自己的檔案」這個表面規則而
生造一個只包一行 Date API 呼叫的檔案),選擇直接沿用 `createdAt`
既有的 `<time dateTime={...}>` JSX 寫法,只透過 component/E2E 測試
驗證,不另建 lib 檔案。

**顯示時機綁定 `executedAt`,與 S007-S011 同組**:「資料何時更新」
只有在真的有結果時才有意義,因此放在 `erpQuery.executedAt` 判斷式
內、緊接在「查詢已執行完成。」之後——不像 S012 的「套用篩選」說明
(那個在情境選定當下就有意義,獨立於執行狀態)。

**AC 2-7 判定不適用**:與 S007-S012 判定理由相同——純衍生呈現層,
沒有新的使用者輸入、非同步 dependency、資料存取、或敏感操作。

一般空白再比對,但測試自己獨立算出的 `formattedExecutedAt` 字串沒有

`.replace(/\s+/g, " ")`,讓兩邊的空白正規化方式一致。這不是實作缺陷
——正式渲染出來的內容從頭到尾都是正確的,純粹是測試比對字串時沒有
處理 locale 格式化字串裡的特殊空白字元。
