# E09-S015 — Query history

- Branch: `story/E09-S015-query-history`
- Date: 2026-08-16
- Status: DONE

## Scope 說明

E09 的第十五個 story,「中繼資訊呈現」子流程(S012-S015)的最後一個。
與 S007-S014 不同,本 story 不是在 `/erp/[id]` 詳情頁疊加內容,而是
把 `/erp` 首頁既有的 `ErpQueryList`(S001)從純文字列表變成真正可
瀏覽的歷史紀錄——每一筆過去的查詢都連到自己的 `/erp/{id}` 詳情頁。

## 設計決策

**這不是憑空猜測的範圍,是 S001 自己當初就寫定的預告**:`
erp-query-list.tsx` 從 S001 起的既有 doc comment 逐字寫著:
「E09-S015 'Query history' is the dedicated full-browse story」。
S002 之後每個新增內容的 story(S007-S014)在自己的 doc comment 都
特別強調「Deliberately does NOT retrofit ErpQueryList (S001) into
linking here」,刻意不去動這個列表——這一路累積下來的克制,就是為了
留給本 story 一次做乾淨。因此本 story 的範圍不是自己發明的,是讀
既有程式碼與既有 doc comment 直接得出的。

**點進去看到什麼,完全不需要新邏輯**:`/erp/{id}` 這個路由與它底下
的 `ErpQueryDetail` 元件從 S002 就存在,且經過 S006-S014 一路疊加,
已經能正確處理「還在選情境」「已確認等待執行」「執行中」「已執行
完成(含全部 S007-S014 的呈現內容)」每一種狀態。本 story 純粹是
「幫使用者連過去」,連過去之後看到什麼是既有邏輯的責任,不需要在
`ErpQueryList` 這邊重複判斷或複製任何狀態邏輯。

**整個列表項目(問題文字+時間戳記)包成一個連結,不是只有文字部分**
:比照「開始新的 ERP 查詢」既有連結的整塊可點擊慣例,而不是只讓
`<strong>` 文字可點、時間戳記維持不可點——避免使用者點到時間戳記
卻沒反應的不一致體驗。

## 既有測試的必要修改(修改,非刪除)

`erp-query-list.test.tsx` 原本有一個 S001 自己的測試:「renders no
links on any query item (no query detail route exists yet)」——這個
測試名稱裡的前提「no query detail route exists yet」在 S002 之後就
已經是假的(`/erp/[id]` 從 S002 就存在),只是因為 S001-S014 都刻意
不連結過去(如上「設計決策」段落所述,是有意的範圍克制,不是遺漏)
,所以這個測試在 S002-S014 期間仍然「碰巧」是真的。本 story 正是
「終於把連結加上去」的那個 story,讓這個測試的字面斷言(零連結)
變成**確實與 AC 要求相反**的斷言——不是精確度不夠(窄化可以解決的
情況,像 S003→S005),而是斷言本身現在就是錯的,與 S005→S006 那次
「靜止狀態變成不可觀察」屬於同一類「後面 story 的新能力讓前面
approved 測試的前提站不住腳」情況。

處理方式:**修改**該測試(不是刪除)——把斷言方向反過來,驗證「每個
項目都連到自己的詳情頁」,並額外新增一個測試驗證「多筆項目分別連到
不同的頁面,不是全部連到同一個」(防止真實可能發生的閉包/off-by-one
錯誤,見下方 SELF-REVIEW 的對抗性突變)。舊測試真正要防的事(「不要
出現連結不出所料的元素數量」)雖然文字斷言完全反過來,但由新測試組
的正確性斷言完整取代,不是單純放寬。

E2E 層級(`erp-home.spec.ts`)有完全對應的既有斷言(S001 自己的
`await expect(... .getByRole("link")).toHaveCount(0);`),同一個
理由、同一種修改方式處理:改為對 3 筆已知種子查詢(`erp-query-
sample-1/2/3`)各自驗證正確的 `href`。
