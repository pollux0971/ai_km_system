## Scope 說明

SOURCE_BASELINE/epic 檔對這個 story 沒有任何專屬內容,只有通用樣板文字
+ 標題。標題本身就是交付物的直接描述:一個橫跨既有多個能力的綜合 E2E

`E05-S031`(Knowledge UI E2E)、`E07-S025`(maintenance E2E)是完全相同
的既有前例——三者都是各自 epic 的收尾 story,都是**純測試 story,零原始
碼變更**,都是稽核既有 spec 檔案找出「單獨驗證過,但從未一起組合驗證
過」的落差,而不是重測已經驗證過的東西。

**核心設計決策**:

1. **零原始碼變更**——完全比照 E03-S033/E05-S031/E07-S025 的既有慣例。
   這個 story 只新增一個測試檔案,不改動 `apps/web/src` 底下任何一行。
2. **稽核方法**:完整讀取現有唯一的 E09 E2E spec 檔案(`erp-home.spec.ts`,
   橫跨 S001-S023 共 2 個測試),逐一確認每個既有測試的範圍,找出真正的
   **組合層級**落差,而非單一功能落差(單一功能早已被各自的 story 測
   過)。具體發現:
   - 兩個既有測試都只從 `/erp/new` 建立全新查詢——從未真的點擊過首頁
     列表裡既有的種子查詢連結進入其詳情頁(S001 自己的測試只驗證過
     連結的 `href` 屬性,從未真的點擊)。
   - **更關鍵的發現**:種子查詢 `erp-query-sample-1` 的問題文字「上個
     月各分公司的營收總額是多少?」直接查證 `erp-scenarios.ts` 原始碼
     後確認會 confidently 命中 `revenue-by-branch`(含「營收」「分公司」
     關鍵字)——`matchErpScenarios` 在有真實命中時只回傳「那一個」情境,
     不是全部 4 個;`isAmbiguousErpQuery` 也因此回傳 `false`。既有測試
     2 刻意用一個「無法比對任何關鍵字」的問題文字來測 S004 的澄清 UI
     與 S003 的「永不清空」fallback——這代表「只有一個確定命中選項的
     單選挑選器」這個路徑,S003/S004 兩個 story 真正主要要處理的情境,
     從未被任何 E2E 測試真正走過,只有各自的 unit test 驗證過。
   - 沒有任何既有測試呼叫過 `page.reload()` 或等效的真實硬重整。
   - 沒有任何既有測試在同一個 session 裡建立/查看超過一筆 ERP 查詢——
     無法證明歷史列表在新增一筆之後正確反映(3→4 筆),也無法證明查看
     某一筆查詢的詳情頁時,不會被同一個 session 稍早查看/操作過的另一
     筆查詢的狀態污染。
3. **兩個測試,同 E03-S033/E05-S031/E07-S025 的既有形狀**——「從既有
   歷史點進去、confident-match 挑選器、完整跑完、撐過真實重整」+「建立
   第二筆查詢後,歷史列表正確反映兩筆,且各自狀態互不污染」。

## 測試撰寫過程的自我修正(誠實記錄,不是造假掩護)

第一次執行新測試 1 時,在 `page.reload()` 之後的斷言全數失敗——追查
`error-context.md` 發現重新整理後頁面顯示的是「登入」畫面,不是預期的
ERP 查詢詳情頁。這**不是** ERP 功能的實作 bug,而是這個 story 自己對
既有、已知限制的錯誤假設:這個 codebase 的 mock `AuthClient` session 是
純記憶體內閉包變數(`packages/auth-client/src/mock.ts`),任何真實硬重整
都會連同 ERP 查詢資料一起把登入狀態也重置,`SessionGate` 會先把使用者
導去 `/login`,ERP 頁面自己根本沒機會渲染——這正是 S021/S022 兩個 story
自己的 EVIDENCE 就已經記載過的同一個限制,只是這次是第一次真的嘗試呼叫
`page.reload()` 才具體撞到。查看 `maintenance-e2e.spec.ts`(E07-S025)
自己的原始碼,確認它早已用同一個限制設計出正確的處理方式:硬導覽/重整
後先偵測被導回 `/login`,重新登入,並讓登入流程自己的 `returnUrl` 機制
(E01-S003)把使用者帶回原本要去的頁面。本 story 的新測試 1 直接沿用
這個既有、已核准的 `reauthenticate()` helper 寫法(逐字比照
`maintenance-e2e.spec.ts` 的實作),修正後重跑立即通過。這個修正沒有
碰觸任何既有原始碼或既有測試,只調整這個 story 自己全新、尚未核准的測試
檔案本身,屬於 Phase 4 第 5 點「測試本身的技術性錯誤」的窄例外(判斷
依據:直接查證這個限制在 S021/S022 已有明文記錄、且 maintenance-e2e
已有正確處理範例,不是含糊的直覺猜測)。

同時也順手修正了兩處文字比對錯誤(自己起草時猜測的「已套用篩選：命中
關鍵字」不是實際文字,直接查證 `erp-applied-filters.ts` 原始碼後改為
逐字正確的「已套用篩選：營收、分公司」;「共發現 5 項...」摘要句誤用
全形逗號,查證 `erp-results.ts` 原始碼後改為半形逗號)——同屬測試撰寫
階段自己發現、自己修正的技術性錯誤,不是實作問題。

## 對抗性自我驗證(SELF-REVIEW,證明新測試不是空殼斷言)

由於這個 story 沒有新增任何原始碼可以突變,改為對**既有、已核准**的
`selectErpQueryScenario`(`erp-queries.ts`)做對抗性突變,驗證這個
story 新增的測試 2(多筆查詢各自狀態互不污染)是否真的在檢查真實行為,
而不是巧合通過。先確認 `git status --short` 顯示已完整 staged,再把
`writeStore(store.map((item) => (item.id === id ? updated : item)))`
的比對條件從 `item.id === id` 改成 `index === 0`(模擬「忘記依 id 篩選,
永遠覆寫陣列第一筆」這個具體、寫實的 bug)。

重跑 `pnpm exec playwright test erp-e2e`:**測試 2 立即在檢查歷史列表
是否完整包含全部 4 筆問題文字時失敗**——`erp-query-sample-1` 的問題文字
「上個月各分公司的營收總額是多少?」從列表中消失,因為它在陣列索引 0,
被剛剛選擇了完全不同情境的第 4 筆查詢的資料覆寫掉了,精準對應突變的
效果。**測試 1 完全不受影響**(它從頭到尾只操作單一一筆查詢,不涉及
「另一筆查詢的操作是否污染這一筆」這個情境,依 `git diff` 差異範圍本來
就不該受這個突變影響)。這證實測試 2 確實是真實、有效的跨紀錄一致性
保護,不是巧合通過的空殼——這也是這整個 epic 至今**第一次**有任何測試
證明多筆 ERP 查詢的狀態彼此獨立。

已用 `git checkout --` 還原(先前已用 `git add -A` 建立 checkpoint),
`git diff --stat` 確認乾淨、`git status --short` 只剩下這個 story 自己
