## 設計決策

### 兌現 E11-S002 自己記錄的延後連結

`user-list.tsx` 自己的 doc comment(S002 寫的)明確說「E11-S003 才擁有 `/users/[id]` 這個路由」——本 story 正是那個 story,直接把連結接上,同時把 doc comment 更新為「已兌現」而非仍然留著「將來才做」的措辭,避免文件與程式碼不同步。

### `getUser` 的 NOT_FOUND 形狀:`value: T | null`,不是 error

比照 `getErpQuery`(E09-S002)/`getMaintenanceCase`(E07-S001)已建立的既有慣例:「這次查詢本身成功了,只是這個 id 沒有對應資料」用 `value: null` 表達,不是包成 `ok: false` 的 NOT_FOUND error——把「查無此 id」與「查詢過程真的出錯」這兩種語意分開,由呼叫端(`user-detail.tsx`)自己決定要顯示 not-found 畫面還是 error 畫面。

### 新增 `createdAt` 欄位:漸進式豐富既有型別,同 `ErpQuerySummary` 既有模式

`AdminUser` 是 S002 已核准的型別;本 story 新增 `createdAt` 而不是回頭重新設計整個型別,理由與 `ErpQuerySummary` 自己橫跨多個 story(S002 加 `selectedScenarioId`、S005 加 `confirmedAt`、S006 加 `executedAt`)漸進成長的既有模式相同——每個 story 只加自己需要的新欄位,不重新設計既有欄位。8 筆種子資料的 `createdAt` 值刻意分散在不同時間點(而非全部相同),讓「詳情頁真的顯示這筆資料自己的建立時間,不是巧合相同的假資料」這件事有意義。

### 詳情頁的欄位集合:與清單相同 + 建立日期,不提前做角色編輯/權限矩陣

詳情頁顯示的欄位(姓名/信箱/部門/角色/狀態)與清單相同,額外加上建立日期。這符合 AC8「MVP 可以簡化」——角色編輯、權限矩陣分別是 `E11-S006`/`E11-S008` 這兩個明確、已命名的未來 story 的範圍,本 story 不偷跑先做那些能力的 UI。

## 過程中發現並修正的兩個真實問題(誠實記錄)

### 1. FIX 循環(1 次):Testing Library 的 `getByRole` 沒有 `exact` 選項

第一次執行 typecheck 時,`user-detail.test.tsx` 出現型別錯誤:`getByRole("heading", {..., exact: true})` 的 `exact` 屬性在 Testing Library 的 `ByRoleOptions` 型別裡不存在。追查後確認:這是把 **Playwright**(E2E,`getByRole` 的 `name` 字串預設是子字串比對,`exact` 是有效選項——見 E11-S001 自己的既有發現)的既有寫法誤用到 **Testing Library**(component/unit test)上——Testing Library 的字串比對本來就預設精確,根本不需要、也沒有這個選項。移除 `exact: true` 後 typecheck 立即通過,從 VERIFY 第一個 gate(typecheck)重跑全部確認乾淨。這是唯一一次 FIX 循環,根因單一且明確,一次修正解決。

### 2. `toLocaleString("zh-TW")` 的隱藏空白字元問題

撰寫「顯示建立日期」測試時,`getByText(new Date(...).toLocaleString("zh-TW"))` 找不到元素,即使畫面上確實顯示著看起來一樣的文字。查證 `erp-query-detail.test.tsx` 自己已有的等價斷言,確認這是已知、已解決過的問題:`toLocaleString("zh-TW")` 在「上午/下午」前面插入 U+2009 窄空白字元,直接用同一個字串當搜尋條件在某些情況下會比對失敗。改用該檔案已建立的 `.replace(/\s+/g, " ")` 正規化寫法,並進一步改為斷言 `<time>` 元素的 `dateTime` 屬性(語意上更精確、不受 locale 格式細節影響)。

## 對抗性自我驗證(SELF-REVIEW,發現並修正一個真實的測試品質落差)

目標:證明 `getUser` 真的依 id 篩選,不是巧合回傳對的資料。

突變:把 `getUser` 改成永遠回傳 `SAMPLE_USERS[0]`,忽略傳入的 `userId`,模擬「忘記依 id 篩選」這個具體錯誤。

**第一輪結果,發現一個真實的測試品質落差**:`users.test.ts` 的「returns the matching user for a known id」測試**意外通過**——追查發現這個測試自己用 `list.value[0]` 當作「已知使用者」,而突變後的 `getUser` 剛好也永遠回傳索引 0,兩者巧合吻合,測試沒有真的驗證「依 id 篩選」這件事。同一個檔案裡的「returns null for an unknown id」測試則正確捕捉到突變(precisely 1 個測試失敗)。

**修正**:把「known id」測試改成使用一個**非索引 0** 的具名使用者(`mock-user-it-admin`,同 E2E 測試使用的同一筆),並加上 `expect(knownUser).not.toBe(list.value[0])` 明確斷言這不是第一筆——確保這個測試不會再因為巧合而通過。重新驗證(突變仍在):**現在 2 個測試都正確失敗**(known id 測試 + unknown id 測試),證實修正後的測試真的在守護「依 id 篩選」這個行為。

**E2E 層的獨立佐證**:即使在第一輪(未修正前),E2E 的 2 個新測試(點擊使用者/未知 id)都**已經**正確命中同一個突變(分別因為顯示了錯的使用者資料、以及沒有顯示 not-found 訊息而失敗)——證實這個 bug class 從一開始就有真實、端對端的覆蓋,只是 unit test 層自己的斷言設計不夠嚴謹。三層測試(lib/component-mock/E2E-real)的分工在這次驗證裡清楚呈現。

## 獨立審核 Round 1 — REQUEST-CHANGES

審核者獨立重新查證核心主張(`getErpQuery`/`getMaintenanceCase` 的 `value: T | null` 形狀、`erp-query-detail.test.tsx` 的 thin-space 正規化先例)皆屬實,並獨立 force 全量重跑 typecheck/lint/build/unit 全綠。

審核者另以獨立對抗性突變、鎖定與 DEV 自己驗證過的層(`users.ts` 的 `getUser` 資料查找邏輯)不同的另一層——`user-detail.tsx` 元件自己的 render 分支邏輯(把 `error` 與 `not-found` 兩個分支的訊息文字互換,模擬複製貼上貼錯位置)。結果:精準命中 1 個測試(「shows a not-found state...」),但「shows an error message when the fetch fails」測試**意外通過**——追查發現該測試只斷言 `screen.findByRole("alert")`(通用),從未斷言具體訊息文字「無法載入使用者資料。」,而 `<ErrorMessage>` 元件對任何 `message` 都會渲染 `role="alert"`,所以兩個分支互換後這個測試看不出差異。

**判定為真實缺陷(MAJOR),不是可接受的既有慣例**:與 S017 那次「exportPending guard 未測試但與既有慣例一致」的情況不同,這裡沒有「這個 codebase 到處都這樣寫」的既有先例可以類比——`erp-query-detail.tsx` 自己的錯誤狀態測試普遍都斷言具體文字,不是只斷言 `role="alert"`。若這兩個訊息真的被寫反,會讓「系統真的出錯」被誤讀成「你自己打錯 id」,或反過來——是一個對使用者有實際誤導後果的迴歸,理應被測試擋下卻沒有。

## 獨立審核 — DEV 修正

在 `user-detail.test.tsx` 的「shows an error message when the fetch fails」測試裡,把斷言從通用的 `screen.findByRole("alert")` 改為具體文字 `screen.findByText("無法載入使用者資料。")`,並在測試裡加註記說明理由(對照這次獨立審核發現的落差)。用同一個「互換 error/not-found 訊息」突變重新驗證:**修正後 2 個測試(error + not-found)都正確失敗**,證實修正確實補上了這個落差。已還原突變、確認 `git diff --stat` 乾淨、重新完整跑過 admin 全部單元測試(25/25)。
