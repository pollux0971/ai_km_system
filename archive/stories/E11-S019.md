## 設計決策

### 「重試永遠回傳 NOT_FOUND」是 S018 設計的直接推論,不是新的猜測

`document-failures.ts` 的 `listFailedDocuments()` 從 S018 開始就永遠回傳空陣列——理由是 admin 沒有真正的跨知識庫聚合查詢管道(S018 EVIDENCE 已完整記錄)。因為沒有這個管道,admin 端也就沒有任何本機儲存可以拿 id 去查「這份文件是否存在、是否真的處於失敗狀態」。`apps/web` 自己的 `retryDocumentProcessing`(E05-S021)之所以能做 `status !== "failed"` 的 `VALIDATION_ERROR` 判斷,是因為它背後有真正的 sessionStorage store;admin 端沒有這個東西,所以唯一誠實、不用猜測的答案就是「任何 id 都找不到」——`NOT_FOUND`。這與 S017「`getFeedback` 對任何 id 都回傳 null」是同一種推論鏈,只是這裡的回傳是 `Result<void, ApiError>` 的失敗分支而非 `T | null`。

### 成功路徑的程式碼與測試依然完整,不因「今天用不到」而省略

比照 AC8「MVP 可以簡化視覺或演算法,但此能力本身不可缺席」的既有判斷:`DocumentFailureRetryButton` 的成功分支(`onRetried()` 被呼叫、清除錯誤訊息、清單重新整理)完整存在且被測試覆蓋——測試在元件層 mock 掉 `retryDocumentProcessing`,不受真實 lib 函式「今天只能回傳 NOT_FOUND」這件事限制,這與 `FeedbackDetail`(S017)的 error-state 測試 mock 一個真實 `getFeedback` 從不會產生的 `SERVICE_UNAVAILABLE` 是同一種手法——UI 需要正確處理的結構性分支,不代表今天的真實資料一定會走到那裡。

### E2E 範圍:證明「空佇列不留孤兒按鈕」,而非「重試真的成功」

因為佇列本身永遠是空的(S018 的核心設計),`DocumentFailureList` 的 `state.documents.map(...)` 永遠不會執行,重試按鈕在真實production 流程裡永遠不會被渲染出來——不像 S017 的 `/feedback/{id}` detail 頁面還能靠「直接造訪未知 id 的 URL」保留一條誠實的 E2E 路徑,重試按鈕沒有獨立路由,無法用同樣手法繞過空清單直接測試。因此本 story 的 E2E 範圍改為驗證一個同樣重要、同樣屬於 UX AC(「loading/empty/error/permission-denied 必須是不同狀態」)的性質:確認空狀態畫面沒有意外留下一顆按了也沒有真實目標的孤兒按鈕——這是誠實可測、且真的有意義的斷言,而不是為了湊 E2E 覆蓋率而測一個假裝會發生的成功流程。

## 對抗性自我驗證(SELF-REVIEW)

第一次嘗試:把 `handleRetry` 開頭的 `if (pending) return;` 防連點守衛移除,執行 `document-failure-retry-button.test.tsx` 全部 5 個測試——**0 個測試失敗**。診斷後確認這個守衛在測試環境下是多餘的:按鈕本身有 `disabled={pending}` 屬性,React Testing Library 的 `fireEvent.click` 對一個真實 disabled 的 `<button>` 元素不會觸發 click handler(與瀏覽器原生行為一致),所以「連點兩次」這個場景在 DOM 層就已經被 `disabled` 屬性擋下,`if (pending) return` 這行防護在測試裡確實測不出來——這與已核准的 `UserStatusToggle`(E11-S005)完全同一種寫法與同一種限制,不是本 story 特有的缺陷,誠實記錄此次嘗試未命中而非隱藏。

第二次嘗試(換一個更有意義的突變):把 `handleRetry` 開頭的 `setError(null)` 移除(模擬「忘記在新一輪重試開始時清掉舊錯誤訊息」)。結果:精準命中 1 個測試——「clears the previous error message once a retry succeeds」,斷言失敗訊息在重試成功後仍殘留在畫面上。其餘 4 個測試不受影響。
