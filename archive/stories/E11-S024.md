## 設計決策

### 為什麼「只建可重用元件,不接線」是誠實的選擇

INIT 階段逐一查核整個 codebase,確認今天沒有任何一個既有 admin 動作是真正「危險/不可逆」的:

- `UserStatusToggle`(S005)、`ModelStatusToggle`(S013)、`ConnectorStatusToggle`(S014)都是可逆的啟用/停用切換,三者各自的既有 EVIDENCE 都已明確判斷「可逆操作不需要確認對話框」。
- `apps/admin` 目前完全沒有任何刪除(delete)能力——每一個既有清單頁 story(Department/Group/Prompt/User)自己的範圍都明確止於 list+create,沒有一個包含 delete。
- 更關鍵的是:**S013 與 S014 自己的 EVIDENCE 已經明確、提前留下伏筆**,誠實記錄「啟用雲端模型」/「啟用連接器」這兩個動作「若未來真的接上有效力的系統,很可能需要 E11-S024 的確認機制」,但「今天這個開關不接任何真正有效力的系統,啟用它本身不產生真實風險」,因此**當時刻意不加確認對話框**。

依此,若本 story 現在回頭把確認對話框硬套到這兩個 toggle 上,等於是在推翻 S013/S014 自己已經核准、有明確理由的判斷,而不是尊重它——那兩個 story 的判斷邏輯(「今天沒有真實風險」)完全沒有改變,S024 開工本身不構成讓它們變成危險動作的理由。

因此本 story 的誠實範圍,比照 `AdminRouteGuard`(E11-S023)已建立的「結構完整、測試完整,但真正接線等待缺失的觸發條件到位」模式:建出一個完整、通過測試、可重用的確認元件,讓未來第一個真正需要它的動作(一個真正的 delete,或 Model/Connector 一旦真正接上有效力的系統之後的 toggle)可以直接套用,不需要重新發明這個已經在 apps/web 驗證過兩次的 pattern。

### 不在元件內寫入 audit event

`audit.ts`(E11-S015)自己的 doc comment 已經確立「沒有正當理由能寫入稽核紀錄,因為沒有真正的 E14 audit append API」。本元件同樣不在內部寫入任何 audit event——一旦真正的 E14 API 存在,真正產生 audit event 的地方會是「呼叫端自己的 `onConfirm`」,不是這個泛用元件本身。

### `isConfirming` 成功後主動重置,而非依賴呼叫端移除元件

`apps/web` 的兩個既有先例都依賴「呼叫端在成功後把整個元件從清單中移除」(例如刪除的項目直接從清單消失)。本元件刻意不依賴這個假設——成功後主動把 `isConfirming` 重置為 `false`,讓這個可重用元件即使被套用在「呼叫端不會移除自己」的情境下也能安全運作,不會卡在開啟狀態。

## 對抗性自我驗證(SELF-REVIEW)

目標:證明 alertdialog 的 accessible name 真的包含目標自己的身份識別,不會被寫死成一個通用文字——直接驗證本元件自己 doc comment 提到的、`KnowledgeDocumentDeleteButton` 當年真實發生過的那個坑是否也會在這裡發生。

突變:把 `<div role="alertdialog" aria-label={dialogLabel}>` 改成 `<div role="alertdialog" aria-label="確認危險操作">`(寫死成通用文字,不含目標身份)。

結果:精準命中 1 個測試——「clicking the trigger reveals a role=alertdialog with the target's own name in its accessible name and the confirmation message」(`getByRole("alertdialog", { name: "確認刪除部門：資訊部" })` 找不到元素,因為 accessible name 已經不含「資訊部」)。其餘 7 個測試不受影響。

已用 `git checkout --` 還原突變(先前已用 `git add -A` 建立 checkpoint),重新執行 admin 全部單元測試(44/44 檔案 308/308 tests)確認全綠。
