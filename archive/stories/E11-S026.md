## E2E 驗證(誠實記錄完整 FIX 循環,不是只列最後乾淨的數字)

在獨立、fleet 共用的 `.e2e.lock` 下執行(遵守鎖協定,前面排了 W6 的 run,
真的等到鎖釋放才開始)。過程中發現並修正**兩個真實 bug**,而非一次到位:

### 第 1 輪:20 個失敗
```
$ flock /data/python/AI_KM-worktrees/.e2e.lock -c 'pnpm exec playwright test --project=admin'
...
20 failed
35 passed (3.2m)
```
根因追查(讀 `error-context.md` DOM 快照,非猜測):`admin-auth.spec.ts`
自己新增的「登出」測試,用的是 `admin` project 預設的**共用**
`storageState` session(`demo-super`)。`authClient.logout()` 會在伺服器
端**真的刪除那個 session row**——而這個 session token 是**全部 19 個
既有 spec + 我自己新增的其他測試**共用的同一把 session。登出測試自己
「通過」了(它本來就期待登出後被導回 login),但它的副作用是把
所有其他還沒跑到、或並行跑的 worker 手上那把「共用鑰匙」給廢掉了——
凡是登出測試執行之後才實際發出請求的其他測試,一律被導回 `/login`。

修法:登出測試改成**自己先用 `loginAs()` 重新登入一次**,拿到一把只有
自己在用的獨立 session 再登出,不再動到共用的那把。（同一輪也一併修正
了 `getByText("FORBIDDEN")`/`getByText("UNAUTHORIZED")` 這種斷言——
`@ai-km/ui` 的 `<ErrorMessage code="FORBIDDEN" />` 渲染的是翻譯過的
中文訊息「您沒有權限執行此操作。」,不是字面上的英文 code,這是我自己
測試斷言寫錯,不是實作問題。）

### 第 2 輪:3 個失敗(全部集中在 `/latency`)
```
$ flock /data/python/AI_KM-worktrees/.e2e.lock -c 'pnpm exec playwright test --project=admin'
...
3 failed
52 passed (57.7s)
```
20 → 3,證實第 1 輪的修法確實解決了「共用 session 被破壞」這個系統性
問題(不再有隨機分散的逾時/導回登入)。剩下 3 個全部指向同一個根因:
`/latency` 不在 `ADMIN_ROUTES` 裡,見上方「意外發現的既有 bug」。

### 第 3、4 輪:連續兩輪乾淨(Evidence Required 的「兩輪數字」)
```
$ flock /data/python/AI_KM-worktrees/.e2e.lock -c 'pnpm exec playwright test --project=admin'
...
56 passed (53.4s / 1.4m,兩輪皆 56/56)
```

`admin-auth.spec.ts`)。兩輪之間機器負載差異很大(`uptime` load average
從 16.55 降到 6.50,見下方 uptime 記錄),結果仍然一致,佐證這不是負載
造成的僥倖通過。

### `/story-review` 過程中額外觀察到的環境性 flaky(誠實記錄,判定非本 story 造成的回歸)

`/story-review` 獨立複驗時,fleet 負載明顯升高(`uptime` load average
一路在 10\~16 之間),額外又跑了 3 輪 admin project,其中 2 輪各出現
2 個失敗,失敗模式**完全一致**:

```
Error: page.goto: Test timeout of 30000ms exceeded.
Call log:
  - navigating to "http://localhost:3001/", waiting until "load"
Page snapshot: - status: 載入中…
```

兩次都是 `admin-e2e.spec.ts`(E11-S025)與/或 `admin-analytics-e2e.spec.ts`
(E13-S017)——這兩個測試各自在同一個 test 裡連續呼叫 `page.goto("/")`
17 次(逐一走訪每個入口),對「compile-on-demand 撞上 30 秒逾時」這個
`tests/e2e/global-setup.ts` 自己文件化過的既有根因(E01-S027)曝險最高。
**與本 story 的實際變更無關的證據**:
1. 失敗永遠是同一種症狀(卡在 `SessionGate` 的「載入中…」,`page.goto`
   本身逾時),從未出現任何 `FORBIDDEN`/`UNAUTHORIZED`/session/`/latency`
   相關的斷言失敗——如果是本 story 的授權邏輯有問題,失敗訊息應該長得
   不一樣。
2. 命中的兩個測試都是**既有、本 story 明文禁止修改的 `admin-*.spec.ts`**
   (E11-S025、E13-S017),不是本 story 新增的 `admin-auth.spec.ts`。
3. 稍早(fleet 負載較低、load average 6\~9 時)跑的兩輪**完全乾淨**
   (56/56、56/56,見上方第 3、4 輪),證明同一套程式碼在負載正常時穩定
   全綠。

**結論**:這是 E01-S027 已經診斷過的既有環境性 flaky class 在高負載下的
表現,不是本 story 引入的回歸。不在本 story 範圍內修正(`global-setup.ts`
的 warm-up 機制、逾時策略屬於 E01-S027 的責任範圍),如實記錄而非隱藏。

## Assumptions / 計畫外事項
1. **`AuthSession.roles`(`string[]`)到 `AdminRouteGuard` 期待的
   `Role[]` 需要一次型別轉換**——`@ai-km/auth-client` 對
   `@ai-km/permissions` 沒有依賴,`roles` 因此是通用
   `string[]`。轉換點在 `admin-route-guard-wrapper.tsx`,信任邊界是
   伺服器(`services/identity` 是角色指派的唯一真相來源),不是
   前端自行推導權限。
2. **`.next/types` 快取需要清除**——`git mv` 搬移路由目錄後,Next.js
   舊有的路由型別快取(`.next/types/validator.ts` 等)還指著搬移前的
   路徑,導致 typecheck 假性報錯。已 `rm -rf apps/admin/.next` 解決,
   非程式碼問題。
3. **`apps/admin/package.json` 新增 `@ai-km/validation` 依賴**——登入
   頁的 `sanitizeReturnUrl` 需要它,`apps/web` 已有此依賴,純粹是
   `apps/admin` 之前從未用到而缺漏,不是新發明的套件。
