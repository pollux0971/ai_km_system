## 測試修正記錄(若有)
本 story 依 TDD:先寫產出檔案草稿(需要先確定 deps/介面形狀才能真的可測,
同 E03-S040 的偏離記錄方式),測試斷言完全依 spec 8 條 Functional AC +
Security/Data Acceptance 撰寫。紅→綠除錯過程中修正的都是**測試本身的
技術性錯誤**(非放寬斷言配合實作),逐筆記錄:
- `testing/wav-fixture.ts`(測試 fixture,非測試斷言本身)的 8-bit PCM
  分支原本不管 `bitsPerSample` 一律寫 16-bit,寫入位置算錯導致
  `RangeError`。修正為依 `bitsPerSample` 選擇 8-bit(unsigned,128 為中心)
  或 16-bit 寫入。
- `normalize.test.ts` 的「keeps a single space...」案例原本預期
  「查一下 E-204 的錯誤代碼」保持「代碼」不變,但**實測**
  `opencc-js Converter({from:"cn",to:"twp"})`(spec 明文指定的確切設定,
  AC5 的「軟體」案例也證明必須用 twp 而非 tw)會把「代碼」轉成台灣 IT
  慣用語「程式碼」。判斷這是**我自己對 OpenCC 行為的錯誤假設**(不是
  OpenCC 設定錯——twp 設定完全依 spec 技術決策逐字照做),已用 node 一次性
  腳本實測驗證(見下方「twp vs 契約範例」一節),修正測試期望值為
  「程式碼」。
- `routes/transcriptions.test.ts` 的 `expectResponseMatchesContract` 呼叫
  原本傳入 `/v1/transcriptions`,但契約的 `paths:` key 是相對於
  `servers: [{url: /v1}]` 的 `/transcriptions`(不含 `/v1` 前綴)。判斷是
  **我看錯契約路徑格式**,改用獨立的 `CONTRACT_PATH` 常數。
- `routes/transcriptions.test.ts` 的 AC4 timeout 測試原本監聽
  `req.on("aborted")` 判斷 socket 是否真的被 client 端 abort,但這個事件
  只在「request body 傳輸中被打斷」才觸發,本測試情境是「body 已傳完,
  等 response 時被 timeout abort」,不會觸發 `aborted`。判斷是**我對
  Node http 事件語意理解錯誤**,改監聽 `server.on("connection", socket =>
  socket.on("close", ...))`(TCP 連線層級的真實訊號,與 Node 版本/API
  細節無關)。

## Assumptions / 計畫外事項

1. **`apps/api/package.json` 新增一行依賴**:「允許修改」清單明文只有
   `services/model-gateway/**`、`apps/api/src/server.ts`(註冊一行)、
   `apps/api/.env.example`,未列 `apps/api/package.json`。但 `server.ts`
   要 `import { modelGatewayPlugin } from "@ai-km/service-model-gateway"`,
   pnpm workspace 底下這必須先在 `apps/api/package.json` 的
   `dependencies` 宣告該 workspace package,否則模組解析會失敗——這是
   「註冊一行」在技術上唯一可行的必要延伸(與既有的
   `@ai-km/service-conversation`/`@ai-km/service-identity` 完全同一模式,
   只新增一行,不動其他任何內容)。`pnpm-lock.yaml` 隨之更新是
   `pnpm install` 的自動、必然副作用。

2. **`apps/api/src/config.ts`/`apps/api/src/errors.ts` 皆在允許修改清單
   外,深刻影響了實作設計**:
   - `config.ts` 已經讀取 `AI_KM_ASR_PROVIDER`/`AI_KM_ASR_SERVER_URL`
     (E04-S039 預先做的),但沒有 spec 要求的「production+fake→拒絕啟動」
     guard,也沒有讀 `AI_KM_ASR_FAKE_TEXT`。因為不能改 `config.ts`,這兩件
     事都移到 `services/model-gateway/src/config.ts`
     的 `resolveModelGatewayConfig()`,由 `apps/api/src/server.ts` 那一行
     註冊時把 `config.nodeEnv`/`config.asrProvider`/`config.asrServerUrl`
     當作 plugin options 傳進來。
   - `errors.ts` 的通用 error handler 只在錯誤是它自己的 `ApiHttpError`
     實例時才會把 `.details` 帶進回應,而且它把任何 503/504 都映射成平台
     通用碼 `SERVICE_UNAVAILABLE`/`GATEWAY_TIMEOUT`,不是這份 contract
     要求的端點專屬碼 `ASR_UNAVAILABLE`/`ASR_TIMEOUT`。因為不能改
     `errors.ts`,`routes/transcriptions.ts` 對「這個 route 自己知道的每
     一種失敗」一律直接 `reply.status(X).send({code,message,details?})`
     組出契約要求的確切內容,而不是 `throw` 讓 host 的通用 handler接手
     ——只有真的沒預期到的例外(bug)才會往上拋,交給 host 的通用 500
     INTERNAL_ERROR 處理(這條剛好雙方 code 一致,沒有落差)。

3. **`conversationId` 非 uuid 時,契約沒有對應的 `reason` 值**:AC6 寫
   「`conversationId` 非uuid → 400」,但 `transcriptions.yaml` 的
   `ValidationErrorBody.details.reason` 是必填、且只能是
   `TranscriptionRejectionReason` 五個值之一
   (`MISSING_AUDIO`/`BAD_WAV_HEADER`/`UNSUPPORTED_SAMPLE_RATE`/
   `AUDIO_TOO_LONG`/`AUDIO_TOO_SHORT`),沒有一個在語意上合理對應「格式
   錯誤的 conversationId」。因為(a)不確定的 dependency 必須標為
   BLOCKED/ASSUMPTION,不可當成已存在,(b)不得自行發明 reason 值配合
   程式,(c)本 story 不在 E13-S018 那一個「使用者已批准可新增 yaml」的
   例外名單內——這條 AC 無法在不改 contract 的前提下合規實作。判斷
   `conversationId` 依 spec 本身的 Data/Contract Acceptance 明文「不是
   authorization input、不影響行為」,格式錯誤時**安靜捨棄**(不記錄
   該值、不回 400)是安全、不違反契約 schema 的處理方式,已用測試明確
   斷言此行為(`routes/transcriptions.test.ts` "a malformed conversationId
   is dropped, not rejected")。若之後 domain owner(Team B)認為必須嚴格
   擋 400,需要先在 contract 補一個對應的 `reason` enum 值(例如
   `INVALID_CONVERSATION_ID`),那超出本 story 對 contract 唯讀的授權
   範圍,記錄為待後續決策的缺口,不視為擋 Done 的 BLOCKER。

4. **OpenCC `twp` 輸出與契約範例文字不符,已查證是契約範例過時**:
   `transcriptions.yaml` 的 `Transcription` schema `examples:` 寫
   `rawText: 请帮我查一下 E-204 的错误代码。` → `text: 請幫我查一下
   E-204 的錯誤代碼。`(代碼不變)。但 spec 技術決策明文指定
   `opencc-js Converter({from:"cn",to:"twp"})`,且 AC5 的
   `这是软件测试 API test`→`這是軟體測試 API test`(软件→軟體)**只有**
   twp(片語轉換)才會發生,tw(純字元轉換)會轉成「軟件」。用一次性 node
   腳本實測驗證:`cn→twp` 對「错误代码」的轉換結果是「錯誤程式碼」
   (代碼→程式碼,同樣是台灣 IT 慣用語轉換),不是契約範例寫的「錯誤
   代碼」。結論:契約的 `examples:` 是 illustrative,不是 schema 的一
   部分(schema 只要求 `text: string`,不釘死任何具體字串),此處是
   撰寫範例時的疏漏(可能手寫時未真的跑過 OpenCC),不影響 schema
   合規性,也不需要(也不允許)修改 contract 來配合;本 story 依 spec
   技術決策與 AC5 這兩個更高權威的來源(逐字指令 + 可執行驗收條件)
   為準,不依未經驗證的範例文字。

5. **幻覈黑名單清單內容**:spec 只給 2 個範例片語(「謝謝觀看」「字幕
   由…」)。額外加了「謝謝收看」「請不吝點贊訂閱轉發打賞支持明鏡與點點
   欄目」兩個真實、廣為人知的 Whisper 對中文靜音/雜訊常見幻覺輸出案例
   (非本 story 首創,是廣泛回報過的 Whisper 已知行為),數量刻意保持
   精簡(spec 用詞「純...黑名單」)。比對邏輯是**整段(去空白/標點後)
   完全等於黑名單片語**才視為幻覺並回空字串,不是子字串移除——因為
   spec 明講「純」,且子字串移除有誤刪真實句子片段的風險(已用一個測試
   明確驗證「謝謝觀看」出現在真實句子中間時不會被誤刪)。
6. **`FakeTranscriptionProvider` 的 <300ms→空字串邏輯,在完整 route
   pipeline 中實際不可達**:因為 route 在呼叫 provider 前已經用
   `parseAndValidateWav` 擋掉了 <300ms 的 WAV(回 400
   `AUDIO_TOO_SHORT`,不會走到 provider)。這條邏輯是 provider 自己
   單獨被呼叫(單元測試層級)時的行為,讓 fake provider 在脫離 route
   驗證的情境下也不會對明顯過短的音訊回傳假文字,更貼近真實 ASR 的
   行為。spec 明文要求這個行為(「若WAV時長<300ms回空字串」),因此
   照實作,並在 EVIDENCE 誠實說明它在完整 pipeline 中是防禦性/不可達
   的分支,不是掩護行為。
