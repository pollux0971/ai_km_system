## 背景 / 設計決策

Epic 檔(`AI_KM_BMAD_High_Granularity/epics/E13_Feedback_&_Analytics.md`)對
E13-S002 只有泛用樣板文字（「此能力」= Answer NG feedback），沒有欄位/UI
形狀。與 E13-S001「Answer OK feedback」共用同一個 SOURCE_BASELINE 黃金流程
錨點：`...→ Show Citation → User Verify → OK / NG → Feedback Loop`——OK 與
NG 是同一個判斷的兩個互斥結果，不是兩個獨立開關。

`contracts/` 目錄 grep 零 feedback 相關 endpoint/schema（與 S001 相同結
論）；`docs/stories/PROGRESS.md` 確認 E13-S001 已 approved，本 story 從最新
main（含 S001 的 4 個 commit）分支出去。

延續（而非重新設計）S001 剛建立的 pattern：

- `lib/messages.ts` 的 `AnswerFeedbackVerdict` 型別從 `"OK"` 加寬為
  `"OK" | "NG"`。`submitAnswerFeedback(messageId, verdict)` 本身**零邏輯
  變更**——S001 當初就把它寫成對 `verdict` 泛型的純 upsert，S002 只需要
  型別加寬即可讓 NG 完整運作，這是 S001 EVIDENCE 已預告的既有 pattern（比
  照 `state`/`revisions` 欄位的漸進擴充史）。
- `message-thread.tsx` 新增「沒有幫助」按鈕，緊鄰既有「有幫助」按鈕，共用
  同一個（現在參數化為 `verdict`）`handleFeedback` 與同一組
  `feedbackPendingIds`/`feedbackErrorIds` 狀態（一則訊息同時只會有一個回饋
  請求在飛行中，不需要依 verdict 分別追蹤）。

**設計決策——OK/NG 是單一 verdict 欄位，不是兩個獨立 toggle**：一旦
`entry.message.feedback` 有任一值（`!= null`，非原本 S001 的
`=== "OK"`），兩個按鈕都永久 disabled，同 S001 已建立的「無 undo feedback」
不變量,只是現在對稱套用到兩個按鈕上。哪個按鈕的 label 換成「已回饋：...」
只看它是否等於實際記錄的 verdict——另一個按鈕維持原本 label 但 disabled，
不會謊稱給出了不同的判斷。`submitAnswerFeedback` 函式本身**沒有**額外
guard 阻止把已有 verdict 覆寫成另一個 verdict（純 upsert，同 S001 已核准
的設計）——UI 是唯一的「無 undo」把關者,同 S001 建立的信任邊界一致，非本
story 縮減。

## FIX 循環紀錄（共 1 次，未達 5 次上限）

第一輪 `pnpm test` 全量執行時，除上述 3 個既有無關 flaky 外，另有 3 個新
增/相關的 E2E 測試失敗：`answer-ng-feedback.spec.ts` 的「giving 沒有幫助
feedback also disables the sibling 有幫助 button」，以及 S001 既有的
`answer-ok-feedback.spec.ts` 兩個測試（「persists across reload」「the
有幫助 button is offered...」）。

- **診斷**：讀取失敗訊息，發現是 Playwright strict-mode violation（單一
  locator 命中多個元素）或 count 斷言的實際數字比預期多。追查後確認根因：
  Playwright 的 `getByRole(role, { name })` 在 `name` 是字串時，預設採
  **不分大小寫的子字串搜尋**（不像 Testing Library 預設 exact match）。
  「有幫助」是「沒有幫助」與「已回饋：沒有幫助」的字面子字串——S002 新增
  「沒有幫助」按鈕之前，`answer-ok-feedback.spec.ts` 裡沒有 `exact: true`
  的 `{ name: "有幫助" }` locator 從未遇過這個問題（當時場上只有一個按鈕
  可能匹配）；S002 讓場上同時存在兩個按鈕後，這些 locator 的字面意圖（只
  想比對 OK 按鈕）與實際行為（也會比對到 NG 按鈕/已給 NG 回饋的按鈕）產生
  落差。這正是這個 codebase 已多次記錄的「Testing Library 與 Playwright
  預設 matching 語意不同」踩坑模式的另一個案例（先前見於 E11-S003 的
  `exact` 選項誤用）。
- **判定「是測試（locator）本身的技術性錯誤而非實作錯」的理由**：實作邏輯
  本身完全正確——單元/元件測試（vitest + Testing Library，exact-by-default）
  已經在完全獨立、不受此問題影響的一層驗證過相同行為（disabled 狀態、
  label 切換）全部正確；純粹是這幾個 Playwright locator 缺少 `exact: true`
  導致比對範圍比撰寫者原意更寬。這屬於 STORY_WORKFLOW Phase 4 第 5 點的窄
  例外，且明確是「因為 S002 合法新增了同名前綴的相鄰功能而暴露的既有
  locator 缺口」，不是用來掩護「有幫助」按鈕本身邏輯不符 AC 的藉口。
- **修正**（均為locator 精確度修正，未放寬或刪除任何既有斷言、未改變任何
  一個測試實際驗證的行為）：
  - `answer-ok-feedback.spec.ts`：第 55 行（點擊 OK 按鈕）與第 83 行
    （count 斷言）的 `{ name: "有幫助" }` 補上 `exact: true`；檔案頂部
    doc comment 新增段落記錄這次跨 story 修正的理由。這是本次唯一觸碰
    S001 既有（已 approved）測試檔案內容的修正，且範圍精確限縮在這 2 個
    locator，斷言的字串/驗證意圖本身逐字不變。
  - `answer-ng-feedback.spec.ts`（本 story 自己新的檔案）：全部 4 個
    `getByRole("button", ...)` 呼叫一致補上 `exact: true`（含原本尚未
    真正衝突、但預防性一致補上的 3 處），避免同一類問題日後再度發生。
- 修正後從 VERIFY 第一個 gate（typecheck）重新全量跑起，最終結果見上方
  Gate 紀錄表。FIX 循環在第 1 次即結束。

## Assumptions / 計畫外事項

1. **Security AC 的範圍限制**：與 S001 完全一致——本 story 沒有新增獨立
   的 negative-authz 測試,沿用本 codebase 所有 E03 對話訊息 mutation
   story（含 S001 自己）已建立的既有安全模型：授權邊界在 route 層
   （E01-S017 RoleGuard）統一把關,訊息層級的 mutation 動作本身不重複
   驗證授權。非本 story 獨有的縮減,是延續 S001 已核准的判斷。
2. **`submitAnswerFeedback` 允許覆寫既有 verdict（函式層無 guard）**：
   `feedback` 欄位若已是 `"OK"`,再呼叫 `submitAnswerFeedback(id, "NG")`
   會成功覆寫為 `"NG"`（見「upserts the same row when switching
   verdicts」測試）。「無 undo」的不變量只在 UI 層強制（兩個按鈕一旦有
   任一 verdict 就永久 disabled,使用者透過真實介面無法觸發覆寫）,同
   S001 對自己單一按鈕建立的信任邊界一致——UI permission hiding 不是
   security control,但這裡不是權限問題,是業務規則,且此路徑（直接呼叫
   函式覆寫）在真實 UI 中不可達。
3. **無真實 audit/E14 pipeline**：與 S001 完全相同的既有限制（Team A 前端
   telemetry 慣例,非真正的 E14 audit event pipeline）。
4. **未更新 `apps/admin` 的 Feedback queue（E11-S016/S017）**：與 S001
   完全相同的既有限制,不屬於本 story 的允許修改邊界。
