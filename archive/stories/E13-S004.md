## 背景 / 設計決策

Epic 檔(`AI_KM_BMAD_High_Granularity/epics/E13_Feedback_&_Analytics.md`)對
E13-S004 只有泛用樣板文字(「此能力」= free-text feedback),沒有欄位形狀、
可用範圍(僅 NG 還是 OK/NG 皆可)或長度限制。grep 整個
`AI_KM_BMAD_High_Granularity/` 目錄(含 `SOURCE_BASELINE.md`)找
「free-text」「自由文字」「補充說明」「freetext」等關鍵字,唯一命中是
`SOURCE_BASELINE.md`/`epics/E07_Maintenance_Assistant_Experience.md` 的
「E07-S09 Free-text Detail」(不同 domain、不同 story,與本 story 無關)。
`SOURCE_BASELINE.md` 第 548 行的黃金流程只到「OK / NG → Feedback Loop」,
沒有再往下定義自由文字欄位。`contracts/` 目錄同樣零 feedback 相關內容。

`docs/stories/PROGRESS.md` 確認 E13-S001/S002/S003 皆已 approved,本 story
從最新 main(含三者的全部 commit)分支出去。讀過
`apps/web/src/lib/messages.ts`、`message-thread.tsx`、`docs/stories/E13-S001.md`
~`E13-S003.md` 完整理解既有機制:`AnswerFeedbackVerdict`/
`submitAnswerFeedback`(OK/NG 兩按鈕、一旦有任一 verdict 就永久 disabled)、
`FeedbackReason`/`submitFeedbackReason`(僅 NG 才顯示的 4 選項 reason
selector)。

**ASSUMPTION 1(誠實記錄,非 BLOCKED)——欄位存在與形狀**:依
ATOMIC_STORY_BOUNDARIES.md「AI Agent Rule:不知道產品行為 →
BLOCKED/ASSUMPTION」的精神,這屬於 UI 欄位存在與否的產品決策,不是
contract/endpoint/permission 這種硬性依賴,且 story 標題本身已經預期這個
能力存在、MVP 允許簡化視覺——因此不整個 story BLOCKED,而是新增獨立的
`feedbackComment?: string` 欄位與 `submitFeedbackComment()` 函式。

**ASSUMPTION 2(設計決策)——可用範圍是 OK/NG 皆可,不像 reason selector
限定 NG**:S003 的 reason selector 只在 NG 後出現,因為一個「原因」在語意上
只解釋「為什麼沒有幫助」。但自由文字留言是使用者「還有什麼想補充」的通用
管道,OK 情境下同樣合理(例如「這個答案特別有幫助,因為引用了正確的政策
條文」),把它限縮成 NG-only 會是本story標題沒有要求的額外限制。因此
`submitFeedbackComment()` 的 gate 是 `existing.feedback == null`(尚未給過
任何回饋才拒絕),而非 S003 `submitFeedbackReason` 的 `existing.feedback
!== "NG"`。

**ASSUMPTION 3(硬性要求,非可選)——長度上限 `MAX_FEEDBACK_COMMENT_LENGTH
= 500`**:Security Acceptance「所有外部輸入均做 schema validation」是硬性
要求,即使 baseline 沒有指定具體數字。500 字是一個寬鬆但有界的補充留言長度
(不是完整文件),誠實記錄為 ASSUMPTION、匯出為常數供 UI(`maxLength`
屬性 + 送出前 disabled 判斷)與函式層共用同一個真相來源,避免兩處數字
漂移。

**設計決策——`feedbackComment` 是獨立於 `feedback`/`feedbackReason` 的
第三個欄位,不是折進其中之一**:一則留言可以跟 reason 並存(NG + 選了
「答案不正確」+ 額外留言說明哪裡不正確),折進任何一個既有欄位都會混淆
語意或強迫每個 fixture 多考慮一個不適用的維度(同 S003 對
`feedbackReason` 為何獨立於 `feedback` 的理由)。

**設計決策——`submitFeedbackComment` 儲存前先 `.trim()`,空白/純空白字串
一律拒絕**:對照 Security Acceptance 的 schema validation 硬性要求,選擇
「僅儲存修剪後內容」而非「儲存原始輸入」,避免使用者送出的留言帶有無意義
的前後空白,也讓「純空白字串」與「空字串」用同一條 `trimmed.length === 0`
判斷式一起處理,不需要兩條規則。

**設計決策——UI 沿用 S001/S002/S003 已建立的「no undo once submitted」
鎖定模式**:留言送出後,textarea + 送出留言按鈕一起變成 `disabled`、顯示
「已送出留言:...」靜態確認文字,不允許事後編輯。這不是規格明文要求
(`submitFeedbackComment` 函式層本身允許覆寫,同 S001~S003 的既有信任
邊界,見下方 Assumptions),而是延續本 codebase 至今每一個 feedback 相關
互動(OK/NG 按鈕、reason 選擇)都採用的一致 UX 語言,避免同一個功能族群
出現不一致的「可編輯 vs 不可編輯」行為造成使用者困惑。

## Assumptions / 計畫外事項

1. **`feedbackComment` 欄位的存在、可用範圍(OK/NG 皆可)、長度上限
   (500)皆為 Team A 的 ASSUMPTION,非規格明文定義**:grep 整個
   `AI_KM_BMAD_High_Granularity/` 目錄零命中任何自由文字回饋的欄位形狀、
   適用範圍或長度規範。依 ATOMIC_STORY_BOUNDARIES.md 的 AI Agent Rule
   精神記錄為 ASSUMPTION 而非 BLOCKED——這是 UI/驗證層級決策,不是
   contract/endpoint/permission。若使用者或 Team B 之後提供真實規格,
   需要新的 story 或本 story 的 follow-up 來對齊。
2. **可用範圍刻意選擇「OK/NG 皆可」而非比照 S003 reason selector 的
   「NG-only」**:見上方「設計決策」——這是本 story 與 S003 最大的分歧
   點,已明確記錄理由(自由文字是通用補充管道,不是 NG 專屬的原因說明),
   非疏忽或不一致。
3. **Security AC 的範圍限制**:與 S001/S002/S003 完全一致——本 story
   沒有新增獨立的 negative-authz 測試,沿用本 codebase 所有 E03 對話
   訊息 mutation story(含 S001/S002/S003 自己)已建立的既有安全模型:
   授權邊界在 route 層(E01-S017 RoleGuard)統一把關,訊息層級的
   mutation 動作本身不重複驗證授權。非本 story 獨有的縮減,是延續
   S001/S002/S003 已核准的判斷。
4. **`submitFeedbackComment` 允許覆寫既有留言(函式層無 guard)**:
   `feedbackComment` 欄位若已設定,再次呼叫會成功覆寫(見「upserts the
   same row when re-submitting a different comment」測試)。「無 undo」
   的不變量只在 UI 層強制(一旦 `entry.message.feedbackComment` 有值,
   整個留言框永久 disabled,使用者透過真實介面無法觸發覆寫),同
   S001/S002/S003 對各自欄位建立的信任邊界一致——此路徑(直接呼叫函式
   覆寫)在真實 UI 中不可達。
5. **telemetry payload 刻意不含留言原文**:`trackEvent` 的
   `conversation_feedback_comment_*` 事件只帶 `conversationId`/
   `messageId`/(失敗時)`code`,不含使用者輸入的留言內容本身——這是
   比 S001/S002/S003(皆為固定枚舉值,天生不敏感)更謹慎的選擇,因為
   自由文字欄位有更高機率包含使用者不預期被記錄的內容,符合
   Observability/Audit Boundary「不得記錄不必要的企業原文或敏感
   payload」。
6. **無真實 audit/E14 pipeline**:與 S001/S002/S003 完全相同的既有
   限制(Team A 前端 telemetry 慣例,非真正的 E14 audit event
   pipeline)。
7. **未更新 `apps/admin` 的 Feedback queue(E11-S016/S017)**:與
   S001/S002/S003 完全相同的既有限制,不屬於本 story 的允許修改邊界。
