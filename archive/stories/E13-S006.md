## 背景 / 現況盤點(決定 scope 的關鍵過程)

Epic 檔對 E13-S006 只有泛用樣板文字(「此能力」= feedback submission
state),沒有欄位形狀或行為細節。grep 整個 `AI_KM_BMAD_High_Granularity/`
目錄零命中任何 story 專屬內容;`contracts/` 目錄同樣零相關 endpoint。

「feedback submission state」字面意思(送出回饋時的 loading/pending/
error/success 狀態)高度懷疑與 S001~S005 已完成的東西重疊——S001~S005
的 EVIDENCE 逐篇都反覆記錄了 disabled 按鈕、pending set、no-undo 鎖定、
error alert。動手前先做一次誠實盤點,而非直接開始寫「新功能」:

1. **完整讀 `apps/web/src/lib/messages.ts` 4 個 submit 函式**
   (`submitAnswerFeedback`/`submitFeedbackReason`/
   `submitFeedbackComment`/`submitCitationFeedback`):全部是
   `async function`,函式本體內**沒有任何 `await`**——`readStore`/
   `writeStore` 是同步的 sessionStorage 操作,所以這些函式本質上是包了
   一層 `Promise` 的同步邏輯,沒有真正的網路延遲模擬。失敗路徑只有
   `NOT_FOUND`(messageId 不存在)與 `VALIDATION_ERROR`(輸入不合法)兩
   種,兩者皆屬於「client 端輸入本身有問題」,不是「dependency
   timeout/unavailable」(Functional AC 4 講的情境)。
2. **完整讀 `message-thread.tsx` 呼叫這 4 個函式的地方**:
   `feedbackPendingIds`/`feedbackErrorIds`、
   `feedbackReasonPendingIds`/`feedbackReasonErrorIds`、
   `feedbackCommentPendingIds`/`feedbackCommentErrorIds`、
   `citationFeedbackPendingKeys`/`citationFeedbackErrorKeys`——四個維度
   **各自獨立**的 pending/error state,每個都已經有：送出中 disabled、
   成功後鎖定+文字確認、失敗顯示 `role="alert"` 訊息且重新啟用供重試。
3. **核對 `message-thread.test.tsx` 既有測試**:
   `grep "mockResolvedValue({ ok: false"` 命中 S001/S002/S003/S004/S005
   各自的「送出失敗顯示錯誤訊息、按鈕保持可重試」測試,全部用
   mock 直接讓 lib 函式回傳 `{ok: false, error: {code: "NOT_FOUND"|
   "VALIDATION_ERROR", ...}}`——這證明 UI 端的錯誤處理邏輯是**通用的**
   (只檢查 `!result.ok`,不分支判斷特定 code),用 NOT_FOUND/
   VALIDATION_ERROR 觸發跟用假設的 DEPENDENCY_ERROR 觸發,測的是同一段
   程式碼、同一個行為(顯示錯誤、不誤標成功、可重試)。`ApiError.code`
   在 `packages/types/src/index.ts` 定義為開放的 `string`(非封閉
   enum),UI 端本來就不需要為每一種 code 各寫一次分支。

**盤點結論**:S001~S005 每一個都已經完整證明了自己那個維度的
loading/success/validation-error/dependency-error(以「任意 `!result.ok`
都會被通用地正確處理」的方式)/permission-denied(沿用既有 route
guard)狀態,而且都用 `.toBeDisabled()`/`role="alert"`/確切文字斷言
過(這是 S001 review round 1 教訓後,S002~S005 都嚴格遵守的紀律)。如果
本 story 現在重新做一次「送出中顯示 loading、失敗顯示錯誤」,會是把
S001~S005 已完成的能力包裝成「新完成」宣告——這正是 STORY_WORKFLOW.md
SELF-REVIEW checklist 明確要防的事,也違反 ATOMIC_STORY_BOUNDARIES.md
的 Change Budget 原則(「每個 Story 的 code change 必須可解釋回某一條
AC...無法追溯的修改應移出 Story」)。

**真正沒有被證明過的東西**:上述四個維度的 pending/error state 全部是
**互相獨立的 state 容器**(不同的 `useState`),但從來沒有任何測試證明
「這四個維度在同一則訊息上真的同時運作、互不干擾」——每個 S001~S005
自己的測試 fixture 都只填自己那個維度需要的最小資料,從未出現過一個
message 同時具備全部四種回饋、或兩個維度同時 pending 的情境。這正是
本 repo「單一能力做完後,補組合層級覆蓋」的既有先例模式
(`docs/stories/E11-S025.md`「admin E2E」、`docs/stories/E09-S024.md`
等——在既有能力都做完後,專門補組合/一致性覆蓋,零或極少production
code 變更)。E13-S006 依此判斷收斂為:**證明「feedback submission
state」這個通用送出狀態模型,在四個維度真正組合在一起時仍然正確**,
這是一個可獨立驗證、S001~S005 都沒證明過的能力,不是重複勞動。

## Scope 收斂決定

- **不新增/修改任何 `messages.ts`/`message-thread.tsx` 的生產程式碼**
  ——盤點確認現有的通用 `!result.ok` 錯誤處理與四個獨立 state 容器已經
  結構性地保證了維度間互不干擾(不同的 `useState`/不同的 store 欄位),
  沒有發現任何需要修的邏輯缺陷。
- **新增組合層級測試**,證明:
  1. 四個維度可以在同一則訊息上共存,各自獨立送出,互不覆寫。
  2. 已設定的三個維度,重新送出第四個維度不會擾動前三者。
  3. 一則訊息的全部四種回饋不會外溢到同一對話中的另一則訊息。
  4. 訊息層級 verdict 送出與 citation 層級送出可以真的同時 pending
     (這是唯二能在真實 UI 中同時進行中的兩個維度——reason fieldset 與
     comment textarea 都只在 `feedback` 已經**持久化**後才渲染,不可能
     與仍在 pending 的 verdict 送出同時發生,見 `message-thread.tsx`
     的 `entry.message.feedback === "NG"` / `!= null` 渲染條件),兩者
     互相不干擾對方的 disabled/pending/error 狀態。
  5. citation 送出失敗只影響 drawer 內部的 error alert,不會外溢到
     message 列本身的 error 狀態。
  6. 完整組合(NG+reason+comment+citation)在一次真實使用者 session 中
     全部送出後,跨頁面導覽(reload 等效操作)仍然正確持久化,且不影響
     同一對話裡另一則未被觸碰的訊息。

## FIX 循環紀錄(0 次,首次執行即全綠)

版本):兩個新的 component 測試最初用
`await screen.findByText("本季成長 12%[1]")` 等待訊息渲染完成——但
`[1]` 是被 `message-content.tsx` 的 `CITATION_PATTERN` 正則解析成獨立
citation 按鈕的,不會以純文字節點的形式存在於 DOM 中,導致
`findByText` 逾時失敗。比照 S005 既有測試的既定寫法,改為直接
`await screen.findByRole("button", { name: "檢視引用來源 1" })`
作為等待條件(citation 按鈕存在即代表該則訊息已經渲染完成),兩處皆
修正後首次執行即全綠。
