## 測試修正記錄(若有)
**1 筆,屬既有測試的「forcing function」設計本身要求的必要新增,非修改
既有內容**:`apps/api/src/csrf/csrf-route-scan.test.ts`(E04-S048,W2 的
既有 story)的 `payloadFor()` 是一個「已知路由 → 合法 body」對照表,檔頭
註解明文:未知路由 fallback 到 `{}`,若因此 400(而非預期的 403)就代表
「有人需要在這裡補上真正的 payload」。本 story 新增了真實的
`POST /v1/usage-events` 狀態變更路由,首次執行 CSRF 掃描測試時果然如此
文件所述地失敗(得到 400 VALIDATION_ERROR 而非 403 CSRF_HEADER_MISSING,
因為 schema 驗證發生在 CSRF 所在的 preHandler 之前)。這正是該測試設計要
觸發的「forcing function」,依其文件指示新增一個
`if (route.path === "/v1/usage-events")` 分支,回傳
`{name: "conversation_created", occurredAt: "2026-01-01T00:00:00.000Z"}`
(過去時間,避開本 story 自己的「未來 >5 分鐘」400 檢查,確保請求真的
會被 CSRF 擋下而非被業務規則擋下)。該檔案其餘既有內容逐字未動。修正後
`apps/api` 全部測試(含這個檔案的 6 個測試)重跑皆綠。

## Assumptions / 計畫外事項

1. **`requireAnyRole` 直接從 `@ai-km/service-identity` import,不走
   `hostRequireSession` 那種窄型別 host-indirection**:`requireSession`/
   `db`/`contracts` 需要窄型別包裝的理由是它們是 host app **per-instance
   裝飾器**(`app.decorate(...)`),不同 `buildServer()` 實例可能有不同的
   值,直接匯入型別會在 apps/api 同時編譯多個 domain 套件的原始碼時撞名。
   `requireAnyRole` 不同:它是一個**無狀態純函式**(只讀 `request.auth`,
   不觸碰任何 per-instance 資源),`apps/api/src/server.ts` 自己的
   `/admin/health`(E04-S047)也是直接這樣匯入使用——這是既有、已驗證過的
   模式,非本 story 發明。
2. **`FeedbackItem.id` 重用 `messageId`**:契約的 `FeedbackItem` schema
   同時要求 `id` 與 `messageId` 兩個獨立必填欄位,但範例把兩者填成不同的
   假資料(`fb-0001` vs UUID)。目前的 schema(E04-S043)裡,一則訊息的
   verdict/reason/comment/citationFeedback 都是該訊息 row 上的單值欄位
   (upsert,不是一個獨立的 feedback 事件表),也就是「一則訊息最多一組
   回饋」——沒有第二個 id 空間可用。範例的差異值判斷為示意用途,不是
   「這兩個欄位必須不同」的規則(schema 本身沒有這種限制),故 `id` 直接
   重用 `messageId`,不新造一個 id 產生機制或新表。若未來 schema 演進成
   多筆回饋歷史,屆時再處理。
3. **`submittedAt` = 訊息的 `updated_at`**:schema 沒有專門的「回饋提交
   時間」欄位,`updated_at` 是既有 schema 裡最接近的訊號——每次
   `setFeedbackVerdict`/`Reason`/`Comment`/`CitationFeedback`(E04-S043)
   都會更新它。已知的誠實限制:若一則訊息在有回饋之後又被 revise(理論上
   可能,`createRevision` 也會動 `updated_at`),`submittedAt` 會變成最後
   一次寫入時間而非真正的回饋提交時間——這是既有 schema 的既有限制,不是
   本 story 引入的新問題,新增欄位超出 Scope Out。
4. **citationFeedback 陣列採數字排序,非插入順序**:契約要求「順序穩定」
   但未指定排序依據。citation marker 在訊息內容裡永遠是 `[數字]` 格式
   (E04-S043 `extractCitationIds`),對 citationId 做數字排序是有意義的
   穩定順序(而非任意的),已在 `admin-read.repository.ts` 註解說明。
5. **`GET /admin/feedback/{messageId}` 不驗證 `messageId` 的 uuid 格式**:
   契約這個 operation 只列出 401/403/404/500 四種回應,**沒有 400**——若
   加上 `format: uuid` 的 schema 驗證,一個格式錯誤的 id 會變成未定義在
   契約裡的 400,而非文件明訂的行為。選擇不驗證格式,讓格式錯誤的 id 與
   不存在的 id 走同一條路徑(`adminGetMessage` 回傳 `undefined` → 404),
   與契約文件的回應集合完全吻合。
6. **`services/feedback` 需要 side-effect import `@fastify/cookie`**(見
   `plugin-types.ts` 檔頭註解):`@ai-km/service-identity` 的生產程式碼
   (`require-session.ts`/`plugin.ts`)使用 `request.cookies`/
   `reply.setCookie` 等 `@fastify/cookie` 自己的 ambient 型別擴充,卻從未
   自己 import 該套件(只有 identity 自己的測試檔案有 import)。identity
   單獨 typecheck 因為它自己的測試檔案剛好把這個擴充帶進同一個編譯單元而
   意外可行;`apps/api` typecheck 因為 `server.ts` 自己有 import
   `@fastify/cookie` 而可行。`services/feedback` 是第一個「只匯入 identity
   production 程式碼、不匯入其測試也不自己 import cookie 套件」的消費者,
   因此第一次讓這個既有缺口浮現。修法:`services/feedback` 自己加上
   `@fastify/cookie` 依賴 + 一行 side-effect import,不動
   `services/identity` 任何程式碼(Scope Out 禁止清單)。
