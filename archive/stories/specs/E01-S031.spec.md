# E01-S031 — 修正 12 支既有 E2E 對「硬導覽會登出」的過時假設

## Metadata
- Epic: E01 Application Shell & User Workspace
- Owner: Team A(W1,`E03-S035` 真實 session 的作者)
- MVP: **Required — 解除 4 個 story 的 AC「既有 E2E 零修改全綠」**
- Story size target: 0.5 developer-day

## 問題陳述(三條 lane 獨立重現,數據一致)
既有 E2E 中有 12 支穩定失敗,**根因是新系統做對了、舊測試的前提過時**:

**類型一(10 支)——把「硬導覽會登出」當成切換使用者的手段**
```ts
await page.goto(`/maintenance/${caseId}`);
await page.waitForURL((url) => url.pathname === "/login");   // 預期被登出
await page.getByLabel("帳號").fill(MOCK_MAINTENANCE_USERNAME); // 換另一個使用者
```
舊的 mock AuthClient 把 session 存在記憶體閉包,硬導覽即遺失——那些 spec 的
**檔案自身 doc comment 明文寫著**這個依賴。E03-S035 的真實 cookie session
**正確地**撐過硬導覽,於是預期的導回登入頁永遠不會發生。

受影響:`case-detail.spec.ts`(59/77/96)、`erp-e2e.spec.ts`(64)、
`maintenance-e2e.spec.ts`(84/195)、`maintenance-session.spec.ts`
(109/150/208/351)。

**類型二(2 支)——真實網路延遲打破 `.check()` 的驗證視窗**
`knowledge-selector.tsx` 的 doc comment 明文:「Non-optimistic... the mock
resolves near-instantly」。checkbox 狀態要等 API 回應才更新;舊 mock 近乎瞬時,
Playwright `.check()` 的內建驗證來得及。真實後端有實際延遲,`.check()` 回報
「Clicking the checkbox did not change its state」。

受影響:`knowledge-selector.spec.ts`(43/80)。

**穩定性已確認**:W7 在 Round 4(`--repeat-each=3`、安靜環境)逐支統計,
12 支全部 `pass=0 fail=3`,與 E03-S038 那輪完全一致。W6 另以 CSP
Report-Only vs 強制生效兩次對照,失敗集合完全相同。**不是 flaky,不是巧合。**

## Scope In
- 類型一:把「依賴硬導覽登出」改為**明確的登出動作**(按登出按鈕或等效的
  明確步驟),再登入另一個帳號。**測試意圖不變**——仍然是「換一個使用者、
  驗證同一份資料的呈現」。
- 類型二:為 checkbox 的狀態變化補上**等待真實回應**的寬容度(例如等待
  `toBeChecked()` 而非依賴 `.check()` 的內建驗證)。**不得改用樂觀更新**,
  那會改變產品行為。
- 每一支的修改都要在 EVIDENCE 逐條記錄:原本斷言什麼、為何過時、改成什麼、
  **測試意圖是否不變**。

## Scope Out
- **不得改任何 production 程式碼**——這批失敗的根因是測試假設,不是產品缺陷。
- 不得刪除任何測試或降低斷言強度;不得加 `retries`、`test.skip`。
- 不碰那 12 支以外的 spec。

## 依賴關係
- HARD 依賴:E03-S035(碼已 merge)、E03-S038(碼已 merge,提供隔離基礎設施)。
- **下游**:E03-S038 AC1、E01-S021 AC4、E01-S022 AC4、E01-S029 AC4。

## Functional Acceptance Criteria
1. 那 12 支全部通過,且**測試意圖與修改前等價**(EVIDENCE 逐條對照說明)。
2. 其餘既有 E2E **零修改**且全綠——修完後全量應只剩已具名的既有 flaky。
3. **反向驗證**:對其中至少 1 支,暫時還原成舊寫法確認它會紅,證明修法真的
   對應到那個根因,而不是碰巧讓測試變綠。
4. 全量 E2E 跑一次,記錄跑前跑後的 `uptime`。

## Security / Authorization Acceptance
- 明確登出必須真的清掉 session(不得只清前端狀態);修改後的測試仍須驗證
  「換人之後看到的是新使用者的資料」,不得弱化這個檢查。
