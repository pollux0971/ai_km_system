# E04-S009 — Authorization scope builder：從 E02 身分產生 `allowedScopeKeys`

## Metadata
- Epic: E04 — RAG & Conversation Intelligence
- Owner: Team B（domain）／開發者待定
- Layer: Platform/Backend
- Priority: P0
- MVP: Required Thin Slice
- Story size target: 1–2 developer-days（估計不可靠，見「為什麼現在 blocked」）
- Story 來源: 原 epic 模板 story，2026-09-02 由使用者啟用並定義實質規格
- Parallel-safe: No

## 為什麼這條是重量級（分級理由）

它是**新增授權判斷**，不是搬移。這是整個產品裡「**哪些部門的資料這個人可以
讀**」的唯一決定點，其下游 `services/retrieval` 只是忠實執行它算出來的範圍。

兩種錯法都不會報錯：

- **算太寬** → 未授權資料進入 retrieval context 與 citation，直接違反
  `DEVELOPMENT_POLICY.md` 第 3 條與 `SOURCE_BASELINE.md` §5 第 8–9 條。
- **算太窄** → 使用者看到「查無資料」，而資料就在那裡、他也有權限。
  2026-09-02 已實測過這個症狀的形狀（sqlite-vec 的 KNN-then-filter 缺陷讓
  維修工程師搜維修紀錄得到 `[]`）；差別是那次是實作缺陷、可用測試釘住，
  而這裡是**授權判斷本身算錯**，沒有任何本地測試能自證正確。

## 🔴 為什麼現在是 `blocked-team-b`

`allowedScopeKeys` 要從「身分」推導，但這個 repo 目前**沒有身分模型可推導**：

- `services/identity` 只有 ADR 0005 定義的 **session-cookie 薄切片**
  （登入、session、管理員 seed），不是 RBAC。
- **E02-S001～S030 全部未實作**，且與 E04/E06 一樣，epic 內文是共用樣板，
  **沒有任何 story 專屬規格**——沒有角色模型、沒有 department／group 的資料
  形狀、沒有 Resource ACL 的定義、沒有 Deny-Wins 的具體判定順序。
- `SOURCE_BASELINE.md` §5 只給了原則（第 5 條 RBAC + Resource ACL、第 6 條
  Permission Conflict 預設 Deny Wins），**沒有給模型**。

依 `policies/ATOMIC_STORY_BOUNDARIES.md` 的 AI Agent Rule：
「不知道 permission → fail closed」「不知道產品行為 → BLOCKED/ASSUMPTION」。

**使用者 2026-09-02 明確裁示：標 `blocked-team-b`，不建任何過渡對應表。**
理由記錄在此以免日後被當成疏漏：一張「暫時的」硬編碼部門對應表一旦存在，
就會成為既成事實，而它的錯誤形態正是本 story 要防的那兩種。

## 解除阻塞需要什麼（給 Team B / 使用者）

1. E02 的角色與 department／group 資料模型（至少：一個 principal 如何對應到
   一組可讀範圍的權威定義）。
2. Deny-Wins 的具體判定順序（角色允許 vs Resource ACL 拒絕時的優先權）。
3. Revoked permission 的失效語意（`SOURCE_BASELINE.md` §5 隱含要求不得因
   cache 繼續有效，但沒有給 TTL 或失效機制）。

## Scope In（解除阻塞後）

- 一個 `buildRetrievalScope(principal) → RetrievalScope` 的實作，輸出
  **必須**經過既有的 `toRetrievalScope()` branded constructor。
- Deny-Wins 的實作與其邊界測試。
- Revoked permission 不因 cache 繼續有效的驗證。

## Scope Out

- `services/retrieval` 內部推導 scope。**`retrieve()` 只收 `RetrievalScope`
  作為輸入（使用者 2026-09-02 設計約束，見 E04-S062）**，本 story 不得改變
  那個介面方向。
- 任何過渡／暫時的對應表。

## Functional Acceptance Criteria（草案，解除阻塞後需重新確認）

1. **(L1)** Given 一個具備角色與部門的 principal，Then 產生的
   `allowedScopeKeys` 等於權威定義所規定的集合。
2. **(L1)** Given 角色允許但 Resource ACL 拒絕，Then 該範圍**不在**輸出中
   （Deny-Wins）。
3. **(L1)** Given 沒有任何權限的 principal，Then 輸出空陣列——**合法狀態，
   意義為拒絕全部**，不得拋錯（既有 `toRetrievalScope` 已如此定義）。
4. **(L5)** Given 權限已被撤銷，Then 後續檢索不得因 cache 繼續看到舊範圍。
5. **(L5)** 未知或無法解析的 principal → fail closed，輸出空陣列或拒絕，
   不得回退到較寬範圍。

## 反向驗證（共同底線，不可省略）

把 Deny-Wins 改成 Allow-Wins，**AC2 必須變紅**；把撤銷後的 cache 失效拿掉，
**AC4 必須變紅**。兩段輸出都要記進 EVIDENCE。

## Anti-hallucination Guard

- **不得發明角色名稱、部門代碼、ACL 欄位或 scope key 命名規則。**
- 不得以 `services/identity` 現有的 session 薄切片推測 RBAC 模型。
- 規格未定義的部分一律 BLOCKED，不得以 ASSUMPTION 帶過後實作。
