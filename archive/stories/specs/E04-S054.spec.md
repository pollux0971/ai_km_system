# E04-S054 — `auth-client` 未送 CSRF header,導致 web 完全無法登入

## Metadata
- Epic: E04(使用者增補追蹤範圍)
- Owner: Team A(W2,E04-S048 的作者)
- MVP: **Required — 阻斷全部七條 lane 的 E2E,且是生產環境阻斷性缺陷**
- Story size target: 0.25 developer-day
- Story 來源: 總指揮 2026-08-29 立案

## 問題陳述(總指揮已實測驗證)
E04-S048 讓所有 state-changing API 要求 `x-requested-with` header,並在
`packages/api-client/src/client.ts` 加了注入。**但 `packages/auth-client`
(E03-S035 的 `createHttpAuthClient`)沒有送這個 header**——`grep -rn
"x-requested-with" packages/auth-client/src/` 零命中。

而登入流程走的正是 `auth-client`,不是 `api-client`。實測:

```
POST /v1/auth/login  無 x-requested-with → 403 {"code":"CSRF_HEADER_MISSING"}
POST /v1/auth/login  有 x-requested-with → 200
```

**後果**:apps/web 的登入表單送出後一律 403,**任何人都無法登入**。這同時
解釋了 2026-08-28 深夜起所有 lane「原因不明的大範圍 30 秒逾時」——E2E 的
第一步 `login()` 從頭到尾就過不去,不是負載、不是冷編譯、不是 worker 數。

## Scope In
- 讓 `packages/auth-client` 的 HTTP 實作在所有 state-changing 請求
  (至少 `login`、`logout`)送出 `x-requested-with`。
- 新增測試鎖住:auth-client 的每個 state-changing 呼叫都帶該 header。
- **新增一條端到端迴歸測試**證明「透過 web 的登入流程能真的登入成功」——
  這個缺口能存活,正是因為沒有任何測試涵蓋「auth-client → 真實 API」這條路。

## Scope Out
- 不改 CSRF 的伺服器端邏輯(E04-S048 已驗證正確)。
- 不改 `packages/api-client`(已正確送出)。
- 不改任何既有 E2E spec。
- 不新增/修改 contract。

## 依賴關係
- HARD 依賴:E03-S035、E04-S048(皆已 merge)。
- **下游:所有需要跑 E2E 的 story**(E01-S021、E01-S022、E01-S029、
  E03-S038 的 AC1、E13-S020 補證等)。

## Functional Acceptance Criteria
1. Given 真實 apps/api(CSRF 啟用),When 透過 `auth-client` 的 `login()`
   送出合法帳密,Then **200 並取得 session**(修正前為 403)。
2. AC1 的測試在修正前必須為**紅**;EVIDENCE 附修正前後兩段輸出。
3. `logout()` 同樣帶 header 並成功。
4. 既有測試零修改且全綠:`packages/auth-client`、`packages/api-client`、
   `apps/web`、`apps/api`、`services/*`。

## Security / Authorization Acceptance
- **不得為了讓登入通過而放寬伺服器端的 CSRF 檢查**——修的是 client 少送
  header,不是 server 要求太嚴。
- 未帶 header 的請求仍必須被拒(E04-S048 的既有否定測試零修改全綠)。

## Data / Contract Acceptance
- `contracts/` 零 diff。
