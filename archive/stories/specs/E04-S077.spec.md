# E04-S077 — 路徑參數評估:全 app 零 `params:` schema,逐路由查證實際曝險

## Metadata

- Epic: E04(衍生,跨 conversation/feedback 兩個 domain)
- Owner: Team B(domain)/評估由 Team A 執行
- Layer: Platform/Backend
- Story 來源:E04-S073 L2-EQ 首次執行(26 條 route,15 條 ABSENT,主因是
  `params:` schema 全 repo 零個)
- Parallel-safe:Yes(唯讀,不改碼)
- HARD 依賴:E04-S073(已 approved)

## 這條為什麼是重量級(分級理由,原文見 PROGRESS.md E04-S077 列)

同時命中「工作分級」的兩條觸發條件:觸及**資料可見性**(路徑參數決定取哪一份
對話、哪一則訊息、哪一筆回饋),且候選失敗模式是**靜默給出錯誤結果**(契約
宣告型別與格式,runtime 一律不檢查,畸形輸入不會讓任何東西報錯)。

**本次評估的結論改變了這個候選失敗模式的機率評估,但不改變分級**:見下方
逐路由表與摘要——**評估本身證明,目前這 11 條 route 沒有一條會真的靜默給出
錯誤結果**,因為每一條的資料庫呼叫都走參數化查詢,且除了一條刻意設計的
跨使用者管理端點外,每一條都在觸碰資料前先做過 ownership 檢查。分級維持
重量級是因為:①「資料可見性」這個觸發條件的認定看的是**這類缺陷所在的
風險面**,不是查完之後量到的實際結果;②`params:` schema 缺失本身仍然是
一個會被 L2-EQ 持續回報 ABSENT 的契約分歧,不會因為這次沒查到可利用漏洞
就消失。

## 評估方法

1. 用 codegraph 與 grep 找出全 repo 每一條**帶路徑參數**的 route
   (`app.get/post/put/patch/delete` 搭配 `:xxx` 語法),逐一讀取 route
   handler 原始碼。`apps/api/src/*.ts` 本身只有 `/health`、`/admin/health`
   兩條 route,皆無路徑參數,不在本表。
2. 對每個路徑參數,讀取 `contracts/openapi/*.yaml` 對應的 `parameters:`
   區塊,記下宣告的 type/format/pattern。
3. 從 route handler 往下追蹤該參數的值一路流向哪裡:repository 函式呼叫、
   SQL 查詢、字串插值、或純粹的記憶體比對。讀取每個 repository 函式的
   完整原始碼,確認是否用 `?`/`@name` 參數化,還是字串插值進 SQL。
4. 對每條 route,讀取其 `preHandler` 陣列與 handler 內部順序,確認
   authorization(session、角色、ownership)是否真的先於資料存取執行,
   而不是只看命名猜測。
5. 不執行任何 exploit;只讀程式碼與契約文字。

## 摘要

- **11 條 route 帶路徑參數,0 條找到可利用的漏洞**(SQL 注入或未授權資料外洩)。
- **10 條**(#1–#10)在觸碰資料前都有**兩層**防線:session/角色 + ownership
  (`lookupConversation`/`getMessage` 的 403/404,或 `prepareOwnerScoped` 這個
  在 SQL prepare 階段就會因缺少 `owner_key` 而直接拋錯的機制)。這 10 條的
  問題純粹是**不整潔**:契約宣告了 `format: uuid`(或 citationId 的
  `pattern`),runtime 完全不檢查,所以 L2-EQ 把它們報成 ABSENT,而且畸形
  輸入(例如帶 SQL 特殊字元的字串、超長字串、非 UUID 格式的字串)會一路
  流到 repository 層才被「找不到列」自然擋下,不是被 schema 主動擋在門口。
  這 10 條中的 citationId(#10)甚至已經有一層**比契約更嚴**的業務層檢查
  (成員檢查,而非只驗形狀)。
- **1 條**(#11,`GET /v1/admin/feedback/:messageId`)防線只有一層(角色),
  這是**設計上刻意如此**(管理端跨使用者讀取模型),不是這條 story 該否決的
  決定,但代表它是**萬一角色檢查本身出錯時,曝險面最大**的一條——其餘 10
  條就算角色/session 檢查失效,ownership 檢查仍然是第二道獨立防線;這條沒有。
- **若使用者授權修法,我會先修 #11**(`GET /v1/admin/feedback/:messageId`)。
  理由:①它是 11 條裡唯一只有單層防線的,補上 `params: { messageId: {type:
  "string", format: "uuid"} }` 直接對應 `analytics.yaml` 已經宣告的形狀,
  是這批修法裡風險最低、契約對應最直接的一條(不涉及 ownership 邏輯變更,
  純粹加一個 Fastify `schema.params`);②修完它,L2-EQ 對這條 route 會從
  ABSENT 轉 MATCH,同時把「防線最薄的路由」的曝險面收斂到跟其他 10 條一致
  (至少形狀錯誤會被 400 擋在角色檢查與 SQL 查詢之前,即使今天角色檢查本身
  沒有問題)。其餘 10 條可以照同一個修法模式(把已存在的 `ConversationId`/
  `MessageId`/citationId pattern 從 `contracts/openapi/conversations.yaml`
  轉成 Fastify `params:` schema)批次跟進,風險相近、彼此獨立。
- **沒有「無法追蹤」的參數**——本表 11 條路徑參數,每一個都完整讀到它從
  route handler 到最終 SQL/物件操作的每一步,沒有需要用「可能」或「應該」
  帶過的環節。

## 規格(僅在使用者另行授權修法時生效——本次不執行)

以下 AC 依本次評估的實際發現而寫,不是「加 schema 驗證」這個問題形狀本身
的樣板 AC。

### Scope In

1. 對本檔評估表 #1–#11 的 11 條 route,各自替 `conversationId`/`messageId`/
   `citationId` 加上 Fastify `schema.params`,值直接取自
   `contracts/openapi/conversations.yaml` 的 `ConversationId`/`MessageId`
   元件與 `analytics.yaml` 對應 `messageId` 參數(`format: uuid`),以及
   citations 路由的 citationId(`pattern: "^[0-9]+$"`)。
2. 加了 schema 之後,**既有的 403/404/400 業務邏輯必須逐字不變**——本次
   評估表已經證明每條 route 的 ownership/業務規則檢查是正確的,修法只是
   在它們之前多加一層「形狀不對就先 400」,不得順手改寫這些檢查的邏輯。

### Scope Out(需使用者裁示,不得在修法 story 內自行決定)

- 是否要把 `format: uuid` 之外再收緊成明確的 UUID `pattern`(v4 專屬 regex)
  ——contracts 目前只寫 `format: uuid`,Ajv 對 `format` 的處理方式需先查證
  (比照 E04-S073 對 `format: password` 的查證方法,不得用讀的假設)。
- `GET /v1/admin/feedback/:messageId` 的單層防線本身(只用角色、不用
  ownership)是否要補上第二層——本次評估已明確判定這是**設計決定**,不是
  路徑參數驗證的問題,補 schema 不等於補這一層;要不要另外加是產品/授權
  模型層級的決定,不在本 story 內回答。

### Functional Acceptance Criteria

1. **(L1)** 對 #1–#11 每一條 route,送出一個 `conversationId`/`messageId`
   不符合 `format: uuid` 的請求(例如 `"not-a-uuid"`),Then 收到 400
   `VALIDATION_ERROR`,**且未執行任何 repository 呼叫**(不是先查到
   not_found 才回 404——是根本沒進 handler 就被 schema 擋下)。
2. **(L1)** 對 #10(citationId),送出不符合 `pattern: "^[0-9]+$"` 的值,
   Then 收到 400 `VALIDATION_ERROR`,先於 `extractCitationIds` 的成員檢查
   執行。
3. **(L2)** L2-EQ(`tools/contract-equivalence/`)對這 11 條 route 的 `params`
   欄位由 ABSENT 轉為 MATCH(全量結果:ABSENT 應從 15 降到不超過 4——確切
   數字待修法時重跑 L2-EQ 核實,不得先假設)。
4. **(L3)** 加了 `schema.params` 之後,本檔評估表 #1–#10 原有的 403/404
   分流結果(合法 id 但非本人擁有 → 403;不存在的 id → 404)必須逐筆維持
   不變——用本檔表格列出的既有測試組合重跑一次,確認狀態碼未被誤改成
   400 或反過來。
5. **(L4,僅 #11)** `requireAnyRole` 的角色檢查必須仍然先於 `adminGetMessage`
   執行,加 `schema.params` 不得把它排到角色檢查之後或之前產生時序副作用
   (Fastify 的 schema 驗證固定在 `preValidation`,早於 `preHandler` 陣列,
   需在實作時明確查證這個順序,不得假設)。
