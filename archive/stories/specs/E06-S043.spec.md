# E06-S043 — 同一 documentId 以不同 scopeKey 重新匯入會靜默改寫可見性

## Metadata
- Epic: E06 — Knowledge Ingestion & Indexing（衍生）
- Owner: Team B（domain）／Team A 開發
- Layer: Platform/Backend
- Priority: P0
- Story size target: 1–2 developer-days
- Story 來源: E06-S042 開發者主動回報,獨立審核者實測確認
- Parallel-safe: No — HARD 依賴 E04-S061、E06-S042

## 這條為什麼是重量級（分級理由）

同時命中「工作分級」的**兩條**觸發條件:觸及**資料可見性**,且失敗模式是
**靜默給出錯誤結果**。該節自己舉的例子(「授權範圍算錯導致召回率下降,使用者
只看到『查無資料』」)幾乎是本缺陷在 finance principal 那一側的逐字描述。

## 實測結果（獨立審核者,2026-09-02,非推論）

以同一 `documentId` 先後用兩個 scope 匯入,**兩個 store 都實跑過**:

```
in-memory store
  重匯前  finance 看到 1 筆, maintenance 看到 0 筆
  重匯後  finance 看到 0 筆, maintenance 看到 1 筆

sqlite-vec store（直接下 SQL 查 _vec 表,非從程式碼推論）
  第一次匯入 (dept:finance)      _vec: [{chunk_id: "shared-doc#0", scope_key: "dept:finance"}]
  第二次匯入 (dept:maintenance)  _vec: [{chunk_id: "shared-doc#0", scope_key: "dept:maintenance"}]
  每個 chunk_id 的列數           n = 1
  重匯後 finance 查詢             0 hits
  重匯後 maintenance 查詢          1 hit,chunkIds: ["shared-doc#0"]
```

**兩個方向同時發生,兩者都不報錯**:
- **未授權揭露**——maintenance 取得一份它從未被授權的文件的完整讀取權。
- **靜默資料遺失**——finance 失去一份它原本讀得到的文件,症狀與「查無資料」
  無法區分。

**技術顧問曾推測 sqlite-vec 會更糟**(`insertVec` 是純 INSERT,舊分片列可能
留著,導致兩個 scope 同時看得到)。**該推測經實測不成立**:`upsert()` 在
`insertVec` 之前先 `deleteVec.run(record.chunkId)`,是刻意且有註解的設計。
兩個 store 行為一致,「用哪個 store」不是授權決定。此段保留是因為「這個假設
被檢驗過並被推翻」本身是資訊。

## 根因

`chunkId` 是 `${documentId}#${ordinal}`(E06-S022,wave0),**沒有 scope 維度**;
兩個 store 都以 `chunkId` 為鍵做 upsert(`store.ts` 的 `rows.set`、
`sqlite-vec.store.ts` 的 delete-then-insert,均為 E04-S061,wave0)。
**缺陷早於 E06-S042 就存在於 main**;E06-S042 是第一個同時真寫入又以真 scope
查詢的呼叫端,使它第一次可觀察。

## 不是假設性需求

E06-S042 的 EVIDENCE 檔把觸發條件寫成「若『同一文件多 scope 共用』成為真實
需求」。**審核者對此提出反對,本檔採納其意見**:觸發它的不是某個未來功能,而是
**重新匯入這個尋常運維動作**——換模型後重建索引、修正文件內容、修正一次
scope 誤分類。這是近乎必然會發生的操作,不是推測。

## Scope In

**工程下限（技術顧問 2026-09-02 裁定,現在就能定）:**

1. 同 `documentId`、**不同** `scopeKey` 重匯 → **明確拒絕**,帶穩定 error code,
   **不寫入任何東西**(不得部分寫入後才失敗)。
2. 同 `documentId`、**相同** `scopeKey` 重匯 → **原子替換**:先刪除該 document
   的全部舊 chunk,再寫入新的。
   理由:新版本 chunk 數少於舊版時,舊版多出來的 chunk 會留在庫裡,而既有引用
   會指向已不存在的段落——這是同一個缺陷的第二張臉。**重匯測試必須涵蓋
   「chunk 數變少」的情形。**

## Scope Out（需使用者裁示,不得在本 story 內自行決定）

「把文件從 A 部門移到 B 部門」是不是合法操作?

若是,它必須是**獨立的、有稽核紀錄的顯式操作**,不能是「用另一個 scope 重匯」
的副作用。**在使用者裁示之前,一律拒絕**(即 Scope In 第 1 點)。

同理:是否允許一份文件同時屬於多個 scope,以及 `chunkId` 是否應帶 scope 維度,
都是產品／授權模型層級的決定,不在本 story 內回答。

## Functional Acceptance Criteria

層級標註依 `policies/TESTING_POLICY.md` 的 L0–L6;涉及 provider 保真度者另標 PF。

1. **(L3)** Given 已以 `dept:finance` 匯入 `doc-1`,When 以 `dept:maintenance`
   匯入同一個 `doc-1`,Then 拒絕並回傳穩定 error code,且 **finance 的可見性
   完全不變**(重匯前後查詢結果逐筆相同)。
2. **(L3)** 承上,Then **maintenance 看不到任何東西**——不得有任何部分寫入。
3. **(L3)** Given 已以 `dept:finance` 匯入 `doc-1`,When 以**相同** scope 重匯
   內容較短(chunk 數較少)的版本,Then 舊版多出來的 chunk **不存在於庫中**,
   且查詢不回傳指向已不存在段落的引用。
4. **(L3)** 替換必須是原子的:替換過程中失敗時,庫中不得留下新舊混合的狀態。
5. **(L5)** 上述行為在 **in-memory 與 sqlite-vec 兩個 store 上一致**。
   兩者若行為不同,「用哪個 store」就成了授權決定,那本身是缺陷。
6. **(L1)** 錯誤訊息說明這是 scope 變更被拒,並指出正確途徑,不得只說「匯入失敗」。

## Security / Authorization Acceptance

- 拒絕路徑必須 fail closed:寧可拒絕合法的重匯,不可接受會改變可見性的重匯。
- 錯誤訊息不得洩漏該 documentId 目前屬於哪個 scope——那本身是一則授權資訊。
- 既有的 partition-key 前置過濾(`AC-V6`)與 `assertNoScopeLeak` 必須逐字不變。

## 反向驗證（共同底線,不可省略）

把「不同 scope 重匯即拒絕」的判斷改成永遠放行 → **AC1 與 AC2 必須變紅**;
把原子替換改回「只覆寫、不刪除多餘 chunk」→ **AC3 必須變紅**。
還原後全綠。紅綠兩段輸出都要記進 EVIDENCE。

**注意**(2026-09-02 新增的規則):存在性斷言不算反向驗證。AC1 不能只斷言
「有拋錯」,必須斷言 **finance 重匯前後查到的結果逐筆相同**——可見性有沒有被
改動,才是這條 story 要守的量。
