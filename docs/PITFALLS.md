## 尚未寫進規則檔,登記在此(下次遇到再決定要不要升級)

### 坑 1:一個會在正確變更上變紅的守門,遲早會被放寬,然後就永遠不會紅了

「閉包檔數上限」提出後被自己的量測推翻:`E04-S069` 把閉包從 98 個檔案增加到 202 個,
同時修好了真正的問題;任何固定上限都會在那次**對的變更**上跳紅。換成 allowlist(每個檔案
必須落在明示的根之下)才對——它守的是**性質**(有沒有落在允許的根),不是**數字**(有幾個檔案)。

「恰好 N 個錯誤」這種釘數字的規則,同樣的理由已經出過第二次(型別錯誤數量門檻)。
**通則:守門的斷言要對著不變量,不要對著會隨著正常演化而改變的計數。**

### 坑 2:守門的「有沒有被接上」跟守門的「會不會紅」是兩件不同的事

`E06-S026` 的守門預設 `false`,靠一行程式碼打開;那行被刪掉後,81 條測試全綠——不是守門
沒抓到問題,是**守門根本沒被執行**,而外部看不出差別。Wave 1 的所有規則都在檢查「守門會不會紅」,
沒有一條檢查「守門有沒有被接上」。

下次寫帶開關的守門(feature flag、env 判斷式提早 return、conditional registration):**額外寫一個
檢查,斷言開關被移除時系統會失敗**(型別層的必填選項優於執行期測試,因為它涵蓋尚未寫出來的呼叫端)。

### 坑 3:發現而未登記的缺陷,從紀錄外面看跟沒發現一樣

`E04-S077`(全 app 不驗證路徑參數)、`E04-S078`(`GET /v1/health` 未登記進任何契約)在
`tools/contract-equivalence` 首次執行時就被列印出來,但只以散文形式躺在 `archive/ROADMAP_TEMP.md`,
直到收尾才被登記成 story。**已發現但未登記,和未發現,在紀錄上長得一模一樣。**

下次任何檢查工具**首次執行**:每一條偏離當場登記為 story 或 allowlist 條目(擇一),
兩者皆非則不得結案——不要讓它先躺在筆記裡。

### 坑 4:單一 CI job 把多個 gate 串成一條,紅燈就不再攜帶資訊

`ci.yml` 曾把 lint → typecheck → build → e2e → test 串成一個 `build` job:任何一步紅,
整個 CI 只有一個紅燈,分不出是型別壞了還是 e2e 起不來。結果是「CI 紅」長期存在卻沒人採取
行動——紅燈習慣性亮著之後就不再攜帶資訊(`main` 有 238 個 commit 五天沒推上去)。

下次拆 CI:**每個獨立性質的檢查(型別、lint、build、e2e、contract-gate)各自一個 job**,
让某一類紅燈不會被另一類淹沒;沒人必須通過的 job(allow-failure)是同一個病的變體,
等同於沒有 gate。

### 坑 5:契約等價檢查的正規化規則本身可能藏住一個方向的盲點,盲點要明說不要埋

`tools/contract-equivalence` 比對契約與實際 route 時,`querystring` 的 `additionalProperties`
在 OpenAPI `parameters:` 裡沒有對應鍵,所以刻意不因這個欄位判分歧——這個放行**只會讓工具更寬鬆**
(可能藏住「契約其實想放行未列出的查詢參數」這件事,目前無此案例)。

下次寫任何等價/正規化比對工具:每一條刻意放寬的正規化規則,**寫明它可能藏住什麼、藏住的方向
是更嚴還是更寬**,不要只寫「這個欄位不影響驗證」就跳過。
