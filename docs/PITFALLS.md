## 尚未寫進規則檔,登記在此(下次遇到再決定要不要升級)

### 坑 1:一個會在正確變更上變紅的守門,遲早會被放寬,然後就永遠不會紅了

「閉包檔數上限」提出後被自己的量測推翻:`E04-S069` 把閉包從 98 個檔案增加到 202 個,
同時修好了真正的問題;任何固定上限都會在那次**對的變更**上跳紅。換成 allowlist(每個檔案
必須落在明示的根之下)才對——它守的是**性質**(有沒有落在允許的根),不是**數字**(有幾個檔案)。

「恰好 N 個錯誤」這種釘數字的規則,同樣的理由已經出過第二次(型別錯誤數量門檻)。
**通則:守門的斷言要對著不變量,不要對著會隨著正常演化而改變的計數。**

### 坑 2:守門的「有沒有被接上」跟守門的「會不會紅」是兩件不同的事

`E06-S026` 的守門預設 `false`,靠一行程式碼打開;那行被刪掉後,81 條測試全綠——不是守門
沒抓到問題,是**守門根本沒被執行**,而外部看不出差別。Wave 1 的所有規則都在檢查「守門會不會紅」,
沒有一條檢查「守門有沒有被接上」。

下次寫帶開關的守門(feature flag、env 判斷式提早 return、conditional registration):**額外寫一個
檢查,斷言開關被移除時系統會失敗**(型別層的必填選項優於執行期測試,因為它涵蓋尚未寫出來的呼叫端)。

### 坑 3:發現而未登記的缺陷,從紀錄外面看跟沒發現一樣

`E04-S077`(全 app 不驗證路徑參數)、`E04-S078`(`GET /v1/health` 未登記進任何契約)在
`tools/contract-equivalence` 首次執行時就被列印出來,但只以散文形式躺在 `archive/ROADMAP_TEMP.md`,
直到收尾才被登記成 story。**已發現但未登記,和未發現,在紀錄上長得一模一樣。**

下次任何檢查工具**首次執行**:每一條偏離當場登記為 story 或 allowlist 條目(擇一),
兩者皆非則不得結案——不要讓它先躺在筆記裡。

### 坑 4:單一 CI job 把多個 gate 串成一條,紅燈就不再攜帶資訊

`ci.yml` 曾把 lint → typecheck → build → e2e → test 串成一個 `build` job:任何一步紅,
整個 CI 只有一個紅燈,分不出是型別壞了還是 e2e 起不來。結果是「CI 紅」長期存在卻沒人採取
行動——紅燈習慣性亮著之後就不再攜帶資訊(`main` 有 238 個 commit 五天沒推上去)。

下次拆 CI:**每個獨立性質的檢查(型別、lint、build、e2e、contract-gate)各自一個 job**,
让某一類紅燈不會被另一類淹沒;沒人必須通過的 job(allow-failure)是同一個病的變體,
等同於沒有 gate。

### 坑 5:契約等價檢查的正規化規則本身可能藏住一個方向的盲點,盲點要明說不要埋

`tools/contract-equivalence` 比對契約與實際 route 時,`querystring` 的 `additionalProperties`
在 OpenAPI `parameters:` 裡沒有對應鍵,所以刻意不因這個欄位判分歧——這個放行**只會讓工具更寬鬆**
(可能藏住「契約其實想放行未列出的查詢參數」這件事,目前無此案例)。

下次寫任何等價/正規化比對工具:每一條刻意放寬的正規化規則,**寫明它可能藏住什麼、藏住的方向
是更嚴還是更寬**,不要只寫「這個欄位不影響驗證」就跳過。

### 坑 6:同型第三次就該升類,我們是第五次才寫進規則

同一種病——**harness 沒有真的走過它宣稱要測的機制**——在本 repo 至少出現五次才被寫成規則:
E06-S026 的守門預設 `false`(坑 2)、E06-S042 的 `hits.length > 0` 在 top-K 下永遠不紅、
E06-S043 的 `.rejects` 排在資料比對之前所以資料比對從未執行、E04-S079 的 `--expect-message`
比對不到被 JSON reporter 截斷的 diff、以及 2026-09-04 的 `accept:phase1` 在 0 個場景時
與全過無法區分。前四次各自被當成個案修掉。

範式來源專案 C(nightmare-assault)的做法是**同型第三次即升類**:第三次出現時不再當個案修,
自動開一張「這一類機制系統掃一遍」的工單,或改 gate。

**待決定(下次 retro)**:要不要把「同型第三次即升類」寫成規則檔的一條,以及「同型」由誰認定。
反對意見先寫在這:同型的判定本身就是主觀的,寫成規則可能變成「每個 bug 都要先論證它不同型」。

來源:技術顧問 ai-km-3a 2026-09-04 轉述專案 C 的實戰,明示「不現在改規則,回顧時決定」。

### 坑 7:收斂指標用「人填的完成數」,會被新工作稀釋,而且沒有人在驗證它

`docs/01-roadmap.md` 的現況表目前數「回填 N / 12 資料夾」。這個數字有兩個問題:
它是**人填的**(填錯沒有東西會紅),而且它衡量的是**做完幾件事**,不是**系統現在能做到什麼**。

專案 C 用的兩個指標都是機器算出來的,而且方向單調:
- 「假玩家 / e2e 能走到第幾階」(只升)
- 「見證器未標記的測試數」(只降)

本 repo 已經有一個現成的機器來源:`pnpm accept:coverage` 印出每個資料夾各自跑了幾個場景,
**那個清單是算出來的,不是填的**。另一個是「目前整合點的 `@e2e` 能不能由人走到」——
那本來就是 `/integrate` 的核心問題。

**待決定(下次 retro)**:現況表的「回填進度」欄要不要改成引用 `accept:coverage` 的輸出,
以及要不要加一欄「目前整合點的 @e2e:使用者確認過 / 未確認」。

來源:同上。

### 對照組:整合點與回填的先後順序

本 repo 的順序**剛好相反**:I1 先綠(2026-09-03,使用者親眼確認引用),再回填 12 個 phase-1。

兩邊都還沒跑完,現在無法說哪個對。**留著當對照**,下次 retro 有兩組資料時再比:
先綁整合點會不會讓回填的形狀被整合點的敘事帶偏(本 repo 的 `integration.steps.ts` 已經
佔用了一批 PDF ingestion 的句子,05-ingestion 的 worker 要繞開它寫——這算是一個早期訊號)。

### 坑 8:「預期輸出」寫的是推出來的數字,而那條指令從來沒被跑起來過

`standalone.json` 是 `/phase-done` 的「單獨執行 exit 0」實際讀的那份清單,也是 `_world.ts`
的 `runStandalone()` 讀的那份。它的十條 cucumber 指令寫成
`pnpm --filter @ai-km/features accept -- --tags '…'`,而 pnpm 11.9.0 把 `--` 原樣轉給
cucumber-js,cucumber 從那裡停止解析選項、把 tag 運算式當成**檔案路徑**開啟:

    path: '…/features/@retrieval and @standalone and not @manual'
    [ERR_PNPM_RECURSIVE_RUN_FIRST_FAIL] … Exit status 1

**十條全錯,包含參考實作 06-retrieval 那條。** 也就是說在 2026-09-04 之前,
「單獨執行」這一項驗收**沒有任何一次真的成立過**,而 `features/06-retrieval/FEATURE.md`
的「單獨執行」段白紙黑字寫著預期輸出 `9 scenarios (9 passed)`。

出處(技術顧問 ai-km-3a 自陳):當時只用 cucumber 直跑過 06,**換成 `accept -- --tags`
形式之後沒有再經 pnpm 跑一次**,就把那個數字寫進 FEATURE.md 當「預期輸出」。

這是 `GHERKIN_WORKFLOW.md` §5.3(**機制要用量的,不要用讀的**)在**同一個人寫下那條規則
的隔天**再犯一次,而且犯在最不容易被發現的地方:一個從來沒被執行過的驗收指令,
和一個通過的驗收指令,在紀錄上長得一模一樣(坑 3 的另一面)。

**下次**:任何寫進文件當「預期輸出」的字串,必須是**從那條指令的實際輸出貼過來的**,
不是從別的跑法推出來的。指令形式改變(換 runner、加 wrapper、改 pnpm 版本)= 那個
預期輸出作廢,要重跑一次才能繼續宣稱。

**連帶修掉的第二件事**:原本的 `expect` 有幾條是精確的 `"N scenarios (N passed)"`。
那是坑 1 的形狀——每加一條場景就假紅一次,然後被靜默放寬。已一律改回寬鬆的
`scenarios (`(它本身就排除掉零,因為 cucumber 印 `0 scenarios` 沒有括號那半),
而「每個資料夾至少一條且全過」改由 `pnpm accept:coverage` **算出來**守。

### 坑 9:一個沒有任何場景用過的通用步驟,壞了多久都不會有人知道

`common.steps.ts` 的 `the {string} plugin is registered on a bare server and the server
becomes ready`——cucumber expression 宣告一個 `{string}`,handler 卻寫成 0 個參數。
cucumber 比對兩者的 arity,不合就判該步驟失敗:

    function has 0 arguments, should have 1 (if synchronous or returning a promise) or 2 (if accepting a callback)

錯在**執行期**,`typecheck` 與 `lint` 都看不到。而它是 ADR 0007 §5 要求的
「走真實 `register()→ready()` 從父實例斷言 decoration」的通用入口——也就是說,
**這個 repo 最想機械保證的一件事,它的通用入口是壞的**。

它沒被發現的原因很簡單:**在此之前沒有任何 `.feature` 用過它**(唯一的參考實作
06-retrieval 自訂了自己的版本)。11 個平行回填同時開工時,五個 worker 各自踩到、
各自自訂同義句繞開、各自寫進「待協調」,才浮出水面。

這是坑 2(守門「會不會紅」與守門「有沒有被接上」是兩件事)的極端形態:**這裡連接上都沒有**。

**下次**:任何寫進 `common.steps.ts` 的通用步驟,**當場配一個最小場景真的去用它一次**
(用完可以刪,但要跑過)。一個沒有任何呼叫端的共用工具,和一個壞掉的共用工具,
從外面看一模一樣。

### 坑 10:閒置機器上跑二十次全綠,不是那個競態不存在的證據

2026-09-04,`file-chat-entry.spec.ts` 在 CI 紅了一次(330 passed / 1 failed)。協調者比對
發現「該 commit 相對上一個綠的唯一差異是一支 e2e job 根本不跑的 Node 腳本」,由此判定
**是 flake**。前半的推論沒錯——它確實不是那個 commit 造成的;**錯在從「不是這個 commit
造成的」滑到「是測試不穩定」**,那一步沒有根據。

實際是產品競態(見下)。而重做反向驗證時量到的東西才是這條坑的重點:

| 條件 | 結果 |
|---|---|
| 帶著修正 | 10/10 綠、20/20 綠 |
| **還原修正、機器閒置** | **20/20 也綠——沒有重現** |
| 還原修正、6 個 busy loop 壓 CPU、8 個 playwright worker | **1/25 紅**,訊息與 CI 逐字相同 |

只跑第一輪(閒置 20/20)就結案的話,會第二次把它判成 flake,**而且這次還有「我自己驗過」
當背書**——比第一次更難推翻。

**下次:凡是懷疑競態的反向驗證,閒置全綠只證明「閒置時沒看到」。** 必須在**負載下**重現:
6 個 busy loop + 8 個 worker(或等效的 CPU 爭用),跑 **≥25 次**,**紅至少一次且訊息與
原始症狀逐字相同**才算重現。配方與指令寫在協調者的合併程序檔。

順帶,這個 bug 本身也是一條通則:**把一個 live 的瀏覽器物件(`FileList`、`FormData`、
event target)傳進 React 的 state updater**,updater 會延後執行,而那個物件可能在延後期間
被它的擁有者就地清空。要在排隊**之前**同步快照。同型在本 repo 一次找到三處。

**還有一半要記**:修好之後,守著它的是那條 e2e spec,而還原修正後它只有約 4%(1/25)會紅
——**那是機率性守門,不是確定性的**。一個 4% 會響的守門,和一個不會響的守門,在單次 CI 上
分不出來。確定性的版本是在單元層給 handler 一個「呼叫後立刻被清空的 live FileList 替身」,
斷言 state 收到的陣列長度仍是 1;它對著會變的量,而且不靠併發。
**機率性守門要當成「還沒有守門」來排後續工作,不是當成已經守住了。**

### 坑 11:用會變的顯示文字當 worker 的識別碼,會把活的 worker 判成死的

2026-09-04,協調者用 orca-cli 派工後要找回自己派出去的兩個 worker,依 spawn 時給的
`--title` 前綴去 `orca terminal list` 裡 grep,**兩個都回 `NOT FOUND`**——而它們活得好好的,
正在做事。

原因:**`--title` 是 agent 自己會改的顯示文字**,它跟著 agent 當下在做的事變:

    ✳ AI_KM 專案工單  →  ◐ AI_KM 專案工單  →  ◑ .orca-brief/TASK.md

這是坑 1(守門的斷言要對著不變量,不要對著會隨正常演化改變的量)與 P-33(對著不變量,
不對著代理指標)在**派工通道**上的同一個形狀:拿一個會變的東西當識別碼。

而它的失敗模式特別壞:**假陰性**。「找不到」看起來像「worker 死了」,合理的下一步是重派——
於是同一份工作跑兩份,或是好好的成果被當成失敗丟掉。

**做法**:
- **存活與定位一律用 `worktreeId` 的路徑尾段比對**,那是不變量(worktree 路徑在它的生命週期內
  不會變)。**永遠不要用 title 判斷 worker 在不在。**
- 每個 worktree 有**兩個** terminal(agent 那個 + 一個裸 shell),挑 title **不是** `pollux@…`
  開頭的那個。
- 三個專案(AI_KM、llm_learning-cards、nightmare-assault)都用 Orca 派工,這條通用。

### 坑 12:批次字串修改「跑完 exit 0」不等於「改到了」

同日,協調者用字串比對批次修正兩份已派出的工單裡一句錯誤指示。指令 exit 0、沒有任何錯誤,
但其中一份的目標文字**跨了兩行**,比對沒命中,**殘留的還是舊指示**——而那份工單正在被一個
worker 讀。是事後 `grep` 才發現的。

這是 P-15(「過濾後空輸出一律視為失敗」)的同一族:**沒有壞消息 ≠ 好消息**。
`str.replace()` 找不到目標時不報錯,它安靜地回傳原字串;`sed` 也一樣。

**做法**:任何批次修改(多檔、字串比對、正則)之後,**用一個會因為「沒改到」而失敗的檢查
收尾**——`assert old in s` 再 replace,或改完 `grep` 舊字串應為 0 命中並確認退出碼。
把那個 grep 的輸出貼進紀錄,不要只說「改好了」。

### 坑 13:同步共用工具之前先 diff,而「程式與設定沒分離」會讓 `--check` 與「填好它」互斥

2026-09-04,範式模板出了 `sync-gates.sh`:把守門腳本複製進各專案、每檔檔頭寫 SOURCE 版本、
`--check` 逐位元比對(手改一字即紅)。三個專案要同步。

協調者在派工單之前先提了一條:**「先 diff,再 sync」**——理由是本 repo 的 `check-step-dup.ts`
是本地演化過的(規則從代理指標換成不變量,兩個方向都反向驗證過),而模板**當天才**收到那個
更正;sync 跑在模板落地之前,會**用舊版蓋掉新版,而且是靜默的**:內容降級了,檔頭 SOURCE
版本號還是新的,看起來像升級。接著 `--check` 會把那個降級**鎖住**。

**同一天,這條在兩個專案各擋下一次真實的損害。** 模板 1.1.x 的三支其實都是舊子集:
`check-doc-links` 的圍欄剝除太天真(巢狀 info-string 圍欄裡的連結誤報)、
`check-boundaries` 的落點表是**空樣板**(sync 會把各專案填好的內容清空)、
`check-standalone` 掉了 `--manifest`、掉了「0 條就是掃描器壞了」的守衛、掉了清理。

**根因不是版本落後,是結構**:**程式與設定沒有分離**。sync 覆蓋整個檔 + `--check` 逐位元
比對 ⇒ 任何專案都**不可能同時**「把落點表填好」與「`--check` 綠」——兩個要求互斥。
修法是把設定抽出去(`boundaries.owners.json`),sync 對設定檔只在缺時複製,`--check` 跳過它。

**通則,兩條:**
1. **同步任何共用工具之前,逐支 diff,以「超集」為準**;本地比較新的**先送回上游**再同步。
   「版本號比較新」是代理指標,**內容是不是超集才是不變量**——這是坑 1 在版本管理上的形狀。
2. **一個會被覆蓋同步、又被逐位元 check 的檔案,裡面不能有「各專案要自己填」的東西。**
   看到這種結構就是設計錯了,不是使用方式錯了。

### 坑 14:`.feature` 的刻意紅對 CI 隱形,`*.test.ts` 不會——所以「測試先紅」階段只有前者能進 main

2026-09-04,**協調者(我)在合併 02-authorization phase-2b 時踩到**。

`GHERKIN_WORKFLOW` §3 的生命週期是:測試 agent 先寫 steps + 單元測試(**紅**)
→ 開發 agent 寫實作(綠)→ 反向驗證 → `/phase-done`。**合併點在綠之後,不在紅之後。**
我在紅的階段就合併了。

為什麼沒有當場發現:**兩半的可見度不一樣**。

| | 刻意的紅 | CI 看得到嗎 |
|---|---|---|
| `.feature` 的 `@phase-2` 場景 | 有 | **看不到**——`accept:phase1` 只選 `@phase-1`,accept job 的三步都碰不到它 |
| `services/**/*.test.ts` | 有 | **看得到**——vitest **沒有這層 tag 過濾**,`turbo run test` 直接紅 |

所以我合併之後 Gherkin 那半一切正常,是推上去再跑 gate 才看到
`Tests 2 failed | 109 passed`,也就是 CI 的 `lint-typecheck-unit` 紅。

**處理方式:`git revert -m 1`,不是 `test.fails()`、不是 `skip`。** 讓它綠會把
「main 是綠的」從「實作都對」退化成「我們把紅的藏起來了」——坑 4 講紅燈習慣性亮著
就不再攜帶資訊,而把紅藏起來會走到同一個結局,而且更難發現。分支完整保留,
開發階段做完連同實作一起合併。

**副作用也要記**:revert 會把該分支上**與紅測試無關的順帶修正**一起帶走
(那次是一行 tag 位置的修正,revert 後 coverage 立刻紅)。revert 一個 merge 之後
要重跑全套 gate,不要假設「回到之前的狀態」就等於「回到綠」。

**通則**:「測試先紅」階段,**`.feature` 可以進 main(tag 過濾讓它對 CI 隱形),
`*.test.ts` 不可以**。要判斷「這個刻意的紅會不會被 CI 看到」,看的是那個測試框架
**有沒有 tag / 標記層讓 CI 選擇性略過**,不是看它紅得多合理。

### 坑 15:cucumber 步驟文字裡的 `/` 是語法,不是字元——比對不到時它「建議一個新步驟」,不報錯

`05-ingestion/phase-2` 的測試 agent 在 Then 的步驟文字裡寫了 `06-retrieval/phase-3`
(一個資料夾路徑,純粹是給人看的)。cucumber-expressions 把 `retrieval/phase` 讀成
**替代詞語法**(`a/b` = 「a 或 b」),於是那句話的實際比對目標變成了另一個字串,
和 step 定義對不起來。

**危險的不是它壞掉,是它壞掉的方式**:cucumber 不會說「你的步驟文字有語法問題」,
它把該步驟判為 **undefined**,然後**印出一段建議你新增的 step snippet**——長得跟
「你還沒實作這個步驟」一模一樣。在「測試先紅」階段,undefined 本來就是預期會看到的東西,
所以這個訊號被自己的背景噪音蓋掉了。

修法是轉義(`06-retrieval\\/phase-3`)。

**通則**:步驟文字裡出現 `/`、`{`、`}`、`(`、`)` 時,先確認你要的是字元不是語法。
更廣的一條:**一個「比對不到」的機制若把失敗呈現成「你還沒做」,它在紅燈階段就是隱形的**
——這和坑 14(`.feature` 的刻意紅對 CI 隱形)是同一個形狀的兩個實例:
**訊號與噪音長得一樣時,訊號等於不存在。**

### 坑 16:守門不跑等於沒有守門——`RETURN TO SENDER` 的 grep 存在了整整一個範式,一次都沒跑過

2026-09-04、09-05 連續兩輪,開發 agent 在 `feat` commit 裡動了共用檔:
`02-authorization/phase-2b` 動 `features/steps/integration.steps.ts`、
`07-generation/phase-2` 動 `apps/api/package.json`。兩次我都在事後才知道
(agent 主動回報),兩次都判「內容無害」接受了。

我當時把它歸類成「規則太嚴,該放寬」,還寫了一條建議放寬的判準送給顧問。
**顧問查完 commit 之後指出真正的問題不在規則,在守門沒跑**:

`GHERKIN_WORKFLOW` §6 底下本來就有一行

```bash
git diff --name-only main...<branch> | grep -E '\.test\.ts$|^features/steps/|\.feature$' && echo "RETURN TO SENDER"
```

而 `a2efe28` 改的 `features/steps/integration.steps.ts` **本來就會被這個 grep 抓到**
——它不只是共用檔問題,是開發 agent 動了 `features/steps/**`,兩條都違反。
**那個 grep 從寫下來到那天為止,沒有任何一次合併真的跑過它。**

我提的放寬判準本身也錯:「移除它 `typecheck` 會紅」對開發 agent 寫的**每一行**都成立
——任何 import 都是自己實作選擇的機械後果。它跟契約那條判準形狀不同:
契約判準看的是**對呼叫端**的後果,這條看的是**對自己**的後果,後者篩不掉任何東西。
真正需要有人簽名的判斷是「composition root 要不要新增一個 workspace 相依」,
而那正好就是我想放行的那一行。

**通則,而且是這份檔案裡最貴的一條**:發現規則被反覆違反時,先問「守門有沒有跑」,
再問「規則要不要改」。**順序反過來,就會用一次放寬去掩蓋一個從來沒有執行過的檢查**
——而放寬之後,連「它本來會抓到」這個事實都消失了,沒有人再有機會發現守門其實沒接上。

這與坑 2(守門的「有沒有被接上」跟「會不會紅」是兩件不同的事)是同一個家族的第三種:
**接上了、也會紅,但沒有人按下去。**

落地:§6 的 grep 已擴充涵蓋共用檔,並加上「對開發 agent 的分支在合併前**必跑**,
輸出貼進 merge commit body;有輸出就退件,不接受『內容無害』」。

### 坑 17:`cmd | tail` 之後的 `$?` 是 `tail` 的,不是 `cmd` 的——用它判斷守門會得到相反的結論

2026-09-05,顧問要我確認兩支剛同步進來、但沒接進任何 script/CI 的守門
(`features/scripts/check-boundaries.ts`、`check-standalone.ts`)現況紅不紅。我跑:

```bash
tsx scripts/check-boundaries.ts 2>&1 | tail -25; echo "EXIT=$?"
```

看到 `✗ 找不到 …owners.json` 的訊息,**而 `EXIT=0`**。差一點就記成「它印了錯誤卻靜默通過」
——那會是坑 2(守門接上了但不會紅)的教科書案例,而且我會據此寫一條完全錯誤的
DECISIONS_NEEDED 給顧問。

**那個 `0` 是 `tail` 的 exit code。** bash 的 `$?` 給的是管線**最後一個**指令的狀態。
重新用重導向到檔案、再取 `$?`,量到的是真正的 **1**——兩支都會紅,只是紅的原因
不是它們要抓的東西(見 `docs/DECISIONS_NEEDED.md` #21/#22)。

**通則**:`$?` 只在你確定它屬於哪一個行程時才有意義。要量一支腳本的 exit code:

```bash
cmd > out.log 2>&1; echo "EXIT=$?"   # ✅ 量到 cmd 的
cmd 2>&1 | tail -25; echo "EXIT=$?"  # ❌ 量到 tail 的(永遠是 0)
```

(`set -o pipefail` 或 `${PIPESTATUS[0]}` 也可以,但重導向最不容易寫錯,而且輸出還留著。)

**這條與 §5.3 的關係**:§5.3 說「機制要用量的不要用讀的」。這次我**確實去量了**,
量出來的數字還是錯的——因為我量的不是那個東西。所以 §5.3 要再加一句:
**量的時候要確定你量的是那個東西。** 一個測錯對象的量測,比從原始碼推斷更危險:
它帶著「我跑過了」的權威,而那份權威剛好指向反方向。

(§5.3 補那一句要動規則檔,已由顧問列給使用者等一句話;本條先記在這裡,這是協調者的檔。)

### 坑 18:兩個設定檔,一個缺了會爆、另一個缺了靜靜回傳空的——後者讓「我設定好了」與「我沒設定」長得一樣

2026-09-05 接 `check-boundaries.ts` 時,**我在派工單裡把路徑寫錯了**:我叫 agent 去改
`features/scripts/boundaries.allow.json`。工具實際讀的是 `<repo-root>/scripts/boundaries.allow.json`
(`ROOT` = `git rev-parse --show-toplevel`)。

**危險的不是我寫錯,是它壞掉的方式**:

| 設定檔 | 缺席時 |
|---|---|
| `owners.json` | **硬錯**:印出「找不到 …owners.json」+ 格式範例,exit 1 |
| `allow.json` | **靜默回傳 `[]`** |

所以 agent 把 11 條有理由的例外寫進**錯的那個檔**之後,工具照樣印
「**允許例外 0 條**」並列出全部 52 條違規——輸出與「這個專案根本沒有 allow list」
**一個字都不差**。它是靠把同樣的內容搬到 repo 根再跑一次、看到違規從 52 掉到 1,
才證明檔案位置是那個變因的。

**這不只是路徑寫錯**:一個設定檔缺席時靜默降級成「空設定」,等於讓
**「我設定好了但沒生效」與「我沒設定」產生完全相同的輸出**。
在守門這個場景裡那特別糟,因為兩者的正確反應相反——前者要修路徑,後者要寫設定。

**通則**:接一個吃設定檔的工具時,**先故意把設定檔改壞或改名,確認它會抱怨**。
不會抱怨的那個設定檔,你永遠不知道它有沒有被讀到。這是坑 2(守門有沒有被接上
≠ 會不會紅)在**設定層**的同一個形狀:**設定有沒有被讀到 ≠ 設定的內容對不對。**

(附帶:`owners.json` 那半做對了——缺席時硬錯而且印出格式範例。同一支腳本裡兩個設定檔
兩種行為,而較危險的那個剛好是安靜的那個。)

**第三種,同日出現(2026-09-05):讀到了,但讀到的是別人的。**

`llm-learning-cards` 用模板 1.4.0 唯讀跑**我們這份** `owners.json`,得到
`scanned=0`、**0 / 248 檔對到落點**;我們用 1.2.2 跑**同一份設定**,得到
**358 檔全部對到、exit 0**。同一份設定,兩個數字,而且**兩種可能的後果相反**:
錯的是舊版 → 我們現在的綠是假的;錯的是新版 → 升版會把守門變成永遠不響。
所以那段時間 roadmap 上寫的是「**這條沒解不升版**」。

原因不是兩版解析不同,是**設定檔搜尋順序**:`GATES_CONFIG_DIR` > 腳本自身目錄 >
`<root>/scripts`。對方從**模板路徑**跑、沒設 `GATES_CONFIG_DIR`,於是**靜默讀了模板自己的
範例 `owners.json`**——248 個檔當然全不在落點。設了之後兩版逐字相同。

所以這一格的三種形態是:

| | 設定 | 輸出看起來 |
|---|---|---|
| 一 | 沒被讀到(路徑錯) | 與「沒有設定」一模一樣 |
| 二 | 沒被讀到(檔案不存在) | `allow.json` 靜默回 `[]`;`owners.json` 硬錯 |
| **三** | **讀到了,是別人的** | **一份完全合理、但描述另一個專案的世界** |

第三種最難:輸出**不是空的、不是錯誤**,它是一份**看起來完全正常的報告**,
只是在講另一個 repo。**沒有任何數字會自己告訴你這件事。**

擋法(1.4.1 已收):**每支守門第一行印出它實際讀到的設定路徑。**
一行 log 就讓三種形態都當場現形——這比任何「記得設環境變數」的規則都可靠。

### 正例 1:同一批違規分成三類,只上報真的那一類——以及「兩種說法只能留一種」

這份檔案幾乎都是踩到的坑。這一條是相反的:一件**做對了**的事,記下來當形狀。

2026-09-05 `check-boundaries` 第一次真的跑起來,吐出 **58 條違規**。起草的 agent 沒有把
58 條一起丟給我,而是分成三類:

| 類 | 內容 | 它怎麼處理 |
|---|---|---|
| 真的越界 | `packages/permissions` 被 6 個非 `02` 的資料夾 import | **上報**——並指出這其實是「這個 package 的定位沒人拍板過」,不是誰寫錯 |
| 架構故意要的 | 服務鏈 `07→04`、`07→06`、`05→04`、`05→06`、`06→04` | 說明是 ADR 0007 的 in-process 主路徑,**該進 allow list 附理由**,不是缺陷 |
| **它自己造成的** | `06→02` 的 11 條 | **主動標明**「這是我把 `services/retrieval/src/authorization/` 切給 02 造成的人為產物」 |

第三類是關鍵。那 11 條**看起來**跟真違規一模一樣,而且數量最多——混進「我抓到 58 條問題」
會讓報告顯得更有價值。它沒有這樣做。

**但故事有第二半,而第二半才是這條的重點。**

下一輪把那條邊寫進 `allow.json` 時,理由欄寫的是「這是設計的核心,不是越界」——
與上一輪的「我造成的人為產物」**是兩種不同的說法**。技術顧問審核時指出:
**兩種說法只能留一種。**

兩種其實都對,只是層次不同:它**確實**是所有權線造成的(所以不是有人越界),但那條線
是顧問裁定的(02 確實擁有那支檔案的行為),所以它是**一條要長期存在、有理由的例外**,
不是一個等著被消掉的暫時產物。已在 `allow.json` 的理由欄把兩層寫在一起,並寫明
「要消掉它只有一條路:把 `scope.ts` 搬出 `services/retrieval`,而那是獨立的重構決策」。

**通則兩條**:
1. 一批違規先分「真的 / 故意的 / 我自己造成的」三類,只上報第一類——
   把後兩類混進去會讓報告看起來更有份量,而那正是它不該有的份量。
2. **同一件事在兩個地方有兩種說法時,不管兩種是不是都對,都要收斂成一種。**
   紀錄的價值來自後人讀到時只有一個答案;兩個並存的答案等於沒有答案,
   而且後人不會知道要去找另一個。

### 正例 2:整合點第一次把五份各自綠的規格放進同一個 run,當場抓到它們互相矛盾

2026-09-05,I2 的五個 phase 全部 `done`——每一個都跑過 `/phase-done` 的四項核心、
每一個都由另一個 session 獨立驗收、每一個的反向驗證都紅在決定性的量上。**五次全綠。**

然後 `/integrate I2` 第一次把它們放進同一個 cucumber run,結果 **26/28**,兩條紅:

1. I2 的整合場景要求「換部門的人拿不到 `eng` 的文件」,但 **ADR 0014 明文裁定 I2 期間
   每個人都拿固定 `dept:eng`**——而 `03-conversation/phase-2.feature` 自己**斷言相反的事**。
   **兩份規格對同一件事各說各話。**
2. 問一個文件裡沒有的主題仍然拿到引用(`retrieve()` 沒有相似度門檻)。

**沒有任何一次 `phase-done` 會發現第 1 條**,因為它不是任何單一 phase 的缺陷——
它是**兩份規格之間**的矛盾,而 `phase-done` 一次只看一個 phase。

時序解釋了它怎麼長出來的:I2 的整合檔寫在 **ADR 0014 之前**,而 ADR 0014 是**為了解除
I2 的阻塞**才立的。立它的時候沒有人回頭看整合檔還寫著什麼。

**通則(技術顧問 2026-09-05 定):phase 各自綠不證明規格之間一致,只有把它們放進
同一個 run 才會。** 這是整合點存在的理由,不是它的失敗——一個從來不會紅的整合點,
跟一個從來不會紅的守門一樣沒有價值(坑 2、§5.2)。

**兩個附帶的形狀也記下來:**

- **檔頭說了一件它不證明的事。** I2 檔頭原本寫 "the seam … exists end to end
  **and fails closed on scope**",而它根本沒有(也不可能)證明後半句。已改掉。
  這與 `createMessage` 的 TRANSITIONAL 段(ADR 0017)是同一類:**散文說謊沒有機械守門會抓**。
- **修法是「搬」,不是「放寬」也不是「硬修」。** 跨部門那條搬到 I3(那本來就是 I3 的定義),
  門檻那條搬到真模型的 phase(今天的 embedding 是 feature hashing,分數沒有語意,
  **對它校準出來的門檻是假調參**)。兩邊各留一條**會在未來變紅**的場景取代它們
  ——斷言的**值**在那天會變,所以它是真的移除條件,而不是 ADR 0014 那種空保證。
