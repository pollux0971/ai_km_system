# E01-S003 — 登入成功後 return-url redirect

- 狀態:DONE
- Branch:story/E01-S003-login-return-url-redirect
- 日期:2026-08-13

## Scope 說明

本 story 只負責「登入成功後導向 returnUrl」這一件事:讀取 `/login` 頁面
query string 的 `returnUrl`、驗證其安全性(防 open redirect)、成功登入後
導向該處(不存在則導向 `/`)。**不**負責「未登入使用者被導向 `/login` 時
附加 returnUrl」——那需要 (app) zone 的 session gating,屬於 E01-S004
範圍;本 story 的測試直接建構帶 `returnUrl` 的 URL 來驗證(模擬 S004 未來
會做的事),不等待 S004 完成。

## 變更檔案

  allow-list 檢查(必須是單一 `/` 開頭的相對路徑,拒絕
  `//`、`/\`、含 `://`、含控制字元的值),防止 open redirect。

### Security / Authorization Acceptance

| AC | 狀態 | 說明 |
|---|---|---|
| 對外輸入 schema/content validation | ✅ | `returnUrl` 是使用者可控的外部輸入(query string),`sanitizeReturnUrl` 做 allow-list 驗證,非 blacklist——這是本 story 的核心安全行為,即「不得讓 client 端邏輯導向未經驗證的外部目的地」的具體落實 |
| Authorization 在敏感操作前完成 | N/A | 導向目的地本身不是敏感操作;目的地頁面自身的 authorization 由該頁面所屬 story 負責 |
| Deny Wins | ✅(以「預設拒絕、只允許明確合法格式」實現) | 任何無法確定安全的 `returnUrl` 一律 fallback 到 `/`,不嘗試「盡量猜測合法意圖」 |

**Open redirect 為何被視為本 story 的 security AC,而非額外加戲**:
`returnUrl` 是使用者/攻擊者可完全控制的輸入,若未驗證直接傳入
`router.push()`,登入成功的使用者可能被導向惡意網站(釣魚)。這正是
ATOMIC_STORY_BOUNDARIES.md Security Boundary「對外輸入視為不可信」與
Frontend/UX Boundary「Client 不得自行推導比 server 更寬鬆的 permission」
背後同一類風險(未驗證信任外部輸入),故列為本 story 必須覆蓋的
security-negative 測試,而非本可省略的加分項。

## Assumptions / 計畫外事項

1. **`page.tsx` → `login-form.tsx` 的檔案分割**是 Next.js
   `useSearchParams()` 的硬性要求(需要 Suspense 邊界),非自選重構;
   純屬完成本 story AC 所必需的最小結構調整,元件對外行為(路由、URL)
   不變。
2. **修正 S002 既有 E2E 測試的斷言方式**:原本斷言登入成功後
   「登入成功。」文字持續可見,但本 story 讓成功登入後立即
   `router.push()`,在真實瀏覽器中該文字的可見時間變得不可靠(race)。
   改為斷言導向後的結果(URL 變成 `/`、首頁標題可見)。元件測試
   (`login-form.test.tsx`,`next/navigation` 為 mock、不做真實導覽)仍
   穩定斷言「登入成功。」文字本身有渲染,兩者互補,沒有測試覆蓋率的
   淨損失。
3. **`returnUrl` query string 參數名稱**選定為 `returnUrl`(story
   標題原文用詞);未來 S004 若要「未登入時導向 `/login` 並附加
   returnUrl」,應延用此參數名稱以保持一致,已在 `login-form.tsx` 的
   doc comment 中留下指向。
