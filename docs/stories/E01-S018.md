# E01-S018 — 建立 app-level error boundary

- 狀態:DONE
- Branch:story/E01-S018-app-level-error-boundary
- 日期:2026-08-14

## Scope 說明

本 story 建立 Next.js App Router 的檔案慣例 error boundary,讓任何未預期
的 render-time 錯誤都有一個一致、不洩漏內部細節的 fallback UI,而不是
瀏覽器預設的空白頁或 Next.js 自帶的原始錯誤畫面。

實作兩層(對應 AC 8「能力本身不可缺席」的完整覆蓋):

1. **`app/error.tsx`**——捕捉根 layout 之下、`(public)` 與 `(app)`
   兩個 route group 內任何一頁的 render 錯誤(兩者都沒有自己的
   `error.tsx`,所以都由這一個共用邊界處理)。
2. **`app/global-error.tsx`**——捕捉根 layout(`app/layout.tsx`)本身的
   render 錯誤,這是 `error.tsx` 無法涵蓋的情況(因為根 layout 本來就是
   提供 `<html>/<body>` 的地方,它自己壞掉時取代它的邊界必須自帶一份)。
   目前根 layout 是純靜態 JSX、無任何資料讀取或邏輯,這個路徑發生機率
   很低,但依 Functional AC 8 仍不應缺席這個能力——見下方 Assumptions
   說明為何這層没有自動化測試直接觸發。

兩者共用同一個新的 `packages/ui`「CrashFallback」呈現元件(標題 +
重用 S012 既有的 `SERVER_ERROR` 文案 + 有 `reset` 時提供「重試」按鈕 +
一律提供「回首頁」連結),避免兩個檔案各寫一份重複的 fallback UI,也讓
未來 E11 Admin Console 需要同樣機制時可以直接重用。

## 除錯記錄(FIX 循環)

### FIX 第 1 輪:`/_debug-throw` 完全無法被路由到

**症狀**:E2E 測試造訪 `/_debug-throw` 得到的是 `not-found.tsx` 的
「頁面不存在」畫面,而不是 error boundary 的 fallback——即使 fixture
裡的 `NODE_ENV` 判斷式在 dev 模式下理論上不該擋下它。

**第一次診斷嘗試(錯誤方向)**:懷疑是 `pnpm build`(production build)
留下的 `.next` cache 被隨後啟動的 `next dev` 沿用,導致路由結果被
「凍結」成 build 當下算出的 404。清掉 `.next` 後重跑,**同樣失敗**——
證明這個假設是錯的,不是 cache 問題。

**換診斷路徑**(依規則:同一錯誤連續 2 次同方式修不好要換方法):直接
用 `curl` 繞過 Playwright/瀏覽器,拿到的 RSC payload 顯示 Next.js
路由器根本沒有把 `_debug-throw` 視為一個頁面——它直接把請求導向
`/_not-found`,連我的 `page.tsx` 都沒有執行到(不是我的 `notFound()`
判斷式生效,是路由器根本沒看到這個路由)。

**根因**:Next.js App Router 有一個內建慣例——**檔名開頭是底線的資料夾
（如 `_debug-throw`）會被視為 private folder,整個從路由系統中排除**。
這正是本 repo `_components/` 資料夾本身依賴的同一個機制(用來確保
`_components/` 底下的檔案不會被誤判成路由)——我在幫這個 fixture 命名
時沒意識到同一個慣例會讓它變成「永遠訪問不到」。

**修法**:資料夾改名 `debug-throw`(去掉底線),更新程式內註解、E2E
spec 的路徑字串。重新從 VERIFY 第一個 gate(typecheck)開始重跑。

### FIX 第 2 輪:`getByRole("alert")` 命中兩個元素

**症狀**:heading 斷言通過(證明第 1 輪的修法有效,fallback 真的渲染
出來了),但 `getByRole("alert")` 斷言以 strict-mode violation 失敗
——同時命中 `<ErrorMessage>` 的 `<p role="alert">` 與 Next.js 自動
注入的 route announcer(`<div role="alert" aria-live="assertive"
id="__next-route-announcer__">`,每一頁都有,是 Next.js 自己的無障礙
機制)。

**根因**:這是本專案第一個在 E2E(真實瀏覽器)層級使用
`getByRole("alert")` 的測試——之前的 story 都是在元件測試(jsdom,
不會有 Next.js 自己注入的 route announcer)用這個 query,或是在 E2E
用文字比對,沒有人踩過這個特定組合。

**修法**:改用 `getByText("系統發生錯誤，請稍後再試。")`(比對既有
`SERVER_ERROR` 的確切文案),與 `login.spec.ts` 既有的
`getByText("帳號或密碼錯誤。")` 是同一個既有模式,不是新發明的方法。
重新從 VERIFY 第一個 gate 開始重跑,兩輪都全過。

兩輪 FIX 都在循環上限(5 次)內,且第 2 輪換了與第 1 輪完全不同的
診斷/修正方式,符合「連續 2 次同方式修不好要換路徑」的規則(第 1 輪
內部就已經換過一次路徑;第 2 輪是全新的獨立問題,非同一錯誤重複)。

## Assumptions / 計畫外事項

1. **`global-error.tsx` 沒有自動化測試直接觸發它的 render 路徑**:
   要讓它啟動,必須是根 layout(`app/layout.tsx`)自己 throw——目前
   根 layout 是純靜態 JSX,沒有任何會失敗的邏輯或資料讀取。要製造一個
   會觸發的情境,只能在根 layout 裡加測試專用的條件式 throw,但根
   layout 是高影響範圍、應該保持單純穩定的檔案,為了測試目的在裡面加
   邏輯的取捨比 `debug-throw` fixture(獨立、不影響任何既有檔案)更差。
   已用 typecheck(確保 `{error, reset}` 簽章正確)+ 程式碼審查
   （render 邏輯與 `error.tsx` 共用同一個 `CrashFallback`,已被
   `error.tsx` 的測試間接驗證過)提供有限但誠實的驗證強度,而非略而
   不提或假裝已用 E2E 涵蓋。
2. **`debug-throw` 是刻意保留、非隱藏的測試 fixture**:error boundary
   的本質是處理「不可預期」的錯誤——不存在一個「本來就該壞掉」的真實
   產品頁面可以用來驗證它,所以唯一誠實的驗證方式就是刻意做一個會
   throw 的 fixture。已確保它在 production build 中安全(命中
   `NODE_ENV === "production"` 時呼叫 `notFound()`,並且 typecheck 通過
   `never` 回傳型別),但它仍是一個會被建置進 production bundle 的
   route(只是 render 時立即 404),不是完全從程式碼中消失。如果未來
   有更完整的 QA/測試基礎設施(例如獨立的 E2E-only 建置目標),可以
   考慮把這類 fixture 移到那裡;目前這個 thin slice 判斷這個取捨是
   合理的。
3. **`CrashFallback` 沒有掛在任何「情境化」的重試邏輯上**:`reset()`
   只是重新渲染該 route segment(Next.js 內建行為),不會重新抓資料或
   清除可能導致原始錯誤的狀態——如果錯誤是持續性的(例如某個元件的
   邏輯 bug),重試會再次觸發同一個錯誤。這是 Next.js `error.tsx` 慣例
   本身的既有行為,非本 story 引入的限制。
4. **修正了一個對本 repo 有參考價值的踩坑**:`getByRole("alert")` 在
   Playwright E2E(真實瀏覽器)會撞到 Next.js 自動注入的 route
   announcer,這個 codebase 之前所有 E2E 都沒踩到是因為都用
   `getByText(確切文案)` 代替——本 story 的 FIX 記錄已把這個原因寫清楚
   （見上方除錯記錄),供之後的 story 參考,不需要重新踩一次才知道。
5. **獨立審核階段補上 `global-error.tsx` 的 `import "./globals.css"`**:
   `global-error.tsx` 啟用時完全取代根 layout(自己提供
   `<html>/<body>`),根 layout 原本的 `import "./globals.css"` 不會
   執行,若不重新 import 會讓這個(本來就很少見的)fallback 畫面失去
   基本樣式重置與字型設定。功能不受影響(`CrashFallback` 沒有依賴任何
   自訂 class),純粹是視覺一致性的小完善,審核時發現後直接補上,重跑
   全部 gate 確認未破壞任何既有測試。
