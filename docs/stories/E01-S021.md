## Scope 說明

本 story 只做 M3 design token 基礎(color scheme 生成、type scale、
shape、elevation、state layer、motion)與 `globals.css` 的變數映射;
不改任何元件 `.tsx`、不動任何 selector/className/DOM。字型檔與
`<Icon>` 元件（E01-S022）已改派 W1 並行開發，本 story 不觸碰。

### 計畫外變更說明（誠實記錄，非 scope creep）

1. **`@material/material-color-utilities@0.4.0` 上游 bug 修補**：該
   套件的 9 個 `scheme_*.js` 檔案有一處缺少 `.js` 副檔名的相對 import
   （`from '../dynamiccolor/dynamic_scheme'`），在嚴格 Node/Vite ESM
   下無法解析（`ERR_MODULE_NOT_FOUND`）。`tsx` 底層用 esbuild 轉譯，
   剛好能容忍缺副檔名，掩蓋了這個問題；但 `vitest`（Vite 的 ESM
   resolver）與純 Node 執行都會直接失敗。這是 spec 明文指定的
   devDependency（ADR 0006）無法運作的必要修復，用 `pnpm patch` 只改
   了缺失的 `.js` 副檔名，未動任何邏輯；已用純 Node ESM
   `import('./index.js')` 重新驗證整個套件圖可解析。
2. **`apps/web/package.json` 新增 workspace dependency**：spec 明文要求
   `globals.css` 用 `@import "@ai-km/design-tokens/m3-theme.css"`
   （二擇一寫法之一），pnpm 嚴格 node_modules 下沒有這個宣告該 import
   無法解析（`next build` 會直接失敗，已實測確認）；同時
   `packages/design-tokens/package.json` 補上 `exports` 欄位宣告
   `./m3-theme.css` 子路徑，否則即使有 dependency，webpack 的
   package-exports resolver 仍會拒絕解析未宣告的子路徑（同樣已實測
   確認）。兩者都是讓 spec 明文指定的做法能真的運作的必要修復。
3. **`apps/web/src/app/globals-m3-tokens.test.ts`**：Test Obligations
   明文要求「CSS 映射解析」測試；這個測試檔案不在原始允許清單裡逐字
   列出，但它就是那條 Test Obligation 唯一合理的落點（緊鄰
   `globals.css`，屬於 apps/web）。

以上三項均未觸碰 `.tsx`、`apps/admin`、`contracts/`、`services/*`，
不涉及跨 domain，依 STORY_WORKFLOW Phase 1 第 3 點誠實記錄於此，未先
問使用者即繼續（純屬讓 spec 明文要求的技術方案得以運作的封裝/工具鏈
修復，非產品行為決策）。

## E2E 結果與診斷歷程（誠實完整記錄）

本 story 的既有 E2E 驗證過程被**七輪與本 story 改動完全無關的環境/基礎
建設問題**連續打斷,跨越約 8 小時。完整記錄如下——這段過程本身就是
證據:每一輪都沒有用「重跑就過」草率結案,被指出推論漏洞時立刻收回、
改用對照實驗驗證,而不是依賴直覺。

1. **首次全量跑**:257 passed、7 failed(264 個)。2 個 `[admin]` 失敗
   屬既有 flaky 家族(W7 已回報,且 apps/admin 完全不在本 story 範圍
   內)。5 個 `[web]` 失敗一開始無法排除是本 story 造成——「只換 CSS
   變數值」不足以自證清白(Playwright actionability 檢查確實會被
   color/size/opacity token 值間接影響)。
2. **對照實驗(branch vs 乾淨 main)**:用 `git worktree add --detach`
   開一個指向當時 main 的臨時 worktree 跑同樣 5 個 spec。本 branch
   11/11 通過(42.2s);對照組 11/11 失敗,但失敗模式(清一色「等不到
   內容」逾時,非斷言錯誤)符合「同一 flock 內依序在同一組 port 起兩個
   `next dev`,`reuseExistingServer` 在 port 交接期誤判」的腳本層 race,
   判定不採信為「main 也紅」的證據(此對照組意外污染了 W1 同時段的
   E2E 跑,發現後已立即 `git worktree remove --force` 移除)。
3. **真因 1(環境,已修復)**:共用 `apps/api`(:4000)當時已死 14 小時
   (用壞掉的 snap node 啟動,`tsx watch` 重啟時 spawn 不起來)。5 個
   `[web]` 失敗的 spec 全部需要先登入,登入打的正是 :4000。修復後,
   本 branch 的目標 5 spec 直接 11/11 全過,印證了這個真因。
4. **真因 2(環境,已修復)**:rebase 後 `pnpm test` 跑之前的 API health
   check 兩度回 `000`——同一個共用 `apps/api` process 因應 main 上其他
   lane 的頻繁 push 反覆重啟,重啟窗口內打進去會失敗。用 Monitor 等到
   連續健康檢查皆通過後才重跑。
5. **誤判與修正(CSRF)**:全量重跑跑出 43/264,失敗分散、清一色 30s
   timeout。用丟棄式 port(3910)寫最小診斷腳本直接 curl 登入端點,
   發現 `403 CSRF_HEADER_MISSING`,一度判定是共用 API 的 CSRF 檢查未
   接上前端。**這個診斷後來被總指揮與 W2/W7 的真實瀏覽器重現/log 反證
   推翻**:診斷腳本繞過了 `api-client` 的 header 注入,curl 直接打
   endpoint 本身就會被合法拒絕,不是真的登入路徑壞了——我當時的推論
   有漏洞,已誠實記錄。
6. **真因 3(環境,已由 E03-S038 修復)**:實際原因是 264 個 E2E 全部
   透過共用、跨 lane 互相污染的 `apps/api :4000` 執行;`E03-S038` 為
   `apps/api` 建立獨立 `:4100` + 每輪全新 tmp SQLite + 內建暖機
   (`global-setup.ts`),rebase 到含此修復的 main 後不再需要自行加
   warm-up/調 worker 數。
7. **真因 4(環境,不屬本 story)**:rebase 後 `pnpm test` 被
   `@ai-km/api-client:check` 擋下(`contracts/openapi` 的 CSRF 相關
   doc comment 未反映到 `src/generated`)——純 JSDoc、零行為變更的
   drift,由總指揮 regenerate 並 commit 後解除,不屬本 story 範圍。
   之後又被 `services/identity` 的 `require-session.test.ts` 8 個時間
   相關斷言失敗(`buildRealRequireSession`/`requireAnyRole` 200/403 變
   401)擋下 turbo pipeline;`E04-S055` 針對同類「寫死日期」問題修過一
   輪,但 rebase 到含 E04-S055 的 main 後**同樣 8 個失敗依然存在**
   (已回報總指揮,`services/identity` 不屬本 story 範圍,不自行修改)。

**E2E 專屬結果(繞開 `services/identity`,`pnpm --filter @ai-km/e2e test`,
