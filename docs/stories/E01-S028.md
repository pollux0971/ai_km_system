## 意外發現的既有 bug(獨立於本 story,已回報 ai-km-e4,ai-km-e4 覆核並核准
本 story 的權宜解法,完整記錄見 `PENDING_DECISIONS.md`)

**`apps/api` 自己文件化的 `pnpm build && pnpm start` 從未真的能跑**:
`services/conversation`／`services/identity`／`services/model-gateway`
的 `package.json` 都是 `"build": "tsc ... --noEmit"`、`"main"` 直接指向
`./src/index.ts`——完全沒有編譯輸出,設計上就是要被 TS-aware runtime
(`tsx`)以原始碼形式消費。`pnpm --filter @ai-km/api build` 成功、但
`node apps/api/dist/main.js` 會 `ERR_UNKNOWN_FILE_EXTENSION`——**在 Docker
之外也重現確認過**,不是 Docker 特有的問題。`apps/web`／`apps/admin`
不受影響(Next.js 自己的 bundler 靠 `transpilePackages` 轉譯)。

**因應**(在本 story 允許清單內,未動對方 domain):
`infra/docker/api.Dockerfile` 改用 `pnpm exec tsx src/main.ts`——與
`pnpm dev` 完全同一條已驗證可行路徑。**代價**(ai-km-e4 要求明寫):
1. image 的 `pnpm install` **沒有**加 `--prod`——`tsx` 是 `apps/api` 的
   devDependency,拿掉 dev 依賴 image 會直接壞掉,已確認並保留完整
   dependency tree。
2. **這代表 production image 帶著整套 TypeScript 開發工具鏈**
   (`typescript`、`tsx`、`eslint`、`turbo`……)——image 體積、攻擊面、
   以及「production 跑 dev 工具」的取捨,已寫進 runbook 的專屬段落
   讓部署者知情。
3. 這是**權宜之計**,不是最終設計;真正修法(讓 `services/*` 真的產出
   JS)是架構取捨,規模明顯超出本 story,ai-km-e4 已記錄選項留給使用者
   裁示是否另立 story。

## 另一個意外發現:SSRF 防護與 `host.docker.internal` 的衝突

`services/model-gateway/src/config.ts` 的 `isLoopbackOrPrivateHost` 只接受
數字 loopback/私網 IP 字面值(或 `localhost`/`::1`),對 URL 的
**hostname 字串**做檢查——不管它實際解析到哪個 IP。`host.docker.internal`
是 DNS 名稱(即使透過 `extra_hosts` 解析到私網 IP `172.17.0.1`,已用
`getent hosts` 實測確認),字串檢查一律拒絕,啟動失敗。

**因應**(同樣在允許清單內,不碰 `services/model-gateway` 的 SSRF 邏輯):
`infra/docker/api-entrypoint.sh` 在啟動前從 `/etc/hosts` 讀出
`host.docker.internal` 已解析的數字 IP,把 `AI_KM_ASR_SERVER_URL` 裡的
DNS 名稱換成該數字 IP 再啟動——SSRF guard 本身的私網範圍允許清單完全
沒被放寬,只是避開了它「不認 DNS 名稱」這個字面限制的誤傷,因為
`host.docker.internal` 本來就只會解析到 guard 已經信任的私網範圍。已
實測確認(`docker compose logs`):`[api-entrypoint] resolved
host.docker.internal -> 172.17.0.1`,api 正常啟動,無 SSRF 拒絕。

## 自己抓到的 bug(寫測試/腳本過程中,已修正,記錄於此而非默默改掉)

`scripts/prod-check.sh` 原本預設檢查 `http://127.0.0.1:4000/v1/health`
當作「api 直接健康檢查」。**這個位址在本機環境剛好是 fleet 共用的長跑
apps/api**(其他 lane 的 E2E 都靠它)——因為 `docker-compose.yml` 刻意
沒有把 `api` 的 port 發布到 host,`curl 127.0.0.1:4000` 根本沒打到我的
container,而是打到了共用的那一個,**卻回傳 200 讓測試看起來像通過**。
已用 `ss -ltnp` 與比對 `uptimeMs`(共用實例 ~20 分鐘 vs 我剛啟動的
container 幾秒)實際證實這個混淆。已修正:`prod-check.sh` 預設不再檢查
「直接 api」(AC2 本來就只要求 proxied 路徑),只在明確傳入
`--direct-api <url>` 時才檢查,並在檔案開頭把這個陷阱寫清楚——避免
未來任何人在這台共用機器上重蹈覆轍。
