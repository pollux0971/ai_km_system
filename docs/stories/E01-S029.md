## CSP 調查(核心發現,交給使用者裁決前的完整記錄)

### 現象
CSP 以 spec 字面值(`script-src 'self'`,dev 額外 `'unsafe-eval'`)**強制生效**時,
既有 264+ 個 E2E 中約 250 個左右在 `login()` helper 的
`getByLabel("帳號").fill(...)` 這一步 30 秒逾時——不論是否暖機
(`curl` 先拿到 200)、不論 `--workers` 設 1 或預設值,現象完全不變。

### 根因(已用第一手證據確認,非推測)
```bash
$ curl -sI http://localhost:3000/login | grep -i content-security-policy
Content-Security-Policy: default-src 'self'; ...; script-src 'self' 'unsafe-eval'; ...

$ curl -s http://localhost:3000/login | grep -o '<script[^>]*>'
<script>                                                              ← 唯一沒有 src 的一個
<script src="/_next/static/chunks/app/error.js" async="">
<script src="/_next/static/chunks/app/global-error.js" async="">
...(其餘皆有 src)
```
那個唯一的 inline `<script>` 內容是:
```
(self.__next_f=self.__next_f||[]).push([0])
self.__next_f.push([1,"5:I[\"(app-pages-browser)/.../next-devtools/..."])
```
這是 **Next.js App Router 的 RSC(React Server Components)streaming
flight-data bootstrap 機制**——`self.__next_f.push(...)`,不是 Fast
Refresh/HMR 用到的 `eval`。**這個機制在 dev 與 production 都存在**(App
Router 用它把 server-render 的 payload 遞給 client 做 hydration),不是
dev-only 產物。`'unsafe-eval'` 管不到它——那只放行 `eval()`/`Function()`,
管不到一個完全沒有 `src` 屬性的 `<script>` 標籤,那需要 `'unsafe-inline'`
或 CSP nonce。

CSP 阻擋這個 inline script → React 無法 hydrate → `/login` 的表單
(client component)永遠不會出現在 DOM 上 → `getByLabel("帳號")` 30 秒逾時。
`curl` 拿到 200 只證明 HTML 骨架有回應,不代表 JS 有執行——這正是「curl 通、
瀏覽器測試不通」這個表面矛盾的真正原因。

### spec 本身的張力,與使用者裁示
- Security AC 明文:「任何放寬...不得整體放寬 `script-src`」。
- Non-Goals 明文排除「nonce-based CSP」——而 nonce 正是 Next.js 官方文件
  (https://nextjs.org/docs/app/guides/content-security-policy)對這個情境
  的建議解法。

兩條路都等於修改本 story 的驗收標準,不是實作層可以自行決定的事,已回報
`ai-km-e4`,由其轉交使用者裁決,附完整證據鏈(見上,含 38 筆違規清單全部
同一根因、其餘 8 條 CSP 指令實測零違規的數據)。

**使用者裁示(2026-08-29,經 `ai-km-e4` 轉達)**:
1. 解除「不做 nonce-based CSP」這條 Non-Goal,採用 Next.js 官方建議做法。
2. `middleware.ts`(兩個 app 各自的)納入本 story 允許修改清單。
3. `script-src` 維持嚴格,不加 `'unsafe-inline'`——XSS 防護完整保留。
4. 使用者接受 story 因此擴大約半天工作量。

理由:另開新 story 處理也是做同一件事,不如當下做對;違規清單的精確定位
(單一根因,非分散問題)讓這個決定容易下。

### nonce 實作

**兩個部分,缺一都不完整**(第二部分是踩過的坑,值得記錄):

1. **`middleware.ts` 產生 nonce 並設定 CSP header**(維持既有 correlation-id
   邏輯不動,純新增):
   ```ts
   const nonce = Buffer.from(crypto.randomUUID()).toString("base64");
   const csp = buildCsp(nonce); // script-src 'self' 'nonce-${nonce}' 'strict-dynamic'[ 'unsafe-eval']
   requestHeaders.set("x-nonce", nonce);
   requestHeaders.set("Content-Security-Policy", csp);
   // 同步設定於 response header
   ```
2. **根 `layout.tsx` 必須呼叫 `headers()`**(即使不使用回傳值)——這不是
   裝飾性程式碼。**踩過的坑**:只做第 1 步時,`next build` 後的 `/login`
   仍是 static(`○`),curl 拿到的 CSP header 有正確 nonce,但實際 HTML 裡
   RSC payload 印出 `"nonce":"$undefined"`,inline `<script>` 標籤完全沒有
   `nonce` 屬性——嚴格 CSP 下這些 script 一樣會被擋。呼叫 `headers()`
   (Next.js 的 dynamic API)才會讓路由退出 static 預先產生,同時是 Next.js
   runtime 決定要把 nonce 套到自己產生的 inline script 的觸發訊號。

`'strict-dynamic'` 讓支援 CSP3 的瀏覽器忽略 `'self'`,只信任帶 nonce 的
script 與其動態載入的子 script——這正是 Next.js chunk 載入的實際行為模式;
`'self'` 保留在清單中是給不支援 `'strict-dynamic'` 的舊瀏覽器的 fallback,
官方建議寫法,非冗餘。

### 第一手驗證(`next build && next start`,非僅 `next dev`)

```bash
$ curl -sD - http://localhost:3999/login -o body1.html
Content-Security-Policy: ...; script-src 'self' 'nonce-N2E2Yj...' 'strict-dynamic'; ...
$ grep -o '<script[^>]*>' body1.html
<script nonce="N2E2Yj...">                              (×4,inline)
<script src=".../webpack-....js" nonce="N2E2Yj..." ...>  (每個外部 chunk 也都有,且與 header 完全相同)

$ curl -sD - http://localhost:3999/login -o body2.html   # 第二次請求
Content-Security-Policy: ...; script-src 'self' 'nonce-ODI4ZW...' 'strict-dynamic'; ...
                                                   ↑ 正確地每次請求都不同
```
再用真實 Playwright 瀏覽器(非 curl)對**強制生效**(非 Report-Only)的 CSP
驗證 hydration 真的成功——`security-headers.spec.ts` 的
`"a real browser page load hydrates under the enforced (non-Report-Only)
CSP"`,以及 `admin-security-headers.spec.ts` 的對應測試,兩者皆通過。

### 靜態最佳化的真實代價(使用者裁示時未被提及,`ai-km-e4` 要求補記)

呼叫 `headers()` 讓**整個路由樹**退出 static 預先產生。實測 `next build`:

```
# 之前(僅 middleware,無 headers() 呼叫)
├ ○ /login          19.1 kB   122 kB    (○ = static)
├ ○ /conversations/new
...(apps/web 20 條路由中多數是 ○)

# 之後(加上 headers() 呼叫)
├ ƒ /login          19.1 kB   122 kB    (ƒ = dynamic,每次請求都重新 render)
├ ƒ /conversations/new
...(apps/web 29 條路由全部變成 ƒ)
```
`apps/admin` 同步驗證:21/21 條路由全部是 `ƒ Dynamic`。這是 nonce-based CSP
的內建、有文件記載的取捨,不是 bug——nonce 定義上每次請求都不同,含 nonce
的頁面本質上不可能是單一份可快取的靜態產物。代價:這些路由的 HTML 骨架
不能再被 CDN/瀏覽器快取,每次請求都要付出 render 成本。已寫入
`docs/runbooks/security-headers.md`。

### 診斷資料(供裁決參考)
1. **CSP 切成 `Content-Security-Policy-Report-Only`(不阻擋,只記錄)後跑全量
   264+ 個既有 E2E**:259/273 通過(94.9%),6.3 分鐘。
   - 2 個失敗是本 story 新增的 `security-headers.spec.ts` /
     `admin-security-headers.spec.ts` 在這個診斷模式下斷言 header 名稱錯誤
     (它們找 `content-security-policy`,這個模式下實際送出的是
     `content-security-policy-report-only`)——不是迴歸,只是診斷模式的預期
     副作用,已在最終選定實作後移除。
   - 12 個失敗(`case-detail.spec.ts` ×3、`erp-e2e.spec.ts` ×1、
     `knowledge-selector.spec.ts` ×2、`maintenance-e2e.spec.ts` ×2、
     `maintenance-session.spec.ts` ×4)是**與 CSP 完全無關**的另一種失敗
     模式:`page.goto(url)` 後 `waitForURL(pathname === "/login")` 逾時
     (預期被導回登入頁但導轉沒發生),跟前述「登入頁表單渲染不出來」是不同
     的錯誤特徵,而且在 CSP 完全不阻擋的 Report-Only 模式下依然出現——證明
     與本 story 的改動無關,屬既有環境/時序脆弱性,不在本 story 範圍內。
2. **CSP 違規清單**(走過 `/login`→登入→`/conversations/new`→`/knowledge`→
   `/profile` 四個頁面,含登入前後):**38 筆違規全部是同一種**——
   `Executing inline script violates the following Content Security Policy
   directive 'script-src ...'`,每筆的 sha256 hash 不同只因為每個 RSC
   streaming chunk 內容不同,語意上是**同一個根因、同一個機制**,重複出現
   在每次 `self.__next_f.push(...)` 呼叫。**沒有任何**其他違規類型
   (無 eval、無 style、無 connect-src/img-src/font-src)——CSP 除了這一個
   機制以外,其餘全部乾淨通過,代表 `default-src 'self'`、`connect-src
   'self'`、`img-src 'self' data:`、`style-src 'self' 'unsafe-inline'`、
   `font-src 'self'`、`frame-ancestors 'none'`、`base-uri 'self'`、
   `form-action 'self'` 這 8 條指令在本 app 的實際使用情境下都是可嚴格執行、
   零例外的。
