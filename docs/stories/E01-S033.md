## 問題根因與修法
`apps/web/src/app/layout.tsx` 的 `metadata.title` 是整站唯一、靜態的
`"AI KM"`(全站沒有任何 route 覆寫 `metadata.title` / `generateMetadata`
——已用 grep 確認),Next.js 在每次用戶端導覽時會把這個字串寫進它自己
注入的 `<div id="__next-route-announcer__" role="alert" aria-live="assertive">`
(供螢幕報讀器宣讀新頁面標題)。凡是**未 scope** 到特定容器、直接對整頁
搜尋 `"AI KM"` 文字的 `getByText`,在這個 announcer div 短暫存在的導覽瞬間
就會同時撞到 header 品牌字樣(`<span class="app-header-brand">`)與這個
announcer div,兩者文字逐字相同 → Playwright strict-mode violation
(resolve 到 2 個元素)。

修法比照 repo 內既有先例(`knowledge-documents.spec.ts`、
`knowledge-folder-sync.spec.ts`、`knowledge-ui-e2e.spec.ts` 等,對
`getByRole("alert")` 的碰撞一律 scope 到 `getByRole("main")`):header 品牌
字樣改 scope 到 `<header>` 元素自帶的 `"banner"` landmark role
(`apps/web/src/app/(app)/_components/header.tsx` 的 `<header>` 沒有被任何
sectioning content 祖先包住,保有原生 `banner` role,`__next-route-announcer__`
div 則掛在 `<header>` 之外,不會被這個 scope 選中)。

## AC2 反向驗證(非空洞驗證,方法論比照 E04-S055 的 non-vacuity check)
用一支**臨時**(未進入最終 commit)的 repro spec,對登入後的真實頁面用
`page.evaluate()` 注入一個與 Next.js 實際產物完全同構的 route-announcer div
(`id="__next-route-announcer__"`、`role="alert"`、`aria-live="assertive"`、
`textContent="AI KM"`),證明:

1. **修正前(未 scope 的 `getByText("AI KM", {exact:true})`)** 對注入後的頁面
   斷言,真的產生 strict-mode violation,逐字訊息:
   ```
   strict mode violation: getByText('AI KM', { exact: true }) resolved to 2 elements:
       1) <span class="app-header-brand">AI KM</span> aka locator('span')
       2) <div role="alert" aria-live="assertive" id="__next-route-announcer__">AI KM</div> aka getByRole('alert').filter({ hasText: 'AI KM' })
   ```
2. **修正後(`getByRole("banner").getByText("AI KM", {exact:true})`)** 對**同一個**
   已注入重複文字的頁面斷言,通過(`✓ ... PASSED despite injected duplicate`)。

過程中的插曲(誠實記錄):第一次注入時「未重現」,診斷後發現是因為注入時機
太早——`waitForURL` 只保證 URL 已切換,但 SessionGate 的 loading 狀態下
header 尚未掛載,此時只有 `<title>` 與剛注入的 div 兩個葉節點命中文字,
header span 還不存在。加入 `await page.getByRole("navigation", {name:"主導覽"}).waitFor()`
等 shell 真正掛載完成後再注入,才重現出上述 2-element 逐字碰撞。這個過程
本身也證明了此驗證方法確實在「偵測真實碰撞」,不是空殼——同樣的注入手法
在 shell 未掛載時、掛載後,分別給出「不重現」與「精確重現」兩種不同結果。

此 repro spec 只用於驗證過程,驗證完成後已刪除,未進入最終 diff
(`git status` 確認乾淨,同 E04-S055 的處理方式)。
