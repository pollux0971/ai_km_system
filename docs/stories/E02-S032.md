## 測試修正記錄(若有)
本 story 全程先寫測試、後寫實作。VERIFY 階段發現 2 類問題,記錄如下(皆屬 Phase 4 第 5 點窄例外——測試本身的技術性錯誤,非放寬驗證行為;所有 `expect()` 斷言內容 FIX 前後完全相同):

1. **`plugin.test.ts` AC9 兩條測試**:原寫法在 `buildTestApp()`(已呼叫 `app.ready()`)回傳後才 `app.get("/__protected__", ...)`,Fastify 對已 boot 的實例禁止再註冊 route(`FastifyError: Root plugin has already booted`)。判斷:這是測試對 Fastify boot 生命週期的用法錯誤,不是 `requireSession`/`composeRequireSession` 的行為有問題(同一份實作在 `require-session.test.ts` 的 `composeRequireSession` 套件級測試中已用正確順序驗證過同樣的行為)。修正:改為自建一個尚未 `ready()` 的裸 Fastify 實例,先加 test route 再 `ready()`。斷言(401 且 handler 未呼叫 / 200 且 request.auth 正確)完全未變。
2. **`plugin.test.ts` AC8 restart 測試**:原寫法對共用的 `:memory:` db 先 `first.close()` 再用同一個 `db` 物件開第二個 Fastify 實例,但 `:memory:` 資料庫的資料只存活於「連線」本身,`buildTestApp` 的 `onClose` hook 會連帶關閉 `db`,導致第二次 `db.prepare(...)` 拋出 `The database connection is not open`。判斷:這是對 `:memory:` SQLite 生命週期的技術性誤用,不是 `seedDemoUsers` 冪等邏輯本身有問題(該邏輯已由 `repository.test.ts` 的「does not re-create users on a second call」直接驗證過)。修正:不關閉 `first`,改成在同一個仍開啟的 `db` 上啟動第二個獨立 Fastify 實例模擬「重啟後仍指向同一份資料」。斷言(count === 4,不重複)完全未變。

此外,`testing/app.ts`(測試輔助檔,非測試本身)一開始沒有加上與 `apps/api/src/server.ts` 完全相同的嚴格 Ajv `validatorCompiler`,導致 Fastify 內建預設 Ajv 的 `removeAdditional: true` 把 `additionalProperties: false` 的違規靜默清掉而非回 400。這不是修改「既有測試斷言」——`400s on an unexpected extra field` 這條測試連同其斷言是本 story 這次一起寫的新測試,從未通過過、也從未被放寬;修正的是測試輔助設施(補上與真實 apps/api 相同的驗證器設定),讓套件級測試準確模擬掛載進 `apps/api` 後的真實行為。

## Assumptions / 計畫外事項
1. **`apps/api/package.json` 新增一行 dependency**:允許修改清單只列了 `apps/api/src/server.ts(註冊一行)` 與 `apps/api/.env.example`,未明列 `package.json`。但少了 `"@ai-km/service-identity": "workspace:*"`,`server.ts` 那一行 `import { identityPlugin } from "@ai-km/service-identity"` 無法在 pnpm workspace 下 resolve —— `@ai-km/service-conversation` 當初(E04-S040/041)被 `conversationPlugin` 註冊時也是同樣加了這一行。視為讓允許清單內那一行真正生效的必要伴隨變更,而非額外範圍;若使用者認為不妥,请指示回退並改採其他接線方式。
2. **`requireSession` 覆寫機制**:`apps/api/src/auth-decorator.ts`/`types.ts` 皆不在允許修改清單內,因此未直接修改它們。改為在 `identityPlugin`(以 `fastify-plugin` 包裝,不建立新的封裝 context)內用「先讀出 `app.requireSession` 目前的值 → 覆寫成 compose 過的版本」的方式接線,而不是 `app.decorate()`(對已存在的 decorator 再 decorate 會丟錯)。這個設計選擇的完整理由與「為什麼不能直接取代」寫在 `require-session.ts` 的檔頭註解。已驗證 `apps/api/src/server.test.ts`(E04-S039、本 story 禁止修改)的既有 3 條 `requireSession` 相關測試完全不必改動、重跑全綠。
3. **`services/identity` 自有 Fastify 型別擴充**(`fastify-types.d.ts`):不 import `apps/api/src/types.ts`,而是在本套件內重新宣告同樣結構的 `declare module "fastify"`。理由:`services/identity` 是被 `apps/api` 依賴的一方,反向 import 會顛倒依賴方向並可能造成 workspace 循環依賴;TypeScript 的 declaration merging 只需要形狀一致,不需要是同一個檔案。完整理由見該檔案檔頭。
4. **`AI_KM_SEED_DEMO_USERS` 未進 `apps/api/src/config.ts`**:`config.ts` 不在允許修改清單內。`services/identity` 因此自帶一份最小 env 解析(`src/config.ts`),在 registration 時直接讀 `process.env`,不透過 `apps/api` 的 `ApiConfig` 傳遞——與 `apps/api/src/server.ts` 對 `identityPlugin` 的註冊因此可以維持「一行,不帶 options」。
5. **`AI_KM_AUTO_MIGRATE=false` 啟動防護**(`repository.ts: identityTablesExist`):規格未明文要求,是 VERIFY 階段用完整 `apps/api pnpm test` 跑出來的真實回歸——`db/migrate.test.ts` 既有一條測試(E04-S040,本 story 禁止修改)驗證「`AI_KM_AUTO_MIGRATE=false` 時 `buildServer()` 仍必須成功啟動,只是 schema 還沒套用」。`identityPlugin` 原本在 registration 時無條件呼叫 `seedDemoUsers()`,若 `users` 表尚不存在會直接拋錯讓整個 `buildServer()` 失敗。修正為:seed 與定期清理 sweep 都先檢查 `identityTablesExist()`,表不存在就靜默跳過(route 本身不加防護,實際打進未 migrate 的 DB 是真正的 SqliteError,行為正確)。
6. **E2E 全機器 port 互斥鎖**(ai-km-e4 2026-08-28 公告):已知悉並在過程中親身驗證過其必要性——執行 `pnpm test`(未過濾)時意外觸發了 `@ai-km/e2e` 的 Playwright `webServer`,雖然最終沒有實際綁定到 port(w7 worktree 當時持有 3000/3001),但已立即改用 `--filter='!@ai-km/e2e'` 排除。本 story 本身無 E2E gate 適用(見 Gate 紀錄 L5),但已記錄此規則供下游 story(E03-S038、E11-S026)注意。
