# E03-S002 — Normal/Advanced mode switch

- 狀態:DONE
- Branch:story/E03-S002-normal-advanced-mode-switch
- 日期:2026-08-14

## Scope 說明

`SOURCE_BASELINE.md` 的 E03 概要(condensed outline,行 1094-1140)列出
S01-S09 依序是:New Conversation → **Conversation Mode** → Knowledge
Selector → Multi Knowledge Selection → Model Selector(註記
「Advanced mode」)→ Message Composer → Multi-line Input → File
Attachment → Send Message。這是同一個對話介面逐步組裝的元件清單,
本 story(S02)是第一個需要「有個地方可以渲染」的 story——E03-S001 的
「list/new route」明確只做了列表 + 建立,沒有做對話詳情頁(其自己的
evidence 檔案寫明:「`/conversations/[id]` 還不存在(那是後續 E03
story 的職責)」)。

因此本 story 的範圍是**兩件事的組合**:

1. **對話詳情頁殼層** `/conversations/[id]`——目前先只有標題 +
   模式切換,不含訊息串/輸入框(那些是 S03-S09 各自的職責,提前做
   等於「不提前實作其他 Story」的違反)。
2. **模式切換本身**——一般/進階兩個選項,可切換、可持久化。

依 SOURCE_BASELINE 目前唯一具體的行為線索(E03-S05 Model Selector
「Advanced mode」)——「進階模式」目前除了本身存在、可切換、可持久化
外,不做任何實際的功能區別(因為 Model Selector 等會被它閘控的功能
都還不存在)。這是誠實的 MVP 簡化,不是遺漏。

## 設計決策

1. **`ConversationSummary.mode` 設為必填欄位**(非 optional):每個對話
   從建立那一刻就有模式,不存在「沒有模式」的中間狀態。
2. **非樂觀更新(non-optimistic)**:mock 的 `setConversationMode`
   幾乎瞬間 resolve,沒有真實網路延遲需要隱藏——樂觀更新的價值主要在於
   「先讓使用者覺得快,之後才確認」,對這個 mock 而言額外的
   rollback 邏輯只會增加複雜度而沒有對應的體驗收益。畫面上的 mode
   只在**確認成功**後才更新,失敗時原本顯示的狀態從未改變,不需要
   rollback。
3. **「找不到對話」是獨立狀態,重用既有 `ErrorMessage code="NOT_FOUND"`**
   (E01-S012 已定義的文案),不是 EmptyState(那是「有效但空的集合」
   語意,不適用於「單一資源不存在」)、也不是把它和一般錯誤混在一起。
4. **列表項目現在連結到詳情頁**:完成 E03-S001 自己留下的伏筆
   （「不連結是因為路由還不存在」),不是臨時起意的重構。
5. **未修改 `/conversations/new` 的導向目標**(建立後仍導回列表,不是
   直接導去新對話的詳情頁)——這不是本 story AC 的必要條件,保持最小
   變更,避免對 S001 的既有決策做非必要的修改。

## 除錯歷程(對比 E03-S001)

**本輪 VERIFY 一次全過,無 FIX 循環**——這是把 E03-S001 那 5 輪除錯換來
的教訓,從一開始就直接應用在寫測試上的直接成果:

- E2E 全程只用站內連結點擊導覽,登入後**沒有任何一次** `page.goto()`
  (E03-S001 第 1 輪教訓)。
- 沒有依賴任何「換頁後另一個 widget 也要反映最新狀態」的假設——本
  story 的模式切換只影響**自己這一頁**,沒有其他頁面顯示對話的
  mode,所以不需要、也沒有呼叫 `router.refresh()`(E03-S001 第 3 輪
  教訓的反面應用:不是每個 mutation 都需要,只有真的有其他快取頁面
  會顯示同一份資料時才需要)。
- 「找不到對話」的 E2E 驗證從一開始就判斷為不可行(`/conversations/[id]`
  是真實動態路由,會經過 SessionGate,不像 E01-S017 的 `/maintenance`
  那樣完全不存在於路由樹、能繞過 SessionGate),直接用元件測試涵蓋,
  沒有繞路徑到 timeout 才發現。

## Assumptions / 計畫外事項

1. **「進階模式」目前沒有任何實際功能差異**:除了「模式本身存在、
   可切換、可持久化」外,本 story 刻意不假裝某個功能只在進階模式
   才有(因為那些功能——Knowledge Selector、Model Selector 等——都
   還不存在)。等 S05(Model Selector)真的實作時,會讀
   `ConversationSummary.mode` 來決定是否顯示,那才是這個欄位真正
   被「用到」的時刻。
2. **對話「擁有者」概念不存在**:mock 目前所有對話都是全域共用的
   假資料,沒有「這個對話屬於哪個使用者」的欄位或邏輯。真正的
   conversation-level authorization 待 E02(RBAC)+ E04(對話實體)
   都存在後才能實作,本 story 不得自行發明一套。
3. **「找不到對話」無法用 E2E 驗證**,原因與 E01-S017 的
   `/maintenance` 情境**表面相似但根因不同**(那裡路由完全不存在,
   繞過 SessionGate;這裡路由存在,會經過 SessionGate,而
   `page.goto()` 會清空 mock session)——已在 spec 檔案與本文件
   誠實記錄,改用元件測試提供對等驗證強度。
