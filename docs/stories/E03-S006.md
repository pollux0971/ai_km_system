## Scope 說明

SOURCE_BASELINE.md 的 E03 條列式大綱對 S06 只給了標題「E03-S06 Message
Composer」,沒有任何欄位形狀、送出語意或字數限制的描述——比 S05(至少
還有一行「Advanced mode。」)更精簡。epic 檔案(High Granularity 展開版)
對 S06-S010 的內文也確認是逐字相同的樣板,沒有額外具體規格。

為了不落入猜測,依 epic 檔案自己對後續故事的展開標題劃出明確邊界:
S07「Multi-line keyboard behavior」(把本故事的單行 `<input>` 升級成
`<textarea>`,並處理 Enter/Shift+Enter——與 S03→S04 知識選擇器
單選→多選的漸進升級模式相同)、S08「File attachment picker」、
S09「Send-message optimistic state」(真正送出訊息並處理
pending/sent/failed 狀態;訊息實體本身是 E04-S02,Team B 擁有,目前
不存在)。

因此本 story 刻意只做**輸入框本身的 input/validation/reset 生命週期**:
不寫入任何訊息清單、不呼叫任何 mock 後端、不新增 `lib/conversations.ts`
的任何內容。送出一則合法草稿只證明輸入框會清空、準備好輸入下一則
——把它接上真正的送出行為是 S09 明確的責任。這與 S01 建立
`ConversationSummary`(當時完全沒有任何訊息串功能)是同一種漸進式
atomic story 精神的延續。

## 設計決策

1. **`MessageComposer` 完全自我包含,不需要修改 `lib/conversations.ts`**
   ——這本身就是範圍界定正確的訊號:composer 目前只管理自己的本地
   `draft` state,沒有任何需要持久化的東西。
2. **維持單行 `<input type="text">`,不是 `<textarea>`**——多行行為是
   S07 明確標題「Multi-line keyboard behavior」的責任,提前做等於
   侵犯下一個 story 的範圍。
3. **驗證邏輯是 `draft.trim().length > 0`,Send 按鈕在無效時原生
   `disabled`**——延續 S04 knowledge-selector 的論證:disabled 的原生
   行為本身就是 fail-closed 機制,使用者在瀏覽器層級就無法觸發無效
   提交,不需要額外的執行期防護。`handleSubmit` 內仍多加一層
   `if (!isValid) return;` 防禦(可被 `fireEvent.submit` 繞過按鈕直接
   測試),不只依賴按鈕的 disabled 屬性。
4. **Telemetry 只記錄 `length`,不記錄 `draft` 原文**——AC7「audit
   payload 不得包含 secret/credential/raw sensitive content」;使用者
   輸入的訊息內容可能是任意甚至敏感文字,記錄長度足以證明「送出
   動作發生過」,不需要也不應該把原文寫進 telemetry payload。
5. **事件命名為 `conversation_message_compose_submit`,不是
   `conversation_message_send_success`**——誠實反映這個故事只做到
   「composer 提交」,不是「訊息真的送出去」,避免命名本身造成
   對能力完成度的誤導。
6. **沒有字數上限**——SOURCE_BASELINE 全文搜尋字元/字數/character
   limit/max length 皆無命中,依「不發明未定義限制」原則不新增
   人為上限。
7. **不論對話目前是 Normal 或 Advanced 模式,composer 都會顯示**——
   與 ModelSelector(明確綁定 Advanced 模式)不同,composer 是任何
   對話都需要的基礎能力,規格沒有把它綁定到特定模式。

  （新增)——單行輸入框 + 本地 `draft` state + disabled-until-valid

  （新增)——5 個測試:初始空白/disabled、輸入後啟用、純空白仍
  disabled、送出後清空且 telemetry 不含原文、繞過按鈕直接送出
  invalid 表單不觸發任何行為。
- `apps/web/src/app/(app)/conversations/[id]/_components/conversation-detail.tsx`
  ——引入並無條件 render `MessageComposer`(不受 mode 影響,置於
  ModelSelector 之後)。
- `apps/web/src/app/(app)/conversations/[id]/_components/conversation-detail.test.tsx`
  ——既有「shows the title...」測試補上 composer 存在的斷言;新增
  1 個 E03-S006 專屬測試(Normal 模式下 composer 仍顯示,按鈕預設

  composer 出現且初始 disabled、輸入後可送出並清空、純空白輸入

## Assumptions / 計畫外事項

1. **送出按鈕文案用「送出」而非「傳送」**:兩者在中文聊天介面用語
   上沒有實質語意差異,選「送出」純粹是中性用詞;真正的誠實界線
   在程式碼註解與本文件(明確聲明尚未真正傳送/持久化),不是靠
   按鈕文案本身傳達完成度。
2. **送出後只清空本地草稿,不做任何持久化或呈現**:刻意如此,以
   避免在 S09 明確擁有「Send-message optimistic state」之前搶先發明
   訊息清單/歷史的資料結構。
3. **沒有為訊息內容設任何字數上限**:SOURCE_BASELINE 未定義,依
   「不發明」原則不新增限制。
