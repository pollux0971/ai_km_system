## Scope 說明

SOURCE_BASELINE.md 對 S07 只給標題「E03-S07 Multi-line Input」,epic 檔案
展開版把它命名為「Multi-line keyboard behavior」。延續 S06 已確立的邊界
論證(S08 File attachment picker、S09 Send-message optimistic state 都是
各自獨立的 story),本 story 把 S06 的單行 `<input>` 升級成多行
`<textarea>`,並加上 Enter 送出 / Shift+Enter 換行的鍵盤行為——與
S03→S04 知識選擇器單選→多選的漸進升級模式相同。

## 設計決策

1. **`<input type="text">` 升級為 `<textarea rows={3}>`**——`rows={3}`
   是沒有規格依據下的合理最小視覺選擇(MVP 可簡化視覺),純粹讓多行
   輸入框在初始狀態就有可視的多行高度,不是規格要求的精確值。
2. **Shift+Enter 換行完全不需要額外程式碼**——原生 `<textarea>` 在任何
   Enter(含 Shift+Enter)都會插入換行,除非 JS 呼叫
   `preventDefault()`;鍵盤處理常式只在「`Enter` 且沒按 `Shift` 且草稿
   有效」時才呼叫 `preventDefault()` 並送出,因此 Shift+Enter 完全落入
   「什麼都不做」的分支,原生行為自然生效。這是刻意設計,不是遺漏。
3. **草稿無效(空白/純空白)時,單純按 Enter 也不攔截**——只有「有效
   草稿 + Enter + 無 Shift」才會攔截送出。空白草稿按 Enter 會退回原生
   行為(插入換行字元),而不是被完全吞掉。這個決策在隔離跑 E2E 時
   被自己的測試斷言錯誤(見下方 Gate 紀錄的說明)反向驗證是正確的:
   對空白 textarea 按 Enter,瀏覽器真的會插入一個換行字元(值變成
   `"\n"`,而非停留在空字串),`"\n".trim()` 仍是空字串,Send 按鈕
   fail-closed 的保證不受影響。
4. **`submitDraft()` 從 `handleSubmit` 抽出成獨立函式**,同時被表單
   `onSubmit`(按鈕點擊路徑)與 `onKeyDown`(Enter 鍵路徑)呼叫——兩條
   路徑走同一份驗證 + telemetry + 清空邏輯,不重複程式碼、不會兩條
   路徑行為不一致。

## 變更檔案

- `apps/web/src/app/(app)/conversations/[id]/_components/message-composer.tsx`
  ——`<input>` 改為 `<textarea rows={3}>`;新增 `submitDraft()` 共用
  函式;新增 `handleKeyDown` 處理 Enter/Shift+Enter。
- `apps/web/src/app/(app)/conversations/[id]/_components/message-composer.test.tsx`
  ——新增 4 個 S07 測試(Enter 送出有效草稿、Shift+Enter 不送出、空白
  草稿按 Enter 不送出、純空白草稿按 Enter 不送出);同時修正 S06 遺留
  的一個測試命名精確度問題(獨立審核 E03-S006 時標記的 MINOR 建議:
  原測試標題宣稱驗證「form does not clear」卻從未真的輸入任何草稿,
  現在改為先輸入純空白草稿、繞過按鈕送出、斷言草稿值真的維持不變)。
- `tests/e2e/specs/message-composer-multiline.spec.ts`(新增)——3 個
  E2E,使用 Playwright 真實鍵盤模擬(`page.keyboard.press`/`.type`),
  不是 component-level 的 `fireEvent.keyDown`——jsdom 的 `fireEvent`
  不會模擬 textarea 原生換行插入行為,要證明 Shift+Enter 真的插入
  換行字元,必須在真實瀏覽器層級驗證。
