## Scope 說明

SOURCE_BASELINE.md 對 S08 只給標題「E03-S08 File Attachment」,epic 檔案
展開版命名為「File attachment picker」。開工前先用背景 agent 徹底搜尋
`AI_KM_BMAD_High_Granularity/` 全文,確認以下皆無定義:檔案類型/MIME
允許清單、檔案大小上限、單則訊息附件數量上限、病毒掃描要求。全文唯一
具體的檔案格式清單(PDF/DOCX/PPTX/XLSX/CSV/TXT/Image/Web/Scan PDF,
SOURCE_BASELINE.md:265-277)屬於 E06 Knowledge Ingestion 的 parser story
（Team B),與本 story 的聊天附件選擇器無關;真正的驗證 story
（E06-S03 MIME allowlist validation、E06-S04 File-size validation、
E06-S07 Antivirus hook contract)全部是 Team B 擁有、尚未展開的空標題。

延續 E03-S006 面對同一種「validate size」樣板文字時,明確拒絕發明訊息
字數上限的先例(「不發明未定義限制」)——本 story 同樣不發明檔案
類型/大小/數量限制。且 Frontend/BFF 依 E03 epic 自己的開發邊界
「不得直接連 Object Storage」,本來就不可能有真正的上傳行為,所以
即使有真正的大小限制也無從在這裡強制執行。因此本 story 純粹是
**客戶端選擇/預覽/移除**能力,不上傳、不驗證、不呼叫任何 mock 後端。

## 設計決策

1. **`attachments` state 放在 `MessageComposer`,不放在
   `FileAttachmentPicker`**——選取的檔案是「這則草稿的一部分」,會
   跟文字草稿一起送出/清空,不是像 ModeSwitch/KnowledgeSelector/
   ModelSelector 那樣獨立持久化到對話的欄位。`FileAttachmentPicker`
   是純展示型受控元件(`files`/`onFilesSelected`/`onRemove` props),
   不擁有自己的 state。
2. **`isValid` 從「文字非空白」擴大為「文字非空白 OR 至少一個附件」**
   ——只附加檔案不打字(例如純粹傳一張照片)是聊天應用的正常情境,
   不需要文字才能送出。這是 S06/S07 既有 `isValid` 的自然延伸,不是
   新概念。
3. **不設 `accept` 屬性、不限制檔案類型/大小/數量**——依上述 Scope
   說明的無發明原則。移除單一檔案的操作(`onRemove(index)`)也不做
   任何額外限制。
4. **`<input type="file">` 每次選取後重設 `value = ""`**——瀏覽器對
   「值未改變」的 file input 不會重新觸發 `onChange`,重設後使用者
   才能在移除某檔案後重新選取同一個檔案。這是標準技術處理,不是
   業務規則發明。
5. **送出時 telemetry 只記錄 `attachmentCount`,不記錄檔名**——延續
   S06 對訊息原文的相同論證:檔名本身可能包含敏感資訊(例如
   「機密文件.docx」),AC7 要求 audit payload 不含 raw sensitive
   content。
6. **隔離跑 E2E 時發現的一個測試范圍問題(非實作問題)**:
   `page.getByRole("listitem")` 在沒有限定範圍時,同時比對到側邊導覽
   的 `<ul>/<li>` 結構(側邊導覽本身也是清單語意),導致「應該有 2 個
   附件」的測試量到 5 個。修正為把查詢限定在 composer 的 `<form>`
   內(`page.locator("form").getByRole("listitem")`),不是修改元件
   本身——這純粹是測試選擇器精確度的問題。

| Gate | 指令 | Exit code | 關鍵測試 |
|---|---|---|---|
| typecheck | `pnpm typecheck` | 0 | — |
| lint | `pnpm lint` | 0 | — |
| build(獨立跑) | `pnpm build` | 0 | 路由結構不變 |
| unit | `pnpm --filter @ai-km/web test`(併入 `pnpm test`) | 0 | 35 檔 181 個測試全過 |
| E2E(關鍵 seam,先隔離跑) | `pnpm --filter @ai-km/e2e exec playwright test specs/file-attachment-picker.spec.ts` | 第一次跑 4 個失敗(測試選擇器範圍問題)、修正後 0 | 見設計決策 6 |
| E2E(全量,併入 `pnpm test`) | `pnpm --filter @ai-km/e2e test` | 0 | 55 個(既有 51 + 新增 4)全過 |

**獨立審核階段發現並修復的真正 FIX 循環**(與上面「先隔離跑」的預檢
不同,這次是 DEV 已經宣稱 done 之後,獨立審核角色重新從 gate 1
force 重跑時才發現):`pnpm turbo run typecheck lint --force` 顯示
`@ai-km/e2e#typecheck` 紅——`specs/file-attachment-picker.spec.ts` 使用
`Buffer.from(...)`(Playwright `setInputFiles` 的標準寫法),但整個
repo 從未安裝 `@types/node`,而這是 E2E 測試套件裡第一個真正引用
Node.js 全域型別的 spec,所以這個缺口一直潛伏未被觸發。

**根因是 DEV 階段自己的 VERIFY 有漏洞**:`pnpm typecheck` 在撰寫這個
E2E spec **之前**就跑過了,之後只用 `playwright test`(先隔離、再
全量)驗證 E2E,而 `playwright test` 底層用 esbuild/SWC 做型別抹除式
轉譯,不做完整型別檢查,所以沒有攔到這個問題。DEV 階段的 EVIDENCE
初稿因此誤報「typecheck 0」——但那是對「加入 E2E spec 之前」的 diff
跑的結果,不是對最終 diff。

**修復**:在 `tests/e2e/package.json` 加入 `@types/node@^22.10.0`
（版本與 `apps/web`/`apps/admin` 既有一致)、`pnpm install` 更新
lockfile、確認 `tsc --noEmit` 轉綠。接著**從 gate 1 重新跑完整
VERIFY 序列**(不是只重跑失敗的 typecheck):`typecheck`+`lint`
force 全綠(32/32)、`build` force 全綠(12/12)、`test` force 全綠
（181 unit + 55 E2E)。

**這次教訓**:之後任何 story 若在 IMPLEMENT 階段新增 E2E spec 檔案,
VERIFY 的 `pnpm typecheck` 必須在**新增/修改所有檔案之後**才跑最後
一次,不能只信任「寫 spec 之前跑過一次」——`playwright test` 能通過
不代表 `tsc` 會通過。
