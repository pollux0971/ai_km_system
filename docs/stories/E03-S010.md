## Scope 說明

SOURCE_BASELINE.md 與 epic 檔案對 S10 只給標題,內文與其他所有 story
逐字相同的樣板,完全沒有 SSE 對 WebSocket 的選擇、chunk 格式、
重連機制等任何技術細節——連「重連」都明確是另一個獨立、尚未建置的
故事(E03-S031「stream disconnect/reconnect UX」)。全文搜尋 assistant
回覆的資料形狀(role/content/citations/sources/confidence/streaming
flag)在整個 `AI_KM_BMAD_High_Granularity/` 裡沒有任何定義。

背景 agent 徹底核對後確認:S11(Generation Status,顯示
Searching/Reading/Generating 階段)、S12(Stop Generation,中止按鈕)、
S13/S14(Citation badge/preview)、S21(Answer State enum:ANSWERED/
PARTIAL/NO_EVIDENCE/ERROR/PERMISSION_DENIED/SOURCE_UNAVAILABLE)全部
是獨立、平行、尚未建置的故事,彼此與 S10 之間在整份 epic 檔案裡沒有
任何一處以 story ID 明確依賴或引用。`contracts/openapi/core.yaml`
明確聲明「真正的 endpoint 必須先與 Team B 協商」,而 E04(RAG &
Conversation Intelligence)與 E12(Model & Prompt Platform)兩個
Team B epic 都還不存在,沒有真正的 Model Gateway、沒有真正的 SSE/
WebSocket contract。

因此本 story 精確界定為:**串流渲染器**本身——給定任何非同步到達的
文字片段來源,漸進顯示、正確處理完成與失敗。這個能力不需要真正的
後端就能誠實建構與測試(渲染邏輯與傳輸機制正交),延續 S01「Team A
自己的本地 mock,非真正 contract」的既有模式,而非發明一個假裝
已完成的真實整合。明確排除:S11 的階段指示詞彙、S12 的中止按鈕、
S13/S14 的引用渲染、S21 的答案品質分類 enum。

## 設計決策

1. **`lib/streaming.ts` 是純粹的 mock chunk 來源,不使用瀏覽器真正的
   `EventSource`/`WebSocket` API**——消費端(`message-thread.tsx`)只
   依賴 `AsyncGenerator<string>` 這個介面本身,不關心 chunk 怎麼來的;
   真正串接 E04/E12 的 SSE 或 WebSocket 時,只需要替換這一個檔案。
2. **模擬回覆文字是固定、明確標示為模擬的佔位文字**,不是假裝合理的
   AI 生成內容——延續 S05「雲端模型(尚未啟用)」的誠實標示原則:
   可見但清楚標記不是真的。
3. **按字元切割而非按空格切割**——中文沒有空格分詞,若用
   `.split(" ")` 整段回覆會變成單一巨大 chunk,完全違背「漸進顯示」
   這個能力本身要證明的東西。`Array.from` 而非索引迴圈,確保萬一
   之後出現 BMP 外的字元也不會被切壞。
4. **`delayMs` 參數預設 20ms、可覆寫為 0**——production 用途需要真正
   人類可感知的漸進節奏(瞬間完成就沒有「串流」的視覺意義);單元
   測試傳入 0 讓整段回覆在一個 microtask flush 內解析完,不需要為了
   加速測試而引入 fake timer 包裹 async generator 的複雜度與脆弱性。
5. **`Message.role` 從 `"user"` 擴大為 `"user" | "assistant"`**——
   這是第一個真正會產生 assistant 角色的故事,現在加入型別是完成
   時機正確(S09 當時明確論證過「沒有東西會產生它,現在加就是投機
   的未使用程式碼」,現在有了)。
6. **`receiveAssistantReply` 是獨立函式,不是 `sendMessage` 加一個
   role 參數**——「送出」是使用者發起的動作;回覆是「到達/收到」,
   語意不同(無附件、不同的行為者),獨立命名比 overload
   `sendMessage` 的簽章更清楚。重用與 `sendMessage` 完全相同的
   `NOT_FOUND` fail-closed 檢查,不是另外發明一個模擬失敗機制。
7. **`streamAssistantReply()` 不接收使用者訊息內容作為「prompt」
   參數**——目前的 mock 永遠回傳固定文字,加一個沒有任何程式碼會
   讀取的參數是死參數;真正串接 Model Gateway 時再由那個故事決定
   簽章,不在這裡投機性地半做。
8. **`DisplayMessage` 新增 `streaming`/`stream-failed` 兩種 kind**,
   與 S09 既有的 `pending`/`failed` 對稱(啟動→嘗試→重試的三段式
   handler:`startStream`/`runStream`/`handleRetryStream`,結構完全
   對應 `handleComposerSubmit`/`attemptSend`/`handleRetry`)。
9. **user 訊息送出成功後自動觸發串流回覆**(`attemptSend` 成功分支
   呼叫 `startStream()`)——這是目前唯一有根據觸發回覆的時機點,不
   需要額外發明一個手動觸發 UI。
10. **修正一個型別安全缺口**:`attemptSend`/`handleRetry` 原本的
    reconcile 篩選條件是 `entry.kind !== "sent"`——這在 S09 寫下時
    正確(當時「非 sent」只可能是 `pending`),但 S10 新增
    `streaming`/`stream-failed` 後,這個篩選在型別上會涵蓋到形狀不同
    的變體,`tsc` 正確攔下(`{...entry, kind: "failed"}` 對
    `streaming`/`stream-failed` 缺少必要欄位)。修正為精確篩選
    `entry.kind === "pending"`(`attemptSend`)與
    `entry.kind === "failed"`(`handleRetry`)——這在執行期本來就不會
    出錯(`localId` 用 `crypto.randomUUID()` 產生,不同來源的項目不會
    撞到同一個 `localId`),但修正後型別與執行期邏輯完全對齊,不再
    依賴「反正不會撞到」的隱含假設。
11. **`content` 從 `<li>` 內的裸文字節點改成獨立 `<span>{content}</span>`**
    ——原本 `{roleLabel}{content}` 混在同一個 `<li>` 裡,`content` 是
    夾在多個元素之間的裸文字節點,無法被 Testing Library 的
    `getByText` 精確定位到(它會抓到整個 `<li>` 混合後的文字)。獨立
    包成 `<span>` 後每段內容都可獨立查詢——這同時修正了測試撰寫時
    發現的問題,也是更正確的標記方式。
12. **E2E 沿用 S08 已修正過的 `listitem` scoping 問題**:未限定範圍的
    `page.getByRole("listitem")` 同時比對到側邊導覽的 `<ul>/<li>`,
    這次改用 `page.getByRole("main")` landmark 限定範圍(對話詳情頁
    整個內容,含 `MessageThread`,都在 `<main>` 裡,側邊導覽是獨立的
    landmark)。

**本輪過程中的兩個真實插曲**(皆在正式 gate 序列跑到最終全綠之前
發現並修復,不是造假或繞過):

   測試最初斷言串流完成後畫面顯示本地累積的文字,但元件正確地
   信任 `receiveAssistantReply`(mock 的)回傳值,而非直接回顯本地
   累積字串——這模擬了真實後端會回傳「canonical」內容的行為。測試
   沒有為這個案例配置對應的 mock 回傳值,修正為明確配置且改用
   `toHaveBeenCalledWith` 直接驗證累積邏輯本身,比只驗證畫面顯示
   更精確。
2. **型別安全缺口(見設計決策 10)**:`tsc` 正確攔下一個 S09 遺留、
   S10 新增 kind 後才浮現的過寬篩選條件,修正為精確篩選。

## Assumptions / 計畫外事項

1. **模擬回覆文字內容是固定佔位文字,不是根據使用者訊息產生的
   「智慧」回覆**:SOURCE_BASELINE 沒有定義任何生成邏輯,依「不發明」
   原則,明確標示為模擬而非假裝真實。
2. **`role` 只有 `"user" | "assistant"` 兩種值**:沒有加入
   `"system"` 或其他角色,規格未定義任何需要它們的情境。
3. **串流失敗的決定性觸發條件與 S09 相同(對話 id 不存在)**——重用
   既有機制,不發明新的模擬失敗方式。
4. **不使用/不部分實作 S21 的 Answer State enum**:那個 enum
   （ANSWERED/PARTIAL/NO_EVIDENCE 等)是語意層級的答案品質分類,
   需要真正的 RAG/權限系統才有意義;本 story 自己的 sent/streaming/
   stream-failed 是單純的傳輸層機制狀態,刻意不混用。
