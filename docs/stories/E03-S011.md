# E03-S011 — Searching/Reading/Generating status UI

- 狀態:DONE
- Branch:story/E03-S011-generation-status-ui
- 日期:2026-08-14

## Scope 說明

與 E03 epic 內大多數 story 不同,SOURCE_BASELINE.md 對 S11 給了具體內容
（line 1146-1152):

```
E03-S11 Generation Status
顯示：
- Searching
- Reading
- Generating
```

`GenerationPhase` 型別直接使用這三個英文詞作為值(可直接對應回規格
原文),`GENERATION_PHASE_LABELS` 另外持有繁體中文顯示文字——與
`ai-models.ts`的`AiModel` id/label 分離方式相同。三項條列的順序視為
執行順序(search → read → generate 也是標準、顯而易見的 RAG pipeline
順序——先檢索、再處理檢索到的內容、最後產生答案——不是任意發明的
排序)。

明確排除:S12「Stop Generation」(中止按鈕)、S13/S14(引用徽章/
預覽——模擬回覆是純文字,無可引用內容)、S21「Answer State」
（ANSWERED/PARTIAL/NO_EVIDENCE 等語意層級的答案品質分類,需要真正的
RAG/權限系統才有意義)。

## 設計決策

1. **`lib/generation-status.ts` 獨立成新檔案**——延續
   `ai-models.ts`/`knowledge-scopes.ts`/`streaming.ts` 各自獨立成檔的
   既有慣例。
2. **`phase` 加在既有的 `"streaming"` DisplayMessage 變體上,不是
   新增一個獨立的 kind**——三個階段是「送出真正文字之前」的暫時性
   前置狀態,概念上仍屬於同一次串流嘗試,不需要另開一條狀態分支。
3. **`runGenerationPhases` 的節奏設計經過兩輪修正**(見下方 Gate 紀錄
   的除錯過程):最初「每個階段之間暫停,最後一個階段(generating)
   之後不暫停」,但這會讓 generating 的可視時間完全取決於
   `streamAssistantReply()` 第一個真實 chunk 多快抵達(預設節奏下
   幾乎瞬間),等於「顯示了但幾乎沒人看得到」,不符合「顯示：
   Generating」這個故事本身的目的。修正為**每個階段(含最後一個)
   都有相同的可視時長**,行為對稱、一致。
4. **`phase` 只在真正收到第一個文字 chunk 時才清空為 `null`**,而不是
   在階段序列跑完的當下就清空——這同樣是除錯過程中發現的真正實作
   缺口(不只是測試問題):原本的寫法會讓 generating 幾乎不可能被
   觀察到,即使 UI 邏輯上「有」顯示過。
5. **節奏預設值從最初的 300ms 調整為 600ms**——不只是為了讓 E2E
   斷言更容易抓到時序,也是真正的產品層面考量:300ms 對人類閱讀
   一個階段標籤而言太快,三個階段快速閃過會讓人幾乎看不清楚寫的
   是什麼字。
6. **修正 E03-S010 既有 E2E 測試因本故事而產生的真正回歸**:
   `streaming-response.spec.ts` 原本用「等待『AI 回覆中…』消失」
   作為「已經完全結算」的代理訊號——但 S011 讓這段文字要等三個階段
   跑完才會出現,導致這個等待條件在早期階段就已經(trivial 地)
   成立,測試因此提前往下跑,在真正的回覆送達並持久化之前就去檢查
   訊息數量。改為等待「thread 內完全沒有任何 `role="status"` 元素」
   （涵蓋 pending/streaming/每個 phase 狀態),這是真正精確、不隨
   狀態機演進而碎裂的「已結算」訊號。
7. **同時發現並修正之前用「訊息清單數量變成 2」當作等待條件的錯誤
   直覺**:樂觀新增的 streaming 佔位項目本身就會讓數量提前變成 2,
   遠早於真正持久化完成——數量不能拿來當作「已完成」的代理訊號。

  才清空;render 依 `phase` 顯示對應中文標籤,無 phase 時退回既有的

- `apps/web/src/app/(app)/conversations/[id]/_components/message-thread.test.tsx`
  ——新增 `@/lib/generation-status` 的 mock 與合理預設值;新增 3 個

  重新跑一次階段序列。
- `tests/e2e/specs/generation-status.spec.ts`(新增)——1 個 E2E:
  送出訊息後依序看到搜尋中/讀取中/生成中,最終正確結算。
- `tests/e2e/specs/streaming-response.spec.ts`(修正,非新故事範圍
  外變更——是讓 S010 既有測試在 S011 改變時序模型後仍然正確反映
  「已結算」狀態的必要修正,見設計決策 6/7)——改用
  「`role="status"` 數量歸零」取代「特定文字消失」/「清單數量」作為
  等待條件。

**這是本 epic 內除錯過程最完整的一個 story,誠實記錄每一輪**:

1. **測試 mock 設定問題**:`vi.mock("@/lib/generation-status", async () => { ... vi.importActual ... })` 的非同步 factory 寫法導致 mock override 沒有正確生效——簡化為與檔案內其他兩個 mock 相同的同步 factory 寫法後解決(純測試層面問題,非實作問題)。
2. **測試本身的競態**:「shows each phase label in order」測試沒有讓 `streamAssistantReply` 保持 pending,導致 phase 序列跑完後立即用預設 mock 瞬間結算,`waitFor` 來不及觀察到中間狀態——修正為讓該測試的 `streamAssistantReply` 永久 pending。
3. **真正的實作缺口**(不是測試問題):`phase` 原本在階段序列跑完的當下就清空為 `null`,不管真實文字是否已經開始抵達——這讓「generating」幾乎不可能被穩定觀察到。修正為只在收到第一個真實 chunk 時才清空。
4. **E2E 時序問題**:預設 300ms 節奏對 Playwright 逐一斷言三個階段而言太快(下一個階段可能在斷言輪詢開始前就已經又跳過去了),對真人閱讀也太快——調整為每階段(含最後一個)都有 600ms 完整可視時長。
5. **既有 S010 E2E 測試的真正回歸**:`streaming-response.spec.ts` 用「等待特定文字消失」/「清單數量」當作「已結算」的代理訊號,S011 改變時序模型後這兩個代理訊號都不再可靠——修正為「等待 thread 內 `role="status"` 元素數量歸零」這個精確訊號。
6. **本人自己的操作失誤**:診斷用的一次性指令(`cd apps/web && cat > ...`)不慎讓 shell 的工作目錄停留在 `apps/web`,由於 Bash 工具的 shell 狀態會在多次呼叫間延續,導致後續數次「全 repo」驗證(`pnpm typecheck`/`pnpm turbo run typecheck lint --force`)其實只在 `apps/web` 範圍內執行(缺少 `@ai-km/admin`、`@ai-km/e2e` 的獨立 typecheck),得到的「全綠」結論並不完整。發現後立即 `cd` 回 repo root,重新執行完整的 VERIFY 序列,確認涵蓋全部 packages。

以上每一輪都定位到根因後才修正,沒有放寬斷言、沒有跳過測試、沒有用
`--force`/`|| true` 之類的手法讓 gate 變綠。

## Assumptions / 計畫外事項

1. **三個階段的順序視為 search → read → generate**:SOURCE_BASELINE
   只給條列順序,沒有明文說明這就是執行順序,但這是標準 RAG
   pipeline 的顯而易見順序,不是任意假設。
2. **節奏(每階段 600ms)是沒有規格依據的視覺選擇**:SOURCE_BASELINE
   未定義任何時間長度,依「MVP 可簡化視覺」選用讓人類可讀、E2E
   斷言也可靠的數值。
3. **修正既有 E03-S010 E2E spec 的等待條件**屬於本 story 必要範圍
   （讓既有測試在新的時序模型下仍正確反映真實狀態),不是無關的
   順手重構——沒有改變 S010 測試驗證的行為本身,只改變了「如何
   判斷已經結算」的技術手段。
