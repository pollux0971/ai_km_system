SOURCE_BASELINE.md 對 S12 只給標題「E03-S12 Stop Generation」,epic
檔案展開版命名為「Stop generation interaction」,內文與其他大多數

`docs/stories/E03-S010.md`)。這是 S10/S11 兩個 story 都明確排除、
留給本 story 的中止按鈕功能——現在補上。

沒有任何規格文字定義「停止」之後應該發生什麼(保留已生成的部分文字?
整個丟棄?可以重新開始嗎?),因此本 story 的行為設計完全基於對現有
串流狀態機(S09-S11 已建立)的合理延伸,並參考真實聊天產品的常見
慣例(ChatGPT、Claude 等停止生成後通常保留已產生的部分內容,而不是
整個丟棄),而非發明任意行為。

## 設計決策

1. **`stoppedRef` 是純 mutable `Set`,不是 React state**——按下停止
   本身不需要觸發重新渲染(迴圈會在自己下一次迭代時注意到),用
   `useRef` 避免不必要的 re-render,也避免把「使用者按過停止」這種
   短暫的命令式意圖硬塞進宣告式的 UI state。
2. **停止只在「目前正在等待的下一個值」解析之後才會生效**,不是
   立即中斷——這如實反映非同步產生器(generator)的本質限制:
   `for await` 迴圈只能在每次 `.next()` 解析之後才有機會檢查旗標。
   對真正的 mock 實作(`streamAssistantReply` 每個字元 20ms、
   `runGenerationPhases` 每階段 600ms)而言,這個延遲最多幾百毫秒,
   使用者不會有感;對真正接上 SSE/WebSocket 的未來實作而言,這也是
   業界標準做法(送出 abort 訊號,伺服器端在下一個可中斷點停止)。
3. **有部分內容時,停止後透過與自然完成完全相同的
   `receiveAssistantReply` → 收斂為 `sent` 路徑持久化**——不是發明
   新的持久化機制。這對應真實聊天產品的常見行為:停止代表「這樣就
   夠了」,不是「整個作廢」。
4. **完全沒有內容時(在三階段序列跑完前就按停止),整個項目直接從
   清單移除**,不呼叫 `receiveAssistantReply` 持久化一則空白內容的
   訊息——沒有東西值得保留時,乾淨地取消才是正確行為。
5. **停止按鈕只在 `kind === "streaming"` 時顯示**——一旦收斂為
   `sent`/`stream-failed`,已經沒有「進行中的生成」可以停止,按鈕
   自然透過既有的 kind-驅動 render 邏輯消失,不需要額外邏輯。
6. **新增 `conversation_message_stream_stopped` telemetry 事件**,
   帶有 `hadContent` boolean 屬性(不是原文內容本身,延續既有的
   「不記錄使用者原文」紀律)——區分「停止時已有內容」與「停止時
   還沒有任何內容」兩種結果,不與既有的
   `_attempt`/`_success`/`_failure` 三個事件混用(停止不是失敗,也
   不是「正常」成功,是第三種明確結果)。

**兩輪除錯,皆已定位根因,誠實記錄**:

1. **單元測試 mock 設計缺陷**:最初用「永久不 resolve 的 Promise」
   模擬「串流仍在進行、還沒有下一個字元」,結果導致 `for await`
   迴圈永遠卡在等待這個 Promise,永遠沒有機會檢查停止旗標——這個
   mock 寫法意外準確地模擬出「停止機制本身有無法瞬間中斷已在進行中
   等待」這個真實限制(見設計決策 2),但也讓測試本身卡死。修正為
   「可控制何時 release 的 gate」模式(與 S010/S011 已使用的模式
   相同):先按下停止,再讓被卡住的 `.next()` 解析,如實模擬「停止
   請求發生在等待下一個值期間,等到那個值解析時迴圈才注意到並跳出」
   這個真實時序。
2. **E2E 時序誤判**:第二個 E2E 測試最初只等待「停止生成」按鈕出現
   （按鈕在串流一開始就會出現,遠早於任何階段或文字顯示)就等待
   300ms 後按下停止,但完整的三階段序列本身就需要約 1.8 秒——300ms
   遠不足以跑到真正開始串流文字的時間點,導致停止時 accumulated 仍
   是空字串,項目被移除而非收斂為已送出,與測試想驗證的情境不符。
   修正為等待「AI 回覆中…」(只有真正開始收到文字後才會顯示的
   通用回退狀態)出現,才代表真正進入文字串流階段。

## Assumptions / 計畫外事項

1. **有部分內容時保留並持久化,而非整個丟棄**:SOURCE_BASELINE
   未定義,依真實聊天產品的常見慣例(而非任意假設)採用「停止=夠了」

   mock 節奏(20ms/字元、600ms/階段)而言延遲在使用者可接受範圍內。

   互動,依「不發明」原則不新增。
