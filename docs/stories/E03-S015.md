## Scope 說明

SOURCE_BASELINE.md 對 S15 只給標題「E03-S15 Citation Open Source」
（第 1178 行),完全沒有內文——是整個引用三部曲（S13/S14/S15)中最少
的一個（對比 S13 的一行範例、S14 的三項欄位列表)。epic 檔展開版把
標題具體化為「Open-source citation navigation」,是本 story 採用
「navigation」（真正的路由導覽,不是彈窗/內嵌展開)作為具體 UI 呈現
方式的依據。

明確排除:
- 不是真正的文件檢視器——沒有真正的文件儲存、Object Storage 或渲染
  服務（E04/E12 尚不存在,且 Frontend/BFF 直連 Object Storage 本身
  就是被禁止的),因此這個「開啟原始來源」頁面誠實地用明確標示的
  版面配置預覽取代真正的文件內容,不是假裝有真正內容。
- S16「Citation Permission Error」延續 S13/S14 已確立的排除範圍——
  本 story 沒有處理「無權限存取來源」的情境。

## 設計決策

1. **獨立的頂層路由 `/citations/[id]`**（不是巢狀在
   `/conversations/[conversationId]/citations/[citationId]` 底下)——
   `getCitationSource(id)`（S14 建立)本身不是依對話 scope 的查詢,
   巢狀路由會暗示一個資料模型裡不存在的從屬關係。沒有「返回對話」
   連結——`(app)` layout 底下每個路由都已經有常駐的 sidebar 導覽
   （AppShell),與 `/profile` 頁面一樣不需要額外的專屬返回連結。
2. **重用 S14 的 `getCitationSource`,不新增 lib 函式**——這個路由是
   同一個 by-id 查詢的第二個、獨立的消費者,證明 citation id 是真正
   可攜的識別碼,不是 drawer 自己發明的內部概念。
3. **與 S14 drawer 內容故意不同**,即使兩者都讀同一組
   File/Page/Snippet 欄位——drawer 是快速預覽,這個頁面代表「真正
   打開文件」。用一段明確標示的版面配置預覽段落取代真正的文件內容
   區域,而不是原封不動重複 drawer 的 snippet 當作「這就是完整文件」
   ——延續本專案每個 mock 的誠實標示紀律（`MOCK_REPLY` 的
   「（模擬回覆)」前綴、E03-S005 的「尚未啟用」雲端模型)。
4. **同分頁導覽（`<Link>`,不是 `target="_blank"`)**——SOURCE_BASELINE
   完全沒有指定分頁行為,這個 app 目前所有其他導覽（對話列表、
   sidebar、「查看全部對話」)都是同分頁,為一個規格沒提到的細節
   新增分頁行為是無依據的額外複雜度。
5. **「開啟原始來源」連結只在 drawer 的 `kind === "loaded"` 時顯示**——
   drawer 還在載入或已經失敗/查無資料時提供「開啟」一個不存在或還
   不確定的來源,沒有意義。
6. **新增 `conversation_citation_open_source_attempt/_success/_failure`
   telemetry 三件套**,延續既有命名規則,與 S14 的
   `conversation_citation_preview_*` 並列而非重疊——這是一個獨立的
   使用者動作（導覽到新頁面),不是同一次 preview 操作的延伸。

**除錯過程（誠實記錄,自己在 IMPLEMENT 階段抓到並修正,未曾提交任何
錯誤版本)**:

1. **`citation-source-view.tsx` 誤用 `role="status"` 標記靜態文字**：
   最初把版面配置預覽段落標成 `role="status"`（可能是無意識沿用了
   別處「載入中」文字的既有模式),但 `role="status"` 是給會即時更新
   的狀態通知用的 live region,不是給不會變化的靜態說明文字用——這是
   ARIA 誤用,寫元件當下就自己發現並移除,沒有留在測試或 commit 裡。
2. **原本規劃的第二個 E2E（未知 citation id → NOT_FOUND)是一個真正
   會踩雷的測試設計**:草稿寫法是 `login()` 後直接
   `page.goto("/citations/does-not-exist")`。但 mock AuthClient
   （`packages/auth-client/src/mock.ts`)的 session 是純記憶體內的
   closure 變數,沒有 cookie/storage 支撐——`page.goto()` 是硬重整,
   會讓整個 JS bundle 重新執行、session 歸零。這與
   `route-guards.spec.ts` 登入後用 `page.goto()` 的既有寫法表面相似,
   但**根本不是同一種情況**:`route-guards.spec.ts` 測的兩個路徑
   （`/this-route-does-not-exist`、`/maintenance`)都完全沒有對應的
   `page.tsx`,Next.js 的 App Router 會在根層級的 not-found 短路,
   根本不會進到 `(app)/layout.tsx` 的 `SessionGate`,所以那兩個測試
   其實不依賴 session 存活;而 `/citations/[id]` 的動態區段會匹配到
   `(app)` layout 底下**真正存在**的頁面,`page.goto()` 在這裡會先讓
   session 消失、被 SessionGate 導去 `/login`,測試會跑錯路徑而非
   測到我想測的內容。這是在寫這個測試草稿、對照 conversations.spec.ts
   的既有文件註解時自己發現並在提交前修正的,從未真的執行過這個
   會誤判的版本。修正:整個移除第二個 E2E（沒有任何合法的 in-app
   連結會導到一個無效的 citation id,勉強用非常規手法（例如直接呼叫
   Next.js router)硬測反而是不具代表性的做法),NOT_FOUND 的渲染
   邏輯已經被 `citation-source-view.test.tsx` 的 unit 測試完整、
   可靠地涵蓋。

## Assumptions / 計畫外事項

1. **頂層路由 `/citations/[id]`,不巢狀在對話底下**:見設計決策 1;
   `getCitationSource` 的資料模型本來就不是對話 scope 的,巢狀路由
   會是無依據的假設。
2. **無「返回對話」連結**:規格未要求,依既有的「不做未要求的額外
   範圍」原則,且 sidebar 導覽已提供基本 wayfinding。
3. **同分頁導覽,非新分頁**:規格未指定分頁行為,依「不發明未定義
   細節」原則採用與這個 app 其他所有導覽一致的同分頁方式。
4. **NOT_FOUND 情境沒有專屬 E2E**:見除錯過程 2 的完整技術理由——
   沒有合法的 in-app 路徑可以測試這個情境而不破壞 mock session,
   已由 unit 測試完整涵蓋。
