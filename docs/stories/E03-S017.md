# E03-S017 — Multi-turn message timeline

## Scope 說明

SOURCE_BASELINE.md 對 S17 只給標題「E03-S17 Multi-turn Conversation」
（第 1186 行),完全沒有內文。epic 檔展開版把標題具體化為「Multi-turn
message timeline」。

先確認現況:S09-S12 建立的架構（`DisplayMessage` 陣列、每個 entry
獨立的 `localId`、`stoppedRef` 以 localId 為 key、`setDisplayMessages`
一律用 functional update)在設計上就沒有任何東西綁死「只能送一次」——
理論上第二次呼叫 `handleComposerSubmit` 應該一樣能運作。但**具體核對
後發現一個真正的缺口**:`MessageComposer` 完全沒有「目前有一輪對話
還沒結束」這個概念,`isValid`（有沒有有效草稿)是送出按鈕唯一的
disabled 條件——代表使用者理論上可以在第一輪的 AI 回覆都還在串流
時,就搶著送出第二則訊息,兩輪會同時並行進行。真實聊天產品
（ChatGPT、Claude 等,延續 S12 已用過的同一個「真實聊天產品慣例」
論證)幾乎都會在等待回覆時鎖住送出動作,不允許重疊的輪次。

因此本 story 的實際工作分兩部分:(1) 補上這個真正的缺口——讓輪次
必須循序進行;(2) 用完整的測試（單元 + E2E)證明「多輪對話」這個
能力本身確實運作正確,包含順序、reload 後的持久化、以及每一輪的
transient 狀態（stop/telemetry)不會互相污染。

明確排除:
- 不處理「AI 是否記得前面輪次的內容」——那是語意層的 context 傳遞,
  屬於下一個 story S18「Conversation Context」的範圍。
  `lib/streaming.ts` 的 `streamAssistantReply()` 本來就不吃任何
  prompt 參數,本 story 維持原樣不變。
- 不新增任何「輪次分組」視覺元件（例如時間戳記分隔線)——規格沒有
  定義,依「不發明」原則不主動加上。

## 設計決策

1. **`MessageComposer` 新增可選的 `disabled` prop,預設 `false`**——
   與 `isValid` 合併成 `canSubmit = isValid && !disabled`,取代所有
   原本只檢查 `isValid` 的地方（送出按鈕的 disabled、Enter 鍵送出、
   `submitDraft` 本身的 guard)。預設 `false` 讓 S06-S09 所有既有
   測試不需要改動就能繼續通過。
2. **只鎖「送出」動作本身,不鎖整個輸入框**——使用者在等待回覆時
   仍然可以打字、選擇附件,只是不能真的送出去,直到目前這一輪結束
   ——比對 ChatGPT/Claude 等真實產品,輸入框在生成期間通常還是活的,
   只有送出動作被擋。
3. **`isTurnInFlight` 是從 `displayMessages` 衍生的值,不是獨立
   state**——`pending`/`streaming` 這兩種 kind 本來就已經在
   `displayMessages` 裡追蹤,不需要另外維護一份重複的旗標。
4. **只有 `pending`/`streaming` 會鎖住送出,`failed`/`stream-failed`
   不會**——後兩者是「已經結束但不成功」的狀態,使用者可以重試,也
   可以直接無視它、送新訊息,S17 之前從來沒有東西阻擋過這件事,本
   story 不新增這個限制。
5. **驗證性測試優先於臆測**——不假設「架構本來就對」,而是實際寫
   一個完整的兩輪對話測試（送出→等待settle→再送出→等待settle→
   核對 4 則訊息順序正確),以及一個「第二輪的停止只影響第二輪、
   不影響已經 settle 的第一輪」的測試,把 IMPLEMENT 階段的假設
   轉換成可執行、可信賴的證據。

- `apps/web/src/app/(app)/conversations/[id]/_components/message-composer.tsx`
  ——新增可選 `disabled` prop（預設 `false`),`isValid`/`canSubmit`
  合併判斷取代原本三處只檢查 `isValid` 的地方。

  ——新增 6 個測試:預設值向下相容、`disabled=true` 鎖住送出（即使
  草稿有效)、`disabled=true` 時仍可打字/附加檔案、`disabled=true`
  時 Enter 鍵不送出、`disabled=true` 時繞過按鈕直接送出表單也不
  觸發、`disabled` 切回 `false` 後重新啟用且草稿不遺失。
- `apps/web/src/app/(app)/conversations/[id]/_components/message-thread.tsx`
  ——新增衍生值 `isTurnInFlight`,傳入 `MessageComposer` 的
  `disabled` prop。
- `apps/web/src/app/(app)/conversations/[id]/_components/message-thread.test.tsx`
  ——新增 5 個測試:訊息 pending 時鎖住送出、AI 回覆 streaming 時
  鎖住送出、整輪 settle 後重新啟用、完整第二輪對話（4 則訊息順序
  正確)、第二輪的停止只影響第二輪自己（第一輪已 settle 的內容不受
  影響)。
- `tests/e2e/specs/multi-turn-conversation.spec.ts`（新增)——2 個
  E2E:第一輪進行中送出被鎖住,settle 後第二輪完整送出並顯示全部
  4 則訊息;完整兩輪對話在離開又返回後仍保持正確順序。

1. **自己的測試又踩到 E03-S012 已經記錄過的同一類陷阱**:
   「第二輪的停止只影響第二輪」這個測試,一開始把第二輪的
   `streamAssistantReply` mock 寫成「yield 一個字元後永久 `await` 一個
   不會 resolve 的 Promise」,結果 `for await` 消費迴圈永遠卡在等待
   `.next()`,永遠沒有機會在點擊停止後重新檢查 `stoppedRef`,測試
   逾時失敗（實際的錯誤訊息是「stillfound 停止生成 button」)。這正是
   `docs/stories/E03-S012.md` 已經記錄過的同一種陷阱,這次在寫新測試
   時又踩了一次。修正:改用既有的「可控制何時 release 的 gate」模式
   （`let releaseGate; const gate = new Promise(...)`),先點停止,
   再 release gate,如實模擬「停止請求發生在等待下一個值期間,等到
   那個值解析時迴圈才注意到並跳出」的真實時序。同時把等待訊號從
   容易撞名的 `screen.getByText("第二輪")`（會同時比對到使用者自己
   的訊息與 AI 累積中的內容,兩者剛好都是同一段文字)改成
   `screen.getByText("AI 回覆中…")`（只有真正開始收到內容才會出現,
   訊號更精確且不會撞名)。

## Assumptions / 計畫外事項

1. **新增「輪次必須循序進行」的鎖定機制**:SOURCE_BASELINE 未定義,
   依「真實聊天產品常見慣例」（ChatGPT、Claude 等,延續 S12 已用過
   的同一個論證來源)採用,而非任意假設。這是本 story 發現的一個
   真正缺口,不是計畫外的臆測性擴充——沒有這個鎖定,「多輪對話」
   在使用者快速連續操作時會產生未定義的重疊行為,直接對應
   Functional AC 5「重複請求/重試不得造成未定義重複 side effect」。
2. **只鎖送出動作,不鎖整個輸入框**:規格未定義,依「不必要地限制
   使用者操作」的最小侵入原則,選擇與真實聊天產品一致的行為
   （可以邊等邊打下一句話)。
3. **不處理跨輪次的語意 context 傳遞**:明確留給 S18「Conversation
   Context」,`lib/streaming.ts` 完全未變動。
