## Scope 說明

SOURCE_BASELINE.md 對 S18 只給標題「E03-S18 Conversation Context」
（第 1188 行),完全沒有內文。epic 檔展開版把標題具體化為
「**Conversation context indicator**」——「indicator」這個字是關鍵:
把這個 story 定調成一個**呈現/透明度**功能,不是「把真正的對話歷史
接進模型呼叫」。

這點特別重要,因為 S17 的 EVIDENCE 曾經把「context」猜測性地聯想到
「AI 是否記得前面輪次的內容」（語意層的 context 傳遞),如果真的要做
那件事,會需要真正的 Model Gateway/RAG 平台（E04、E12,Team B,皆
不存在),`lib/streaming.ts` 的 `streamAssistantReply()` 也刻意沒有
`prompt` 參數——照那個猜測做下去很可能要 BLOCKED。直接核對 epic 檔的
展開標題「indicator」後,確認這個顧慮不成立:S18 真正要做的是**顯示
給使用者看**「目前對話有多少歷史可以作為上下文」,不是真的把歷史
餵給任何模型。`lib/streaming.ts` 完全不需要變動。

明確排除:
- 不把任何訊息內容真的傳給 `streamAssistantReply()`——那是需要真正
  Model Gateway 才有意義的能力,留給接上 E04/E12 contract 的未來
  story。
- 不發明任何 context window 截斷上限（例如「只計入最近 10 則」)——
  SOURCE_BASELINE 沒有定義任何數字,虛構一個上限等同發明未定義的
  業務邏輯。指標直接顯示真實的已持久化訊息數,沒有上限。
- 不做「輪次分組」或時間戳記——同樣沒有規格依據,不主動加上。

## 設計決策

1. **`ConversationContextIndicator` 是純展示元件,吃 `messageCount`
   prop,不自己抓資料**——`message-thread.tsx` 本來就已經在
   `displayMessages` state 裡追蹤所有訊息,讓這個元件自己再呼叫一次
   `listMessages` 只會重複抓取,還可能因為沒同步到父層的樂觀更新而
   顯示過期的數字。
2. **只計算 `kind === "sent"` 的項目**——`pending`（使用者訊息還在
   送出中)與 `streaming`（AI 回覆還在生成中)都還沒有真正持久化,
   對一個「假設性地,真正的後端會看到什麼上下文」的指標而言,尚未
   確定的內容不該算進去。這個決策在實作過程中被自己的 E2E 測試
   意外驗證出一個更精確的真相（見下方除錯過程)。
3. **只計「則訊息」,不發明「輪」這個單位,也不設截斷上限**——
   「則訊息」是這個 codebase 已經確立的既有單位（沿用既有的空狀態
   文案「尚無訊息，開始對話吧。」的用詞),不引入新概念。
4. **不使用 `role="status"` 這種 live region**——訊息數每次有訊息
   settle 就會變動,如果標成 live region,使用者每送一則訊息就會被
   螢幕報讀器打斷一次,太吵、沒有幫助。這不是在回報「使用者剛做的
   動作的結果」（像「傳送中…」那樣),沒有真正需要即時播報的急迫性。
5. **不新增 telemetry**——這是被動、持續呈現的顯示元件,不是一個
   離散的使用者動作,不適用既有的 `_attempt`/`_success`/`_failure`
   三件套模式（比對既有的引用 badge 渲染本身也不發 telemetry,只有
   點擊動作才發,是同一套判斷標準)。

**除錯過程,誠實記錄**:

1. **E2E 測試的時序假設一開始就是錯的,直接跑就抓到**:第一版 E2E
   測試假設「使用者送出訊息後、AI 回覆還在生成期間,指標應該全程
   維持在『目前尚無先前訊息』」——第一次跑就失敗,而且失敗的原因
   讓我重新檢視 `attemptSend` 的真實順序:`sendMessage` 成功後,
   使用者自己的訊息會先從 `pending` 收斂為 `sent`（`sentMessageCount`
   立刻變成 1),**之後**才呼叫 `startStream()`。這代表指標實際的
   變化順序是 0 → 1（使用者訊息 settle)→ 2（AI 回覆也 settle),
   不是我原本假設的 0 → 2 一次跳過去。這不是實作有 bug,是我自己
   對時序的理解有誤。修正:把斷言改成核對「搜尋中…階段可見時,
   指標正確顯示 1（不是 0,也還不是 2)」,並額外在 unit test 補上
   一個對應這個中繼狀態的測試（「AI 回覆仍在 streaming 時只計入
   已 settle 的使用者訊息」),把這個原本只在 E2E 意外發現的行為
   轉換成一個明確、可信賴的 unit 層級證據。

2. **獨立審核抓到一個 MINOR:完全空的對話會同時顯示兩句意思重複的
   「尚無內容」文案**——`EmptyState`（「尚無訊息，開始對話吧。」)
   與指標自己的空狀態（「上下文：目前尚無先前訊息。」)在
   `displayMessages.length === 0` 時原本會同時出現,是不必要的
   重複。已修正:`message-thread.tsx` 改成只在 `displayMessages.length
   > 0` 時才渲染指標——完全沒有訊息時只顯示 `EmptyState`;一旦有
   第一則訊息在傳送中（即使還沒 settle,`sentMessageCount` 仍是 0),
   `EmptyState` 就不再顯示,此時指標的「目前尚無先前訊息」不再是
   重複資訊,會正常出現。這個修正連帶影響 4 個既有測試原本用指標的
   空狀態文案當作「thread 已完成載入」的等待訊號,已全部改用
   `EmptyState` 的文案作為等待訊號,並新增/調整對應測試明確驗證
   「完全空的對話不顯示指標」與「有第一則進行中的訊息時指標才出現」
   兩種情境。修正後重新完整跑過 unit（288 個)、E2E 隔離＋全量
   （73 個)、以及 `typecheck`/`lint`/`build`/`pnpm turbo run test
   --force` ×2,皆確認全綠無回歸。

## Assumptions / 計畫外事項

1. **「indicator」定調為純展示功能,不接真正的 context 傳遞**:
   SOURCE_BASELINE 沒有內文,依 epic 檔展開標題的明確用詞判斷,而非
   臆測性地假設這是要求真正的模型 context 整合（那會需要 E04/E12
   不存在的 contract,極可能導致 BLOCKED)。
2. **只計 `sent`,不計 `pending`/`streaming`**:規格未定義精確語意,
   依「只有真正持久化的內容才算得上『上下文』」的最保守、最誠實
   詮釋採用。
3. **無 context window 截斷上限**:規格未定義任何數字,不虛構業務
   邏輯,直接顯示真實的已持久化訊息總數。
