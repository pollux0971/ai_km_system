# E03-S020 — Answer Revision

- 狀態:DONE
- Branch:story/E03-S020-answer-revision
- 日期:2026-08-14

## Scope 說明

SOURCE_BASELINE.md 對本 story 的全部內容只有一行:

> E03-S20 Answer Revision
>
> 需留下 Revision。

Epic 檔(`E03_AI_Conversation_Experience.md`)的展開標題是「Answer
revision/history UI」，比 SOURCE_BASELINE 多了「history UI」這個字面
依據，用來決定「留下 Revision」不能只是資料庫層悄悄保留、使用者完全
看不到——至少要有一個可觀察的最小 UI。

這條線直接牽動 E03-S019(Regenerate Answer)已合併的實作：S19 的
`handleRegenerate` 是「先 `deleteMessage` 刪掉舊訊息、再靠
`receiveAssistantReply` 建一筆新的」，刪除後舊內容已經不存在，無處
可留 Revision。因此本 story 的核心變更是把 regenerate 的落地機制從
「刪除＋新增」改成「原地更新＋保留舊內容」，而不是在原機制外面再加一層
儲存。

## 設計決策

1. **`Message.revisions?: string[]`為 optional，不是必填 `[]`**——
   只有真正被修訂過的訊息才會有這個欄位；`sendMessage`/
   `receiveAssistantReply` 建立的訊息完全不設定它（不是設成
   `[]`）。選 optional 而非必填，是為了不強迫 S009 到 S019 所有既有
   測試 fixture 都要補上一個跟它們的行為完全無關的欄位——那會是一筆
   純機械、與本 story 無關的大範圍 diff，違反 Change Budget 精神。

2. **`reviseMessage` 取代 `deleteMessage`，原地更新同一筆 row**——
   `reviseMessage(messageId, newContent)` 找到既有 row，把它目前的
   `content` push 進 `revisions`，再覆寫 `content`，用同一個 `id`
   寫回 store。因為 id/位置都不變，「reload 不出現重複」這條
   S019 就有的 Functional AC 5 保證，現在是「同一筆 row 被更新」的
   自然結果，而不必再靠額外的刪除步驟。`deleteMessage`
   因此完全沒有呼叫端了，予以移除（連同它的測試）——確認過整個
   repo 只有 S019 的 `message-thread.tsx` 呼叫過它。

3. **`runStream` 用 `reviseTarget?: Message` 參數在兩種落地路徑間切換**
   ——沒有 `reviseTarget` 走原本的 `receiveAssistantReply`（新一輪
   對話）；有 `reviseTarget` 就呼叫 `reviseMessage(reviseTarget.id,
   accumulated)`。同一份 phase/streaming/stop 邏輯完全重用，不建
   平行實作。

   這個改動連帶讓 S19 文件裡「regenerate 途中在任何內容抵達前按停止
   ，會讓該輪完全沒有回覆」這個已知、已記錄的行為變得更好：因為
   S20 不再「一按重新產生就先刪除舊訊息」，原始 row 在
   `reviseMessage` 真的被呼叫之前完全沒被動過，所以空內容停止時
   `runStream` 直接把 `streaming` entry 還原成
   `{ kind: "sent", message: reviseTarget }`——舊回覆原封不動，沒有
   任何東西遺失。這是新機制「不先動 row」的直接必然結果，不是額外
   夾帶的功能。

4. **Revision 歷史用原生 `<details>/<summary>`，內容用 `<p>` 而非
   `<ul>/<li>`** ——`<details>` 不需要外部套件、預設可鍵盤操作、
   預設收合（符合「MVP 可簡化視覺」但功能本身要在）。刻意不用
   `<ul>/<li>`：本組件最外層的訊息列表本身就是一個
   `<ul>`，每個 E2E spec 的
   `page.getByRole("main").getByRole("listitem")` 都假設
   listitem 數量＝訊息數量——一旦某則訊息有 revisions 又用
   `<li>` 呈現歷史，listitem 計數會被悄悄灌水，這正是本 session
   之前在別的 story 反覆踩過的「listitem scope 碰撞」同一類陷阱。
   舊版本一律用純文字呈現（不透過 `MessageContent`/citation 解析）
   ——歷史記錄是「這則回覆以前長怎樣」的靜態存證，不是可互動的
   當前答案，把 `[N]` 引用標記重新解析成可點擊按鈕會是本 story
   沒人要求的互動語意發明。

## 除錯過程

無需除錯。本 story 開發過程中發現一處自己在撰寫測試時的筆誤（
`messages.test.ts` 第一個 `reviseMessage` 測試裡寫成

## Assumptions / 計畫外事項

1. **`revisions` 存的是內容字串，不是完整 Message 快照**——因為除了
   `content` 以外，被修訂訊息的其他欄位（id、conversationId、
   attachmentNames、createdAt）從未改變，沒有需要額外保留的理由；
   若未來有 story 需要「每個版本各自的時間戳記」，屬於那個未來
   story 自己的 scope，本 story 不預先發明。
2. **歷史 UI 不隨 `isLastEntry` 限制**——`重新產生`按鈕只在最後一則
   assistant 回覆上出現（S019 既有限制未變），但「先前版本」歷史
   顯示與訊息在不在最後一則無關：一則訊息就算後來不再是最後一則
   （使用者送出了下一輪），它自己曾經被修訂過的歷史仍應該永久
   可見——這是資料語意本身的要求，不是新發明的功能。
3. **E2E 測試刻意不比對修訂前後的實際文字內容**——
   `lib/streaming.ts`的 `MOCK_REPLY`是固定字串，同一個環境下每次
   regenerate 產生的內容完全相同，E2E 若斷言內容差異就是在驗證
   一個環境不可能為真的前提。E2E 因此只驗證結構（歷史區塊出現、
   計數正確遞增、reload 後仍存在）；真正驗證「舊內容確實被保留、
   且是舊的那個字串」在 component test 層完成（在那裡可以完全
   控制 mock 回傳的內容，不受 MOCK_REPLY 固定字串限制）。
4. **`reviseMessage`失敗時的行為沿用既有 `stream-failed` 路徑**——
   沒有為「修訂失敗」設計獨立的 UI 狀態或訊息文案，因為
   `runStream`本身早已有 `!result.ok` → `stream-failed`
   的通用處理，`reviseTarget`只是切換呼叫哪個持久化函式，失敗後的
   UI 呈現沒有理由不同。
