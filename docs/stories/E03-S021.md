## 設計決策

1. **`AnswerState` 6 個值直接取自 SOURCE_BASELINE 的英文名稱**(同
   `GenerationPhase` 的既有慣例:英文值可追溯回規格,`ANSWER_STATE_LABELS`
   另外提供中文顯示文字)。

2. **`classifyAnswerState(userQuestion)` 是純函式,基於 bracket 標記
   觸發**,不是真正的內容分析。ANSWERED 沒有對應 trigger——找不到任何
   標記時的預設值,確保這個 story 之前送出的每一則訊息(不可能包含
   還不存在的 trigger 文字)行為完全不變。

3. **`Message.state?: AnswerState` 為 optional**,理由與 S020 的
   `revisions` 完全相同:避免強迫 S009 到 S020 所有既有測試 fixture
   補上一個與其行為無關的欄位。`message-thread.tsx` 渲染時把
   `undefined` 當作 "ANSWERED" 處理。

4. **`runStream` 依分類結果分兩條路徑,不是渲染層自己判斷要不要顯示
   內容**:ANSWERED 與 PARTIAL 維持原本逐字元 `streamAssistantReply()`
   串流(PARTIAL 代表「有給出真的答案,只是不完整」,內容仍值得顯示);
   其餘 4 個狀態直接用 `ANSWER_STATE_FALLBACK_CONTENT` 的固定誠實
   佔位句子取代,一次性設定(不逐字元),因為「查無依據」這種狀態
   沒有什麼好「逐步生成」的。這讓渲染邏輯變得單純:`content` 欄位
   本身就已經是該顯示的內容,渲染層只需要另外加一個簡短的狀態
   標籤,不需要重複顯示或條件判斷內容本身。

5. **Regenerate(S019/S020 既有機制)重用原訊息的 `state`,不重新分類**
   ——`handleRegenerate` 傳入 `originalMessage.state ?? "ANSWERED"`。
   重新產生回答的是同一個潛在問題,mock 對那個問題的分類沒有理由
   改變;這也避免了「往回找出當初的使用者問題文字」這種在
   `displayMessages` 陣列裡額外查找的複雜度。

6. **badge 的 ARIA role 選擇經過一次真實除錯修正**:ERROR 與
   PERMISSION_DENIED 用 `role="alert"`(比照這個檔案既有的
   `stream-failed` 狀態同樣是永久、已落定的負面狀態,同樣用
   `role="alert"`,不會與任何 E2E spec 的
   `waitForThreadToSettle`(靠 `role="status"` 數量歸零判斷「是否
   還在等待中」)衝突);其餘非 ANSWERED 狀態(PARTIAL/NO_EVIDENCE/
   SOURCE_UNAVAILABLE)不给 ARIA role,純粹資訊性標籤。最初設計曾
   讓這三者也用 `role="status"`,在 E2E 撰寫階段就自行發現這會讓
   `waitForThreadToSettle` 永遠等不到 0(因為這個 badge 是永久
   存在、不會消失的,不像既有的「傳送中…」/「AI 回覆中…」是
   transient),已在正式跑 gate 之前修正,詳見除錯過程。

## 除錯過程

1. **`role="status"` 與 `waitForThreadToSettle` 的衝突**:最初設計讓
   PARTIAL/NO_EVIDENCE/SOURCE_UNAVAILABLE 三個狀態的 badge 也用
   `role="status"`(理由是「非 alert 等級的資訊性狀態」)。撰寫
   E2E spec 時,在還沒執行任何正式 gate 前就自行發現:這三個 role
   會讓每個既有 E2E spec 共用的 `waitForThreadToSettle` 輔助函式
   (靠 `page.getByRole("main").getByRole("status")` 數量歸零判斷
   「是否已解決」)永遠等不到 0,因為這個 badge 是回覆落定後的
   **永久**標籤,不是「傳送中…」那種會消失的暫時狀態。修正:只有
   ERROR/PERMISSION_DENIED(比照既有的 `stream-failed` 狀態同樣是
   永久負面狀態)用 `role="alert"`,其餘三個非 ANSWERED 狀態不給
   ARIA role。同步修正了對應的 component test(原本斷言
   `expectedRole = ... ? "alert" : "status"`,改為非 alert 狀態時
   斷言「沒有 role 屬性」)與 E2E spec。
2. **`getByRole(role, { name })` 對 `role="alert"` 的 accessible
   name 計算**:E2E 的 PERMISSION_DENIED 測試最初寫
   `page.getByRole("main").getByRole("alert", { name: "無權限查看" })`,
   在隔離跑該測試時穩定失敗(重跑 2 次结果一致,非 flaky)。用一個
   拋棄式的診斷測試(送出 PERMISSION_DENIED trigger 後分別查詢
   `getByRole("alert")`(無 name 過滤)與帶 name 過滤的版本)確認:
   前者找到 1 個、文字正確為「無權限查看」;後者找到 0 個。結論:
   `role="alert"` 的純文字 `<span>`(無 `aria-label`)不會像
   `button`/`link`/`heading` 那樣把文字內容當作 accessible name 來源
   ——這是 ARIA/Playwright 的既有行為差異,不是元件邏輯錯誤。修正:
   E2E 測試改為先用 `getByRole("alert")`(不帶 name)確認角色與
   可見性,再用 `.toHaveText("無權限查看")` 另外驗證文字內容,不
   依賴 name-from-content。診斷測試檔案已刪除,未留在正式測試套件。

## Assumptions / 計畫外事項

1. **`classifyAnswerState` 依 `ANSWER_STATES` 陣列順序檢查，非
   優先權設計**——SOURCE_BASELINE 未定義多個 trigger 同時出現時的
   優先順序；目前實作依陣列定義順序（ANSWERED 略過、PARTIAL 優先於
   NO_EVIDENCE...）回傳第一個相符者。這是一個未被要求、但為了函式
   行為確定性（不能回傳「不確定」）而必須做的選擇，已在函式文件
   註解中明確記載，不是隱藏假設。
2. **`handleRetryStream`（S010 既有的串流失敗重試路徑）未傳遞
   `answerState`，沿用預設值 "ANSWERED"**——這個路徑本來就不知道
   觸發失敗的原始問題文字是什麼（S010 從未把它保留下來），本 story
   沒有理由、也沒有 grounding 去擴大這個既有限制的修復範圍；沿用
   預設值是唯一在不擴大 scope 的前提下能做的一致選擇。
3. **PARTIAL 狀態沒有獨立的 fallback 內容**——PARTIAL 語意上代表
   「有給出真的答案，只是不完整」，所以刻意讓它沿用正常的
   `streamAssistantReply()` 串流內容而非取代成固定句子；這與其餘
   4 個「沒有真的答案可以給」的狀態在概念上有本質區別，已在設計
   決策段落說明。
4. **E2E 只涵蓋 3 個代表性狀態（無 trigger/NO_EVIDENCE/
   PERMISSION_DENIED），非全部 6 個**——其餘狀態（PARTIAL/ERROR/
   SOURCE_UNAVAILABLE）的渲染邏輯已在 component test 層用
   `it.each(ANSWER_STATES)` 逐一驗證過，E2E 選擇涵蓋「正常路徑」
   「內容取代型代表」「security 相關代表」三種質性不同的案例，避免
   對 6 個結構相似的狀態做重複性的端對端驗證（component test 已
   證明其渲染正確，E2E 的價值在於證明「真實應用中打字觸發真的能
   走到渲染」，這點 3 個代表性案例已足夠證明）。

## Rollback

Revert 本 story 的 merge commit 即可，是自包含的變更集（新增
`lib/answer-state.ts` 及其測試、`messages.ts`/`message-thread.tsx`
的欄位與參數擴充、5 個既有測試斷言修正、新增 E2E spec 檔）。5 個
既有測試斷言的修正必須與 `messages.ts`/`message-thread.tsx` 的
函式簽名變更一起 revert（不能只 revert 其中一邊），否則會造成
gate 紅——這是 revert 時需要注意的唯一耦合點。
