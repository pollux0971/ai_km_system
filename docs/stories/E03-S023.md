## 設計決策

1. **搜尋只比對 `title`,不比對 `lastMessagePreview`**——真實聊天
   產品(ChatGPT、Claude 自己的側欄搜尋,沿用 S012/S017/S019 已用過
   的「真實聊天產品」判斷先例)搜尋的是對話標題,不是全文內容;
   全文搜尋會是完全不同、更重的機制,SOURCE_BASELINE 沒有要求,
   MVP 不應該發明。

2. **搜尋(filter)發生在分頁(paginate)之前,而非兩個獨立步驟**
   ——`listConversations(page, query)` 內部先用 `query` 過濾整個
   資料集,再對過濾後的結果計算 `totalCount`/`totalPages`/切頁。
   這確保搜尋進行中時「共 N 頁」永遠指「符合搜尋的結果」的頁數,
   不是「未過濾清單」的頁數——如果分開處理,容易讓使用者在搜尋
   後看到語意錯誤的分頁狀態(例如「第 1 頁，共 2 頁」但過濾後其實
   只有 1 筆符合)。

3. **搜尋即時觸發(每次按鍵都重新查詢),不做 debounce、不需按鈕
   送出**——這個 mock 的「搜尋」是純記憶體陣列的即時 filter
   (`listConversations` 本身沒有真正的網路延遲),不像真實 API
   呼叫有 debounce 想避免的成本。加上 debounce 邏輯會是這個 mock
   不需要、卻仍要多寫的複雜度,不是簡化。

4. **變更搜尋字串時,頁碼重置回 1**——沒有這一步,在第 2 頁時輸入
   搜尋字串,若過濾後結果只剩 1 頁,畫面會呈現一個不存在的「第 2
   頁」空清單,而不是搜尋到的實際內容。

5. **空結果訊息依是否有作用中搜尋而不同**——沿用既有的
   「尚無對話，開始你的第一個對話。」(`EmptyState`)只在
   *真的* 沒有任何對話時顯示;搜尋沒有結果時顯示新的
   「查無符合「{查詢字串}」的對話。」。沿用舊訊息會誤導使用者
   以為自己完全沒有任何對話,實際上只是搜尋沒有匹配——呼應
   Frontend/UX Boundary「Loading/empty/error 必須是不同狀態,不得
   把 403 當 empty data」的精神(同一類「不要把兩種不同的空狀態
   混為一談」原則)。

6. **搜尋框本身無條件渲染,不受 `state.status` 影響**——換頁沿用
   既有的 loading 狀態(S022 已確立的模式),但搜尋框在 loading
   狀態顯示時仍應維持可見且保留使用者已輸入的字串,不應該在
   重新查詢期間消失或清空。

## Assumptions / 計畫外事項

1. **搜尋沒有最小字元數限制**——SOURCE_BASELINE 未要求,單一字元
   也會觸發過濾,避免發明未被要求的限制。
2. **搜尋字串不透過 URL query 參數**——與 S022 的頁碼狀態一樣,只
   存在於元件 local state,離開再返回會重置為空搜尋。理由同 S022:
   沒有任何依據要求可分享/可加書籤的搜尋 URL。
3. **未做搜尋結果的關鍵字醒目提示(highlight)**——SOURCE_BASELINE
   與 epic 檔皆未提及,MVP 簡化為純過濾,不含視覺強調效果。
4. **搜尋比對邏輯使用 `.toLocaleLowerCase()` 而非 `.toLowerCase()`**
   ——確保繁體中文與其他非 ASCII 字元的大小寫比對行為正確,是
   一個誠實、必要的技術選擇,非過度設計。
