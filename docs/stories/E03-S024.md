## Scope 說明

SOURCE_BASELINE.md 對本 story(line 1223)只有標題「E03-S24 Rename
Conversation」,無任何內文。Epic 檔的展開標題「Rename conversation」
與標題本身一致,未提供額外方向——與 S023 同類情況,實作路徑清楚
(替既有的對話詳情頁加上重新命名能力),不需要升級到 /advisor 流程。

## 設計決策

1. **重新命名只在對話詳情頁(`/conversations/[id]`)提供,不在列表頁
   內嵌**——SOURCE_BASELINE 未提及從列表直接重新命名,列表頁還有
   S022 分頁、S023 搜尋兩組互動狀態,硬加內嵌重新命名 UI 需要處理
   與這些狀態的互動,是沒人要求的範圍擴張。

2. **`RenameConversation` 元件完整擁有標題區塊(含靜態 `<h1>` 顯示與
   編輯表單兩種模式),不是 `ConversationDetail` 保留 `<h1>` 只在旁邊
   加一顆按鈕**——這樣「顯示」與「編輯」永遠是同一個元件狀態機的
   兩個分支,不會有兩份標題文字短暫同時存在的中間狀態。沒有其他
   兄弟元件(像 `currentMode` 之於 `ModelSelector`)需要讀取即時
   標題,因此不需要往上提升狀態或加 callback prop。

3. **非樂觀更新(non-optimistic)**——與既有的 `ModeSwitch`/
   `ModelSelector`/`KnowledgeSelector` 同一個先例:這個 mock 幾乎
   瞬間 resolve,沒有真正的網路延遲需要用樂觀更新掩蓋。標題只在
   收到確認成功後才更新。

4. **空白/純空白標題在 UI 與資料層雙重擋下**——`儲存` 按鈕在草稿
   trim 後為空時停用(防止常見情況甚至連 API 都不呼叫);
   `renameConversation()` 自己也驗證並 fail-closed 回傳
   `VALIDATION_ERROR`,不只依賴 UI 的停用狀態——與
   `setConversationModel` 拒絕停用模型「不只依賴 UI 的 disabled
   `<option>`」同一個既有先例。這是 Functional AC 2 在這個 story
   具體、有依據的落地:空白標題會讓列表、搜尋結果、Home Dashboard
   小工具全部顯示一個沒有意義的名稱。

5. **失敗訊息用既有的通用「失敗，請稍後再試」文案,不呈現伺服器
   訊息本身**——與 `ModeSwitch`/`ModelSelector` 既有的錯誤呈現方式
   一致。因為 UI 層的停用按鈕已經擋掉最常見的空白情況,能真正打到
   伺服器驗證的路徑相對少見(主要是 NOT_FOUND),用既有的通用文案
   已足夠,不需要為這個 story 另外發明新的錯誤呈現慣例。

## Assumptions / 計畫外事項

1. **重新命名沒有長度上限**——SOURCE_BASELINE 未要求,只驗證
   「非空白」這一條 Functional AC 2 直接對應的規則,不發明額外
   長度限制。
2. **重新命名沒有確認對話框(如「確定要更改標題嗎？」)**——這是
   低風險、可逆的操作(可以再次重新命名改回去),真實聊天產品
   (同 S012/S017/S019/S023 已用過的判斷先例)通常也不會為重新命名
   加確認對話框,加上去會是未被要求的摩擦。
3. **重新命名的錯誤訊息用通用文案,不揭露伺服器實際錯誤內容**——
   與既有 ModeSwitch/ModelSelector 的既有慣例一致,見設計決策 #5。
4. **`RenameConversation` 沒有 `onTitleChange` callback**——不像
   `ModeSwitch` 的 `onModeChange`(有其他兄弟元件 `ModelSelector`
   需要即時知道模式),沒有其他元件需要即時讀取重新命名後的標題,
   加上這個 callback 會是投機性、目前沒有消費端的擴充點。
