# E03-S025 — Delete Conversation Confirmation

## Scope 說明

SOURCE_BASELINE.md 對本 story(line 1227)只有標題「E03-S25 Delete
Conversation」,無任何內文。Epic 檔的展開標題「Delete conversation
confirmation」比標題多了「confirmation」這個具體字眼——這是本 story
唯一、但明確的方向依據:刪除動作前必須有一個明確的確認步驟,不能是
單擊即刪除。

同一份 SOURCE_BASELINE 緊接著下一條就是「E03-S26 Archive Conversation」
——「刪除」與「封存」在規格裡被列為兩個獨立的未來 story,這確認了
本 story 的「刪除」應該是真正的移除,不是軟刪除/封存旗標(那是 S26
的範圍,本 story 不得偷跑)。

## 設計決策

1. **刪除只在對話詳情頁提供,不在列表頁內嵌**——與 S024 重新命名
   同一個既有理由:列表頁還有 S022 分頁、S023 搜尋兩組互動狀態,
   硬加內嵌刪除 UI 需要處理與這些狀態的互動,是沒人要求的範圍擴張。

2. **真正從 store 移除,不是軟刪除/封存旗標**——見上方 Scope 說明。
   `deleteConversation()` 直接 filter 掉該筆記錄,不是加一個
   `deleted: true` 欄位。

3. **確認流程沿用 S024 建立的「按鈕→揭露第二步」UI 慣例,但用
   `role="alertdialog"`(不是 S024 表單用的純 `<div>`)**——這是
   ARIA 中專門給「中斷工作流程、需要使用者明確回應」的確認情境
   使用的角色,語意上比 S024 的一般編輯表單更準確。沒有實作
   focus trap——這個 codebase 目前任何互動介面(包含既有的
   `CitationPreviewDrawer`,非 modal)都沒有 focus 管理的先例,只在
   這一個元件加上去會是不一致的例外,而非改善。

4. **成功刪除後串接刪除該對話的所有訊息**(`deleteMessagesForConversation`,
   新增於 `lib/messages.ts`)——這個編排(orchestration)發生在
   UI 元件層,不是 `deleteConversation()` 內部呼叫 messages.ts:
   `conversations.ts` 目前沒有反向讀寫 `messages.ts` store 的先例
   (既有方向永遠是 messages.ts 呼叫進 conversations.ts 的
   `touchConversationLastMessage`,從未反過來),在這裡第一次引入
   反向依賴會把兩個刻意分開的集合(S009 就已經說明 Message 與
   ConversationSummary 為何分開)纏在一起。`deleteMessagesForConversation`
   本身刻意無條件執行(同 S019 舊版 `deleteMessage` 的既有理由)——
   它只在 `deleteConversation` 已經成功之後才被呼叫,是清理步驟,
   不是需要自己驗證存在性的使用者操作。

5. **成功後用 `router.refresh()` + `router.replace("/conversations")`**
   ——與 `/conversations/new` 既有的建立流程用同一個模式
   (`refresh()` 清 Router Cache,再導頁)。用 `replace` 而非 `push`:
   這個對話已經不存在了,使用者按「上一頁」不應該回到一個現在會
   404/not-found 的死連結。

6. **確認訊息帶入對話標題**(「確定要刪除「{title}」嗎？」),不是
   泛用的「確定要刪除嗎？」——讓使用者明確知道自己正在刪除的是
   哪一個對話,對一個不可逆操作而言是合理、有依據的最低限度資訊,
   不是過度設計。

## Assumptions / 計畫外事項

1. **`role="alertdialog"` 沒有實作 focus trap**——見設計決策 #3,
   與這個 codebase 既有的(缺乏)focus 管理慣例一致,不在這一個
   元件單獨加上去造成不一致。
2. **確認提示不是瀏覽器原生 `confirm()`**——沿用 S024 建立的「按鈕
   →揭露第二步」inline UI 慣例,不使用原生 dialog(這個 codebase
   目前沒有任何使用原生瀏覽器 dialog 的先例,且原生 `confirm()`
   無法客製化文字樣式、也難以在元件測試中可靠斷言)。
3. **刪除訊息(`deleteMessagesForConversation`)的清理是 fire-and-
   forget,不會讓整個刪除流程失敗**——這個函式本身刻意設計成
   無條件成功(同舊版 `deleteMessage` 的既有理由),沒有真正的
   失敗路徑需要處理;對話本身的刪除(使用者直接感知的操作)已經
   成功,不應該因為一個必然成功的清理步驟而顯得整體操作失敗。
4. **沒有「復原刪除」(undo)機制**——SOURCE_BASELINE 與 epic 檔皆
   未提及,MVP 範圍就是「confirmation」這一個明確要求的能力,復原
   語意是沒人要求的擴張(同這整個 session 一貫的反發明紀律)。
