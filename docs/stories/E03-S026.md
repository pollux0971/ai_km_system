# E03-S026 — Archive/unarchive conversation

- 狀態:APPROVED
- Branch:story/E03-S026-archive-unarchive-conversation
- 日期:2026-08-14

## Scope 說明

SOURCE_BASELINE.md 對本 story(line 1231)只有標題「E03-S26 Archive
Conversation」,無任何內文。Epic 檔的展開標題「Archive/unarchive
conversation」比標題多了「unarchive」——這是本 story唯一、但明確的
方向依據:這是一個**雙向、可逆**的狀態切換,不是單向的封存動作。

上一個 story(E03-S025 刪除對話)的 EVIDENCE 已經記錄:SOURCE_BASELINE
把「刪除」與「封存」列為兩個獨立的 story,S025 的刪除是真正從 store
移除,不是軟刪除旗標——這確認了本 story(S026)才是那個「軟刪除/狀態
旗標」語意真正的歸屬地,不是偷跑或重複。

## 設計決策

1. **`archived` 是 view selector,不是 include-toggle**——`listConversations`
   新增第三個參數 `archived = false`,語意是「回傳作用中對話」或「回傳
   已封存對話」兩個互斥視圖之一,不是「把封存項目也混進同一份列表」。
   這與真實聊天/信箱產品(這個 codebase 在 S012/S017/S019/S023 已多次
   採用的「real product」先例)呈現 Active/Archived 為分開視圖、而非
   交錯清單的慣例一致。`totalCount`/`totalPages` 描述「當下請求的那個
   視圖」,延續 S023 搜尋已建立的「描述實際過濾後結果」原則。

2. **`listConversations` 的第三參數有預設值 `false`,對既有呼叫端
   向後相容**——已用 grep 確認生產程式碼中唯一呼叫端
   (`conversation-list.tsx`)已同步更新為傳入 `viewingArchived`;
   簽名本身的預設值確保任何理論上省略第三參數的呼叫仍維持 S001-S023
   既有行為不變。

3. **`getRecentConversations`(Home Dashboard 最近對話 widget)排除
   已封存對話**——這是「新增 archived 概念」必然的推論結果,不是從
   別的 story 借來的範圍擴張:封存的目的就是讓對話從日常會經過的
   介面消失;如果 Home Dashboard 仍然照常顯示已封存對話,這個功能
   對使用者實際會用到的介面等於沒有作用。與 S025 用「正確性要求」
   理由串接刪除訊息是同一類推論。

4. **`archiveConversation`/`unarchiveConversation` 是兩個獨立具名
   函式,不是一個 `setArchived(id, boolean)`**——與這個檔案既有慣例
   一致(`renameConversation`/`deleteConversation` 都是動詞具名,不是
   泛用的 `updateX`)。兩者皆透過既有的 `updateConversation` 內部
   helper 實作,對稱、無重複邏輯。

5. **UI 沒有確認步驟,單擊直接切換**——與 S024 重新命名、S025 刪除
   刻意做相反選擇的理由對稱:S025 需要確認是因為刪除不可逆;封存/
   取消封存是完全可逆的動作(這正是「archive」與「delete」在真實
   產品中語意不同、也是 SOURCE_BASELINE 把兩者列為獨立 story 的
   原因),比照 S024 重新命名沒有二次確認的先例,加一個確認步驟會是
   沒人要求的過度設計。

6. **按鈕文字本身變化(「封存對話」⇄「取消封存」),不使用
   `aria-pressed`**——`aria-pressed` 語意上是「切換型按鈕維持同一個
   動作標籤,靠 pressed 狀態表達當下狀態」(這個檔案自己在
   `conversation-list.tsx` 的 Active/Archived 視圖切換按鈕上就是這樣
   用的);但這裡兩個狀態對應的是兩個不同動作(「封存」與「取消
   封存」是使用者會採取的兩個不同意圖動詞),用會變化的按鈕文字更
   準確地反映「這是一個動作按鈕,不是一個狀態顯示器」。

7. **列表頁的 Active/Archived 切換用 `role="group"` 按鈕組
   (`aria-pressed`),放在搜尋框之上**——與 S023 搜尋框「無條件
   渲染、不受 state.status 影響」相同的可見性原則;切換視圖時同時
   重置 `page` 與 `query`(見 `conversation-list.tsx` 內建的文件
   註解),避免帶著另一個視圖的分頁/搜尋殘留狀態進入新視圖。

8. **第三種 empty-state 訊息(「尚無已封存的對話。」)**——與 S023
   建立「查無符合...的對話」訊息是同一類理由:重用既有任何一則訊息
   在此情境下都不準確(可能有很多作用中對話,只是沒有已封存的)。
   搜尋優先權高於「已封存為空」:在已封存視圖內搜尋但沒有符合結果,
   仍然是「查無符合」情境,不是「封存區是空的」情境。

## Assumptions / 計畫外事項

1. **UI 沒有確認步驟**——見設計決策 #5,與 S025 刪除刻意相反的
   選擇,理由是封存可逆、刪除不可逆,對稱於 S024 重新命名也沒有
   確認步驟的先例。
2. **`archived` 欄位是 optional 而非永遠存在的 `false`**——與
   `messages.ts` 既有的 `revisions`/`state` optional 欄位處理方式
   一致,既有 seed 資料(`SAMPLE_CONVERSATIONS`)不需要逐筆補上
   `archived: false`。
3. **`listConversations` 修改了既有函式簽名(新增第三參數)而非
   新增一個平行函式**——已 grep 確認生產程式碼只有一個呼叫端且已
   同步更新;第三參數帶預設值,理論上任何遺漏更新的呼叫端行為仍
   不變。這是延續 S022(加 `page`)、S023(加 `query`)已經建立的
   「同一函式漸進式擴充參數」慣例,不是本 story 獨有的風險決定。
4. **沒有「批次封存」或「從列表頁直接封存」機制**——僅在對話詳情頁
   提供封存/取消封存操作,與 S024/S025 相同理由(列表頁已有 S022
   分頁、S023 搜尋兩組既有互動狀態,不做沒人要求的範圍擴張)。
