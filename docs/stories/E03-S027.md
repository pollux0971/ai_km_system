# E03-S027 — Copy answer action

- 狀態:APPROVED
- Branch:story/E03-S027-copy-answer-action
- 日期:2026-08-14

## Scope 說明

SOURCE_BASELINE.md 對本 story(line 1235)只有標題「E03-S27 Copy
Answer」,無任何內文。Epic 檔的展開標題「Copy answer action」——
「answer」一詞本身就是範圍依據:這是複製 AI **回覆**的動作,不是
複製使用者自己的訊息(比照 S19「Regenerate Answer」的標題同樣只提
「Answer」、從未涵蓋使用者訊息的既有先例)。

「unarchive」在 S26 是唯一的方向依據;這裡「answer」同樣是唯一但明確
的依據。至於「是否只有最後一則回覆才能複製」——SOURCE_BASELINE 與
epic 檔皆無限制,且複製與 S19 的重新產生本質不同:重新產生是
destructive(取代原內容),只在最後一則合理;複製是非破壞性、
唯讀的動作,真實聊天產品(這個 codebase 一貫援引的先例)在任何一則
回覆上都提供複製,不限於最後一則。因此本 story 刻意不比照 S19 的
`isLastEntry` 限制。

## 設計決策

1. **每一則已完成(`kind: "sent"`)的 assistant 回覆都有複製按鈕,
   不限最後一則**——見上方 Scope 說明。使用者訊息不提供複製按鈕
   (「Copy Answer」的「Answer」明確排除)。

2. **內聯實作在 `message-thread.tsx`,不是獨立元件**——比照這個檔案
   既有慣例:S19 重新產生、S12 停止生成、S09/S10 重試,全部是內聯
   `<button>` + 內聯 handler,不是獨立元件檔;只有真正複雜/獨立的
   部分(CitationPreviewDrawer、ConversationContextIndicator、
   MessageContent)才拆成獨立檔案。複製按鈕的複雜度與 regenerate/
   stop/retry 同一量級,理應遵循同一慣例。

3. **複製的是 `content`(該訊息的原始純文字,含 `[1]` 這類引用
   標記字面字元),不是經過清理/去除標記的版本**——`MessageContent`
   將 `[1]` 解析為 `<sup>` 內的可點擊 badge 只是「渲染呈現方式」,
   底層 `entry.message.content` 字串本身就是純文字,badge 顯示的
   文字就是這段原始字串的字面內容(見 message-content.tsx:
   citation marker 是直接內嵌在純文字裡的字面 substring,不是結構化
   資料)。複製這個原始字串等於複製使用者「看到的文字」,不需要
   額外的清理/剝離邏輯。

4. **按鈕文字本身變化(「複製」⇄「已複製」),成功後透過
   `setTimeout` 在短暫延遲後自動還原**——這與 S26
   `archive-conversation.tsx` 的按鈕文字變化「表面上」相似,但語意
   刻意不同:S26 的文字變化反映一個**持久狀態**(封存與否),
   直到使用者再次點擊才會變回來;複製完全不是一個持久狀態,把按鈕
   永久停在「已複製」會錯誤暗示這是某種持續生效的狀態。真實聊天
   產品(這個 codebase 一貫援引的先例)複製按鈕的標準行為就是短暫
   確認後自動還原,不需要使用者再點一次才能變回可再次複製的樣子。

   **修正(獨立審核 MAJOR 發現後)**:狀態追蹤的資料結構最初設計成
   單一共用的 `{ messageId, status }` slot(假設「同一時間只會有一則
   訊息顯示複製確認」),獨立審核實際重現了一個真正的 race:對兩則
   不同訊息各按一次複製,兩個 `navigator.clipboard.writeText()`
   呼叫各自獨立、以任意順序 resolve——後 resolve 的那個會直接覆蓋/
   清掉另一則訊息已經顯示的確認,且各自的還原計時器可能清到不屬於
   自己的訊息狀態(甚至在元件卸載後才觸發,繞過只追蹤「最新一個」
   計時器控制代碼的卸載清理)。修正為 `copyStatuses`(以 messageId
   為 key 的 `Map`)與 `copyResetTimeoutsRef`(同樣以 messageId 為
   key 的 `Map`)——每則訊息自己的 pending/copied/failed 轉換與還原
   計時器,結構上就不可能互相干擾;兩則訊息也可以同時合法地各自顯示
   「已複製」,這才是正確行為,不是需要避免的邊界情況。

5. **失敗狀態用 `role="alert"`,不是 `role="status"`**——延續這個
   檔案自己在文件註解中已經明確建立的規則(S21 的 ERROR/
   PERMISSION_DENIED badge、stream-failed 項目都是這樣處理):
   `role="status"` 在這個 codebase 的慣例裡專指「仍在等待中」,
   每個 E2E spec 的 `waitForThreadToSettle` helper 都會輪詢
   `role="status"` 的數量直到歸零;複製失敗是一個**已結束、直到下次
   操作前都不會改變**的負向狀態,重用 `role="status"` 會讓那些
   settle-detection helper 誤判仍在忙碌。

6. **複製進行中停用按鈕**——比照 S24/S25/S26 每一個會觸發
   mutation 的單一動作按鈕都有的既有慣例(即使 clipboard 寫入通常
   接近即時、不像這些故事的網路呼叫有實質延遲,仍維持與既有模式
   一致的嚴謹度)。這個「停用」本身只防止**同一則訊息**被快速連續
   點擊;真正需要處理的是**不同訊息之間**的並行,見決策 #4 的修正
   說明。

7. **不做「批次複製」或訊息以外任何位置的複製功能**——僅在
   assistant 回覆本身提供複製,沒人要求的範圍擴張一律不做,同這整個
   session 一貫的紀律。

## Assumptions / 計畫外事項

1. **這個 repo 第一次在單元測試中使用 `vi.useFakeTimers()`**——
   為了測試「已複製」在短暫延遲後自動還原,不用真實等待 2 秒
   拖慢測試套件。用 `shouldAdvanceTime: true` 選項讓 Testing
   Library 內部的 `findBy*`/`waitFor` 輪詢機制仍以真實時間運作,
   只有明確呼叫 `vi.advanceTimersByTime()` 的那一步是手動快轉——
   這是標準、有據可查的 RTL/Vitest 搭配用法,不是這個 codebase
   特有的發明,且已透過 `try/finally` 搭配 `vi.useRealTimers()`
   確保不會洩漏到檔案內其他 describe block。
2. **複製的是原始文字(含 `[1]` 引用標記字面字元),不是去除標記
   後的「乾淨」版本**——見設計決策 #3,這就是使用者在畫面上實際
   看到的文字。
3. **成功確認的還原延遲固定為 2 秒,沒有讓使用者自訂**——
   SOURCE_BASELINE 與 epic 檔皆未提及此細節,2 秒是真實聊天產品
   常見的短暫確認時長,MVP 不需要做成可設定值。
4. **沒有為「複製失敗」提供重試按鈕**——與 S25 刪除失敗的處理不同
   (那裡失敗後仍停留在確認畫面,可以再按一次「確認刪除」);這裡
   失敗訊息旁邊就是同一顆「複製」按鈕本身,再點一次就是重試,不需要
   額外的「重試」按鈕造成重複的互動元素。
5. **同一則訊息被「繞過 `disabled` 保護」重疊觸發兩次
   `handleCopy` 的情境未特別處理**(第 2 輪獨立審核 MINOR,經審核者
   自行寫模擬程式確認):後 resolve 的呼叫在
   `copyResetTimeoutsRef.current.set(messageId, ...)` 時會覆蓋前一個
   計時器控制代碼而不去 clear 它,理論上可能讓一個計時器變成孤兒、
   提早觸發還原。審核者已確認這條路徑在目前的 UI 下**不可觸發**——
   `disabled` 屬性在事件處理函式的同一次同步執行內、第一個 `await`
   之前就已提交,瀏覽器不可能在按鈕變成 disabled 之前送出第二次
   點擊,且整個 codebase 沒有任何地方直接呼叫 `handleCopy` 繞過這顆
   按鈕。故意不為一個結構上不可能發生的情境加防呆——同這個 repo
   一貫「不為不會發生的情境加驗證/防禦」的紀律。
