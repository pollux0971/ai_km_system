# E03-S028 — File-chat entry flow

## Scope 說明

SOURCE_BASELINE.md 對本 story(line 1239)只有標題「E03-S28 File
Chat」,無任何內文。Epic 檔的展開標題「File-chat entry flow」——
「entry flow」是關鍵字:這是一個**進入點**(如何開始一個以檔案為
中心的對話),不是 E03-S008「File Attachment Picker」(在已存在的
對話中,對訊息附加檔案)的變形或重複。緊接在後的下一個 story
(E03-S29「File Processing Status」)進一步確認這個判斷:「上傳檔案
→ 開始對話」與「顯示該檔案的處理狀態」是刻意分開的兩個 story,
本 story 的範圍止於「進入」這個動作本身,不含檔案處理狀態呈現
(那是 S29 的範圍,本 story 不得偷跑)。

「unarchive」在 S26、「answer」在 S27 都是唯一但明確的方向依據;這裡
「entry flow」同樣是唯一但明確的依據——這是一條**新的進入路徑**,
不是修改既有進入路徑的內部行為。

## 設計決策(含考慮過的替代方案)

這個 story 的核心設計問題:「以檔案開始新對話」這個能力,應該
**retrofit 既有的 `/conversations/new`**(E03-S001,目前是零互動、
mount 時立即建立並導回列表頁的設計),還是**新增一個獨立、附加性的
進入點**?兩者都能滿足「File-chat entry flow」這個名稱,但風險與
影響範圍差異很大,值得記錄完整的權衡過程:

**選項 A(retrofit `/conversations/new`)**:把檔案選擇器加進這個
既有頁面,移除 mount-時自動建立的行為,改成「選檔案(可為零)→
按鈕觸發建立」。優點是只有一個「開始新對話」進入點,語意統一。
缺點:這會直接改變 E03-S001(已核准)明確測試過的行為——
`conversations.spec.ts` 的「starting a new conversation creates it
and lands back on the list showing it」寫死了「點擊開始新對話 →
立即回到列表頁」這個零互動流程;`page.test.tsx` 的 StrictMode
雙重呼叫防護測試也建立在「mount 時自動觸發」這個前提上。要保留
這些既有斷言的精神(而非直接刪改),同時又要支援檔案優先進入,
勢必要在同一個元件裡分岔出兩條路徑,複雜度與回歸風險都不小,且
SOURCE_BASELINE 完全沒有提示「這兩個進入點必須合併成一個」。

**選項 B(新增獨立進入點,本 story 採用)**:新增
`/conversations/new-file` 路由,`/conversations/new` 完全不動。
列表頁上「開始新對話」旁邊加一個語意清楚區隔的「上傳檔案開始
對話」連結。優點:零風險觸碰任何既有已核准 story 的行為與測試
(已用完整迴歸套件驗證,見下方 Gate 紀錄);兩個進入點的意圖本來就
不同(「我要開始打字」vs「我要上傳檔案讓 AI 看」),分開陳列對使用者
反而更清楚,不是刻意規避複雜度的偷懶選擇。缺點:多一個路由、多一個
連結,列表頁的視覺選項從 1 個變 2 個——這是這個決策唯一的實質
代價,相對於選項 A 的回歸風險,判斷這個代價更值得付出。

**判斷依據**:依 `/advisor` 演算法 Step 4 的自主採納標準——這個決策
單一 story(其實還是同一個 domain: E03 對話)範圍內、低風險、
可回退(純前端 mock,revert merge commit 即可),不涉及 contract
變更、不涉及安全/授權行為、不涉及跨 Team A/B 介面——屬於「可自行
採納推薦解」而非「必須問使用者」的類別。已查過 SOURCE_BASELINE §5
的 40 條 pinned 決策,無一條與「新舊進入點是否該合併」相關,規格
本身無答案,故依風險/回退成本分析後採用選項 B,記錄於此。

## 其他設計決策

1. **重用既有的 `FileAttachmentPicker`(S008),不重造一個**——這個
   元件本來就是「受控、狀態由 parent 擁有」的設計,對它而言「在哪個
   父層被渲染」是無關的,不需要修改就能直接在新頁面重用。從
   `[id]/_components/` 用相對路徑匯入,而不是搬移到共用
   `_components/` 資料夾——唯一另一個使用者(MessageComposer)
   不受影響,搬移一個已核准 story 在用的檔案是比跨路由 segment
   匯入更大、更沒必要的變更,純粹為了目錄整潔不是理由。

2. **「開始對話」必須至少選 1 個檔案才能啟用**——這個路由存在的
   唯一理由就是「檔案優先」進入;想要空白對話的使用者本來就有
   「開始新對話」可用,這裡不重複那個路徑。

3. **`createConversation()` 成功、但 `sendMessage()` 附加檔案失敗時,
   rollback(呼叫 `deleteConversation()` 刪掉剛建立的對話)**——
   對應 Functional AC 2/5「不得產生部分 side effect」:沒有這個
   rollback,失敗畫面背後會留下一個使用者從未真正開始、也看不到的
   「幽靈」空對話。這個 race 在目前單分頁 mock 下實際上不可能發生
   (`sendMessage` 唯一的失敗分支是 NOT_FOUND,而附加訊息呼叫的 id
   就是剛剛才建立、同一個同步流程內的 id,沒有外部干擾管道)——
   但 rollback 邏輯本身是真實、有測試覆蓋的程式碼,正確實作了 AC
   要求的語意,不是為了看起來嚴謹而寫的沒有意義的防呆(對照 S027
   round 2 審核者判斷「繞過 disabled 保護」的邊界情況不可觸發、
   故意不加防呆是同一種判斷力,這裡的差異在於：這裡的失敗分支
   `sendMessage` 本身是真實存在、可測試的分支,不是要繞過 UI 保護
   才能觸發的情境）。

4. **成功後導向新對話的「詳情頁」(`/conversations/${id}`),不是
   列表頁**——與 E03-S001 的既有導頁目標刻意不同:檔案優先進入的
   重點就是「馬上進到那個對話裡」,導回列表頁只會讓使用者需要再點一次
   才能看到剛剛附加的檔案,不是好的使用者體驗。

5. **不會在導頁後自動觸發 AI 串流回覆**——`sendMessage()` 只是資料層
   函式,真正觸發 AI 串流的邏輯(`attemptSend`→`startStream`)存在於
   `message-thread.tsx`,由 MessageComposer 的送出動作觸發,這個
   story 沒有理由發明一個「對話一 mount 就自動觸發串流」的新機制
   (這個 codebase 目前沒有任何地方這樣做)。使用者進入新對話後,
   看到自己剛附加檔案的訊息,可以照常透過既有的 composer 繼續對話
   ——MVP 可以簡化演算法,但「檔案優先進入」這個能力本身(不是
   「AI 自動先開口」)才是這個 story 名稱實際要求的。

6. **內容(content)採用空字串,只附加檔案,不預先填入提示文字**——
   `sendMessage` 的「純附件、無文字」路徑已經是 S009 既有、有測試
   覆蓋的合法用法(`send-message.spec.ts`「an attachment-only
   message (no text) can be sent」);發明一段「請幫我分析這個
   檔案」之類的預設提示文字,SOURCE_BASELINE 沒有要求,且落入這個
   session 一貫避免的「捏造沒人要求的內容」。

## Assumptions / 計畫外事項

1. **`/conversations/new` 與 `/conversations/new-file` 是兩個平行、
   都會長期存在的進入點,不是後者取代前者**——見上方完整的選項 A/B
   權衡分析。若未來使用者/Product Owner 認為應該合併成一個進入點,
   那是一個需要重新評估既有 S001 測試與行為的決策,超出本 story
   範圍。
2. **不自動觸發 AI 對上傳檔案的第一則回覆**——見設計決策 #5,MVP
   範圍止於「檔案優先進入」這個能力,不含「AI 自動先開口」。
3. **檔案本身沒有真正上傳到任何儲存服務**——與 S008 完全相同的既有
   限制(這個 codebase 的 Frontend/BFF 依規定不得直連 Object
   Storage),只有檔名被記錄為 `attachmentNames`。
4. **沒有檔案型別/大小/數量限制**——與 S008 的既有判斷完全相同
   理由:SOURCE_BASELINE 對這個層級的限制沒有定義任何具體數值,
   真正的驗證規則屬於 E06(Team B)的 ingestion parser story。
