## Scope 說明

SOURCE_BASELINE.md 對本 story(line 1243)只有標題「E03-S29 File
Processing Status」,無任何內文。Epic 檔的展開標題「File-processing
status UI」——這是為「檔案」顯示「處理狀態」的 UI,不是新的附件
機制本身。緊接在前的 S28「File-chat entry flow」的 EVIDENCE 已經
明確記錄「本 story 止於建立對話並附加檔案、導頁,不含檔案處理狀態
呈現(那是 S29 的範圍)」——這正是本 story 要接手完成的部分,適用於
S08(既有 composer 附件選擇器)與 S28(新的檔案優先進入點)兩個
附件來源。

## 設計決策(含考慮過的替代方案)

**核心設計問題**:這個 codebase 沒有真正的 E06(Knowledge Ingestion,
Team B)後端可以回報檔案處理的真實結果,要如何讓「處理中」與
「處理失敗」兩個狀態都真的「不可缺席」(而不只是寫在程式碼裡卻永遠
不會被觸發)?

依循 S21「Answer State」已經建立的先例(SOURCE_BASELINE 同樣沒有給
真正的分類依據,S21 用 `MOCK_ANSWER_STATE_TRIGGERS` 這種明確具名、
可匯出、有文件記錄的 mock trigger 常數解決同一類問題)——本 story
新增 `lib/file-processing.ts` 的 `classifyFileProcessing`,用同一種
`[模擬:X]` 括號標記慣例(`MOCK_FILE_PROCESSING_FAILURE_TRIGGER =
"[模擬:PROCESSING_FAILED]"`),讓檔案名稱裡含有這個標記時確定性地
（deterministic）觸發處理失敗。這不是唯一可能的做法,但是與這個
codebase 既有慣例最一致、風險最低的做法——沒有發明新的 mock 機制
類型,只是把 S21 已經驗證過的模式套用到另一個需要 mock 分類的情境。

**「處理中」狀態該顯示在哪裡**:考慮過兩個選項——

1. **持久化狀態,存在 Message 物件上,每次載入歷史對話都重新顯示**
   ——會導致每次重新整理/重新進入對話,已經處理完成的舊檔案都會
   再閃一次「處理中」,這是真實產品不會有的、明顯錯誤的使用者體驗
   （重新處理已經處理過的檔案),故排除。
2. **純前端、ephemeral(不持久化)的模擬,只依附在「這個 session 中
   剛送出」的訊息生命週期上(本 story 採用)**——`message-thread.tsx`
   既有的 `pending` DisplayMessage kind 本來就只在「這次 session
   中剛送出、尚未確認」的訊息才會出現(從 `listMessages()` 載入的
   歷史訊息一律直接是 `sent`,從未經過 `pending`)——這個既有的
   結構本身就是「這是不是這次新送出的」的天然信號,不需要另外
   發明一個新的追蹤機制。把處理模擬掛在 `attemptSend`
   （`pending`→處理→`sendMessage`→`sent`/`failed`)這條既有生命
   週期上,歷史訊息完全不受影響,自然、正確地只顯示已完成的附件。

**兩個附件來源(S08 composer / S28 file-chat entry)是否要有一致的
「處理中」視覺呈現**:考慮過讓 `/conversations/new-file`
（S28)也加一個像 `message-thread.tsx` 一樣的多階段可見「處理中」
畫面,但決定不這麼做——那個頁面已經有自己的通用「建立中…」
pending 指示器涵蓋整個多步驟流程(建立對話+附加檔案),另外加一個
獨立的「檔案處理中」視覺概念是這個 story 沒有要求的新 UI 模式。
改為讓兩個進入點共用**同一個**純函式 `classifyFileProcessing`
（無延遲版本),`/conversations/new-file` 在建立對話之前就先檢查,
失敗就提早結束、顯示專屬錯誤訊息,不需要建立任何東西才失敗
（比 S28 原有的「sendMessage 失敗才 rollback」路徑更早、更簡單)。

## 其他設計決策

1. **新增 `attachment-failed` 這個獨立的 DisplayMessage kind,不
   重用既有的 `failed`**——延續 S23/S26 已經建立的「不同成因不共用
   同一個標籤」原則:「檔案處理失敗」與「訊息傳送失敗」是不同的
   底層原因,重用同一個「傳送失敗」文字會誤導使用者以為問題出在
   網路/傳輸層,而不是檔案本身。對應的重試文字也不同(「重新處理」
   vs.「重新傳送」),但實際重試機制(回到 `pending`、重跑
   `attemptSend`)完全共用既有的 `handleRetry`,只是把判斷條件從
   `entry.kind === "failed"` 擴大成 `failed || attachment-failed`
   ——顯示要分開,機制不需要分開。

2. **`pending` 狀態的文字依是否有附件分岔("檔案處理中…" vs. 既有的
   "傳送中…")**——同樣是「不同情境不共用同一段文字」的既有原則;
   沒有附件的訊息完全不會呼叫 `simulateFileProcessing`,行為與
   文字都與 S29 之前完全一致(已用既有測試套件的零回歸驗證確認)。

3. **重試是確定性的(同樣的檔名 → 同樣的結果)**——與 S21
   answer-state trigger 的既有行為一致:同一個觸發字串每次都
   分類成同一個結果,不是隨機成功/失敗。這不是 bug,是這個 mock
   分類機制本身的設計。

4. **`simulateFileProcessing`(有延遲)與 `classifyFileProcessing`
   (無延遲)分成兩個匯出**——見上方「該顯示在哪裡」的分析:兩個
   呼叫端需要的東西不一樣(一個要看得見的等待階段、一個只要快速
   判斷結果),硬塞成同一個 API 會強迫其中一端接受不需要的行為。

## Assumptions / 計畫外事項

1. **處理狀態是純前端 ephemeral 模擬,不持久化到 Message 物件**——
   見設計決策的完整分析,這是刻意的選擇,避免歷史訊息重新載入時
   錯誤地重新顯示「處理中」。
2. **`/conversations/new-file`(S28)沒有可見的多階段「處理中」畫面,
   只有提早失敗檢查**——見設計決策的完整分析,那個頁面已有自己的
   通用 pending 指示器,不需要第二個獨立的視覺概念。
3. **重試是確定性的(同檔名必定同結果)**——與 S21 既有的
   mock trigger 行為一致,不是隨機化的 mock。
4. **沒有為個別檔案分別顯示狀態(一則訊息的多個附件共用一個聚合
   狀態)**——SOURCE_BASELINE 未要求逐檔案的細粒度狀態,MVP 簡化
   為整批訊息層級的單一狀態,同這整個 session 一貫的「不做沒人
   要求的細節」紀律。
