## 設計決策

1. **沒有真正的網路傳輸可以斷線,所以用確定性 mock trigger**——
   延續 S21 `MOCK_ANSWER_STATE_TRIGGERS`、S29
   `MOCK_FILE_PROCESSING_FAILURE_TRIGGER` 已經建立的
   `[模擬:X]` 括號標記慣例,新增
   `MOCK_STREAM_DISCONNECT_TRIGGER = "[模擬:STREAM_DISCONNECT]"`
   與 `shouldSimulateStreamDisconnect(userQuestion)`。這是讓斷線
   路徑真正可以被觸發、可以被測試的唯一方式,不是在寫死不會被執行
   的程式碼。

2. **新增獨立的 `stream-disconnected` DisplayMessage kind,不重用
   既有的 `stream-failed`**——延續 S23/S26/S29 已經建立的「不同
   成因不共用同一個標籤」原則:`stream-failed` 是**串流已經完整
   產生完畢後,持久化(receiveAssistantReply/reviseMessage)失敗**;
   `stream-disconnected` 是**串流本身在生成過程中中途中斷**。這是
   兩個發生在完全不同時間點、意義完全不同的失敗——重用同一個標籤
   會誤導使用者對發生了什麼、重試代表什麼的理解。對應的文字
   (「連線中斷」vs.「AI 回覆失敗」)與重試按鈕文字(「重新連線」
   vs.「重新產生回覆」)都刻意不同,但底層機制(都是「回到某個
   pending-like 狀態,重跑 runStream」)可以共用同一種模式,只有
   呈現需要分開。

3. **保留已經收到的部分內容,不丟棄**——延續 S12「Stop
   Generation」已經建立的先例(「real chat products keep whatever
   was generated so far rather than discarding it」):斷線發生時,
   使用者已經看到部分文字出現在畫面上,直接消失會比保留、標示
   「連線中斷」更讓人困惑。`streamAssistantReply` 刻意在產生**部分
   真實內容之後**(約整體長度的一半,不是一開始就斷)才拋出,確保
   這個保留行為有真正的內容可以測試。

4. **重新連線是從頭重新開始整個串流,不是真正從中斷點續傳**——這個
   mock 沒有任何基礎設施可以支援真正的續傳(沒有 chunk 序號、沒有
   伺服器端狀態可以查詢從哪裡繼續),假裝有續傳能力會是對一個未來
   真實實作能誠實承諾什麼的誤導。符合 AC8「MVP 可以簡化演算法」的
   允許範圍,同時忠實反映這個 mock 的真實限制,不誇大。

5. **重新連線沿用原本的 `answerState`,不是重新分類或預設回
   ANSWERED**——`stream-disconnected` 這個 kind 本身攜帶原本的
   `answerState`(只可能是 ANSWERED 或 PARTIAL——其餘 4 個狀態的
   固定 fallback 內容是同步設定的,從未進入真正的串流迴圈,結構上
   不可能發生斷線),`handleReconnect` 直接把這個值原封不動傳回
   `runStream`,確保重新連線後的最終持久化結果與最初的分類一致。

6. **確定性重試(同樣的 trigger 會再次斷線)**——與 S21/S27/S29/S30
   已經一致建立的「同樣輸入 → 同樣的 mock 結果」原則完全一致,不是
   隨機化的 mock,重新連線後如果原始訊息仍含有觸發字串,會再次
   斷線,這是正確、預期的行為,不是 bug。

7. **刻意不接上 `handleRegenerate`**——`handleRegenerate` 只接收
   已經settled 的 assistant `Message` 物件本身,從來沒有存取過
   使用者原本問題的文字(這正是 S21 讓 regenerate 重用既有
   `state` 而非重新分類的同一個既有理由)。要讓 regenerate 也能
   觸發斷線,需要發明新的資料傳遞路徑(把使用者原始問題文字一路
   傳到 `handleRegenerate`)——這是沒人要求的新管線工程,不做。
   斷線模擬因此只套用在「全新一輪對話」(attemptSend →
   startStream)這條路徑上,這也是 S21/S29 既有的
   classifyAnswerState/classifyFileProcessing 唯一會檢查「剛送出
   的使用者訊息」的地方,保持一致。

## 變更檔案

- `apps/web/src/lib/streaming.ts` ——新增
  `MOCK_STREAM_DISCONNECT_TRIGGER` 常數與
  `shouldSimulateStreamDisconnect(userQuestion)` 純函式;
  `streamAssistantReply` 新增第二個參數 `simulateDisconnect = false`
  (預設值確保所有既有呼叫端行為完全不變),為 true 時在產生約一半
  內容後 `throw`。文件註解更新,呼應 S10 當初預留的伏筆。
- `apps/web/src/lib/streaming.test.ts` ——新增 5 個測試:
  `shouldSimulateStreamDisconnect` 的一般/含 trigger 兩種輸入;
  `simulateDisconnect` 預設 false 時行為完全不變;為 true 時在產生
  部分真實內容後拋出(非零、非完整長度);同樣輸入下斷線點具確定性
  (兩次呼叫结果一致)。
- `apps/web/src/app/(app)/conversations/[id]/_components/message-thread.tsx`
  ——`DisplayMessage` 新增 `stream-disconnected` kind(帶
  `content`、`answerState`)。`attemptSend` 計算
  `shouldSimulateStreamDisconnect(content)` 並傳給 `startStream`。
  `runStream`/`startStream` 新增 `simulateDisconnect` 參數,一路
  傳給 `streamAssistantReply`;串流迴圈包上 try/catch,catch 到的
  任何錯誤視為斷線(這個 generator 是迴圈內唯一可能拋錯的來源,見
  程式內文件註解說明為何不需要專屬錯誤型別)。新增
  `handleReconnect(localId, answerState)`,把該筆訊息拉回
  `streaming` 狀態並重跑 `runStream`,`simulateDisconnect`
  無條件傳 `true`(能走到這個狀態代表原本就是 true)。渲染:
  `role`/`attachmentNames` 的既有 ternary 補上 `stream-disconnected`
  分支(否則會誤判為使用者訊息、缺少 attachmentNames 型別);新增
  「連線中斷」`role="alert"` + 「重新連線」按鈕的渲染區塊,放在
  `attachment-failed` 之前。文件註解新增 S31 段落。
- `apps/web/src/app/(app)/conversations/[id]/_components/message-thread.test.tsx`
  ——`@/lib/streaming` 的 mock 新增
  `shouldSimulateStreamDisconnect: vi.fn().mockReturnValue(false)`,
  `beforeEach` 新增對應 reset+預設值(確保所有既有測試不受影響地
  繼續通過)。新增獨立 describe block「MessageThread stream
  disconnect/reconnect UX (E03-S031)」共 5 個測試:斷線時顯示
  「連線中斷」且保留已收到的部分內容;`streamAssistantReply` 正確
  依 `shouldSimulateStreamDisconnect` 的結果傳入 true/false;點擊
  「重新連線」重新開始整個串流,成功後以**原本的**
  answerState(用 PARTIAL 觸發字串驗證,不是預設的 ANSWERED)持久化;
  重新連線在同樣觸發字串仍存在時會確定性地再次斷線,不會卡住或
  靜默成功;attempt/disconnected telemetry 共用同一個
  correlationId。
- `tests/e2e/specs/stream-disconnect-reconnect.spec.ts`(新增)——
  2 個關鍵流程測試:含觸發字串的訊息顯示「連線中斷」且保留部分
  回覆內容;點擊「重新連線」真的重新嘗試(不是卡住的舊狀態),
  在同樣觸發字串下確定性地再次斷線。

## Assumptions / 計畫外事項

1. **SOURCE_BASELINE.md 完全沒有本 story 的章節**——已完整搜尋
   確認,E03 的條目在 S30 就結束。本 story 完全依據 epic 檔的展開

2. **重新連線是從頭重新開始,不是真正的續傳**——這個 mock 沒有

   更完整的能力。
3. **斷線模擬只套用於全新一輪對話,不套用於 regenerate**——
   `handleRegenerate` 沒有存取使用者原始問題文字的既有管線,新增
   這個管線是沒人要求的擴張,見設計決策 #7。
4. **斷線點固定在約一半長度,不可設定**——SOURCE_BASELINE 與 epic
   檔皆未要求特定斷線時機,約一半是確保「有部分真實內容可以保留」
   這個行為能被真正測試到的最簡單選擇。
