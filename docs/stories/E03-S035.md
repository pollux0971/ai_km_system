## AC6 rewrite 即時驗證
自動化測試(`next-config-rewrites.test.ts`)只驗證 `rewrites()` 回傳的設定物件正確(source/destination、`API_INTERNAL_URL` 覆寫與預設值),不啟動真實伺服器。AC6 要求「以 Next dev server + 假 API...驗證」,因此額外手動跑過一次真實代理:

```
# 1. 起一個假 API,只回應 GET /v1/health
node /tmp/fake-api-health.mjs   # 監聽 127.0.0.1:4171,回 {"status":"ok","from":"fake-api"}

# 2. 用非爭用中的 port(3910,避開 :3000/:3001 多 lane 共用資源)起 apps/web dev server
cd apps/web && API_INTERNAL_URL=http://127.0.0.1:4171 npx next dev -p 3910

# 3. 驗證
curl -i http://127.0.0.1:3910/api/v1/health
# HTTP/1.1 200 OK
# content-type: application/json
# {"status":"ok","from":"fake-api"}
```

回應 body 逐位元等於假 API 的原始回應,證明 `/api/v1/:path*` → `${API_INTERNAL_URL}/v1/:path*` 的轉發確實生效。驗證後已 `pkill`/`kill -9` 關閉兩個臨時程序並確認 3910/4171 port 已釋放,未留下背景程序;過程未使用 :3000/:3001,不需 `flock`(那條規則是為 `tests/e2e/playwright.config.ts` 綁死的固定 port 而定,本次驗證刻意避開)。

## Assumptions / 計畫外事項
- AC3「5xx→SERVICE_UNAVAILABLE」的字面解讀與 `auth.yaml` 實際契約(`/auth/session` 的 500 回應是 `INTERNAL_ERROR`,不是 `SERVICE_UNAVAILABLE`)有落差。判斷:AC 原文重點是「5xx/網路錯誤都必須是 `ok:false`(觸發 session-gate 的 error 狀態),不能被誤判成登出」,而不是「所有 5xx 都要被改寫成 `SERVICE_UNAVAILABLE` 這個特定 code」——把伺服器真實回傳的 `INTERNAL_ERROR` 硬改寫成 `SERVICE_UNAVAILABLE` 反而違反 API/Contract Boundary「不得讓 consumer 依賴 exception text」以外的另一條原則(不得竄改 server 給的穩定 machine-readable code)。因此實作採「code 原樣保留,只有真正的網路/解析失敗才用 `SERVICE_UNAVAILABLE`」,並在測試中分別驗證這兩種情況(500→`INTERNAL_ERROR`、fetch 拋出→`SERVICE_UNAVAILABLE`),`session-gate.tsx` 本身也只檢查 `!result.ok`、不檢查 code,所以兩種情況都會正確顯示 error 狀態、不誤判登出,行為上完全符合 AC3 的真正意圖。
- AC5(L5 多分頁/重整/登出 E2E)明確延後至 E03-S038 合併後補齊,依 spec 自己的 Definition of Done 這是被允許的,不視為本 story 不完整。
