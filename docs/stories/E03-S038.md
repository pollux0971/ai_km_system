## 開發過程中的除錯（誠實記錄，非 AC1 的 12 個失敗）
本 story 自己的 7 個新測試開發過程中，發現並修正 4 個問題，全部是**測試碼本身**的 bug，不是產品邏輯：

| # | 症狀 | 根因 | 修法 |
|---|---|---|---|
| 1 | 兩個 context 隔離測試：`expect(count).toBe(baseline+1)` 得到 0 | 建立對話後 SPA 已 client-side 導到 `/conversations`，我的 helper 又多呼叫一次 `page.goto()`，觸發真正 hard reload；重新掛載的元件在讀取當下還沒 fetch 完（console log trace 證實：一次 loading log 都還沒出現） | 已在該 URL 就不重複 `goto` |
| 2 | 同 context 第二分頁測試：同樣得到 0，但已排除是 reload 問題 | `SessionGate` 自己的 `role="status"` 在 React Strict Mode 的「掛載→cancel→重新掛載」之間短暫消失又重新出現，我原本的「等 status 歸零」在那個空檔被騙過，實際 session 還沒解析完（console log trace 證實：兩次都沒看到 session-gate 或 conversation-list 自己的 log） | 改成等待頁面固定渲染的 `<h1>對話</h1>` 標題可見（只有 SessionGate 進入 authenticated 才會渲染），正訊號不受空檔影響 |
| 3 | E04-S052 seed 接線後，兩個 isolation 測試又紅：`expected 3, received 2` | 改用 DOM `<li>` 計數時，`CONVERSATIONS_PAGE_SIZE=2` 的分頁上限讓「種子 3 筆 + 新建 1 筆」的 delta 判斷失效 | 改成直接讀 API `totalCount`，不受分頁影響，也不用等 UI render（順帶解決 #1/#2 這整類 DOM 計數時序問題） |
| 4 | 改用 API 計數後，同 context 第二分頁測試又紅：`fetch` 解析 URL 失敗 | `context.newPage()` 產生的全新分頁停在 `about:blank`，沒有合法 origin 給相對路徑 `fetch()` 解析 | 偵測到 `about:blank` 就先 `page.goto()` 一次 |

每一輪都用 `curl`／console log trace／直接讀原始碼獨立驗證根因後才動手修，未曾用「放寬斷言」或「加 retry」處理。

## AC1 現況與待裁示（誠實記錄，非宣稱完成）
**259/271 通過，12 個失敗全部歸類到兩個有文件根據的根因，皆非本 story 回歸：**

**根因 1（10 個失敗：`case-detail.spec.ts` ×3、`erp-e2e.spec.ts` ×1、`maintenance-e2e.spec.ts` ×2、`maintenance-session.spec.ts` ×4）**：這些既有 spec 的檔案自身 doc comment 明文記載測試設計前提——例如 `case-detail.spec.ts`：「loses the mock AuthClient's in-memory session（a hard reload always does）」、`erp-e2e.spec.ts`：「a hard reload/navigation loses the mock AuthClient's in-memory-only session」。這些測試用 `page.goto(受保護路徑)` 或硬重整，預期觸發「session 遺失 → 導向 /login」來建構「未登入」情境。但 E03-S035 的真實 cookie session **正確地**在硬重整後仍然存活（`session-persistence.spec.ts` 本身就是專門驗證這件事的測試），於是這些既有測試預期的 `waitForURL(pathname === "/login")` 永遠不會發生而逾時。**這是新系統做對了、舊測試前提過時，不是回歸。**

**根因 2（2 個失敗：`knowledge-selector.spec.ts` ×2）**：`knowledge-selector.tsx` 元件自身 doc comment 明文：「Non-optimistic...the mock resolves near-instantly, nothing to hide latency-wise」——checkbox 勾選狀態要等 API 回應才更新。舊 mock 近乎同步，Playwright `.check()` 內建的「點擊後驗證狀態改變」能在其較短的內部逾時內完成；真實後端有真實（即使很小的）網路延遲，讓 `.check()` 自己的驗證視窗來不及看到真正的 re-render，回報「Clicking the checkbox did not change its state」。

**兩個根因的共同性質**：既有 264 個 E2E 是對著 client 端 mock 撰寫，隱含「mock 近乎同步」與「任何 reload 清空 mock 的記憶體狀態」兩個假設。這批批次（E03-S034~S038）的整體目的正是把這些假設換成真實基礎設施——而這 12 支測試恰好是**依賴**這兩個假設本身作為測試手法（不是被這兩個假設影響的旁觀者），所以它們的失敗是「基礎設施升級的直接、可預期後果」，不是升級過程中的意外破壞。

**待使用者/ai-km-e4 裁示**：AC1 原文「既有 264 個零修改全綠」在這 12 支 spec 上可能永遠無法達成（除非另立 story 修改這 12 支測試本身的假設——那需要修改既有測試，不在本 story 或任何人目前的允許修改清單內）。兩個可能方向已於 2026-08-29 提交 ai-km-e4 裁示，尚未收到回覆：
1. 接受這 12 個為已知、有文件根據的例外，記錄於此即視為 AC1 精神上已達成（因根因是「新系統更正確」而非「新系統壞了」）；
2. 另立 story 修正這 12 支測試的過時假設（範圍：把「硬重整會登出」改成「明確按登出鈕」、`knowledge-selector` 補上等待真實延遲的寬容度）。

## Assumptions / 計畫外事項
- **跨 lane 協調**：開發過程中一度以為 seed sandbox 接線（`registerSandboxSeeder`）是本 story 範圍，經與 ai-km-e4 逐行核對 spec 邊界後確認屬於另一個 domain（後續立案為 E04-S052，由 W3 完成），本 story 全程未觸碰 `apps/api/src`/`services/*`。
- **共用 apps/api 與本 story 自管實例的 port 分離**：開發過程中一度把新 webServer 設在預設的 4000 port 並 `reuseExistingServer:true`，實測發現這會靜默重用 ai-km-e4 手動維護的共用實例（同 port），完全架空本 story 的隔離設計。改為專用 port 4100 + `reuseExistingServer:false` 後解決，記錄於 `playwright.config.ts`/`README.md`。
- **`globalSetup` 與 `launchOptions.args` 的執行時機限制**：假麥克風 WAV 路徑最初想透過 Playwright 的 `globalSetup` hook 產生，實測發現 `globalSetup` 執行時機晚於 config 物件建構完成，路徑無法餵進 `use.launchOptions.args`（該欄位在 config 求值當下就已固定）。改為在 config 模組頂層同步呼叫 `ensureFakeMicrophoneWav()` 解決。
- E01-S027（下一個 lane 內 story）現在有了具體、可驗證的根因素材：本 story 的暖機修正讓 admin 的兩支長期 flaky（`admin-e2e`/`admin-analytics-e2e`）穩定通過，強烈佐證「冷編譯，非測試本身不穩」的假設；`maintenance-e2e.spec.ts` 仍在本 story 的 12 個失敗名單中，但那是根因 1（session 前提過時），與 flaky 無關，屆時需要區分清楚。
