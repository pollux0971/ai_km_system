## AC1 開發當下的狀況（歷史快照，已由下方「AC1 最終結果」結案）
**259/271 通過，12 個失敗全部歸類到兩個有文件根據的根因，皆非本 story 回歸：**

**根因 1（10 個失敗：`case-detail.spec.ts` ×3、`erp-e2e.spec.ts` ×1、`maintenance-e2e.spec.ts` ×2、`maintenance-session.spec.ts` ×4）**：這些既有 spec 的檔案自身 doc comment 明文記載測試設計前提——例如 `case-detail.spec.ts`：「loses the mock AuthClient's in-memory session（a hard reload always does）」、`erp-e2e.spec.ts`：「a hard reload/navigation loses the mock AuthClient's in-memory-only session」。這些測試用 `page.goto(受保護路徑)` 或硬重整，預期觸發「session 遺失 → 導向 /login」來建構「未登入」情境。但 E03-S035 的真實 cookie session **正確地**在硬重整後仍然存活（`session-persistence.spec.ts` 本身就是專門驗證這件事的測試），於是這些既有測試預期的 `waitForURL(pathname === "/login")` 永遠不會發生而逾時。**這是新系統做對了、舊測試前提過時，不是回歸。**

**根因 2（2 個失敗：`knowledge-selector.spec.ts` ×2）**：`knowledge-selector.tsx` 元件自身 doc comment 明文：「Non-optimistic...the mock resolves near-instantly, nothing to hide latency-wise」——checkbox 勾選狀態要等 API 回應才更新。舊 mock 近乎同步，Playwright `.check()` 內建的「點擊後驗證狀態改變」能在其較短的內部逾時內完成；真實後端有真實（即使很小的）網路延遲，讓 `.check()` 自己的驗證視窗來不及看到真正的 re-render，回報「Clicking the checkbox did not change its state」。

**兩個根因的共同性質**：既有 264 個 E2E 是對著 client 端 mock 撰寫，隱含「mock 近乎同步」與「任何 reload 清空 mock 的記憶體狀態」兩個假設。這批批次（E03-S034~S038）的整體目的正是把這些假設換成真實基礎設施——而這 12 支測試恰好是**依賴**這兩個假設本身作為測試手法（不是被這兩個假設影響的旁觀者），所以它們的失敗是「基礎設施升級的直接、可預期後果」，不是升級過程中的意外破壞。
