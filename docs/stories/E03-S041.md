## 一個真正的環境限制發現:jsdom 讀不回 FormData 裡的 Blob

**現象(已用最小重現腳本驗證,與本專案程式碼無關)**:在這個
vitest+jsdom 環境下,`new Request(url, {body: someFormData})`——只要
`someFormData` 裡有**任何**一個 `Blob`(不論大小/內容/來源),之後對這個
`Request` 呼叫 `.formData()`、`.text()`、`.arrayBuffer()`,甚至直接
`request.body.getReader()` 手動讀 raw stream,**全部永遠 hang,不丟
例外**。純字串欄位的 FormData(無 Blob)完全正常、秒級回應。直接對
jsdom 的 `Blob` 呼叫 `.arrayBuffer()`——同 E03-S040 已記錄過的發現——
方法根本不存在(`TypeError: b.arrayBuffer is not a function`)。嘗試在
`Blob.prototype` 上補一個用 `FileReader` 實作的 `arrayBuffer()`(E03-S040
自己的測試就是這樣繞過的)**沒有修好**這個更深層的問題——jsdom 內部的
multipart 編碼/解碼顯然還依賴其他非公開方法,不是單補一個公開方法能
解決的。

**處理方式**:`transcribeAudio()` 本身的實作完全不變(照常建立真正的
`FormData` + 真正的 `Blob`,呼叫 `apiClient.transcriptions.POST`——這是
真實瀏覽器唯一正確的做法)。改的只有**測試**:`transcription.test.ts`、
`voice-input-button.test.tsx`、`message-composer.test.tsx` 這三個需要
驗證「有沒有把語音送出去」的測試檔,一律直接
`vi.spyOn(apiClient.transcriptions, "POST")`,在 openapi-fetch 真的建構
出那個會 hang 的 `Request` 之前攔截,同時仍然完整驗證
`transcribeAudio()` 自己組出的 `FormData` 內容(`formData.get("audio")`
`instanceof Blob`、`language`、`conversationId` 欄位)。完整重現步驟與
理由記在 `transcription.test.ts` 檔頭註解。

**`fake-api.ts` 的 `/transcriptions` 部分沒有被浪費**:它是完整、真的會
對 `contracts/openapi/transcriptions.yaml` 做 Ajv 驗證的 handler,只是
**這個 story 自己的 jsdom 單元測試用不到它**(上述限制)。它是為將來
E03-S038/E03-S044 的**真實瀏覽器**(Playwright,非 jsdom,不會有這個
問題)E2E 準備的基礎設施,`resetFakeApi()`/`setNextTranscriptionText()`/
`setNextTranscriptionError()` 三個 test hook 都已就緒可直接用。

## `lib/voice/recorder.ts` 的跨 story 擴充(`onAutoStop`)

**問題**:設計 push-to-talk 的「說完自動辨識送出」流程(AC3)時發現,
E03-S040(已 approved/merged)的 `recorder.ts` 內部靜音/時長自動結束時
是這樣寫的:
```ts
function triggerAutoStop(reason) {
  void stop(reason).catch(() => {});
}
```
自己呼叫 `stop()` 但把回傳的 `VoiceCapture` 直接丟棄(fire-and-forget)。
下游(這個 story)完全沒有管道能拿到那次自動結束產生的錄音——`onStateChange`
只能觀察到「發生了、reason 是什麼」,拿不到資料本身。E03-S040 當時的 AC
沒有任何一條要求下游拿得到那份錄音,只要求自動結束這件事真的發生、
reason 正確,所以這個缺口在當時完全通過測試,沒被抓到。

**試過、證明不可行的替代方案(避免碰 `lib/voice/**`,它不在本 story
允許修改清單內)**:
1. 按鈕自己在 `onStateChange` 觀察到 `state==="finalizing"` 時搶著呼叫
   `recorder.stop("manual")`——不成立。`state` 在自動 stop 的**同步**
   階段(`stop()` 函式一開始、任何 `await` 之前)就已經被設成
   `"finalizing"`,按鈕這個第二次呼叫會因為 `state !== "recording"`
   立刻 `throw`,拿不到任何東西,只是把例外換個地方發生。
2. 按鈕自己在 `onLevel` 上重新做一套 VAD(靜音偵測),搶在 recorder 自己
   偵測到靜音前手動呼叫 `stop("manual")`——技術上可以繞過,但等於在
   E03-S041 domain 裡重造一份 E03-S040 已經有的 VAD 邏輯,兩份的
   threshold/timing 沒有機器保證一致(未來任一邊調參數就會悄悄產生行為
   分歧),而且兩邊的偵測都在跑,仍可能同時觸發、互相 race(誰先呼叫
   `stop()` 誰赢,另一邊落空)。

已把這兩段實際嘗試過程記錄於此(ai-km-e4 明確要求「不要只寫結論」)。

**授權與修法(ai-km-e4 2026-08-28 授權,五條件全部滿足)**:
1. 已證明不做就無法達成 AC3、且已實際試過兩種替代方案並記錄失敗原因
   (見上)。
2. **純加法**:`VoiceRecorder` 介面新增 `onAutoStop(cb: (capture, reason)
   => void): void`,與既有 `onLevel`/`onStateChange` 同一種「不註冊就是
   no-op」模式;`stop()`/`start()` 簽名、VAD threshold/timing、任何預設
   值全部未變。
3. **零商業邏輯**:`triggerAutoStop()` 唯一的改動是把原本
   `.catch(() => {})` 丟棄的 `stop()` 結果,改成
   `.then(capture => autoStopCallback?.(capture, reason)).catch(() =>
   autoStopCallback?.(null, reason))` 轉交出去;沒有動任何 VAD 判斷、
   threshold、時間常數。
4. E03-S040 既有 23 個測試**零修改**,rerun 全綠;新增 5 個
   `onAutoStop` 專屬測試(silence 交付 capture、max_duration 交付
   capture、max_duration+從未偵測到語音時交付 `null`、手動/cancel stop
   時**不**觸發 `onAutoStop`、不註冊 callback 時行為與修改前完全一樣)
   ——全部**新增**進既有測試檔,沒有改動任何既有案例。現為 28 個測試,
   全綠。
5. 雙向留痕:本節即 E03-S041 這邊的記錄;`docs/stories/E03-S040.md`
   檔尾已附一段「附註(E03-S041 追加)」說明同一件事。

## Assumptions / 計畫外事項

1. **`onTranscript: (text: string) => boolean` 的回呼設計**:spec 只說
   「新增 prop onVoiceTranscript 不外露——由 composer 內部處理」,未定義
   `VoiceInputButton` 與 `MessageComposer` 之間內部回呼的確切簽名。因為
   `conversation_voice_transcribe_success` 的 telemetry 需要
   `autoSent`(是否真的自動送出了)這個欄位,而「是否自動送出」是
   `MessageComposer` 自己的決定(取決於它當下的草稿是否為空)——按鈕本身
   不可能知道——設計成 `onTranscript` 回傳 `boolean`,讓決策方(composer)
   把結果回傳給需要記錄 telemetry 的一方(button)。這是內部實作細節,
   `MessageComposer` 的公開 props 完全未變。
2. **`isVoiceCaptureSupported()` 不支援時的 tooltip 文案**:spec 給的 3
   個範例(「語音輸入需要HTTPS連線」「瀏覽器未授權麥克風」「找不到麥克風」)
   其實對應 3 種不同來源——第一個是 `isVoiceCaptureSupported()` 的靜態
   環境檢查(啟動前就知道),後兩個是**啟動後**`getUserMedia` 實際失敗的
   執行期錯誤(`VoiceCaptureError.code`)。`isVoiceCaptureSupported()`
   本身無法區分「非HTTPS」與「瀏覽器太舊無AudioWorkletNode」,spec 3 個
   範例也不是窮舉——為「不支援」的其他靜態原因(如舊瀏覽器)補了一個
   通用 fallback 文案「此瀏覽器不支援語音輸入」,不在 spec 明列的 3 句
   內,但屬於同一類「原因說明」精神的合理延伸,非新增行為分支。
3. **`DEVICE_BUSY`/`UNKNOWN`/`NOT_SUPPORTED`(啟動期)、client 端
   `TOO_SHORT` 的訊息文案**:spec 只明講 `PERMISSION_DENIED`/`NO_DEVICE`
   兩種 tooltip 與 API 的 `AUDIO_TOO_SHORT`→「錄音太短」;
   `VoiceCaptureError` 還有 `DEVICE_BUSY`/`UNKNOWN`/`NOT_SUPPORTED`
   三種 code(E03-S040 既有定義),以及 recorder 自己 `stop()` 可能丟出的
   client 端 `TOO_SHORT`(語音太短,連伺服器都沒送到,不同於 API 的
   `AUDIO_TOO_SHORT`)。這些都補上了與既有文案風格一致的合理訊息(見
   `voice-input-button.tsx` 的 `startErrorMessage`/
   `transcribeErrorMessage`),避免任何錯誤 code 落到「無訊息」的死角,
   非 spec 逐字要求但屬必要的錯誤處理完整性。
4. **元件卸載時的資源釋放**:spec 未明文要求,但若使用者在錄音中途離開
   頁面,不清理會留下一個活的麥克風串流(隱私/資源洩漏)。加了一個
   unmount 時的 `useEffect` cleanup,狀態為 `recording`/`requesting` 時
   呼叫 `stop("cancel")`。判斷為必要的正確性/隱私考量,不算 scope 外
   功能擴張。
