## 開發過程中發現並修正的既有 bug：`isFeatureEnabled()` 的動態 env 存取在真實瀏覽器裡從未生效

**症狀**：單元測試（vitest，真實 Node.js `process.env`）全數通過後，第一輪完整 E2E 單輪跑出 18 個失敗，且失敗集中在本 story 新增測試（`answer-state.spec.ts`、`stream-disconnect-reconnect.spec.ts`、`file-processing-status.spec.ts`、`knowledge-documents.spec.ts` 等）——具體看 `answer-state.spec.ts`：`[模擬:NO_EVIDENCE]` 觸發字串送出後，UI 從未顯示「查無依據」badge，等同 `playwright.config.ts` 設的 `NEXT_PUBLIC_FEATURE_MOCK_TRIGGERS=true` 完全沒有生效，flag 在瀏覽器裡一直讀到 `false`。

**根因**：`isFeatureEnabled()` 原本用範本字面值動態組出 env 變數名稱：
```ts
const envValue = process.env[`NEXT_PUBLIC_FEATURE_${flag.toUpperCase()}`];
```
Next.js 只會把**靜態**的 `process.env.NEXT_PUBLIC_X` member expression 內嵌進瀏覽器 bundle（webpack `DefinePlugin` 在編譯期做字面替換）；`process.env[運算式]` 這種動態存取無法被靜態分析，瀏覽器端的 `process.env` 實際上是空物件（或至少不含這個動態 key），所以無論伺服器啟動時實際設了什麼，瀏覽器端永遠讀到 `undefined`，永遠 fallback 到 `FLAGS[flag].defaultEnabled`。

這是一個**開發前就已存在**的 bug（`isFeatureEnabled` 是 E01-S015 建立的既有機制，本 story 只是延用），過去從未被抓到的原因：`sso`／`voice_input` 兩個既有 flag 預設值都是 `true`，且沒有任何既有 E2E spec 測試過「用 env 把它們關掉」這條路徑在真實瀏覽器裡是否生效——bug 一直藏在「預設值剛好正確」的假象後面。`mock_triggers` 預設 `false`，且本 story 的 E2E 需要用 env 把它**打開**才能通過，第一次真正踩到這條需要 override 生效的路徑，才第一次暴露這個 bug。

**修法**：改成每個 flag 各自一個靜態 member expression（`switch` 陳述式逐一列舉，見上方「變更檔案」的程式碼），讓每一個 `process.env.NEXT_PUBLIC_FEATURE_X` 都是編譯期可靜態分析的字面存取。`isFeatureEnabled(flag)` 的簽章、對外行為、預設值查表邏輯完全未變，只換了 env 讀取的實作方式。

**驗證**：修正後單元測試（`feature-flags.test.ts` 10/10、apps/web 全量 123 個檔案 1735/1735）全綠；E2E 重新跑一輪後，`answer-state.spec.ts`（含 NO_EVIDENCE/PERMISSION_DENIED 兩個觸發測試）、`stream-disconnect-reconnect.spec.ts` 全部通過——直接確認 flag 現在真的能在瀏覽器裡讀到 `true`。

**未曾用的權宜解法**：沒有考慮過放寬測試斷言或跳過這些測試——這是一個真實的產品 bug（`sso`/`voice_input` 兩個既有 flag 的 env override 在瀏覽器裡同樣從未生效過，只是預設值恰好掩蓋了症狀），修正它是唯一正確的路徑；也沒有用「改用 server-only 判斷」之類會改變既有元件（禁止修改清單內）的方式繞過。

## Security / Authorization Acceptance 對照
production 使用者無法觸發假的 `PERMISSION_DENIED`/`SOURCE_UNAVAILABLE` 等狀態（fail closed）——`classifyAnswerState` 在 flag 關閉時**無條件**回 `ANSWERED`，不會先解析觸發字串再決定要不要套用（即先短路判斷，觸發字串的比對邏輯根本不會執行到），所以就算使用者在正式環境輸入 `[模擬:PERMISSION_DENIED]`，程式碼路徑上不會有任何地方讀到這個字串並影響 state 判定，是真正的 fail closed，不是「判斷完再忽略結果」。四個閘門函式（`classifyAnswerState`/`shouldSimulateStreamDisconnect`/`classifyFileProcessing`/`addKnowledgeBaseDocument` 內嵌條件）皆採同一模式。

## Assumptions / 計畫外事項
- **spec 文字與實際程式碼的兩處落差**（觸發數「6」vs 實際「5」、函式名 `shouldSimulateFileProcessingFailure` vs 實際 `classifyFileProcessing`）——已在「與 spec 文字的落差核對」誠實記錄，依實際程式碼與 spec 自己「依既有函式名」的指示執行，未發明不存在的函式或觸發。
- **`isFeatureEnabled()` 動態讀取 env 的特性**——依 ai-km-e4 對 E03-S046 的提醒特別確認：這次的閘門函式（`classifyAnswerState` 等）每次呼叫都重新讀 `process.env`，不像 `CONVERSATIONS_PAGE_SIZE` 是 module load 時計算一次的常數，理論上 `vitest.setup.ts` 的設定時序要求沒那麼嚴格，但仍以同樣位置/同樣模式設定以維持一致性與可讀性。
- **`knowledge-documents.ts` 的觸發不是獨立函式**：與其他三個（各自有獨立具名函式）不同，`MOCK_DOCUMENT_PROCESSING_FAILURE_TRIGGER` 的比對是內嵌在 `addKnowledgeBaseDocument()` 函式體中間的一個條件式，本 story 只在該條件式前加閘門判斷，未抽出成獨立函式（抽出會是額外重構，超出本 story「僅閘門」的允許範圍）。
- **`service-error`（server-side）未修改任何程式碼**：`services/*` 不在允許修改清單，本 story 只確認 E2E 環境已開啟（E03-S038 早已設定 `AI_KM_DEV_TRIGGERS: "true"`）並在 runbook 列出，符合 spec 原文「本 story 只確認 E2E env 開啟並在文件對照表列出」。
