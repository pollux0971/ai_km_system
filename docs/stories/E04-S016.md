## 概述

`SOURCE_BASELINE.md` §17:E04-S16 = MVP Basic / GA Dedicated reranker。
使用者裁示(2026-09-02):**MMR(Maximal Marginal Relevance)作為 Basic tier
的預設實作,可調整** — 這是一個提案,不是定案,程式與文件都必須明講這點。
使用既有的 similarity score + 向量,不呼叫任何新模型 / embedding / cross-
encoder。

λ(relevance/diversity trade-off)是產品決策,不是本 story 可以自行決定的
(登記為 `(d5)`),因此以具名、有文件、可注入的常數
`DEFAULT_MMR_LAMBDA = 0.5` 提供一個「有理由但暫定」的起始值,等待使用者裁示。

## 掛載位置與理由

**Reranking 是獨立、由呼叫端明確組合的步驟(`retrieveWithReranking`),
NOT 直接烤進 `retrieve()`。**

理由:
1. `service.test.ts` 的 AC-R1 已經把 `retrieve()` 的既有行為(依 store 自己
   的 score 由大到小排序)當作凍結的斷言直接測試(`scores` 必須嚴格遞減)。
   MMR 重排的本質就是不保證嚴格 score 遞減 — 這正是多樣性的意義所在。若把
   MMR 無條件烤進 `retrieve()`,AC-R1 會靜默變成錯的,而 STORY_WORKFLOW
   Phase 2/4 明文禁止「改既有測試斷言去配合新實作」。因此 `retrieve()`
   本身完全不動。
2. `SOURCE_BASELINE.md` §10 Principle 2 把 Reranking 畫成 Retrieval 與
   Context Builder 之間「自己的一個 pipeline stage」,不是 Retrieval 內部的
   隱藏選項。獨立、可組合的函式更貼近這個形狀。
3. MMR 的 relevance 項就是 `RetrievalHit.score`(store 已經算好的
   sim(query, d)),完全不需要重新拿 query 向量 —— 只有 redundancy 項
   (`sim(d, s)`,已選結果之間的相似度)需要候選項自己的向量。這代表
   `rerankMmr` 可以是一個「只吃 `RetrievalHit[]`」的純函式,不需要
   `retrieve()` 額外把 query embedding 洩漏出來,也不會需要呼叫 embedding
   provider 第二次。

## Candidate pool 的處理

`retrieve()` 本來就只回傳 `topK` 筆(store 自己截斷過)。如果重排時只跟
`retrieve()` 要 `topK` 筆,MMR 沒有東西可以多樣化 — 每次都會把整批全選走,
在所有情境下都是 no-op。

`retrieveWithReranking()` 因此先呼叫 `candidatePoolSize(topK)` 算出一個
**嚴格大於 `topK`** 的 pool size(預設 `topK * DEFAULT_CANDIDATE_POOL_
MULTIPLIER(3)`,並設 `MIN_CANDIDATE_POOL_OVERFETCH(4)` 下限,避免 `topK`
很小時 pool 意外算出等於 `topK`),用這個 pool size 呼叫
`service.retrieve()`,再把回來的候選集丟給 `rerankMmr()` 砍到 `topK`。

`retrieve-with-reranking.test.ts` 的
"asks the store for MORE candidates than the final topK" 直接斷言
`requestedTopKs[0] > topK` 且等於 `candidatePoolSize(topK)`,防止未來改動
悄悄把 pool size 退化回 `topK`。

**Pool 小於 `topK` 時**:`rerankMmr` 不補齊、不丟錯,回傳實際拿到的全部
(重排過,但數量就是 `min(topK, 實際可用數)`)——見
"a candidate pool SMALLER than topK" 測試。

## 授權邊界(未動)

`dept:maintenance`。

composition root 把 sqlite-vec store 接到 `retrieve()`(`plugin.ts` 預設用
in-memory store)。留給後續 story;此處選擇「大聲失敗」而非「靜默不重排」,
與 codebase 既有的 fail-loud 慣例一致。
