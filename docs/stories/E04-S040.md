## 測試修正記錄

依 TDD 先寫 51 個測試(api 22 + service 29),確認為紅才實作。**沒有刪除任何
測試,沒有放寬任何斷言。** 兩筆屬 STORY_WORKFLOW Phase 4 第 5 點的
「測試本身的技術性錯誤」窄例外,逐筆記錄:

1. **`migrate.test.ts`「migration 不含 seed/secret」** ——
   原斷言 `expect(sql).not.toMatch(/password|secret|token/i)` 直接比對整份
   檔案,結果被我自己寫在**註解**裡的
   `-- Schema only: no seed rows, no secrets.` 命中。
   **判斷「是測試錯而非實作錯」的理由**:該斷言的意圖是「migration 不寫入
   任何 secret **值**」;migration 裡 `INSERT` 數為 **0**(已另行驗證),
   唯一命中的是散文註解。比對散文等於檢查了錯的東西。
   **修正**:先剝除 SQL 註解再斷言,意圖完全保留(仍會抓到任何真正的
   secret 字面值),涵蓋範圍沒有縮小。
2. **`migrate.test.ts`「server close 時關閉 DB」** ——
   原斷言 `toThrow(/closed/i)`,實際 better-sqlite3 的訊息是
   `The database connection is not open`。
   **判斷理由**:行為本身**完全正確**(連線確實已關閉),錯的是我猜的錯誤
   字串。改為 `/not open/i` 並加註來源。這沒有放寬任何行為要求。

兩者都**不是**「實作不符合 AC,把測試改鬆」——第 1 點的實作(零 INSERT)
本來就符合;第 2 點的實作(關閉連線)本來就正確。

## AC 對照

### Functional

| AC | 實作 | 測試 |
|---|---|---|
| 1. 建立全部表與 index、`schema_migrations` 一筆、WAL 與 FK 已啟用(PRAGMA 斷言) | `db/index.ts`、`migrate.ts`、migration SQL | `openDatabase` 4 個(WAL / foreign_keys / busy_timeout / 自動建父目錄)+「applies the real repo migrations」+「records each applied file exactly once」 |
| 2. 重複執行冪等、零變更 | `runMigrations` 以 `schema_migrations` 過濾 | 「is idempotent — a second run applies nothing」 |
| 3. 已套用檔被改 → 拒絕並指出檔名,不套用任何後續檔 | 先做**全量驗證 pass**,才跑任何 pending 檔 | 3 個測試:REGRESSION(永久回歸測試)、「不套用任何後續檔」、「已套用檔被刪除也拒絕」 |
| 4. 刪除 conversation → messages 因 cascade 消失 | migration 的 `ON DELETE CASCADE` + 連線層 `foreign_keys=ON` | 「cascades message deletion」+「rejects a message pointing at a conversation that does not exist」 |
| 5. 同 owner 連續 100 次 → seq 1..100;不同 owner 各自從 1 | `appendChangeEvent` 的 `MAX(seq)+1` + `UNIQUE(owner_key, seq)` | 「numbers a single owner's events 1..100 with no gaps」、「gives each owner its own sequence starting at 1」 |
| 6. `listChangeEventsAfter(owner, 50, 20)` → seq 51..70 | `WHERE owner_key = ? AND seq > ? ORDER BY seq LIMIT ?` | 「returns seq 51..70」+ 升冪、已最新、跨 owner 隔離、limit 上限共 6 個 |
| 7. 沒有 ownerKey 就查不了(型別層 + runtime 斷言) | branded `OwnerKey` + `prepareOwnerScoped()` | `owner-scope.test.ts` 16 個 |

AC7 的兩道防線刻意都做,因為它們擋的是**不同**的失誤:
branded 型別擋「忘了把 owner 一路傳下去」(變成編譯錯誤,而不是一句回傳
所有人資料的查詢);SQL runtime 檢查擋「查詢忘了寫 `owner_key` 條件」
(連 prepare 都不給過)。只有型別會被 cast 繞過,只有 SQL 檢查會被傳錯
owner 繞過。測試涵蓋 select / update / delete / insert 四種語句,並確認
`owner_key` **只出現在字串字面值或註解裡不算數**。

### Security / Authorization

| AC | 驗證 |
|---|---|
| 所有 domain 查詢以 `owner_key` 為必要條件 | `prepareOwnerScoped` 拒絕未帶條件的語句(7 個 negative 測試);repository 內**所有**查詢都走它——`grep "db.prepare("` 於 repository 只在 `owner-scope.ts` 內部出現 2 次(就是那個 helper 本身) |
| DB 路徑不從 request 取得 | `dbPath` 只來自 `config.dbPath`(env)或 `buildServer` 選項(僅測試);無任何 request 參與 |
| migration 不含 seed／secret | 測試斷言:零 `INSERT`、剝註解後無 `password|secret|token` |

資料層額外的 fail-closed(規格未明列但 Database Boundary 要求):
每張 domain 表的 `owner_key` 皆 `NOT NULL`——無主資料列不會被任何
owner-scoped 查詢匹配到,等於對它的擁有者隱形、卻可能被別人的 bug 讀到。
`messages.owner_key` 刻意從 parent 反正規化,讓每個 message 查詢能各自
owner-scoped,而不必依賴一個「忘了寫就悄悄放寬範圍」的 join。

### Data / Contract

- 欄位 snake_case;時間為 ISO-8601 UTC 字串(排序即字典序,SQL 內不做時區換算)。
- JSON 欄位皆有 `json_valid()` CHECK(有測試:寫入 `not-json` 被拒)。
- 額外(超出規格但符合 Database Boundary):所有表為 `STRICT`,列舉欄位有
  `CHECK ... IN (...)` 完全對齊 E04-S038 契約的枚舉值(有測試:`mode`
  寫入 `telepathic`、`role` 寫入 `system` 皆被拒)。

### UX

N/A。migration 拒絕訊息為繁體中文且指出檔名——有專門測試斷言訊息同時含
檔名與中日韓字元。

## Assumptions / 計畫外事項

1. **`pnpm-workspace.yaml` 增列 `allowBuilds: better-sqlite3: true`** ——
   不加則 pnpm 封鎖其 install script,原生模組無法載入,本 story 直接
   BLOCKED。規格的「允許修改」清單未列此檔,但
   `docs/architecture/voice-persistence-sync-m3.md` §5 的檔案交集矩陣
   **明確預期**「根 `.gitignore`／`pnpm-workspace.yaml`:E04-S037、E12-S030、
   E04-S040 各加不同行」。註解說明其 install script 是 `prebuild-install`
   (下載本平台預編譯 binary),與既有 `esbuild` 條目同型。
   實測:成功載入,SQLite 3.49.2,無需 node-gyp 編譯。
2. **`apps/api/src/server.ts` 加 2 行註冊** —— 規格的技術決策要求
   `fastify.decorate("db", db)`,必須有註冊點。同一份架構文件 §5 明列
   「`apps/api/src/server.ts` 註冊行:E02-S032／E04-S040／E12-S031 各一行」。
   實際是 2 行(db plugin + conversation domain plugin),兩者都是本 story
   Scope In 的產物。另加 2 個**測試用**選項(`dbPath`、`migrationsDir`),
   讓每次測試用自己的暫存 SQLite 檔。
3. **`apps/api/src/config.ts` 加 `AI_KM_AUTO_MIGRATE`** —— 規格技術決策明列
   此變數且「預設 true」。E04-S039 已立下「所有 env 由 config.ts 一次讀取並
   驗證」的慣例,另開一條讀 env 的路徑會破壞它,所以加在 config.ts。
4. **`pnpm-lock.yaml`** —— 新增套件的必然產物。
5. **`change_events.conversation_id` 刻意不設 FK** —— `conversation.deleted`
   事件必須比它指涉的資料列**活得久**,否則重新連線的 client 永遠不會知道
   那筆對話被刪了。已在 migration 註解與 `db/schemas/README.md` 說明。
6. **`MAX_CHANGE_EVENT_PAGE = 1000`** —— 規格未給 replay 的分頁上限。
   Security Boundary 要求對外輸入做 range validation,不能讓 client 一次把
   整份 log 拉走。1000 遠高於任何真實斷線落差、遠低於「整張表」。
   E04-S044 可依實測調整(放寬為 non-breaking)。
7. **`seq` 以 `MAX(seq)+1` 取得** —— 規格明訂此作法,並說明「單 process、
   WAL 下 write 序列化,安全」。我另外加了
   `UNIQUE (owner_key, seq)` index,讓這個假設一旦不成立(未來多 process)
   會變成**大聲的 constraint error**,而不是兩個 client 悄悄共用同一個
   event id。
