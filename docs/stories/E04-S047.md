`asr: down` here is the genuinely-expected state — this dev machine has no

than either lying "ok" or refusing to answer at all. This matches ai-km-e4's
explicit expectation that the endpoint will likely read `degraded` for a
while after merge and that must not be mistaken for the API itself being
down.

## 測試修正記錄(若有)
`server.test.ts`'s pre-existing `GET /v1/health (AC1) > returns 200 with
status, version and uptimeMs` test asserted `body.status === "ok"`. Its
`build()` call never overrode `AI_KM_ASR_PROVIDER`, so it ran against the
config default (`whisper-server`, pointing at an unreachable
`127.0.0.1:8178` in this environment) — before this story, `/v1/health`
never actually checked anything, so that default was harmless; after this
story's AC1/AC3, `checkAsr` genuinely reports `down` for that default,
which flips the aggregate to `degraded`.

**裁示**(ai-km-e4,2026-08-28,已依此執行,零斷言修改):
> 改測試的「設定」,不要改測試的「斷言」。

具體做法:在該測試唯一的 `build()` 呼叫加上 `AI_KM_ASR_PROVIDER: "fake"`
覆寫,讓這個測試的環境變回「所有子系統健康」的原始意圖,`expect(body.status)
.toBe("ok")` 這行**完全沒有改動**。理由(裁示原文的三點,逐一核對):
1. 該斷言表達的意圖(「所有子系統健康時 `/v1/health` 回 ok」)沒有因本
   story 而失效,失效的只是「測試環境預設會連到一個真實 whisper-server」
   這個隱含前提——修前提,不修結論。
2. 順便避掉「這個 build() 每次都要對一個不可達位址做網路請求」的不必要
   成本(雖然實測 ECONNREFUSED 只需要 ~24ms,遠低於原本擔心的 2 秒逾時,
   但仍是不必要的網路 I/O)。
3. 若改成斷言 `degraded`,這條測試就不再驗證任何有意義的東西——
   `degraded` 在那個設定下純粹是「環境缺 sidecar」,不是要驗證的產品行為。

**另外新增的兩條測試鎖住 AC 的另一個方向**,確保「健康→ok」與「ASR 掛→
degraded」都有真測試,而不是只改了前者的設定就結束:
- `AC1/AC3: reports status degraded when a subsystem (asr, unreachable
  whisper-server default) is down` — 不覆寫 ASR 設定,直接用預設的
  「不可達 whisper-server」狀態,驗證 `status` 真的變成 `degraded`。
- `AC1's own literal example: status degraded when the database connection
  is closed` — spec AC1 原文明確舉的例子(「DB 關閉時 status: degraded」),
  用 `server.db.close()` 製造真實的 DB down 狀態後驗證。
- `stays 2xx even when degraded` — 鎖住 ai-km-e4 特別強調的相容性要求
  (全 fleet 的 E2E 前置檢查用 `curl -sf`,任何非 2xx 都會讓 7 條 lane
  誤判 API 掛了),同時斷言這次真的是 `degraded`(non-vacuity guard)。

Diff 摘要(僅這一處設定變更,無斷言變更):
```diff
   it("returns 200 with status, version and uptimeMs", async () => {
-    const res = await (await build()).inject({ method: "GET", url: "/v1/health" });
+    const res = await (await build({ AI_KM_ASR_PROVIDER: "fake" })).inject({
+      method: "GET",
+      url: "/v1/health",
+    });
     expect(res.statusCode).toBe(200);
     const body = res.json();
     expect(body.status).toBe("ok");
```

## Assumptions / 計畫外事項
1. **`checkAsr` 的 `unknown` 分支在今天的程式碼裡技術上不可達**:
   spec 技術決策寫「未設定 → unknown」,而 SOFT 依賴段落把它解釋為
   「E12-S031(asr provider)未合併時 asr 為 unknown」的相容性備案。
   E12-S031 在本 story 開工前已 approved 並合併(`modelGatewayPlugin`
   已在 `server.ts` 註冊,`config.asrProvider` 的型別是封閉的
   `"whisper-server" | "fake"` 二選一聯集,沒有第三種「未設定」值),
   所以這個 SOFT 依賴今天已經被滿足,「未設定」情境不會在正常流程中
   發生。`checkAsr` 仍保留這個分支(對非 `"fake"`/`"whisper-server"`
   的任何值回傳 `unknown`)作為防禦性/窮舉完整性寫法,對應 AC3 的字面
   要求,而非猜測性發明——見 `checks.ts` 該分支的註解說明。
2. **`GET /v1/admin/health` 未對回應綁定 `schema: { response: ...
   contracts.getSchema(...) }`**:與既有 `/v1/health` 的風格一致(該
   route 本身也未走 contract schema 綁定),Contract Acceptance 用手動
   核對回應形狀而非 Ajv 自動驗證滿足(見上方 curl 輸出與型別定義逐欄位
   比對)。若之後要加自動化 contract 驗證,屬於後續強化,不影響本 story
   的 AC 通過。
3. **`checkDatabase` 把 `journal_mode = "memory"` 也視為 `ok`**:
   SQLite 無法對 `:memory:` 資料庫啟用 WAL(`db.pragma("journal_mode =
   WAL")` 對 `:memory:` 會被靜默忽略,實測回傳 `"memory"`),而本專案
   幾乎每個測試檔都用 `:memory:`。若只接受 `"wal"`,`checkDatabase` 在
   整個測試套件裡永遠是假警報。這不是放寬 AC——真實部署(`config.dbPath`
   預設 `./data/ai-km.sqlite`,一個真實檔案)永遠回報 `"wal"`,`"memory"`
   只在故意選擇 `:memory:` 的情境(測試)才出現,兩者都是「這個連線正在
   按設計運作」,不是異常。
4. **原先擔心的「2 秒 × 15 個測試」效能問題,實測不成立**:對一個
   `ECONNREFUSED` 的位址,`fetch()` 在約 24ms 內就會 reject(不會等滿
   `AbortSignal.timeout`),已用一次性腳本實測驗證(見對話記錄,未留
   痕跡於 diff)。真正會吃滿逾時的只有「連線但不回應」的情境,本 story
   的測試用真實 HTTP server 搭配縮短的 `timeoutMs: 200`(而非 production
   的 2000)專門驗證這個情境,避免拖慢整個測試套件。
