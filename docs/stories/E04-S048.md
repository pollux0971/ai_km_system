### 字面照做 spec 掛法的實測紅燈(偏離理由的證據,非推論)
在 `services/conversation/src/routes/conversations.ts` 的
`registerConversationRoutes(app)` 開頭暫時加入一個 `app.addHook("onRequest", ...)`
模擬「照 spec 字面把 CSRF preHandler 直接掛進 route 檔」,實測後**完整
`git checkout --` 還原**,未留任何痕跡於最終 diff:

```
$ pnpm exec vitest run src/routes/conversations.test.ts
 Test Files  1 failed (1)
      Tests  28 failed | 6 passed (34)

$ pnpm exec vitest run   # 整個 services/conversation
 Test Files  2 failed | 8 passed (10)
      Tests  53 failed | 94 passed (147)
```

53/147 個既有測試見紅,全部原因相同:測試從不帶 `x-requested-with`。這就是
「字面掛法與 AC2『既有 route 測試零修改』直接衝突」的實測證據,詳細機制
說明見 `docs/stories/PENDING_DECISIONS.md` 對應條目與 `require-session.ts`
的檔頭註解。

## 測試修正記錄(若有)
本 story 對 `services/identity` 既有(E02-S032/S033/S034 遺留)的 POST 測試
做了大量**新增 header,不改動任何既有斷言**的修改:37 處 `app.inject({method:
"POST", ...})` 呼叫補上 `headers: {"x-requested-with": "XMLHttpRequest"}`
(其中 1 處在 `loginAs` 輔助函式裡用 `instance.inject`,自動化腳本沒抓到,
手動補上)。判斷理由(符合先前 ai-km-e4 確認過的三個條件):
1. 行為變更是本 story AC 明文要求的(所有 state-changing 請求必須帶這個
   header),不是為了讓實作過關而動手腳。
2. 這些檔案(`services/identity/**`)在本 story 允許清單內(「四個 plugin」
   之一)。
3. 只加了 header 這一個欄位,原本每條測試驗證的行為(狀態碼、body 內容、
   session 語意)完全沒變動;用 Python 腳本批次處理後,逐一以
   `pnpm typecheck` + `pnpm test` 確認全部仍通過,而非盲改。

另外,`csrf-route-scan.test.ts` 自己開發過程中發現並修正一個**測試輔助設施
本身**(非既有測試)的技術性問題:`buildRealServer()` 一開始沒有指定
`dbPath`,沿用 `config.dbPath` 預設值(真實磁碟檔案 `./data/ai-km.sqlite`,
非 `:memory:`),導致多次測試執行之間共用同一份 SQLite 檔案,殘留的
session/login_attempts 造成診斷時的假象(見上方 debug 過程)。已改為每次
測試用 `os.tmpdir()` 下的隨機檔名,問題不再重現。

   `services/identity` 的 `requireSession`):完整理由、實測紅燈證據見

   還只有 README,尚未有任何程式碼與路由。掃描測試因此發現 8 條實際
   state-changing route,而非 spec 假設的更多。
3. **意外發現的獨立 bug(E04-S051)**:`conversationPlugin` 綁死 E04-S039
   舊 stub,導致 conversations/messages 在正式環境完全無法使用、在
   dev/test 環境可被 `x-test-user` 任意繞過。已完整回報 ai-km-e4,經其
   獨立覆核確認、立案 E04-S051 指派 W3 最優先處理。不在本 story 允許清單
   內,未動手修。**已於 2026-08-28 merge(b3ebbb6),本 story 隨即補完
   AC5 對這些路由的正面驗證,見上方「阻塞解除記錄」。**
7. **rebase 後追加的兩個小修正**(見上方「阻塞解除記錄」第 3、4 點):
   `payloadFor()` 補齊 4 條 feedback route 的 schema-valid payload(依
   `contracts/openapi/conversations.yaml` 既有 schema,無發明欄位);
   `packages/api-client/src/generated/*.d.ts` 補跑生成器並提交(純
   JSDoc 文件性差異,無型別變更)。兩者都是修正 E04-S048 自己遺漏的
   小事項,不屬於 E04-S051 的範圍。
4. **`packages/api-client` 實際改的是 `client.ts` 而非 spec 寫的
   `index.ts`**:`index.ts` 只是 re-export,真正的 header 注入邏輯(既有
   `x-correlation-id`／`x-client-id` 也在這裡)在 `client.ts`。改對地方
   才能達到 spec 真正要的行為(每個請求自動帶 header),`index.ts` 本身

   origin」),加上永遠允許 loopback(127.0.0.1/localhost,不需額外設定

6. **`requireAnyRole` 尚無任何真實 consumer**:已核對全repo,目前沒有任何
