## Assumptions / 計畫外事項

1. **選擇候選 1(`apps/api/src/server.ts` composition root),理由**:
   - `services/identity`'s `SandboxSeeder` 型別是 `(ownerKey: string) => void
     | Promise<void>`(無 db 參數),而 `services/conversation` 自己的
     `SandboxSeeder` 介面是 `{name, seed(db, ownerKey)}`(有 db 參數)——這是
     E02-S032 與 E04-S041/S042 各自獨立設計、從未對齊過的兩個形狀。composition
     root 本來就同時持有兩個 domain 的模組參照與 `app.db`,是唯一能在**不
     修改任一 domain 對外介面**的前提下把兩者橋接起來的地方。
   - 候選 2(`services/conversation` 模組載入時自行呼叫)需要新增
     `services/conversation` → `services/identity` 的 workspace 依賴,違反
     CLAUDE.md 鐵律 3「前端與 BFF 不直連...」同源精神的延伸——更廣義地說,
     違反「跨 Domain 互動只能經由已宣告的介面」邊界原則,會讓兩個原本互不
     知道對方存在的 domain package 產生編譯期耦合。
2. **`registerSandboxSeeder` 是無法反註冊的模組層陣列,而 `buildServer()`
   在測試套件裡每個 process 會被呼叫數十次——已用「只註冊一次 + 讀取當下
   db」的模式化解,而非天真地每次 `buildServer()` 都呼叫一次
   `registerSandboxSeeder`**:若每次 `buildServer()` 都直接註冊一個新
   closure(各自綁定當時的 `app.db`),測試套件裡稍後的每一次 sandbox 登入
   都會把**所有**歷史 closure 跑一遍(`runSandboxSeeders` 對已註冊的每個
   seeder 逐一執行),其中大多數綁定的是早已被前面測試 `afterEach` 關閉的
   db 連線——在 `better-sqlite3` 上呼叫已關閉連線的 `db.prepare(...)` 會
   同步拋錯,等於讓同一個 test 檔案裡任何用到真實 sandbox 登入的測試,只要
   不是該檔案第一個執行的,就會炸掉。改為模組層 `sandboxDb`(在每次
   `buildServer()` 呼叫時被重新指到「這次」的 `app.db`)搭配
   `sandboxSeederRegistered` guard(整個 process 只真正呼叫
   `registerSandboxSeeder` 一次,那個唯一的 closure 在被呼叫的當下才去讀
   `sandboxDb` 目前的值)——在 vitest 預設每個測試檔案有獨立模組狀態、且
   同一檔案內測試依序執行(不用 `.concurrent`)、同一時間只有一個
   `buildServer()` 實例在跑的前提下,這個模式永遠讀到正確的、當下存活的
   db。production 下 `buildServer()` 整個process 生命週期只被呼叫一次,
   本來就不受此問題影響——這個修正純粹是為了讓 apps/api 自己的測試套件
   (以及本 story 新測試自己)在真實登入下正確可靠,不是規格明文要求,
   但若不處理,AC1/Security AC 的測試會因為模組狀態污染而變 flaky 或直接
   炸掉,故記錄於此作為誠實的計畫外技術決策。
3. **`Security AC` 的「seeder 只能寫入自己 ownerKey」大部分驗證繼承自
   E04-S041/S042 既有測試**(`seed/sample-conversations.test.ts`、
   `seed/sample-messages.test.ts` 的 UUID v5 idempotency/per-owner 衍生測試,
   本 story 未修改、零回歸重跑仍綠),本 story 新增的測試只額外證明「兩次
   真實、獨立的 sandbox 登入」這個更貼近生產情境的路徑同樣成立,避免只在
   repository 單元層級驗證而遺漏 wiring 層本身可能引入的洩漏。
