## 根因(總指揮已獨立重現,本 story 重新確認)
```
services/identity/src/require-session.ts:39
  export const SESSION_IDLE_LIMIT_MS = 12 * 60 * 60 * 1000;   // 12 小時(product 行為,未動)

services/identity/src/require-session.test.ts:16(修正前)
  const NOW = "2026-08-28T05:00:00.000Z";                      // 寫死
```
`seedSession()` 用 `NOW` 當 `last_seen_at` 寫進 DB,`buildRealRequireSession`
用**真實 wall-clock**(`Date.now()`)計算 `idleMs`。測試檔案本身**沒有使用
假時鐘**(`grep useFakeTimers` 修正前零命中)。當真實時間距離 `NOW` 超過
12 小時,所有以 `NOW` 種下的 session 一律被判閒置過期 → 401。

## 同類缺陷掃描(spec 明文要求)

**方法**:時間炸彈需要兩個條件同時成立:(a) 測試寫死時間戳字面值,
(b) production 程式碼**拿它跟真實 `Date.now()` 比對某個時間窗**。單純
把日期當資料存(`createdAt` 之類)不會爆——只有窗口比較才會。

**(b) 的完整清單**(對整個 `services/**`、`apps/**` grep `Date.now()`,
排除純量測時長的用法如 `uptimeMs`/`processingMs`/`correlationId`):
```
services/identity/src/require-session.ts:155   session 閒置/絕對過期(本 story 的已知缺陷)
services/identity/src/plugin.ts:108,124,186     登入節流窗口(E02-S034)
apps/api/src/health/checks.ts:157               checkedAt 報告時間戳,非窗口比較,且 now() 本身可注入測試控制
```
**風險完全集中在 `services/identity`**。

**(a) 在 `services/identity` 裡有寫死日期字面值的檔案**:
- `require-session.test.ts`(1 處 `NOW`)→ **本 story 已修正**。
- `repository.test.ts`(`NOW` 出現 13 處,另有 `FIFTEEN_MIN_AGO` 等相對
  `NOW` 計算的常數)→ **獨立確認不受影響,理由如下**。

### 為什麼 `repository.test.ts` 不受影響(逐一核對,非臆測)

檢查它呼叫的所有時間窗函式簽章(`services/identity/src/repository.ts`):
```ts
deleteExpiredSessions(db: Database, nowIso: string, idleCutoffIso: string)
countRecentFailuresByUsername(db, username, windowStartIso: string)
countRecentFailuresByIp(db: Database, ip: string, windowStartIso: string)
deleteOldLoginAttempts(db: Database, cutoffIso: string)
```
**全部接受明確的 `nowIso`／`windowStartIso`／`cutoffIso` 字串參數,函式
內部從不呼叫 `Date.now()`。** `repository.test.ts` 對這些函式的每一次
呼叫都是自己算好一個相對 `NOW` 的字串(例如 `FIFTEEN_MIN_AGO =
"2026-08-28T04:45:00.000Z"`、`cutoff = "2026-08-27T05:00:00.000Z"`)直接
傳進去——**整條比較鏈完全在測試自己控制的字面值之間進行,從頭到尾沒有
碰到真實 wall-clock**。這與 `require-session.test.ts` 的缺陷本質不同:
後者是「用寫死時間戳寫資料,但拿去跟 production code 內部呼叫的真實
`Date.now()` 比較」;前者是「寫死時間戳,但比較的另一邊也是同一批寫死
時間戳算出來的,兩邊永遠自洽,不管現實世界是哪一天」。

**實測驗證**(不只是推論):`services/identity` 184/184(含
`repository.test.ts` 全部案例)在本 story 開工前就已經是綠的——8 個失敗
全部集中在 `require-session.test.ts`,`repository.test.ts` 沒有任何一條
失敗,與上述分析一致。

另外檢查 `plugin.test.ts`(測試真正呼叫 `Date.now()` 的登入節流 handler
本身,而非底層 repository 函式)——`grep "2026-08-2[0-9]T"
src/plugin.test.ts` 零命中,它的節流測試場景全部用相對真實 `Date.now()`
的方式建構,同樣不受影響。

**結論**:本 repo 目前只有 `require-session.test.ts` 一個檔案有真正的
時間炸彈,已修正;`repository.test.ts`、`plugin.test.ts` 皆確認不受影響,
未修改。
