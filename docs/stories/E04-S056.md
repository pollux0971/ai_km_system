## 規格前提更正(先於本 story 其餘內容發生,誠實記錄)

原始規格聲稱「自 `ca7ef86` 起每條 lane 的每一次全量 E2E 都固定紅
`api-sandbox.spec.ts:143`」。實作前先在未修正的樹上實跑
`pnpm exec playwright test api-sandbox --project=web`,結果 **4/4 全綠**：

```
✓  4 [web] › specs/api-sandbox.spec.ts:143:5 › apps/web's /api/v1/health rewrite reaches the real apps/api instance (527ms)
✓  3 [web] › specs/api-sandbox.spec.ts:121:5 › a fake microphone is available: ... (2.7s)
✓  1 [web] › specs/api-sandbox.spec.ts:95:5 › a second page in the same context ... (7.0s)
✓  2 [web] › specs/api-sandbox.spec.ts:66:5 › two browser contexts each logging in ... (7.1s)
4 passed (33.7s)
```

原因:`tests/e2e/playwright.config.ts`（修正前）第 163 行早在 E03-S038
(`304c83f`) 就已對 api webServer 設 `AI_KM_ASR_PROVIDER: "fake"`，且該
webServer `reuseExistingServer: false`、獨佔 :4100，所以 Playwright 管理的
路徑從一開始就是 fake ASR。真正會 `degraded` 的只有 §5-penta 手動啟動的
共用 :4000 實例（未設 `AI_KM_ASR_PROVIDER`），且它目前不會讓任何 lane 的
E2E 變紅（E2E 走 :4100，且舊 preflight 只看 HTTP 200，`degraded` 一樣回
200）。此發現已回報總指揮，總指揮確認並改寫規格（`c0f22e8`），story 範圍
因此從「修一個紅測試」變成「(1) 讓 :4000 preflight/啟動指令名副其實 (2)
把路由測試的耦合解掉 (3) 修一個規格重寫過程中意外發現、影響更大的真實
hazard：`reuseExistingServer` 會靜默丟棄整組 webServer env」。

## 反向驗證（AC1 + AC3 共用一組實測，未捏造紅燈）

在隔離的、未修正的樹上，起一個全新 apps/api 實例（無 whisper sidecar，
模擬 §5-penta 共用實例目前的真實設定）：

```
$ AI_KM_API_PORT=4200 AI_KM_DB_PATH=<tmp>.sqlite AI_KM_LOG_LEVEL=silent node_modules/.bin/tsx src/main.ts &
$ curl -s http://127.0.0.1:4200/v1/health
{"status":"degraded","version":"0.1.0","uptimeMs":571}
```

同一個實例，加上 `AI_KM_ASR_PROVIDER=fake`（AC1 建議的修法）：

```
$ AI_KM_API_PORT=4200 AI_KM_DB_PATH=<tmp>.sqlite AI_KM_ASR_PROVIDER=fake AI_KM_LOG_LEVEL=silent node_modules/.bin/tsx src/main.ts &
$ curl -s http://127.0.0.1:4200/v1/health
{"status":"ok","version":"0.1.0","uptimeMs":1088}
```

這證明了機制本身有效（AC3），同時也是 AC1「修正後對沒有 sidecar 的新啟動
API 直接 curl /v1/health」的證據。未對 `api-sandbox.spec.ts` 本身捏造一個
假紅燈 —— 它在 Playwright 管理的路徑上本來就是綠的（見上方前提更正）。

## AC5.2：交由 W6（ai-km-01）獨立執行 —— 已完成

總指揮指示：AC5.2 的價值在於執行者事先不知道答案（W6 自己在 E01-S025 的
12 個 `waitForURL` 逾時上，已經自己發現「重跑證據無法區分『系統性延遲』
與『重跑時 server 本來就是全新啟動』兩個假說」，是最適合執行這個實驗的人）。
已將 AC5.2 的機制（scratch config、env 需求、真實登入帳密）交接給 W6，
刻意未透露我自己 scratch 環境已經跑出的結果，避免污染他們的獨立判斷。

**W6 的設定**：scratch apps/api（:4200，throwaway sqlite，
`AI_KM_TEST_SANDBOX`/`AI_KM_DEV_TRIGGERS`/`AI_KM_SEED_DEMO_USERS=true`，
`AI_KM_ASR_PROVIDER=fake`），web 起在 :3200（而非規格字面寫的 :4000 ——
W6 判斷：不想動到其他 lane 依賴的共用長駐實例，而本實驗要驗的因果機制
「adopted server 缺 `NEXT_PUBLIC_*`」用 scratch port 一樣能忠實重現，
風險更低。此偏離已誠實記錄，判斷合理，予以採用）。

**RUN 1(實驗組 —— 只設 `API_INTERNAL_URL`，不設
`NEXT_PUBLIC_CONVERSATIONS_PAGE_SIZE`/`NEXT_PUBLIC_FEATURE_MOCK_TRIGGERS`)**：
7 個測試 6 個失敗。**RUN 2(對照組 —— 同一 scratch 環境，全新 api 實例，
三個變數都正確設定)**：7/7 全過（25s），證明 scratch 環境本身可靠，
且正是這兩個變數在起作用。

**結論：config drift 是真實、可重現的缺陷**——沒有 `PAGE_SIZE=2`，3 筆種子
對話全部擠在第 1 頁，「下一頁」按鈕根本不存在。**但失敗形狀跟 W6 原本
E01-S025 的 12 個失敗對不上**，這是本次實驗最重要的部分：
- RUN 1 的失敗：1 個 `toHaveCount(0)` 斷言失敗（第 1 頁顯示 3 筆而非 2 筆）
  + 5 個 `locator.click: Test timeout of 30000ms exceeded`（等
  「下一頁」按鈕，但按鈕根本不存在，連點擊目標都找不到）。
- W6 原本 E01-S025 的 12 個失敗是 `page.waitForURL: Test timeout of
  30000ms exceeded`——點擊本身成功、有正確 dispatch，只是點擊後的導覽
  沒在時限內完成。這在 W6 當時的 EVIDENCE 就已經明確區分過
  （waitForURL 逾時 ≠ click 逾時）。

兩種失敗簽章指向不同機制：config drift 讓按鈕不存在；W6 原本的失敗是
「按鈕存在、點了、只有導覽逾時」。**依此證據，config drift 不像是
W6 原本 12 個失敗的成因**——它確實重現了一個真實、獨立的缺陷（AC5.1
本來就要修，不受此結論影響），但很可能不是那次事故的解釋。負載/併發
仍是原本失敗更一致的解釋，雖然 W6 尚未跑正向實驗證實負載這一側。

**判定**：AC5.2 到此為止，不再追加正向實驗（W6 有提議但我判斷 AC5.2
「兩種結果都要落檔，價值在於得到答案不在於哪個答案」的要求已經滿足，
追加正向重現屬於另一個問題「W6 原本的失敗到底是不是負載」，超出本
story 的範圍，不在此追加)。原始輸出存於 W6 的 scratchpad，已由 W6
清理 scratch ports/DB。
