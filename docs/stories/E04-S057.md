## 問題陳述(已由總指揮查證,見 spec)

`turbo.json:18` 的 `test` pipeline 會把 `@ai-km/e2e:test`(即
`tests/e2e/package.json:9` 的完整 `playwright test`)一起跑進去,完全不知道
`.e2e.lock` 存在。`tests/e2e/helpers/port-check.ts:18` 的
`resolveReuseExistingServer()` 本機恆為 `!process.env.CI` = `true`,於是
無鎖的 Playwright 會直接沿用持鎖者已經起好的 dev server。

**已造成的實際損害**(2026-08-29,W4 自己踩到並主動揭露):W1 持
`.e2e.lock` 跑 E01-S022 的補救重跑時,W4 在不知情下於 repo 根目錄跑
`pnpm test`;W4 誠實揭露沒有保留該次 e2e task 的 webServer log、無法排除
真的接上了 W1 的 dev server;W1 該次重跑到 133/271 出現 6 個逾時後判定
資料污染並中止。**沒有人違規**——`pnpm test` 是最自然的全量驗證指令,
沒有任何東西警告它會碰 E2E。

## 開發過程中發現並修正的第二個真缺陷(誠實記錄)

實作完第一版(以 `.e2e.owner` 的存在與否 + 其記錄的 pid 存活與否決定
block/proceed)後,`ai-km-83` 在實際使用時踩到一個第一版沒有涵蓋的狀態:

**症狀**:`ai-km-83` 檢查 `.e2e.owner`,發現檔案不存在,判斷鎖是空的。
實際上鎖是真的被持有的——用 `fuser`/`lsof` 查證,5 個活躍 fd。

**根因**:`.e2e.owner` 是 wrapper **取得鎖之後才寫入**的檔案,所以「取得鎖」
與「寫入 owner 檔」之間有一個時間窗;任何在這個窗口內執行、或是完全沒有
走過 wrapper 寫檔步驟的路徑,都會產生「鎖真的被持有,但 owner 檔不存在」
這個狀態——這正是本 story 想防的那個「無鎖但實際有人在用」情境,只是換了
一個方向出現:第一版的 guard 會把「owner 檔不存在」誤判為「沒人持鎖」而
放行,**在這個特定狀態下完全失效**。

**修正**:把判斷 block/proceed 的權威從 `.e2e.owner`(courtesy 檔案)換成
`.e2e.lock` 本身——用非阻塞的 `flock -n <lockfile> -c true` 直接問「現在
能不能拿到鎖」,這個問題沒有時間窗、也不可能過期。`.e2e.owner` 降級為
**只用來在錯誤訊息裡標註是誰持有**,不再影響任何決策。

這個修正同時讓第一版另外做的「`.e2e.owner` 記錄的 pid 已死 → 視為 stale」
邏輯變成**對正確性而言不再必要**(但仍是對的方向,只是理由更深一層):
**一個已死的行程不可能還持有 flock**(行程死亡時 OS 會自動釋放它持有的
flock,因為底層的 file descriptor 被關閉了)——所以「崩潰留下的 stale
owner 檔」現在會在 `flock` 判斷這一步就自然解決(判斷為「未被持有」而
放行),根本不會走到讀取(可能過期的)owner 檔那一步。**這段 PID 存活檢查
邏輯已經整段移除**,而不是留著當作「看起來有用但其實不再是決定性因素」的
程式碼——刻意選擇移除而非保留,理由記錄如下。

**為什麼選擇移除而不是保留**(ai-km-e4 的提醒,記錄於此):保留一段不再是
正確性所需的邏輯,會讓未來的維護者誤以為它仍然是必要的,進而圍繞一個已經
不存在的限制去「修正」這個 guard。移除是比較困難但正確的選擇。

**驗證**(不是用推理帶過,是實際重現 `ai-km-83` 的情境):
1. 用一個獨立的暫時 lock 路徑(不是共用的 `.e2e.lock`),讓一個行程真的
   持有這個暫時鎖,然後在持有期間刻意刪掉 `.e2e.owner`,重現「鎖真的被
   持有,owner 檔不存在」這個確切狀態。
2. 從外部行程呼叫 `assertNotBlockingLockHolder()`——**修正前**的版本會
   放行(BUG,完全等同 `ai-km-83` 踩到的狀況);**修正後**的版本正確擋下。
3. 用真正的 `e2e-locked.sh` wrapper(同樣指向暫時路徑)重新驗證 AC3(在
   wrapper 內部執行的行程必須能跑)與「外部行程被擋下並指名持有者」兩種
   情境都正確——這次是用**真正的 wrapper 輸出格式**驗證,不是單元測試裡
   手寫的 fixture。

## Functional Acceptance Criteria 對照(含反向驗證)

### AC1 — `.e2e.owner` 指向別人時,`pnpm test` 在根目錄明確失敗並指名持鎖者

**修正前**(用 `--list` 模式安全示範,不啟動任何真實 server/port):

```
$ AI_KM_E2E_OWNER_FILE=<fake-owner-file with someone else's claim> \
  pnpm exec playwright test --list --project=web specs/app-shell.spec.ts
Listing tests:
  [web] › app-shell.spec.ts:32:5 › ...
  ...
Total: 5 tests in 1 file
```
(靜默通過,完全沒有察覺鎖被別人持有——這正是造成 W1 那次污染的行為。)

**修正後**(同樣的 fake owner file,同一個指令):

```
Error: [E04-S057] Refusing to start Playwright: the shared E2E lock is
currently held, most likely by fake-other-lane pid=... ..., and this
process is not them. ...
    at assertNotBlockingLockHolder (.../helpers/lock-guard.ts:...)
    at Object.<anonymous> (.../playwright.config.ts:...)
```

`pnpm test` 本身透過 turbo 呼叫到同一個 `playwright test`,同一個
`playwright.config.ts`,故涵蓋。

### AC2 — 直接跑 `playwright test` 與 `--last-failed` 同樣被擋

兩者都會先載入同一個 `playwright.config.ts`(Playwright 的既有行為,
`--last-failed` 只是額外過濾要跑的測試清單,不影響 config 的載入時機),
故上面 AC1 的驗證同時涵蓋兩者——並非只涵蓋 bare `playwright test` 一種
入口。

### AC3 — 持鎖者自己必須能跑(最容易做壞的一條,已實測不是推理)

見上方「驗證」段落第 3 點:用真正的 `e2e-locked.sh` 在暫時路徑上實際取一次
鎖,鎖內執行的行程呼叫 `assertNotBlockingLockHolder()`——**放行**
(`PROCEEDED AS EXPECTED`)。此設計刻意**不**讓這個判斷自己呼叫
`flock`——見 `lock-guard.ts`/README 的完整推理:一次全新的 `flock -n`
探測會開一個獨立的 file description,Linux 的 flock() 互斥是以
open-file-description 為單位、不是以行程為單位,所以連持鎖者自己的子行程
用全新探測都會誤判成「被別人佔用」。改用「比對 wrapper 寫入的一次性
token」在**任何 flock 探測之前**先判斷身分,徹底避開這個陷阱。

### AC4 — `.e2e.owner` 不存在時一切照舊可跑

單元測試「AC4: proceeds when the lock itself reports not contended,
regardless of the owner file」+「2026-08-29 ai-km-83 incident: proceeds
when nobody holds the lock even though .e2e.owner does not exist」兩個
案例直接驗證:決策權威是 `flock` 本身,不是 owner 檔案是否存在。

### AC5 — 強制反向驗證,修正前/修正後皆有真實輸出

見 AC1 段落的完整 before/after 輸出,以及「ai-km-83 情境驗證」的 3 步驟
——修正前的版本**確實會**放行(不是「應該會」),修正後**確實會**擋下。

### AC6 — `pnpm test` 仍涵蓋 E2E,沒有靠拿掉 E2E 了事

`tests/e2e/package.json` 的 `"test"` 腳本完全沒有改動,仍是
`"playwright test"`;turbo 的 `test` pipeline 依然把
`@ai-km/e2e:test` 包含在內。新增的 `"test:unit"` 是**額外**的腳本,只用來
跑 `helpers/*.test.ts`,不在 turbo 的 `test` pipeline 裡,不影響
`pnpm test` 的既有行為/涵蓋範圍。

   到共用 main。
2. **rollout 的協調缺口(留給總指揮/艦隊)**:這個 guard 上線後,任何
   *其他* lane 現有的、手寫的 ad-hoc `flock -c '...'` 腳本(不透過
   `e2e-locked.sh`、沒有設定 `AI_KM_E2E_LOCK_TOKEN`)在**自己持鎖跑的時候
   會被自己的新 guard 擋下**——因為他們的 wrapper 不知道要匯出這個新的
   token 環境變數。這不是本 story 範圍內能片面解決的問題(需要通知/更新
   每個 lane 各自的腳本),但必須明確標註,避免上線後造成艦隊級的意外
   卡關。建議:合併後由總指揮向所有 lane 廣播「請改用
   `/data/python/AI_KM-worktrees/e2e-locked.sh <label> -- <command>`
   取代自己手寫的 flock 包裝」。
