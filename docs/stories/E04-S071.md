## `analytics-compat.ts` 的延伸——超出原始允許清單,附機械證明與理由

**本 story 交付說明只把 `generation-compat.ts` 列入允許修改清單,沒有列
`analytics-compat.ts`。實測後發現這是不夠的**,理由如下,附機械證明:

`analytics-compat.ts` 原本的 `reasonAssignable` 是**單向**
`AssignableTo<AdminFeedbackItem["reason"], Schemas["FeedbackItem"]["reason"]>`。
這個方向在 `Schemas["FeedbackItem"]["reason"]` 是 `string`(收緊前)或收緊後的
四值 enum 時**都成立**(`FeedbackReason` 的四個字面值本來就是 `string` 的子集,
收緊後又剛好完全相同)——也就是說,**這個既有斷言不管契約收不收緊都不會變色**,
不能拿來當 AC2 反向驗證要求的守門。

**機械證明**(把 `contracts/openapi/__checks__/generated/analytics.d.ts` 的
`reason` 手動改回 `reason?: string;`,不動 `analytics-compat.ts` 半個字):

```
$ ./node_modules/.bin/tsc -p contracts/openapi/__checks__/tsconfig.json --noEmit
(no output — 0 errors)
```

`analytics-compat.ts` 保持全綠——完全沒有任何斷言會因為 `reason` 被鬆綁回
`string` 而變紅。這代表 AC2 明文要求的反向驗證(「把 `analytics.yaml` 的
`reason` 改回 `type: string` → `analytics-compat.ts` 必須紅」)在原始允許清單
下**機械上不可能通過**。

**處理方式**:比照 AC4 對 `generation-compat.ts` **同一類**的既有作法——把
`reasonAssignable`(單向 `AssignableTo`)換成 `reasonExact`(雙向 `Exact`),
並改寫其上方那段「CONTRACT LOOSE / IMPLEMENTATION STRICT」註解為過去式,連帶
修正兩處引用 `reasonAssignable`「divergence」字樣的下游註解(`feedbackItemSample`
與 `implFeedbackItemSample` 附近)。**這不是新邏輯,是把 AC4 已經授權的同一種
「單向 AssignableTo → 雙向 Exact + 改寫過時註解」處理方式套用到孿生檔案的孿生
欄位**,而不是引入新的檢查種類或新的行為。
