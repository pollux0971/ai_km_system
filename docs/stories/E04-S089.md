## 概述

ADR 0009 D3。在 `services/retrieval` 的檢索管線裡**新增** cross-encoder 重排
階段,插在 dense 召回與既有 `rerankMmr`(E04-S016/E04-S074,多樣性)之間:

```
dense 召回(大候選池) → cross-encoder 重排(相關性,新增) → MMR(多樣性,取 topK)
```

相關性。這個 story **不取代它**,只是在它前面補上一個真正讀 `(query,
passage)` 的相關性模型(`bge-reranker-v2-m3`,`models/rerank/README.md`,
E04-S087 量出的端點形狀)。

## `retrieve-with-reranking.ts` 的改動

`RetrieveWithRerankingOptions` 新增 **optional** `crossEncoder?:
CrossEncoderProvider`。管線變成:

```ts
const candidates = await service.retrieve(question, scope, poolSize);
const relevanceRanked = options.crossEncoder
  ? await applyCrossEncoder(options.crossEncoder, question, candidates)
  : candidates;
return rerankMmr(relevanceRanked, topK, options);
```

`applyCrossEncoder` 對每個候選項呼叫 `crossEncoder.score(question,
candidates.map(h => h.text))`,並用回傳的 `relevanceScore` **取代**
`RetrievalHit.score`(用 `{...hit, score: ...}` 產生新物件,其餘欄位——含
`embedding`——原樣保留,`rerankMmr` 的冗餘項因此不受影響),再交給
`rerankMmr`。

**為什麼是 optional 而不是必填**:這是 `STORY_WORKFLOW.md` 規則的直接
後果,不是設計偏好。`retrieve-with-reranking.test.ts` 既有的五條測試(凍結
內容,只能新增不能改)完全沒有 cross-encoder 的概念,用手寫的
`fakeService` + 手動指定的 `.score` 斷言精確的 MMR-only 順序
(`["a","c"]`)。若把 cross-encoder 設為必填或無條件啟用,這五條測試會在
沒有任何 HTTP mock 的情況下嘗試打一個不存在的伺服器,或者靜默改變其精確
斷言的順序——兩者都違反「不改既有測試內容配合新實作」。做法是讓它
optional、預設「跳過此階段,行為與 story 前完全一致」,真正的生產組合根
(目前 `retrieveWithReranking` 在 main 上還沒有除了測試以外的呼叫者——見
`index.ts` 的匯出,`grep -rln retrieveWithReranking` 只命中
`index.ts`/`retrieve-with-reranking.ts`/其測試檔)未來接上時應該總是傳入
一個真實 provider;省略它是給這五條「story 之前就存在」的測試的逃生口,
不是給新呼叫者的靜默預設。

`HttpCrossEncoderProvider` 因此仍然做主動、可測試的預算檢查,不依賴這個
安全邊際。

## 超長情況的處理(明確截斷,不靜默)

⚠️ **重要更正**:任務指示假設「`max_length=512` 會靜默截斷」。**這個假設
針對本次實際使用的 llama-server 建置經實測不成立**——用超過 512 token 的
真實請求打真正跑起來的 `llama-server --reranking`,伺服器回應
**HTTP 500**:

```json
{"error":{"code":500,"message":"input (650 tokens) is too large to process. increase the physical batch size (current batch size: 512)","type":"server_error"}}
```

這是大聲的錯誤,不是靜默截斷。但同時量到一個任務指示沒提到、比「靜默截斷」
更麻煩的真實風險:**`/rerank` 一次送一整批 documents,任何一筆超長都會讓
整批全部 500**——不是只有那一筆失敗,是候選池裡其他原本正常的段落也全部
拿不到重排分數。這才是本 story 需要主動處理的「靜默/連坐失效」風險:如果
放著不管,一個異常長的候選項會讓整個候選池的相關性重排全部掛掉,而
`retrieveWithReranking` 若沒有妥善處理,結果可能是整段 reranking 直接
拋錯,或(更糟)被上層不小心 catch 掉退回 dense 排序而不留痕跡。

**處理方式**:`HttpCrossEncoderProvider` 主動預先檢查每個 (query, passage)
組合的 token 數,超過預算就在送出 `/rerank` 之前**明確截斷該 passage**
(不是整批放棄),並透過 `onTruncated` callback 記錄
`{index, originalTokens, truncatedTokens}`,`CrossEncoderScore.truncated`
也會標記在回傳結果上。

**截斷公式(量出來的,不是讀 source 猜的)**:

```
tokenize(query,   add_special=true).length  =: Q
tokenize(passage, add_special=true).length  =: D
Q + D === /rerank 該筆組合實際使用的 token 數(usage.prompt_tokens)
```

對真實伺服器兩組不同 query/document 各驗證一次(`7+37=44`、`9+22=31`,
皆與伺服器 `usage.prompt_tokens` 逐位元組相符),因此 passage 的截斷預算是
`maxTokens - Q - 2`(`-2` 是 passage 自身 `add_special` 計入、但組合公式
的抵銷推導中實際沒有花在它身上的 bos/eos——已用真實伺服器驗證:用這個
預算截斷後,組合請求剛好落在 512、無錯誤;用差 1 的錯誤預算會重現 500、
回報 514)。截斷本身呼叫伺服器自己的 `/tokenize`/`/detokenize`(同一個
tokenizer,不是猜的字元比例),往返一致性也已驗證(截到 505 個內容
token,detokenize 後再 tokenize 回來仍是 505)。

`query` 自己超過預算(`contentBudget <= 0`)時直接拋 `CrossEncoderError`
拒絕整個呼叫,不送出保證失敗或保證錯誤截斷的請求。

## Assumptions / 計畫外事項 / 對 E04-S088 的交接

- **任務指示的「靜默截斷」假設經實測不成立**（見上「超長情況的處理」一節）
  ——這是量出來的更正，不是臆測；已在此誠實記錄理由與量測過程。
- **`retrieveWithReranking` 的 `crossEncoder` 目前仍是 optional**，因為
  main 上還沒有真正的生產呼叫者（見上）。等某個 composition root（可能是
  `plugin.ts` 或 `apps/api` 的路由）真正把這個函式接上線時，應該總是傳入
  一個真實 `HttpCrossEncoderProvider`；那條接線本身超出本 story 範圍
  （允許清單未涵蓋 `apps/**`），留給後續 story。
- **與 E04-S088 共用的東西**：沒有發現任何需要共用型別/設定的地方。
  `HttpCrossEncoderProvider` 完全自成一體，活在 `services/retrieval` 內，
  不 import `services/model-gateway` 的任何東西（`EmbeddingProvider` 那條
  依賴邊是既有的、E04-S088 不會動它）。兩個 story 的伺服器 URL/port
  也不同（embedding 用的 port 與本 story 用的 `8182` 不是同一個服務）。
  若未來有一個共用的「llama-server sidecar 設定」抽象（例如共用的
  SSRF-safe URL 驗證,參考 `services/model-gateway/src/config.ts` 的
  `isLoopbackOrPrivateHost`),那會是協調者層級的共用檔決定,本 story
  刻意不搶先發明。
- `models/rerank/README.md` 未修改——本 story 只讀取、驗證其中的量測結果,
  未發現需要更正或補充的地方。
