## 設計決策

1. **`listKnowledgeBases(query?: string)`——搜尋只比對 `name`,
   不比對 `description`**——與 `listConversations` 只比對 `title`
   不比對 `lastMessagePreview` 的既有理由完全一致:真實聊天/知識庫
   產品的側邊欄搜尋比對名稱,不比對完整內容,完整內容搜尋需要一套
   本 story(MVP 簡化)沒有要求的更重機制。空白/純空白查詢視為
   「無搜尋」,回傳完整未過濾列表,與既有每個呼叫端(S001 的
   `KnowledgeList`)行為不變一致。
2. **大小寫不敏感比對(`.toLocaleLowerCase()`),但無專屬 ASCII
   大小寫測試**——延續既有 `.toLocaleLowerCase()`(而非
   `.toLowerCase()`)的防禦性選擇,但本 story 的 3 筆範例資料
   (「產品保固政策」等)全為中文,漢字沒有大小寫可摺疊,不像
   `ConversationSummary` 範例資料裡「E-204」那樣天然存在 ASCII
   大小寫案例可測——沒有為了測試而虛構一個不存在的 ASCII 範例名稱。
3. **搜尋框無條件渲染在所有 `state.status` 分支之外**——與
   `conversation-list.tsx` 的既有結構完全一致:reload 時或載入/
   錯誤畫面時搜尋框仍保持可見,且保留使用者已輸入的文字,避免
   使用者以為自己打的字消失了。因此把 `KnowledgeList` 的原本
   S001 早期 return 結構(`if (loading) return ...`)改寫成單一
   wrapping `<div>` + `&&` 分支渲染的結構,與 `conversation-list.tsx`
   同期重構的形狀一致。
4. **空結果訊息依 `query.trim()` 區分「真的沒有知識庫」與「搜尋
   沒有符合結果」**——沿用 `listKnowledgeBases` 自己的 trim 判斷,
   兩側保持一致;沿用既有的「重用『尚無知識庫』訊息會誤導使用者
   以為完全沒有知識庫」既有理由(`conversation-list.tsx` 的 S023
   doc comment 已經講過同一件事)。
5. **無 debounce**——這個 mock 的搜尋是即時記憶體陣列過濾,沒有
   真正的網路延遲需要 debounce,加入 debounce 邏輯會是沒有對應成本
   的多餘複雜度。
