## Scope 說明

E05 的第四個 story。與 S001-S003 相同情況:SOURCE_BASELINE.md 對 E05 只有
一份扁平標題清單,本 story(`E05-S04 Edit KB`,line 1440)只有標題,無
進一步內文。epic 檔展開標題「Edit KB metadata」把 `name`+`description`
兩個欄位一起視為單一「metadata」編輯動作(不是兩個獨立欄位各自的
setter)。已讀過 epic 檔本 story 自己的章節(line 642-851,下一節
`# E05-S005 — KB detail page` 從 line 852 開始),確認與其他 story 相同,
是逐字相同的通用 MVP 樣板文字,無本 story 專屬內容。

**關鍵範圍/位置判斷**:`/knowledge/[id]`(E05-S05「KB detail page」)
目前仍不存在(下一個 story 才會建立)。與 E03-S024「Rename Conversation」
不同——那個 story 的編輯 UI 是內嵌在早已存在的 `/conversations/[id]`
詳情頁裡的一個元件——本 story**沒有**詳情頁可以內嵌,因此把編輯做成
自己獨立的路由 `/knowledge/[id]/edit`,入口連結(「編輯」)加在
`KnowledgeList`(`/knowledge`)每個項目上。這不是重新引入 S001 刻意
避免的「整項連到詳情頁」的連結(那個連結至今仍不存在,`/knowledge/[id]`
本身依然沒有 `page.tsx`)——是一個不同、明確標示、指向本 story 自己建立
的真實路由的連結。

**刻意不與 `/knowledge/new`(S003)共用表單元件**——雖然兩者都有
`name`+`description` 兩個欄位,但這兩個表單有實質差異(本 story 需要
先 fetch 既有資料、需要 loading/error/not-found 三態、儲存後行為也不同),
且這個 codebase 沒有「create 表單與 edit 表單共用元件」的既有先例——
`RenameConversation` 與 `conversations/new/page.tsx` 同樣都是「文字輸入
+送出」,兩者也是完全獨立、不共用元件的實作。

## 設計決策

1. **`updateKnowledgeBase(id, name, description?)` 一次接收完整
   name+description,而非兩個獨立的 setter**——epic 展開標題把兩個欄位
   綁成一個「metadata」編輯動作,不同於 `lib/conversations.ts` 裡各自
   獨立觸發的 `renameConversation`/`setConversationMode` 等單欄位
   setter。
2. **`getKnowledgeBase(id)` 回傳 `Result<KnowledgeBaseSummary | null,
   ApiError>`**——`value: null`(非 error)代表「合法路由,但 id 沒有
   對應資料」,與 `lib/conversations.ts` 的 `getConversation`/
   `AuthClient.getSession()` 用 `null` 表達「預期內的沒有結果」是同一種
   建模方式,不是 dependency failure。
3. **`updateKnowledgeBase` 沿用 `createKnowledgeBase` 的
   VALIDATION_ERROR-on-空白-name 規則**,並新增 NOT_FOUND(id 不存在)
   ——鏡射 `lib/conversations.ts` 內部 `updateConversation` helper 的
   既有模式,讓呼叫端不會把「已經不存在」誤判為「剛剛存好了」。
4. **每次編輯都會刷新 `updatedAt`**——編輯本身就是對這筆紀錄的異動,
   與該欄位在 `SAMPLE_KNOWLEDGE_BASES` doc comment 裡自己定義的
   「recency signal」意義一致。**保留項目在 `listKnowledgeBases()`
   裡原本的位置**(用 `.map()` 原地取代,不是刪除再 prepend)——
   `listKnowledgeBases()` 從未依 `updatedAt` 排序,編輯不應該連帶造成
   排序跳動,這不是本 story AC 要求的行為。
5. **`/knowledge/[id]/edit/page.tsx` 是薄的 async Server Component
   wrapper,拆出 `_components/edit-knowledge-base.tsx` 當 client
   component**——這是 Next.js 15 async `params`的既有必要拆分,逐字
   鏡射 `conversations/[id]/page.tsx` 拆出
   `_components/conversation-detail.tsx` 的既有先例,不是本 story
   自創的架構。
6. **初始載入的 loading/error/not-found 三態鏡射
   `ConversationDetail` 的既有模式**,包含重用 `ErrorMessage` 既有的
   `NOT_FOUND` code(「找不到您要的內容。」)而非自創文案——
   `ConversationDetail` 已經為這個確切情境(合法路由、id 沒有對應資料)
   建立了先例。
7. **成功儲存後導向 `/knowledge`(列表),不導向 `/knowledge/[id]`**——
   後者仍不存在(S05 的範圍);也不像 `RenameConversation` 停留原地
   顯示新值,因為本 story 的編輯頁本身就是獨立頁面,沒有「詳情頁的
   其他內容」可以停留著一起看,鏡射 S003 `/knowledge/new` 成功後導向
   列表的既有選擇。
8. **表單非樂觀更新、儲存失敗時保留已輸入值**——與 S003
   `/knowledge/new`、`RenameConversation` 的既有慣例一致。
9. **Telemetry/log 不記錄使用者輸入的 name/description 原文**,只記錄
   correlationId 與 `knowledgeBaseId`——沿用 S003 對「已持久化實體內容
   不記錄原文」既有先例的判斷,理由相同。

## 開發過程中的技術發現(FIX 循環,1 次)

`knowledge-edit.spec.ts` 原本包含第 4 個測試,直接 `page.goto()` 造訪
一個不存在 id 的編輯網址,驗證 not-found 訊息。第一次執行時失敗,診斷
過程:

1. 第一次懷疑是 `getByRole("alert")` 與 Next.js 自己注入的
   `role="alert"` route announcer(`id="__next-route-announcer__"`)
   衝突(`error-boundary.spec.ts`/`answer-state.spec.ts` 已有這個
   已知問題的既有註解)——改用 `page.getByRole("main").getByRole
   ("alert")` 縮小範圍(既有慣例)後重跑,**仍然失敗**,這次是
   「element(s) not found」,顯示連 `<main>` 內都沒有 alert 元素。
2. 換診斷路徑(不是重複同一種修法):讀取 Playwright 產生的
   `error-context.md` accessibility snapshot,發現畫面實際停在
   **登入頁**(`heading "登入"`),不是編輯頁。
3. 追查根因:`packages/auth-client/src/mock.ts` 的 `currentSession`
   是一個**純記憶體內的 closure 變數**,無 cookie/sessionStorage
   backing。`conversations.spec.ts` 的檔案級 doc comment已經明確記載
   這件事,並說明為什麼「登入後一律用站內連結導覽,絕不用
   `page.goto()`」——`page.goto()` 是整頁重新載入,會重新執行整個
   bundle(重置成一個全新、空的 session)。我的第 4 個測試在
   `login(page)` 後直接 `page.goto()` 到編輯網址,正好命中這個已知
   限制,導致 session 遺失、被導回登入頁。
4. 進一步確認這與 `route-guards.spec.ts` 既有的「authenticated user
   hitting an unknown route」測試(同樣在 login 後 `page.goto()`)
   不衝突、不代表那個既有測試有問題:那個測試的目標路徑
   (`/this-route-does-not-exist`)在任何地方都沒有對應的
   `page.tsx`,Next.js 根本不會掛載 `(app)` layout(也就不會經過
   `SessionGate`),所以那個 404 天生與 session 狀態無關。本 story的
   `/knowledge/[id]/edit` 則是一個真實存在、巢狀在 `(app)` 底下的
   `page.tsx`,任何造訪都必須先通過 `SessionGate`——`page.goto()`
   重置 session 後,`SessionGate` 正確地(依它自己的邏輯)導向登入頁,
   根本沒有機會走到本 story 自己的 not-found 畫面。這是兩種結構上
   不同的「404」,不是同一件事。
5. 由於沒有任何站內連結會指向一個不存在的 id(依定義不可能存在),
   這個情境在本 mock 架構下沒有合法的 E2E 路徑可測。依循
   `conversations.spec.ts` 檔案本身已建立的先例(「刪除,而非
   skip」一個經過完整根因驗證、確認不是產品缺陷的測試),移除這個
   E2E 測試,在檔案 doc comment 完整記錄上述推理鏈。not-found 狀態
   本身**沒有失去測試覆蓋**——`edit-knowledge-base.test.tsx`的
   「shows a distinct not-found state」測試直接用 mock 的
   `getKnowledgeBase` 回傳 `{ ok: true, value: null }` 驅動同一段
   程式碼路徑,是真實斷言,非空殼測試。
6. 修正後**從 VERIFY 第一個 gate 重新完整跑過**(typecheck→lint→
   unit→build→E2E 隔離→E2E 全量 force 兩輪),而非只重跑失敗的
   E2E,符合 STORY_WORKFLOW Phase 4 規則。
