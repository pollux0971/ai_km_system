## Scope 說明

E05 的第五個 story。與 S001-S004 相同情況:SOURCE_BASELINE.md 對 E05 只有
一份扁平標題清單,本 story(`E05-S05 KB Detail`,line 1442)只有標題,無
進一步內文。已讀過 epic 檔本 story 自己的章節(line 852-1061,下一節
`# E05-S006 — KB permission editor` 從 line 1062 開始),確認與其他
story 相同,是逐字相同的通用 MVP 樣板文字,無本 story 專屬內容。

**關鍵範圍判斷**:`KnowledgeList`(S001)的既有 doc comment 早已明確
記錄「Items aren't linked to a detail view — /knowledge/[id] doesn't
exist yet (that's E05-S05 "KB Detail"'s job)」——這正是本 story 要
完成的事,與 E03-S001→E03-S002 的既有先例(conversation-list.tsx 同樣
先留白、後由對應 story 補上連結)完全對等。

`KnowledgeBaseSummary`(S001 建立)目前只有 `id`/`name`/`description`/
`updatedAt` 四個欄位,沒有文件數量、成員、權限等其他資料——本 story
只呈現現有欄位,不提前實作 S06(KB Permission)、S07(KB Members)、
S08(KB Prompt)、S09(KB Model)、S10(KB Document List)、S28(KB
Usage Stats)等後續 story 各自的範圍。

**編輯維持獨立路由,不內嵌到詳情頁**——與 `RenameConversation`(內嵌在
早已存在的 `/conversations/[id]` detail 頁面裡)不同,S04「Edit KB
metadata」在本 story(detail 頁面)存在之前就已經把編輯做成獨立路由
`/knowledge/[id]/edit`(因為當時沒有 detail 頁可以內嵌)。把 S04 已核准
合併的編輯 UI 重構成內嵌表單,會是本 story 名稱(「detail page」,不是
「redesign editing」)之外、且違反 Change Budget 的範圍外變更;本 story
只在詳情頁加入一個指向該既有路由的「編輯」連結。

## 設計決策

1. **`/knowledge/[id]/page.tsx`(薄 async Server Component)+
   `_components/knowledge-detail.tsx`(client component)**——鏡射
   `conversations/[id]/page.tsx` 與本 epic自己的
   `knowledge/[id]/edit/page.tsx`(S04)已建立的既有拆分方式,處理
   Next.js 15 async `params`。
2. **loading/error/not-found/loaded 四態鏡射 `ConversationDetail`/
   `EditKnowledgeBase` 的既有模式**,包含重用 `ErrorMessage` 既有的
   `NOT_FOUND` code。
3. **完全重用 S04 既有的 `getKnowledgeBase(id)`,不新增任何
   `lib/knowledge-bases.ts` 的變更**——這是純讀取,S04 已經為「合法
   路由但 id 無對應資料」建立了 `null`(非 error)的既有回傳語意,
   本 story 不需要、也不應該重新發明。
4. **沒有 `trackEvent` 呼叫,只有 `logger.info`/`logger.error`
   (皆帶 correlationId)**——與 `ConversationDetail` 的初始載入、
   `KnowledgeList`(S001)自己完全一致:這個 codebase 的既有慣例是
   `trackEvent`(telemetry)只用於使用者主動觸發的動作(建立/編輯/
   刪除/重新命名等 mutation),純讀取的頁面載入用 `logger` 滿足
   Functional AC 6 的「correlation id / structured telemetry」
   要求,不是遺漏。
5. **`KnowledgeList` 把項目名稱包進
   `<Link href={\`/knowledge/${item.id}\`}>`**——逐字鏡射
   `conversation-list.tsx` 把 `item.title` 包進
   `<Link href={\`/conversations/${item.id}\`}>` 的既有寫法(只包
   名稱,不是整個 `<li>`);移除 S001 doc comment 裡「items aren't
   linked」這段現在已經不成立的舊說明,改記錄本 story 在此補上。
6. **「編輯」連結沿用 S04 既有樣式,新增的名稱連結與「編輯」連結是
   兩個獨立元素**——不是把整個項目變成單一連結再讓「編輯」變成
   nested link(HTML 不允許 `<a>` 內嵌 `<a>`),兩者維持 S001/S004
   既有的並列結構。
7. **不顯示原始 `id`**——真實產品不會把內部 UUID 直接展示給使用者,
   AC 也沒有這項要求。
8. **不加「返回列表」連結**——`ConversationDetail` 沒有這個既有
   先例(仰賴側邊欄導覽/瀏覽器上一頁),本 story 維持一致,不額外
   發明 AC 未要求的 UI。

## 開發過程中的技術發現(FIX 循環,1 次)

`knowledge-detail.test.tsx` 原本用
`screen.getByText(new Date(sampleKnowledgeBase.updatedAt).toLocaleString("zh-TW"), { exact: false })`
斷言渲染出的時間文字,第一次執行時失敗:錯誤訊息顯示「Unable to find
an element with the text: 2026/8/14 上午8:00:00」,但同一份錯誤輸出的
DOM 快照裡明明就有 `<time>2026/8/14 上午8:00:00</time>`,兩者用肉眼看
完全相同。

診斷:`Intl`/`toLocaleString("zh-TW")` 對日期時間格式化時,「上午/下午」
與時間之間常會插入不可見的特殊空白字元(如 narrow no-break space,
U+202F),而 Testing Library 的預設文字比對只會正規化(collapse)DOM
裡實際渲染出來的文字,不會對「傳入的比對字串」做同樣的正規化——我在
測試裡另外呼叫一次 `toLocaleString` 產生的比對字串,與元件渲染出來、
經過正規化的 DOM 文字,在那個不可見字元上不一致,導致位元級不相符
但肉眼完全看不出差異。

複驗:`grep` 全 repo 確認沒有任何既有測試(包含 `knowledge-list.test.tsx`
自己)曾經斷言過 `.toLocaleString(...)` 的渲染文字內容——這不是巧合,
而是這個 codebase 對這類 Intl 格式化字串既有的(雖未明講,但一致遵守
的)迴避模式。修正方式:改用 `<time>` 元素的 `datetime` 屬性(原始
ISO 字串,非 locale 格式化)斷言,不依賴 Intl 格式化輸出。修正後
**從 VERIFY 第一個 gate 重新完整跑過**(typecheck→lint→unit→build→
E2E 隔離→E2E 全量 force 兩輪),符合 STORY_WORKFLOW Phase 4 規則。

E2E 層級完全不受影響——`knowledge-detail.spec.ts` 從一開始就沒有
斷言任何 `.toLocaleString(...)` 渲染文字(只斷言 heading 名稱與
description 文字),也沒有嘗試對本 story 的 not-found 狀態寫
`page.goto()` 直連測試——已知這會因為 mock session 是純記憶體變數而
在 login 後的 `page.goto()` 遺失(S04 EVIDENCE 已完整記錄根因),本
story 從一開始設計 E2E 時就沿用同一個已知限制,不需要重新踩雷一次。
