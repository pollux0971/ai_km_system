E05 的第七個 story。與 S001-S006 相同情況:SOURCE_BASELINE.md 對 E05 只有

**與 S006(KB Permission editor)的關係**:兩者都是「誰可以存取這個
知識庫」這個大主題底下的子能力,但緯度不同——S006 是**角色**層級
(哪些角色可存取),S007 是**特定個人**層級(額外把哪些具體使用者
加進來,即使他們的角色本身不在 S006 設定的允許清單裡)。這是常見
產品模式(「角色可存取」+「另外分享給這些人」並存),`grep` 全文

不是「誰是這個 KB 的成員」)與 E05-S07 標題本身兩處提及,沒有更具體
規格,故依產品常識+ S006 已建立的先例做出上述判斷,記入 assumptions。

**沿用 S006 已確立的關鍵界線**:這仍然只是一個「設定」,不建立任何
強制執行——`listKnowledgeBases()` 完全不因 `members` 而過濾結果
(已用專屬測試驗證,鏡射 S006 的「is a setting only」測試)。真正的

## 設計決策

1. **`members?: string[]`,不透過 `@ai-km/permissions` 的 `Role`
   型別,而是不透明識別字串**——E02-S01「User Entity」(Team B)不
   存在,`packages/auth-client` 的 mock 只有 3 個**登入測試用**帳號
   (`MOCK_VALID_USERNAME` 等,給 E2E 測試登入用),不是一份可以正當
   拿來當「使用者目錄」的清單。與
   `updateKnowledgeBaseVisibleRoles` 自己的 doc comment 對
   DEPARTMENT/GROUP/PROJECT/USER 這幾種 ACL scope 目標「沒有真正實體
   目錄,不假裝有 picker」的既有理由完全一致地延伸到本 story。
2. **`updateKnowledgeBaseMembers` 在資料層做正規化(trim、去除空白、
   去重),而非回傳 VALIDATION_ERROR**——與 `createKnowledgeBase`
   對 `name` 的 fail-closed 拒絕不同,因為這是一個**清單型**欄位,
   單一雜訊項目(空白字串、重複)沒有對應的「這個輸入本身是錯的」
   概念,寬容地正規化掉遠比拒絕整個儲存動作更合理;且這不是
   security-relevant 的驗證(空字串留著或濾掉都不會產生任何存取層面
   的差異,因為根本沒有強制執行機制)。UI 層(「新增」按鈕在輸入
   為空/純空白時 disabled)才是 Functional AC 2 的主要防線,資料層
   正規化是防禦性的第二層安全網,不是取代 UI 層防線。
3. **UI 互動模式:新增/移除皆為即時生效的獨立動作**(呼叫
   `updateKnowledgeBaseMembers` 時送出「完整新清單」,不是逐一
   add/remove 的 API)——與 S006 checkbox 群組、
   `setConversationKnowledgeScopes` 的既有「呼叫端回報目前完整狀態」
   模式一致;但因為「成員」不是像角色一樣的固定小清單,UI 本身需要
   「文字輸入+新增鈕」+「清單項目各自的移除鈕」,是這個 codebase
   第一個此類「自由文字清單編輯器」——沒有直接先例可鏡射,是本
   story 自己建立的新 UI 模式(仍遵循既有的 pending-disable-一切、
   非樂觀更新、失敗時保留使用者輸入以便重試等既有慣例)。
4. **新增失敗時保留輸入框內容(不清空),成功才清空**——與
   `EditKnowledgeBase`/`NewKnowledgeBasePage` 失敗時保留已輸入值的
   既有慣例一致,避免使用者重新輸入。
5. **獨立路由 `/knowledge/[id]/members`,S05 詳情頁新增摘要+連結**
   ——鏡射 S06 剛建立的確切模式(不是 S04/S05 的一部分,只在詳情頁
   加一行摘要與一個連結)。
6. **Functional AC 7(稽核事件)適用,telemetry 內含實際 from/to
   成員清單**——沿用 S006 的判斷邏輯:變更誰能存取資源是敏感操作;
   成員識別字串(如 `demo-user`)已經是這個 codebase 既有 log/
   telemetry 慣例會記錄的東西(例如 `session-gate.tsx` 自己的
   「session bootstrap succeeded」log 就會記錄 `userId`),不是
   新增一類原本不記錄的敏感資料,一個不記錄實際變更內容的權限異動
   稽核軌跡會失去稽核本身的意義。
