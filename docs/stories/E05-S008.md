## Scope 說明

E05 的第八個 story。與 S001-S007 相同情況:SOURCE_BASELINE.md 對 E05 只有
一份扁平標題清單,本 story(`E05-S08 KB Prompt`,line 1448)只有標題,
無進一步內文。已讀過 epic 檔本 story 自己的章節(line 1482-1691,下一節
`# E05-S009 — KB model binding UI` 從 line 1692 開始),確認與其他 story
相同,是逐字相同的通用 MVP 樣板文字,無本 story 專屬內容。

**與 S006/S007 的關鍵差異**:S006(角色)、S007(成員)都是「誰可以
存取」這個 ACCESS CONTROL 主題底下的子能力;本 story 是「這個知識庫
綁定什麼提示詞」,屬於**內容/設定**主題,性質更接近 S003/S004
(建立/編輯 metadata)而非 S006/S007。這個判斷直接影響三個設計決策
(見下方):Functional AC 7 是否適用、telemetry 是否記錄實際內容、
UI 互動模式選擇。

**「Prompt」實體本身尚不存在**:`grep` 全文確認 SOURCE_BASELINE 對
「Prompt」的提及——「8. 系統核心體驗」的 Admin 管理清單裡列出
「Prompt」與「KB」並列為個別管理項目(line 341,暗示真正系統裡
Prompt 是獨立實體,不是 KB 的附屬欄位);「E12 — Model & Prompt
Platform」(line 1908,Team B 所有,尚未實作任何 sub-story);
「E11-S12 Prompt Admin」(line 1873,Team A 的 E11 Admin Console 底下,
但 E11 全部 25 個 story 目前皆為 todo,尚未開工)。也就是說,「真正的
Prompt 實體 + 管理介面」要等 Team A 自己先做完 E11-S12,且真正的
執行(Model Gateway、Prompt Assembly)要等 Team B 的 E12——兩者都不
存在。因此本 story**不能**做成「從既有 Prompt 目錄挑選一個綁定」,
只能是「把提示詞文字直接存在這個知識庫自己身上」——與 S007 對
「沒有真正使用者目錄,不假裝有 picker」的既有判斷同一類別的延伸。

## 設計決策

1. **`boundPrompt?: string`——提示詞文字直接存在 KB 自己身上,不是
   對外部 Prompt 實體的參照**——見 Scope 說明。選填,理由與
   `visibleToRoles`/`members` 相同(缺席代表「尚未設定」,與明確存成
   空字串是不同狀態;不強迫回填既有 fixture)。
2. **`updateKnowledgeBaseBoundPrompt` 只 trim,不因空白回傳
   VALIDATION_ERROR**——空提示詞是合法、有意義的狀態(「不使用自訂
   提示詞,回退平台預設」),與 S006/S007 對空清單的既有判斷一致。
3. **UI 互動模式:文字框+明確「儲存」按鈕,而非 S06/S07 的即時切換**
   ——提示詞是使用者會反覆編輯、可能較長的自由格式多行文字,不是
   一個離散的勾選/新增動作,每個按鍵都送出會是糟糕的 UX 也會產生
   過多呼叫。儲存成功後**留在本頁**(不像 S03/S04 導向列表)——與
   S06/S07「留在自己的子路由」先例一致,且對「反覆調整提示詞用詞」
   這個使用情境更實用。用「已儲存。」`role="status"` 訊息作為成功
   回饋(因為沒有導向可以隱含成功),使用者一旦繼續編輯就清除這個
   訊息,避免對「目前(可能已被修改的)草稿」的儲存狀態說謊。
4. **Telemetry 不記錄提示詞文字本身**——提示詞是**自由格式內容**
   (更接近 `description` 而非 S006/S007 的角色/成員這種固定詞彙/
   短識別字串),沿用 `createKnowledgeBase`/`updateKnowledgeBase`
   對 `name`/`description` 「不記錄企業原文」的既有克制,而非
   S006/S007「記錄實際 from/to 內容」的既有先例。專屬測試直接斷言
   `trackEvent` 的**所有**呼叫都不包含提示詞原文,不只是斷言事件
   有被觸發。
5. **Functional AC 7(敏感操作稽核事件)本 story 判定為不適用**——
   與 S006/S007(判定適用)不同:編輯 KB 綁定的提示詞文字是內容/
   設定變更,不是存取控制變更,與 S003-S005 metadata 編輯屬於同一
   類別,理由同 S003-S005 對這條 AC 的既有判斷。
6. **詳情頁摘要只顯示「已設定」/「尚未設定」,不顯示提示詞全文**——
   與角色/成員摘要(直接列出短標籤/識別字串)不同,提示詞可能是
   一整段文字,不適合塞進詳情頁的一行摘要,且完整內容已經在專屬
   editor 路由可以看到,重複顯示沒有必要。

## 開發過程中的技術發現(FIX 循環,1 次,橫跨兩個檔案)

`knowledge-detail.tsx` 新增的「綁定提示詞:已設定/尚未設定」摘要,在
知識庫未設定任何權限**也**未綁定任何提示詞的情況下(`sampleKnowledgeBase`
這個測試 fixture、以及任何全新建立的知識庫皆是如此),畫面上會**同時**
出現兩個文字完全相同的「尚未設定」——一個來自 S006 的「可存取角色」
摘要,一個來自本 story 新增的「綁定提示詞」摘要。

第一次執行單元測試時,S006 既有測試「shows 尚未設定 when no
permission has been configured yet」(斷言用
`screen.findByText("尚未設定")`,未指定範圍)因此變成模稜兩可,失敗;
第一輪修正後(把該測試改為先定位「可存取角色:」摘要段落、再斷言其
內容)重新執行完整迴歸 E2E 時,同一個問題**在 E2E 層級**再次出現——
`knowledge-permissions.spec.ts`(S006 既有 E2E spec)裡兩個測試同樣用
未限定範圍的 `page.getByText("尚未設定")`,在真實瀏覽器的 strict mode
下直接回報「resolved to 2 elements」。

修正:比照第一輪對單元測試的修法,把這兩個 E2E 斷言也改為先定位
「可存取角色:」摘要段落(`page.getByText("可存取角色:", { exact:
false })`)、再對該段落斷言內容,不再使用容易被未來新摘要撞名的
裸字串比對。

**這是本 story 自己選擇兩個獨立欄位共用「尚未設定」這個字串所直接
造成的必要修正,不是無關的順手修改**——依 Change Budget 原則
(修改必須可解釋回某條 AC/test obligation/必要 refactor)記入本
EVIDENCE 而非另開 story;範圍侷限在 E05 knowledge 領域自己的既有
測試檔案,未跨 domain,不需要 BLOCKED。修正後**從 VERIFY 第一個 gate
重新完整跑過**(typecheck→lint→unit→build→E2E 隔離→E2E 全量 force
兩輪),符合 STORY_WORKFLOW Phase 4 規則。
