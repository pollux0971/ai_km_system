# E05-S010 — KB document list

## Scope 說明

E05 的第十個 story。與 S001-S009 相同情況:SOURCE_BASELINE.md 對 E05
只有一份扁平標題清單,本 story 在 epic 檔中只有標題,無進一步內文。已讀
過 epic 檔本 story 自己的章節(line 1902-2111,下一節「Single-file
upload」從 line 2112 開始),確認與其他 story 相同,是逐字相同的通用
MVP 樣板文字,無本 story 專屬內容。

**與 S001-S009 的關鍵差異:第一次引入全新實體「Document」**。S006(角色)
重用既有 `@ai-km/permissions` 的 `Role`;S007(成員)是不透明字串,無
真正實體;S008(提示詞)是文字直接存於 KB 自身;S009(模型)重用既有
`AI_MODELS`。本 story 不同——「文件」是這個知識庫底下的**一組獨立
實體**(有自己的 id、名稱、大小、上傳時間),不是 KB 的單一設定值。
`grep` 全文確認整個程式庫目前沒有任何 `Document`/`DocumentSummary`
型別存在。真正的 Document 實體屬於 **E06(Team B,Knowledge Ingestion
& Indexing)**——36 個 sub-story(Upload API、Object Storage、MIME/
大小/checksum 驗證、重複偵測、防毒、各格式 parser、OCR、chunking、
embedding、vector write、版本控制、worker queue),目前全部
`todo`,`contracts/openapi/core.yaml` 對此無任何 path。

**確認範圍邊界:本 story 只做「列表」,不做「上傳」**。讀完 epic 檔
本 story 之後的標題清單(line 2112 起)確認:`E05-S011 Single-file
upload`、`S012 Multi-file upload`、`S013 Folder upload`、`S014 URL
import`、`S015 Text knowledge input`、`S016 Folder sync setup UI`、
`S017 Upload progress`、`S018 Parse progress`、`S019 Index progress`、
`S020 Processing failure state`——上傳、進度、失敗狀態全部是後續
獨立 story。這與 S001(list)先於 S003(create)的既有 sequencing
完全一致。因此本 story:(a) 不提供任何上傳入口/按鈕;(b) 文件資料
是**唯讀種子資料**,無任何 mutation function;(c) 文件的 shape 刻意
最小(id/knowledgeBaseId/name/sizeBytes/uploadedAt),不包含
status/mimeType/version 等欄位——那些屬於 S011-S020 與 E06-S30-32
(Team B)的範圍。

## 設計決策

1. **`KnowledgeBaseDocument` 獨立於 `KnowledgeBaseSummary`,存在自己
   的檔案 `lib/knowledge-documents.ts`,不是 KB 的欄位**——直接複用
   `lib/messages.ts`(Message vs. ConversationSummary)已建立的先例:
   讀取該檔確認 `listMessages(conversationId)` 是獨立模組、獨立
   collection,理由是「conceptually its own collection keyed by a
   parent id」。同理,`listKnowledgeBases()` 若在每筆項目內嵌一個
   可能很大的文件陣列,會是典型的 over-fetching(真正的
   `GET /knowledge-bases/{id}/documents` 端點就會避免這種設計)。
   `knowledge-bases.ts`(S001)自己的既有 doc comment 也明確預告了
   這個決定:「No document count or other summary stat — E05-S10
   'KB Document List' is its own later story...」。
2. **只有 `readStore()`,沒有 `writeStore()`**——本 story 是純列表,
   目前沒有任何呼叫端需要寫入。曾經一度仿照
   `knowledge-bases.ts`/`messages.ts` 加入 `writeStore()`,但發現
   完全沒有呼叫端(連測試都不需要),屬於「為假設性的未來需求設計」
   ,予以移除。`readStore()` 仍是 sessionStorage-backed(而非直接
   讀常數),因為這是本程式庫既有、一致的持久化慣例,而非投機新增
   ——S011(Single-file upload)會在真正新增第一個寫入呼叫端時
   自行補上 `writeStore()`。
3. **`listKnowledgeBaseDocuments()` 只過濾,不檢查 KB 是否存在**
   ——與 `listMessages(conversationId)` 完全相同的簡化(讀取
   `messages.ts` 原始碼確認其行為與理由),因為呼叫端(本 story 的
   `KnowledgeDocumentList` 元件、以及 `KnowledgeDetail`)本身都已經
   各自呼叫 `getKnowledgeBase(id)` 取得 loading/error/not-found
   狀態,不需要第二層重複檢查。
4. **文件不存在單獨的檔案類型欄位**——僅用 `name`(含副檔名,如
   「產品保固條款.pdf」)視覺呈現類型,不新增
   `fileType`/`mimeType` enum——E06 自己的 parser story(PDF/DOCX/
   PPTX/XLSX/CSV/TXT/Image/OCR)都還沒開工,提前發明分類等於用猜的。
5. **文件列表頁的兩段循序 fetch(先 getKnowledgeBase,確認存在後才
   fetch documents),不是平行 fetch**——文件離開了存在的 KB 沒有
   意義,沒有理由在確認 KB 存在前就去要文件。專屬測試證明「KB
   fetch 回傳 not-found 或 error 時,listKnowledgeBaseDocuments
   完全不會被呼叫」。
6. **文件列表頁只有一個共用的 `error` 狀態,涵蓋兩個 fetch 來源的
   失敗**——目前的 mock `listKnowledgeBaseDocuments()` 實際上永遠
   不會回傳 `ok:false`(與 `listMessages`/`listKnowledgeBases` 相同,
   純過濾、不會失敗),這條分支本來就與每個手足元件自己的
   getKnowledgeBase 失敗分支一樣,是「技術上一定要處理但目前不可能
   觸發」的防禦性分支,不值得為此分裂成兩種不同措辭的錯誤狀態,
   增加不必要複雜度。
7. **`knowledge-detail.tsx` 加的是「文件數量」摘要,不是文件清單
   本身**——與角色/成員(直接列出短標籤/識別字串)不同:文件名稱
   可能很多、個別很長,不適合塞進一行摘要,與 `boundPrompt` 摘要只
   顯示「已設定」/「尚未設定」而非提示詞全文,是同一種理由。這是
   本頁第一次需要「第二層 fetch」(先前 S006-S009 全部只需要
   `getKnowledgeBase` 一次呼叫);為了不讓次要的、目前技術上不可能
   失敗的第二個 fetch 拖垮整頁,文件數量 fetch 失敗時只降級顯示
   「－」佔位符,不會讓已經成功載入的知識庫本身也一起顯示整頁錯誤
   ——這是刻意的優雅降級決定,不是隨意的例外處理。
8. **文件 fixture 資料刻意分布在既有 3 個 KB fixture 上
   (3 筆/1 筆/0 筆),不新增第 4 個純測試用 fixture**——延續 S002
   搜尋測試「重用既有 fixture 呈現不同狀態」的既有做法,讓 UX
   Acceptance 需要的多筆/單筆/空清單三種狀態,都能用既有 KB 名稱
   直接在 E2E 呈現,不需要發明新知識庫。
9. **`formatFileSize` 在新元件內部直接複製,不從
   `file-attachment-picker.tsx`(E03-S008)抽成共用函式**——雖然是
   逐字相同的 4 行函式,但該檔案屬於 E03 domain,不在本 story 允許
   修改清單內;STORY_WORKFLOW 的 Domain Ownership Boundary 明確禁止
   「不得順手重構其他 Epic、其他 Domain 或無直接關係的 shared
   package」,即使只是抽一個小函式也不例外。真正共用的格式化函式
   應該進 `@ai-km/ui`,但那是比本 story 更大的決定,不該由本 story
   單方面決定。
