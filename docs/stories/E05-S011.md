## Scope 說明

E05 的第十一個 story。與 S001-S010 相同情況:SOURCE_BASELINE.md 對 E05
只有一份扁平標題清單,本 story 在 epic 檔中只有標題,無進一步內文。已讀
過 epic 檔本 story 自己的章節(line 2112-2321,下一節「Multi-file
upload」從 line 2322 開始),確認與其他 story 相同,是逐字相同的通用
MVP 樣板文字,無本 story 專屬內容。

**核心邊界確認**:本 story 開發邊界明文禁止「不得讓 Frontend / BFF
直接連 Database、Vector DB、Object Storage 或 Provider credential」
(line 2184,與每個 story 相同的通用樣板句)。真正的 Upload API
(E06-S01)與 Object Storage(E06-S02)都屬於 E06(Team B),目前皆
`todo`。這與 E03-S008「File attachment picker」當年面對的完全相同
情境——該 story 自己的 doc comment 明確記錄「no upload happens
here... Frontend/BFF may never connect directly to Object Storage」,
是純前端檔案選擇 UI,零真實上傳。本 story 直接沿用同一先例:只用
瀏覽器 `File` 物件本來就能取得的中繼資料(`name`/`size`),不讀取、
不儲存、不傳輸任何檔案位元組內容到任何地方。

## 設計決策

1. **上傳元件內嵌在既有的 `/knowledge/[id]/documents` 頁面上,不是
   新的獨立路由**——與 S03/S04/S06/S07/S08/S09 的「KB 層級設定,各自
   獨立路由」模式不同:「文件」是一個會持續成長的**子集合**,新增
   項目理應與呈現該集合的頁面同頁,不是另開一個路由。直接類比
   `lib/messages.ts` 的 Message 與 ConversationSummary 的關係——
   `sendMessage()` 是從內嵌在 `conversation-detail.tsx`
   (`/conversations/[id]`)裡的訊息輸入框呼叫,並沒有獨立的
   `/conversations/[id]/messages/new` 路由。
2. **`addKnowledgeBaseDocument` 收純值(`name: string`,
   `sizeBytes: number`),不收原始 `File` 物件**——與
   `sendMessage()` 收 `attachmentNames: string[]`(呼叫端已從
   `File[]` 抽出名稱)而非原始 `File[]` 同一種設計,讓 lib 層維持
   平台無關、可直接單元測試,不需要 DOM File polyfill。呼叫端
   (`KnowledgeDocumentUpload`)負責從 `File` 物件抽取必要欄位。
3. **`addKnowledgeBaseDocument` 只做結構性驗證(trim 後拒絕空白
   名稱、KB 必須存在),不驗證檔案大小或類型**——延續
   `FileAttachmentPicker`(E03-S008)自己 doc comment 已有的判斷:
   `AI_KM_BMAD_High_Granularity/` 全文沒有任何檔案大小上限、MIME
   allowlist 定義,唯一具體的格式清單屬於 E06 自己的 parser story
   (Team B),此刻發明一個限制等於用猜的。與 `createKnowledgeBase`/
   `renameConversation` 相同的「伺服器端也驗證,不只靠 UI」原則
   ——即使真實瀏覽器 `File.name` 幾乎不可能是空字串,函式本身仍
   拒絕空白輸入。
4. **選擇後需明確按「上傳」確認,不是選檔即自動上傳**——與 S06/
   S07/S09 的即時套用模式不同:那些是在一組已知安全的固定選項中
   切換,使用者選錯可以直接重選;檔案是從系統選擇器挑出來的,值得
   給使用者一次「確認這是我要的檔案」的機會,更接近 S08 的
   草稿→儲存兩段式。上傳失敗時**保留**已選擇的檔案(不清空),
   讓使用者不需要重新選檔就能重試——與 S08「儲存失敗保留草稿」
   同一種對使用者友善的失敗處理。
5. **`formatFileSize` 抽成本 story 與 S010 共用的
   `format-file-size.ts`,不第三次複製**——`knowledge-document-
   list.tsx`(S010)與 `knowledge-document-upload.tsx`(本 story)
   都是**同一個 story 範圍內、同一個 domain(E05)、同一個路由**
   自己的檔案,彼此重構完全合法,與兩者都各自獨立複製
   `file-attachment-picker.tsx`(E03,不同 domain,不在本 story
   允許修改清單內)的既有先例不衝突——那條界線只擋「跨 domain」,
   不擋「同一個 story 範圍內自己新增的兩個檔案」。
6. **Telemetry 記錄 `sizeBytes`,絕不記錄檔案名稱**——檔案名稱是
   使用者/檔案系統決定的自由格式文字,可能本身就洩漏敏感資訊
   (例如「XX客戶合約.pdf」),性質更接近 `name`/`description`/
   `boundPrompt`(S008 排除記錄提示詞原文)而非 S006/S007/S009的
   固定詞彙(角色/成員/模型)。`sizeBytes` 只是數字,不是內容,
   可安全記錄。專屬測試直接斷言所有 `trackEvent` 呼叫都不含檔案
   名稱字串,不只是斷言事件有觸發。
7. **Functional AC 7(敏感操作稽核事件)判定不適用**——新增一筆
   文件記錄是內容新增動作,不是存取控制變更,與 S003「Create KB
   form」(建立新實體,AC7 不適用)同一類別,不同於 S006/S007
   (真正變更誰能存取什麼)。此外,本 mock 完全沒有讀取/儲存/
   傳輸任何真實檔案內容,不存在真正需要稽核的內容流動,除了下方
   已有的 structured telemetry 外,沒有更多值得記錄的東西。
8. **上傳成功後只重新 fetch 文件列表(`refetchDocuments`),不重新
   fetch 知識庫本身**——效能考量在 mock 情境下不重要,但語意上
   更正確:知識庫本身沒有變,沒理由連帶重抓;也避免一個不相關的
   KB fetch 失敗反而讓剛剛成功的上傳被連累顯示錯誤。`refetchDocuments`
   失敗時延續 S010 對 `knowledge-detail.tsx` 文件數量 fetch 失敗
   的既有原則——安靜記錄、保留已顯示的(略舊)清單,不讓整頁報錯
   蓋掉剛剛已經成功的上傳動作。

## 開發過程中的技術發現(FIX 循環,1 次,E2E locator 衝突)

第一輪執行完整 E2E 測試時,兩個新增的 E05-S011 測試皆因
`page.getByRole("button", { name: "上傳" }).click()` 觸發 Playwright
strict-mode violation 失敗:`<input type="file" id="...">` 本身在
可及性樹(accessibility tree)中會以其關聯 `<label>`(「上傳文件」)
作為 accessible name,並以隱含 `role="button"` 曝露;Playwright
`getByRole` 預設非 exact(子字串)比對,導致「上傳」同時比對到這個
file input(accessible name「上傳文件」包含「上傳」)與真正的
`<button>上傳</button>`,造成兩個元素都命中。

Playwright 自己的錯誤訊息直接建議了修法(`aka getByRole('button',
{ name: '上傳', exact: true })`),對兩處使用同一 locator 的斷言
加上 `exact: true`,不放寬任何其他斷言。這是測試 locator 精確度的
問題,不是產品本身的邏輯錯誤——`KnowledgeDocumentUpload` 元件本身
運作正確,單元測試(對同一個互動用 `getByRole("button", { name:
"上傳" })` 搭配 RTL,RTL 對此沒有 Playwright 的 strict-mode 檢查,
因此未曾暴露這個問題)全數維持原樣未修改。修正後**從 VERIFY 第一個
gate 重新完整跑過**(typecheck→lint→unit→build→E2E),符合
STORY_WORKFLOW Phase 4 規則。
