## Scope 說明

E05 的第十二個 story。與 S001-S011 相同情況:SOURCE_BASELINE.md 對 E05
只有一份扁平標題清單,本 story 在 epic 檔中只有標題,無進一步內文。已讀
過 epic 檔本 story 自己的章節(line 2322-2531,下一節「Folder
upload」從 line 2532 開始),並用 `diff` 直接逐字比對本 story章節與
S011 章節的內文(排除 H1 標題與「User / System Value」段落唯一的
story 名稱代換),確認兩者逐字相同,是通用 MVP 樣板文字,無本 story
專屬內容。

**本 story 的本質是延伸既有元件,不是新建獨立能力**:S011 已經建立
`KnowledgeDocumentUpload` 元件與 `addKnowledgeBaseDocument` 函式,
S012「Multi-file upload」是同一個上傳動作的自然延伸(允許一次選取
多個檔案),不是平行的新頁面或新 lib 函式集合。這與
`FileAttachmentPicker`(E03-S008)自己一開始就支援 `multiple` 不同
——KB 文件上傳被 epic 明確拆成 S011(單檔)與 S012(多檔)兩個獨立
story,因此依規格順序,S011 故意不含 `multiple`,由本 story 補上。

## 設計決策

1. **選取採「累加」而非「取代」,鏡射 `MessageComposer`/
   `FileAttachmentPicker`(E03-S008)既有先例**——讀
   `message-composer.tsx` 原始碼確認
   `handleFilesSelected` 用 `setAttachments((previous) => [...previous,
   ...Array.from(fileList)])` 累加、`handleRemoveAttachment(index)`
   依索引移除,而非讓每次選取取代整個清單。原生
   `<input multiple>` 每次開啟對話框都會讓 `.files` 整個換掉,所以
   「可以分多次選取、逐步累積」這件事必須靠 component state 累加,
   不能只信任 input 當下的 `.files`——與 `MessageComposer` 面對的
   限制完全相同,直接沿用同一解法。
2. **循序(非平行)逐一呼叫既有的 `addKnowledgeBaseDocument`,不新增
   batch 函式**——具體分析了平行呼叫的風險:`addKnowledgeBaseDocument`
   內部是「一個真正 await 點(`getKnowledgeBase`)夾住一段同步
   read-modify-write(`readStore()`→`writeStore()`,中間沒有
   await)」的結構。目前用 `Promise.all` 平行呼叫「剛好」不會產生
   競態(因為 microtask 排程使每次 resume 後的同步區塊不會被打斷),
   但這是依賴實作細節的巧合,不是可以信賴的保證——只要
   `getKnowledgeBase` 或 `addKnowledgeBaseDocument` 未來任何一個
   環節多了一個真正的非同步延遲,平行呼叫就可能產生 lost-update。
   選擇循序執行,行為不依賴這個巧合,天生正確,也自然提供逐步
   進度的基礎。這也是本 story 對 Functional AC 5(重複/並發請求不得
   產生未定義 side effect)的具體回應——循序執行讓每個檔案的完成
   順序完全確定。
3. **每個檔案是獨立的工作單位,一個失敗不影響其他檔案**——與真實
   多檔上傳器的直覺行為一致(5 個檔案有 4 個成功不該因為 1 個失敗
   就全部作廢)。失敗的檔案保留在選取清單(從清單移除的只有成功
   的),讓使用者不需要重新選取成功的部分就能單獨重試失敗的——是
   S011「失敗保留選擇」既有設計,從單檔延伸到批次內逐檔套用同一
   原則。`onUploaded()` 只在「至少一個檔案成功」時觸發一次——全部
   失敗的批次沒有理由讓父層重新整理清單。
4. **Telemetry 維持 S011 既有的兩個事件名稱,每個檔案各觸發一組
   attempt/success/failure(不是整批一組)**——每個檔案本來就是
   獨立的「一次嘗試」,延伸既有事件的語意即可,不需要發明新的
   batch 事件類型。專屬測試直接驗證:2 個檔案產生 2 組獨立
   correlationId 的 attempt/success 配對。
5. **`<ul>` 加上 `aria-label="待上傳檔案"`**——開發過程中的技術發現
   (見下方),讓 E2E 測試能明確區分這份清單與 app shell 本身的
   `<nav><ul><li>` 導覽項目,鏡射本檔案自己既有的
   `sidebarNav`(`getByRole("navigation", {name:"主導覽"})`)手法。

## 開發過程中的技術發現(FIX 循環,2 次)

**第一次(typecheck)**:新增測試時把 Playwright E2E 測試慣用的
`{ name: "上傳", exact: true }` 誤用在 React Testing Library(RTL)
的 `getByRole` 呼叫上,typecheck 直接報錯——`ByRoleOptions`
(`@testing-library/dom`)型別定義中根本沒有 `exact` 欄位。直接讀
`node_modules/.pnpm/@testing-library+dom@10.4.1/.../queries.d.ts`
確認:RTL 的 `getByRole` 的 `name` 選項若給純字串,**本來就是精確
比對**,沒有子字串比對模式,因此也不需要(也沒有)`exact` 選項——
與 Playwright 的 `getByRole`(預設子字串比對,需要 `exact: true`
才會轉成精確比對)行為剛好相反。修法:移除全部 16 處誤加的
`exact: true`(RTL 呼叫本來就是精確比對,拿掉後行為不變)。這也
反向確認:S011 既有 RTL 測試裡的 `getByRole("button", {name:
"上傳"})`(沒有 exact 選項)從未受過任何子字串誤命中風險影響
(即使檔名恰好包含「上傳」兩字,例如「新上傳的檔案.pdf」的
「移除」按鈕),因為 RTL 的字串比對本來就是精確的。

**第二次(E2E)**:修正第一個 FIX 後跑 E2E,兩個測試因
`page.getByRole("listitem")`(未限定範圍)在真實瀏覽器頁面上同時
命中 app shell 自己的 `<nav><ul><li>` 導覽項目(首頁/對話/知識庫)
而失敗——單元測試因為只獨立渲染這個元件本身(沒有 app shell),
從未暴露這個問題;E2E 測試渲染整個頁面,才讓這個範圍問題現形。
修法:比照本檔案自己既有的 `sidebarNav` 手法,給上傳預覽清單的
`<ul>` 加上 `aria-label="待上傳檔案"`(見設計決策 #5),E2E 測試
新增 `pendingUploadList(page)` helper(`getByRole("list", {name:
"待上傳檔案"})`),把兩處未限定範圍的 `getByRole("listitem")`
改為透過這個 helper 限定範圍。兩次修正皆從 VERIFY 第一個 gate
重新完整跑過(typecheck→lint→unit→build→E2E),符合
STORY_WORKFLOW Phase 4 規則。
