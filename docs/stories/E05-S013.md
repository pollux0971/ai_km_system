**本 story 的本質是再一次延伸既有元件,不是新建獨立能力**——與
S012 面對 S011 的關係完全相同。「資料夾上傳」在瀏覽器裡的實際
機制是 `<input type="file" webkitdirectory>`:使用者選一個資料夾,
瀏覽器把該資料夾底下所有檔案攤平成一個 `FileList`,每個 `File`
物件額外帶有 `webkitRelativePath`(相對路徑)。這與 S012 已經建立
的「選取→預覽→逐一移除→批次上傳」機制,本質上是同一組 `File[]`
處理管線,差別只在「怎麼選出這一批 `File`」與「怎麼顯示/儲存它們
的名稱」。因此本 story 不新建元件、不新建 lib 函式,只在既有元件上
新增第二個輸入來源。

## 設計決策

1. **新增第二個獨立的 `<input type="file">`(「上傳資料夾」),不是
   讓既有輸入切換模式**——`webkitdirectory` 是瀏覽器在開啟選擇對話框
   當下讀取的靜態屬性,不是能在單一 input 上依點擊情境動態開關的
   東西(不透過整個替換 DOM 節點的話)。因此比照真實產品常見做法
   (例如 Google Drive 分別提供「上傳檔案」與「上傳資料夾」兩個
   獨立入口),用兩個各自標籤清楚的 `<input>`。兩者都呼叫同一個
   `handleFilesSelected`,累加進同一個 `selectedFiles` 陣列——資料夾
   選出來的檔案本質上就是 `File` 物件,對既有的預覽/移除/上傳/
   telemetry 管線而言完全不需要任何特殊處理。
2. **`webkitdirectory` 透過 callback ref 命令式設定,不是 JSX prop**
   ——React 內建的 `InputHTMLAttributes` 型別沒有收錄
   `webkitdirectory`(非標準、WebKit 前綴,但所有主流瀏覽器都支援)。
   沒有用 `any` 型別繞過(避免打開一個型別安全的破口),改用
   callback ref 在節點掛載當下直接賦值——比 `useEffect` 少一次
   render round-trip,也不需要任何型別斷言。
3. **`displayName(file)` 優先採用 `file.webkitRelativePath`,退回
   `file.name`**——只有資料夾選取產生的 `File` 才會有非空的
   `webkitRelativePath`;個別選取的檔案(S011/S012 既有流程)行為
   完全不變,純粹是新增的判斷分支,不影響既有路徑。保留相對路徑
   (而非攤平成純檔名)是因為選取整個資料夾樹狀結構時,不同子資料夾
   下可能存在同名檔案——不保留路徑會讓預覽清單與最終文件列表出現
   視覺上無法分辨的重複項目。文件 `name` 欄位本來就是自由格式字串
   (見 `knowledge-documents.ts` 自己的既有欄位設計),帶路徑的名稱
   仍然只是一個字串,不需要任何 lib 層或資料結構變更。
4. **`aria-label`/`移除 {name}` 等既有可及性機制,一併套用
   `displayName()`,不只套用在純顯示文字上**——確保資料夾底下
   兩個同名檔案(不同子資料夾)不只在畫面上看得出差異,對應的
   「移除」按鈕 accessible name 也能互相區分,維持 S012 已建立的
   「多檔案時每個移除按鈕都可個別定位」保證。

## 開發過程中的技術發現(FIX 循環,1 次,Playwright API 限制)

E2E 測試第一次嘗試時,對「上傳資料夾」input 呼叫
`setInputFiles([{name, mimeType, buffer}, ...])`(與 S011/S012 對
一般檔案 input 的既有寫法相同)直接被 Playwright 自己拒絕:
`[webkitdirectory] input requires passing a path to a directory`——
Playwright 對 `webkitdirectory` input 有特殊限制,只接受一個真實
存在的資料夾路徑(字串),不接受記憶體中的 File-like 物件清單,
它會自己讀取該路徑底下的真實檔案來驅動選取。

這個限制反而讓測試變得**更好**而非更差:改用 Node 的
`fs.mkdtempSync` 建立一個真實的臨時資料夾(內含一個根目錄檔案與
一個子資料夾內的巢狀檔案),把路徑交給 `setInputFiles(dir)`——這樣
Playwright 會在真實的 Chromium 瀏覽器中執行真正的資料夾選取,產生
**真正非空的 `webkitRelativePath`**,不是模擬出來的。這是單元測試
(jsdom 沒有真實檔案系統可供瀏覽器走訪,只能用
`Object.defineProperty` 手動指定 `webkitRelativePath`)與原本
buffer-based E2E 寫法都做不到的——E2E 現在能真正驗證「選取一個
真實資料夾樹狀結構,相對路徑(含子資料夾)被正確保留並顯示/上傳」
這件事在真實瀏覽器裡的實際行為,不只是單元測試模擬出來的行為。
測試最後在 `finally` 區塊清理臨時資料夾,避免在 CI runner 上留下
殘留檔案。修正後從 VERIFY 第一個 gate 重新完整跑過
(typecheck→lint→unit→build→E2E),符合 STORY_WORKFLOW Phase 4 規則。
