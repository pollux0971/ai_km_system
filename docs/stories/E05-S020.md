# E05-S020 — Processing failure state

- 狀態:APPROVED
- Branch:story/E05-S020-processing-failure-state
- 日期:2026-08-15

## Scope 說明

E05 的第二十個 story,也是 S017/S018/S019(upload→parse→index 暫態
進度序列)三個 story 從一開始就明確預告、刻意延後的那個 story。與
S001-S019 相同情況:SOURCE_BASELINE.md 對 E05 只有一份扁平標題清單,
本 story 在 epic 檔中只有標題,無進一步內文。已讀過 epic 檔本 story
自己的章節(line 4002-4211,前一節「Index progress」於 line
3792-4001,下一節「Retry processing action」於 line 4212 開始),並用
`diff` 直接逐字比對本 story 章節與 S019 章節的內文(排除 H1 標題與
「User / System Value」段落唯一的 story 名稱代換),確認兩者逐字
相同,是通用 MVP 樣板文字,無本 story 專屬內容。

**這是三個「progress」story(S017/S018/S019)一路刻意迴避、明確留給
本 story 的東西**:S017-S019 的 EVIDENCE 都各自記錄了同一個判斷——
「progress」是暫態的單次操作內顯示,不持久化;「state」(本 story
標題)才是持久化狀態該進場的地方。本 story 正式替
`KnowledgeBaseDocument` 新增第一個持久化的 `status` 欄位。

## 設計決策

1. **`status` 欄位選填,缺席代表「ready」,只有明確失敗時才寫入
   `"failed"`**——延續這個型別上每個選填欄位一致的「缺席=常見/
   預設狀態」慣例(`sizeBytes`/`content`/`folderSyncEnabled` 皆是
   同一套邏輯)。所有 S011-S019 建立的既有文件(含 4 筆種子資料)
   完全不需要回填,天然維持「ready」語意。
2. **新增 `MOCK_DOCUMENT_PROCESSING_FAILURE_TRIGGER =
   "[模擬:KB_PROCESSING_FAILED]"`,檢查邏輯放在
   `addKnowledgeBaseDocument` 內部**——延續 E03-S021
   (`MOCK_ANSWER_STATE_TRIGGERS`)/E03-S029
   (`MOCK_FILE_PROCESSING_FAILURE_TRIGGER`)已建立的既有慣例:沒有
   真實後端可以回報處理失敗,加入這個決定性 mock 觸發機制是唯一
   能讓失敗路徑真正透過 UI 可達、可測試的方式,而非只是理論上寫在
   程式碼裡但永遠碰不到。故意選用與 E03 自己的常數不同的字串
   (`KB_PROCESSING_FAILED` 而非沿用 E03 的
   `PROCESSING_FAILED`)——雖然兩者分屬完全獨立的程式碼路徑不會
   真的衝突,但用不同字串可讓未來 grep 這個 marker 時不會混淆
   兩個不同領域的觸發器。
3. **`addKnowledgeBaseDocument` 觸發到 marker 時仍然回傳
   `ok: true`,只是建立出的文件帶 `status: "failed"`**——這是本
   story 最核心的設計判斷:與 S011 既有的 empty-name/NOT_FOUND
   失敗(`ok: false`,完全沒有文件被建立,S017-S019 既有的「失敗
   則跳過解析/索引、保留檔案供重試」邏輯就是為這種情況設計的)是
   兩種本質不同的失敗——「上傳失敗」代表文件記錄根本沒被建立;
   「處理失敗」代表文件記錄確實被建立了,只是(模擬的)後續處理
   結果是失敗,鏡射真實非同步處理管線「上傳當下就成功回應,處理
   結果要等管線真的跑完才知道」的行為模式。
4. **`KnowledgeDocumentUpload` 的既有上傳→解析→索引迴圈完全不需要
   修改**——因為 `result.ok` 對一個「即將處理失敗」的文件仍然是
   `true`,程式碼自然而然會走完整個既有的三階段流程(見設計決策
   #3);唯一新增的是:一旦知道 `result.value.status === "failed"`,
   多發一則獨立的 `knowledge_base_document_processing_failed`
   telemetry(與既有的 success 事件共用同一個 correlationId——上傳
   真的成功了,這是關於同一次操作的第二個、獨立的事實,不是否定
   前者)。
5. **失敗指示器(「處理失敗」純文字)畫在 `knowledge-document-list.tsx`,
   不是 `knowledge-document-upload.tsx`**——本 story 新增的是文件
   本身的持久化屬性,自然該由渲染文件清單的元件負責顯示,不是負責
   「新增」動作的上傳元件;上傳元件的角色只到「新增文件+回報
   telemetry」為止,不涉及清單如何呈現。
6. **只有純文字指示器,不含任何重試操作**——UX Acceptance 明確
   要求「不得只靠顏色傳達狀態」,純文字滿足這點,無需額外視覺
   設計;重試功能是 E05-S021「Retry processing action」自己的
   later story,本 story 的界線就停在「讓失敗狀態存在且可見」。
7. **只擴充 `addKnowledgeBaseDocument`(檔案上傳路徑),不擴及
   `addKnowledgeBaseDocumentFromUrl`/`addKnowledgeBaseDocumentFromText`**
   ——延續 S017/S018/S019 一路建立的「只擴充檔案上傳元件」範圍
   界線;額外的語意理由:文字輸入(S015)的內容就是使用者直接打的
   字,沒有「處理」這個步驟可能失敗;URL 匯入(S014)本身完全不做
   真實擷取,替一個不做任何真實事情的 mock 疊加處理失敗語意會是
   mock 之上疊 mock,意義不大。若未來某個 story 需要替 URL 匯入
   也加上處理失敗語意,那該是它自己明確論證的範圍,不是本 story
   順手夾帶。
