## 設計決策

1. **重試成功後一律確定性地清空 `status`(變回 ready),不重新
   評估 `MOCK_DOCUMENT_PROCESSING_FAILURE_TRIGGER`**——這是本 story
   最核心的設計判斷。文件的 `name` 在重試過程中不會改變,若重試
   邏輯重新對同一個 name 跑一次同樣的觸發字串檢查,會導致「凡是
   靠 marker 產生的失敗文件,永遠不可能重試成功」這種荒謬結果,
   讓整個重試功能形同虛設。改用「使用者主動點擊重試,視為
   (模擬的)根本原因已被視為解決」的語意——與本 story 自己 epic
   樣板文字中「MVP 可以簡化視覺或演算法,但此能力本身不可缺席」
   的允許範圍一致:這是刻意的簡化,不是遺漏,且明確記錄於
   doc comment,任何未來想加上「重試也可能再次失敗」擬真度的人
   有清楚的起點可以參考。
2. **`retryDocumentProcessing` 新增為獨立函式,驗證文件存在
   (`NOT_FOUND`,含跨知識庫防呆)且目前確實是 `"failed"`
   (否則 `VALIDATION_ERROR`)**——延續本模組既有的 fail-closed
   紀律(`addKnowledgeBaseDocument` 自己的 NOT_FOUND 檢查是直接
   先例);「不允許重試一個根本沒壞的文件」是有意義的防呆,不是
   過度設計。
3. **`retryDocumentProcessing` 本身零延遲,視覺延遲交給呼叫端**
   ——與 `addKnowledgeBaseDocument` 自己零延遲、由
   `KnowledgeDocumentUpload` 呼叫端編排延遲的既有分工完全一致。
   重試呼叫端重用既有的 `simulateParseStep`/`simulateIndexStep`
   (E05-S018/S019),不新增第四個計時原語檔案——重試在概念上是
   重跑解析與索引(文件本身、檔案本身都已經存在,不是重新上傳)。
4. **新增獨立元件 `KnowledgeDocumentRetryButton`,每個失敗文件一個
   實例,而非把邏輯內嵌進 `knowledge-document-list.tsx`**——這個
   路由既有的組成方式本來就是「每個獨立互動各自一個小元件,由
   `knowledge-document-list.tsx` 組裝」(上傳/URL 匯入/文字輸入
   三個既有元件皆是此形狀),重試按鈕延續同一個架構慣例,而非
   讓原本單純的清單渲染元件承擔新的 pending/error 狀態管理。
5. **`onRetried` 直接重用既有的 `refetchDocuments`**——與上傳/
   URL 匯入/文字輸入三者共用同一個回呼是同一種「清單改變了」
   事件,不需要新的專屬回呼機制。
6. **Telemetry 包含 `documentId`(純識別碼),不包含文件名稱**——
   延續 S011/S014/S015/S017 一致的「不記錄自由格式使用者內容」
   克制。
