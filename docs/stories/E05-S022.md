## 設計決策

1. **只有文字輸入(S015)來源的文件有真實 `content` 可預覽;檔案
   (S011-S013)與 URL 匯入(S014)來源的文件明確顯示「此文件目前
   無法預覽。」,不假造內容**——直接延續本story鏈從 S011 起一路
   堅持的「不假裝擁有不存在的資料」原則(`sizeBytes`/`content`
   兩個欄位各自的選填理由早已建立這個先例)。檔案上傳從未真的讀取
   位元組、URL 匯入從未真的擷取任何內容,兩者都沒有真實內容可以
   誠實地拿來預覽。
2. **新增獨立元件 `KnowledgeDocumentPreview`,每個文件一個實例
   (不限失敗文件)**——延續本頁「每個獨立互動各自一個小元件」的
   既有組成方式(上傳/URL 匯入/文字輸入/重試按鈕皆是此形狀)。
3. **不新增 lib 函式,`content` 直接由父元件當作 prop 傳入**——
   因為根本不需要新的資料存取,見 Scope 說明。這也是為什麼本
   story 沒有 NOT_FOUND/VALIDATION_ERROR 之類的 fail-closed 路徑
   ——沒有一個可能因輸入不合法或資源不存在而失敗的操作。
4. **Telemetry 只有單一 `knowledge_base_document_preview_viewed`
   事件,不是 attempt/success/failure 三件組,且每次展開都會發送
   (不是只有第一次)**——因為這是「檢視」互動而非「變更」操作,
   沒有成功/失敗的區分;鏡射本應用既有的 `page_view`(E01-S019)
   「每次真的發生都記錄,不是只記錄一次」語意,而非把收合後重新
   展開當成需要去重的重複事件。收合本身不發任何 telemetry(只有
   展開才代表使用者真的看了內容)。
5. **`aria-expanded` 反映展開狀態,按鈕文字也隨之改變
   (「預覽」/「收合預覽」)**——標準的 disclosure widget
   可及性模式,狀態變化同時透過文字與 ARIA 屬性傳達,不只靠外觀。
6. **內容用 `<pre style={{whiteSpace: "pre-wrap"}}>` 呈現,保留
   原始換行**——使用者在 S015 輸入的文字本來就可能有多行,原樣
   呈現才是真正的「預覽」,不是重新格式化過的近似值。

## 開發過程中的技術發現(1 次 FIX 循環)

**根因**:自己新增的測試「shows the real stored content, verbatim,
when expanded」使用了 RTL 的自訂函式 matcher
(`getByText((_, element) => element?.textContent === "第一行\n第二行")`)
來驗證換行符確實保留——但這個 matcher 對「每個」textContent 符合
條件的元素都會比對到,而 `<pre>` 與其外層 `<div>` wrapper 的
textContent 剛好完全相同,導致 `TestingLibraryElementError: Found
multiple elements` 崩潰。這是測試撰寫本身的疏漏(matcher 不夠
精確),不是元件實作的錯誤——元件本身的換行保留行為是正確的,只是
驗證方式選錯了斷言目標。

**修法**:改用 `document.querySelector("pre")` 直接鎖定唯一的
`<pre>` 元素,斷言其 `textContent` 恰好等於預期字串(含真實換行
符),而非依賴 RTL 的文字 matcher 在多層巢狀元素間做選擇。修正後
重跑,測試通過且斷言的精確度沒有降低(依然直接驗證真實換行符
存在)。

## Assumptions / 計畫外事項

1. **只有文字輸入來源的文件有真實內容可預覽,檔案/URL 來源誠實
   顯示無法預覽**——見設計決策 #1,延續本 story 鏈從 S011 起一路
   堅持的原則。

   story 與先前每個 story 相比架構上明顯更簡單的原因。
3. **Telemetry 每次展開都發送,不是只發送一次**——見設計決策 #4
   的完整理由。
4. **本 story 零 fail-closed 路徑**——因為沒有一個操作可能失敗,
   誠實記錄於 AC 對照表與 Gate 紀錄的 L4 段落。
