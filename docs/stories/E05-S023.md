## Scope 說明

E05 的第二十三個 story。與 S001-S022 相同情況:SOURCE_BASELINE.md 對
E05 只有一份扁平標題清單,本 story 在 epic 檔中只有標題,無進一步
內文。已讀過 epic 檔本 story 自己的章節(line 4632-4841,前一節
「Document preview」於 line 4422-4631,下一節「Document version
history」於 line 4842 開始),並用 `diff` 直接逐字比對本 story 章節
與 S022 章節的內文(排除 H1 標題與「User / System Value」段落唯一的
story 名稱代換),確認兩者逐字相同,是通用 MVP 樣板文字,無本 story
專屬內容。

**範圍界定**:`KnowledgeBaseDocument` 目前只有 `name` 這一個欄位
同時符合「真的是描述性中繼資料」與「使用者有意義地可編輯」兩個條件
——`sizeBytes`/`content` 是衍生值或原始內容本身,`status` 是系統
管理的處理狀態,`uploadedAt` 是不可變的歷史事實。因此本 story 的
範圍就是「重新命名文件」,不發明額外的中繼資料欄位(標籤、描述、
分類等 SOURCE_BASELINE 從未提及的概念)。

**設計上直接鏡射既有先例**:`RenameConversation`(E03-S024)是本
codebase 已經建立、已核准的「單一文字欄位重新命名」元件,形狀與本
story 的需求幾乎完全相同(view/edit 切換、draft 狀態、空白時
disabled 儲存按鈕、失敗時通用錯誤訊息)。本 story 沒有從零設計一個
新模式,而是逐項比對後直接複用同一套已驗證過的互動邏輯。

## 設計決策

1. **新增 `renameKnowledgeBaseDocument`,驗證邏輯與
   `retryDocumentProcessing`(E05-S021)的跨知識庫防呆 NOT_FOUND
   檢查相同,空白名稱驗證與 `renameConversation`(E03-S024)相同**
   ——不是重新發明驗證邏輯,是重用兩個已核准 story 各自已經解決過
   的問題的組合。
2. **新增獨立元件 `KnowledgeDocumentNameEditor`,逐項比對
   `RenameConversation` 的狀態形狀(`name`/`isEditing`/`draftName`/
   `pending`/`error`)、函式命名(`startEditing`/`cancelEditing`/
   `handleSubmit`)、與互動細節(儲存按鈕在草稿空白時 disabled、
   成功後採用伺服器回傳值而非本地草稿、取消後重新開啟編輯會從
   目前值而非被捨棄的草稿重新開始)**——刻意逐項複製這個已核准
   story 的設計判斷,而非只在概念上相似卻各自為政。
3. **顯示層用 `<h1>` 換成不帶語意的元素(本 story 選用單純的
   `<strong>`,搭配 React Fragment 而非額外包一層 `<span>`)**——
   `RenameConversation` 的 `<h1>` 是頁面自己唯一的標題,本 story的
   情境是「清單中每一列各自的名稱」,不是頁面標題,用 `<h1>` 會
   在一個頁面產生多個同語意標題,對輔助技術是誤導;改用
   Fragment(而非 `<span>`包裝)是為了不在 DOM 中插入這個元件
   出現之前就不存在的額外巢狀層級,維持與這個清單其他手足元件
   (`KnowledgeDocumentRetryButton` 等)一致的「回傳 Fragment,不
   額外包一層容器元素」慣例。
4. **失敗時顯示與 `RenameConversation` 完全相同的通用錯誤訊息
   「重新命名失敗，請稍後再試。」,不是 S014/S016/S021 那種具體
   伺服器訊息**——刻意的、有明確理由的選擇,而非隨意的不一致:
   儲存按鈕本身已經在草稿空白時 disabled,把最常見的失敗情境
   (空白名稱)排除在使用者能真的送出的路徑之外;因此真正能送達
   伺服器並失敗的路徑只剩 NOT_FOUND 這種罕見情境(例如文件已在
   另一個分頁被刪除)——沒有使用者能針對性採取行動的具體資訊,
   通用措辭與 `RenameConversation`/`ModeSwitch`/`ModelSelector`
   已建立的既有選擇一致。這與 S014(URL 格式錯誤,常見且使用者
   能立刻修正)、S016(啟用時忘記填路徑,常見)、S021(NOT_FOUND/
   VALIDATION_ERROR 皆可能是使用者真的會遇到的日常情境)刻意
   顯示具體訊息的判斷並不矛盾——兩者背後是同一套原則(「client
   端已擋掉的常見情境 vs. 真正會送達伺服器的情境」),只是套用
   在不同 story 各自的實際情境會得出不同結論。

## 開發過程中的技術發現

**在實作階段(執行 gate 之前)就發現並修正的結構性問題,非正式
FIX 循環**:一開始撰寫 `KnowledgeDocumentNameEditor` 時,兩個
return 分支各自用 `<span>` 包裝內容。在撰寫 E2E 測試時意識到:
`knowledge-document-list.tsx` 既有(S022 已核准)的測試用
`page.getByText(檔名).locator("..")` 取得文件名稱文字節點的
「父元素」來限定後續查詢範圍(例如限定在同一個文件項目內尋找
「預覽」按鈕)——這個既有慣例假設檔名文字的直接父元素就是
`<li>`。若 `KnowledgeDocumentNameEditor` 用 `<span>` 包裝,會在
DOM 中插入一層新的巢狀元素,讓 `.locator("..")` 改為找到這個新的
`<span>`(而非 `<li>`),導致既有 S022 測試的後續查詢(在
`fileDocItem`/`textDocItem` 範圍內尋找「預覽」按鈕)找不到,因為
「預覽」按鈕實際上是 `<li>` 的子元素、`<span>` 的手足元素,不在
新的(過窄的)查詢範圍內。**在執行任何 gate 之前**,把兩個 return
分支的 `<span>` 改為 React Fragment(`<>...</>`),讓
`KnowledgeDocumentNameEditor` 的輸出直接是 `<li>` 的子元素,不
插入額外巢狀層級——這同時也是與清單中其他手足元件
(`KnowledgeDocumentRetryButton`)一致的既有慣例。修正後完整重跑
全部 gate,S022 既有測試與本 story 新增測試皆一次通過,證實修法
正確且未在既有測試上留下任何回歸。
