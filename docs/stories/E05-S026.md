## 設計決策

1. **`deleteKnowledgeBaseDocument(knowledgeBaseId, documentId)` 真實
   從 store 移除,不是軟刪除/封存旗標**——與 `deleteConversation` 同
   理由:S025「Archive document action」已經是獨立存在的可逆能力,
   「封存」與「刪除」在本 codebase 是刻意分開的兩種能力,不因本
   story 而混淆。NOT_FOUND fail-closed 涵蓋:文件不存在、文件存在但
   屬於別的知識庫(跨庫防呆,與 `archiveKnowledgeBaseDocument`/
   `retryDocumentProcessing`/`renameKnowledgeBaseDocument` 同一套
   檢查)、對同一個已刪除 id 的第二次刪除(直接鏡射
   `deleteConversation` 自己的「重複刪除同一 id 第二次正確 NOT_FOUND」
   既有測試,對應 Functional AC 5「重複請求不得造成未定義重複 side
   effect」)。
2. **不像 `deleteConversation`→`DeleteConversation` 那樣串接一個
   cascade 步驟**——`deleteConversation` 成功後,呼叫端
   `DeleteConversation` 會接著呼叫 `deleteMessagesForConversation`,
   因為一個對話底下有屬於它的訊息這個子實體。`KnowledgeBaseDocument`
   沒有這種子實體:`content`/`status`/`sizeBytes`/`archived` 全部是
   文件記錄自己的欄位,不是另外儲存、只能透過文件間接存取的資料。
   刪除記錄本身就是整個操作,`deleteKnowledgeBaseDocument`
   自己的 doc comment 明確記錄這個差異的理由,而非略過不提。
3. **`KnowledgeDocumentDeleteButton` 不像 `DeleteConversation` 那樣用
   `useRouter` 在成功後導覽離開**——`DeleteConversation` 活在對話
   自己的詳情頁上,刪除後那個頁面對應的資料已經不存在,必須
   `router.replace("/conversations")` 離開一個即將變成死路由的頁面。
   本元件活在 `knowledge-document-list.tsx` 的清單項目裡,刪除後
   沒有「這個頁面」需要離開——文件列表頁本身還是有效的,只是這一項
   該從清單中消失。`onDeleted` 直接複用這個頁面上每個會改變清單的
   元件(上傳/URL匯入/文字新增/重試/封存)早已共用的同一顆「清單
   變了」callback,呼叫的是同一個 `refetchDocuments`——連帶自動享有
   S025 獨立審核 MAJOR 修正後的 `viewingArchivedRef` 行為(見
   `docs/stories/E05-S025.md` 設計決策 #3),不需要為本 story 再處理
   一次同樣的 race condition。
4. **確認對話框的可存取名稱直接帶入文件名稱
   (`確認刪除文件：${name}`),不是只在可見的 `<p>` 內文裡才提到**
   ——直接沿用 `DeleteConversation` 自己已經修正過的版本(該元件
   初版的可存取名稱本來也只有通用文字,是 E03-S025 獨立審核時的
   MINOR 發現才加上具體對話標題),從一開始就採用已修正過的正確
   形狀,而非重新從「先寫通用名稱」的起點出發再被抓到同一個問題。
5. **刪除按鈕在作用中與已封存兩個視圖都會渲染,不像三個新增元件
   只在作用中視圖顯示**——刪除是「永久移除」,對一份已經封存(暫時
   收起來)的文件仍然是合理、使用者可能會做的操作;限制成只能在
   作用中視圖刪除,會讓使用者必須先取消封存才能刪除一份他已經不想
   要的舊文件,徒增不必要的步驟。`deleteKnowledgeBaseDocument` 自己
   的 doc comment 明確記錄「封存」與「刪除」是刻意保持正交、互不
   限制的兩種能力。

## Assumptions / 計畫外事項

1. **不做 cascade 刪除**——見設計決策 #2,`KnowledgeBaseDocument`
   沒有子實體,與 `deleteConversation`→`deleteMessagesForConversation`
   的情況不同。
2. **不做導覽離開**——見設計決策 #3,本元件活在清單項目裡,不是
   詳情頁,沒有「這個頁面」需要離開。
3. **刪除按鈕在兩個視圖都顯示,不像三個新增元件限制在作用中視圖**
   ——見設計決策 #5,封存與刪除是刻意正交、互不限制的兩種能力。
4. **確認對話框的可存取名稱從一開始就帶入文件名稱**——見設計決策
   #4,直接沿用 `DeleteConversation` 自己已修正過的版本,不重新
   從有缺陷的起點出發。
