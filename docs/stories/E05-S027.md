重試/預覽皆是如此),不是重新發明。

## 設計決策

1. **`KnowledgeBaseDocument` 新增選填欄位 `visibleToRoles?: Role[]`,
   語意與 `KnowledgeBaseSummary.visibleToRoles`(S006)完全相同**——
   缺席代表「尚未設定」,與明確存的空陣列(「刻意不開放給任何角色」)
   是兩種不同狀態,對權限類欄位這個區分有意義(不像
   `archived?: boolean` 那種缺席即視為 `false` 即可)。是與知識庫層級
   `visibleToRoles` 並存的「文件層級覆寫」,不是取代它——一份文件
   可以獨立設定自己的可見角色,不需要透過知識庫本身。
2. **`updateKnowledgeBaseDocumentVisibleRoles` 一次送出完整的新角色
   清單,不是單一新增/移除**——與 `updateKnowledgeBaseVisibleRoles`
   同一套理由:呼叫端回報「現在勾選的狀態」,不對前一次選擇做 diff。
   沒有 VALIDATION_ERROR 分支——空陣列是合法、有意義的狀態(刻意
   不開放給任何角色),不是驗證錯誤。NOT_FOUND fail-closed 涵蓋文件
   不存在、文件存在但屬於別的知識庫,與本檔案其餘 targeted-by-id
   mutation 同一套跨庫防呆邏輯。
3. **`KnowledgeDocumentPermissionEditor` 不像其他 mutating 手足元件
   (封存/刪除)那樣接收一個 `onXxx` callback 通知父層重新整理**——
   權限變更不會改變這份文件屬於哪個「視圖」(不像封存/刪除),也
   不影響清單渲染的其他任何欄位(不像重新命名),元件自己接住
   mutation 的回傳值、自己反映最新已存狀態就已經完整,與
   `KnowledgeDocumentNameEditor` 完全不接收 callback 的既有先例
   (只接收 `initialName` prop)同一種形狀。有一個獨立測試直接證明
   這個設計判斷屬實(儲存權限不會觸發任何 `listKnowledgeBaseDocuments`
   重新呼叫)。
4. **權限編輯器在作用中與已封存兩個視圖都會渲染**——與刪除按鈕
   (S026)同一套理由:權限設定與封存狀態是正交的兩個維度,不應該
   因為文件被封存就無法調整它的權限。
