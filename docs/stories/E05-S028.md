## 設計決策

1. **不新增任何 lib 函式或欄位**——`knowledge-detail.tsx` 已經在呼叫
   `listKnowledgeBaseDocuments(id)`;本 story 只是多呼叫一次
   `listKnowledgeBaseDocuments(id, true)`(S025 既有的 `archived`
   視圖參數)取得已封存清單,並對既有回傳的文件陣列做用戶端
   `.filter()`/`.length` 聚合——這是本 session 至今第二個「零 lib
   變更」的 story(第一個是 S022 Document preview),用
   `git diff -- apps/web/src/lib/ | wc -l` 可獨立複驗為 0。
2. **兩個 fetch 用 `Promise.all` 平行執行,不是循序**——彼此沒有
   相依關係(都只需要 `knowledgeBase` 已確認存在這個前提,不互相
   依賴對方的結果),循序執行只會多等一輪 round-trip 時間卻沒有
   任何好處。
3. **兩個新統計數字各自獨立降級為「－」,不因為其中一個 fetch 失敗
   就波及另一個或整頁**——完全複用 `documentCount` 自己已經建立的
   「次要 fetch 失敗不該讓整頁報錯」既有先例,只是延伸到兩個獨立
   的欄位,各自獨立追蹤成功/失敗。
4. **標籤文字選用「處理失敗文件數:」/「已封存文件數:」,不是
   「處理失敗文件:」/「已封存文件:」**——在實作階段(撰寫 E2E
   測試前)自行發現:若省略「數」字,這兩個新標籤的文字尾端恰好
   是「文件:」,與既有的「文件:」標籤形成子字串包含關係,會讓
   `tests/e2e/specs/knowledge-documents.spec.ts` 裡大量既有的
   `page.getByText("文件:", { exact: false })`(共 19+ 處)從「精準
   比對 1 個元素」變成「同時比對 3 個元素」,導致 Playwright strict
   mode violation、讓一大批既有、與本 story 完全無關的 E2E 測試
   全部壞掉。用 `node -e` 寫小腳本直接驗證 `"處理失敗文件數:".
   includes("文件:")` 為 `false`,確認修正後的字串真的安全,而非
   憑感覺猜測。**這個問題在執行任何 gate 之前就被發現並修正,不是
   正式 FIX 循環**,但影響範圍夠大(19+ 個既有測試),值得在此
   明確記錄檢查過程。
