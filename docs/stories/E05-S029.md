E05 只有一份扁平標題清單,本 story 在 epic 檔中只有標題,無進一步

**設計上直接鏡射既有先例,但先找對正確的先例**:一開始考慮過
`message-content.tsx` 的 `CitationBadge`(`[1]` 這種 `<sup>` 引用
標記),但讀過該檔案完整原始碼後確認那是完全不同性質的「標記」
(inline citation marker),不是「狀態指示」;真正對應的先例是
`message-thread.tsx` 自己已經建立的「用 `<span role="alert">`(失敗/
需注意狀態)與 `<span role="status">`(良性/資訊性狀態)呈現各種
訊息狀態」既有慣例(`AI 回覆失敗`/`ANSWER_STATE_LABELS`/`複製失敗`
皆用 `role="alert"`;`檔案處理中…`/`AI 回覆中…` 皆用 `role="status"`)
——這個既有慣例裡,`message-thread.tsx` 從來沒有一個明確的「一切
正常」badge:badge 的「缺席」本身就代表「沒有需要注意的事」,只有
真正偏離正常狀態時才會出現 badge。

## 設計決策

1. **既有「處理失敗」文字指示器(S020)升級為 `<span
   role="alert">`**——目前 `apps/web/src/app/(app)/knowledge/[id]/
   documents/_components/knowledge-document-list.tsx` 裡這個指示器
   從 S020 建立以來就是純文字 `<span>`,完全沒有 ARIA role,與
   `message-thread.tsx` 對同類「處理失敗/需注意」狀態一律使用
   `role="alert"` 的既有慣例不一致——這是本 story 真正要修的落差。
   只加屬性,不改文字內容,既有 `getByText("處理失敗")` 系列測試
   (S020/S021)完全不受影響。
2. **新增「已封存」`<span role="status">` badge,每份已封存文件都會
   顯示**——這是目前完全空缺的一塊:一份文件被封存後(S025),
   清單項目本身沒有任何專屬指示——唯一得知「這是已封存文件」的
   方式是使用者自己記得剛才點了頁面層級的「已封存文件」切換按鈕。
   `role="status"`(不是 `role="alert"`)因為「已封存」是良性、
   資訊性的狀態,不是需要使用者注意的錯誤——與 `message-thread.tsx`
   把 `role="status"` 保留給良性狀態(`傳送中…`)、`role="alert"`
   保留給錯誤狀態的既有區分完全一致。
3. **刻意不新增「就緒」badge**——見 Scope 說明,`message-thread.tsx`
   自己從未對一則正常結算的訊息顯示明確的「成功」badge,badge
   缺席即代表正常;新增一個「就緒」badge 會打破這個既有慣例,而非
   遵循它。
4. **「已封存」badge 在已封存視圖裡技術上是多餘的**(該視圖裡每一
   項本來就都是已封存文件,見 `listKnowledgeBaseDocuments` 的
   `archived` 參數語意)——刻意保留,理由與加 `role="alert"`/
   `role="status"` 本身完全相同:提供明確、逐項的狀態溝通,不依賴
   使用者記得先前在頁面層級點過的切換按鈕狀態,對逐項瀏覽的螢幕
   閱讀器使用者尤其重要。

## 開發過程中的技術發現(正式 FIX 循環)

**唯一一次真正的 FIX 循環**(gate 真的變紅,不是執行 gate 之前就
發現並修正的問題):完整重跑 `pnpm test` 時,`@ai-km/e2e` 的既有
(S020,已核准)測試「a file whose processing is mock-triggered to
fail still uploads successfully, but shows 處理失敗 in the list」
失敗:

```
Error: expect(locator).not.toBeVisible() failed
Locator:  getByRole('main').getByRole('alert')
Expected: not visible
Received: visible
14 × locator resolved to <span role="alert">處理失敗</span>
```

**根因**:該既有測試(line 499)原本用
`page.getByRole("main").getByRole("alert")` 確認「這個情境不該出現
上傳元件自己的通用『N 個檔案上傳失敗』重試提示 alert」(該提示與
「上傳成功但處理失敗」是兩條不同、互斥的路徑,S020 EVIDENCE 早就
記錄過這個區分)。這個查詢在 S029 之前是安全的,因為當時頁面上
唯一可能出現的 `role="alert"` 就是那個通用提示本身。設計決策 #1
讓「處理失敗」指示器自己也變成 `role="alert"`,使這個查詢從「精準
確認『通用提示』不存在」變成「確認『任何 alert』都不存在」——但
在這個情境下,「處理失敗」本身現在就是一個真實、合理的 alert,
會使這個既有斷言必然失敗。

**修法**:把斷言改為直接比對通用提示自己的具體文字模式
(`page.getByText(/個檔案上傳失敗/)`),不再依賴 role 本身的存在與否
——這樣無論「處理失敗」指示器有沒有 `role="alert"`,斷言都精準比對
它原本真正要確認的東西(通用提示的具體文案),不會再被本 story 新增
的、合理存在的第二個 alert 影響。修正後從 VERIFY 第一個 gate
(typecheck)重新完整跑過一輪,不只重跑失敗的那一個 E2E 測試。

**是否有其他既有測試受到同樣影響?** 逐一搜尋整個
`knowledge-documents.spec.ts`/`knowledge-detail.spec.ts` 裡所有
`getByRole("alert")`/`alert` 相關的既有斷言(共檢查 5 處),確認
只有這一處(line 499)是「確認 alert 不存在」的否定斷言、且情境
恰好會出現一份失敗文件;其餘皆是「確認特定文字內容的 alert 存在」
的肯定斷言(S014 的網址驗證錯誤、S026 的
`role="alertdialog"`),情境裡都沒有失敗文件,不受影響。也確認
`knowledge-document-upload.test.tsx` 這類單元測試是獨立渲染
`KnowledgeDocumentUpload` 本身(不經過
`knowledge-document-list.tsx`),本 story 新增的 badge 根本不在那些
測試的渲染樹裡,同樣不受影響。
