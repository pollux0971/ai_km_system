## Scope 說明

E05 的第三十個 story。與 S001-S029 相同情況:SOURCE_BASELINE.md 對
E05 只有一份扁平標題清單,本 story 在 epic 檔中只有標題,無進一步
內文(line 6102-6311),通用 MVP 樣板文字,無本 story 專屬內容。

**本 codebase 完全沒有既有的多選/批次操作先例**——開工前先確認過:
逐一讀過 `conversation-list.tsx`/`knowledge-list.tsx`/
`knowledge-document-list.tsx` 三個既有清單頁面的完整原始碼,全 repo
搜尋 `type="checkbox"` 的每一處使用(共 4 處),確認全部都是「一個
實體自己的多值屬性 checkbox 群組」(如 S006 的角色權限、S027 的
文件權限),不是「從清單中勾選多個項目」的那種多選;`packages/ui`
也沒有任何 `Checkbox`/`Toolbar`/`DataTable` 之類的共用元件可以借用。
因此本 story 的選取機制(checkbox-per-row、全選、條件式工具列)需要
從零設計,但可批次操作的「動作」本身(封存/刪除)直接沿用既有
單筆操作的既有函式,不是從零設計。

## 設計決策

1. **批次操作不新增任何新的 lib 函式**——沿用
   `KnowledgeDocumentUpload`(E05-S012「Multi-file upload」)已經
   為「一次操作、多個獨立項目」這個問題形狀建立的既有解法:在
   元件層用 `for...of` + `await` 循序呼叫既有的單筆函式
   (`archiveKnowledgeBaseDocument`/`unarchiveKnowledgeBaseDocument`/
   `deleteKnowledgeBaseDocument`),而不是新增
   `bulkArchiveKnowledgeBaseDocuments(ids)` 這種本檔案從未有過先例
   的批次 export。S012 自己的 doc comment 明確分析並拒絕了依賴
   microtask 排程巧合的平行呼叫方案,選擇循序;本 story 直接沿用
   同一個已經被驗證過的判斷,不重新推導一次。
2. **`selectedIds` 是 `Set<string>`,只在切換視圖或批次操作成功後
   清空**——一個被選取的 id 一旦視圖切換就可能根本不在新視圖裡
   (已封存/作用中是伺服器端過濾出的兩個互斥集合,不是同一份資料的
   不同呈現),留著過期 id 會讓「已選擇 N 份文件」這個數字與畫面上
   實際勾選的 checkbox 對不上;批次操作成功後同理,剛被封存/刪除的
   文件也不會再出現在目前視圖。
3. **全選 checkbox 不做三態(indeterminate)顯示,只在「目前視圖
   全部都被選取」時才勾選**——「MVP 可以簡化視覺」這條 AC 在此
   story 直接適用:三態需要额外的 ref 與 imperative DOM 操作(HTML
   checkbox 沒有宣告式的 indeterminate prop),對「部分選取」與
   「完全未選取」两種狀態的視覺區分價值不足以證成這個額外複雜度。
4. **批次封存/取消封存與批次刪除的「部分失敗」處理方式刻意不同,
   但背後是同一套原則**:`onCompleted` 只在「至少一筆真的成功」時
   才呼叫(直接沿用 S012 自己的 `if (anySucceeded) onUploaded()`
   寫法)——如果全部失敗,清單其實什麼都沒變,沒有東西需要重新整理
   或清空選取。批次刪除的確認對話框則是「不論部分或全部失敗,
   嘗試後一律關閉」——不像單筆刪除(S026)那樣失敗時停留在確認
   畫面讓使用者重試同一個操作,因為「重試整批」對批次操作沒有
   對應的單一、有意義的「重試」語意(已經成功的那些不該被重複
   處理);失敗筆數改成獨立於對話框之外的訊息,對話框關閉後仍然
   看得到。
5. **批次刪除的確認對話框訊息用筆數,不用檔名清單**——沿用單筆
   刪除(`KnowledgeDocumentDeleteButton`,S026)完全相同的
   `role="alertdialog"` 確認/取消結構,只把「確定要刪除「{name}」
   嗎」換成「確定要刪除這 {count} 份文件嗎」,因為批次情境下列出
   每個檔名會讓對話框過長且非本 story 的「thin slice」範圍要求。

## 開發過程中的技術發現(自我檢視時發現,執行任何 gate 之前修正)

**在完成第一版實作、執行 VERIFY 之前,自我檢視時主動分析「本 story
是否引入 S025 那種新的 race condition」**(延續 S026/S027/S028/S029
審核建立的習慣,DEV 階段本身就先做一次)時發現一個真實的縫隙:

`KnowledgeDocumentBulkActions` 這個工具列只在 `selectedIds.size > 0`
時才渲染。批次操作進行中(`for...of` 迴圈還在等待某一筆的
`await`)時,清單上每份文件的選取 checkbox 完全沒有被鎖定——使用者
可以在批次操作進行中把所有 checkbox 取消勾選,讓 `selectedIds`
變空,導致 `KnowledgeDocumentBulkActions` 這個元件本身被
unmount,而它自己那個還在執行中的迴圈仍會繼續跑完(JS 的 promise
不會因為元件 unmount 就取消)。若使用者接著重新勾選並再次點擊批次
按鈕,會啟動第二個、與第一個真正重疊執行的批次操作。

**嚴重度評估**:比 S025 的既有發現輕微(不會靜默弄錯畫面顯示的
視圖資料,mock 函式也沒有真實延遲,視窗極窄),但屬於同一類「新
功能讓既有元件可以在非同步操作進行中被 unmount」的風險,且 mock
延遲為零並不代表「不可能發生」,只代表「不容易被隨手手動測試
發現」——比照 S025 的處理標準,判定值得修正而非接受。

**修法**:新增 `onPendingChange(pending: boolean)` callback,由
`KnowledgeDocumentBulkActions` 在批次操作開始/結束時回報給父層;
`knowledge-document-list.tsx` 用這個訊號鎖定「全選」與每個文件的
選取 checkbox(`disabled={bulkActionPending}`),讓使用者在批次操作
進行中完全無法變更選取狀態,從根源關閉這個縫隙——與
`KnowledgePermissionEditor` 自己用 `disabled={pending}` 的
`<fieldset>` 鎖定所有 checkbox 防止競態的既有理由完全相同,只是
需要鎖定的元素(checkbox)活在父層,不是這個元件自己身上,所以
用一個 callback 把 pending 訊號往上傳一層。

新增 2 個單元測試直接驗證 `onPendingChange` 在批次封存與批次刪除
兩種操作開始/結束時都正確地依序回報 `true`/`false`;新增 1 個
整合測試在 `knowledge-document-list.test.tsx` 驗證父層真的用這個
訊號鎖定了每一個 checkbox(用可控制的 pending promise 精確驗證
「鎖定中」與「解除鎖定後」兩個時間點的狀態)。因為是在執行第一次
VERIFY 之前的自我檢視階段發現並修正,不計入正式 FIX 循環,但因為
修法本身有實質複雜度、且是本 session 第二次主動做「新 story 是否
重演 S025 那類 race condition」的專門分析並真的抓到問題,值得完整
記錄而非隱藏在一般設計決策段落裡。

## Assumptions / 計畫外事項

1. **批次操作零新增 lib 函式,循環呼叫既有單筆函式**——見設計
   決策 #1,直接沿用 S012 已建立的既有解法。
2. **全選 checkbox 不做三態(indeterminate)視覺**——見設計決策
   #3,MVP 簡化視覺的合理範圍。
3. **批次刪除的部分/全部失敗處理方式與批次封存不完全對稱(對話框
   一律關閉 vs. 只在有成功時才觸發 onCompleted)**——見設計決策
   #4,背後是同一套「有變化才需要重新整理/清空選取」原則,只是
   批次刪除多了「對話框沒有可對應的單一重試語意」這個額外考量。
4. **不做批次重新命名/批次權限設定**——這兩個既有的單筆操作
   概念上不適合批次化,非本 story 名稱明確要求的範圍。
5. **新增 `onPendingChange`/`bulkActionPending` 鎖定選取
   checkbox**——見「開發過程中的技術發現」,SELF-REVIEW 階段主動
   分析「本 story 是否重演 S025 的 race condition」時發現的真實
   縫隙,已修正並補上對應測試。
