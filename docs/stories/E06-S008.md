## 範圍

只做 PDF 文字抽取(`services/ingestion/src/extraction/`),不做 OCR、其他格式剖析、
batch import,也不碰 `services/retrieval`、`services/model-gateway`、
`services/rag-skeleton`。實際的 index-time 管線(parse→chunk→embed→store)
由 E06-S042 補上;本 story 只交付 `extractPdfText()` 這個純函式介面,
回傳的 `{ text, extractorVersion, pageCount }` 供 E06-S042 落庫時一起持久化。

## `@napi-rs/canvas`(optionalDependency)處理

`pnpm why @napi-rs/canvas`(加入 `pdfjs-dist` 依賴、`pnpm install` 後、
排除前):

```
@napi-rs/canvas@1.0.8
└─┬ pdfjs-dist@6.3.289
  └── @ai-km/service-ingestion@0.0.0 (dependencies)

Found 1 version of @napi-rs/canvas
```

確實被拉入(33MB 原生 binary,`node_modules/.pnpm/@napi-rs+canvas-linux-x64-gnu@1.0.8`)。
排除過程(誠實記錄失敗的中間嘗試,供未來參考):

1. `pnpm.packageExtensions` 設 `optionalDependencies: {}`(想清空整個欄位)
   → 無效。`pnpm config get packageExtensions` 確認設定有被讀到,
   `packageExtensionsChecksum` 也隨編輯而變,但實際解析結果 `@napi-rs/canvas`
   依然存在——pnpm 的 packageExtensions 只會「新增/取代」欄位裡的 key,
   空物件對既有欄位是 no-op,無法藉此刪除單一 key。
2. 把該 key 設為 `false`(`optionalDependencies: { '@napi-rs/canvas': false }`)
   → 仍無效,`pnpm why` 照樣列出 1.0.8;checksum 有變但解析結果沒變,
   代表 pnpm 對這個型別不符的值直接忽略掉整個 merge,而非套用它。
3. **最終做法**:`pnpm-workspace.yaml` 頂層 `overrides`(pnpm 11 起
   `pnpm.overrides`/`pnpm.packageExtensions` 已從 `package.json` 移到
   `pnpm-workspace.yaml`)設 `'@napi-rs/canvas': '-'`——pnpm 官方文件的
   「刪除此依賴」語法,而非改版本號。`pnpm install` 後 `Packages: -2`,
   `pnpm why @napi-rs/canvas` 輸出為空(exit 0,zero matches),
   `pnpm-lock.yaml` 對 `@napi-rs/canvas` 的所有 7 個平台變體 entry 全部消失,
   `pdfjs-dist@6.3.289` 的 snapshot 從 `optionalDependencies: {'@napi-rs/canvas': 1.0.8}`
   變成 `{}`。

排除後證明純文字抽取仍可運作:`src/extraction/pdf-extract.test.ts` 全數在
「零 `@napi-rs/canvas`」的這次 install 下通過(見下方 gate 紀錄),
執行時只留下一則無害警告(`Cannot load "@napi-rs/canvas" package`——
pdfjs 內部想選擇性載入它來 polyfill `DOMMatrix`/`Path2D`,那兩者只影響
**渲染**,不影響 `getTextContent()` 的文字抽取路徑)。

## Unicode 正規化政策(依 story 要求,二選一並寫死)

**選擇:不做 `String.prototype.normalize()`。** 落庫文字就是 `join.ts` 產出的
原樣字串(唯一例外是 `join.ts` 自己版本化過的連字展開,如 `ﬁ`→`fi`——
這屬於 join rules 的一部分而非一般 Unicode 正規化,計入
`JOIN_RULES_VERSION`)。`chunking/chunk.ts` 本來就沒有對輸入文字做任何
normalize(已讀原始碼確認),之後也不得補上——偏移量是對著這個未正規化的
字串算的,事後才 normalize 會讓每一個既有偏移量位移。政策寫在
`src/extraction/pdf-extract.ts` 檔頭註解。

## Assumptions / 計畫外事項 / 未解疑問

- **非內嵌字型 fixture 的產生方式**:環境沒有現成的「非內嵌 CJK 字型」PDF
  樣本,改用 Python `reportlab`(`pdfbase.cidfonts.UnicodeCIDFont('STSong-Light')`)
  產生——這是 PDF 規格 §9.7.4.2 定義的標準機制(引用 Adobe 內建 CJK 字型,
  不內嵌,搭配 predefined CMap `/UniGB-UCS2-H`),已用 `grep -a FontFile`
  確認產出的 PDF 完全沒有 `/FontFile*`。**確實達成了真正的非內嵌字型中文
  案例**,非文字宣稱。
- **`isEvalSupported: false` 無法設定**:story 指示裡列出的這個 pdfjs 選項,
  在 `pdfjs-dist@6.3.289` 的 `DocumentInitParameters` 型別裡已不存在
  (`tsc` 直接報 `TS2353`)。查證:對編譯後的 `legacy/build/pdf.worker.mjs`
  grep `new Function(`/`eval(` 零命中——這個版本已經完全移除了當年
  `isEvalSupported` 要擋的 eval-based glyph 路徑,選項本身變成無意義而被
  移除,不是我方遺漏。已在 `pdf-extract.ts` 對應位置寫註解說明,`useSystemFonts:false`
  與 `disableFontFace:true` 兩項如期設定。
- **`cMapUrl`/`standardFontDataUrl` 不能傳 `file://` URL**:一開始依直覺傳
  `pathToFileURL(...).href`,結果兩者都以「Unable to load … data」失敗——
  追進 `legacy/build/pdf.mjs` 原始碼發現這兩個選項在 Node 端是直接字串
  相接(`${baseUrl}${filename}`)後丟給 `fs.readFile`,而不是先當 URL
  物件解析,所以 `file:///…` 字串會被 `fs.readFile` 當成一個真的以
  `file:` 開頭的檔名去找,自然找不到。正確做法是傳純檔案系統路徑
  (結尾帶路徑分隔符),已在 `resourceDir()` 與檔頭註解記錄這個發現,
  避免未來的人重蹈覆轍。
- **`extractorVersion` 的「持久化」範圍**:本 story 只保證 `text` 與
  `extractorVersion` 在同一個回傳物件裡成對出現,不做任何 DB/檔案落地——
  真正把它寫進儲存層是 E06-S042(index-time 管線)的範圍,本 story 的
  開發邊界（Do NOT）明確排除碰 `services/retrieval`/`rag-skeleton` 等,
  且 `services/ingestion/src/service.ts` 目前仍是 E06-S041 建立的空殼。
- **未解疑問(留待 E06-S042 或使用者裁示)**:「多短算太短」的最小長度
  門檻——本 story 依指示刻意不發明,只擋 exact-zero。
