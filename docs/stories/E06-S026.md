## Schema 變更

`services/retrieval/src/vector/sqlite-vec.store.ts` 的 `SQLITE_VEC_MIGRATION`：

```diff
 CREATE TABLE IF NOT EXISTS ${tableName}_meta (
-  chunk_id     TEXT PRIMARY KEY,
-  document_id  TEXT NOT NULL,
-  text         TEXT NOT NULL,
-  start_offset INTEGER NOT NULL,
-  end_offset   INTEGER NOT NULL
+  chunk_id             TEXT PRIMARY KEY,
+  document_id          TEXT NOT NULL,
+  text                 TEXT NOT NULL,
+  start_offset         INTEGER NOT NULL,
+  end_offset           INTEGER NOT NULL,
+  embedding_model      TEXT,
+  embedding_dimensions INTEGER
 );
```

兩欄皆為**可為 NULL**（不是 `NOT NULL`）：NULL 代表「這筆資料沒有記錄身分」，
`assertEmbeddingIdentityMatches` 把 NULL 當成 UNKNOWN 一律拒絕比對（AC5），
寫入層的 fail-closed 由 `services/ingestion`（見下方）負責，不是靠資料庫的
`NOT NULL` 約束——理由見下方「未解假設」第一條。

新增 `migrateEmbeddingIdentityColumns(db, tableName)`：`CREATE TABLE IF NOT
EXISTS` 對已存在的舊表是 no-op（不會補欄），這個函式在每次
`createSqliteVecVectorStore()` 建構時無條件執行一次 `PRAGMA table_info` 讀取，
缺欄才 `ALTER TABLE ... ADD COLUMN`（已存在則不做事，冪等）。這是唯一的
「migration」——**判斷不需要停下來問使用者**的理由：純新增欄位、不改動任何
既有欄位語意、不做資料回填/猜測、完全侷限在 `services/retrieval` 這個既有
`*_MIGRATION` 慣例內（該檔案本來就叫 `SQLITE_VEC_MIGRATION` 且本來就是
inline 執行，不是另立一套 migration 系統），且 spec 自己的開發邊界明文允許
「對應的 migration」。沒有觸碰 `db/`（Team B 資料夾，本 story 不在 CLAUDE.md
鐵律 6 的例外清單內）。

`VectorRecord` / `RetrievalHit`（`store.ts`）新增 **optional** 欄位
`embeddingModel?: string` / `embeddingDimensions?: number`——刻意不設為
required，理由見下方「與既有測試的衝突與解法」。

### 第二輪修正：`enforceEmbeddingVersion` 從 optional 改為 required（技術顧問，2026-09-02）

上面第 3、4 點原本的寫法——`enforceEmbeddingVersion?: boolean` 加
`?? false`——本身的推理（三份既有測試會被弄壞）是對的，但留下一個新的
「靜默」缺口：**這個開關自己既沒有預設值被測到，也允許呼叫端完全不寫它**，
一旦 `plugin.ts` 那行 `true` 哪天被誤刪，退回的正是「optional 型別 + 不寫
就是 false」這條路徑，編譯器不會抱怨,而測試(在第一輪修正前)也沒有專門盯著
這一行。獨立審核第一輪正是在這裡抓到問題(見上方「獨立審核第一輪 REJECTED」
一節)。

修法：把型別改成必填(`enforceEmbeddingVersion: boolean`，刪除 `?? false`
與函式參數的 `= {}` 預設值)，每個呼叫端(`plugin.ts` 本身、上面列的三份既有

一律**明寫** `true` 或 `false`。第 3、4 點的核心決定——fixture 誠實寫

## 未解假設 / 後續工作（誠實記錄，未經使用者確認前不擴大 scope）

1. **版本欄位的粒度**：只加了 `embedding_model`（字串）與
   `embedding_dimensions`（整數），沒有另加獨立的「version」欄位。理由：
   `EmbeddingProvider.model` 這個字串本身就是 provider 自己選擇要編碼多細
   （例如一個真實 provider 大可回報 `"text-embedding-3-small@2024-01"`）；
   本 story 不知道 `E04-S037` 最終會選什麼 provider、也不知道它的版本命名
   慣例，依 Anti-hallucination Guard「不知道 provider capability → 不猜」，
   不發明一個目前沒有任何 provider 會填、格式未知的第三欄位。
2. **`enforceEmbeddingVersion` 預設 `false`**：如上一節所述，這是為了不
   修改既有測試而做的妥協，不是「這個保護在正式環境不重要」的判斷。後續
   工作：把 `service.test.ts`／`plugin.test.ts`／
   `retrieve-with-reranking.test.ts` 的 fixture 補上真實身分欄位，
   把預設值全面改成 `true`（或乾脆移除這個 flag，讓比對永遠發生）——這是一個
   會改動既有測試 fixture 的變更，依 STORY_WORKFLOW 需要走獨立的一輪
   FIX-with-narrow-exception 或另開一個 story，本 story 不做。
3. **`IngestDocumentResult` 沒有新增 `embeddingDimensions` 欄位**（只沿用既有的
   `embeddingModel`）：spec 的 AC 沒有要求呼叫端從 `ingest()` 的回傳值讀到
   dimensions，維持最小變更。
