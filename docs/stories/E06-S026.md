## 一句話摘要

`<table>_meta` 新增 `embedding_model` / `embedding_dimensions` 兩欄；索引管線
(`services/ingestion`)寫入時把 provider 回報的身分一併落庫，缺身分即拒絕寫入
（AC2）；`VectorStore.query()` 新增可選的第四參數 `expectedIdentity`，提供時會
在做任何相似度排序**之前**比對索引身分與查詢身分，不符或缺失一律拋
`EmbeddingVersionMismatchError` 並拒絕回傳任何結果（AC3/AC5）；
`RetrievalService`/`plugin.ts` 的composition root 預設把這個檢查打開
(`enforceEmbeddingVersion: true`)。

## 為什麼是重量級（依 STORY_WORKFLOW 判準，本 story 自己的理由）

失敗模式是「靜默給出錯誤結果」的原型：換 embedding provider 後，
`services/retrieval` 的 `dot()`/`sqlite-vec` 只要維度相同就會照算相似度，
不拋錯、不留日誌、輸出看起來完全合理。`services/retrieval/src/embedding/
provider.ts` 的既有註解與 `contracts/openapi/embedding.yaml` 都已經把「換
embedding 函式」定義成 re-index event，但 store 的 schema 裡從未有欄位記錄它
——規則寫在註解裡而不在 schema 裡，等於沒有。

## Schema 變更

`services/retrieval/src/vector/sqlite-vec.store.ts` 的 `SQLITE_VEC_MIGRATION`：

```diff
 CREATE TABLE IF NOT EXISTS ${tableName}_meta (
-  chunk_id     TEXT PRIMARY KEY,
-  document_id  TEXT NOT NULL,
-  text         TEXT NOT NULL,
-  start_offset INTEGER NOT NULL,
-  end_offset   INTEGER NOT NULL
+  chunk_id             TEXT PRIMARY KEY,
+  document_id          TEXT NOT NULL,
+  text                 TEXT NOT NULL,
+  start_offset         INTEGER NOT NULL,
+  end_offset           INTEGER NOT NULL,
+  embedding_model      TEXT,
+  embedding_dimensions INTEGER
 );
```

兩欄皆為**可為 NULL**（不是 `NOT NULL`）：NULL 代表「這筆資料沒有記錄身分」，
`assertEmbeddingIdentityMatches` 把 NULL 當成 UNKNOWN 一律拒絕比對（AC5），
寫入層的 fail-closed 由 `services/ingestion`（見下方）負責，不是靠資料庫的
`NOT NULL` 約束——理由見下方「未解假設」第一條。

新增 `migrateEmbeddingIdentityColumns(db, tableName)`：`CREATE TABLE IF NOT
EXISTS` 對已存在的舊表是 no-op（不會補欄），這個函式在每次
`createSqliteVecVectorStore()` 建構時無條件執行一次 `PRAGMA table_info` 讀取，
缺欄才 `ALTER TABLE ... ADD COLUMN`（已存在則不做事，冪等）。這是唯一的
「migration」——**判斷不需要停下來問使用者**的理由：純新增欄位、不改動任何
既有欄位語意、不做資料回填/猜測、完全侷限在 `services/retrieval` 這個既有
`*_MIGRATION` 慣例內（該檔案本來就叫 `SQLITE_VEC_MIGRATION` 且本來就是
inline 執行，不是另立一套 migration 系統），且 spec 自己的開發邊界明文允許
「對應的 migration」。沒有觸碰 `db/`（Team B 資料夾，本 story 不在 CLAUDE.md
鐵律 6 的例外清單內）。

`VectorRecord` / `RetrievalHit`（`store.ts`）新增 **optional** 欄位
`embeddingModel?: string` / `embeddingDimensions?: number`——刻意不設為
required，理由見下方「與既有測試的衝突與解法」。

## 與既有測試的衝突與解法（本 story 最重要的設計決定）

**發現**：把 `VectorRecord.embeddingModel/embeddingDimensions` 設為 required、
並讓 `RetrievalService.retrieve()` 無條件對 `store.query()` 傳入
`expectedIdentity`，會讓下列**既有、非本 story 產生**的測試從綠變紅：

- `services/retrieval/src/vector/store.test.ts`（E06-S043 的 in-memory 測試，
  明文禁止修改）的 `chunk()` fixture 不帶身分欄位。
- `services/retrieval/tests/sqlite-vec-store.integration.test.ts`（E06-S043
  同批禁止修改）的 `record()` fixture 同樣不帶身分欄位。
- `services/retrieval/src/service.test.ts` 的 `seed()`（AC-R1/R2/R4/R5）、
  `services/retrieval/src/plugin.test.ts`（AC-RS3）、
  `services/retrieval/src/rerank/retrieve-with-reranking.test.ts` 的端到端測試
  都直接建構 `VectorRecord` 且不帶身分欄位，並預期 `retrieve()` 成功返回結果
  （AC-R5 更進一步預期在維度不符時丟出的是 `EmbeddingError`，而不是本 story
  的 `EmbeddingVersionMismatchError`）。

這三份（`service.test.ts`／`plugin.test.ts`／
`retrieve-with-reranking.test.ts`）雖然不在使用者点名的「E06-S043 測試」清單
內，但仍是 **既有、已合併** 的測試，STORY_WORKFLOW 與交辦指示都要求「不得
修改任何既有測試，只能新增」。實測驗證：在把上述三個選項都改成無條件開啟後
重跑 `pnpm --filter @ai-km/service-retrieval test`，`service.test.ts` 的
AC-R1/AC-R2/AC-R4 與 `plugin.test.ts` 的 AC-RS3、
`retrieve-with-reranking.test.ts` 的端到端測試全數變紅（詳細訊息未收錄於此
——因為最終沒有採用這個設計，以下是採用的替代設計）。

**採用的設計**（不需要改動任何既有測試一個位元組，經上方全部 67→81 條測試
驗證維持全綠）：

1. `VectorRecord.embeddingModel` / `embeddingDimensions` 保持 **optional**。
2. `VectorStore.query()` 新增**可選**第四參數 `expectedIdentity`；不傳就完全
   不做任何身分比對，行為與 story 之前逐位元相同——這是既有 18+9=27 條
   store 層測試全數維持零修改通過的關鍵。
3. `RetrievalServiceOptions` 新增 `enforceEmbeddingVersion`（預設 `false`）。
   `retrieve()` 只有在這個 flag 為 `true` 時才把
   `{ model: embedding.model, dimensions: embedding.dimensions }` 傳給
   `store.query()`。預設 `false` 不是因為正式環境不該開，而是因為
   `service.test.ts`／`plugin.test.ts`／`retrieve-with-reranking.test.ts`
   這三份既有測試都是呼叫 `createRetrievalService({ store, embedding })`（不
   傳這個 flag），所以只要函式層級的預設值是 `false`，它們就完全不受影響。
4. **真正的 composition root**——`services/retrieval/src/plugin.ts` 的
   `retrievalPluginImpl` 預設路徑（`options.service ?? createRetrievalService(...)`）
   ——改成顯式傳 `enforceEmbeddingVersion: true`。這是唯一會被
   `apps/api` 未來註冊時實際呼叫到的預設值；`plugin.test.ts` 的四條測試沒有
   一條會踩到這個變更（AC-RS1/AC-RS4 不查真實資料；AC-RS2 對的是空 store，
   身分比對迴圈沒有任何東西可迭代；AC-RS3 用自己組的 `createRetrievalService(
   { store, embedding })` 繞過了這個預設值）。

**目前真實曝險**：`grep -rn "retrievalPlugin\|ingestionPlugin" apps/api/src`
零命中——`services/retrieval` 與 `services/ingestion` 的 plugin 都還沒註冊進
`apps/api`，與 E06-S043 記錄的「🚩 硬前置」是同一個前提。因此
`enforceEmbeddingVersion` 預設 `false` 這件事，今天不造成任何真實風險；
它只影響「哪一天這三份既有測試被回頭補上身分欄位、把預設值全面打開」這個
後續工作何時發生，不影響今天的行為。

## 未解假設 / 後續工作（誠實記錄，未經使用者確認前不擴大 scope）

1. **版本欄位的粒度**：只加了 `embedding_model`（字串）與
   `embedding_dimensions`（整數），沒有另加獨立的「version」欄位。理由：
   `EmbeddingProvider.model` 這個字串本身就是 provider 自己選擇要編碼多細
   （例如一個真實 provider 大可回報 `"text-embedding-3-small@2024-01"`）；
   本 story 不知道 `E04-S037` 最終會選什麼 provider、也不知道它的版本命名
   慣例，依 Anti-hallucination Guard「不知道 provider capability → 不猜」，
   不發明一個目前沒有任何 provider 會填、格式未知的第三欄位。
2. **`enforceEmbeddingVersion` 預設 `false`**：如上一節所述，這是為了不
   修改既有測試而做的妥協，不是「這個保護在正式環境不重要」的判斷。後續
   工作：把 `service.test.ts`／`plugin.test.ts`／
   `retrieve-with-reranking.test.ts` 的 fixture 補上真實身分欄位，
   把預設值全面改成 `true`（或乾脆移除這個 flag，讓比對永遠發生）——這是一個
   會改動既有測試 fixture 的變更，依 STORY_WORKFLOW 需要走獨立的一輪
   FIX-with-narrow-exception 或另開一個 story，本 story 不做。
3. **`IngestDocumentResult` 沒有新增 `embeddingDimensions` 欄位**（只沿用既有的
   `embeddingModel`）：spec 的 AC 沒有要求呼叫端從 `ingest()` 的回傳值讀到
   dimensions，維持最小變更。

## 反向驗證（`tools/mutate.mjs`，兩段輸出逐字如下）

（`services/retrieval/src/vector/store.ts`）在進入任何比對邏輯前直接
`return`，等於讓身分比對「永遠通過」（對應 spec 反向驗證節：
「把版本比對改成永遠通過」）。分別用 `--test-name` 鎖定 AC3 語意的測試
