# E07-S001 — Maintenance home

- Branch: `story/E07-S001-maintenance-home`
- Date: 2026-08-15
- Status: DONE

## Scope 說明

E07(Maintenance Assistant Experience)的第一個 story,對應
`nav-items.ts` 早在 E01-S006/S009 就已存在、但一直指向不存在頁面的
`/maintenance` entry(role-gated 給 `maintenance_engineer`/
`super_administrator`)。這是該路由第一次真正渲染內容,而不是落到
Next.js 自己的 not-found。

E08(Maintenance Intelligence Backend,Team B)目前 `contracts/` 內
零 schema,依 SOURCE_BASELINE §5 pinned 決策 #35(「Team A 不等待
Backend 完成才開始」)與 E05 全程建立的先例,本 story 建立純前端 mock,
不等待/不假裝 E08 已存在。

## 設計決策

**「Maintenance home」與「Maintenance history」(E07-S020)刻意分開**:
epic 檔案把兩者列為兩個獨立 story,且兩者的 boilerplate AC 模板文字
完全相同(只有標題不同,無額外文字可資區分),因此範圍判斷需要自行
推理,而非照抄文字。採用的推理:

1. 「home」與「history」在同一個 epic 內各自成一個 story,意味著
   「home」不應該預先做完「history」的完整範圍(搜尋/分頁/完整清單),
   否則「history」會沒有東西可做——同一種「不要搶未來 story 的範圍」
   紀律,`KnowledgeBaseSummary` 每個欄位(`visibleToRoles`/`members`/
   `boundPrompt`...)都是各自的 story 才加上去的,而非 S001 一次到位。
2. 但 Testing Boundary 明確要求「Unit: happy path + validation +
   permission + error mapping」與「Negative path 至少涵蓋 validation、
   unauthorized/forbidden、dependency failure」——一個純靜態、沒有任何
   fetch 的「首頁」無法誠實地滿足這些義務(沒有 loading/error/empty
   狀態可測)。這代表 S001 需要一個真實(mock)的非同步讀取,而非純
   靜態連結頁。
3. 結論:S001 = 一個唯讀的「最近維修案例」清單landing page,有真實的
   loading/error/empty/loaded 狀態,鏡射 `KnowledgeList`(E05-S001)
   的既定形狀。**不**加入「開始新的維修診斷」連結——E07-S002「Equipment
   selector」是那個流程真正的第一步,對應路由(推測為
   `/maintenance/new`)目前不存在,加入連結會是「連到還不存在的路由」,
   直接違反 `KnowledgeList`(E05-S001)自己的 doc comment 已經立下的
   「不發明連到不存在路由的連結」紀律,S002 才是加上那個連結的正確
   story(鏡射 E05-S001 → E05-S003「新增知識庫」連結的關係)。
4. 清單項目本身也刻意不加連結——E07-S021「Case detail」是
   `/maintenance/[id]` 的擁有者,目前不存在,同一條紀律。

**`MaintenanceCaseSummary` 型別刻意最小化**:只有 `id`/`title`/
`updatedAt` 三個欄位。設備(Equipment,S002)、序號(Serial number,S003)、
錯誤代碼(Error code,S004)、狀態(可能於 S018-S019 才有意義的
escalated/completed 等)都**不**在此提前建立欄位——同一種
「欄位屬於真正擁有它的 story,不要提前發明」紀律,`KnowledgeBaseSummary`
自己的 doc comment 已反覆引用同一原則。`title` 是自由文字,擔任目前
唯一誠實可用的案例標籤角色,同一個 role `name`(KB)/`title`(對話)
已經扮演過的角色。

**E08 依賴判定**:`contracts/` 對 maintenance/E08 零命中,E08 本身是
Team B 的獨立 epic(25 個 story,涵蓋設備/錯誤代碼/決策樹/SOP 等)。
依 SOURCE_BASELINE §5 pinned #35 與 E05 全程(31 個 story,零真實後端)
的先例,本 story 直接建 mock,不視為 BLOCKED。

## 開發過程中的技術發現

**嘗試新增一則「general_user 造訪 `/maintenance` 應該看到真正的 403」
E2E 測試,撞見並理解了一個既有、記載良好的架構限制,最終判斷不該
勉強繞過,而是移除該測試並記錄理由**:

第一次撰寫時用 `page.goto("/maintenance")` 直接造訪(因為 general_user
根本看不到「維修助手」側邊連結,無法用真實 in-app 點擊到達)。VERIFY
時這個測試失敗——不是找不到 403 訊息,而是整個瀏覽器停在 `/login`
頁面。追查後在 `conversations.spec.ts`/`citation-open-source.spec.ts`
自己的 doc comment 中找到明確、既有的解釋:mock `AuthClient`
的 session 是純粹的記憶體內 closure 變數,沒有 cookie/storage 支撐;
`page.goto()` 是硬重新整理,會整個重跑 JS bundle,session 因此被清空,
`SessionGate` 正確地(這是它該做的事)把使用者導回 `/login`,`RoleGuard`
根本沒有機會執行。`route-guards.spec.ts` 自己用 `page.goto()` 之所以
「安全」,唯一原因是它導向的路由(`/erp`、`/this-route-does-not-exist`)
根本沒有對應的 `page.tsx`,Next.js 的 root not-found 在觸及
`(app)/layout.tsx` 的 `SessionGate` 之前就已經短路了。`/maintenance`
現在是`(app)` layout 內一個真正的頁面,不再具備這個「安全」條件。

`citation-open-source.spec.ts` 自己的 doc comment 早就為
`/citations/[id]` 的 NOT_FOUND 案例記載了同一種情況的正確處理方式:
「沒有合法的 in-app 連結可以到達這個情境,所以刻意把這個渲染留給
component 層級的單元測試覆蓋,而非用不具代表性的變通方法在 E2E
層硬測」。本 story 的情況完全相同——`role-guard.test.tsx` 早已用
`renderGuardAs(["general_user"], "/maintenance")` 直接、明確地測過
這個路由自己的 403 渲染,測試依然存在且未被本 story 修改、仍然通過。
移除了那則有缺陷的 E2E 測試,在 `maintenance-home.spec.ts` 的檔案
doc comment中完整記錄這個推理,而非留下一個名義上通過、實際上測到
完全不同事情(session 過期重導,而非 RoleGuard 的 403 分支)的假陽性
測試。

**`route-guards.spec.ts` 的既有測試因本 story 而失效,更新而非保留**:
該檔案原本(自 E01-S017 建立以來唯一一次 commit,`git log` 確認)只用
`/maintenance` 作為「role-restricted 但頁面還沒蓋好」的範例,標題與
doc comment 本身已經預告這是暫時性的(「/knowledge、/maintenance、/erp
是 E05/E07/E09 各自的第一個 story——這個 repo 不會搶在它們前面」)。
本 story 蓋出真正的 `/maintenance` 頁面後,一般使用者造訪它會得到真正
的 403(經由既有、未變動的 `RoleGuard`),不再是「沒有頁面所以 404」——
這則既有測試的前提不再成立。改為測試 `/erp`(E09 尚未開工,仍然是
「role-restricted 但沒有頁面」的真實案例),保留測試原本要驗證的行為
(role-restricted 但未建置的路由,安全地落到 not-found 而非崩潰或
出現非預期畫面)。第一版的 commit 訊息曾誤寫「E05-S001 也對這個檔案
做過同樣的搬移」,經 `git log --all -- tests/e2e/specs/
route-guards.spec.ts` 確認整個檔案史只有一個 commit(從未被修改過)後,
在提交前就自行發現並更正了這個說法,doc comment 現在誠實記載「這是
本檔案自建立以來的第一次更新」。

## AC 對照

**Functional**:
1. 合法輸入 → 預期成功結果:單元測試「shows each case's title and
   timestamp once loaded」+ E2E 測試顯示 3 筆 seed 案例。
2. 缺少必要輸入 → fail-closed → N/A,本 story 沒有任何使用者輸入
   (純唯讀 landing page,沒有表單/mutation)。
3. 無權限使用者 → 不得讀取/顯示 → 由既有、未修改的
   `role-guard.test.tsx` 覆蓋(明確針對 `/maintenance` 本身);E2E 層級
   的嘗試與其架構限制已誠實記錄於上方技術發現,判斷不強行繞過。
4. Dependency timeout/unavailable → 單元測試「shows a distinct error
   state when loading fails」(mock SERVICE_UNAVAILABLE)。
5. 重複請求不得有未定義 side effect → 單元測試「returns the same
   items on repeated calls」;`listMaintenanceCases()` 本身是純讀取,
   無 side effect 可言。
6. Correlation id/telemetry → 每個 log 呼叫皆含 `correlationId`。
7. Audit event → N/A,讀取唯讀清單不是敏感操作,同
   `KnowledgeList`/`ConversationList` 自己的既定判斷。
8. MVP 可簡化但能力不可缺席 → 案例清單確實存在、可運作、有測試覆蓋。

**Security**:由既有 `role-guard.test.tsx` 覆蓋(見 AC 3);未修改該
測試,重跑後依然通過。

**Data/Contract**:None。

**UX**:loading(單元測試)/empty(單元測試——目前沒有刪除功能,
無法在 E2E 層自然清空清單,判斷單元測試覆蓋已足夠,同本 codebase
其他過渡態的一貫作法)/success(單元+E2E)/validation(N/A,無輸入)/
