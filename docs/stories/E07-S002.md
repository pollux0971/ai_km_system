## Scope 說明

E07 第二個 story,緊接 E07-S001「Maintenance home」——`/maintenance`
首頁上線後,本 story 補上 S001 自己刻意留白的「開始新的維修診斷」進入點
(鏡射 E05-S001 → E05-S003「新增知識庫」連結補上的關係)。

依 epic 檔的 sequencing 說明(S002 設備選擇 → S003 序號輸入 → S004
錯誤代碼搜尋 → S005 問題描述 → S006 診斷會話外殼),本 story 判斷為
「新增維修案例」表單的第一個欄位,而非獨立的一次性選擇動作——理由:

1. Testing Boundary 明確要求每個 story 都要有 loading/error/permission
   等狀態可測,一個純選擇、不落地任何真實變更的元件無法誠實滿足這點。
2. Functional AC 8「MVP 可以簡化但此能力本身不可缺席」——如果 S002 只是
   一個「選好但沒有任何後續動作」的元件,這個能力等於不存在。
3. 因此判斷:S002 建立 `/maintenance/new` 頁面,目前只有「選擇設備」
   一個欄位,選定後送出即建立一筆最小可用的維修案例,並導回
   `/maintenance` 首頁(該案例會出現在清單中)。後續 S003(序號)/
   S004(錯誤代碼)/S005(問題描述)各自為這個同一張表單新增一個欄位,
   鏡射 E05-S011→S015 陸續為同一個「文件列表」頁面新增三種不同來源
   新增文件方式的既定形狀,而非各自開新路由。

**`EQUIPMENT_OPTIONS` 為何是純前端固定清單,而非 mock store**:
SOURCE_BASELINE.md 的 E08 實體清單明確列出 `Equipment`/
`EquipmentModel` 為 E08-S01/S02(Team B)的責任範圍,`contracts/` 對此
零命中。Team A 的 25 個 E07 story 清單裡沒有任何一個「設備管理」story
(不像 KnowledgeBase 有完整的 S01-S05 CRUD),代表設備本身在 Team A
的範圍內是一份**唯讀的固定參考清單**,而不是像 `MaintenanceCaseSummary`
一樣是可變動的集合——因此 `equipment.ts` 是一份 plain array,不像
`maintenance-cases.ts` 需要 sessionStorage-backed store,鏡射
`ai-models.ts` 的 `AI_MODELS` 扮演的角色。

**`MaintenanceCaseSummary.equipmentId` 儲存 id 而非名稱快照**:同
`boundModel` 儲存 `AiModel` id、顯示時才查表(`AI_MODELS.find(...)`)
的既定形狀,而非把設備名稱字串直接複製進案例紀錄——避免顯示名稱與
來源清單走鐘的風險。`title` 欄位在 S002 這個階段等於設備名稱本身
(在 S005 真正的問題描述存在之前,這是唯一誠實可用的案例標籤),
S005 之後可以自由覆寫它,同 `KnowledgeDocumentNameEditor`(S023)
後來成為既有欄位顯示唯一擁有者的先例。

## 開發過程中的技術發現

**`getByRole("list")` 不加 scope 會連到側邊欄自己的導覽清單**:更新
既有 E2E 測試的「案例清單裡沒有任何連結」斷言時(因為新增了「開始新的
維修診斷」連結,原本斷言整個 `<main>` 內連結數為 0 已經不成立,需要
改成只檢查案例清單本身),第一版改成
`page.getByRole("list").getByRole("link")`,VERIFY 時發現這個查詢
不只比對到案例清單自己的 `<ul>`,也比對到側邊欄導覽自己的
`<nav><ul>`(首頁/對話/知識庫/維修助手,4 個連結)——因為
`getByRole("list")` 沒有限定在頁面的哪個區域,會抓到整個頁面上所有
list role 的元素。修正為 `page.getByRole("main").getByRole("list")
.getByRole("link")`,先透過 `main` 排除側邊欄,再確認清單本身依然
是 0 個連結。

## AC 對照

**Functional**:
1. 合法輸入 → 預期成功結果:單元測試「creates a case titled after the
   selected equipment's own name」+「a newly created case appears in
   listMaintenanceCases()」+ E2E 測試完整流程(側邊欄點入→選設備→
   建立→回到首頁看到新案例)。
2. 缺少必要輸入 → fail-closed:提交按鈕在未選設備前停用(client-side)
   +`createMaintenanceCase("")`/未知 id 皆回傳 VALIDATION_ERROR 且對
   store 無副作用(單元測試明確驗證前後 `listMaintenanceCases()`
   結果相同)。
3. 無權限使用者 → N/A,同 S001——沿用既有 RoleGuard,本 story 未新增
   任何受保護資源。
4. Dependency timeout/unavailable → 單元測試+元件測試皆有
   SERVICE_UNAVAILABLE mock 情境,確認顯示明確錯誤且不導覽離開、
   保留使用者的選擇。
5. 重複請求不得有未定義 side effect → 元件測試「disables the submit
   button while the request is pending, preventing a double submit」,
   確認即使按兩次也只呼叫一次 `createMaintenanceCase`。
6. Correlation id/telemetry → `maintenance_case_create_attempt/
   success/failure` 三個事件共用同一個 correlationId,元件測試明確
   驗證。
7. Audit event → N/A,建立新案例是內容建立行為,非權限異動,同
   createKnowledgeBase(S003)/addKnowledgeBaseDocument(S011)既有判斷。
8. MVP 可簡化但能力不可缺席 → 設備選擇→建立案例→出現在首頁,完整
   閉環,不是半成品。

**Security**:N/A,理由同 Functional AC 3。

success(單元+元件+E2E)/validation(送出按鈕停用+伺服器端二次驗證)/
