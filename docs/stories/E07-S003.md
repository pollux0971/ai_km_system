## Scope 說明

E07 第三個 story,延續 S002 已建立的「`/maintenance/new` 是 S002-S005
共用的同一張表單,各自負責加一個欄位」設計(理由見 E07-S002.md 自己的
「設計決策」章節)。本 story 在同一張表單上新增「設備序號」欄位。

**`serialNumber` 為何是選填,而非必填**:S002 自己的 EVIDENCE 已經明確
記載「設備選擇→建立案例→出現在首頁,完整閉環,不是半成品」——如果
S003 把序號改成必填,會回頭破壞 S002 已經審核通過、已經合併的能力
(單靠設備就能建立有效案例)。因此採用與 `KnowledgeBaseSummary` 完全
相同的先例:`visibleToRoles`/`members`/`boundPrompt`/`boundModel`/
`folderSyncPath` 全部是選填欄位,S003(KB 那邊的「新增 KB 表單」)
建立的「只有名稱」的知識庫,在 S006-S016 陸續加完所有欄位後依然有效
——同一種「持續新增選填欄位到同一個實體上」的形狀。序號本身沒有做
格式驗證(只有 trim)——SOURCE_BASELINE 沒有任何地方定義序號格式,
發明一個會直接違反 Anti-hallucination Guard「不確定的規則不可假裝
存在」。

## AC 對照

**Functional**:
1. 合法輸入 → 預期成功結果:單元測試「stores a trimmed serial number
   when one is given」+ E2E 測試(選設備+填序號→建立→首頁顯示
   「序號:SN-2026-0042」)。
2. 缺少必要輸入 → fail-closed:序號本身選填,無「缺少」情境;唯一
   必要輸入(設備)仍由 S002 已建立的驗證把關,單元測試「stays
   valid...when serialNumber is omitted, empty, or whitespace-only」
   確認省略序號不影響案例建立成功;E2E 新增測試明確驗證「只填設備、
   不填序號」依然完整可用,且清單上不會出現空的「序號:」行。
3. 無權限使用者 → N/A,同 S001/S002——沿用既有 RoleGuard。
4. Dependency timeout/unavailable → 沿用 S002 已有的
   SERVICE_UNAVAILABLE mock 情境測試,序號欄位不影響這條路徑。
5. 重複請求 → 沿用 S002 已有的 pending-guard 測試,序號欄位是額外
   state,不影響既有防護機制。
6. Correlation id/telemetry → 沿用 S002 已有機制;新增測試明確驗證
   序號本身(自由文字)不會出現在任何 telemetry payload 中。
7. Audit event → N/A,同 S002。
8. MVP 可簡化但能力不可缺席 → 序號輸入是真實可用的欄位,有輸入、
   有持久化、有條件式顯示,不是半成品。
