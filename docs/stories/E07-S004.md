# E07-S004 — Error-code search UI

- Branch: `story/E07-S004-error-code-search-ui`
- Date: 2026-08-15
- Status: DONE

## Scope 說明

E07 第四個 story,延續 S002-S003 已建立的「`/maintenance/new` 共用表單,
各自負責加一個欄位」設計。本 story 在同一張表單上新增第三個欄位:
錯誤代碼。

**為何是「搜尋」而非單純的下拉選單(與 S002 的「選擇器」刻意不同)**:
這個 story 自己的標題明確寫「search UI」,不是「selector」(S002 自己
的標題)——這個文字差異被視為有意義的訊號,而非隨意用詞。因此本 story
建立一個文字搜尋框,即時依代碼或描述關鍵字過濾一個 `<select>` 的可選
選項,而非直接複用 S002 的「純選擇器」形狀。清單目前仍然很小
(4 筆),但「加上搜尋能力」是這個 story 自己要求的,不是依清單目前
大小做的判斷。

**`errorCode` 為何選填但「有值就要驗證」,而非像 `serialNumber` 完全
不驗證**:`errorCode` 和 `equipmentId` 一樣是參照一份固定清單
(`ERROR_CODE_OPTIONS`,理由同 `equipment.ts`——SOURCE_BASELINE 的 E08
實體清單明確把 `ErrorCode` 列為 E08-S03/S04 的責任),而 `serialNumber`
是純自由文字。因此「選填」只代表「這個欄位可以完全不填」,不代表
「填了什麼都接受」——有值時必須是 `ERROR_CODE_OPTIONS` 中真實存在的
代碼,否則以 VALIDATION_ERROR 拒絕,同 `equipmentId` 永遠必填時的驗證
邏輯,只是放寬了「允許空值」這一點。

**搜尋文字改變後,已選定的代碼若被篩選掉會自動清空選取**:如果不這樣
做,`<select>` 可能顯示一個「已選定但目前選單畫面上看不到」的值,對
使用者造成混淆(尤其是螢幕閱讀器使用者,選單改變後卻聽不到目前選取
狀態實際上已經不在可見選項內)。這個處理只在使用者「打字改變搜尋條件」
時觸發,不影響「清空搜尋框」的情境(清空搜尋框會顯示全部選項,原本的
選取自然還在可見範圍內,不需清空)。

## 開發過程中的技術發現

**Playwright 的 `getByLabel` 預設做子字串比對,`@testing-library/react`
的 `getByLabelText` 預設做完全比對——同一個查詢字串在單元測試通過、
E2E 測試卻失敗**:`"錯誤代碼(選填)"` 這個字串剛好是
`"搜尋錯誤代碼(選填)"` 的子字串(前者是 select 的 label,後者是搜尋框
自己的 label)。單元測試用 `screen.getByLabelText("錯誤代碼(選填)")`
在 Testing Library 底下能正確、唯一地比對到 select(因為 Testing
Library 的 `getByLabelText` 預設是精確比對),但同一個字串在 E2E 測試
的 `page.getByLabel("錯誤代碼(選填)")` 底下(Playwright 預設做子字串
比對)會模糊比對到搜尋框自己身上,導致 `selectOption()` 找不到真正的
select 元素而逾時。第一輪 VERIFY 時 158 個既有測試全過、只有這一個新
測試失敗,精確定位到問題後,修正為 `getByLabel("錯誤代碼(選填)", {
exact: true })`,並在測試檔案中記錄這個兩套測試工具「同名查詢預設行為
不同」的差異,避免未來再次撞到同一類問題。
