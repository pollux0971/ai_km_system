# E07-S007 — Current-step card

- Branch: `story/E07-S007-current-step-card`
- Date: 2026-08-15
- Status: DONE

## Scope 說明

E07 第七個 story,是 E07-S006「Diagnostic session shell」自己的 EVIDENCE
明確留言的下一步:「S007『Current-step card』是下一個 story,對應 Team B
E08-S10『Node Transition』之前的第一個真正診斷步驟內容,需要重新設計『決策
樹尚不存在時,單一步驟卡片要顯示什麼』」。

**開工前先跑 `/advisor`**(依全域規則第 7 條「規格未明、多種做法難以取捨」):
SOURCE_BASELINE.md 對 E07-S07 只有標題「Current Step」,真正決定「目前是
哪個步驟」的邏輯(決策樹遍歷)屬於 Team B 的 DecisionTree/DecisionNode/
DecisionEdge(E08-S05/S06/S07)與 Node Transition(E08-S10),`contracts/`
底下完全沒有這些 contract。分析後判斷:要守住的界線是「不 model 分支/
遍歷」(那是 Team B 的演算法,自己補一套會構成 Domain Ownership Boundary
說的「影子實作」),但「目前步驟」這個概念本身、以及它的卡片 UI,可以誠實
地做成一個**單一、不分支、明確標示為模擬**的內容,延續這個 codebase 對
「Team B 尚未存在的實體」一路以來的既定模式(E07-S006 自己的
`DiagnosticSession`、E05 的 `upload-progress.ts`/`parse-progress.ts`/
`index-progress.ts`「每個 story 自己的計時原語」)。此判斷屬於
單一 story 範圍、低風險、可回退、不涉及 contract/安全/跨 Team A-B 介面,
依 advisor Step 4 判準可自行採納,不需使用者決策,故未寫入
`PENDING_DECISIONS.md`。

**核心設計決策**:
1. `lib/diagnostic-steps.ts` 新增 `DiagnosticStep`(`stepIndex` +
   `instruction`)與 `getCurrentDiagnosticStep()`——**無參數、同步、不回傳
   `Result<>`**:這是一個純計算,不是模擬網路呼叫(不像
   `getMaintenanceCase`/`getDiagnosticSessionForCase`),沒有失敗模式可
   表示,同 `answer-state.ts` 的 `classifyAnswerState` 一樣的「純函式,直接
   回傳值」寫法。永遠回傳同一個 `stepIndex: 0` 的步驟——目前沒有任何機制
   能讓 session 前進到下一步(那是 E07-S08「Decision Options」起的範圍),
   所以「目前步驟」對任何 session 而言此刻都是同一個值,誠實反映現狀而非
   假裝有分支。
2. `instruction` 文字明確以「（模擬步驟）」開頭——同 `answer-state.ts` 的
   `ANSWER_STATE_FALLBACK_CONTENT`(「（模擬回覆）」)已建立的慣例:誠實
   標示這是站在「Team B 真正的 SOP/決策節點內容」位置上的暫代文字,不是
   偽裝成真實企業維修知識。內容本身刻意保持通用(要求描述觀察到的異常
   現象),不是針對特定設備/錯誤代碼編造的具體維修步驟——這種「任何診斷
   流程共通的第一步」不構成杜撰真實 SOP 內容。
3. **不在 `DiagnosticSession` 上新增 `currentStepIndex` 欄位**——`getCurrentDiagnosticStep()`
   是純推導,沒有任何東西被持久化。這是刻意的保守選擇:現在存一個猜測性
   的欄位形狀,將來 E08 真正的 contract 一旦出現,很可能需要遷移;不存,
   就沒有東西需要遷移走。
4. 新增獨立元件 `current-step-card.tsx`(而非把 JSX 直接寫進
   `maintenance-session.tsx`),與 `lib/diagnostic-steps.ts` 皆為全新
   sibling 檔案——延續 `upload-progress.ts` 等「每個 story 自己的檔案,
   對既有檔案零/最小 diff」慣例。`diagnostic-sessions.ts` 唯一的變更是
   doc comment(不是邏輯),因為它自己先前的 doc comment 明確預告了
   S007 的到來,現在需要更新為「已經到來」的現況——同 `maintenance-cases.ts`
   自己「每個後續 story 追加一段」的既定慣例。

**既有測試的必要修正(非 FIX 循環,PLAN 階段即識別、非技術性錯誤例外)**:
`tests/e2e/specs/maintenance-session.spec.ts` 有一個 E07-S006 自己的既有
E2E 斷言 `await expect(page.getByText("尚未有診斷步驟。")).toBeVisible();`
——這不是 Phase 4 第 5 點講的「測試技術性錯誤」,而是 S006 自己的 EVIDENCE
（AC 對照 #8)早已明文記載的「刻意佔位文字(S007 起才會有真正內容)」,
現在被本 story 自己的 AC 要求正面取代。與 E05-S020→E05-S029(既有「無
alert 可見」斷言被後續 story 合理更新為「role=alert 可見」)屬於同一類、
已有先例並經審核通過的「後續 story 依自己 AC 合理取代前一個 story 自己
預告的佔位斷言」,不是放寬驗證強度來配合實作。修正方式:原斷言改為
「確認舊佔位文字消失 + 新的『步驟 1』標題出現」,並新增一個本 story
專屬的 E2E 測試驗證完整的模擬步驟內容。
