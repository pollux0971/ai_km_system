# E07-S010 — Previous-step action

- Branch: `story/E07-S010-previous-step-action`
- Date: 2026-08-15

## Scope 說明

E07 第十個 story。SOURCE_BASELINE 的標題是「Back」,epic 檔的完整標題是
「Previous-step action」。範圍判斷本身不需要 `/advisor`——不像 S008/S009,
這裡沒有兩個明顯不同、都說得通的設計岔路,只是「讓 session 的
`currentStepIndex` 往回退一格」這個對稱、機械性的操作,直接延續
S008/S009 已建立的資料模型與慣例。

**核心設計決策**:
1. `goToPreviousStep(sessionId)` 讓 `currentStepIndex` 減一,同時清空
   `lastSelectedOptionId`/`lastFreeTextDetail`——被離開的那個步驟所記錄的
   選擇/補充說明,對「session 現在顯示的步驟」而言已經不再適用;使用者
   明確要求「回去重新考慮」,若還留著舊答案會造成語意上的殘留。
2. `status` 刻意不變(不從 `IN_PROGRESS` 退回 `OPEN`)——一旦 session 真的
   進入過 `IN_PROGRESS`(代表發生過一次真實的診斷動作),回去重新考慮
   那個動作不等於「回到尚未開始」,同 `selectDecisionOption` 自己「已經
   前進過的 session 不因為再次呼叫而被降級」的既有判斷同一個道理。
3. `currentStepIndex === 0` 時回傳 `VALIDATION_ERROR`(「已經是第一步。」)
   ——不是靜默 no-op/clamp,拒絕比裝作成功更誠實;這個情境在真正的 UI
   裡結構上不可達(`current-step-card.tsx` 只在 `step.stepIndex > 0` 時
   才渲染「上一步」按鈕),同 `selectDecisionOption` repeat-guard 已建立的
   「structural, not just client-hidden」判斷同一類。
4. `goToPreviousStep` 不重新驗證要回到的那個步驟——`currentStepIndex - 1`
   必然是這個 session 自己已經走過的步驟(`DIAGNOSTIC_STEPS` 陣列裡一定
   存在),與 `selectDecisionOption` 的 `optionId`(呼叫方任意輸入,必須
   驗證)性質不同。

**IMPLEMENT 階段主動抓到的真實 bug(非 FIX 循環,VERIFY 之前就發現並修正)**:
撰寫 E2E 測試時發現:`current-step-card.tsx` 的 `detailText`(補充說明
文字框的草稿內容)是這個元件實例自己的 local state,而
`maintenance-session.tsx` 在步驟切換時只是把新的 `step` prop 傳進**同一個**
元件實例(不會 unmount/remount)——這代表如果不特別處理,使用者在步驟 0
打的字,選了選項前進到步驟 1、再按「上一步」回到步驟 0 之後,文字框會
顯示上一輪**已經送出或已經放棄**的舊草稿,而不是空白。修正:新增
`useEffect(() => setDetailText(""), [step.stepIndex])`,讓草稿內容跟著
「目前顯示的是哪個步驟」重置,不論是前進還是後退造成的切換。這個問題
在真正呼叫任何 gate 之前,靠著撰寫 E2E 測試時的推理就先抓到並修正,
沒有讓它進入 VERIFY 紅燈再回頭修。
