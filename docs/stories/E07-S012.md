## Scope 說明

E07 第十二個 story。SOURCE_BASELINE 標題是「Skip Step」,但 epic 檔的完整
標題明確是「Skip-step UX **with reason**」——「with reason」不是裝飾性
措辭,它是本 story 與 S008/S009 最關鍵的差異:S009 的 `detail` 是選填,
本 story 的 `reason` 是必填。這個判斷直接來自 epic 檔本身,不需要
`/advisor`。

**核心設計決策**:
1. `skipDiagnosticStep(sessionId, reason)`——`reason` trim 後為空一律
   `VALIDATION_ERROR`(「請填寫略過原因。」),與 `selectDecisionOption`
   的 `detail`(選填,空白視為未提供而非錯誤)刻意不同。
2. **新增獨立的 `lastSkipReason` 欄位,不重用 `lastFreeTextDetail`**——
   兩者語意不同:`lastFreeTextDetail` 是「對一個真實選擇的選填補充」,
   `lastSkipReason` 是「不做選擇的必填理由」。重用同一個欄位會混淆這兩種
   不同意圖,即使兩者在型別上都只是字串。
3. **advances `currentStepIndex` 但不記錄任何 `lastSelectedOptionId`**
   ——略過就是「沒有做出選擇」,不是偽裝成第三個選項;`selectDecisionOption`
   的 `lastSelectedOptionId`/`lastFreeTextDetail` 兩者在略過時都明確清空
   (同 `goToPreviousStep`/`restartDiagnosticSession` 已建立的「切換到
   不適用的情境就清空舊欄位」慣例)。
4. **repeat-guard 與 `selectDecisionOption` 同一種形狀**——當前步驟沒有
   選項時(已經略過或已經選擇過)`VALIDATION_ERROR`,結構上不可達(UI
   只在 `step.options` 存在時才顯示略過 UI)。
5. **UI 端「跳過此步驟」按鈕在原因欄位為空/純空白時保持 disabled**——這是
   對伺服器端必填驗證的前端映射,不是取代;伺服器端仍然獨立驗證(同這個
   session 建立的「client 不得自行推導比 server 更寬鬆的 permission」
   原則的同類應用,這裡是驗證邏輯而非權限,但道理相同——不信任可能被
   繞過的 client)。
6. **首次略過同樣讓 status 從 OPEN 轉為 IN_PROGRESS**——略過仍然是一次
   真實的診斷動作(明確選擇不回答),不是「什麼都沒發生」。
