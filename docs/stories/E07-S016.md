# E07-S016 — Safety warning component

- Branch: `story/E07-S016-safety-warning-component`
- Date: 2026-08-15
- Status: DONE

## Scope 說明

E07 第十六個 story。SOURCE_BASELINE/epic 檔標題僅有「Safety warning
component」,無更多描述。這次判斷不需要額外的先例研究即可有信心地決策
(理由見下方),直接進入實作。

**核心設計決策**:
1. **主動、無條件顯示,不是 S014/S015 的 toggle 面板模式**——安全警告不是
   使用者可能想探索的選填內容(像 AI 說明或 SOP 引用來源),而是使用者
   必須看到的內容。把安全資訊藏在一個要點擊才會展開的按鈕後面,本身就是
   錯誤的 UX 決策,不是這個 story 該延續的模式。
2. **不 gated 在 `sessionId`**——這與 S014/S015 的 toggle 按鈕不同(那兩個
   因為是 `<button>`,必須 gated 在 `sessionId` 才不會打破 S007 的
   凍結測試「zero buttons when no sessionId」);安全警告是 `<p
   role="alert">`,不是按鈕,不會撞到那個測試,也沒有理由讓警告的顯示
   依賴「是否有一個 active session」——已對抗性複驗確認這個設計決策真實
   生效(見下方 Gate 紀錄)。
3. **新增 `DiagnosticStep.safetyWarning?: string` 純欄位,不是像
   S014/S015 那樣的獨立 async lookup 模組**——安全警告是這個步驟本身
   已知、固定的內在內容,與 `instruction`/`options` 同一類,不是使用者
   觸發才去問的探索性內容(不需要「詢問」,答案永遠已知)。因此直接加在
   `diagnostic-steps.ts` 既有的 `DiagnosticStep` 型別上,不新建
   `lib/diagnostic-*.ts` 檔案——這也呼應 `diagnostic-steps.ts` 自己 doc
   comment 一貫主張的「保持同步、沒有真正的失敗模式」哲學,這次不是
   繞過它,而是完全符合它。
4. **只有 step 0 有安全警告,step 1 沒有**——同 `options` 已建立的
   per-step 不對稱先例:step 0 涉及觀察/接近可能有風險的設備,step 1
   只是「已記錄,繼續進行」的純文字銜接,沒有物理接觸,沒有安全疑慮。
5. **本 story 不做任何阻擋/強制確認邏輯**——選項按鈕、略過按鈕等現有
   互動完全不受這個警告影響,使用者不需要先「確認已讀」才能繼續。這是
   刻意的界線:epic 檔本身緊接在後的下一個 story 正是「E07-S017 High-risk
   confirmation gate」,標題已經清楚指向「必須確認才能繼續」屬於那個
   story 的範圍,不是這個 story 該提前實作的。這個判斷同
   `restartDiagnosticSession` 自己 doc comment 對「不加確認對話框,那是
   S017 的範圍」的既有立場完全一致。
