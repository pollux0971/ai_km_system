# E07-S024 — session-resume UX

- Branch: `story/E07-S024-session-resume-ux`
- Date: 2026-08-16
- Status: DONE

## Scope 說明

E07 第二十四個 story,也是這個 epic 倒數第二個 story。SOURCE_BASELINE/
epic 檔標題僅有「session-resume UX」,無更多描述。

**核心設計決策**:

1. **「恢復 session」這個能力本身早就存在**——`maintenance-session.tsx`
   自己的既有邏輯(E07-S006)已經會檢查案例是否已有 session,若有就
   直接恢復,不會重複建立第二個。這個 story 缺的不是「恢復機制」
   本身,而是**使用者從首頁根本沒有任何方式知道自己有進行中的診斷
   、也沒有連結可以直接跳回去**——唯一能到達既有 session 的方式是
   直接輸入網址,或透過 S021 的 case detail 頁面(如果知道案例 id
   的話)。
2. **全新獨立元件 `ContinueDiagnosisPrompt`,不 retrofit
   `MaintenanceCaseList`**——同 S021 自己遇到、且已經完整記錄理由的
   同一個結構性限制:`MaintenanceCaseList` 自己已核准的「renders no
   links」測試斷言零連結,把項目改成連結會直接推翻那個斷言的真假值
   ,不合 STORY_WORKFLOW 測試凍結規則的既有窄例外。全新元件完全繞開
   這個問題——不觸碰 `MaintenanceCaseList`/`MaintenanceHistoryList`
   任一個檔案。
3. **只顯示 OPEN/IN_PROGRESS 兩種狀態,不是最近一筆**——已解決/已升級
   /已取消都是已經有結果的案例,沒有「恢復」的意義;沒有 session 的
   案例從未開始,也沒有東西可恢復。刻意顯示**全部**符合的案例,不是
   只顯示最新一筆——維修工程師完全可能同時有多個診斷在進行中,只顯示
   一筆會隱藏其他同樣可恢復的工作。
4. **完全重用 `MaintenanceHistoryList` 自己已經在用的同一組函式**
   (`listMaintenanceCases` + `getDiagnosticSessionForCase`),零新
   lib 函式。
5. **失敗時降級為完全不顯示(不是 fail-closed,也不是顯示錯誤訊息)**
   ——這是疊加在一個已經完整可用的首頁上的**輔助性**提示,不是主要
   內容(首頁自己的 `MaintenanceCaseList` 完全不受影響),同 S023 自己
   對候選查詢失敗的降級理由一致。沒有 `role="alert"`——這整個功能的
   本質就是「一條通往別處也能到達的捷徑」,查詢失敗時安靜地不顯示,
   不需要用錯誤訊息打斷使用者。
6. **連結文字前綴「繼續診斷:」,不是裸案例標題**——這不只是文案選擇
   ,是結構性必要:見下方獨立一節的完整說明。

## 一個真正的 FIX 循環:連結文字與既有測試的文字碰撞

**與 S020-S023 每一次記錄的「環境負載雜訊」不同,這次 VERIFY 階段
發現的是這個 story 自己造成的真實 bug,不是無關的既有測試偶發抖動
——完整誠實記錄如下。**

**發現**:第一次執行完整 `npx turbo run test --force` 時,E2E 出現 3
個失敗,其中 2 個是 `maintenance-home.spec.ts` 自己既有、已核准的
測試(`E07-S002`「creating a maintenance case for a chosen equipment
adds it to the home list」、`E07-S005`「a typed problem description
becomes the case's title」)。實際錯誤不是逾時,是 Playwright 的
strict-mode violation:`getByText("空壓機 A")` 同時比對到兩個元素
——`MaintenanceCaseList` 自己既有的 `<strong>空壓機 A</strong>`,
以及這個 story 剛新增的 `<a href="...">空壓機 A</a>`。

**根因**:每一個「建立案例」的 E2E 流程都會先落地在
`/maintenance/[id]/session`(依既有邏輯自動建立一個 `OPEN` 狀態的
session),再導回首頁——這代表**任何**建立案例後導回首頁的既有測試
,現在都會**必然**、不是偶發地,同時看到 `ContinueDiagnosisPrompt`
顯示同一個案例。這不是巧合或環境雜訊,是這個 story 的新能力與既有
頁面結構之間真實、決定性的互動,必須正式走 FIX 循環處理,不能歸類為
無關的環境問題。

**判斷「是實作該調整,還是測試該調整」**:兩個既有測試在撰寫當下
(S002、S005)完全正確、完全無歧義——當時頁面上只有一個元素會顯示
案例標題。是這個 story 的新能力讓同一段文字合法地在頁面上出現第二次
,兩個既有測試的 locator 才變得需要更精確。這正是
`.claude/rules/STORY_WORKFLOW.md` Phase 4 第 5 點「非決定性,對是否
测试錯沒有把握時預設當作實作錯」原則下,經過具體判斷後認定屬於
「selector 精確度需要調整」的技術性情況——同 E07-S004/E07-S008/
E07-S018 已經三次採用過的「後面 story 的新能力讓文字子字串產生碰撞
,用 `exact: true` 消歧義」同一類別的窄例外,不是放寬任何斷言本身
要驗證的行為。

**修正(雙管齊下,缺一不可)**:
1. `continue-diagnosis-prompt.tsx`:連結文字從裸標題改成
   `繼續診斷:{title}`。這一步是修正的關鍵——`exact: true` 這個
   既有前例本身**不足以**單獨解決這次碰撞:兩個元素當時都是「自己的
   完整文字內容剛好等於案例標題」,`exact: true` 無法區分兩個「完全
   相等」的文字節點。改成有前綴的文字後,連結自己的完整文字內容
   變成「繼續診斷:空壓機 A」,不再與 `<strong>` 的「空壓機 A」完全
   相等,`exact: true` 才真正能夠消歧義。這個決策同時是真實的 UX
   改善(明確標示「這是可以點擊繼續」而非只是重複顯示標題),不是
   單純為了讓測試通過而硬湊的技巧。
2. `maintenance-home.spec.ts`:對 E07-S002(第 102 行)與
   E07-S005(第 120 行)兩個既有斷言各自加上 `{ exact: true }`
   ,並在旁邊寫清楚原因與這次的既有前例引用。兩者驗證的內容完全
   沒有改變(仍然是「案例標題在首頁列表中可見」),只有 locator
   本身的精確度提高。

**重新驗證**:`pnpm exec playwright test maintenance-home` 單獨重跑
,8/8 全過(含這個 story 自己新增的第 8 個測試)。完整
`npx turbo run test --force` 全量重跑:87→89 個 unit 測試檔案、
1180/1180 unit test、**200/200 E2E 全過(這次連通常不穩定的
E05-S031 都一併通過)**。
