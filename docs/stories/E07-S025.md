# E07-S025 — maintenance E2E

- Branch: `story/E07-S025-maintenance-e2e`
- Date: 2026-08-16
- Status: DONE

**這是 E07 Maintenance Assistant Experience 的最後一個 story。**

## Scope 說明

SOURCE_BASELINE/epic 檔對這個 story 沒有任何專屬內容,只有通用樣板文字
+ 標題。標題本身就是交付物的直接描述:一個橫跨既有多個能力的綜合
E2E 測試。這與 `E03-S033`(conversation E2E with mocked backend)、
`E05-S031`(Knowledge UI E2E)是完全相同的既有前例——兩者都是各自
epic 的收尾 story,都是**純測試 story,零原始碼變更**,都是稽核既有
spec 檔案找出「單獨驗證過,但從未一起組合驗證過」的落差,而不是重測
已經驗證過的東西。

**核心設計決策**:

1. **零原始碼變更**——完全比照 E03-S033/E05-S031 的既有慣例。這個
   story 只新增一個測試檔案,不改動 `apps/web/src` 底下任何一行。
2. **稽核方法**:完整讀取現有 5 個 maintenance-domain E2E spec 檔案
   (`case-detail.spec.ts`、`maintenance-history.spec.ts`、
   `maintenance-home.spec.ts`、`maintenance-report.spec.ts`、
   `maintenance-session.spec.ts`,橫跨 S001-S024 共 21 個測試),
   逐一確認每個既有測試的範圍,找出真正的**組合層級**落差,而非
   單一功能落差(單一功能早已被各自的 story 測過)。具體發現:
   - 每一個既有測試永遠只建立**一個**案例,永遠只操作**一個**
     功能/頁面。
   - 補充說明+附加照片從未與 AI 說明/SOP 引用來源在同一次提交裡
     組合出現。
   - `上一步`(goToPreviousStep)自己會清空
     `lastFreeTextDetail`/`lastPhotoFileName` 這件事(不只是清空
     `currentStepIndex`)只有 lib 層的 unit test 驗證過,從未在
     E2E 層、搭配真正的照片上傳一起驗證過。
   - `case-detail`/`history`/`report` 三個頁面從未在**同一次**
     測試裡同時看到超過一個「正在被操作」的案例——沒有任何測試
     證明這三個頁面在多案例同時存在、狀態互不相同時,彼此仍然保持
     一致。
   - `重新開始` 的重置效果只在 session 頁面自己身上驗證過,從未
     確認這個重置會正確反映到 case detail/history 這兩個**獨立
     重新查詢**同一份底層資料的頁面上——理論上有可能重置只在
     session 頁面自己的 in-memory state 生效,而其他頁面若有任何
     快取/推導邏輯錯誤就可能繼續顯示舊資料。
   - `case-detail.tsx` 自己的「查看診斷內容」連結,S021 自己的既有
     測試只驗證過它的 `href` 屬性,從未真的點擊過,沒有證明這個
     連結真的能把使用者帶回正確的、活著的 session。
   - 沒有任何既有測試呼叫過 `page.reload()` 或等效的真實硬重整。
3. **兩個測試,同 E03-S033/E05-S031 的既有形狀**——「全部功能組合在
   一起仍然成功,且撐過真實重整」+「一個動作(重新開始)的效果正確
   傳播到每一個相關頁面,不只是動作發生的那個頁面」。

## Gate 紀錄

**0 次 FIX 循環**——但誠實記錄一個真實的測試撰寫過程中的自我修正,
不是環境雜訊,也不是需要走 Phase 4 FIX 循環的紅燈(因為發生在還沒有
提交任何內容之前,是撰寫測試當下就發現並修正的):

第一次執行 `pnpm exec playwright test maintenance-e2e` 時,測試 1
在「`上一步` 後確認補充說明與照片仍然可見」這個斷言失敗。追查後發現
是**測試自己對既有行為的假設錯誤**,不是實作 bug——直接讀取
`goToPreviousStep` 的既有原始碼(第 291-313 行)確認它會清空
`lastSelectedOptionId`/`lastFreeTextDetail`/`lastPhotoFileName`/
`lastPhotoSizeBytes`(不只是 `currentStepIndex`),這是 S010 自己
既有、已核准的行為,合理(「回上一步」意味著要重新回答,不是保留
舊答案)。修正測試本身的假設:改成斷言這些欄位在回上一步後**消失
**,並在流程裡重新提交一次補充說明+照片,讓後續測試 1 的其餘斷言
(case detail 顯示補充說明/照片)有正確的資料來源。這個修正沒有
碰觸任何既有原始碼或既有測試,只調整這個 story 自己全新、尚未核准
的測試檔案本身。

**SELF-REVIEW 階段對抗性複驗(證明新測試不是空殼斷言)**:由於這個
story 沒有新增任何原始碼可以突變,改為對**既有、已核准**的
`restartDiagnosticSession`(`diagnostic-sessions.ts`)做對抗性突變
,驗證這個 story 新增的測試 2 是否真的在檢查真實行為,而不是巧合
通過。先確認 `git status --short` 顯示已完整 staged,再把
`restartDiagnosticSession` 裡清空 `lastEscalationReason` 那一行
刪除(模擬「新增 completion 欄位時,不小心漏刪 escalation 欄位」
這個具體 bug)。重跑 `pnpm exec playwright test maintenance-e2e`:
**測試 2 立即在第一個相關斷言失敗**(session 頁面自己的
`已升級` 文字仍然存在),測試 1 不受影響(它不涉及升級/重新開始),
證實這個 story 新增的跨頁面一致性測試確實是真實、有效的保護,不是
巧合通過的空殼。

**還原過程的一個操作失誤,誠實記錄**:第一次執行 `git checkout --`
還原這個突變時,因為前一個 `pnpm exec playwright test` 指令把當前
shell 目錄留在 `tests/e2e/` 底下,`git checkout --
apps/web/src/lib/diagnostic-sessions.ts` 被解讀成相對於
`tests/e2e/` 的路徑,得到 `pathspec did not match` 錯誤,還原**沒有
真的發生**。立即透過 `git status --short`/`git diff --stat` 發現
突變仍在,`cd` 回 repo 根目錄後重新執行 `git checkout --` 才真正
還原成功,並重新完整跑過 `maintenance-e2e` 兩個測試確認 2/2 全過、
`git status` 乾淨作為最終確認。記錄這件事是因為它正是「已核准原始碼
被還原前必須先確認 `git diff` 真的為空」這個既有紀律存在的理由
——差一點就因為工具層面的路徑失誤讓已核准程式碼帶著沒被注意到的
突變繼續往下走。
