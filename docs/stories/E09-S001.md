## Scope 說明

E09(AI ERP & Reporting Experience)的第一個 story,對應 `nav-items.ts`
早在 E01-S006/S009 就已存在、但一直指向不存在頁面的 `/erp` entry
(role-gated 給 `sales_purchasing`/`super_administrator`)。這是該路由
第一次真正渲染內容,而不是落到 Next.js 自己的 not-found——與
E07-S001「Maintenance home」對 `/maintenance` 的關係完全對應。

E10(Enterprise Data Integration,Team B)目前 `contracts/` 內零 erp/E10
命中,E10 本身是 Team B 的獨立 epic。依 SOURCE_BASELINE §5 pinned 決策
#35(「Team A 不等待 Backend 完成才開始」)與 E05/E07 全程建立的先例,
本 story 建立純前端 mock,不等待/不假裝 E10 已存在。

## 設計決策

**直接複用 E07-S001「Maintenance home」已驗證過的「landing list」形狀**,
而非猜測新設計:

1. 讀取 `docs/stories/E07-S001.md` 自己的 EVIDENCE 得知,E07-S001 當初
   也面對同樣的「home」boilerplate AC 模板文字(所有 story 的四類 AC
   文字都相同,只有標題不同),其推理路徑是:(a) Testing Boundary 要求
   「Unit: happy path + validation + permission + error mapping」與
   Negative path 涵蓋 dependency failure——純靜態頁面無法誠實滿足,因此
   S001 必須是一個真實(mock)的非同步讀取,而非純連結頁;(b)「home」與
   後續專屬 story(E07 是「history」,E09 是「Query history」/E09-S015)
   分屬不同 story,「home」不能搶「history」的範圍(搜尋/分頁/完整清單)。
   這兩條推理對 E09-S001 同樣成立,直接套用而非重新推導。
2. 結論:S001 = 一個唯讀的「最近 ERP 查詢」清單 landing page,有真實的
   loading/error/empty/loaded 狀態,鏡射 `MaintenanceCaseList`
   (E07-S001)/`KnowledgeList`(E05-S001)的既定形狀。**不**加入任何
   「開始新查詢」連結——E09-S002「Natural-language query composer」是
   那個流程真正的第一步,對應路由目前不存在,加入連結會是「連到還不存在
   的路由」,同一條 `MaintenanceCaseList`/`KnowledgeList` 自己的 doc
   comment 已經立下的紀律。
3. 清單項目本身也刻意不加連結——E09 的 24 個 story 中沒有任何一個是
   per-query detail 頁面(E09-S015「Query history」是專屬的完整瀏覽
   story,不是 detail 頁),所以連結永遠沒有目標路由可指。

**`ErpQuerySummary` 型別刻意最小化**:只有 `id`/`questionText`/
`createdAt` 三個欄位,鏡射 `MaintenanceCaseSummary` 當初的
`id`/`title`/`updatedAt`。`resultRows`/`sqlPreview`/`scenario` 等欄位
刻意不在此提前建立——同一種「欄位屬於真正擁有它的 story,不要提前發明」
紀律。`questionText` 是使用者輸入的自然語言問題全文,扮演
`title`(維修案例)/`name`(知識庫)已經扮演過的角色。

**`route-guards.spec.ts` 的既有測試移除,而非新增/修改**(誠實記錄,
非測試凍結例外的濫用):INIT 階段讀取該檔案時發現,它自己的 doc comment
早已明確預告本story這個時刻——「This file always used /maintenance as
its sole 'no page yet' example... E07-S001 built the real /maintenance
page, so the example below moves to /erp... Once E09-S001 ships its own
first /erp page, this test will have no remaining role-restricted-but-
unbuilt route left to target and should be removed rather than moved
again.」逐一確認 `nav-items.ts` 的 `NAV_ITEMS`(5 筆:`/`、
`/conversations`、`/knowledge` 皆 `roles: "all"`,只有 `/maintenance`
與 `/erp` 是真正 role-restricted),確認 `/erp` 確實是最後一個「role-
restricted 但沒有頁面」的路由,且沒有其他候選路由可以移過去(E11/E13
都還沒開工,`nav-items.ts` 裡完全沒有它們的 entry)。因此依該檔案自己
先前立下的指示移除該測試,而非修改其斷言邏輯——這不是「放寬測試配合
實作」,是測試自己的前提(存在一個 role-restricted 但無頁面的路由)
永久不再成立。該檔案剩下的另一個測試(unknown route → not-found)完全
不受影響,獨立驗證通過。403 guard 的實際 deny 渲染邏輯本來就是在
component 層(`role-guard.test.tsx`)驗證,不依賴任何真實頁面存在,
不受此次移除影響——已直接讀取 `role-guard.tsx` 原始碼確認其 deny 邏輯
完全 route-agnostic(唯一 route-specific 的部分是純函式
`rolesRequiredFor()`,由 `nav-items.test.ts` 既有測試涵蓋,本 story
未觸碰 `nav-items.ts`)。

- Functional AC 2(validation error)與 AC 5(重複請求 side effect)
  對本 story 不適用——純讀取、無使用者輸入的 landing page 沒有這兩種
  情境,與 E07-S001 當初的判定一致。
- Functional AC 7(audit event)對本 story 不適用——讀取的是 mock 種子
  資料,不是真實 ERP 資料或 AI-generated SQL 執行(SOURCE_BASELINE

  段落詳細記錄判斷依據(該檔案自己的 doc comment 明確預告 + 直接確認
  沒有其他候選路由可移轉 + 該測試涵蓋的邏輯改由更早、更貼近實作的
  component 測試獨立覆蓋),不屬於「放寬測試配合實作」的禁止行為。
- SAMPLE_ERP_QUERIES 的 3 筆種子資料為虛構的自然語言問題範例(營收
