## Scope 說明

E09 的第四個 story,直接對應 E09-S003 自己的 doc comment 早已預告的
延伸點——`matchErpScenarios` 零匹配時的 fallback(顯示全部情境),
S003 自己只保證「picker 永遠不空」,把「用更好的方式呈現這個情境」
留給本 story。

## 設計決策

**新增獨立函式,不修改 `matchErpScenarios` 的既有簽章**:這是本 story
最核心的判斷。原本考慮讓 `matchErpScenarios` 回傳一個帶
`confident: boolean` 的物件而非純陣列,但這會是 breaking change,直接
牴觸 E09-S003 自己已核准、凍結的測試(`erp-scenarios.test.ts` 既有
斷言把回傳值當純陣列處理,例如 `expect(matches).toEqual(ERP_SCENARIO_OPTIONS)`)
——修改這些斷言的資料結構屬於「修改既有測試內容配合實作」,不屬於
Phase 4 第 5 點的窄例外(這不是測試自己寫錯,是本 story 想要不同的
資料形狀)。改為新增一個完全獨立的 `isAmbiguousErpQuery(questionText)`
函式,內部與 `matchErpScenarios` 共用同一個私有 `realMatches` helper
(避免兩者對「什麼算匹配」的判斷分裂),但 `matchErpScenarios` 自己的
簽章、行為、既有測試全部零異動——`git diff` 已確認 `erp-scenarios.test.ts`
既有的 3 個 `describe("matchErpScenarios (E09-S003)"...)` 測試區塊
完全沒被修改,只有新增。

**只換文案,不做真正的澄清對話**:AC 8 明確允許 MVP 簡化演算法但不能
省略能力本身。「Clarification UI」的最小誠實實作,是在偵測到零匹配
(`isAmbiguousErpQuery` 為 true)時,把 S003 中性的「請選擇最符合您
問題的查詢情境:」換成明確承認不確定、引導使用者選擇或換句話說的文案
——picker 本身(選項清單、點擊行為)完全不變,只有 prompt 文字分支。
真正的重新輸入問題/多輪對話式澄清,屬於本 story 明確排除的範圍(不在
`erp/[id]` 現有的最小 shell 裡發明新的輸入框)。

**`erp-queries.ts` 零異動**:本 story 純粹是「怎麼呈現既有的匹配結果」
的問題,不涉及任何資料模型或 mutate 邏輯變更——`git diff main --stat --
apps/web/src/lib/erp-queries.ts` 確認空白。
