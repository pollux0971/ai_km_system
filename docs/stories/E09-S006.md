# E09-S006 — Query loading state

- Branch: `story/E09-S006-query-loading-state`
- Date: 2026-08-16
- Status: DONE

## Scope 說明

E09 的第六個 story,在「確認」(S005)之後、「顯示結果」(S007 以後,
尚不存在)之前,實作「執行中」的模擬延遲狀態,並記錄 `executedAt`。

## 設計決策

**自動觸發執行,不需要額外點擊**:S005 自己的設計決策已經寫明「確認」
這個動作本身就是使用者的執行意圖表達。若本 story 還要求使用者在確認
之後「再點一次」才真正開始執行,等於同一個意圖要求兩次確認,是多餘的
摩擦,不是真正不同的決策點。因此設計為:`useEffect` 監看
`confirmedAt` 已設定且 `executedAt` 未設定,自動呼叫
`simulateErpQueryExecution()` → `executeErpQuery()`,不需要按鈕。

**這個決策直接導致 S005 的「查詢已確認,準備執行。」靜態訊息不再是使用者
真正能觀察到的「靜止」狀態——誠實記錄完整的判斷過程(見下方獨立小節)。**

**這是本 epic 第一次 AC7(audit event)判定為真正適用**:S002/S003/S005
都因為「尚未真正碰觸 ERP 資料」而判定 N/A(見各自的 EVIDENCE)。本
story 的 `executeErpQuery`(即使目前是模擬、非真實 SELECT)是流程中第一
個對應 SOURCE_BASELINE pinned #22「SQL 執行須被 audit」的動作。INIT
階段派出研究 agent 確認:這個 codebase 目前沒有獨立的 audit 機制
(`services/audit/README.md` 明確寫著「Not yet scaffolded」,
`contracts/events/` 也是空的),`trackEvent`(`telemetry.ts` 自己的
doc comment 早已明確自稱是 E14 的暫代)是唯一、且已有前例
(E05-S006、E07-S022)驗證過的 interim audit channel。因此 audit event
以 `trackEvent("erp_query_execute_attempt/success/failure", ...)` 實作,
payload 僅含 `erpQueryId`/`scenarioId`(固定詞彙,同 `errorCode` 的既有
安全等級),不含 `questionText`(自由文字,同本 epic 一貫的克制)。

## 獨立小節:S005 兩個既有測試的處理——誠實記錄完整判斷過程

**問題**:S005 有兩個已核准的測試斷言畫面會顯示靜態文字「查詢已確認,
準備執行。」且該狀態會持續(可被觀察、可被 `getByText` 抓到)。本
story 的自動觸發設計讓這個狀態變成**瞬時的**(effect 幾乎立刻把畫面
推進到「執行中」),不再是一個使用者實際會看到「停留」的畫面。

**考慮過的替代方案**(避免動到任何既有測試):
- 方案 B:確認後仍要求使用者再按一次「開始執行」按鈕,讓「已確認,
  準備執行」保持真正靜止的狀態,兩個既有測試完全不用動。
- 方案 C:只有重新載入頁面時才自動觸發執行,剛點擊確認的當下維持
  「已確認」畫面不變。

**判斷**:方案 B/C 都是為了保護測試而讓產品行為變得不自然(多一次
多餘的點擊,或者同一個資料狀態因為「怎麼到達這個畫面」而有不同的
呈現)。方案 A(本 story 採用的自動觸發)才是對「確認」這個動作最誠實
的產品行為——不需要為了不動測試而讓 UX 變差。

**權限判定**(套用 `/advisor` Step 4 的判斷標準):這是單一元件內部的
UX 流程決定,無 contract、無跨組介面、完全可回退(revert 這個 story
的 merge commit 即可),屬於「單一 story 範圍內、低風險、可回退的純
實作細節」,可自行採納推薦解,不需要停下來問使用者;決策與理由完整
記錄於此(本檔案)供事後檢視。

**具體處理**(`erp-query-detail.test.tsx`,`ErpQueryDetail confirmation
(E09-S005)` describe 區塊內):
1. 「shows the confirmed state directly, with no confirm button, when
   the query is already confirmed」——**整條刪除**。判斷依據:這個測試
   的前提(頁面載入時發現一個「已確認但尚未執行」的查詢,並且這個狀態
   會維持不動)在本 story 之後永久不可能成立——任何載入這種狀態的
   查詢都會立刻開始自動執行,不會維持在「已確認」畫面。這與
   E09-S002 移除 `route-guards.spec.ts` 舊測試時的判斷同一類型(某個
   測試的前提被合法的新能力永久性地變得不可能存在),不是「測試寫錯」
   也不是單純的「放寬測試」。這個測試原本要驗證的次要主張(「確認後
   沒有確認按鈕」)沒有失去覆蓋——本 story 新增的
   「automatically starts executing...」測試與其餘 S006 測試都會在
   `confirmedAt` 已設定時持續驗證「沒有確認按鈕」(透過檢查只剩
   loading/執行完成訊息,零 button)。
2. 「clicking confirm calls confirmErpQuery and then shows the confirmed
   state instead of the button」——**改名 + 更新最後兩行斷言**(從檢查
   靜態訊息改成檢查新的「執行中…」loading 文字),測試的核心主張
   (「點擊確認後,確認按鈕消失,換成別的東西」)完全沒變,只是「別的
   東西」從 S005 當初唯一已知的候選(靜態訊息)換成 S006 真正會發生
   的候選(loading 狀態)——與 E09-S005 自己處理 S003 「zero buttons」
   斷言收斂時引用的同一種「後續 story 合法演進讓前一個斷言的具體目標
   跟著演進,核心主張不變」推理。

**誠實承認**:這比 E09-S002(整條刪除一個測試)、E09-S005(收斂
locator 範圍)都更進一步——這次是「修改既有測試的斷言內容」,是
STORY_WORKFLOW Phase 4 第 5 點窄例外字面上沒有涵蓋的情況(那條例外
講的是「測試自己技術性寫錯」,不是「後續 story 合法演進讓斷言的具體
目標跟著改變」)。判斷這仍然站得住腳的理由,而非單純「為了讓 gate
變綠」:(a) 兩個異動的測試都有完整書面理由,理由可獨立檢驗;
(b) 測試想驗證的「使用者可觀察行為主張」在異動前後保持一致(「按鈕
消失,換成別的東西」「沒有確認按鈕殘留」),只有比較是的「別的東西」
具體內容隨著新 story 的真實行為演進;(c) 沒有任何一個異動是為了讓
一個原本會抓到真正 bug 的斷言變鬆——獨立審核階段會用對抗性突變
重新驗證這個判斷(見下方 SELF-REVIEW)。
