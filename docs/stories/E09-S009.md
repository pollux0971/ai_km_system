# E09-S009 — Server pagination UI

- Branch: `story/E09-S009-server-pagination-ui`
- Date: 2026-08-16
- Status: DONE

## Scope 說明

E09 的第九個 story,在「結果表格」(S008)之後,為表格加上分頁控制——
「顯示結果」子流程(S007-S011)的第三個。這個 mock 系統沒有真正的伺服器
可分頁查詢(見 `erp-execution.ts` 自己的 doc comment:整個「執行」都是
模擬的),所以這是「呈現上長得像伺服器分頁」的 client-side 分頁,對
`getErpResultTable()` 已經完整讀進記憶體的小表格做切片。

## 設計決策(precedent research)

**先查既有先例,再動手**:實作前先確認這個 codebase 有沒有既有的分頁
元件/樣式可以照抄,而不是自己發明一套。搜尋後發現:
- `packages/ui` 沒有共用的 `Pagination` 元件。
- 唯一的既有分頁 UI 是 `conversation-list.tsx`(E03-S022,`
  maintenance-history-list.tsx` 自己的 doc comment 稱其為「E03 裡唯一
  的分頁 story」,放大來看也是整個 app 目前唯一的分頁 UI)——local
  `page` state、只有 prev/next(明確拒絕了頁碼連結,理由是「涵蓋
  『瀏覽所有頁』的最簡單 UI」)、`<nav aria-label="...">` 包裹
  上一頁/下一頁按鈕與「第 X 頁,共 Y 頁」文字。
- `packages/types`/`packages/validation`/`contracts/openapi/core.yaml`
  雖然定義了一個 `Pagination { page, pageSize, total }` 型別,但目前
  沒有任何實際功能真的使用它——唯一真正上線的分頁功能
  (`conversations.ts`)用的是自己的一套詞彙
  `{ items, page, pageSize, totalCount, totalPages }`。

**決定**:比照 `conversation-list.tsx` 的 UI 形狀(prev/next-only、
`<nav>`+頁碼文字)與 `conversations.ts` 的詞彙(`page`/`pageSize`/
`totalPages`),而非套用未被使用過的 contract 型別——這是「跟已經被
驗證過的實作模式一致」優先於「跟目前沒人用的 scaffold 型別一致」。

**Page size 刻意選小(2),不是隨便選的**:4 個白名單情境的表格只有
3-5 列(S008 自己的 mock 資料)。若沿用 `conversations.ts` 那種為了
真實大量資料設計的頁面大小,4 個情境會全部剛好只有 1 頁,分頁按鈕
永遠不會真的被使用者按到、也永遠無法在測試裡真正驗證翻頁行為——這樣
雖然「程式碼存在」,但違反 AC 8「MVP 可以簡化視覺或演算法,但此能力
本身不可缺席」的精神(能力形同虛設)。選 2 讓 4 個情境都至少有 2 頁
(revenue-by-branch 3→2 頁、low-stock-items 5→3 頁、
overdue-receivables 4→2 頁、purchase-order-status 4→2 頁),確保分頁
能力在每個情境都真正可被觸發與測試。

**純函式 + component-local state,不做 async 假分頁**:`
paginateErpResultTable(table, page, pageSize?)` 對已經在記憶體裡的
`ErpResultTable` 做同步切片,不像 `conversations.ts` 的
`listConversations()` 需要模擬一次新的非同步請求——因為執行結果本身
(S006 已經模擬過、已經被 audit 過)在這裡不會因為換頁而重新取得或重新
判斷權限,純粹是同一份已授權資料的呈現切片。

**獨立檔案**:`erp-result-table-pagination.ts` 不併入 `
erp-result-tables.ts` 本身——「表格內容是什麼」(S008 的責任)與
「怎麼把表格切成一頁一頁」(本 story 的責任)是不同關注點,同一種
「每個 story 管自己的檔案」既有紀律。

**AC 2-7 判定不適用**:翻頁不是新的使用者輸入驗證情境(沒有欄位可能
缺漏)、不是新的非同步 dependency(純同步切片)、不會讀取任何原本未
授權的資料(整張表格本來就已經在記憶體裡)、沒有新的敏感操作需要
audit——與 S007/S008 判定 AC 2-7 不適用的理由完全相同。

## 既有測試的必要窄化(narrowing,非刪除)

S006 在「執行完成」這個靜止畫面留下一條斷言:「這個狀態底下沒有任何
按鈕殘留」(unit test 用 `querySelectorAll("button")).toHaveLength(0)`
、E2E 用等價的 `getByRole("main").getByRole("button")).toHaveCount(0)`
)。這條斷言原本的真正意圖是「沒有殘留的、還在推進查詢流程的按鈕(如
確認/重試)」,在 S006-S008 都成立,因為當時真的沒有任何按鈕存在。

本 story 在同一個畫面合法新增了上一頁/下一頁這兩個**瀏覽用**按鈕——
性質上與「推進流程」的按鈕完全不同(瀏覽已經完成、已經被授權過的結果
,不會產生新的 side effect 或新的資料存取)。這讓「零按鈕」這個原始
斷言的前提(沒有任何按鈕)不再成立,但斷言真正要防的事(沒有殘留的
流程推進按鈕)完全沒有改變。比照 S003→S005 既有的窄化先例(把「零
按鈕」窄化成「picker 自己的按鈕消失」),本 story 把這兩處斷言窄化為
「排除分頁 nav 之後零按鈕」:
- Unit test:改用 JS `.filter()` 排除落在 `role=navigation
  name="查詢結果分頁"` 內的按鈕(jsdom 環境下不依賴 CSS `:not()`
  接受複雜選擇器的瀏覽器實作細節)。
- E2E test:改用 Playwright/瀏覽器原生支援的 CSS 選擇器
  `main button:not(nav button)`(Selectors Level 4,Chromium/Firefox/
  WebKit 皆已支援多年),保留原斷言「排除已知合法例外後,不允許任何
  其他未預期按鈕殘留」的完整防護力,而非退化成寫死數字(如
  `toHaveCount(2)`)——寫死數字會失去「保護任何未預期按鈕」的原始
  用意,也是 S008 獨立審核才剛發現的「魔術數字跨檔案漂移」風險的
  同類陷阱,這次直接避開。

S008 自己新增的「執行完成後顯示情境專屬表格(每個欄位、每個儲存格)」
測試,同樣因為本 story 讓「所有列一次全部顯示」的前提不再成立而窄化為
「顯示表格欄位 + page 1 自己的儲存格」,並新增本 story 自己的測試涵蓋
換頁後其餘列的顯示(見下方「變更檔案」的測試清單)。

兩處窄化的判斷依據與 S005→S006 相同的準則:先確認被窄化斷言原本要
防的事(而非字面斷言)在窄化後仍然被覆蓋,而不是單純放寬到測試變綠
為止——兩處都額外新增了本 story 自己的測試,明確覆蓋「換頁後,前一頁
的內容真的消失,後一頁的內容真的出現」這個更完整的行為,不是只刪減
舊斷言而沒有補強。
