# E09-S011 — Chart renderer

- Branch: `story/E09-S011-chart-renderer`
- Date: 2026-08-16
- Status: DONE

## Scope 說明

E09 的第十一個 story,在「KPI 卡片」(S010)之後,加一個長條圖呈現查詢
結果——「顯示結果」子流程(S007-S011)的最後一個。至此摘要文字/表格
/分頁/KPI 卡片/圖表五種呈現形式全部到齊,S012 起進入不同的子流程
(applied-filter/data-freshness/source-system 等中繼資訊呈現)。

## 設計決策

**沒有既有圖表函式庫,不新增依賴**:實作前搜尋確認
`packages/ui`、`apps/web/package.json`、`pnpm-lock.yaml` 全部沒有任何
圖表函式庫(recharts/chart.js/victory/visx/nivo/apexcharts/d3 等零
命中)。這個 epic 至今沒有任何 story 新增過 npm 依賴,新增一個圖表庫
是比「加一個檔案」重得多、更難回退的決定(套件、bundle size、往後的
維護面)。AC 8 明確允許「MVP 可以簡化視覺」,因此選擇手刻一個
零依賴、純 CSS 寬度比例的水平長條圖,而不是引入新依賴。

**長條資料直接來自表格本身,不是另一份手寫資料**:同一種
`erp-result-kpis.ts` 已經建立的「衍生而非手寫」紀律(直接回應
E09-S008 獨立審核抓到的跨檔案數字漂移教訓)。每一根長條的 label 是
該列第一格(`row[0]`)、旁邊顯示的文字是該列第二格(`row[1]`)原文
——兩者都是表格已經核准、已經顯示過的既有內容,不是重新計算或猜測
出來的新數字。

**用第二欄位驅動長條寬度,失敗則整體退回等寬**:4 個情境的表格結構
不同,不是每個情境的第二欄位都是數字(`purchase-order-status` 的
第二欄是「供應商」,是人名/公司名文字)。與其為每個情境各自寫一套
「這個情境該抓哪一欄」的特判邏輯(容易出錯、難以維護、也是另一種
沒有真相來源的猜測),選擇統一規則:嘗試解析每一列的第二格
(`parseNumericCell`,處理 `NT$`/千分位逗號/`%`/`+` 前綴這些既有
mock 資料實際出現過的格式);只要表格裡「任何一列」解析失敗,整張
圖表就退回等寬長條(仍然把每一列都畫出來,只是不假裝有量化比例)
——寧可誠實地退化成「條列」也不要顯示錯誤或誤導的比例。

**AC 2-7 判定不適用**:與 S007-S010 判定理由相同——圖表是純衍生
呈現層,沒有新的使用者輸入、非同步 dependency、資料存取、或敏感操作。

(E09-S011)」describe 區塊新增 1 個測試「renders each bar's visual
