## 設計決策
1. **格式:CSV(Excel 可直接開啟),非真二進位 `.xlsx`。** 理由:(a) 全 monorepo grep 確認零 `xlsx`/`exceljs` 等產生二進位 Excel 格式的套件依賴(`package.json`、`pnpm-lock.yaml` 皆零命中)——比照 S011 圖表元件「零現有 charting library 依賴」的相同查證紀律;(b) AC8 明確允許「MVP 可以簡化視覺或演算法,但此能力本身不可缺席」;(c) 此 codebase 已有直接可比對的既有先例:`maintenance-report.tsx`(E07-S022)的 `casesToCsv` + `data:` URI 下載,是這個 codebase 目前唯一的匯出/下載功能,其自身 doc comment 確認從未抽出任何共用工具(csv 建構/跳脫邏輯完全 bespoke),所以 `erp-result-export.ts` 是仿照相同技法重寫的新檔案,不是跨 epic import。下載檔名誠實維持 `erp-query-result.csv`,只有可見的連結文字用「匯出 Excel」表達這個 story 自己命名的產品意圖(CSV 是 Excel 可直接雙擊開啟的通用格式,不是誤導)。
2. **匯出完整表格,非目前分頁畫面。** `getErpResultTable(scenarioId)` 的完整回傳值,而非 `paginateErpResultTable` 的目前頁切片——匯出的使用者預期是拿到整個結果集,不是螢幕上恰好顯示的那一頁。已用對抗性突變驗證這個決策真的被測試守護(見下方「對抗性自我驗證」)。
3. **不建立共用 CSV 工具檔跨 epic import。** 研究確認 E07-S022 自己的 `casesToCsv`/`escapeCsvField` 從未被抽成共用套件——直接 import `maintenance-report.tsx`(page-local component)會是不恰當的跨 epic/跨 domain 耦合,不符合開發邊界「不得直接讀寫其他 Domain 的 private table、private module」的精神。改為在 E09 自己的 domain 內重寫一份小型、獨立的等價邏輯,符合 E07-S022 自己當初「這是全 codebase 第一個匯出功能,沒有既有先例可循」時的相同處理方式。
4. **S017「Export progress」明確排除在本 story 之外。** 已讀取 S017 完整章節(同樣是純標題 boilerplate,無更多細節),確認它是獨立的下一個 story。本 story 的 CSV 產生是同步、記憶體內運算(小型 mock 表格),沒有真正的非同步落差需要進度指示——不提前發明 S017 自己的能力,同 S008 對 S009 分頁、S006 對 S013 徽章已建立的「不搶下一個 story 的範圍」紀律。
5. **AC2/AC4/AC5/Security AC 判定 N/A 的理由:**
   - AC2(缺少必要輸入 fail-closed):本功能無使用者輸入表單,是對既有已授權資料的純顯示衍生匯出;等效的「資料不存在就不給動作」情境由「執行完成前不顯示匯出連結」測試涵蓋。
   - AC4(dependency timeout/unavailable):純前端同步字串生成,不呼叫任何外部 dependency,無逾時/不可用情境可測。
   - AC5(重複請求的未定義 side effect):每次點擊只是重新觸發瀏覽器對同一份已算好靜態內容的下載,加上各自獨立的 telemetry 事件(這正是預期行為,不是需要防範的重複 side effect)——沒有伺服器端 mutation、沒有持久化狀態變更。
   - Security AC(未授權來源不得進入 export):此功能沒有引入新的資料存取面——匯出的就是頁面本身已經授權顯示的同一份 `getErpResultTable` 結果,沿用 E01 建立的既有 role-gate(`/erp` 路由已限定 sales_purchasing/super_administrator),不是新的洩漏管道。
