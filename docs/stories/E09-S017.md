## 設計決策
1. **為什麼需要改變 S016 的觸發機制,而不是單純疊加。** S016 的匯出是同步、瞬間完成的(小型記憶體內字串運算),`<a>` 連結一直是「已經算好、隨時可下載」的狀態——沒有任何「進行中」的時間窗可以顯示進度。要讓「Export progress」這個 story 名稱描述的能力真正存在(AC8:「此能力本身不可缺席」),必須先讓匯出這件事有一段可觀察的執行時間,同 S006 當初用 `simulateErpQueryExecution` 給查詢執行一段可觀察時間的完全相同理由。一個一直存在、立即可點的 `<a>` 元素沒有辦法表達「pending」狀態,所以改成 `<button>` + state 是這個故事名稱本身要求的必要手段,不是無關的重構。
2. **自動轉場,不需要第二次點擊。** 點擊「匯出 Excel」後直接進入「匯出中…」再自動觸發下載,不要求使用者在進度結束後再點一次才下載——同 S006「確認後自動開始執行,不需要第二次『真的執行』的點擊」已建立的先例。
3. **telemetry 拆成 attempt/success,不是保留 S016 原本單一事件再加一個。** S016 的 `erp_query_export` 原本只在點擊當下發一次,代表的是「使用者點了」而非「匯出成功了」。現在有真正的起訖時間,拆成 attempt/success(共用 correlationId)才誠實對應 AC6「成功與失敗路徑皆具有 correlation id / structured telemetry」——同檔案內 `erp_query_execute_attempt`/`_success` 已經是這個確切命名慣例。延遲本身必定成功(同 `erp-execution.ts` 自己的「Always succeeds」doc comment 一樣的計時原始函式,不是真正可能失敗的操作),所以沒有對應的 `_failure` 事件。
4. **下載觸發手法:detached `<a download>` 程式化 click,而非保留渲染中的連結。** appendChild → click → removeChild,是業界對「以程式碼觸發下載」常見且相容性良好的做法。單元測試用攔截 `HTMLAnchorElement.prototype.click` 取得下載當下的 anchor 內容直接斷言,不需要 jsdom 真正實作 navigation;E2E 則用 Playwright 的 `page.waitForEvent("download")` 驗證瀏覽器真的收到下載事件,同 S016/E07-S022 已建立的驗證分工不變。

(...) : (...)`。結果:精準命中同一個 describe 區塊內 6 個測試中的 5 個失敗(僅「執行完成前不顯示按鈕」不受影響,因為那個測試驗證的是外層 `executedAt` 判斷式,不涉及內層 `exportPending` 分流),其餘 46 個測試維持通過——證實 pending 狀態的分流邏輯被廣泛且精準地守護,反轉後幾乎整個區塊都會示警。已用 `git checkout --` 還原,`git diff --stat` 確認乾淨,兩個測試檔重跑全綠(53/53)。
