## 設計決策
1. **「Prediction 情境」不是第二個業務情境白名單,而是預測的時間範圍。** 動筆前完整查證:`SOURCE_BASELINE.md` 全文、本 epic 檔全文、`docs/adr/`、`TRACEABILITY.md`、`readme_zh.md`,除了故事標題本身之外零命中任何更具體的定義(SOURCE_BASELINE 只把「Prediction」列為與 Table/KPI/Chart/Excel Export 同一批「ERP AI」能力之一,沒有描述預測什麼或如何預測)。Pinned #19-21 明確只定義了**一個**查詢情境白名單(`ERP_SCENARIO_OPTIONS`);若把「Prediction scenario selector」理解成「再選一次業務情境」,等於是在前端自行發明一個 spec 未授權的第二套業務分類,不符合「不發明 contract」與 Anti-hallucination Guard 的精神。改為把 story 標題裡的「scenario」讀作「可選項」而非業務情境的再選擇——`ERP_PREDICTION_HORIZONS` 是針對「這筆查詢已經選定的業務情境」的時間範圍選項(下月/下季/下年),不是與 `ERP_SCENARIO_OPTIONS` 競爭的第二白名單。
2. **純 local state,不寫回 mock 後端。** 比照 `tablePage`(E09-S009)的既有先例——這是一個沒有真正後端後果的顯示選擇,不像 S003 的 `selectErpQueryScenario` 是會被稽核的真實狀態變更。不新增 `erp-queries.ts` 的欄位或函式,避免無授權地擴張 mock 契約形狀。
3. **自由切換的 toggle 群組,不是 S003 式的一次性 picker。** S003 選定後 picker 消失、換成已選標籤顯示,因為那個選擇有真實後果(決定哪個 SQL view 執行)。這裡的時間範圍切換沒有那種後果,鎖死成單向選擇只會增加不必要的摩擦,所以用 `aria-pressed` 的 toggle-button 語意讓所有按鈕持續可見、可自由切換。
4. **重複點擊已選取的範圍時 no-op,不重複發送 telemetry。** 對抗性突變已驗證這個防護確實被測試守護(見下方)——與 S017 的 `exportPending` 防護不同,這裡的按鈕在「已選取」狀態下**仍然留在畫面上、仍然可點擊**(不像匯出按鈕在 pending 時會從 DOM 移除),所以這個防護對應的情境是使用者透過正常 UI 互動就能真實觸發的(重複點擊同一個已選按鈕),不是難以測試的競態,值得且應該被測試涵蓋。
5. **S019「Prediction result」、S020「Prediction disclaimer」明確排除在本 story 之外。** 本 story 只負責選擇 UI 本身,不提前顯示任何預測數字或免責聲明——同 S008 對 S009 分頁、S016 對 S017 進度狀態已建立的「不搶下一個 story 範圍」紀律。
6. **AC2/AC4/AC5/Security AC 判定 N/A 的理由**(同 S016/S017 的判定基礎,略作調整):
   - AC2:沒有自由輸入表單,固定選項按鈕沒有驗證失敗的情境。
   - AC4:純前端同步 state 切換,不呼叫任何外部 dependency。
   - AC5:`handleSelectPredictionHorizon` 對重複選取同一範圍 no-op,已用對抗性突變驗證這個防護被測試守護(見下方)。
   - Security AC:沒有引入新的資料存取面,沿用頁面既有 role-gate;選取的時間範圍本身不是受保護資料。
