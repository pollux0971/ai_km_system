## 設計決策
1. **統一的每時間範圍成長率,而非每情境各自捏造的業務敘事。** 核心判斷:`getErpResultKpi`(S010)有真正的 ground truth 可以推導(已執行結果的實際列數),所以手動重複打字會產生真正的 drift 風險(S008 自己的獨立審核就抓到過這種 drift)。但「預測」本質上沒有任何 ground truth 可以推導——任何描述「還沒發生的未來」的數字,不管是用公式算出來還是直接手打,同樣都是虛構的。與其為 4 個業務性質差異很大的情境(營收成長、低庫存數量、逾期應收帳款、採購單狀態)各自編造 12 句(4 情境 × 3 時間範圍)聽起來煞有其事卻同樣虛構的業務敘事(尤其「採購單狀態」這種非數值情境,套用「成長率」語意本身就很牽強),不如誠實採用一個對所有情境一致套用的簡化成長率模型(AC8 明確允許簡化演算法),用已知的情境標籤代入同一句模板——這是「一個事實一個來源」紀律的延伸應用,只是這次沒有「事實」可以當來源,所以來源改成「同一份誠實標示為簡化模擬的假設」。
2. **時間範圍的標籤從 `ERP_PREDICTION_HORIZONS`(S018)查找,不重複打字。** `getErpPrediction` 內部用 horizonId 查找 `ERP_PREDICTION_HORIZONS` 取得 label,而不是要求呼叫端額外傳入一個可能與 id 不同步的 label 參數——避免呼叫端自己維護一份可能 drift 的複本。
3. **成長率隨時間範圍遞增(3%→8%→15%)。** 一個內部一致、直覺合理的簡化假設(時間範圍越長,累積變化越大),不是隨機數字;已用對抗性突變驗證這個遞增關係確實被測試守護(見下方)。
4. **顯示時機:只在使用者已選取時間範圍後才顯示。** 選了才有東西可以顯示,呼應 S018 選擇 UI 本身「先選再看結果」的自然順序,同時避免預先渲染一個使用者根本沒要求的預測(fail-closed 精神的自然延伸,雖然嚴格來說不是 Security AC 而是 UX 誠實性)。
5. **AC2/AC4/AC5/Security AC 判定 N/A 的理由**(延續 S018 的判定基礎):
   - AC2:沒有自由輸入表單,選項本身是固定按鈕(S018 已處理驗證)。
   - AC4:純前端同步查表計算,不呼叫任何外部 dependency。
   - AC5:純讀取顯示,沒有 mutation,重複顯示同一個預測結果沒有「未定義副作用」的問題(不像 S018 的選取本身有 telemetry 需要防重複)。
   - Security AC:沒有引入新的資料存取面,沿用頁面既有 role-gate;預測文字本身不含受保護資料,只是情境標籤與固定百分比的組合。
