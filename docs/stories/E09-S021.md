## 設計決策
1. **重試機制:重用既有 effect,而非另建獨立元件。** 這個 codebase 已有 `KnowledgeDocumentRetryButton`(E05-S021)作為「獨立重試元件」的既有先例——研究後判斷**不**照搬,而是採用「計數器 bump 重新觸發既有 `useEffect`」的做法。理由:`erp-query-detail.tsx` 本身已經有一個很強的內部慣例——狀態轉換時整個畫面區塊互換(confirm→執行中…、匯出→匯出中…),而不是「原地 relabel + disable 按鈕」。載入與執行這兩個 effect 本身已經擁有完整的錯誤處理與(執行的部分)telemetry 邏輯,重新觸發同一個 effect 100% 重用這些邏輯、零重複程式碼;若改用 E05-S021 的獨立元件模式,反而需要在這個檔案裡混入第二種、形狀不同的 UI 慣例(disabled+relabel 按鈕),與檔案自身既有慣例衝突。這是「與本檔案自身慣例一致」優先於「照搬其他檔案先例」的判斷,取捨已在程式碼 doc comment 中明確記錄。
2. **查詢載入重試不發 `trackEvent`,只用 logger;查詢執行重試重用既有 `erp_query_execute_attempt`/`_success`/`_failure` 事件名稱,不發明 `_retry_*` 新事件。** 前者理由:原始(非重試)的查詢載入本身就只有 `logger.info`/`logger.error`,從未發過 `trackEvent`(S002 自己的 doc comment 已判定讀取操作的 AC7 稽核需求為 N/A)——重試同一個讀取操作沒有理由比原始操作本身需要更高規格的稽核。後者理由:SOURCE_BASELINE pinned #22 要求的是「SQL 執行必須被稽核」,不是「人類事後看稽核紀錄時能標出這是第幾次嘗試」——每次執行(不論是首次或重試)都已經在 effect 頂部產生全新的 `correlationId`,足以個別區分每一次嘗試,不需要另外發明新的事件名稱。
3. **只為載入、執行兩個狀態加重試按鈕,不動 `selectionError`(情境選擇)、`confirmError`(確認執行)。** 查證這兩個既有錯誤狀態的 render 邏輯:情境選擇按鈕群與確認執行按鈕在失敗後都**沒有**被隱藏或替換——`disabled={selectionPending}`/`disabled={confirmPending}` 只在請求進行中才 disable,失敗後按鈕本身依然可見可點,使用者原本就可以直接再點一次同一個按鈕重試,不需要新增獨立的「重試」機制。真正需要新按鈕的只有載入與執行這兩個——它們是**自動觸發**的 `useEffect`(掛載時自動載入、確認後自動執行),失敗後沒有任何使用者可點的按鈕能讓它們重新執行,這才是本 story 真正要補的「死路」。這個範圍判斷不是遺漏,是查證既有程式碼行為後的刻意決定。
4. **AC5(重複請求 / 重試不得造成未定義重複 side effect)的落實方式,不是額外加一個 boolean guard。** 兩個重試按鈕都定義在對應的錯誤畫面 render 分支之內(`state.status === "error"` 分支 / `executionError` 分支內),而不是定義在一個「即使失敗也還留在畫面上」的常駐區塊——按鈕本身的可見性已經跟著狀態轉換走:點擊後,同一個 tick 內先觸發計數器遞增,effect 重跑後緊接著 `setState({status:"loading"})`/`setExecutionError(false)` 讓按鈕從畫面上消失。React 18 的自動批次處理(automatic batching)加上 effect 相依陣列比對只看「最終落地的值」而非「每一次遞增」,代表就算使用者在同一個 render tick 內點兩次,effect 也只會依最終計數器值重跑一次,不會產生兩個並行的重試請求。這與 S017 對 `exportPending` guard 的既有調查結論相同:這個時間窗口本來就不是人類點擊速度能命中的,同一套判斷這裡直接沿用,不需要重新驗證。

## 對抗性自我驗證(DEV 自查)
目標:本 story 真正新增的邏輯核心——`loadAttempt`/`executionAttempt` 計數器是否真的讓 effect 重新執行,而不是一個「按下去畫面不動」的假重試按鈕。

突變:將執行 effect 的 dependency array 從 `[state, id, executionAttempt]` 改回 `[state, id]`(移除 `executionAttempt`),模擬「忘記把計數器接進 dependency array」這個最容易犯的錯誤。

結果:精準命中預測的 2 個測試失敗——「clicking retry on an execution failure shows 執行中… immediately, then succeeds on the retried attempt」與「retrying execution re-fires erp_query_execute_attempt/_success telemetry with a fresh correlation id」——兩者都是因為點擊重試後 effect 不會重跑,執行狀態永遠停在失敗、沒有第二次 `執行中…`/成功畫面、也沒有第二組 telemetry。其餘 68 個測試(含「shows a retry button alongside the execution error」與全部 4 個載入重試測試)維持通過,證實突變的影響範圍精確落在「執行重試是否真的生效」這一件事,沒有波及其他邏輯,測試本身確實在守護這個新增能力,不是空殼測試。已用 `git checkout --` 還原(先前已用 `git add -A` 建立 checkpoint),`git diff --stat` 確認乾淨,測試檔重跑全綠(70/70)。
