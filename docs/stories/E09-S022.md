## 設計決策(本 story 的核心是這一節,不是變更檔案清單)

### 1. 為何本 story 沒有新增任何 production 程式碼

先做了三輪徹底查證(避免在 spec 沒有更具體描述、只有故事標題「permission-denied UX」的情況下,對「該做什麼」做出未經檢驗的假設——同 S018/S019/S021 已建立的先查證再設計紀律):

1. **`RoleGuard` 已經是完整、正確運作的權限拒絕機制**,由 E01-S017 建立、E01-S006 起就已全域套用於 `apps/web/src/app/(app)/layout.tsx`,把每個受保護路由包起來。讀取原始碼(`role-guard.tsx` 21-38 行)確認:未授權時是一個真正的提前 `return`,`{children}` 完全不會被掛載——也就是說,受保護頁面自己的資料抓取 effect(`getErpQuery`/`listErpQueries` 等)在未授權情境下**從未被呼叫過**,不是「抓了資料再隱藏」。`erp/page.tsx` 自己的 doc comment(第 4-10 行)也明確寫著:「role-gated to sales_purchasing/super_administrator via the global RoleGuard...這頁本身不需要額外的授權邏輯」——這是 E09-S001 自己當初就已經預告的設計。AC3(無權限使用者不得讀取/推導/顯示/記錄受保護內容)因此在結構上已經被滿足,不需要新寫任何攔截邏輯。
2. **查證是否存在真正的測試缺口**:`role-guard.test.tsx` 對 `/erp` 只測過 ALLOW(57-60 行,`allows a sales_purchasing user on /erp`),從未測過 DENY,也從未測過 `/erp` 的巢狀路徑(`/erp/[id]`)。`erp-home.spec.ts` 自己的 doc comment 明確承認「沒有 general_user 的否定授權測試」,並解釋原因(見下方 E2E 段落)。`route-guards.spec.ts` 的 doc comment 也確認舊的、涵蓋 `/erp` 的 E2E 否定測試在 E09-S001 生出真正的頁面後被刪除,沒有東西補上。這是一個真實、具體、可驗證的測試缺口——不是憑空想像出來的工作。
3. **查證是否應該比照 E03-S016(Citation permission-error UX)新增「資源層級」的權限拒絕**(例如仿照 `citations.ts` 的 `FORBIDDEN_CITATION_IDS`,為某些 ERP 查詢加上「即使角色正確也被拒絕」的機制)。結論:**不應該**,理由是兩者的權限模型本質不同——citations 的資源層級權限有堅實的 spec 基礎:知識庫本來就有 per-KB 權限編輯器(E05-S006)與 per-document 權限編輯器(E05-S027),citation 指向某份使用者無權存取的知識庫文件是這個 domain 本來就有的真實情境。ERP 則完全不同:查證 `SOURCE_BASELINE.md` 374-377 行的 pinned 決策 #19-22(ERP MVP read-only、AI SQL 僅 SELECT、僅 whitelist view、SQL 執行需 audit),以及 `erp-queries.ts` 42-49 行的 `ErpQuerySummary` 型別,兩者都**沒有任何 per-record 擁有者/可見性欄位**,整個 mock 資料是一份不分使用者的全域陣列。ERP 唯一被規格確立的權限維度就是這個角色層級的粗粒度閘門。如果為了「看起來更像一個完整的 story」而發明一套 `FORBIDDEN_ERP_QUERY_IDS`,那就是在沒有 spec 依據的情況下捏造一個新的授權語意——直接違反本 story 開發邊界自己明訂的「不得改變既有 authorization semantics...來配合功能」與「不得自行猜測」。因此判定:ERP 目前唯一站得住腳、有 spec 依據的權限拒絕情境就是角色層級的路由守門,而它已經存在且正確運作。

綜合以上,本 story 誠實、精準的範圍就是:**補齊「`RoleGuard` 對 `/erp` 的覆蓋」這個真實存在、但先前一直沒人補上的測試缺口**——這正是 AC8「MVP 可以簡化視覺或演算法,但此能力本身不可缺席」的精神:能力(`RoleGuard`)不缺席,缺的只是「證明它對 `/erp` 這條路由也確實有效」的驗證,而補上這個驗證正是本 story 唯一、也是全部的價值所在。

### 2. 為何在共用檔案 `role-guard.test.tsx` 新增測試,而非在 E09 自己的資料夾

`role-guard.tsx`/`role-guard.test.tsx` 屬於 E01(Application Shell)的元件,不是 E09 自己的 domain。但讀取該測試檔案後發現**直接、明確的既有先例**:62-71 行已經是 E07-S006(不同 epic 的 story)在同一個共用檔案裡,為自己的路由(`/maintenance` 巢狀路徑)新增的測試,測試名稱前綴自己的 story ID(`(E07-S006) denies...`/`(E07-S006) allows...`)。這確立了這個檔案本身的既有慣例:當某個 story 需要驗證共用的 `RoleGuard` 機制對自己 domain 的路由是否正確運作時,就在這個檔案裡疊加,而不是各自建立平行的驗證檔案。本 story 直接沿用這個既有慣例(同一個 `describe` 區塊、同樣的 story-ID 前綴命名法),而不是發明新的做法——沒有修改 `role-guard.tsx` 或 `role-guard.test.tsx` 既有測試的任何一行,純粹疊加。

### 3. E2E 覆蓋範圍(誠實記錄,非遺漏)——與 S021 不同的技術原因

查證確認:E2E 測試框架的 mock session 存放在 `packages/auth-client/src/mock.ts` 的記憶體內閉包變數(`let currentSession`),任何「整頁重新導覽」(`page.goto()`)都會重置它。要測試「無 ERP 權限的使用者造訪 `/erp`」,唯一能保留登入態的方式是同分頁的 client-side 導覽(例如點擊一個真實渲染出來的連結)——但 `nav-items.ts` 的設計本身就是:沒有 ERP 權限的角色,首頁與側邊欄都不會渲染任何指向 `/erp` 的連結(`visibleNavItems`/`visibleEntryCards` 共用同一份過濾邏輯)。也就是說,一個真的無權限的使用者,在真實瀏覽器情境下**沒有任何路徑能點到 `/erp`**——這正是這個 UX 設計本身要達成的效果(先用導覽隱藏,`RoleGuard` 是進一步的縱深防禦)。要在 E2E 測試裡繞過這點,勢必得用 `page.goto()` 直接導覽,但那會先弄丟 mock session,連 `RoleGuard` 都還沒執行到,`SessionGate` 就先把使用者導去 `/login` 了——這與本 story 想驗證的「已登入、但角色不足」情境完全不同。這個限制不是 S021 那種「mock 後端沒有失敗注入機制」,而是「mock session 的實作方式本身讓這個情境在真實瀏覽器裡無法重現」——兩個 story 的 E2E 缺口原因不同,誠實分開記錄。`erp-home.spec.ts`(E09-S001 起)與 `route-guards.spec.ts` 的既有 doc comment 都已經承認這個限制,本 story 的判定與既有文件一致,不是新發現的規避理由。

## 對抗性自我驗證(DEV 自查)
本 story 沒有新增 production 邏輯,所以自查目標改為:**證明新增的 3 個測試不是空殼測試,而是真的在守護 `rolesRequiredFor` 的巢狀路徑比對邏輯**(這正是新測試唯一新驗證的機制面向——bare-path 比對早已被既有測試覆蓋)。

突變:`apps/web/src/lib/nav-items.ts` 的 `rolesRequiredFor` 從 `item.href === pathname || pathname.startsWith(\`${item.href}/\`)`(exact-or-nested)改回其 doc comment 自己記載的「舊行為」——`item.href === pathname`(僅 exact match,模擬 E07-S006 之前的舊版本重新出現的迴歸)。

結果:精準命中 2 個測試失敗——「(E07-S006) denies a general_user on a route nested under /maintenance」與「(E09-S022) denies a maintenance_engineer on a route nested under /erp」——兩者都是因為移除巢狀比對後,`rolesRequiredFor("/erp/query1")`/`rolesRequiredFor("/maintenance/x/session")` 都回傳 `undefined`,被 `RoleGuard` 當成「不受限制」而放行,造成本應拒絕的存取被允許。其餘 9 個測試(含新增的「allows...nested under /erp」,因為該測試驗證的是「允許」,守門失效後仍然允許,不受此突變影響,這是預期中的行為而非測試缺陷)維持通過——證實新增的 2 個 deny 測試確實在守護巢狀路徑比對邏輯,而不是空殼斷言,同時也再次確認了既有 E07-S006 測試的價值。已用 `git checkout --` 還原(先前已用 `git add -A` 建立 checkpoint),`git diff --stat` 確認乾淨,測試檔重跑全綠(11/11)。
