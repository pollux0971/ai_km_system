## 範圍決策(本 story 的核心)

### 為何只做 bootstrap,不做 session/auth/login/route gating

查證 `docs/stories/E01-S001.md` 逐字確認:E01-S001(`apps/web` 自己的第一個 story)範圍嚴格限定為「route group 結構、root layout、correlation-id middleware、全域 404」,刻意排除 login(S002)、session gating(S004)、chrome(S005)、401/403 guard(S017)——這些是後續個別 story 的範圍,不是 S001 自己要做的事。查證 `apps/web/src/app/(app)/layout.tsx` 現在的內容(`SessionGate` → `AppShell` → `RoleGuard`)確認這三層都是 S004/S005/S017 這幾個**後來**的 story 才加上去的,S001 自己完全沒有。

E11 自己的 25 個 story 清單裡沒有任何一個明確叫「Admin login」,但有 `E11-S023 — admin route authorization`——這正是 `RoleGuard`(E01-S017)的直接對應物,而且在 25 個 story 中排序在很後面(第 23 個),與 E01-S017 在 E01 自己 story 序列中的相對位置(接近後段)吻合。這代表:`apps/web` 自己當年也是先讓 S002 到 S016(整整 15 個 story)在沒有 RoleGuard 的情況下上線,S017 才回頭補上路由層級的角色守門——本 story 依循的是這個 codebase 自己已經核准、已經實際發生過的既有排序,不是憑空假設。

因此判定:E11-S001(本 story)可以安全地完全比照 E01-S001 的範圍——純 bootstrap,零 session/auth/login/gating——不需要為了「該不該現在就決定 admin 的登入架構」這個問題升級 advisor 或寫入 PENDING_DECISIONS.md。這是單一 story 範圍內、有直接且已核准前例可循的判斷,不是難以取捨的多種做法。

**誠實記錄一個開放問題,而非略過**:與 E01 不同,E11 的 25 個 story 清單裡確實沒有任何一個明確命名為「Admin login」的 story。這代表「admin 究竟如何建立 session(而不只是路由層級怎麼守門)」目前沒有一個已經被規劃、已經命名的未來 story 負責。查證 `packages/auth-client/src/mock.ts` 確認 mock session(`currentSession`)是純記憶體內閉包變數,`apps/web`(:3000)與 `apps/admin`(:3001)是兩個獨立的 Next.js process,無法共享這個變數——也就是說,admin 遲早需要自己的某種登入建立機制,只是**不是本 story 的範圍**。這個開放問題留給實際需要它的第一個未來 story(很可能是 E11-S023 自己,或屆時發現需要一個新的、目前規格沒有明確命名的 story)去解決,屆時若仍難以取捨,才是真正該升級 advisor 的時機——本 story 只誠實記錄這個觀察,不代替未來的 story 做決定。

### 為何不預先建立 `(app)`/`(public)` route group

`apps/web` 當年會用 route group,是因為 E01-S001 當時**已經有 2 個既有頁面**(`page.tsx` 與 `login/page.tsx`)需要重新組織成「公開區」與「登入後區」——這個結構本身是為了解決一個真實存在的組織需求。`apps/admin` 目前只有 1 個頁面、沒有 login 頁面,沒有任何「公開 vs 登入後」的實際區分需要表達。提前建立 route group 會是「在真正需要這個結構的 story(可能是未來的 admin login story)出現之前,先發明它」——與這個 codebase 一路以來「不預先建立目前用不到的結構」的紀律(例如 S013/S014 不為純字面常數建 lib 檔案)相同,故本 story 刻意不做,留給真正需要它的未來 story。

### `page.tsx` 內容為何刻意精簡,以及與 `apps/web` 首頁的關鍵差異

`apps/web` 自己的首頁在 E01-S001 當時保持完全空白的 placeholder,一路到 E01-S008「Home dashboard」才有真正內容——中間隔了 7 個 story。E11 沒有對應的「S008」——**本 story 自己的標題就是「Admin dashboard」**,沒有另一個保留給「把 placeholder 換成真正內容」的未來 story。因此本 story 判定:`page.tsx` 不能只是換一個新的 placeholder 文字了事,必須放上這個頁面「未來會是什麼」的真正起點內容(標題 + 一句話說明),但也不能捏造任何統計數字、使用者清單連結或其他子頁面連結——因為使用者/角色/稽核紀錄等資料模型全都是尚未開工的後續 story 才會定義的東西,提前連結會是連到一個不存在的頁面,或提前假裝擁有不存在的資料。這與 `erp/page.tsx`(E09-S001)只放「開始新的 ERP 查詢」連結、把「ERP 查詢歷史清單」的真正內容留給後續 story(E09-S015)填入的做法是同一種紀律。

### E2E 基礎設施擴充過程中發現並修正的真實 config bug

`tests/e2e/playwright.config.ts` 原本只有單一 `webServer`/`baseURL`,只服務 `apps/web`。本 story 改為 `webServer` 陣列(web + admin 各自的 dev server)與 `projects` 陣列(`web`/`admin` 兩個 project,各自 `baseURL`,以 `admin-` 檔名前綴分流哪個 spec 屬於哪個 project)。

第一版寫法對 `web` project 用 `testIgnore: /^(?!admin-).../`、對 `admin` project 用 `testMatch: /^admin-.../`(都用 `^` 錨定字串開頭)。用 `pnpm exec playwright test --list` 驗證時發現 `admin-smoke.spec.ts` 的兩個測試被錯誤路由到 `[web]` project,而不是預期的 `[admin]`。追查後確認:Playwright 的 `testMatch`/`testIgnore` 比對的是**檔案的完整絕對路徑**,不是檔名——`^` 錨定字串開頭時比對的是路徑最前面(`/data/python/AI_KM/...`),永遠不會等於 `admin-`,導致正規表達式邏輯整個失效(negative lookahead 恆真、positive match 恆假)。修正為不錨定開頭、改用 `admin-.*\.spec\.ts$`(比對路徑結尾)後,`--list` 確認正確路由(`[admin] › admin-smoke.spec.ts`),窄範圍 `--project=admin` 執行也確認 2/2 通過。這個修正過程本身就是一次真實、即時的自我驗證,不是事後補的。

## 對抗性自我驗證(SELF-REVIEW,發現並修正一個真實的測試品質落差)

目標:證明新增的 E2E 測試(`admin-smoke.spec.ts`)真的在驗證正確的伺服器/內容,而不是意外通過。

突變:把 `apps/admin/src/app/page.tsx` 的標題從「AI KM 管理主控台」改成「AI KM 管理主控台(測試突變)」。

第一次結果(**意外通過,非預期**):`apps/admin` 自己的 unit 測試(`page.test.tsx`)正確捕捉到這個突變並失敗——但窄範圍執行 `--project=admin` 的 **E2E 測試卻通過了**,沒有捕捉到。追查發現這是一個真實的測試品質落差,不是環境問題:`page.getByRole("heading", { name: "AI KM 管理主控台", level: 1 })` 這個寫法在 Playwright 裡,`name` 給字串時預設是「不分大小寫的子字串比對」,不是精確比對(與 Testing Library 的字串比對預設是精確比對不同)——突變後的標題「AI KM 管理主控台(測試突變)」把原本的字串當作**前綴子字串**包含在內,所以依然「比對成功」。

修正:在兩個 `admin-smoke.spec.ts` 測試的 `getByRole` 呼叫都加上 `exact: true`。重跑 `--project=admin`:**測試 1(首頁標題)精準命中並失敗,測試 2(404 頁面,與 page.tsx 無關)不受影響維持通過**——證實修正後的斷言確實在做精確比對。已用 `git checkout --` 還原 `page.tsx` 的突變(先前已用 `git add -A` 建立 checkpoint),保留 `exact: true` 這個修正(這是本次驗證過程中發現的真實修正,不是要還原的突變本身)。`git diff --stat` 確認乾淨,重新完整跑過 unit(5/5)與窄範圍 E2E(2/2)確認全綠。

**誠實補充說明**:這個「Playwright name 預設子字串比對」的落差,查證確認 `specs/smoke.spec.ts` 自己既有的 `getByRole("heading", { name: "登入" })` 等寫法也沒有加 `exact: true`——這似乎是這個 codebase E2E 測試裡廣泛存在的既有慣例,不是本 story 自己發明的疏漏。本 story 只修正自己新增的測試(`admin-smoke.spec.ts`),不擴大範圍去改動 `apps/web` 既有的、與本 story 無關的測試檔案——那已經超出「本 Story 所屬 Domain」的範圍,若要全面修正應該是另一個獨立的技術債 story。
