## 設計決策

### 兩個獨立函式,不是一個 boolean toggle:比照 archive/unarchive 既有 pattern

`disableUser`/`enableUser`是兩個獨立、各自命名的函式,不是一個 `setUserStatus(userId, status)`——直接沿用 `archiveKnowledgeBaseDocument`/`unarchiveKnowledgeBaseDocument` 自己 doc comment 明確記錄的理由:「每個都是自己獨立、有명確使用者意圖的動作(停用 vs 啟用),不是一個通用的『設定這個 flag』操作」。這是這個 codebase 對「切換兩態」這件事唯一的既有先例,直接複製其形狀而非自創。

### Idempotent,不是 VALIDATION_ERROR:同樣比照既有先例

重複停用已停用的使用者、或重複啟用已啟用的使用者,回傳成功而非錯誤——`archiveKnowledgeBaseDocument`/`unarchiveKnowledgeBaseDocument` 對「重複封存已封存的文件」也是同樣處理(無 current-state 檢查,直接覆寫),明確與同檔案內 `retryDocumentProcessing`(對「不是 failed 狀態就重試」會回傳 `VALIDATION_ERROR`)的既有對比案例區分開來。「使用者可能連續點兩次、或分頁開兩個都按到同一個按鈕」本來就是這種 UI 動作的正常情境,不應該被當成錯誤。

### UI 位置:清單列,不是詳情頁

`disableUser`/`enableUser` 的 UI 入口放在 `user-list.tsx` 每一列,不是 `user-detail.tsx`——比照 `KnowledgeDocumentArchiveToggle` 同樣是清單列動作(不是文件自己的詳情頁動作,文件甚至沒有獨立詳情頁)。使用者清單本身從 S002 開始就是「所有狀態混在同一個清單顯示」(不像知識文件清單有作用中/已封存的 VIEW 切換),所以這個 toggle 不需要處理「切換後這一列從目前檢視消失」的情境——`onToggled` 觸發父層重新抓取後,同一列繼續存在,只是狀態文字換了。

### 沒有確認對話框

同 `KnowledgeDocumentArchiveToggle` 自己的既有判斷:停用/啟用都是可逆操作(管理員按錯了,再按一次就能復原),比照 `RenameConversation`/`KnowledgeDocumentNameEditor` 已建立的「低風險、可逆的操作不需要 confirm dialog」先例。

## 過程中發現並修正的一個真實 bug(誠實記錄:Testing Library 與 Playwright 對「元素自己的文字」定義不同)

### 現象

實作完成、admin 單元測試(61/61)全綠後,執行 E2E 卻出現 2 個失敗,而且其中 1 個是**先前已核准、本 story 完全沒碰過的 S002 舊測試**(斷言 `示範已停用帳號` 那一列顯示「已停用」)——這是很強的訊號:不是新測試寫錯,是實作本身造成了真實 regression。

### 根因

`user-list.tsx` 原本的寫法把狀態文字與 toggle 按鈕放在同一個 `<p>` 裡:
```tsx
<p>
  {STATUS_LABEL[user.status]}{" "}
  <UserStatusToggle ... />
</p>
```
這造成 `<p>` 元素的 DOM `textContent`(包含子元素文字)變成「已停用 啟用」而非單純「已停用」。**Testing Library 的 `getByText` 預設只比對元素「自己直接的文字節點」(`childNodes` 中 `nodeType === TEXT_NODE` 的部分),明確排除巢狀元素(如 `<button>`)自己的文字**——所以單元測試裡 `screen.getByText("已停用")`/`screen.getByText("啟用中")` 完全不受巢狀按鈕影響,照樣通過。但 **Playwright 的 `getByText` 用的是標準 DOM `textContent` 語意,會把所有子孫元素的文字都算進去**——`exact: true` 比對「已停用」時,找不到任何元素的完整文字剛好等於「已停用」(`<p>` 的文字含按鈕文字,`<button>` 的文字又不含「已停用」),導致 E2E 找不到元素而逾時失敗。

這是本 session 第三種被發現的 Testing Library / Playwright API 語意差異(前兩種:`name`/`text` 字串比對預設 exact vs substring;`ByRoleOptions` 有無 `exact` 屬性)——這次是關於「一個元素的『自己的文字』要不要含巢狀子元素的文字」,單元測試層完全測不出來,只有跑真實瀏覽器的 E2E 才會暴露。

### 修正

把 toggle 按鈕移到自己獨立的 `<p>`,與狀態文字的 `<p>` 分開(不巢狀):
```tsx
<p>{STATUS_LABEL[user.status]}</p>
<p>
  <UserStatusToggle ... />
</p>
```
`<p>{STATUS_LABEL[user.status]}</p>` 恢復成與 S002 原本完全相同的形狀(只有一個文字節點,無巢狀元素),兩個先前失敗的 E2E 測試(S002 舊測試 + 本 story 新測試)重新執行後都通過。已從 VERIFY 第一個 gate(typecheck)完整重跑一次確認全綠(typecheck 20/20、lint 20/20、admin unit 8/8 檔案 61/61 tests、build 12/12、E2E 213/213)。

## 對抗性自我驗證(SELF-REVIEW)

目標:證明 `disableUser` 真的只改動目標使用者,不會意外波及其他人的記錄。

突變:把 `disableUser` 的 `writeStore(store.map((user) => (user.userId === userId ? updated : user)))` 改成 `writeStore(store.map(() => updated))`——模擬「忘記帶入條件判斷,把更新套用到每一筆記錄」這個具體錯誤(效果嚴重:會把全部使用者都覆寫成同一筆「目標使用者、已停用」的記錄)。

結果:精準命中預期的 1 個測試——「only changes the targeted user's status, leaving every other user's own record untouched」(斷言其他使用者的記錄前後相等,突變後其他使用者全部消失、變成同一筆記錄的重複,斷言正確失敗)。其餘 24 個測試不受影響,包括「returns NOT_FOUND for disabling an unknown user id」(guard 在 mutated 那行之前,不受影響)與「disables an active user...」(回傳值本身不受 `writeStore` 內容影響,只有讀回 store 後才會暴露問題,而該測試恰好沒有比對其他使用者,所以沒被這個特定突變命中——這點誠實記錄,不代表這個突變是這個 codebase 唯一會測到的入口:「只改目標使用者」這個測試才是專門為了堵住這個 bug class 設計的)。

已用 `git checkout --` 還原突變(先前已用 `git add -A` 建立 checkpoint),`git diff --stat -- apps/admin/src/lib/users.ts` 確認乾淨,重新執行 admin 全部單元測試(8/8 檔案 61/61 tests)、`pnpm typecheck`/`pnpm lint`(皆 0)確認全綠。

**判定為真實缺陷(MAJOR:測試品質不足)**:若這個 bug 真的存在於 production,管理員停用/啟用失敗一次後重新點擊並成功,畫面會繼續顯示「停用失敗,請稍後再試。」這個過期、與目前真實狀態矛盾的錯誤訊息(此時按鈕文字已經因為父層重新抓取而換成相反的動作),對管理員是會誤導判斷的真實使用者體驗缺陷,性質與 S003 Round 1 的「錯誤訊息文字寫反」同屬「殘留/錯誤的錯誤狀態誤導使用者」這一類真實缺陷,不是可以用既有先例開脫的情況。
