## 設計決策

### `description` 內容來自 SOURCE_BASELINE §7,不是發明

實作前先確認過 `packages/permissions/src/index.ts`(僅有 `Role` type union,無任何描述性資料)、`contracts/permissions/README.md`(明確寫「Not yet populated」)、apps/admin 現有程式碼(僅有 `AdminUser.roles: Role[]` 與 `ALL_ROLES`,無描述)——這個 codebase 目前**沒有**任何角色描述的既有實作可以重用。但 `AI_KM_BMAD_High_Granularity/SOURCE_BASELINE.md` §7(第 445–533 行)**確實**有每個角色的責任摘要(「管理/使用/查看 X」的條列形式),9 個角色全部涵蓋。本 story 把這份既有內容改寫成單句描述(內容與範圍不變,只是格式從條列改成一句話),不是自己編造角色職責——這是「不發明 contract」鐵律在「角色職責描述」這種 domain 內容(非嚴格意義的 API contract,但同樣是需要真實來源的規格內容)上的具體實踐。

### 明確排除權限矩陣(resource:action grid)

`E11-S008「Permission matrix」`是後續獨立、已命名的 story,`contracts/permissions/README.md` 自己也確認目前沒有任何角色到權限的對應表存在。本 story 的 `RoleSummary` 只有 `role` + `description` 兩個欄位,刻意不塞入任何「這個角色能做什麼具體動作」的清單——避免偷跑做 S008 的範圍,也避免在沒有真實來源的情況下自己發明一份權限清單。

### `role` 而非 `id`

`RoleSummary` 的識別欄位命名為 `role: Role`,不是泛用的 `id: string`——這個識別值本身就是有意義的 `Role` enum 值(也是 `AdminUser.roles[number]` 直接重用的同一個型別),不是一個外掛在顯示名稱上的不透明產生式 id。

### 顯示原始角色字串,不是中文標籤

延續 apps/admin 從 S002 開始的既有呈現慣例(`user-list.tsx`/`user-detail.tsx`/建立使用者表單的角色 checkbox 全部顯示原始英文 slug,不是中文名稱)——本 story 的角色清單同樣顯示 `general_user`/`super_administrator` 等原始字串,保持整個 app 內角色識別方式的一致性,不在這個 story 單獨引入新的中文化慣例。

### `ALL_ROLES` 重用 `users.ts` 既有匯出,不重複定義

`users.ts`(E11-S004)已經匯出 `ALL_ROLES: Role[]`。本 story 的 `roles.ts` 直接 `import { ALL_ROLES } from "./users"` 重用,不在 `roles.ts` 自己再定義一份重複的角色清單——避免兩份清單未來不同步的風險。概念上「roles.ts 從 users.ts 引入」略為反直覺(理想上是反過來),但比照本 session 一貫的「不做無直接必要性的既有檔案重構」紀律,保留這個小小的不對稱,而非為了概念整潔去動 `users.ts` 這個已核准、正常運作的既有檔案與其既有 import 路徑。留給後續 story(S007/S008)在真的有必要時再重新評估。

### `listRoles()` 仍用 `Promise<Result<T[], ApiError>>` 而非直接回傳陣列

雖然這個特定 mock 實作**不可能**真的失敗(`ALL_ROLES`/`ROLE_DESCRIPTIONS` 都是常數),但「Role list」本質上是一個「清單頁的主要資料來源」,與 `listUsers`/`listErpQueries`/`listMaintenanceCases` 屬於同一類——這些即使目前 mock 也不會失敗,仍統一用這個 shape,以便清單頁的 loading/error 狀態機保持與所有既有清單頁一致。這與 `ALL_ROLES`/`ERP_SCENARIO_OPTIONS` 這種「純靜態下拉選單 OPTIONS,不是頁面主要資料來源」的用途不同,不適用同一種「就是個常數陣列」的簡化。

## 對抗性自我驗證(SELF-REVIEW)

目標:證明 `listRoles()` 真的把每個角色對應到「自己的」描述,不是巧合看起來正確或全部共用同一段文字。

突變:把 `ALL_ROLES.map((role) => ({ role, description: ROLE_DESCRIPTIONS[role] }))` 改成 `ALL_ROLES.map((role) => ({ role, description: ROLE_DESCRIPTIONS.general_user }))`——模擬「複製貼上時忘記把 key 換成迴圈變數,九個角色全部套用同一個角色的描述」這個具體錯誤。

結果:精準命中預期的 1 個測試——「uses the real SOURCE_BASELINE §7 responsibility text, not placeholder content」(斷言 `super_administrator` 的描述應為「最高系統權限。」,突變後變成「一般企業員工。」,斷言正確失敗)。其餘 3 個測試不受影響,包括「every role has a non-empty description」(任何非空字串都算通過,突變後描述仍非空,不會被這個測試命中——誠實記錄這個測試本來就不是設計來抓這種錯誤的)與「no duplicates or omissions」(角色鍵值本身沒變,只有描述內容被覆蓋,不受這個突變影響)。

已用 `git checkout --` 還原突變(先前已用 `git add -A` 建立 checkpoint),`git diff --stat -- apps/admin/src/lib/roles.ts` 確認乾淨,重新執行 admin 全部單元測試(10/10 檔案 72/72 tests)確認全綠。

## 獨立審核 Round 1 — REQUEST-CHANGES

審核者獨立重新查證核心主張(SOURCE_BASELINE §7 的角色責任文字、`contracts/permissions/README.md` 確認無權限矩陣既有先例)皆屬實,並獨立以 `--force` 全量重跑 typecheck(20/20)/lint(20/20)/build(12/12)全綠。

審核者另以獨立對抗性突變、鎖定與 DEV 自己驗證過的層(`roles.ts` 的 `listRoles()` 資料對應邏輯)不同的另一層——`role-list.tsx` 元件自己的清單渲染邏輯(把 `state.roles.map(...)` 改成 `state.roles.slice(0, 5).map(...)`,模擬「加了分頁但忘記拿掉除錯用的截斷、或單純的邊界錯誤」這個具體錯誤,只渲染前 5 個角色)。結果:既有全部 5 個測試**意外通過**——追查發現「shows each role's own identifier and description once loaded」這個唯一涵蓋渲染內容的測試,自己的 mock fixture 只給 2 筆資料(`general_user`、`super_administrator`),`slice(0, 5)` 對一個只有 2 個元素的陣列不會截斷任何東西,所以這個測試完全沒有能力偵測「渲染邏輯把清單截斷」這一整類錯誤——本 story 唯一與「渲染多筆真實資料」有關的驗證是 E2E(用真實的 9 個角色),但單元/元件測試層完全沒有涵蓋接近正式資料量的情境。

**判定為真實缺陷(MAJOR:測試品質不足)**:若這個 bug 真的存在於 production,管理員在 `/roles` 只會看到 9 個角色中的 5 個,其餘 4 個(含 `auditor`、`super_administrator` 等重要角色)完全消失且沒有任何錯誤提示——這是「未定義截斷,不誠實呈現」的真實缺陷,理應在**元件測試層**就被攔下,不該只靠 E2E(執行成本高、且如果之後 E2E 本身有任何原因被跳過或改壞,這個 bug class 就完全無防護)。與本 story 自己 DEV SELF-REVIEW 發現的 `roles.ts` 缺口屬於同一種模式(既有測試 fixture 量太小、太巧合,沒有真的逼近正式資料規模去驗證行為),只是發生在 UI 渲染層而非資料轉換層。
