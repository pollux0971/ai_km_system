## 設計決策

### 為什麼不是一個真正的 resource:action 權限模型

`packages/permissions` 目前只匯出 `Role` 型別,沒有任何 permission/action 的概念;`contracts/permissions/README.md` 明確寫著這個 contract「Not yet populated」,由 Team B(E02)所有。若本 story 自行發明一套 resource:action 的權限判斷邏輯,會直接違反 Anti-hallucination Guard(「不得自行發明不存在的 API/table/queue/provider」)與 API/Contract Boundary(「不得自行猜測... 或 error code」——雖然這裡講的是 API,但精神相通:不得猜測一個尚未存在的權限模型的形狀)。因此本 story 的「矩陣」只呈現 SOURCE_BASELINE §7 已經明確寫出的角色責任範圍,不是一個可執行的授權判斷系統——這與 `RoleGuard`(E01-S017)、未來 admin 端的授權(E11-S023)是完全不同的東西,本頁面純粹是唯讀的參考資訊。

### `super_administrator` 的能力欄位

SOURCE_BASELINE §7 對其餘 8 個角色都逐項列出「管理/使用/查看」的具體項目,但對 `super_administrator` 只寫了一句「最高系統權限」,沒有逐項列舉。本 story 把這句話的字面意涵直接翻譯成「擁有其餘 8 個角色全部能力的聯集」(`ROLE_CAPABILITIES.super_administrator = ALL_CAPABILITIES`),而不是新增 SOURCE_BASELINE 從未提過的個別能力宣稱——這是對「最高」兩個字最小、最保守的字面推導,已誠實記錄為 assumption(見下)。

### 為什麼是 `<table>` 而非清單

「矩陣」本質是二維的(角色 × 能力),`RoleList`(E11-S006)的 `<ul>` 清單形狀不適用。選擇原生 `<table>` 而非自訂 CSS grid,理由是 `<table>` 自帶 `columnheader`/`rowheader`/`cell` 的語意角色,對螢幕閱讀器與測試查詢(`getByRole`)都更明確,且天然滿足 UX Acceptance「Keyboard/focus 基本可操作」與「不得只靠顏色傳達狀態」(cell 內容是文字「✓」或空白,不是背景色)。
