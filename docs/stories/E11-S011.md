## 設計決策

### 唯讀清單,不像 E11-S009/S010 一樣加 create

`Department`(E11-S009)與 `Group`(E11-S010)在這個 codebase 裡本來就沒有任何地方可以建立它們,所以那兩個 story 自己就是這些 entity 唯一的建立/管理入口,理所當然要有 list+create。但 `Knowledge Base` 完全不同——`apps/web` 自己的 E05 epic(31 個 story,30 個已核准)早就是這個 entity 完整、真實的建立與管理路徑(搜尋、權限、成員、prompt/model 綁定、資料夾同步、文件生命週期……)。如果本 story 在 apps/admin 這邊又做一個獨立、互不相通的「建立知識庫」表單,等於為同一個 entity 建立第二個、彼此不同步的權威來源——這正是 Domain Ownership Boundary 禁止的「不得自行在對方 Domain 補一套影子實作」與 Non-Goals「不因『順便比較方便』而擴大資料存取範圍或權限」。本 story 因此比照 `RoleList`(E11-S006,角色是固定 enum,同樣無法被建立)的唯讀清單形狀,是管理主控台對既有知識庫的**唯讀 oversight 檢視**,不是第二個建立入口。

### 種子內容逐字取自 `apps/web`,不是新發明

`id`/`name`/`description`/`updatedAt` 三筆種子資料逐字等於 `apps/web/src/lib/knowledge-bases.ts` 的 `SAMPLE_KNOWLEDGE_BASES`(包含 `updatedAt` 時間戳記)——同 `users.ts` 自己的 `SAMPLE_USERS` doc comment 已建立的「reuse `@ai-km/auth-client` 的真實身分,不是巧合相似的虛構內容」同一種紀律,只是這次的來源是 apps/web 的既有真實資料而非 auth-client。

### 顯示 `updatedAt`,不像 Role List 只顯示 identifier + description

`updatedAt` 是這個 codebase 對 `KnowledgeBaseSummary` 已經建立的既有欄位,對「管理主控台的知識庫 oversight」這個用途而言是有意義的資訊(哪些知識庫可能已經過時、需要留意),因此本 story 選擇顯示它,並重用 `UserDetail`(E11-S003)已經建立的 `<time dateTime>` + `toLocaleString("zh-TW")` 既有呈現方式,不是自創一套新的日期格式。

## Assumptions / 計畫外事項

- 本 story 刻意不提供建立/編輯/刪除知識庫的能力——那個能力已經完整存在於 `apps/web` 的 E05 epic,本 story 只是管理主控台對既有知識庫的唯讀 oversight 檢視,理由已於設計決策一節完整記錄。
