## 設計決策

### 種子內容逐字取自 `apps/web`,只有 `cloud` 的 label 拿掉「（尚未啟用）」後綴

`id`/`label`/初始 `disabled` 狀態全部逐字對應 `apps/web` 的 `AI_MODELS`(標準模型/進階模型/雲端模型,均為 SOURCE_BASELINE 編號決策 #28-30 的既有落地,非發明的廠商名稱)。唯一的差異是 `cloud` 的 label 從「雲端模型（尚未啟用）」簡化成「雲端模型」——因為 `apps/web` 那個字串是在「還沒有任何啟用/停用機制」的情境下寫的,狀態被直接寫死進 label 文字裡;本 story 已經提供一個獨立的「狀態」欄位(`STATUS_LABEL`,同 `AdminUser.status` 既有作法),繼續保留寫死在 label 裡的「尚未啟用」字樣,一旦管理者真的把它啟用,label 文字就會變成自相矛盾的過時資訊。

### ⚠️ 誠實記錄:「啟用雲端模型」只是 apps/admin 自己 mock store 內的畫面狀態,不會真的影響任何資料流向

這是本 story 最重要的誠實揭露:`apps/admin` 與 `apps/web` 是兩個完全獨立的 app、各自獨立的 sessionStorage(同 `departments.ts`/`groups.ts`/`prompts.ts` 已經建立的既有邊界)。本 story 的 `enableModel("cloud")` 純粹只是把 apps/admin 自己 mock store 裡那一筆記錄的 `status` 欄位改掉,**不會、也不可能**:
- 改變 `apps/web` 自己 `AI_MODELS` 常數的 `disabled: true`(那是編譯期常數,與 sessionStorage 無關);
- 讓 `apps/web` 對話頁面的模型選單真的多出一個可選的雲端選項;
- 觸發任何真正的 Model Gateway 路由決策或資料外送——因為真正的 Model Gateway 屬於 `E12`,Team B 尚未建置,`contracts/` 也還沒有任何 model 路由 endpoint。

也就是說,這個切換目前是一個「後台功能示範」的 UI 狀態展示,不是一個會產生真實跨組資料外流風險的動作。這個誠實揭露直接呼應 Non-Goals「不以 mock 假裝 production path 已完成」——本 story 沒有假裝這個開關真的接上任何東西。

### 沿用「無確認對話框」的既有 disable/enable 判斷,但誠實記錄這個判斷可能不夠用

`UserStatusToggle`(E11-S005)的既有判斷是「低風險、可逆操作不需要確認對話框」,本 story 逐一比照沿用。但「啟用外部 Cloud LLM」在概念上比「停用一個使用者帳號」更接近敏感操作(SOURCE_BASELINE 決策 #29 特別把它預設關閉,暗示背後有資料外送/合規考量)。本 story 沒有加上確認對話框,原因有二:(1)如上一節所述,這個開關目前不接任何真正有效力的系統,啟用它本身不產生真實風險;(2)`E11-S024`「dangerous-action confirmation」是這個 codebase 自己規劃、明確命名、目前尚未建置的獨立 story,專門負責這類「危險動作需要二次確認」的通用機制——本 story 不越權替 E11-S024 決定它的介面規格,只誠實記錄「等這個開關未來真的接上有效力的 Model Gateway 時,啟用外部雲端模型這個動作很可能需要 E11-S024 的確認機制」這個觀察,留給實際需要它的未來 story 決定,不是本 story 自行猜測 E11-S024 的規格。

### 不做「新增/刪除模型」

模型 tier 是 SOURCE_BASELINE 已經固定的 3 個既有 tier(同角色 enum 一樣是封閉集合),不像 Department/Group/Prompt 那樣沒有既有內容可以列舉——`ModelId` 因此故意保持嚴格的字面值聯集型別(3 個值),不像 `Department`/`Group` 允許任意新記錄。本 story 只做「查看 + 切換啟用狀態」,不做新增/刪除,理由與 `RoleList`(角色是固定 enum,無法被建立)相同。

## 對抗性自我驗證(SELF-REVIEW)

目標:證明「切換一個模型的狀態不影響其他模型」這個關鍵不變量真的被測試守護(同 E11-S005 `disableUser` 的既有 mutation pattern)。

突變:把 `disableModel` 內的 `writeStore(store.map((model) => (model.id === id ? updated : model)))` 改成 `writeStore(store.map((model) => ({ ...model, status: "disabled" })))`——模擬「忘記帶入條件、把停用套用到全部模型」這個具體錯誤。

結果:精準命中預期的 1 個測試——「only changes the targeted model's status, leaving every other model untouched」(斷言其他模型的狀態前後相等,突變後全部模型都變成 disabled,斷言正確失敗)。其餘 23 個測試檔案不受影響。

已用 `git checkout --` 還原突變(先前已用 `git add -A` 建立 checkpoint),`git diff --stat -- apps/admin/src/lib/models.ts` 確認乾淨,重新執行 admin 全部單元測試(24/24 檔案 195/195 tests)確認全綠。

- 「啟用雲端模型」目前純粹是 apps/admin 自己 mock store 內的畫面狀態切換,不接任何真正的 Model Gateway 或資料路由——完整誠實揭露已於設計決策一節記錄,避免任何誤解為真實安全控制的可能。
