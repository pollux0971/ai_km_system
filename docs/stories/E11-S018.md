## 設計決策

### 與 Audit/Feedback 表面相似(永遠空清單),但缺口性質完全不同

`Audit`(E11-S015,缺 Team B 的 E14 事件管線)與 `Feedback`(E11-S016,缺 Team A 自己尚未排到的 E13)都是「這個概念在系統裡根本還不存在」。`Document failure` 不同——`apps/web` 自己的 `knowledge-documents.ts` 早就把「文件處理失敗」這個概念做成真的了(`E05-S020`「Processing failure state」定義 `DocumentProcessingStatus = "ready" | "failed"`,`E05-S021`「Retry processing action」提供真正的 `retryDocumentProcessing()`,兩者皆已核准),而且有一個可透過 UI 真實觸發的確定性 mock 觸發字串(`MOCK_DOCUMENT_PROCESSING_FAILURE_TRIGGER`)讓一份文件真的能進入 `status: "failed"`。

真正缺的是**跨知識庫聚合的查詢管道**:本 story 的核心價值是「一次看到全系統所有知識庫的失敗文件」,這需要一個真正的後端聚合查詢(例如 `GET /admin/documents?status=failed`,跨越每個知識庫),`contracts/openapi/core.yaml` 對此完全沒有任何路徑定義。直接讀取 `apps/web` 自己的 sessionStorage 不是合法的替代方案——`apps/admin` 與 `apps/web` 是完全獨立的兩個 Next.js app,各自的瀏覽器儲存互不相通(同一份 `models.ts`(E11-S013)doc comment 早已建立的「apps/admin 與 apps/web 各自獨立 sessionStorage」邊界),而且一個真實的生產環境管理主控台本來就應該查詢真正的共用後端,不會去讀另一個前端的本機瀏覽器狀態。

同時獨立確認這個「空」答案不只是安全牌,也確實是誠實答案:查核 `apps/web/src/lib/knowledge-documents.ts` 的 `SAMPLE_KNOWLEDGE_BASE_DOCUMENTS` 種子資料,逐筆確認沒有任何一筆帶有 `status: "failed"`——每一筆種子文件都隱含是 `"ready"`。也就是說,即使真的有一個跨 KB 聚合管道存在,今天誠實查詢的結果也一樣是空的。

### `FailedDocument` 鏡射真實既有型別,不是發明

因為 `KnowledgeBaseDocument`/`DocumentProcessingStatus` 是 Team A 自己的 E05 epic 已經核准建出的真實概念,`FailedDocument` 直接鏡射它相關欄位(id/knowledgeBaseId/name/sizeBytes/uploadedAt),不是像 Audit/Feedback 那樣「暫定顯示形狀」——這是本 story 與前兩者在誠實程度上更進一步的地方:欄位本身有真實依據,只是「取得資料的管道」還不存在。

### 本 story 不含「重試」動作

「Document failure queue」是純檢視能力;`E11-S019`「Retry processing」是下一個獨立 story 的範圍,本 story 刻意不越權實作任何 mutation。

已用 `git checkout --` 還原突變(先前已用 `git add -A` 建立 checkpoint),`git diff --stat -- apps/admin/src/app/document-failures/_components/document-failure-list.tsx` 確認乾淨,重新執行 admin 全部單元測試(34/34 檔案 251/251 tests)確認全綠。
