## 使用者範圍決策(開工前)

本 story 在 INIT 階段發現一個真實的架構缺口:`apps/admin` 完全沒有 login/session
機制,共用的 `@ai-km/auth-client` mock(E01-S002)只種了 3 個非管理員帳號
(`general_user`/`maintenance_engineer`/`sales_purchasing`),真正的 RBAC/身分驗證
後端是 `E02`(Team B,未建置)。若真的把每個 admin 路由都掛上強制登入檢查,會讓
現有全部 22 個 admin E2E 測試(S002–S022,皆為直接、無登入的導覽)全部失敗——
這些測試檔案分屬其他已核准 story 自己凍結的測試內容,修改它們牽涉到跨 story
的凍結測試規則,遠超一個 0.5–2 天 thin slice 的合理範圍。

依 `.claude/rules/STORY_WORKFLOW.md` 全域規則第 7 條(「不確定就問 advisor」),
本 story 在動任何程式碼前先以 `AskUserQuestion` 向使用者提出三個範圍選項,使用者
選擇:**「只建結構,不接線」**——建立角色需求對應表 + `AdminRouteGuard` 元件,
完整單元測試(fixture 驗證 allow/deny 邏輯),但不掛進真正的 `layout.tsx`,不
新增/修改任何既有 E2E 測試。本 EVIDENCE 記錄此決策與其理由,供未來 E02 就緒後

## 設計決策

### 為什麼「只建結構」是誠實的選擇,而非規避

比照本 epic 從 S015 起一路建立的「能力完整存在、通過測試,但真正整合等待缺失的依賴到位」模式(Audit/Feedback/Document-failures 的永遠空清單、S019 Retry 的永遠 NOT_FOUND、S021/S022 的誠實零值/未知狀態)——本 story 把同一個原則套用到「接線」這個維度上:`ADMIN_ROUTES`/`rolesRequiredForAdminRoute`/`AdminRouteGuard` 三者的邏輯都是真實、完整、通過測試的,唯一缺席的是「真正掛進 layout.tsx,搭配一個真實的 session 來源」——這個缺席被诚实記錄,而非用一個假的「所有人都已經是 super_administrator」預設偽裝成已完成(那正是本 story 自己 Scope/Out 明確禁止的「以 mock 假裝 production path 已完成」)。

### 角色→路由對應的可追溯性

每一條 `ADMIN_ROUTES` 的角色指派都能回溯到 `roles.ts` 自己已核准的 `ROLE_DESCRIPTIONS`(E11-S006,源自 SOURCE_BASELINE §7):

| 路由 | 角色 | 依據 |
|---|---|---|
| `/users` | it_administrator, super_administrator | 「管理 Account」 |
| `/connectors` | it_administrator, super_administrator | 「管理...Connector」 |
| `/settings` | it_administrator, super_administrator | 「管理...System」 |
| `/health` | it_administrator, super_administrator | 「管理...System」(系統層面監控) |
| `/models` | ai_administrator, super_administrator | 「管理 Model」 |
| `/prompts` | ai_administrator, super_administrator | 「管理...Prompt」 |
| `/audit` | auditor, super_administrator | 「查看 Audit」 |
| `/knowledge` | knowledge_manager, super_administrator | 「管理 Knowledge」 |
| `/feedback`(+`/feedback/[id]`) | knowledge_manager, super_administrator | 「管理...Feedback」 |
| `/document-failures` | knowledge_manager, super_administrator | 「管理 Knowledge、Document...」 |
| `/roles`、`/permissions`、`/departments`、`/groups`、`/usage` | super_administrator only | 無角色描述有明確文字對應,Deny Wins 收斂至最嚴格選項 |

`general_user`/`department_manager`/`maintenance_engineer`/`sales_purchasing` 完全不出現在表中——四者自己的 `ROLE_DESCRIPTIONS` 都沒有點名任何 admin console 領域,依「無明確依據就不給」的原則,他們在這個 admin console 裡沒有任何合法路由。

### 未分類路由的 fail-closed 預設,刻意反轉 `RoleGuard` 的預設

`RoleGuard`(E01-S017)未列在 `NAV_ITEMS` 的路由預設「對任何已登入角色開放」,這對 apps/web 的低敏感度路由(例如 `/profile`)是安全的既有選擇。但 admin console 本身就是高敏感度系統,同一個預設在這裡是危險的——任何未來新增、尚未被分類進 `ADMIN_ROUTES` 的路由,若沿用 `RoleGuard` 的預設,會意外對任何已登入角色開放。本 story 刻意反轉這個預設:未分類 = 拒絕。此分歧已在 `admin-route-guard.tsx` 自己的 doc comment 完整說明,並由對抗性複驗的第一次突變直接驗證(見下)。

### 401(無 session)與 403(角色不符)是不同訊息,不可合併

比照 Security AC 與本 story 自己的 UX AC(「loading/empty/success/validation/permission 狀態皆有明確呈現」),`userRoles === null`(UNAUTHORIZED,「請先登入。」)與角色不符(FORBIDDEN,「您沒有權限執行此操作。」)是兩個獨立分支、兩個不同訊息——由對抗性複驗的第二次突變直接驗證兩者不會被意外合併成同一種訊息。

## 對抗性自我驗證(SELF-REVIEW)

因這是安全性相關程式碼,本次執行兩次獨立突變(較一般 story 多一次),分別鎖定兩個獨立的安全性判斷分支。

**第一次突變**:把 `allowed` 的判斷從 `requiredRoles !== undefined && requiredRoles.some(...)` 改成 `requiredRoles === undefined || requiredRoles.some(...)`(模擬「不小心把 fail-closed 預設反轉成 fail-open」)。結果:精準命中 1 個測試——「denies access to a route not in the access table, even for super_administrator — fail-closed, not silently open」。其餘 5 個測試不受影響。

**第二次突變**:把獨立的 `userRoles === null` 分支(回傳 UNAUTHORIZED)合併進 `allowed` 判斷式(`userRoles !== null && requiredRoles !== undefined && ...`),讓 null session 落入同一個 `!allowed` 分支、顯示 FORBIDDEN 而非 UNAUTHORIZED。結果:精準命中 1 個測試——「shows an UNAUTHORIZED message and hides children when there is no session at all」(斷言文字從「請先登入。」變成「您沒有權限執行此操作。」)。其餘 5 個測試不受影響。

兩次突變皆已用 `git checkout --` 還原(先前已用 `git add -A` 建立 checkpoint),每次還原後重新執行 admin 全部單元測試(43/43 檔案 300/300 tests)確認全綠。

## Assumptions / 計畫外事項

- **重大已知限制,明確記錄**:`AdminRouteGuard` 未接線至 `apps/admin/src/app/layout.tsx`,admin console 目前仍是完全開放、無登入檢查的狀態——與 S001 至 S022 的既有行為完全一致,本 story 未改變任何實際存取控制。真正接線需要:(a) 一個真實或至少可信賴的 admin session 來源(E02 Team B 或一個經過審慎設計的 admin-local mock),(b) 協調更新全部 22 個既有 admin E2E spec 加上登入流程——這是遠超本 story 範圍的後續工作,建議留給 E02 就緒後的一個獨立、明確範圍的未來 story。
