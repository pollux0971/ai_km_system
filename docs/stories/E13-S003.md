## 背景 / 設計決策

Epic 檔(`AI_KM_BMAD_High_Granularity/epics/E13_Feedback_&_Analytics.md`)對
E13-S003 只有泛用樣板文字(「此能力」= feedback reason selector),沒有
reason 選項清單或 UI 形狀。grep 整個 `AI_KM_BMAD_High_Granularity/` 目錄
(含 `SOURCE_BASELINE.md`)找「feedback reason」「回饋原因」「不正確」
「不完整」「離題」等關鍵字,除 epic 檔自己的樣板文字外零命中——
`SOURCE_BASELINE.md` 第 548 行的黃金流程只到「OK / NG → Feedback Loop」,
沒有再往下定義 reason 選項。`contracts/` 目錄同樣零 feedback 相關內容。

**ASSUMPTION(誠實記錄,非 BLOCKED)**:依 ATOMIC_STORY_BOUNDARIES.md「AI
Agent Rule:不知道產品行為 → BLOCKED/ASSUMPTION」的精神,這屬於 UI copy
層級的產品決策,不是 contract/endpoint/permission 這種硬性依賴,且 story
標題本身已經預期這個能力存在、MVP 允許簡化視覺——因此不整個 story
BLOCKED,而是採用一組最小、常識性、可從 story 名稱直接推導的 4 個選項:
`INCORRECT`(答案不正確)/`INCOMPLETE`(答案不完整)/`OFF_TOPIC`(答案離題)/
`OTHER`(其他)。

`docs/stories/PROGRESS.md` 確認 E13-S001/S002 皆已 approved,本 story 從
最新 main(含兩者的全部 commit)分支出去。讀過 `apps/web/src/lib/messages.ts`
與 `message-thread.tsx` 完整理解 S001/S002 建立的既有機制
(`AnswerFeedbackVerdict`/`submitAnswerFeedback`/兩個 feedback 按鈕、
「一旦有任一 verdict 就永久 disabled」不變量)。

**設計決策——`feedbackReason` 是獨立於 `feedback` 的新欄位,附加資訊,
不是擴充 verdict 本身**:一個 reason 永遠只用來「附加說明」一個已經給出
的 NG verdict,它自己從來不是 verdict。若把它折進 `feedback` 型別(例如
`"OK" | "NG" | "NG:INCORRECT" | ...`)會強迫每一個 OK-feedback 的既有
fixture 也要考慮一個對它完全不適用的維度,且會讓「先給 NG、之後才選
reason」這個自然的兩步驟互動變得不自然。

**設計決策——NG 按鈕的既有行為完全不變,reason selector 是純附加 UI**:
按下「沒有幫助」仍然像 S002 一樣**立即**呼叫 `submitAnswerFeedback(id,
"NG")` 並讓兩個按鈕永久 disabled——這保留了 S002 全部既有(已 approved)
單元/元件/E2E 測試逐字不動、無需修改任何既有斷言。Reason selector
(`<fieldset>` + 4 個 radio + 獨立的「送出原因」按鈕)只在
`entry.message.feedback === "NG"` 已成立後才出現,是這個已解決狀態之上的
**新增**互動,不重新設計「按下 NG 會發生什麼」這件事。曾考慮過的替代方案
(讓 NG 按鈕本身先開啟 selector、選了理由才真正送出 NG)會需要修改 S002
既有測試斷言「clicking 沒有幫助 submits NG feedback...immediately」的
驗證意圖,牴觸 Phase 2 第 2 點「測試內容只增不減」,故不採用。

**Functional AC 2(缺少必要輸入 fail-closed)的落地方式**:「送出原因」
按鈕在尚未選擇任何 radio 前保持 `disabled`(client-side gate),真實 UI
無法觸發「未選擇就送出」;`submitFeedbackReason()` 函式層另外對
`feedback !== "NG"` 的情況(尚未給過回饋,或給的是 OK)回傳
`VALIDATION_ERROR`、不寫入 `feedbackReason`——涵蓋「這個呼叫在真實 UI
中不應該可達」與 S001/S002 對 `submitAnswerFeedback` 的 `role !==
"assistant"` 檢查同一種 fail-closed 理由。

## Assumptions / 計畫外事項

1. **4 個 feedback reason 選項是 Team A 的 ASSUMPTION,非規格明文定義**:
   grep 整個 `AI_KM_BMAD_High_Granularity/` 目錄零命中任何 reason 選項
   清單。`INCORRECT`/`INCOMPLETE`/`OFF_TOPIC`/`OTHER` 是從 story 標題
   「feedback reason selector」與業界常見 pattern(YouTube dislike
   reason、ChatGPT thumbs-down reason)推導的最小常識性集合,依
   ATOMIC_STORY_BOUNDARIES.md 的 AI Agent Rule 精神記錄為 ASSUMPTION 而
   非 BLOCKED——這是 UI copy 決策,不是 contract/endpoint/permission。
   若使用者或 Team B 之後提供真實的 reason taxonomy,需要新的 story 或
   本 story 的 follow-up 來對齊。
2. **Security AC 的範圍限制**:與 S001/S002 完全一致——本 story 沒有新增
   獨立的 negative-authz 測試,沿用本 codebase 所有 E03 對話訊息
   mutation story(含 S001/S002 自己)已建立的既有安全模型:授權邊界在
   route 層(E01-S017 RoleGuard)統一把關,訊息層級的 mutation 動作本身
   不重複驗證授權。非本 story 獨有的縮減,是延續 S001/S002 已核准的
   判斷。
3. **`submitFeedbackReason` 允許覆寫既有 reason(函式層無 guard)**:
   `feedbackReason` 欄位若已設定,再次呼叫會成功覆寫(見「upserts the
   same row when switching reasons」測試)。「無 undo」的不變量只在 UI
   層強制(一旦 `entry.message.feedbackReason` 有值,整個 selector 永久
   disabled,使用者透過真實介面無法觸發覆寫),同 S001/S002 對
   `submitAnswerFeedback` 建立的信任邊界一致——此路徑(直接呼叫函式覆寫)
   在真實 UI 中不可達。
4. **無真實 audit/E14 pipeline**:與 S001/S002 完全相同的既有限制
   (Team A 前端 telemetry 慣例,非真正的 E14 audit event pipeline)。
5. **未更新 `apps/admin` 的 Feedback queue(E11-S016/S017)**:與
   S001/S002 完全相同的既有限制,不屬於本 story 的允許修改邊界。
6. **NG 按鈕本身的既有互動完全未變**(見上方「設計決策」):選擇讓
   selector 純附加於已解決的 NG 狀態之上,而非把「選擇原因」變成 NG
   提交流程的必經步驟,是為了保留 S002 既有(已 approved)測試逐字不動,
   非規格明文指定的順序,已誠實記錄為設計決策而非規格事實。
