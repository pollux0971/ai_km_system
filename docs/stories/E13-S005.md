## 背景 / 設計決策

Epic 檔(`AI_KM_BMAD_High_Granularity/epics/E13_Feedback_&_Analytics.md`)對
E13-S005 只有泛用樣板文字(「此能力」= citation-specific feedback),沒有
欄位形狀、資料結構或互動位置。grep 整個 `AI_KM_BMAD_High_Granularity/`
目錄(含 `SOURCE_BASELINE.md`)找「citation-specific」「引用回饋」「per
citation」等關鍵字,唯一命中是 epic 檔自己的樣板標題,無其他內容。
`contracts/` 目錄同樣零 citation feedback 相關內容。

`docs/stories/PROGRESS.md` 確認 E13-S001~S004 皆已 approved,本 story從
最新 main(含全部四者的 commit)分支出去。讀過既有機制:

- `apps/web/src/lib/messages.ts` 的 `AnswerFeedbackVerdict`/
  `submitAnswerFeedback`/`submitFeedbackReason`/`submitFeedbackComment`
  ——整個 S001~S004 建立的回饋機制全部作用在**整則訊息**層級(一個
  `feedback` 欄位對應一個 assistant reply)。
- `apps/web/src/lib/citations.ts`(E03-S014/S015/S016)——citation 不是
  `Message` 上的結構化陣列欄位,而是從 assistant reply 的 `content` 文字
  中用 `[N]` marker 正則解析出來(`message-content.tsx` 的
  `CITATION_PATTERN`),點擊後透過 `getCitationSource(id)` 查詢
  `MOCK_CITATION_SOURCES`(File/Page/Snippet),顯示在 `message-thread.tsx`
  唯一共用的 `CitationPreviewDrawer`。

**核心產品判斷——"citation-specific" 與 S001-S004 的「整則訊息」層級不同,
必須是「該訊息內某一個特定 `[N]` 引用」的層級**:story 名稱本身就是
「citation-specific」,若直接重用 message 層級的 `feedback` 欄位,等於
重複做了 S001 已經做過的事,完全沒有反映 story 名稱裡「citation-specific」
這個限定詞。因此設計為一個 `Record<string, AnswerFeedbackVerdict>`(鍵是
citationId),而非單一欄位——因為同一則訊息的 content 可能含有多個不同的
`[N]` marker,各自需要獨立記錄。

**ASSUMPTION 1(誠實記錄,非 BLOCKED)——欄位存在與形狀**:依
ATOMIC_STORY_BOUNDARIES.md「AI Agent Rule:不知道產品行為 →
BLOCKED/ASSUMPTION」的精神,這屬於 UI/資料形狀的產品決策,不是
contract/endpoint/permission 這種硬性依賴,且 story 標題本身已經預期這個
能力存在、MVP 允許簡化視覺——因此不整個 story BLOCKED,而是新增
`citationFeedback?: Record<string, AnswerFeedbackVerdict>` 欄位與
`submitCitationFeedback(messageId, citationId, verdict)` 函式。重用既有
`AnswerFeedbackVerdict`("OK" | "NG")型別,而非發明平行的 citation 專屬
verdict 型別——「這個引用來源有幫助/不準確」與「這整個回答有幫助/沒幫助」
是同一種 OK/NG 判斷形狀,只是範圍縮小到單一引用。

**ASSUMPTION 2(設計決策)——UI 掛在 `CitationPreviewDrawer`,不是 badge
本身**:citation badge(`<sup><button>`)本身只是文字中一個 `[N]` marker
的行內按鈕,沒有空間容納額外的回饋 UI;而 `CitationPreviewDrawer` 才是
使用者實際「看到這個引用來源內容」的地方(File/Page/Snippet),在這裡
問「這個引用有幫助嗎」才有語意——使用者要先看到來源內容才能判斷,不是
盲目對一個 `[N]` 數字按讚。`CitationPreviewDrawer` 是整個 thread 唯一共用
的單一 drawer(非每則訊息各自一個),因此它必須同時知道「目前預覽的是哪個
citationId」與「屬於哪個 messageId」才能正確記錄回饋——`message-thread.tsx`
新增 `previewMessageId` state(與既有 `previewCitationId` 並存),
`handleCitationClick` 從只接收 `citationId` 擴充為同時接收
`(citationId, messageId | null)`。

**ASSUMPTION 3(fail-closed 驗證,對應 Security Acceptance「所有外部輸入均
做 schema validation」)——`citationId` 必須真的出現在該訊息的 content
裡才接受回饋**:`submitCitationFeedback` 新增 `extractCitationIds(content)`
輔助函式(鏡射 `message-content.tsx` 的 `CITATION_PATTERN` 正則,獨立實作
而非跨檔 import——這個 lib 模組沒有既有先例從一個 `"use client"`
元件檔案 import 東西,兩邊各自的用途也不同:一個是渲染、一個是驗證),
若呼叫端傳入一個這則訊息從未顯示過的 citationId,回傳 `VALIDATION_ERROR`
而非靜默接受——沒有這個檢查,呼叫端能夠對一個使用者從未在真實 UI 上看過
的引用 id 記錄回饋,這樣的輸入沒有經過驗證就被接受了。

**設計決策——`messageId` 為 `null`(而非只是 disabled)時完全不渲染回饋
按鈕**:比照 `message-thread.tsx` 既有的「只在 `entry.kind === 'sent'`
才渲染整則訊息回饋按鈕」判斷——一個仍在串流中(`kind === 'streaming'`)、
尚未真正持久化的訊息沒有真實 `messageId` 可以掛回饋,`CitationPreviewDrawer`
在這種情況下完全隱藏回饋 UI,而不是顯示一個永遠會失敗的按鈕。

**設計決策——`CitationPreviewDrawer` 維持既有的純呈現(presentational)
角色,新的 pending/error/verdict 狀態全部由 `message-thread.tsx` 擁有並
以 props 傳入**:比照這個元件既有的 citation-lookup 狀態管理方式(它自己
只管 `getCitationSource` 的 loading/error/loaded,不管 mutation),新的
`feedbackVerdict`/`feedbackPending`/`feedbackError`/`onSubmitFeedback`
四個 props 全部有預設值(`null`/`false`/`false`/no-op),讓
`citation-preview-drawer.test.tsx` 既有的 14 個測試呼叫點完全不需要修改
——這是刻意的向下相容設計,不是巧合。

**設計決策——沿用 S001~S004 已建立的「no undo once given」鎖定模式,且是
「雙向」鎖定(給了 OK,NG 按鈕也一起鎖,反之亦然)**:`CitationPreviewDrawer`
的 disabled 條件是 `feedbackVerdict != null`(不分哪個按鈕),與 S002 對
message 層級 OK/NG 按鈕的雙向鎖定邏輯完全一致——這是刻意重複 S002 已核准
的 pattern,不是新發明。

## FIX 循環紀錄(0 次,首次執行即全綠)

實作與測試皆一次寫完即通過 `pnpm typecheck`/`pnpm lint`/`pnpm test`
(unit)/E2E,無需修改任何邏輯或測試內容。撰寫過程中發現一個非邏輯錯誤的
小插曲(不計入 FIX 循環,因為未曾提交過失敗版本、屬於撰寫階段自我糾正):
`getByRole("button", { name: ..., exact: true })` 這個寫法對 Testing
Library(而非 Playwright)的 `ByRoleOptions` 型別無效——`tsc --noEmit`
報錯「'exact' does not exist in type 'ByRoleOptions'」。這是誤用了
S002 EVIDENCE 記錄的 Playwright 慣例(Playwright 的 `getByRole({name})`
預設子字串比對,需要 `exact: true`);但 Testing Library 的 `getByRole`
對 `name` 的比對**預設本來就是精確比對**,不像 Playwright 那樣預設子字串
——因此 `exact` 選項對 `getByRole` 根本不存在(它只存在於
`getByText`/`queryByText` 這類文字比對 API 上,`citation-preview-drawer.tsx`
既有的 3 處 `queryByText(..., {exact:true})` 屬於這一類、完全正確、未
改動)。發現後直接移除新增測試裡誤加的 `exact: true`(共 22 處
`getByRole` 呼叫),改回純 `{name: "..."}"`,`tsc --noEmit` 立即轉綠。
