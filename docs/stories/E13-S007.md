## 現況盤點(Scope 判斷的依據)

`AI_KM_BMAD_High_Granularity/epics/E13_Feedback_&_Analytics.md` 的 E13-S007 章節逐字比對後確認與其他 E13 story 完全相同,是泛用樣板文字,無任何 story 專屬內容(標題「feedback queue filter」外無其他線索)。`contracts/` 逐字搜尋零 feedback 相關內容。

這是 `apps/admin`(不是 `apps/web`)的能力。已核准的 `docs/stories/E11-S016.md`(Feedback queue)與 `docs/stories/E11-S017.md`(Feedback detail)建立了 `apps/admin/src/lib/feedback.ts` 的 `listFeedback()`/`getFeedback(id)`——兩者皆誠實地永遠回傳空陣列/`null`,理由是這個 codebase 沒有真正的後端 API server,`apps/admin` 與 `apps/web` 是兩個獨立 Next.js app、各自獨立的 `sessionStorage`,admin 端沒有任何管道能讀到使用者在 `apps/web` 端(E13-S001~S006)實際送出的回饋資料。E11-S016 的設計決策明確記錄:「回饋的核心價值就是『使用者真的給出的判斷』,讓 admin 自己填入等於允許偽造使用者意見」。

本 story 的核心限制因此是:`listFeedback()` 本身不變(仍永遠回傳 `[]`),任何「filter」功能在今天的真實生產環境裡都沒有東西可濾。判斷:比照 `feedback-list.test.tsx` 既有的 loaded 狀態測試方式(用 `vi.mock` 注入 fixture 資料驗證渲染邏輯,而非依賴 `listFeedback()` 真的回傳東西),filter *邏輯* 的正確性可以用測試 fixture 完整證明,但畫面上*呈現*必須誠實反映「目前系統沒有任何真實回饋資料」——filter 控制項本身只在真的有資料可濾時才顯示;真正空佇列時不顯示任何 filter UI(避免展示一個沒有東西可操作的控制項,誤導管理者以為系統裡已經有可篩選的資料)。

這條路徑被判斷為可行、且不需要 BLOCKED——filter 邏輯本身(`filterFeedback`)是一個對已載入資料做純函式篩選的能力,不涉及任何新的資料來源、endpoint 或偽造資料,完全可以誠實地被證明正確。

## 變更檔案

- `apps/admin/src/lib/feedback.ts`(修改)— 新增 `FeedbackFilterCriteria { verdict?, hasReason? }` 型別與 `filterFeedback(items, criteria)` 純函式(依 verdict 精確比對、依 hasReason 判斷 `reason` 是否為非空字串,兩條件同時給出時取交集)。`listFeedback()`/`getFeedback()` 完全未修改。
- `apps/admin/src/lib/feedback.test.ts`(修改,純新增)— 新增 8 個 `filterFeedback` 測試:無條件回傳全部、依 verdict ok/ng 各自篩選、依 hasReason true/false 各自篩選、verdict+hasReason 交集、空陣列輸入不受 criteria 影響、無符合項回傳空陣列、不修改輸入陣列(purity)。既有 `listFeedback`/`getFeedback` 測試零修改。
- `apps/admin/src/app/feedback/_components/feedback-list.tsx`(修改)— loaded 狀態拆出 `LoadedFeedbackList` 子元件,新增依判斷篩選(`<select>`:全部/只看 OK/只看 NG)與只顯示有填寫原因的回饋(`<checkbox>`)兩個 filter 控制項,`useMemo` 呼叫 `filterFeedback(items, criteria)` 做純前端篩選。**Filter 結果為空與「佇列本身為空」是兩個不同的正式狀態**:前者顯示「沒有符合篩選條件的回饋。」,後者維持既有的「尚無回饋。」,不得混為一談。Filter 控制項只在 `items.length > 0` 時才渲染(佇列本身為空時,沒有東西可濾,顯示 filter UI 會誤導)。既有渲染邏輯(verdict label、reason 段落、submittedAt time、連結)原封不動搬進新的子元件,無行為變更。
- `apps/admin/src/app/feedback/_components/feedback-list.test.tsx`(修改)— 新增 9 個 filter 互動測試(見下)。**唯一對既有程式碼的修改**是 `vi.mock("@/lib/feedback", ...)` 從完全替換模組改為 `importOriginal` + 覆寫 `listFeedback`(見「窄例外」一節),import 語句相應擴充。既有 9 個 `it(...)` 測試本體(斷言內容)逐行核對,零修改。
- `tests/e2e/specs/admin-feedback.spec.ts`(修改,純新增)— 新增 1 個 E2E 測試:真實空佇列時不顯示任何 filter 控制項。既有 2 個測試零修改。
- `docs/stories/E13-S007.md`(新增)— 本檔。
- `docs/stories/PROGRESS.md`(修改)— 進度轉換。

## 窄例外:`vi.mock` 宣告方式修正(STORY_WORKFLOW Phase 4 第 5 點)

**問題**:既有 `vi.mock("@/lib/feedback", () => ({ listFeedback: vi.fn() }))` 完全替換整個模組,導致新增的 `filterFeedback`(真實函式,非 mock 對象)在元件內部呼叫時變成 `undefined`,拋出 `[vitest] No "filterFeedback" export is defined on the mock` 執行期錯誤——這不是任何既有測試斷言邏輯有誤,而是既有 mock 宣告的技術性限制(完全替換模組 vs 部分替換)在新增第二個真實 export 後才會顯現的技術問題。

**修正**:改用 `vi.mock("@/lib/feedback", async (importOriginal) => { const actual = await importOriginal(); return { ...actual, listFeedback: vi.fn() }; })`——保留模組其餘的真實 export(`filterFeedback`、`FeedbackItem` 型別),只覆寫 `listFeedback`。

**判斷理由**:這是純技術性修正,不是放寬任何測試的斷言或行為。`listFeedback` 的 mock 行為(`vi.fn()`,每個測試各自 `mockResolvedValue`/`mockReturnValue`)完全不變,既有 9 個測試的斷言內容逐字核對後零修改、預期行為不變——重跑後全部照常通過。修正後 `filterFeedback` 首次成為真實可呼叫函式,這正是本 story 需要的行為(讓元件測試用真實 filter 邏輯,而非再次 mock 一層假的篩選邏輯)。

**目標 1**:證明 `filterFeedback` 的 verdict/hasReason 篩選邏輯真的被測試守護,不是恆定回傳全部或恆定回傳空。
