## 設計決策

### 新增獨立模組:`feedback-knowledge-candidates.ts`

`FeedbackKnowledgeCandidate { id, sourceMessageId, conversationId, answerContent, reason, comment, createdAt }` ——欄位形狀是 Team A 的 ASSUMPTION(epic 檔案零規格依據),`reason`/`comment` 直接重用 `messages.ts` 已核准的 `FeedbackReason`/`feedbackComment` 型別與值,不重新發明。獨立於 `messages.ts` 的原因同 `usage-events.ts` 已建立的先例(見其 doc comment):一個訊息衍生出的、獨立可審核的產物,不是 `Message` 本身要再長出的欄位。獨立於 E07-S023 的 `knowledge-candidates.ts` 的原因見上一節。

`submitFeedbackKnowledgeCandidate(message: Message)`:fail-closed 驗證 `message.feedback === "NG"`、`feedbackReason != null`、`feedbackComment` 非空白(三個獨立檢查各自獨立的 VALIDATION_ERROR 訊息),不信任呼叫端已經做過檢查(同 `submitAnswerFeedback`/`submitCitationFeedback` 對 `role !== "assistant"` 的既有 defense-in-depth 慣例)。以 `sourceMessageId` 去重(不是像其他 submit* 函式那樣允許覆寫)——同一則訊息重複標記回傳**同一個既有候選**,不是新建一筆,因為候選沒有「換一個版本」的概念(不像 verdict 可以從 OK 換成 NG)。

### UI wiring:`message-thread.tsx`

新按鈕「標記為知識落差候選」只在 `feedback === "NG" && feedbackReason != null && feedbackComment != null` 三者皆滿足時才 render,緊接在既有留言 fieldset 之後。點擊後鎖定(no-undo,同 S001~S014 一路建立的 pattern),pending/error 狀態各自獨立 local state(`knowledgeCandidateIds`/`knowledgeCandidatePendingIds`/`knowledgeCandidateErrorIds`)。

**開發過程中自行發現並修正的第二個真實 bug**:初版把「已標記」狀態完全放在 local React state,元件重新掛載(切換頁面再返回、或重新整理)後這個 local state 會重置為空——即使候選資料本身已經真的持久化在 `feedback-knowledge-candidates.ts` 的 sessionStorage 裡,畫面上的按鈕卻會顯示回「尚未標記」的可點擊狀態,這是不誠實的 UI(資料明明存在,介面卻假裝不存在)。用新增的 E2E 測試(見下)在本機真實重現後定位到根因,修正方式:`listMessages` 成功載入後,額外呼叫 `listFeedbackKnowledgeCandidates()` 並依 `conversationId` 過濾,初始化 `knowledgeCandidateIds`,讓「已標記」狀態正確地在每次掛載時從真實持久化資料重新推導,而非只靠一次性的 local state。修正後補上對應的 unit test(初始載入時若已有候選,按鈕直接鎖定;不同 conversation 的候選不會誤鎖）與 E2E 測試(見下)驗證,兩者皆在修正前會失敗、修正後通過。

## 獨立審核 Round 1 — REQUEST-CHANGES 修正記錄

**審核者發現的問題(1 個 MAJOR)**:`feedback-knowledge-candidates.test.ts` 裡「fails closed with VALIDATION_ERROR for an OK-feedback message, even with a comment」這個測試的 fixture 是 `feedback: "OK"` + `feedbackComment`,**沒有** `feedbackReason`——這樣的輸入會先落進 `submitFeedbackKnowledgeCandidate` 的第二道 guard(`feedbackReason == null`)就被拒絕,回傳一樣的 `VALIDATION_ERROR` code,測試斷言區分不出來是哪一道 guard 擋下的。審核者對抗性突變第一道 guard(`message.feedback !== "NG"` 改成恆定 `false`)後,原本 9 個測試全部依然通過,證明第一道 guard 本身完全沒有獨立測試覆蓋。

**根因**:第二道 guard(`feedbackReason == null`)意外掩護了第一道 guard(`feedback !== "NG"`)——因為現實中 OK feedback 永遠不會真的有 reason(這是 production 端的不變量),既有測試沿用這個現實情境當 fixture,反而讓兩道獨立的檢查在測試裡永遠疊在一起觸發,無法單獨證明任何一道真的在運作。

**修正**:新增(未修改既有斷言)1 個測試「fails closed with VALIDATION_ERROR for an OK-feedback message even when it also has a reason and comment (isolates the feedback!==NG guard from the reason guard)」——fixture 刻意給 OK feedback 一個 production 端不可能出現的 `feedbackReason`+`feedbackComment` 組合,純粹用來讓第一道 guard 在沒有第二道 guard 介入的情況下獨立被測試命中。這是純新增覆蓋,不是放寬既有斷言配合實作,既有測試逐字未動。用審核者的原始突變(`if (message.feedback !== "NG")` → `if (false)`)驗證:精準命中這 1 個新測試(10 個測試中僅 1 個失敗,其餘 9 個不受影響),突變已還原,`git diff HEAD -- apps/web/src/lib/feedback-knowledge-candidates.ts` 確認空白(逐位元組復原)。

## Assumptions

1. `FeedbackKnowledgeCandidate` 的欄位形狀是 UI/資料層級的 ASSUMPTION,不是任何已核准 contract 的事實。
2. 沿用 S001~S014 既定的 Security AC 邊界(route-level guard,無新增 per-action authz test)。
3. `submitFeedbackKnowledgeCandidate` 是 idempotent dedup(同一訊息回傳同一候選),不是像其他 submit* 函式那樣允許覆寫——候選沒有「換版本」的概念。
4. 候選資料完全存在 apps/web 自己的 sessionStorage,`apps/admin` 完全未觸碰,沒有任何審核/彙總 UI(那可能是本 epic 之外、需要 Team B 提供真正 ingestion contract 之後的未來 story)。
5. Telemetry payload(`conversation_knowledge_candidate_*`)只帶 `conversationId`/`messageId`/(失敗時)`code`,不含留言原文,延續 S004 已建立的敏感內容原則。
