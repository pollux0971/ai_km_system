## Scope 判斷

epic 檔 E13-S016 本身零 story 專屬內容（樣板文字，已 grep `AI_KM_BMAD_High_Granularity/` 確認）。依 story 標題與 `DEVELOPMENT_POLICY.md` 第 3 點（「Unauthorized data must never enter retrieval context, LLM prompt, citation, export, logs, or analytics」）與 Observability/Audit Boundary（「Telemetry 可記錄 operation metadata，不得記錄不必要的企業原文或敏感 payload」），本 story 的合理範圍是：**系統性稽核整個 E13 epic（S001~S015）累積下來的所有 analytics/usage/telemetry 資料結構與 payload，確認是否含個資/敏感原文，並補上防止未來回歸的證明測試**——不是重新設計已有的功能。

## 逐欄位稽核清單

### 1. `apps/web/src/lib/usage-events.ts`（`UsageEvent`，S009~S013 建立）

| 欄位 | 型別 | 風險判斷 | 結論 |
|---|---|---|---|
| `name` | enum(`UsageEventName`) | 結構化列舉，非原文 | 安全 |
| `userId` | string（識別符） | 分析維度必要欄位，這個 codebase 一路（S009 起）都用它做 DAU 去重，非本 story 新風險 | 安全 |
| `occurredAt` | ISO timestamp | 純時間戳 | 安全 |
| `answerState` | enum(`AnswerState`) | 結構化列舉（ANSWERED/PARTIAL/NO_EVIDENCE/...），非原文 | 安全 |
| `citationCount` | number | 純數值 | 安全 |
| `latencyMs` | number | 純數值 | 安全 |

`UsageEvent` 型別本身完全沒有任何 free-text 欄位——`interface` 定義即為安全的證明（TypeScript 結構本身就是白名單）。

**發現的真實風險（已修正，見下方「修正」章節）**：`recordUsageEvent(name, userId, details)` 原本用 `...details` spread 建構要持久化的物件。`details` 參數型別雖然只宣告 `answerState`/`citationCount`/`latencyMs` 三個 optional 欄位，但 TypeScript 的 excess-property check **只在呼叫端傳入物件字面量（literal）時生效**——若未來某個呼叫點先把 details 存進一個變數（尤其是型別寬鬆或用了 `as`/`any` 的情況）再傳入，spread 會把任何額外欄位（例如不小心複製貼上 `feedback-knowledge-candidates.ts` 的 `comment`/`answerContent`）原封不動寫進 sessionStorage 的持久化 analytics store，TypeScript 不會在執行期擋下這個情況。**這是本 story 稽核發現的唯一真實問題**，已用 explicit field-picking（而非 spread）修正，讓 `recordUsageEvent` 自己就是強制點，不再只依賴呼叫端的型別紀律。

### 2. `apps/web/src/lib/telemetry.ts`（`trackEvent`，跨 50+ 呼叫點的既有機制，非本 story 新建）

`trackEvent(name, { correlationId, properties })` 的 `properties: Record<string, unknown>` 本身是刻意開放式設計（服務全 codebase 各種 domain 的 UI 功能遙測，不是本 epic 專屬）。逐一 grep `apps/web/src/app/(app)/conversations/[id]/_components/message-thread.tsx`（本 epic 唯一大量呼叫 `trackEvent` 的檔案）內全部 27 處 `trackEvent`/`logger.*` 呼叫，確認每一處 `properties`/log context 只包含 `correlationId`/`conversationId`/`messageId`/`citationId`/`verdict`/`reason`/`code`/`attachmentCount`/`length`（數字）這類 ID/enum/數值/錯誤碼，**沒有任何一處把 `feedbackComment`、`answerContent`、訊息 `content` 本身塞進 payload**。逐項核對：

- `conversation_feedback_comment_attempt/success/failure`（S004 留言功能自己的 telemetry）：只有 `conversationId`/`messageId`/`code`，不含留言文字本身——這正是 S004 自己 EVIDENCE 就已經記錄過的設計決策，本次稽核獨立重新驗證屬實。
- `conversation_knowledge_candidate_attempt/success/failure`（S015）：只有 `conversationId`/`messageId`/`candidateId`/`code`，不含 `answerContent`/`comment`。
- `conversation_citation_feedback_*`（S005）：只有 `citationId`/`verdict`，不含引用來源內容本身。

修改 `trackEvent` 本身的型別（例如收斂 `properties` 的 schema）會是一次跨全 codebase 50+ 呼叫點的 shared package 變更，逾越本 story（Team A、E13 domain）的 Domain Ownership Boundary，且目前逐一查證後零風險，**不需要也不應該修改**。

### 3. `apps/web/src/lib/messages.ts`（`Message.feedback`/`feedbackReason`/`feedbackComment`/`citationFeedback`，S001~S005）

這些是 domain 資料本身（使用者實際回饋內容），不是「analytics」——`feedbackComment` 儲存使用者自己輸入的留言原文是這個欄位存在的目的（S004 已核准），不是意外洩漏。稽核重點是「這些欄位有沒有意外流入 usage-events.ts 這種自動化彙總 store」——已在第 1 點確認沒有。`apps/admin` 的 `FeedbackDetail`（S008）顯示 `comment` 也是刻意設計（管理者審閱介面），非自動化分析輸出。

### 4. `apps/web/src/lib/feedback-knowledge-candidates.ts`（`FeedbackKnowledgeCandidate`，S015）

`answerContent`/`comment` 兩個欄位**刻意**儲存完整原文——S015 自己的 doc comment 已說明這是「給知識庫維運人員審閱」的產物，不是自動化 analytics 彙總。這跟 `usage-events.ts` 的用途本質不同：後者是要被 `computeDAU`/`computeQuestionsAsked`/`computeAverageLatencyMs` 這類跨使用者統計函式讀取的匿名化分析資料，前者是給人類逐筆審閱的內容型 artifact，兩者的隱私考量標準不同，不能一概而論。**結論：`FeedbackKnowledgeCandidate` 含原文是刻意且正確的設計，不是本 story 要修正的對象**——但這正是為什麼第 1 點發現的 `recordUsageEvent` 缺乏 runtime allowlist 是真實風險：若未來開發者把這兩個模組搞混（S015 自己的 doc comment 就記錄過一次真實的檔名撞名插曲），沒有 runtime 防護的話，`comment`/`answerContent` 就可能被誤塞進 `usage-events.ts` 的持久化 store。修正後的 `recordUsageEvent` 現在是這個風險的最後防線。

### 5. `apps/admin` 端（`feedback.ts`/`usage-metrics.ts`/`latency-metrics.ts`）

grep 確認這三個檔案完全沒有 `trackEvent`/`logger.*` 呼叫，`listFeedback()`/`getUsageMetrics()`/`getLatencyMetrics()` 皆是純讀取函式，不涉及任何 telemetry payload 建構。無風險。

## 修正

`apps/web/src/lib/usage-events.ts` 的 `recordUsageEvent`：把 `events.push({ name, userId, occurredAt, ...details })`（spread）改為逐一明確列出 `answerState`/`citationCount`/`latencyMs` 三個已知安全欄位（不再 spread `details` 整個物件）。這讓函式本身成為強制點，即使未來某個呼叫端不小心傳入含 `comment`/`answerContent` 的物件，也不會被寫進持久化 store。純函式層修正，零行為變更（JSON 序列化本來就會丟棄 undefined 值的 key，round-trip 後既有測試斷言的物件形狀完全不變，33 個既有測試零修改全數通過）。
