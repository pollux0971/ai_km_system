## 稽核過程

完整讀過 `docs/stories/E13-S001.md`~`E13-S016.md` 全部 EVIDENCE,盤點
這個 epic 累積下來的全部能力:

- **apps/admin**:feedback queue+filter+detail+OK/NG rate(E11-S016/
  S017、E13-S007/S008/S014)、usage dashboard(E11-S021,由 S009/S010/
  S012 供資料模型)、latency dashboard(S013)。

逐一讀過 `tests/e2e/specs/` 下全部與 E13 相關的既有 spec(11 個檔案:
`answer-ok-feedback`/`answer-ng-feedback`/`feedback-reason-selector`/
`free-text-feedback`/`citation-feedback`/`feedback-submission-state`/
`feedback-to-knowledge-candidate`/`usage-event-instrumentation`/

`latency-instrumentation`,加上 apps/admin 端 4 個相關 spec:
`admin-feedback`/`admin-usage`/`admin-latency`/`admin-e2e`),找到兩個
具體落差:

### 落差 1(apps/web):真實多動作 session 的事件序列從未被端對端驗證過

S009~S013 各自的測試只驗證「單一動作 → 單一事件」——
`usage-event-instrumentation.spec.ts` 只送一則訊息、
`conversation-created-event.spec.ts` 只建立一個空對話、
`rag-outcome-analytics.spec.ts`/`latency-instrumentation.spec.ts` 各自
只檢查一則回答的單一事件。從未有任何測試證明「一個真實使用者 session
裡連續發生多個動作(送出多則訊息)後,`usage-events` sessionStorage
累積出的完整事件序列本身正確、一致、可歸因(同一個 userId、每則回覆
各自一組 `conversation_message_sent`+`rag_answer_outcome`、依真實發生
順序排列、無交叉污染)」——這正是這一整組 analytics 事件真正要交付的
價值(可靠的原始資料序列,供未來 Team B 提供真實跨 app 管道時直接
消費),但從未被端對端驗證過。

另外,`E13-S006`(feedback submission state)驗證了 verdict/reason/
comment/citation 四個回饋維度在同一則回覆上的組合,但 S006 完成時
`E13-S015`(feedback-to-knowledge-candidate flow)還不存在——沒有任何
測試證明「知識落差候選標記」與其他四個回饋維度、以及背景自動記錄的
usage/RAG events,在同一個真實 session 裡全部同時發生時彼此不干擾,
也未證明這五者跨頁面導覽後仍然全部正確持久化。

### 落差 2(apps/admin):`ALL_ADMIN_ENTRIES`(E11-S025)在 E13-S013 之後
已經過時,且三個 E13 analytics 頁面從未一起連續造訪過

`admin-e2e.spec.ts` 的 `ALL_ADMIN_ENTRIES` 清單是 `E11-S025`(E11 收尾
story)凍結時寫死的 15 個入口——**但 `E13-S013`(latency dashboard)
後來才在 apps/admin 首頁新增了第 16 個入口「延遲儀表板」
(`/latency`)**。`ALL_ADMIN_ENTRIES` 是既有已核准測試內容,依
STORY_WORKFLOW 測試凍結規則只能新增不能修改既有陣列,所以「延遲儀表板
現在也真的可以在同一個連續 session 裡,跟其他既有入口一起被走到」這件
事從未被任何測試涵蓋過——獨立查證:`apps/admin/src/app/page.tsx` 目前
確實有 16 個 `href`(直接 grep 確認),`admin-e2e.spec.ts` 的陣列只有
15 個,兩者的差集正好是 `/latency`。

另外,E13 自己在 apps/admin 新增的三個 analytics 相關頁面——回饋佇列
(含 E13-S007 filter/E13-S014 OK/NG 比例統計)、使用量儀表板
(E11-S021,由 E13-S009/S010/S012 供資料模型)、延遲儀表板
(E13-S013)——從未在同一個連續 session 裡被一起連續造訪過,無法證明
三者各自的誠實空/零狀態文字互不混淆、彼此獨立。

## 新增測試(零 production code 變更)

1. `tests/e2e/specs/analytics-e2e.spec.ts`(新檔,apps/web 端)—— 1 個
   關鍵流程測試:在既有 seeded 對話裡送出兩則訊息(自動觸發 2 次
   `conversation_message_sent` + 2 次 `rag_answer_outcome`),對第一則
   回覆給 NG+原因+留言+標記為知識落差候選(五個動作全部發生在同一則
   回覆),對第二則回覆給 OK+留言(不同回覆、不同維度組合),直接讀
   sessionStorage 驗證:
   - 事件總數恰好 4(2 個 `conversation_message_sent` + 2 個
     `rag_answer_outcome`),全部歸屬同一個真實 `userId`。
   - 每個 `rag_answer_outcome` 都有數值型的 `citationCount`/
     `latencyMs`。
   - 全部 4 個事件的 `occurredAt` 依真實發生順序遞增排列(這是本測試
     真正新增覆蓋的不變量——見下方對抗性複驗)。
   - 知識落差候選記錄恰好 1 筆,只對應被標記的那則回覆,不外溢到第二則
     回覆。
   - 頁面導覽離開再回來(in-app 導覽,非 `page.reload()`——同其餘 E13
     spec 一貫慣例,見 `answer-ok-feedback.spec.ts` 的檔案 doc comment)
     後,UI 狀態(候選標記、留言文字)與底層 sessionStorage 事件序列
     兩者皆維持一致。
2. `tests/e2e/specs/admin-analytics-e2e.spec.ts`(新檔,apps/admin 端)
   —— 2 個測試:
   - 依序造訪目前 apps/admin 首頁**全部 16 個**入口(含 `/latency`,
     補上 `E11-S025` 凍結後才出現的落差),每個都到達自己正確的頁面。
   - 在同一個連續 session 裡依序造訪回饋佇列、使用量儀表板、延遲儀表板
     三個頁面,確認各自的誠實空/零狀態文字互不混淆(例如延遲儀表板的
     「尚無資料」不會被誤判為回饋佇列的「尚無回饋。」),最後繞回回饋
     佇列確認狀態未被中間造訪的另外兩個頁面污染。

## 對抗性複驗

對 `apps/web/src/lib/usage-events.ts` 的 `recordUsageEvent` 做突變:
`events.push(...)` 改成 `events.unshift(...)`(把新事件插入陣列最前面
而非最後面,模擬「事件順序寫反」這類真實可能發生的實作錯誤)。結果:

- 既有 `usage-events.test.ts` 一個 S010 單元測試(「keeps
  conversation_created and conversation_message_sent distinguishable」)
  精準命中——證明既有覆蓋對「兩個事件的順序」已有基本保護。
- **本 story 新增的 E2E 測試也精準命中**(`timestamps` 遞增排序斷言
  失敗,4 個事件的實際順序被完全反轉)——證明新測試對「一個真實多動作
  session 累積出的完整事件序列順序」提供了既有單元測試規模之外的
  額外、真實的端對端保護(單元測試只驗證 2 個事件,本測試驗證跨兩則
  訊息、跨 4 個事件的完整真實 session)。
- 突變已還原,`git diff` 對 `usage-events.ts` 位元組層級確認乾淨。

兩個 apps/admin 測試在撰寫階段第一次執行就直接命中真實功能(`/latency`
入口確實可達、三個頁面的空/零狀態文字確實互不混淆),證明這兩個測試
本身不是空殼——它們驗證的是真實存在、此前從未被任何既有測試走過的
路徑。

## 撰寫過程的兩處自我糾正(不計入 FIX 循環,未曾提交過失敗版本)

   (無「目前」二字)與「尚無資料」(無句號),修正後兩個測試皆一次
   通過。
