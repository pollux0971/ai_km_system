(第 1、2 輪的指令未包含 `uptime` 起訖列印,只有取鎖前的單點量測;第 3、4
輪的指令已改為在 `flock` 內、`playwright test` 前後各印一次 `uptime`,
數字直接取自那兩次真實輸出,非事後估算。)

**第 2 輪發現的問題**:`admin-usage.spec.ts`/`admin-latency.spec.ts`/
`admin-analytics-e2e.spec.ts` 的第一版修正(前一輪已回報總指揮並取得裁示
的「免責宣告→真實資料」窄幅修正)寫成硬編碼「今天/目前一定是 0」——這個
假設在 `admin-analytics-real.spec.ts`(AC5,同一個共用 `demo-super`
session)存在後不再成立,`fullyParallel: true` 對跨檔案順序沒有保證,
三支測試在同一輪全量執行中都因為真實值已經不是 0 而斷言失敗。修法:
比照 `admin-feedback.spec.ts` 已經用過的模式,改成「先用 `page.request.get`
問真實 API 現在的值,再斷言 UI 精確顯示同一個值(不管是不是 0)」。

**第 3 輪發現並修正的第二個、更隱蔽的問題**:改完上述修正後,
`admin-analytics-e2e.spec.ts` 的 E13-S017 測試**仍然紅了**,原因不同——
這個測試會依序導覽 3 個頁面,原本的寫法是在測試最前面用 `Promise.all`
一次問完 usage/latency/feedback 三個 API 的「當下真相」再逐頁比對。但
`admin-analytics-real.spec.ts` 在**另一個平行 worker**用**同一個共用
session**寫入真實資料的時間點完全不可控——第 3 輪實測真的抓到:測試一
開始問到的快照,到幾秒後真正導覽到 `/usage` 頁面比對時,已經被另一個
worker 寫入的新資料變成不同的值,斷言失敗(`element(s) not found`,期待
舊快照的數字)。修法:把三個 API 呼叫,從「測試最前面一次問完」改成
「每個頁面各自導覽到、渲染出標籤後,當場立刻問該頁對應的那一個 API」,
把競態窗口從「三次頁面導覽的總時間」縮小到接近零——與
`admin-usage.spec.ts`/`admin-latency.spec.ts` 兩支單頁測試原本就採用的
模式一致。第 4 輪重跑證實此修正有效。

三次修正皆是先看到真實紅燈才動手,不是憑空預防——這正是本 story 稍早
被總指揮糾正「換一次全新登入」提案(見下方對抗性複驗)之後,刻意採用
「每一步都親自重跑驗證,不假設修法一定有效」的做法。

`admin-e2e.spec.ts` 的 E11-S025 是**本 story 完全未觸碰的既有測試**,連續
三輪(第 2、3、4 輪)皆在同一步(`page.waitForURL` 30 秒逾時)失敗,訊號與
`ROADMAP_TEMP.md` 第 5-nona/5-deca 節明文記載的既有 flaky 家族
(`admin-e2e`/`admin-analytics-e2e`/`admin-knowledge`/`admin-roles` 的
30 秒 navigation timeout,根因為 Next dev 按需編譯 + 多 lane 併發 CPU 競爭)
完全吻合——執行當下 `uptime` 顯示 load average 持續 14–21(8 核機器),
`.e2e.owner` 顯示同時有其他 lane(W6/W7)在搶同一把鎖,與 ROADMAP 描述的
情境一致。本 story 自己新增/修正的全部 7 支測試在最後兩輪(第 3、4 輪)
中,除了第 3 輪那個已修正的競態問題外**全數皆綠**,第 4 輪起連續全綠,
不受這個既有 flaky 影響。

## Assumptions / 計畫外事項

1. **`system-health.ts`/`system-health-dashboard.tsx` 是結構重寫,非單純換
   資料源**:舊 stub 的 2 個 subsystem(`connectors`/`models`,中文顯示名,
   單一 `"unknown"` 狀態)與凍結契約的 4 個真實 subsystem
   (`api`/`database`/`migrations`/`asr`,4 態狀態)完全是不同的兩組概念——
   前者對應 apps/admin 自己已核准的 domain(連接器/模型管理頁面),後者
   對應 `apps/api`(E04-S047)實際做的健康檢查。中文顯示標籤
   (`SUBSYSTEM_LABEL`)是本 story 新增的展示層對照,契約本身沒有規定
   顯示文字。
2. **`computeOkNgRate` 的統計範圍從「整個佇列」變成「當頁」**:分頁後
   `feedback-list.tsx` 只拿得到當頁 `items`,凍結契約沒有聚合統計的
   endpoint(不得發明新 endpoint,CLAUDE.md 鐵律 1)。已在 `feedback.ts`
   `computeOkNgRate` 的檔頭註解、`feedback-list.tsx` 對應段落與此處三處
   一致記錄這個誠實的語意窄化,不是隱藏的行為變更。
3. **`filterFeedback` 保留但不再被呼叫**:依 spec 技術決策「純函式保留,
   分頁改由 server 篩選時移除 client 篩選(擇一,記錄)」,選擇後者——
   `verdict`/`hasReason` 現在是送到 server 的真實查詢參數,`filterFeedback`
   仍匯出、仍測試,供未來若有需要重新引用。
4. **admin 端使用量儀表板的「提問數」標籤維持「今日提問數」四字不變**,
   雖然 `questionsAsked` 語意上其實是全期間累計(E13-S019 EVIDENCE 的既有
   決策,非本 story 引入),不是真的按日期範圍。原本考慮改成更精確的
   「提問數」三字,但既有 E2E(`admin-usage.spec.ts`)逐字斷言「今日提問數」
   四個字,而這個文案本身不屬於「被本 story 正當推翻的 stub 標記」——
   維持四字不變,不擴大本 story 對既有 E2E 的修改範圍。
5. **`admin-analytics-real.spec.ts` 的 fire-and-forget usage-event 時序**:
   `recordUsageEvent`(`apps/web/src/lib/usage-events.ts`)是
   fire-and-forget,不等待完成才繼續 UI 流程。本測試在送出訊息後還會
   完成 4 次額外的回饋互動(verdict/reason/comment/citation),每次都是
   真實的網路往返,足夠讓稍早的 usage-event POST 完成;真實執行(見 Gate
   紀錄)證實這個時序假設成立,未觀察到不穩定。
6. **E2E 執行時的機器負載**:實際跑 64 個 admin E2E 測試時
   `uptime` 顯示 load average 約 8–14(8 核機器),`admin-e2e.spec.ts` 的
   1 個既有測試在其中一輪超時失敗——比對 `ROADMAP_TEMP.md` 第 5-nona/
   5-deca 節,這正是已知、與本 story 無關的既有 flaky 家族(冷編譯/CPU
   競爭),不影響本 story 自己新增或修改的 7 支測試(獨立重跑皆綠,見上方
   兩輪 Gate 紀錄的第一輪「僅 7 支測試」結果)。
