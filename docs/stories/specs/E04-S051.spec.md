# E04-S051 — 修復 `hostRequireSession` 快照綁定:真實 session 對 conversation routes 一律 401

## Metadata
- Epic: E04 RAG & Conversation Intelligence(使用者增補追蹤範圍)
- Owner: Team A
- MVP: **Required — 阻擋 E03-S038(全專案 E2E 匯流點)**
- Story size target: 0.5 developer-day
- Story 來源: W2 於 E04-S048 開發中發現;總指揮 2026-08-28 依使用者對
  E04-S049/E04-S050 的同類裁示授權新增

## 問題陳述(已由總指揮逐行覆核確認)

`services/conversation/src/plugin-types.ts:39` 的 `hostRequireSession(app)`
**回傳呼叫當下的 `app.requireSession` 值**(快照,非動態讀取)。三個 route 檔
(`conversations.ts:116`、`messages.ts:121`、`message-feedback.ts:96`)都在
**route 註冊階段**呼叫它一次,把函式參考存進區域變數。

而 `apps/api/src/server.ts` 的註冊順序是:
```
131: registerAuth(app, …)                  // decorate 一個 E04-S039 的 stub
154: await app.register(conversationPlugin) // ← 讀到的是上面那個 stub
156: await app.register(identityPlugin)     // 這裡才 app.requireSession = composeRequireSession(…)
```
`identityPlugin`(`services/identity/src/plugin.ts:290`)是**重新賦值**
`app.requireSession`,但 conversation 的區域變數已經綁死舊參考——JS 的變數
綁定不會追蹤物件屬性後續的重新賦值。

**後果**:在 production 等效設定(`enableTestAuthProvider: false`)下,真實登入
取得的合法 session cookie 打 `POST /v1/conversations` 等 route **一律回 401
UNAUTHENTICATED**,對話功能完全不可用。

**為什麼沒被任何測試抓到**:各 domain 的隔離測試 harness 都自己
`app.decorate("requireSession", <fake>)`,而 `apps/api` 與 `services/conversation`
**都沒有任何「真的登入 → 打受保護 route」的全鏈路測試**。這個測試缺口才是
本 story 真正要補的東西。

**已確認不受影響**:`services/model-gateway`(`transcriptions.ts`)雖用同一個
快照模式,但它在 `server.ts:160` 註冊,**晚於** `identityPlugin`(156),因此
抓到的是正確的 composed 版本。**不要因為機制相同就假設它壞了**——要實測確認。

## Scope In
1. 讓 `hostRequireSession` 改為**動態讀取**:回傳一個每次請求都即時讀
   `app.requireSession` 的 preHandler,而不是快照當下的值。
   `services/conversation` 與 `services/model-gateway` 各一份,兩份都改
   (後者目前雖正確,但同樣脆弱,一旦排序再變就會重蹈覆轍)。
2. `apps/api/src/server.ts`:把 `identityPlugin` 的註冊移到
   `conversationPlugin`/`modelGatewayPlugin` **之前**。這是縱深防禦——
   與 E04-S049 確立的「所有 decorate/賦值先於 route plugin 註冊」同一原則。
3. **補上缺失的全鏈路整合測試**(本 story 的核心交付):
   在 `apps/api` 以真實 `buildServer()`(`enableTestAuthProvider: false`)
   → 真實 `POST /v1/auth/login` 取得 cookie → 帶該 cookie 打受保護的
   conversation route → **必須 200/201**。

## Scope Out
- 不改任何 route 的商業邏輯、路徑或回應 schema。
- 不處理 CSRF(E04-S048)、不處理條件註冊(E04-S050)。
- 不改 `enableTestAuthProvider` 的預設值或 `x-test-user` 測試通道的設計
  (見下方「另行記錄」)。
- 不新增/修改任何 contract yaml。

## Functional Acceptance Criteria
1. Given `enableTestAuthProvider: false` 的真實 server,When 真實登入取得
   合法 cookie 後打 `POST /v1/conversations`,Then **201**(修復前為 401)。
2. AC1 的測試在修復前必須為**紅**;EVIDENCE 需附修復前後兩段輸出。
3. 對 `GET /v1/conversations`、`POST /v1/messages`、message-feedback 的
   四個 PUT 各補一條同樣的全鏈路正面驗證(帶合法 cookie → 非 401)。
4. `services/model-gateway` 的 `/v1/transcriptions` **實測**確認修復前後
   行為一致(EVIDENCE 記錄實測結果,不得只寫推論)。
5. 既有測試零修改且全綠:`apps/api` 91+、`services/conversation` 172、
   `services/identity` 153、`services/model-gateway` 65。

## Security / Authorization Acceptance
- 未登入 / 竄改 / 過期 cookie 仍必須被拒(既有 security-negative 測試零修改全綠)。
- **修復不得放寬任何授權**:AC1 的正面驗證必須搭配一條「同一 route、無 cookie
  → 401」的否定驗證,證明放行的是合法 session 而非全部放行。
