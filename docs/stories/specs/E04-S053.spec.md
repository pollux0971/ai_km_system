# E04-S053 — test sandbox 起始狀態必須對齊既有 264 個 E2E 的既定契約(有對話、無訊息)

## Metadata
- Epic: E04 RAG & Conversation Intelligence(使用者增補追蹤範圍)
- Owner: Team A(W3,`services/conversation` 與 `server.ts` 接線的 owner)
- MVP: **Required — 阻擋 E03-S038 核心 AC、E01-S021、E01-S022 的 AC4**
- Story size target: 0.25 developer-day
- Story 來源: 總指揮 2026-08-28 發現並立案

## 問題陳述(已由總指揮以程式碼比對確認)
E04-S052 把 **`conversationSandboxSeeders` 與 `messageSandboxSeeders` 兩者**都
接進 registry。但既有 264 個 E2E 是對著 `apps/web/src/test/fake-api.ts` 的
client 端 fake 寫的,而那個 fake 的起始狀態是:

- `seedSampleConversations()` 只填 `store`(**對話**),
- `messageStore = []`(**零訊息**)。

也就是說,**既有 spec 的既定契約是「有對話、但每個對話都是空的」**。伺服器
sandbox 現在額外 seed 了訊息,於是所有「開啟一個應該是空的對話」的 spec 全部
斷言不符。W1 在 E01-S022 的全量 E2E 實測:**220/264 通過,44 個失敗,其中 41
個是此模式**,例如:

- `send-message.spec.ts`:等 `尚無訊息,開始對話吧。` 逾時(對話已有訊息)。
- `citation-badge.spec.ts`:`toHaveCount(2)` 實得 4(seeder 2 則 + 測試自送 2 則)。

其餘 3 個是已具名的既有 flaky(`maintenance-e2e`、`admin-analytics-e2e`、
`admin-e2e`),與本問題無關。

## Scope In
- 讓 test sandbox 的起始狀態**與既有 spec 的既定契約一致**:登入後該 ownerKey
  有種子**對話**,但**沒有種子訊息**。
- 實作方式由開發者判斷並在 EVIDENCE 說明,建議最小改動:在
  `apps/api/src/server.ts` 的接線處只註冊 conversation seeder。
- 新增測試鎖住這個契約:sandbox 登入後 **conversations 數 > 0 且該 owner 的
  messages 數 == 0**。

## Scope Out
- **不得修改任何 seeder 的資料內容**(`seed/sample-*.ts` 維持原樣)。
  `messageSandboxSeeders` 保留不刪——它是 E04-S042 的正當產出,只是不屬於
  sandbox 的預設起始狀態。
- **不得修改任何既有 E2E spec**(那是 E03-S038 的核心 AC:零修改)。
- 不碰 `tests/e2e/**`、不改 contract。

## 依賴關係
- HARD 依賴 Story:E04-S052(approved)。
- **下游 Story:E03-S038**(核心 AC)、E01-S021、E01-S022(兩者的 AC4)、
  E13-S020(5 支 E2E 補跑)。

## Functional Acceptance Criteria
1. Given `AI_KM_TEST_SANDBOX=true`,When 真實登入,Then 該 ownerKey 的
   `GET /v1/conversations` 回傳 > 0 筆,且對其中任一筆
   `GET /v1/conversations/{id}/messages` 回傳 **0 筆**。
2. AC1 的測試在修正前必須為**紅**(目前會回傳非 0 筆訊息);EVIDENCE 需附
   修正前後兩段輸出。
3. `messageSandboxSeeders` 的既有單元測試零修改且全綠(它本身沒有壞,只是
   不再是 sandbox 的預設)。
4. 既有測試零修改且全綠:`apps/api`、`services/conversation`、
   `services/identity`、`services/model-gateway`。
