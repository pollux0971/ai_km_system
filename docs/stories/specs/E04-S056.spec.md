# E04-S056 — `/v1/health` 在 dev/test 永遠回 `degraded`,`api-sandbox` E2E 因此永久紅

## Metadata
- Epic: E04(使用者增補追蹤範圍)
- Owner: Team A(W5,`apps/api` health + ASR 設定的 domain owner)
- MVP: **Required — 每條 lane 的每一次全量 E2E 都固定帶著這個失敗**
- Story size target: 0.5 developer-day

## 問題陳述(總指揮已獨立重現)

```
$ curl -s http://localhost:4000/v1/health
{"status":"degraded","version":"0.1.0","uptimeMs":30381333}
```

四個環節各自正確,接起來永久紅:

```
apps/api/src/config.ts:165
  asrProvider: readEnum(env, "AI_KM_ASR_PROVIDER", ASR_PROVIDERS, "whisper-server")
                                                                  ^^^^^^^^^^^^^^ 預設

apps/api/src/health/checks.ts  checkAsr()
  fetch(`${asrServerUrl}/health`)  → 連不上 127.0.0.1:8178 → { status: "down" }

apps/api/src/health/checks.ts  overallStatus()
  任一 subsystem down → "degraded"          ← E04-S047 AC1 明文要求,邏輯正確

tests/e2e/specs/api-sandbox.spec.ts:147
  expect(body).toMatchObject({ status: "ok" })
```

**dev/test 從來沒有人跑 whisper sidecar**(`ss -ltn` 確認 8178 沒在聽),
所以 `checkAsr` 恆為 `down`,`/v1/health` 恆為 `degraded`。

### 這不是環境偶發,是跨 story 接縫斷裂

- `api-sandbox.spec.ts:143` 這條測試由 **E03-S035** 寫下,測試名是
  「apps/web's /api/v1/health rewrite reaches the real apps/api instance」
  ——它要驗的是**路由有沒有接到真的 apps/api**,寫的當下 health 還沒有
  ASR subsystem,斷言 `ok` 完全正確。
- **E04-S047**(`ca7ef86`)之後在底下加了 ASR subsystem。
- 兩邊各自都對,接縫斷了。**自 `ca7ef86` merge 起,每條 lane 的每一次
  全量 E2E 都固定紅這一條**,而每個 lane 都要重新診斷一次。

這正是本批 11 個修正 story 的同一種模式。

## Scope In
1. 讓 dev/test 環境下 `/v1/health` 能真實地回 `ok`(ASR 不是 dev 的硬相依)。
2. 讓 `api-sandbox.spec.ts:143` 斷言它真正要驗的東西(路由到達真 API)。
3. 確保「ASR 真的掛掉時 health 仍必須回 degraded」的能力**沒有被弱化**,
   且有測試證明。

## Scope Out
- 不改 `overallStatus` 的語意(E04-S047 AC1「任一 subsystem down → degraded」
  是正確的,不准為了讓測試變綠而放寬)。
- 不改 production 預設。`whisper-server` 作為 production 預設是正確的
  **fail-loud** 選擇,不得為了 dev 方便改成 `fake`(那是 fail-open,違反鐵律 2)。
- 不要求在 dev/test 真的跑起 whisper sidecar。

## 候選做法(實作者自行判斷並在 EVIDENCE 說明取捨)

**(a) dev/test 環境設 `AI_KM_ASR_PROVIDER=fake`**
`checkAsr` 對 `fake` 直接回 `ok`(`checks.ts:23-25`,既有行為,不用改碼)。
需要涵蓋**兩個**啟動路徑:playwright `webServer` 起的 API,以及 §5-penta
那個手動啟動的共用 `:4000` 實例(後者要同步更新 ROADMAP_TEMP 的啟動指令)。

**(b) 修正 `api-sandbox.spec.ts:143` 的斷言**
該測試的目的是路由,`status` 的**值**是它不該關心的耦合。

⚠️ **(b) 若單獨採用,等於放寬斷言** —— 依總指揮既有規則:
**移除斷言必須把覆蓋搬到正確的層級,不得淨減少覆蓋。** 要主張
「`ok` 已由別處驗證」就必須指名是哪個測試在驗,並確認它真的在驗。

總指揮的傾向是 **(a) + (b) 一起做**:(a) 讓 `ok` 在 dev 變成真的可達成,
(b) 讓路由測試不再耦合到選配子系統的營運狀態。只做 (a),下次任何子系統
在 dev 合理地 degraded 時同一條又會紅;只做 (b),dev 的 health 永遠顯示
degraded,那個雜訊本身就會掩蓋真問題。**但這是傾向,不是指令**——你有更好
的理由就照你的做,寫進 EVIDENCE。

## Functional Acceptance Criteria
- **AC1**:全新啟動的 apps/api(**不跑 whisper sidecar**)下,
  `pnpm exec playwright test api-sandbox` 通過。
- **AC2(反向驗證,強制)**:先在**未修正**的樹上跑 `api-sandbox`,
  貼出它紅的實際輸出;再貼修正後綠的輸出。**沒有「修正前是紅的」的證據,
  這個 story 不算完成**——否則無法區分「修好了」與「本來就會過」。
- **AC3(不得弱化 fail-loud)**:必須有測試證明 `asrProvider=whisper-server`
  且 sidecar 不可達時,health **仍然**回 `degraded`。既有的
  `checks.test.ts` / `admin-health.test.ts` 若已涵蓋,指名是哪一條即可,
  不必新寫。
- **AC4**:`git grep -n 'status: "ok"' tests/e2e/specs/api-sandbox.spec.ts`
  的結果,若被移除,EVIDENCE 必須指名接手驗證 `ok` 的測試。

## Security / Authorization Acceptance
- 不得放寬 `/v1/admin/health` 的授權(該路由目前對未授權回 401,已實測)。
- 不得為了讓 health 變綠而讓任何 subsystem 檢查回傳假的 `ok`——
  `fake` provider 是**明示宣告「這裡沒有 ASR」**,不是假裝 ASR 正常。

## Anti-hallucination Guard
`/v1/health` 的回應形狀(`status` / `version` / `uptimeMs`)已由總指揮實測,
如上。不要臆測其他欄位。`checkAsr` 對 `fake` 回 `ok` 是既有行為
(`checks.ts:23-25`),不是要新增的功能。

## Evidence Required Before Done

- 修正後對**沒有 sidecar 的新啟動 API** 直接 `curl /v1/health` 的輸出。
- AC3 指名的測試名稱與其通過輸出。
- 若採 (b):接手驗證 `ok` 的測試名稱。
- L0 全跑(typecheck / lint / unit)。
