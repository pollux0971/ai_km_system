# E04-S071 — 兩份契約寫得比實作寬,收緊為實作永遠成立的保證

## Metadata
- Epic: E04 — RAG & Conversation Intelligence（衍生）／涉及 analytics 契約
- Owner: Team B（domain）／Team A 開發
- Layer: Contract
- Priority: P1
- Story size target: 1 developer-day
- Story 來源: E04-S064 與 E04-S069 的 compat repoint 實測浮現
- 使用者授權: 2026-09-02「我批准了」——**改 `contracts/` 屬跨組事件(鐵律 #1),已取得**
- Parallel-safe: No — 動到兩份 yaml 與其產生型別

## 這條為什麼是重量級（分級理由）

**不是因為難,是因為改 `contracts/`。** 鐵律 #1 與 `STORY_WORKFLOW` 全域規則 3 都
把契約列為唯一真相來源、改動屬跨組事件。domain ownership 屬 Team B。

## 兩條缺陷（實測,非推論）

### (1) `generation.yaml` — `GenerationResponse.model` 選填,實作必填

`services/model-gateway` 的 `GenerateResult.model` 是 `string`(必填);
`generation.yaml` 的 `GenerationResponse.model` 是**選填**。
**一個符合 schema 但省略 `model` 的回應,會違反實作型別。**

**為什麼一直沒被發現**:`generation-compat.ts` 在 E04-S064 之前指向
`@ai-km/rag-skeleton` 的 `GenerationResult`,而**那個型別根本沒有 `model` 欄位**
——「契約回應可用於管線結果之處」這個方向恆真。**一個因為對著「沒有東西可以
不一致的東西」而永遠綠的 gate。**

### (2) `analytics.yaml` — `FeedbackItem.reason` 無約束,實作只給四個值

契約寫 `string`;實作(`services/conversation` 的 `FeedbackReason`)永遠只給
`INCORRECT` / `INCOMPLETE` / `OFF_TOPIC` / `OTHER` 四個字面值之一。

**為什麼一直沒被發現**:`analytics-compat.ts` 在 E04-S069 之前指向
`apps/admin/src/lib/feedback.ts`——前端鏡像,不是提供端。

**兩條的共同點**:在 compat 檢查改指接縫本體之前,**兩條都不可能被任何檢查看到**。

## 方向：收緊,不是放寬

兩條皆屬「**契約寬／實作嚴**」。修法是**把契約收緊到實作永遠成立的程度**,
不是把實作放寬去遷就一份寫寬了的契約——後者削弱一個真實存在的保證。

**向後相容性論證(限回應欄位)**:
- 讀 `string` 的消費端程式,接受 enum 值。
- 處理「欄位可能不存在」的消費端程式,接受一個永遠存在的欄位。
- **請求欄位則相反**——收緊請求欄位會讓既有呼叫端失敗。**本案兩者皆為回應欄位。**

## Scope In

1. `contracts/openapi/generation.yaml`:`GenerationResponse.model` 加入 `required`。
2. `contracts/openapi/analytics.yaml`:`FeedbackItem.reason` 由 `type: string` 改為
   `enum: [INCORRECT, INCOMPLETE, OFF_TOPIC, OTHER]`,**列舉值須與實作的
   `FeedbackReason` 逐字一致(先讀實作,不得憑本檔轉抄)**。
3. 重新產生 `contracts/openapi/__checks__/generated/` 與
   `packages/api-client/src/generated/` 兩處型別。
4. 更新 `generation-compat.ts` 中因收緊而過時的敘述:該檔目前有一段長註解說明
   「為何逐欄檢查」與 `modelAssignable` 只斷言單向。收緊後該情況不再成立,
   **註解與斷言須一併更新為雙向,不得留下描述舊狀態的註解。**

## Scope Out（不得在本 story 內自行決定）

- **不得放寬任何實作型別**去遷就契約。方向只有一個:收緊契約。
- **不得順手收緊其他欄位**,即使看起來同類。本 story 只涵蓋這兩條。
- **不得改動任何 route 的 runtime 行為**。這是型別與契約層的變更。
- `analytics.yaml` 其餘 `*Body` 錯誤信封 schema 的綁定,屬 E04-S065 已登記的
  `error-envelope-self-check-only` class,**不在本 story**。

## Functional Acceptance Criteria

- **AC1** `generation.yaml` 的 `GenerationResponse` 將 `model` 列入 `required`。
- **AC2** `analytics.yaml` 的 `FeedbackItem.reason` 為 enum,且其值與實作的
  `FeedbackReason` **逐字相同**（測試須斷言兩者相等,不得只斷言 enum 存在）。
- **AC3** 兩處 generated 型別重新產生後,全 repo `pnpm typecheck` 綠。
- **AC4** `generation-compat.ts` 的 `modelAssignable` 改為雙向斷言,
  且該檔不再有任何描述「契約 optional／實作 required」舊狀態的註解。
- **AC5** `pnpm contract-gate` exit 0,且 `analytics.yaml::FeedbackReason`
  (若收緊後產生具名 schema)不得使覆蓋率新增未在 allowlist 的 UNBOUND 項目。

## Data-Contract Acceptance

- **AC-D1** 兩份 yaml 的變更**僅限**上述兩個欄位。`git diff` 對兩檔的其餘部分為零。
- **AC-D2** 不新增、不刪除任何 schema、path、operation 或 securityScheme。

## 反向驗證（共同底線,不可省略）

**兩條各自獨立,兩段輸出都要記錄。斷言必須對著會變的值,不是存在性。**

1. 把 `generation.yaml` 的 `model` 改回選填 → **`generation-compat.ts` 必須紅,
   且失敗訊息必須指名 `model` 這個欄位**。只要它紅在別的地方,就不算通過。
2. 把 `analytics.yaml` 的 `reason` 改回 `type: string` → **`analytics-compat.ts`
   必須紅**,同樣要看失敗訊息的內容。

**依 `STORY_WORKFLOW`「工作分級」新增條款:證據是失敗訊息原文,不是紅的條數。**
兩段原文都必須進 EVIDENCE 檔與 commit body。

## Anti-hallucination Guard

- `FeedbackReason` 的四個值**必須從實作原始碼讀出**再寫進 yaml。
  本 spec 列出的四個值是**寫作當下的紀錄,不是權威**——若實作與本檔不符,
  以實作為準並在 EVIDENCE 記錄差異。
- 若發現 `GenerateResult.model` 實際上並非必填,**停止並回報**,不得自行調整方向。
