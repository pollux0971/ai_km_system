## 這條為什麼是輕量級(分級理由)

`.claude/rules/STORY_WORKFLOW.md`「工作分級」的兩條重量級觸發條件都不成立
於**這次量測到的結果**:

1. **不是靜默給出錯誤結果**——這句話描述的是「壞掉的時候沒有東西會報錯,而且
   輸出看起來合理但是錯的」。本次逐路由實際量測(見下表)結果是 **21/21 條
   被實際打過的路由,回應欄位與契約逐字相符,0 個多送、0 個少送**;另一條
   (`POST /v1/transcriptions`)雖未被本工具重新打過,但既有的 contract-check
   測試(`services/model-gateway/src/routes/transcriptions.test.ts:53`)已經
   用同一份契約 schema 驗證過同一個 2xx 回應,同樣是 0 落差。沒有壞掉的東西,
   就沒有「靜默給出錯誤結果」這件事在發生。
2. **不是新增或改變授權判斷**——這次的產出是唯讀比對工具 + 一次性量測,完全
   落在 `tools/contract-equivalence/`(Team A 工具,不需授權),未觸碰任何
   RBAC/ownership/授權邏輯。

**與 E04-S077 的差別,明說**:E04-S077 即使查完「11 條裡 0 條可利用」仍然
**維持重量級**,因為那條 story 判斷的是「缺陷所在的風險面」(路徑參數決定
存取哪一筆資料,屬於資料可見性),不是量測後的機率。這條 story 不一樣:
response 形狀落差的風險面本身(欄位外洩/欄位缺失)理論上可以撞上資料可見性
——但本次量測後,**外洩清單是空的**(見下表「多送欄位」欄全部是「無」),
沒有任何一個實際存在的欄位需要被逐一評估「它是不是敏感資料」。「工作分級」
一節明文要求「疑義時預設重量級」,但這裡沒有疑義:找不到任何一個需要判斷
是否敏感的多送欄位,就沒有東西可以疑義。若未來這個工具在某條新路由上真的
測出一個多送欄位,那筆發現本身(不是這整個評估 story)才需要重新評估是否
夠格轉重量級。

## 評估方法,以及為什麼選這個方法(story 要求明說,不埋)

**選擇:透過真實的 `apps/api` 伺服器(`buildServer()`,與 `check.live.test.ts`
/ `apps/api/src/full-chain-session.test.ts` 用的是同一個函式)實際打每條路由
——真的登入(`identityPlugin`,`enableTestAuthProvider: false`,真 cookie,
沒有 `x-test-user` 繞過)、真的建立資料、真的收下 Fastify 實際序列化出來的
JSON body——然後把這個「實際回應實例」拿去跟契約宣告的 2xx schema 做欄位級
比對(`response-instance-diff.ts`)。**

**為什麼不選另一個選項(從 handler 的 TypeScript 回傳型別推導)**:一個回傳
型別只說得出「作者相信這個函式回傳什麼」,不是「線路上實際傳輸的是什麼」。
它看不到 `JSON.stringify` 悄悄丟掉的 `undefined` 屬性、看不到一個 getter
拋出例外、看不到一個 class 實例的可列舉自身屬性跟它宣告的 interface 不一致
——而這個 repo 的 repository 層**大量使用**條件式展開只在值非 null 時才加入
欄位(例如 `messages.repository.ts` 的 `toMessage`),這正是型別推導看不到、
而回應形狀評估最該抓的那種落差。真的送一個請求、真的讀回應,比對的是同一件
事實的更直接來源。

**這個方法看不到什麼(明說,不是不知道)**:

1. **每條路由只驗證一個代表性 2xx 分支,不是每一種可能的 2xx 分支**。例如
   `Message` 的 `state`/`feedback`/`revisions`/`feedbackReason`/
   `feedbackComment`/`citationFeedback` 都是選填欄位,只有在某件事發生過後
   才會出現——本次的情境序列刻意依序觸發了其中幾個(見下表),但不是所有
   組合,也沒有測過任何錯誤/邊界分支的 2xx(這些路由的錯誤分支本來就不是
   2xx,不在本次比對範圍內)。
2. **只比對欄位是否存在,不比對型別/format/enum**。一個型別是 `string` 卻
   宣告 `integer` 的欄位,這個比對看不到——`apps/api/src/testing/
   contract.ts` 的 `expectResponseMatchesContract`(ajv)才是抓型別錯誤的
   工具;這次刻意做的是「哪些欄位名字對不上」這個更直接的問題。
3. **四條路由完全沒有打**,原因各自不同(見下表「未涵蓋路由」)。
4. **`POST /v1/transcriptions`** 技術上可以打(契約有 2xx JSON schema),但
   刻意沒有:要打到 200 需要建構合法的 16kHz/mono/PCM16 WAV buffer、把它
   編碼成 multipart/form-data、並在 `buildServer()` 之前設定
   `AI_KM_ASR_PROVIDER=fake`。`services/model-gateway/src/testing/
   wav-fixture.ts` + `multipart-fixture.ts` 已經為了同一個目的建好這組
   fixture,而 `services/model-gateway/src/routes/transcriptions.test.ts`
   的 "AC1: valid 16k mono PCM16 WAV + fake provider -> 200" 測試已經對
   真實回應呼叫 `expectResponseMatchesContract`(對著同一份 `Transcription`
   schema)且今天是綠的。在這個 Team A 工具裡重建一份等價的 WAV/multipart
   fixture,只為了再問一次一個既有、目前通過的測試已經回答過的問題,判斷
   不值得多出的 fixture 建構面——本次調查改為直接讀
   `services/model-gateway/src/routes/transcriptions.ts` 的 handler
   原始碼(`:196-203`),確認它回傳恰好契約要求的 7 個欄位、不多不少。

工具實作分兩個檔案(都在 `tools/contract-equivalence/src/`,新增檔案,
`package.json` 沒有動——仍然沒有 `test`/`build`/`lint` script,`pnpm turbo
run test` 不會碰它):

- `response-instance-diff.ts`——純函式,遞迴走訪 schema 的
  `properties`/`required`/`items`,回報「存在於實例但契約沒宣告」
  (`extra`)與「契約要求但實例沒有」(`missing`)的欄位路徑。10 個單元測試
  (`response-instance-diff.test.ts`)涵蓋:完全相符、多送、少送、
  `undefined` 視同缺席、選填欄位缺席不算 missing、巢狀物件遞迴、陣列每個
  元素聯集、`additionalProperties`-only 的 map 不遞迴、無 schema 可比對時
  不拋錯、型別不符(非物件)時不誤報。
- `check-response-shapes.live.test.ts`——建立真實伺服器、真實登入
  (`demo-super`,`super_administrator` 角色涵蓋本次每一條 admin 路由的角色
  檢查)、依序打 21 條路由、把每條的實際回應丟給
  `response-instance-diff.ts` 跟契約 2xx schema 比對,印出逐路由報告,並斷言
  零落差(斷言失敗時用純文字 `Error` 訊息(不是 `expect().toEqual()`)把每條
  違規路由的 key、狀態碼、`extra`/`missing` 陣列**逐字寫進訊息本體**——原因
  見下方「反向驗證」:`tools/mutate.mjs` 跑在 vitest 的 `--reporter=json`
  之下,`toEqual` 失敗時物件差異會被截斷成 `…(N)`,只有真的寫進訊息字串的
  文字保證留在 `failureMessages[0]` 裡)。

## 摘要

- **21 條路由被本次新工具實際打過:21/21 完全相符**——0 個多送欄位、0 個
  少送欄位。加上讀碼查證的 `POST /v1/transcriptions`,**22 條目前可觀察的
  JSON 2xx 路由,22 條都與契約逐字相符**。4 條路由沒有 JSON 2xx body 或根本
  不在任何契約裡,不適用這個問題。
- **多送欄位(潛在外洩):0 個**。E04-S077 的規則「多送欄位要逐一判斷是不是
  敏感資料,不能只數數量」在這裡沒有東西可以判斷——清單是空的。**如果日後
  這個工具在某條新路由上量到一個多送欄位,那才是需要逐一判斷的時候。**
- **少送欄位(會弄壞消費端):0 個**。
- **既有測試覆蓋率:22 條裡 21 條,今天如果真的出現落差,會被既有測試抓到**
  (逐條檔名列在上表最後一欄)。唯一的例外是 **`GET /v1/admin/health`**——
  它現有的測試只檢查個別欄位存在與否/型別,沒有任何一處對整個 body 做
  `additionalProperties:false` 等級的完整形狀比對,是**22 條裡唯一一條「今天
  就算多送一個欄位,也不會有任何東西報錯」的路由**。
- **如果要挑一件事先做,我會先做的不是「修一個資料形狀 bug」(因為量測結果
  是 0 個),而是把 `GET /v1/admin/health` 這個測試覆蓋率缺口補起來**——
  在 `apps/api/src/health/admin-health.test.ts` 加一個對整個 body 做完整
  形狀比對的斷言(例如 `Object.keys(body).sort()` 對照 `SystemHealth` 的
  `properties` 鍵集合,或比照其他路由接上 `expectResponseMatchesContract`
  等級的 ajv 檢查)。理由:①它是本次 22 條路由裡唯一一條「未來真的多送一個
  欄位,今天不會有任何東西發現」的路由,補測試比補 schema 更直接地關掉這個
  盲點;②這條路由的契約(`SystemHealth`)本身就是
  `additionalProperties:false`,補一個完整形狀斷言不需要猜測允許哪些欄位。
  **這仍然是一個測試檔的修改,但 `apps/api/` 是 CLAUDE.md 明列的 Team B
  資料夾——即使只改測試、不動 production 邏輯,本 story 的規則(「Do not
  modify any route, service, app, or yaml」)一樣不允許在這次評估裡動它。**
  這是本次「先做什麼」的建議,不是本次已經做的事——需要跟下方「需要的
  授權」表裡其他修法項目一起,由使用者給範圍授權或指派 Team B 才能落地。
