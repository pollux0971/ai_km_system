# E06-S026 — Embedding 模型／版本 metadata：版本不符時拒絕檢索，而非靜默給出錯誤排序

## Metadata
- Epic: E06 — Knowledge Ingestion & Indexing
- Owner: Team B（domain）／**Team A 開發**（使用者 2026-09-02 指派）
- Layer: Platform/Backend
- Priority: P0（使用者 2026-09-02 裁示：優先序提升到早於原編號位置）
- MVP: Required Thin Slice
- Story size target: 1–2 developer-days
- Story 來源: 原 epic 模板 story，2026-09-02 由使用者啟用並定義實質規格
- Parallel-safe: No — HARD 依賴 E04-S061、E06-S042

## 為什麼這條是重量級（分級理由，依 STORY_WORKFLOW「工作分級」必須寫）

失敗模式是「**靜默給出錯誤結果**」的原型，而且是本專案最難事後察覺的一種：

向量檢索的前提是「索引時的向量」與「查詢時的向量」來自**同一個函式**。換掉
embedding provider（或同一 provider 換版、換維度、換 tokeniser）之後，兩者不再
可比。結果是：

- **不會拋錯**——維度若相同，點積照算，回傳 top-k 照回。
- **不會有日誌**——沒有任何一層知道發生了什麼。
- **輸出看起來完全合理**——使用者拿到 4 段有引用的答案，只是那 4 段是錯的。
- **事後無法歸因**——沒有任何測試能分辨「排序品質差」與「模型被換過」。

`services/retrieval/src/embedding/provider.ts` 的註解已經寫明
「Determinism is contractual… Any change to the embedding function is a
**re-index event** and must be treated as a migration」，`contracts/openapi/
embedding.yaml` 也重複了同一句。**但 store 至今沒有任何欄位記錄它。** 規則寫在
註解裡而沒有落到 schema，等於沒有。

## 問題陳述（已查證，2026-09-02）

- `SQLITE_VEC_MIGRATION`（`services/retrieval/src/vector/sqlite-vec.store.ts`）
  的 `<table>_meta` 只有 `chunk_id / document_id / text / start_offset /
  end_offset`；`<table>_vec` 只有 `chunk_id / scope_key / embedding`。
  **沒有 model、沒有版本、沒有維度、沒有 tokeniser 標識。**
- `createSqliteVecVectorStore({ db, dimensions })` 的 `dimensions` 只在建表時
  用到，之後不再比對；換一個維度相同但語意不同的 provider 完全無感。
- `EmbeddingProvider` 介面有 `dimensions`，`EmbedResult` 有 `model`，但這兩個值
  在 `RagPipeline.ingest()` 寫入 store 時被丟棄。
- Wave 1 之後至少會有兩個 provider 同時存在（`E12-S032` 搬入的 deterministic
  PF1，以及 E04-S037 決定的真實 PF3 provider），**這條缺口會在那一刻被踩到**。

## Scope In

- `<table>_meta`（或等價位置）新增 embedding 身分欄位：至少 `embedding_model`、
  `embedding_dimensions`。是否加入更細的版本欄位由實作者判斷並寫進 EVIDENCE。
- 寫入路徑（索引管線）把 provider 回報的身分一併落庫，不得使用預設值填補。
- 查詢路徑在檢索**之前**比對查詢 provider 的身分與索引內的身分；不符即
  **拋出具名錯誤並拒絕檢索**。
- migration：既有資料若無身分欄位，視為未知，**一律拒絕檢索**（fail closed），
  不得猜測為「大概是現在這個 provider」。
- 一個明確的 re-index 路徑或指引（可以是文件＋錯誤訊息指路，不需自動化）。

## Scope Out

- 自動 re-index（屬 `E06-S029 Reindex workflow`）。
- 多 provider 並存或按知識庫選 provider（GA 能力，不在 MVP）。
- 真實 provider 的選型與接線（`E04-S037`、`E12` 後續）。
- 逾時／取消分層（`E04-S028`）。

## Functional Acceptance Criteria

每條標最低可證明層級（policy L0–L6，`policies/TESTING_POLICY.md`），涉及
provider 保真度者另標 PF（`services/.../evidence-tier.ts`）。

1. **(L1)** Given 索引時使用 provider A，When 寫入 chunk，Then 該 chunk 的
   `embedding_model` 與 `embedding_dimensions` 等於 provider A 回報的值。
2. **(L1)** Given 缺少 provider 身分的寫入請求，Then fail closed 拒絕寫入，
   不得以預設值補齊。
3. **(L3, PF1)** Given 索引時用 provider A、查詢時用 provider B，When 呼叫
   檢索，Then **拋出具名錯誤並拒絕檢索**；錯誤訊息同時指出索引身分與查詢身分。
   **不得回傳任何結果，即使維度相同。**
4. **(L3, PF1)** Given 索引與查詢同為 provider A，Then 檢索正常，且既有
   `sqlite-vec-store.integration.test.ts` 的 11 條斷言全部不變地通過。
5. **(L3)** Given 既有（migration 前）無身分欄位的資料，Then 檢索被拒絕，
   而非被當成相容。
6. **(L1)** 錯誤訊息必須說明這是 re-index event，並指向 re-index 途徑；
   不得只說「檢索失敗」。

## Security / Authorization Acceptance

- 本 story 不改變任何授權語意。`scope_key` 的 partition-key 前置過濾
  （ADR 未涵蓋，實作見 `sqlite-vec.store.ts`）必須逐字不變，
  `AC-V6`（不得退回 JOIN 後濾）必須持續通過。
- 錯誤訊息不得洩漏文件內容、chunk 原文或 scope key 清單。

## Anti-hallucination Guard

- 不得為了讓比對通過而放寬「相同」的定義（例如只比維度不比 model）。
- 不知道真實 provider 會回報什麼身分字串 → **不猜**；以 `EmbeddingProvider`
  介面已宣告的 `model`／`dimensions` 為準，其餘標 ASSUMPTION。
- 不得把「拒絕檢索」降級成警告或 fallback 到未版本化的結果。
